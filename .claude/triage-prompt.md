# 棚卸しのプロンプト

**未整理の issue**——棚卸しの結論（`kind:` と `goal:`）が揃っていないもの——を分類し、投入できる形へ
翻訳する係の本文。投入するのは盤面（[`board-move.mjs`](../scripts/agent/board-move.mjs) の `CYCLES`）で、
未整理が1件でもあれば一日二回立つ。渡し方は
[`dispatch-chore.sh`](../scripts/agent/dispatch-chore.sh)。

**未整理の全件をまとめて1セッションに渡す。** 1件ずつ配ると、この係にしかできない仕事が全部落ちる
——**別々に立った issue が同じ原因であること**（#1042・#1043・#1044 はどれもカードの移動
アニメーションの話だった）、**張るべき順序**、**重複**。どれも複数を並べて見た者にしか見えない。
1件だけを見る仕事なら、そもそもワーカーにさせればよい。

題は下の `題:` の行が持つ（`board-design.md` 2.9）。

題: 棚卸 未整理の issue

---

````
[デーモン] 未整理の issue を棚卸しします。

**未整理**とは、open で**棚卸しの結論が揃っていない** issue です（`.claude/board-design.md` 2.17.1）。

- **`kind:` のラベルを1つも持たない** —— まだ分類されていない。
- **`kind:task` なのに `goal:` のラベルを持たない** —— 分類は済んでいるが、向かう先が名乗られて
  いない。**盤面はこれを整備として並べ、`NOTE` で告げます**（2.18.1）。拾う者はあなたしか居ません。

これらを分類し、投入できる形へ翻訳するのが、このセッションの仕事です。

## GitHub を触る道具

**道具は `.claude/github-access.md`「issue を読む・書く」に従ってください。**

引くのは**開いている issue**で、**打ち切らずに全部**引いてください——**引く数を渡さないと30件で
切れます。** この係は未整理の**全件を並べて見る**のが仕事なので（同じ原因の重複も、張るべき順序も、
並べて見た者にしか見えません）、黙って落ちたぶんは分類されないまま次の周へ回ります。

そこから未整理を選ぶのはあなたです。`gh` で `number,title,labels` を引いたなら、次で絞れます
（上の2つの形を両方拾います）。

```
... | jq -r '.[] | [.labels[].name] as $l
  | select(($l | map(startswith("kind:")) | any | not)
           or (($l | index("kind:task")) and ($l | map(startswith("goal:")) | any | not)))
  | "\(.number)\t\(.title)"'
```

**依存（`blockedBy`）だけは、どの道具でも自分では触りません。** 頼み方は下の「順序を張る」。

## やること

1. 全件をまず読む。**先に全部読んでから、1件目に手を付けてください。**
   同じ原因の issue が混ざっていることがあります（症状は別でも、壊れているのは1箇所）。
2. コードを読んで、直す場所の見当を付ける。**再現手順が書いてあるならテストにして実際に失敗させて
   から**（`CLAUDE.md`「再現手順を最初にテストへ落とす」）。
3. issue を、下の出口のどれかへ振り分ける。
4. 全部終えたら報告して終わり。**PRは作りません。**

## 出口

**(a) そのまま** — 1セッションで片付く大きさで、直す場所も決まっている。`kind:task` を付ける。
**本文が既に `task` の型（`.claude/parallel-work.md` 3節）になっているなら、書き換えません**
——未整理の多くは、別の作業中のセッションが自分の仕事の外で見つけて立てたもので、`## 担当` も `## 案` も
既に揃っています。**足りない節だけを足す。**

**(b) 翻訳** — 人が自分の言葉で書いていて、担当も完了条件も無い。**同じ番号のまま本文を書き換えて**
`task` の型にし、`kind:task` を付ける。

**(c) 分解** — 2つ以上のセッションに分かれる、または仕様を決める段と実装する段に分かれる。
**子の issue を新しく立て、元の issue はそのまま残す**（元がゲートになる。
`.claude/parallel-work.md`「束ねる関門は、ゲートの issue を1件立てる」）。子にも元にも `kind:` と
`goal:` を付けること——**付け忘れた issue は、次の周でまた棚卸しへ回ってきます。** **新しく立てた子には
`origin:agent` も付けます**（下の「付けるラベル」）。

**(d) 束ねる** — 複数の issue が同じ原因。**1件を代表にして本文へまとめ、残りは代表を指す1行だけに
書き換える**（閉じない。閉じるのはマージのときです）。代表は `kind:task`、残りは (e)。

**(e) 返却** — **もう成り立たない**（既に直っている・前提が変わった・仕様が変わって不要になった）、
または**あなたには決められない判断が要る**。`kind:task` を付けたうえで、issue へこの形のコメントを
1つ置いてください。

```
[返却] <なぜ返すか。1行で>
```

1行目がこの形なら [`board-labels.yml`](../.github/workflows/board-labels.yml) が `判断待ち` を
付け、**ワーカーへは渡らずユーザーの手番になります。** 分類そのものは動かしません——「もうやる必要
が無い」は分類ではなく人の手番の印で、ユーザーが閉じるか、`判断待ち` を外して列へ戻すかを決めます。

**投入する先が無い常設の盤**（#656 のような、ずっと開いたまま人が使う issue）は、どの出口でもなく
**常設の盤の値**（下）を付けて終わりです。

**答えを待っている issue**（`判断待ち` が付いていて、まだ答えが無いもの）は、**本文を書き換えず**
`kind:task` を付けて終わりです。**本文のチェックボックスがユーザーの答えの置き場**なので、task の型へ
翻訳すると押すはずのものが消えます。分類さえ付いていれば、ユーザーがラベルを外したその周から
配られ、受け取ったセッションが答え込みで読みます。

## 付けるラベル

**`kind:` は必ず1つ付ける。** 付け忘れた issue は未整理のまま残り、毎日ここへ戻ってきます。

1セッションで片付く作業単位なら **`kind:task`**。**そのまま配られます**——配らせたくないものは、
ラベルではなく (e) の返却で止めてください。

投入する先が無い常設の盤なら、**その本文を機械がどう扱うか**で値が決まります
（`.claude/board-design.md` 2.17.5）。**見るのは本文で、題ではありません。**

| 本文のチェックが | 値 |
|---|---|
| ユーザーの**答え**で、拾った者が項目ごと消す | `kind:ask` |
| ユーザーが切り替える**設定**で、誰も消さない | `kind:switch` |
| **無い**、または機械が読まない飾り | `kind:board` |

**`kind:ask` を付けた issue の本文のチェックは、機械が「ユーザーの答え」として拾い、盤面の
`## 確定待ち` へ出します**（[`checked-items.sh`](../scripts/agent/checked-items.sh)）。**下ろす者の
居ないチェックへ付けないでください**——下ろされない項目が居座り、本物の答えがその中に埋もれます。

**自分で立てた issue には `origin:agent` を付ける**（(c) の分解で作った子）。人が立てた issue には
何も付けません——**印が無いことが「人が立てた」を表します**（`.claude/parallel-work.md`「自分で
立てた issue には `origin:agent` を付ける」）。**数えるためだけの軸なので、配る順には効きません。**

**`goal:` も必ず1つ付ける**（`.claude/board-design.md` 2.17.1・2.18.1）。**`kind:task` を付けた
issue には、例外なく**付けてください。

| 値 | 何へ向かうか |
|---|---|
| `goal:game` | 完成の定義を1つ埋める（世界の中身・遊びの仕組み・画面） |
| `goal:upkeep` | 作る仕組みと記述を整える（盤面の道具・参照のずれ・置き場の直し） |

**盤面はこの印で、完成へ近づける仕事を整備より先に配り、掘り起こす係を立てるかを決めます。**
**既定はありません**——`goal:game` を持つものだけが完成へ近づける仕事で、**付け忘れた issue は整備
として並びます**（盤面が `NOTE` で告げるので、次の周のあなたが拾うことになります）。

- **元の issue が既に `goal:` を名乗っていれば、その値を尊重してください。** 立てた本人が向かう先を
  知っています。**明らかに食い違うときだけ**直し、報告に1行書いてください。
- **(c) の分解では、元の向かう先をそのまま子へ書きます。** **分解は向かう先を変えません。**
- **迷ったら `goal:upkeep`。** 整備を前へ出す誤りのほうが高くつきます。

**立てた側の印（`origin:agent`）から向かう先を推し量らないでください。** あれが答えられるのは
**誰が書き込んだか**だけです。**(c) で立てた子には必ず `origin:agent` が付く**ので、そこから既定を
引くと、**元が人の issue でも子は「機械が立てたもの」に見え、人の仕事が分解された瞬間に整備へ
落ちます。**

加えて、当てはまるものだけ:

- **`env:bridge`** — **クラウドではできない仕事**のとき。手元の画面やローカルにしか無いものを使う、
  など（`.claude/board-design.md` 2.16）。**`.claude/**` を触ることも、既存 issue の本文やラベルを
  書き換えることも理由になりません**——クラウドのセッションもどちらもできます。
- **`急ぎ`** — **それが片付くまで他の仕事が止まる**とき（盤面が回らない・`main` のCIが赤い、など）。
  効くのは投入の順だけです（`.claude/board-design.md` 2.18）。**迷ったら付けないこと**——
  全部に付けば、無いのと同じ「古いものから」に戻ります。
- **`area:art`** — 画像を生成する。GPUを専有するので同時に1本しか走れません。
- **`area:daemon`** — 走らせながらは書き換えられないデーモンの仕組み
  （`scripts/agent/**`・`.github/workflows/board-labels.yml`）。

分類している issue に付けるのは `kind:` から下だけです。**出どころの印は動かしません**——立てた側が
起票のときに名乗るもので、後から見分けられる者は居ません。`origin:agent` を渡すのは (c) で新しく
立てる子だけで、**起票のときに一緒に**渡します。

打ち方は上の「GitHub を触る道具」。**`:` を含む綴りで身構えるのは
`git show origin/main:.claude/x.md` のような引数のほう**で、Windows ではあれが
`origin\main;.claude\x.md` に化けるので `MSYS2_ARG_CONV_EXCL='*'` を前に置きます。`/tmp/...` のような
絶対パスも書き換わりますが、行き先は同じなので害はありません。

## 順序を張る

**issue の本文に `## 順序` 節があったら、`blockedBy` を張ってください。** そこは立てたセッションが
「先に片付いていないと着手できない issue」を申告した場所です（`.claude/parallel-work.md`「順序は
issue の本文で申告し、棚卸しが決める」）。**決めるのはあなたです**——セッションの側は申告までで、
**張るかどうかの判断はここに集めてあります。**

**張るのは、待つ側の issue へ次の形のコメントを1つ置くことです。** 1行目がこの形なら
[`board-labels.yml`](../.github/workflows/board-labels.yml) が `blockedBy` を張ります
（`.claude/board-design.md` 2.17.3）。**自分で依存の API を叩かないでください**——この経路なら、
どこで走っていても同じ手で張れて、**なぜその順序かも issue に残ります。**

```
[順序] #<先に要るほう> の後（<なぜ後でないと着手できないか>）
```

**1件につき1つのコメント**にしてください。読むのは1行目だけで、そこに挙がった番号が先に要るほうです。

- **推定しないこと。** 申告の無い issue に順序を作らない。本文を読んで思いついた前後関係も、
  同じ原因だと見抜いた組も、**申告が無いなら張りません。**
- **例外は、(c) で自分が分けた元と子の間だけ。** そこは申告が無いのではなく、**申告する側が
  あなた**です。元はゲートとして残るので、**元の issue へ、子1件につき1つ `[順序]` のコメントを
  置きます**（子が全部済むまで元は配られない）。
- **張るかどうかはあなたが判断します。** 申告の理由が**「同じファイルを触る」なら張らない**
  ——それは依存ではありません（同文書「同じファイルを触ることは、依存ではない」）。衝突は
  コンフリクトとして出るので、盤面が直させます。
- **迷ったら張らない。** 張り忘れ（早すぎる着手）はリベース1回で済みますが、余分な鎖は黙って
  遅くなり、誤りに誰も気づきません。
- 循環は GitHub が 422 で拒み、張りに行ったワークフローが赤くなります。

## 守ること

- **ユーザーが書いた原文を消さないこと。** 書き換えた本文の末尾に `## 元の報告` という節を作り、
  **原文をそのまま**残す。翻訳を誤っても、読んだ人が原文と突き合わせて気づけるようにするためです。
  **(a) で本文を書き換えないなら、この節も要りません**（消していないので）。
- **コードは1行も変えないこと。** 成果物は issue の本文とラベルと `blockedBy` だけです。テストを
  書いて再現を確かめるのは構いませんが、それも捨ててください（残すのは翻訳先の issue に書いた
  再現手順）。
- 仕様が決まっていない箇所は、**あなたが決めずに「決める」ことを (c) の子 issue にする。**
  **確定の宣言**（節の `【確定】` と、文書単位の `**本書は全体が確定です。**`）に反する判断が要る
  ときだけ、**`判断待ち` を付けた issue を1本立てて訊く**（`CLAUDE.md`「確認は、1問1 issue で
  出す」）。

## 書き換えた本文の形

**型は [`.claude/parallel-work.md`](./parallel-work.md) 3節が持ちます**——節名も、必ず置く節も、
書かないものも、そちらが唯一の定義です。**ここへ書き写さないので、開いて読んでから書いてください。**
節名は `dispatch-prompt.md`（`## 担当` の列挙）と `review-prompt.md`（完了の条件）が名前で引く
ので、揺れると両方が探す先を失います。

- **見た目が変わる issue には、`## 担当` に絵や画面のファイルが入っているかを確かめる。**

## 報告に書くこと

1件1行で、**番号・出口・付けたラベル・一言**。最後に、張った順序（`#A は #B の後`）と、申告が
あったのに張らなかったものとその理由、再現しなかったもの、判断を保留したものを挙げてください。
````
