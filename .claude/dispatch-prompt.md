# タスクを投入するときの指示のひな形

`create_session` へ渡す本文。**組み立てるのは
[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh)** で、下の ``` の中を読んで `<番号>` を埋め、
最後の行を渡された補足へ差し替える。**投入する側が書くのは補足だけ**——写す作業が残っている限り必ず
何かが落ちる（2026-08-27 に「PRを見張らない」の一文が3本すべてから抜け、3セッションが
`subscribe_pr_activity` と `send_later` を呼んで承認待ちで止まった）。

つまり**このファイルを直せば、次の投入から全部に効く**。禁止は指示文でしか効かないので、箇条書きは
削らない（`create_session` に道具の拒否リストは無く、渡せる `extra_allowed_tools` は広げる方向だけ）。

## 走る場所で文面を変えない

**受け取る側は、自分がクラウドとブリッジのどちらで走っているかを知らない。** 触ってよい範囲を
場所で切ると、当たらないほうのセッションにも渡って害になる——`.claude/**` を触るなと書いた行が、
まさにそこを直すために立てたブリッジのセッションへ届き、**着手した時点で仕事をせずに返した**
（PR #1567 のレビュー指摘）。

だから切る軸は場所ではなく**担当に挙がっているか**の1つだけにしてある。どちらで走っていても同じ
文面でよい。承認で止まるかは走ってみれば分かることなので、止まった側が `[ブリッジ]` で配り直しを
頼む（[`board-design.md`](board-design.md) 2.16.2）。

**``` の行と、`<このタスク固有の補足…>` の行は目印として使っている。** 消すと投入が止まる。

---

```
[デーモン] https://github.com/gooyyu1/UnmappedIsland/issues/<番号>

この issue 1件がこのセッションの仕事です。

- 進め方は `CLAUDE.md`、並列作業の取り決めは `.claude/parallel-work.md`。
- **issue 本文の `## 決まっていること` と `## 案` は、重みが違います。** 前者はユーザーが
  決めたことで、1件ずつ出どころが添えてあります——**覆せません。** 後者は実現案でしかないので、
  **違うと思ったら従わなくてよい。ただし、その場合は実装せずに下の「返す」で返してください**（どちらで
  行くかはユーザーが決めます）。節が分かれていない issue は、**全部が「案」**だと思って
  読んでください。
- **必ず置く2節（`## 担当`・`## 完了の条件`）に手順が混ざっていたら、それも「案」です。** どの
  ファイルをどう変えるか・どの係がその仕事を引き取るか・どの順で打つか——**出どころが添えられて
  いないものは、書いた側が置いただけ**かもしれません。**`## 担当` は触ってよい範囲**で、そこを
  どう変えるかの指定ではありません（`.claude/parallel-work.md`「実現案を書くなら、ユーザーが
  決めたことと分けて書く」）。
- **ユーザーへ問いかけて答えを待たないでください。** ユーザーはこのセッションを見ません。訊いた
  時点で、あなたは答えの来ない相手を待ち続けることになります。決まっていない箇所は仮決めして
  進み、`## 仮決め` に書けば届きます。
- **仮決めすらできないときは、issue へコメントを1つ置いて終わってください**（「返す」）。1行目を
  `[返却] <なぜ返すか。1行で>` にすると、それが合図になって issue に `判断待ち` が付き、ユーザーが
  答えるまで誰にも配られません。2行目から下に詳細を——何を調べて、どこで詰まったか。**ユーザーが
  リポジトリを開かずに答えられるだけの文脈を添えること**（スマホから読みます）。
  **PRは作らないでください**（作れないから返すので）。**黙って止まらないこと**——返さないまま手が
  止まると、盤面が代わりに返し、あなたが何を調べたかは誰にも残りません。
- **issue の「担当」に挙がっていないファイルは、原則として触らない。** 気づいた別の問題は、直さずに
  新しい issue を立てる。「同じファイルを触る」は依存ではありません。
- **このPRの中では終わらないことは、issue か `[スメル] ` へ出してください。** PR本文へ申し送りを
  書かないこと——**本文を読むのはマージまでで、その後に手を動かす者は誰も読み返しません。**
  （**マージの前にレビューが読む `## 仮決め`・`## ユーザーの指示` は別です**——決めきれなかった
  問いは、今までどおり `## 仮決め` へ。読んだレビュアーが人へ回します。）
  - **やる必要があること → issue を立てる。** 範囲外だと判断したものも、仕組みそのものへの直し
    （ひな形・`scripts/agent/**`・`.claude/parallel-work.md`・`CLAUDE.md` のうち担当に挙がって
    いないもの）も同じです。**`kind:` のラベルは付けないでください**——付けるのは棚卸しで、
    付いていない issue はそちらへ回ります。自分で付けると、投入の列に載せるかを自分で決めることに
    なります。**`origin:agent` は、起票のときに一緒に渡してください**——人が立てたものと見分ける
    ための印で、付けるのは立てた本人しか居ません（`.claude/parallel-work.md`「自分で立てた issue
    には `origin:agent` を付ける」）。**クラウドで立ったセッションは、後からラベルだけを付け直せ
    ません**（`.claude/board-design.md` 2.16）。**番号をPR本文へ書き写さないでください**（issue が
    在れば盤面が配るので、写しは何も起こしません）。
  - **順序が要るなら、立てた issue の本文へ `## 順序` 節を置いて申告する。** 1行1件で、
    **先に要るほうの番号と、なぜ後でないと着手できないかを添えてください**（`- #1234 の後（理由）`）。
    理由を読んで `blockedBy` を張るのは棚卸しなので、**理由の無い申告は張られません。**
    `blockedBy` は自分で張らないでください——**張るかどうかを判断するのは棚卸し**で、自分で張ると
    その判断を通らないからです（`.claude/parallel-work.md`「順序は issue の本文で申告し、棚卸しが
    張る」）。
  - **issue を立てるほどではない気づき → `[スメル] ` で始まる行としてPRへコメントする。**
    レビュアーが書くのと同じ形（`.claude/board-design.md` 4.4）で、後から分析係が拾います。
    **語形を崩さないでください**——拾う側がこの行頭で読みます。
- **例外は、あなたの変更がその記述・コードを事実でなくしたとき。** 「まだ無いので待つ」が入ったことで
  嘘になった、隣の文が噛み合わなくなった——こうした直しは担当外でも**同じPRで**入れてください。
  判定は「**自分の差分がこの行を嘘にしたか**」だけで、「ついでに気づいた」「直したほうがよさそう」は
  入りません（それは今までどおり issue）。入れたぶんは **PR本文の `## 担当外へ入った直し` 節に、
  1件ずつ「何が嘘になったから直したか」を書く**（無ければ節ごと省く）。
- **生成物は、担当に挙がっていなくても作り直してよい**——`stats/balance.yaml` は
  `npm run stats:balance`、`stats/climate.yaml` は `npm run stats:climate`。鮮度検査があるので、
  作り直さないとCIが落ちます。**手で書き換えないこと。**
- **PR本文に置く節（`Closes` / `## 仮決め` / `## 自己点検` / `## 見た目`）は `CLAUDE.md`「PR本文に
  置く節」にあります。** そのまま従ってください。ここに足すのは、タスクのセッションにだけ掛かる
  次の3点です。
  - **節名は綴りちょうどで書く。** 節を読む側はどこも名前を `$` で留めるので、
    `## 担当外へ入った直し（3周目）` のように語を足すと**その節だけ誰にも届きません**。周回番号や
    補足は節の中へ書いてください。
  - **確定の宣言**（節の `【確定】` と、文書単位の `**本書は全体が確定です。**`）に反する変更が要る
    ときだけ、仮決めせずに issue #656 へ積む。
  - 画面の画像で変更前後を並べるなら、URLに `?seed=12345` を付けて撮ること——付けないと実行ごとに
    島も開始時刻も変わるので、2枚の差が変更由来だと言えません。**`## 見た目` が節ごと無いPRは、
    レビューへ回る手前で盤面が差し戻します。**
- **作業中にユーザー本人から直接の指示が届いたら、PR本文の `## ユーザーの指示` 節に、届いた内容と
  それをどう反映したかを書いてください**（無ければ節ごと省く）。**レビューはその指示を見ていません。**
  書かないと、issue の担当や完了条件から外れた理由が読めず、範囲外へ伸びたPRとして差し戻されます。
  デーモンからの `send_message`（`[デーモン]` で始まるもの）はここに書きません。
- **書き換えが拒否されて進めなくなったら、issue へコメントを1つ置いて終わってください。** 1行目を
  `[ブリッジ] <なぜブリッジが要るか。1行で>` にすると、それが合図になって issue に `env:bridge` が
  付き、**ユーザーのPCで走るセッションへ配り直されます**——そちらは承認を挟まずに動きます。
  気づけるのは走ってみたあなただけなので、**黙って回避路を探さないこと。** 2行目から下に、どこまで
  進んだかを書いてください（次に受け取る側が読みます）。
- **価値観の記録（`.claude/decisions/`）は書かないでください。** `CLAUDE.md`「価値観の記録」は
  書けと言っていますが、**タスクのセッションはこの1点に従わないでください。** 出どころにできるのは
  ユーザー本人の発言だけで、issue の本文や届いた指令から汲み取ったものを書くと、あなたの考えが
  ユーザーの名前で全セッションへ配られます。**ユーザー本人から直接メッセージが届いたときだけ**、
  上の `## ユーザーの指示` 節へ**原文をそのまま**引用してください。記録するかどうかはユーザーが
  決めます。**既に在る履歴を `archive/` へ移すことと、そこへ見送りの印を足すことは、この禁止に
  入りません**——出どころを作る作業ではないので、担当に挙がっていれば行ってください。
- **調べるためにサブエージェントを立てるのは、いつでも構いません。** 同じ誤りの兄弟を grep で洗う、
  仕様書の該当節を探す、退行がいつ入ったかを二分する——**読むだけの仕事は、読んだ量が子の文脈に
  留まって、あなたには結論だけが返ります。** 一方**書く仕事は自分でやってください**（ファイルの
  編集・PR・コメント・issue）。サブエージェントはあなたと同じチェックアウトに居るので、並列に
  書かせると整形のフックや git の状態を互いに壊します（`.claude/parallel-work.md` 1節）。
- **push する前に、サブエージェントを1本立てて、これから出す差分をレビューさせてください。**
  手順は `CLAUDE.md`「**PRを出す前に、サブエージェントへ一次レビューさせる**」——**開いて読んでから
  通してください。** 渡すものも、結果を `## 自己点検` へどう書くかも、そちらが唯一の定義です。
  ここに書き写さないのは、**この手順が誰のPRにも掛かる**（相談役やユーザー自身のPRも同じ）ためで、
  ひな形の側に置くと作業セッションのPRしか通らなくなるからです。
- そのうえで、push の直前に `main` を取り込み直し、`npm run lint` / `npm run typecheck` / `npm test` /
  `npm run format:check` の4つを通す。**`## 仮決め` の前提が変わっていないかの確認も含む**——手順は
  `CLAUDE.md`「順序は、自己レビューの直しを載せてから」の直後（誰のPRにも掛かるため、ここには
  書き写さない）。
- 完了条件を満たしたらPRを作る（本文は上のとおり）。
- **PRを作ったら報告して終わりです。CIの結果もレビューも見張らないでください。**
  **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。見張るのはデーモンで、直しが要れば
  `send_message` で起こしに行きます。

<このタスク固有の補足。直列にした相手、issue 本文が古くなっている箇所など。**担当の重なりは
書かない**——受け取った側はどのみち担当の範囲を書くので、知らせても作業が変わらない。無ければ省く>
```
