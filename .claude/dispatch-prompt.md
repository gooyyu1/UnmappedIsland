# タスクを投入するときの指示のひな形

`create_session` へ渡す本文。**組み立てるのは
[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh)** で、下の ``` の中を読んで `<番号>` を埋め、
最後の行を渡された補足へ差し替える。**投入する側が書くのは補足だけ**——写す作業が残っている限り必ず
何かが落ちる（2026-08-27 に「PRを見張らない」の一文が3本すべてから抜け、3セッションが
`subscribe_pr_activity` と `send_later` を呼んで承認待ちで止まった）。

つまり**このファイルを直せば、次の投入から全部に効く**。禁止は指示文でしか効かないので、箇条書きは
削らない（`create_session` に道具の拒否リストは無く、渡せる `extra_allowed_tools` は広げる方向だけ）。

**``` の行と、最後の `<このタスク固有の補足…>` の行は目印として使っている。** 消すと投入が止まる。

---

```
[デーモン] https://github.com/gooyyu1/UnmappedIsland/issues/<番号>

この issue 1件がこのセッションの仕事です。

- 進め方は `CLAUDE.md`、並列作業の取り決めは `.claude/parallel-work.md`。
- **issue 本文の `## 決まっていること` と `## 案` は、重みが違います。** 前者はユーザーが
  決めたことで、1件ずつ出どころが添えてあります——**覆せません。** 後者は実現案でしかないので、
  **違うと思ったら従わなくてよい。ただし、その場合は実装せずに報告して止まってください**（どちらで
  行くかはユーザーが決めます）。節が分かれていない issue は、**全部が「案」**だと思って
  読んでください。**古い issue では、案の側が `## 司令塔の案` という名前で残っています。**
- **issue の「担当」に挙がっていないファイルは、原則として触らない。** 気づいた別の問題は、直さずに
  新しい issue を立てる。「同じファイルを触る」は依存ではありません。
- **ユーザーに手を動かしてほしいことは、PR本文の `## ユーザーへ` 節に書いてください**（無ければ節ごと
  省く。**`## 仮決め` と違い、「なし」とは書きません**）。**このPRの中では終わらず、ユーザーが何かを
  しないと終わらないもの**だけが入ります。
  - **立てた issue の番号**（範囲外だと判断して立てたもの）。**`task` ラベルは付けないでください**
    ——付いた issue はデーモンがそのまま投入するので、投入の列に載せるかはユーザーが決めます。
  - **順序が要るなら「#A は #B の後」。** `blockedBy` を張ろうとしないでください——このセッションから
    は GitHub の REST に届かないので張れません。ユーザーが張ります。
  - **仕組みそのものへの直しの依頼。** ひな形（`.claude/dispatch-prompt.md`・`review-prompt.md`）・
    盤面の道具（`scripts/agent/**`）・運用の文書（`.claude/parallel-work.md`・`CLAUDE.md`）に
    ついて、直したほうがよいと気づいたこと。**自分では直さないでください**（担当外で、ユーザーと
    他のセッションが同時に触ります）。
  この節に中身があると、マージのときPRに `ユーザーへ` ラベルが付きます。**読むのはユーザーで、
  すぐには読まれません。** ここに書かなかったものは、誰にも届きません。
- **例外は、あなたの変更がその記述・コードを事実でなくしたとき。** 「まだ無いので待つ」が入ったことで
  嘘になった、隣の文が噛み合わなくなった——こうした直しは担当外でも**同じPRで**入れてください。
  判定は「**自分の差分がこの行を嘘にしたか**」だけで、「ついでに気づいた」「直したほうがよさそう」は
  入りません（それは今までどおり issue）。入れたぶんは **PR本文の `## 担当外へ入った直し` 節に、
  1件ずつ「何が嘘になったから直したか」を書く**（無ければ節ごと省く）。
- **生成物は、担当に挙がっていなくても作り直してよい**——`stats/balance.yaml` は
  `npm run stats:balance`、`stats/climate.yaml` は `npm run stats:climate`。鮮度検査があるので、
  作り直さないとCIが落ちます。**手で書き換えないこと。**
- **PR本文に置く節（`Closes` / `## 仮決め` / `## 自己点検` / `## 見た目`）は `CLAUDE.md`「PR本文に
  置く節」にあります。** そのまま従ってください。ここに足すのは、タスクのセッションにだけ掛かる
  次の3点です。
  - **節名は綴りちょうどで書く。** 後片付けのスクリプトは節の名前を `$` で留めて抜き出すので、
    `## 担当外へ入った直し（3周目）` のように語を足すと**その節だけ誰にも届きません**。周回番号や
    補足は節の中へ書いてください。
  - **確定の宣言**（節の `【確定】` と、文書単位の `**本書は全体が確定です。**`）に反する変更が要る
    ときだけ、仮決めせずに issue #656 へ積む。
  - 画面の画像で変更前後を並べるなら、URLに `?seed=12345` を付けて撮ること——付けないと実行ごとに
    島も開始時刻も変わるので、2枚の差が変更由来だと言えません。**`## 見た目` が節ごと無いPRは
    レビューが差し戻します。**
- **作業中にユーザー本人から直接の指示が届いたら、PR本文の `## ユーザーの指示` 節に、届いた内容と
  それをどう反映したかを書いてください**（無ければ節ごと省く）。**レビューはその指示を見ていません。**
  書かないと、issue の担当や完了条件から外れた理由が読めず、範囲外へ伸びたPRとして差し戻されます。
  デーモンからの `send_message`（`[デーモン]` で始まるもの）はここに書きません。
- **`.claude/**` の下は、1ファイルも書き換えないでください**（`policies.md` も含めて例外なし）。
  あそこへの書き込みは**必ずユーザーの承認を求められ、そこでセッションが止まります**。担当に
  挙がっていても書かず、`## ユーザーへ` へ回してください——ユーザーが `main` へ直接入れます。
  - **価値観の記録もここに掛かります。** `CLAUDE.md`「価値観の記録」は `.claude/decisions/` へ
    書けと言っていますが、**タスクのセッションはこの1点に従わないでください。** 出どころに
    できるのはユーザー本人の発言だけで、issue の本文や届いた指令から汲み取ったものを書くと、
    あなたの考えがユーザーの名前で全セッションへ配られます。
  - **ユーザー本人から直接メッセージが届いたときだけ**、上の `## ユーザーの指示` 節へ**原文を
    そのまま**引用してください。記録するかどうかはユーザーが決めます。
- **調べるためにサブエージェントを立てるのは、いつでも構いません。** 同じ誤りの兄弟を grep で洗う、
  仕様書の該当節を探す、退行がいつ入ったかを二分する——**読むだけの仕事は、読んだ量が子の文脈に
  留まって、あなたには結論だけが返ります。** 一方**書く仕事は自分でやってください**（ファイルの
  編集・PR・コメント・issue）。サブエージェントはあなたと同じチェックアウトに居るので、並列に
  書かせると整形のフックや git の状態を互いに壊します（`.claude/parallel-work.md` 1節）。
- **push する前に、サブエージェントを1本立てて、これから出す差分をレビューさせてください。**
  手順は `CLAUDE.md`「**PRを出す前に、サブエージェントへ一次レビューさせる**」——**開いて読んでから
  通してください。** 渡すものも、結果を `## 自己点検` へどう書くかも、そちらが唯一の定義です。
  ここに書き写さないのは、**この手順が誰のPRにも掛かる**（相談役やユーザー自身のPRも同じ）ためで、
  ひな形の側に置くと作業セッションのPRしか通らなくなるからです。
- そのうえで、push の直前に `main` を取り込み直し、`npm run lint` / `npm run typecheck` / `npm test` /
  `npm run format:check` の4つを通す。**`## 仮決め` の前提が変わっていないかの確認も含む**——手順は
  `CLAUDE.md`「順序は、自己レビューの直しを載せてから」の直後（誰のPRにも掛かるため、ここには
  書き写さない）。
- 完了条件を満たしたらPRを作る（本文は上のとおり）。
- **PRを作ったら報告して終わりです。CIの結果もレビューも見張らないでください。**
  **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。見張るのはデーモンで、直しが要れば
  `send_message` で起こしに行きます。

<このタスク固有の補足。**担当が他のセッションと重なっているなら、どのファイルのどこを向こうが
掴んでいるかを名指しする**（重なりは止める理由にならないので、境目を書いて並列に流す）。
直列にした相手、issue 本文が古くなっている箇所なども。無ければ省く>
```
