# タスクを投入するときの指示のひな形

司令塔が `create_session` へ渡す本文。**組み立てるのは
[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh)** で、下の ``` の中を読んで `<番号>` を埋め、
最後の行を渡された補足へ差し替える。**司令塔が書くのは補足だけ**——写す作業が残っている限り必ず
何かが落ちる（2026-08-27 に「PRを見張らない」の一文が3本すべてから抜け、3セッションが
`subscribe_pr_activity` と `send_later` を呼んで承認待ちで止まった）。

つまり**このファイルを直せば、次の投入から全部に効く**。禁止は指示文でしか効かないので、箇条書きは
削らない（`create_session` に道具の拒否リストは無く、渡せる `extra_allowed_tools` は広げる方向だけ）。

**``` の行と、最後の `<このタスク固有の補足…>` の行は目印として使っている。** 消すと投入が止まる。

---

```
[司令塔] https://github.com/gooyyu1/UnmappedIsland/issues/<番号>

この issue 1件がこのセッションの仕事です。

- 進め方は `CLAUDE.md`、並列作業の取り決めは `.claude/parallel-work.md`。
- **issue 本文の `## 決まっていること` と `## 司令塔の案` は、重みが違います。** 前者はユーザーが
  決めたことで、1件ずつ出どころが添えてあります——**覆せません。** 後者は司令塔が書いた実現案で、
  **違うと思ったら従わなくてよい。ただし、その場合は実装せずに報告して止まってください**（どちらで
  行くかは司令塔が決めます）。節が分かれていない issue は、**全部が「司令塔の案」**だと思って
  読んでください。
- **issue の「担当」に挙がっていないファイルは、原則として触らない。** 気づいた別の問題は、直さずに
  新しい issue を立てる。「同じファイルを触る」は依存ではありません。
- **司令塔に手を動かしてほしいことは、PR本文の `## 司令塔へ` 節に書いてください**（無ければ節ごと
  省く）。**このPRの中では終わらず、司令塔が何かをしないと終わらないもの**だけが入ります。
  - **立てた issue の番号**（範囲外だと判断して立てたもの）。司令塔が投入します。
  - **順序が要るなら「#A は #B の後」。** `blockedBy` を張ろうとしないでください——このセッションから
    は GitHub の REST に届かないので張れません。司令塔が張ります。
  - **仕組みそのものへの直しの依頼。** ひな形（`.claude/dispatch-prompt.md`・`review-prompt.md`）・
    司令塔の道具（`scripts/agent/**`）・運用の文書（`.claude/parallel-work.md`・`CLAUDE.md`）に
    ついて、直したほうがよいと気づいたこと。**自分では直さないでください**（担当外で、司令塔と
    他のセッションが同時に触ります）。
  この節は**マージの後に司令塔が読んで下ろします**。ここに書かなかったものは、誰にも届きません。
- **例外は、あなたの変更がその記述・コードを事実でなくしたとき。** 「まだ無いので待つ」が入ったことで
  嘘になった、隣の文が噛み合わなくなった——こうした直しは担当外でも**同じPRで**入れてください。
  判定は「**自分の差分がこの行を嘘にしたか**」だけで、「ついでに気づいた」「直したほうがよさそう」は
  入りません（それは今までどおり issue）。入れたぶんは **PR本文の `## 担当外へ入った直し` 節に、
  1件ずつ「何が嘘になったから直したか」を書く**（無ければ節ごと省く）。
- **生成物は、担当に挙がっていなくても作り直してよい**——`stats/balance.yaml` は
  `npm run stats:balance`、`stats/climate.yaml` は `npm run stats:climate`。鮮度検査があるので、
  作り直さないとCIが落ちます。**手で書き換えないこと。**
- 決まっていない箇所は仮決めして進み、**PR本文の先頭の `## 仮決め` 節に申告する**（無いなら「なし」と
  書く。書かせないと、無かったのか書き忘れたのかが区別できない）。`【確定】` の節に反する変更が要る
  ときだけ、進めずに issue #656 へ積む。
- **見た目が変わる変更なら、PR本文に `## 見た目` 節を作って画面の画像を貼ってください。**
  撮り方は `.claude/skills/run/SKILL.md`、貼り方は
  `bash scripts/agent/push-screenshot.sh <画像> <名前>`（返ってきたURLを `![<名前>](URL)` の形で
  本文へ）。`src/game/**` か `src/assets/**` を触ったのに貼らないなら、同じ節に「不要」と理由を
  1行書いてください。**節ごと無いPRは司令塔が差し戻します。** 変更前後を並べるなら、URLに
  `?seed=12345` を付けて撮ること——付けないと実行ごとに島も開始時刻も変わるので、2枚の差が変更
  由来だと言えません。
- push の直前に `main` を取り込み直し、`npm run lint` / `npm run typecheck` / `npm test` /
  `npm run format:check` の4つを通す。
- **PRを作る前に、最終diffを自分で点検して、結果を PR本文の `## 自己点検` 節に書いてください。**
  項目は `CLAUDE.md`「修正作業の進め方」の2〜4節そのままで、3行あれば足ります。
  - **原因の深さ**（2節）: 症状の出ている行を止めたのではなく、不変条件が破れた場所を直したか。
  - **同じ誤りの兄弟**（3節）: 同じパターンが他に無いかリポジトリ全体を探したか。**使った検索語を
    そのまま書く**——「探した」だけでは、探し方が甘かったのか本当に無かったのかが区別できません。
    見つけたが範囲外だと判断したものは、**見つけたことと直さない理由**を書く。黙って落とさない。
  - **不要になった旧コード**（4節）: この修正で意味を失った分岐・回避策・特別扱いを消したか。
- **作業中にユーザー本人から直接の指示が届いたら、PR本文の `## ユーザーの指示` 節に、届いた内容と
  それをどう反映したかを書いてください**（無ければ節ごと省く）。**司令塔はその指示を見ていません。**
  書かないと、issue の担当や完了条件から外れた理由が読めず、範囲外へ伸びたPRとして差し戻されます。
  司令塔からの `send_message` はここに書きません——あれは司令塔自身が送ったものです。
- 完了条件を満たしたらPRを作り、**本文の先頭に `Closes #<番号>`** と書く。**issue は自分で閉じない。**
- **PRを作ったら報告して終わりです。CIの結果もレビューも見張らないでください。**
  **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。待つのは司令塔の仕事で、直しが要れば
  `send_message` で起こしに行きます。

<このタスク固有の補足。**担当が他のセッションと重なっているなら、どのファイルのどこを向こうが
掴んでいるかを名指しする**（重なりは止める理由にならないので、境目を書いて並列に流す）。
直列にした相手、issue 本文が古くなっている箇所なども。無ければ省く>
```
