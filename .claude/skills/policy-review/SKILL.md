# 価値観の棚卸し

## 何を分けてあるか

| | 置き場 | いつ書くか | セッションへ注入 |
| --- | --- | --- | --- |
| 判断の履歴 | `agent-ops/decisions/*.md` | ユーザーの発言を受けたその場 | しない |
| 一般則 | 下の「行き先」の文書 | この棚卸しのときだけ | 文書による（下の表） |
| 処理済みの履歴 | `agent-ops/decisions/archive/*.md` | 棚卸しが移す | しない |

**1件だけを見て「これは一般則か」は判断できない。** 別の題材で同じ選び方をした判断が出て初めて、
それが通底している価値観なのか、その題材だけの判断なのかが分かる。記録の場を分けてあるのは、
その判断を棚卸しまで遅らせるため。

## 行き先

**新しく文書を作らない。** 方針を持つ文書は既に在るので、畳んだ一般則はそのどれかへ入る。

| 行き先 | 持つもの | セッションへ注入 |
| --- | --- | --- |
| [`policies.md`](../../../agent-ops/policies.md) | これまでの判断全体に通底している価値観・好み | 全文 |
| [`DesignPrinciples.md`](../../../docs/concept/DesignPrinciples.md) | ゲーム内容を決めるときに効く判断軸 | 見出しだけ |
| [`parallel-work.md`](../../../agent-ops/parallel-work.md) | 盤面を回す側だけが要る運用の取り決め | しない |
| [`board-design.md`](../../../agent-ops/board-design.md) | 盤面・デーモンそのものの作りを決める判断 | しない |
| [`DocumentStyle.md`](../../../docs/DocumentStyle.md) | `docs/` の文書の構造（見出し・節番号・確定の表し方）と、何を書き残し何を書かないか | しない |
| [`CodingConventions.md`](../../../docs/CodingConventions.md) | TypeScript の規約のうち、機械で強制できないもの | しない |
| [`CodeStructure.md`](../../../docs/CodeStructure.md) | `src/` の置き場と、どこが何を知ってよいか | しない |
| [`DesignNotes.md`](../../../docs/engine/DesignNotes.md) | 繰り返さないために残す事例 | しない |

**`policies.md` へ入れるのは、行き先が他に無いものだけ。** ここだけが全文を注入するので、
入れた分だけ全セッションの文脈が減る。**題材の決まっている判断は、その題材の文書が持つ。**

**`DesignNotes.md` だけは一般則の置き場ではない。** 3行の書式に収まらず、具体の出典を外すと意味を
失うものは、一般則ではなく事例——畳まずにそちらへ書く。

## 一般則と、個別の判断の見分け方

`policies.md` が持つのは、**これまでの意思決定全体に通底している価値観・好み**であって、
**個別の判断でもなければベストプラクティスでもない**（出どころ: ユーザーの指示・2026-09-07）。
束ごとに次を順に当て、1つでも落ちたら畳まない。

1. **異なる題材にまたがっているか。** 束の出どころが**同じ題材への判断だけ**なら——同じ仕組み・
   同じ文書・同じラベル体系の中で下した判断が並んでいるだけなら——それは**その題材についての
   個別の判断**で、通底ではない。それはその題材の文書が仕様として持つものなので、一般則にはしない。
   **別々の題材で同じ選び方をしていることだけが、通底していることの証拠。**
2. **一般論から再現できないか。** 一般論に照らして当然の判断は、その場で同じ答えに辿り着くので
   置く価値が無い。「技術的にまともだ」と思えるだけのものは畳まない。残るのは、
   **このリポジトリ特有・ユーザー特有・甲乙つけがたいもの**だけ。
3. **既に在るものから導けないか。** `CLAUDE.md` と `policies.md` に同じ趣旨が既に在るなら足さない。
   在るものが古い・足りないなら、追記ではなく**書き換え**の候補として出す。

**件数は通す理由にならない。** 同じ題材への判断は10件並んでも通底しないし、別々の題材の2件で
通底する。**数えるのは件数ではなく、束がまたがっている題材の数。**

## 履歴の書式

`agent-ops/decisions/<YYYY-MM-DD>-<英小文字のslug>.md` に1件1ファイル。並列に走るセッションが
同時に書いても衝突しない。

```markdown
---
date: 2026-09-05
context: policies.md の書き方の見直し（会話のみ）
---

## ユーザーの発言

> 今は何かしらの判断があるたびにpolicies.mdに直接書き込まれていくのが問題の根本だと思います。
> ユーザーの判断の履歴と、そこから抽出したポリシーを分離すべきです。

## エージェントの解釈

- 判断を書き留める場と、そこから抽出した一般則の場を分ける。
```

**節を分けるのは、どちらが誰のものかを読み手に渡すため**（出どころ: ユーザーの指示・2026-09-07）。
混ぜて書くと、**エージェントの読みがユーザーの判断そのものとして読まれる**——棚卸しは原文と読みの
食い違いを見る仕事なので、両者が1つの声になった記録では見分けが付かない。

- **`## ユーザーの発言` には原文だけを置く。** 要約しない——抽出が正しかったかを後から確かめられる
  ことが、分けてある一番の利点。発言と発言の間をつなぐ説明はここへ入れてよい（引用の文脈なので）。
- **`## エージェントの解釈` は、1つの発言に入っていた判断のぶんだけ書く**（1行に縮めない）。
  **縮めるより、そのまま残すほうがよい**（出どころ: ユーザーの指示・2026-09-06）——畳むのは後の
  工程で、そこには元の記録が要る。
- **解釈が発言より広いのは構わない。** どこまでが読みかは節が示している。ただし**他の判断と束ねる
  のは棚卸しの仕事**なので、ここで書くのは**この発言から読み取れる範囲**まで。
- `context` には、どの作業の途中だったかを書く。issue・PRの番号があれば添える。
- 迷ったら書く。注入されないので、溜めてもセッションのコストにならない。
- `archive/` の履歴には `declined:` が付いていることがある（手順4）。**書くのは棚卸しだけ**で、
  記録するときには付けない。
- **記録はレビューの対象ではない**（出どころ: ユーザーの指示・2026-09-07。
  [`review-criteria.md`](../../../agent-ops/review-criteria.md)「見ないもの」）。質を見るのはこの棚卸し。

## 棚卸しの手順

1. `agent-ops/decisions/` の未処理を全部読み、**選び方が同じもの**で束ねる。**束ねる前に、各件の
   `## エージェントの解釈` が `## ユーザーの発言` から読み取れる範囲かを確かめる**——読みの広さを
   見るのはここだけで、**レビューは記録を読まない**（[`review-criteria.md`](../../../agent-ops/review-criteria.md)
   「見ないもの」）。読み取れないものは、原文の側へ寄せて書き直してから束ねる。
2. 束ごとに上の「一般則と、個別の判断の見分け方」を当て、**通ったものだけ**を候補にする。書式は
   下の「一般則の書式」、行き先は上の「行き先」から1つ。落ちた束と孤立した1件は、抽出せず履歴に
   残す。**同じ見分け方を、既に在る項目にも頭から当てる**——通らないものが在れば、それは今も個別の
   判断のまま置かれているので、外す・移す候補になる。
3. **諾否をユーザーに出させる。** 選択肢を出すツール（`AskUserQuestion`）は使わない。**どちらの
   経路でも、リポジトリを開かずに答えられるだけの文脈を添える**——ここだけが人間の仕事。
   - **ユーザーと会話しているなら、普通の文章で訊く。** 答えを受けたら手順4へ。
   - **周期の係として立ったなら、候補をチェックボックスで並べた issue を1本起票して終わる**
     （[`policy-cycle-prompt.md`](../../../agent-ops/prompts/policy-cycle-prompt.md)）。訊いた側が答えを待って止まる
     ので、同じセッションでは反映しない。手順4以降は、チェックの付いた issue を受け取った別の
     セッションが行う。
4. 承認されたぶんを反映し、元になった履歴を `archive/` へ `git mv` する。**一般則にならずとも、
   既にどこかの文書へ反映されている履歴も同じく `archive/` へ**——残すと、まだ手が要るものと
   区別が付かない。**候補に出したが承認されなかったぶんも `archive/` へ移す。** ただし front
   matter の `context` の**後ろ**へ `declined: <見送られた場所>`（issue の番号か日付）を足して
   から——**見送ったことが残っていないと、次の棚卸しが同じ候補をもう一度出す。** `date` と
   `context` の**間へ挿すと `tests/docs/policies.test.ts` が落ちる**（隣り合っていることを見ている）。
   候補に出さなかった履歴——束にならなかった1件も、見分け方で落ちた束も——が
   `agent-ops/decisions/` に残る。
5. 節を畳んだ・改名したなら、**その節名を引いている参照を直す。** どこが切れたかは
   `npm test`（`tests/docs/docReferences.test.ts`）が挙げる。
6. `policies.md` の総量が上限（220行）を超えているなら、畳むか捨てるかしてから終える。
   **上限は、乗せる候補の数を決める理由にはならない。** 空きが足りないのは、見分け方を通らない
   項目が居座っている合図で、乗せる側を削る合図ではない。

**書式・総量・履歴の必須項目は `tests/docs/policies.test.ts` が見ている。** 質の判定——出どころが
ユーザー本人か、**解釈が原文から読み取れるか**、上の見分け方を通るか——は機械では決まらないので、
そこがこの棚卸しの仕事。

## 一般則の書式

1項目は3行以内で、フィールドをこの順に置く。

```markdown
## 名前の付け方

- **場面**: 短くて一語で済む名前と、長いが何をするかが読める名前。
  **選ぶ方**: 後者。「つい短くしたくなる」ときほどこちら。
  **重視**: 名前は読み手への説明そのもので、字数は書く側のコストにすぎない。
```

- **事例を本文へ書かない。** 具体のファイル名・節番号・PRやissueの番号は、履歴と
  [`DesignNotes.md`](../../../docs/engine/DesignNotes.md) が持つ。3行に収まらないなら、束ね方が
  粗いか、まだ一般則になっていない。
- **重視は「何をどう見ているか」を書く。** 「短いから」「速いから」のような表面的な利点は、
  字面の違う場面で逆を向く。
- **場面は、題材の名前を出さずに書けるはず。** 出さないと書けないなら、それは通底していない証拠
  （上の「一般則と、個別の判断の見分け方」）。
