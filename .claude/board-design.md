# 盤面の設計

司令塔の仕組みを、**機械的な処理だけで回る形**へ作り直す。ここは**決まったことを積む場所**——
決まった項目から順に節を足し、まだ決まっていないものは末尾の「未決」に並べる。実装が追いついた
節は、[`parallel-work.md`](parallel-work.md)・各プロンプト・`scripts/agent/**` の側を書き換えて
合わせる。**この文書と実装が食い違ったら、この文書が正。**

向かう先は3つ（出どころ: ユーザーの指示・2026-09-04）。

- **中心は機械的な処理だけに絞る。** 判断が要るものは非同期の別エージェントへ切り離す。今の司令塔が
  やっていることが、自動スクリプトだけで完結する状態を目指す。
- **作業領域の衝突は、投入のときに考えるのではなく、予め棚卸し係が付けたラベルで避ける。**
  領域は一次元ではなく複数次元。
- **ワーカー・レビュアーからの申し送りを中心が読んで総合判断することをやめる。** 急がない懸念
  （アーキテクチャスメル・長期の検討課題）は残す場所を決めておき、後段のエージェントがまとめて拾う。

## 1. 状態の持ち方【確定】

### 1.1 事実と占有を分ける

分ける基準は「**持ち主が死んだとき、その状態は嘘になるか**」。

| | 事実 | 占有 |
|---|---|---|
| 例 | PRの存在・コミットのSHAと時刻・レビューの結論・issue の open/closed・`Closes` の紐付け | 「今このissueを誰かが作業している」「今このPRを誰かがレビューしている」 |
| 持ち主が死んだら | 真のまま | **嘘になる** |
| 置き場 | GitHub。消えてよい理由が無いので、消えない場所でよい | **セッションそのもの**。消えれば占有も消える |

**偽になるべき状態を、自分では消えない場所に書かない。**

`レビュー中`・`作業中` のラベルが破綻するのは、異常終了を防げないからではなく、**占有を事実の
置き場に書いたから**。ラベルは持ち主と無関係に生き続けるので、落ちたセッションのぶんが残り、
掃除役を足すことになる——それは嘘を後から拭く仕事を増やしているだけ。**異常終了は防げないので、
防ぐのではなく「落ちたら勝手に消える表し方」を選ぶ。**

### 1.2 セッションへの問いは2つある

`task-<issue番号>` / `review-<PR番号>` のタグを持つセッションを `list_sessions` から引く。
**トップレベルの `status` は常に `null` なので使えない**——見るのは `session_status` と
`status_bucket` の2つ。

**この2つを1つの「占有」へ畳んではいけない。** 訊きたいことが別だから。

| 問い | 判定 | 使う場所 |
|---|---|---|
| **その仕事に、生きたセッションが居るか**（投入済みか） | `session_status != SESSION_STATUS_ARCHIVED` | 盤面（[`board-move.mjs`](../scripts/agent/board-move.mjs)）と、新しいタスクを立てる直前（`occupancy.sh --live`） |
| **今、手が動いているか**（二重に走らせない） | `status_bucket` が `..._WORKING` か `..._BLOCKED` | レビュー・直しの再開を立てる直前（`occupancy.sh --busy`）。1.4 の不変条件 |
| そのとき消費していたか | `status_bucket` が `..._WORKING` | 使用量の割り当て（2.5） |

**片方だけで書くと、必ずどちらかが壊れる。**

- 生死だけで排他すると、**判定を書き終えたレビューが占有し続け、再レビューが永久に止まる。**
  レビューは差分ごとに使い捨てで、次の差分のレビューは別の仕事（`dispatch-review.sh`「再レビューでも、
  前のセッションを起こさずに新しく立てる」）。
- 手が動いているかだけで「投入済み」を読むと、**PRを出して手が空いたセッションの上へ2本目を立てる。**
  `..._COMPLETED` は「終わった」ではなく「**今は手が空いている**」——2026-09-05 の実測で、畳まれて
  いない `IDLE` のセッションがこの値だった（1.5）。仕事はまだそのセッションの手元にあり、次の指示が
  来れば同じ文脈で続きを書く。

**`..._BLOCKED` は動いている側に数える。** 承認待ちで止まっているだけで、許可が下りれば書き始める。
**`..._FAILED` は数えない**——落ちたセッションの上へは立て直してよい（1.5 の `01Wcy9XLj85X`）。

**畳まれたセッションでも、`unarchive_session` → `send_message` で文脈ごと再開できる**（1.5 で実測）。
それでも畳まれた側を「居ない」と読むのは、**畳むのが「この仕事は終わった」と判断した側の明示の操作**
だから（マージのとき・次のレビューを立てるとき）。

**`updated_at` はどの問いにも使わない。** 実測（2026-09-05）で、**走っているセッションでも
`updated_at` は動かない**——`SESSION_STATUS_RUNNING` のセッションの `updated_at` が、実際には走り
続けている1日前の時刻で止まっていた。**「古いから止まっている」は書けない。**

一覧を出す [`live-sessions.sh`](../scripts/agent/live-sessions.sh) は**畳まれていないもの全部を、
`status_bucket` を添えて**返す。**どの問いで絞るかは呼び手が決める**——条件をあちらへ持つと、
どの呼び手にも合わない定義が1つできる。

止まったまま固まったセッションは、畳むまで「居る」と読まれ続ける。**それでよい**——時間で自動的に
剥がすと、生きているセッションの上へ二重投入する側に倒れる。止まっていることは盤面の側で見える
（2.4 の根拠と同じ）。

### 1.3 ラベルには結論だけを置く

- `直し待ち` … レビューが「直しが要る」を出した
- `通してよい` … レビューが通した
- `判断待ち` … 人間の返事が要る

どれも**真であることが、誰かが生きていることに依存しない**。`レビュー中`・`作業中` は置かない。

**`直し待ち` だけでは、「直している最中」と「誰も居ない」が区別できない。** ラベルは事実
（直しが要る）しか持たないので、これは正しい——**区別は 1.2 のセッションの側にある**。読む側が
両方を引かないと、直している最中のPRを止まっていると読む。

### 1.4 二重投入は、投入する側が自分で止める

**不変条件「同じ差分へ走るセッションは1本」は、投入するスクリプト自身が持つ。**
`dispatch-review.sh` / `dispatch-task.sh` が、立てる直前に 1.2 の**「今、手が動いているか」**を引き、
動いていれば**立てずに終わる**（既に走っていることを終了コードで返す）。

**盤面の側が同じ手を2回出しても、2本にはならない。** 正しさは呼び手に依存しない。

残る競合は「2本が同時に、引いて→無い→立てる」を通る数百ミリ秒の窓。**投入の経路をロックで1本に
する**ことで閉じる。

判定は [`occupancy.sh`](../scripts/agent/occupancy.sh)、**立ててよいかを答える口**は
[`may-dispatch.sh`](../scripts/agent/may-dispatch.sh)（手綱もここで見る）。呼び手が条件を並べずに
1つ訊くだけで済む形にしてある。

### 1.5 根拠（2026-09-04 に実測）

**異常終了は実在する。** セッション `01Wcy9XLj85X`（タグ `review-1493`、09-03T14:57 作成・15:00
更新）は `status_bucket = SESSION_STATUS_BUCKET_FAILED`。3分で落ちている。

**二重投入も実在する。** PR #1493 に、09-03T15:58 の**同じ分**に立ったレビューのセッションが2本
（`01SE1TqFmnRh` / `019gWmVuTtDE`）。結果はPRのコメントに残っていて、**食い違っている**。

```
16:04:59  [レビュー] 直しが要る
16:05:38  [レビュー] 通してよい
16:06:22  [レビュー] 直しが要る
```

83秒に3つ。**二重投入の害は「無駄」ではなく、矛盾した結論のどれを拾うかが運任せになること。**
機械が最初に見つけた「通してよい」を拾ってマージしていたら、他の2本が落とした差分が `main` へ
入っていた。

**本数では見分けられない。** PR #1512 も同じ日に3本立っているが、こちらは正当な再レビュー
（commit 13:25 → 判定 13:31 → commit 13:40 → 判定 13:45 → commit 13:54 → 判定 14:00）。

**原因は「印が無いこと」ではない。** 黙らせる判定は見張りの側にあり、`dispatch-review.sh` には
無かった。あちらは前のレビューを `archive-reviews.sh` で畳んでから立てるが、これは排他ではないので、
**2本が同時に「畳んで立てる」を通ると2本とも生き残る**。不変条件を、それを作る側ではなく呼び出し側が
肩代わりしていた（`CLAUDE.md`「自分のことは自分でする」）。ラベルを足しても、判定が投入の外にある
限り同じ競合が起きる。

**値の実測（2026-09-05・直近100件）。** `session_status` は
`SESSION_STATUS_ARCHIVED` 98 / `SESSION_STATUS_IDLE` 1 / `SESSION_STATUS_RUNNING` 1、
`status_bucket` は `..._COMPLETED` 86 / `..._FAILED` 13 / `..._WORKING` 1。**最上位の `status` は
常に `null`** なので見ない。

**手が空いたセッションは `..._COMPLETED` になる（2026-09-05）。** 畳まれていない `IDLE` の1本が
`..._COMPLETED` だった——**「終わった」ではなく「今は手が空いている」**の意味。**1.2 の前の版は
これを「占有していない」の一言で済ませていた**（【確定】の記述だが、実測と食い違ったので問い自体を
2つに割った）。

**畳んだセッションも文脈ごと再開できる（2026-09-05）。** 使い捨てのセッションを1本立てて畳み、
`unarchive_session` → `send_message` を通したところ、**畳む前の会話を覚えたまま返事をした**。
「直しの再開」を、書いた本人のセッションを起こして頼めるという根拠（3.3）。

**`list_sessions` の `tags` での絞り込みは、この呼び出し元からは使えない**（指定すると異常終了する。
ツールの説明にも OAuth の呼び出し元だけと書いてある）。`limit:100` で取って**手元で絞る**。
占有しているセッションは定義上いちばん新しいので、100件で足りる。

## 2. 機械ループの実行基盤【確定】

### 2.1 分け目は「CCRの資格情報が要るか」

置き場を決める軸は「PCが要るか」ではなく「**その処理は CCR の資格情報を要るか**」（根拠は 2.6）。
この軸は、1節で分けた事実／占有とちょうど一致する。

| | 動かすもの | 置き場 |
|---|---|---|
| 事実 | PR・コミット・レビューの結論・ラベル・マージ | **GitHub Actions** |
| 占有 | セッションの投入・生死の確認・畳み | **ブリッジの常駐デーモン**（bash、モデル不要） |

**効きどころは、デーモンが止まったときの壊れ方。** 投入できないことは盤面を壊さず、**進みが止まる
だけ**になる。投入待ちのものは GitHub 側にラベルとして残り、復帰したデーモンがそのまま拾う。
セッションの起動には元々ブリッジが要るので、これは追加の弱点ではない。

### 2.2 GitHub Actions が持つもの

イベント駆動を主とし、cron は取りこぼしの拾い直しに使う。

- `pull_request` の `synchronize` … `直し待ち` を外す
- `issue_comment` … `[レビュー] 通してよい` / `[レビュー] 直しが要る` からラベルを付ける
- `check_suite` … CIの結果をラベルへ
- マージ

**マージには PAT を使う**（出どころ: ユーザーの指示・2026-09-04）。`GITHUB_TOKEN` によるプッシュは
他のワークフローを起こさないので、そのままでは `pages.yml`（`push: main` で起動）が動かず**サイトが
更新されなくなる**。

### 2.3 ブリッジのデーモンが持つもの

`list_sessions` で占有を引き（1.2）、投入すべきものへセッションを立て、終わったものを畳む。投入の
種類は4つ——**新しいタスク**・**レビュー**・**直しの再開**・**その他のエージェント**（棚卸し・傾向分析）。

**ロック（1.4）は、この形で構造として満たされる。** 投入の経路がデーモン1プロセスに限られるので、
投入ごとの排他は要らない。要るのは**デーモンが二重に起動しないこと**だけで、起動時の `flock` 1つで済む。

**落ちたことを検知して知らせる仕組みは置かない**（出どころ: ユーザーの指示・2026-09-04）。走っている
セッションが増えないことで、盤面の側から見えるため。

### 2.4 投入の手綱【確定】

**人間の都合で投入を止められること**が要る（使用量の5時間上限が近いときなど。出どころ: ユーザーの
指示・2026-09-04）。**手綱が掛かるのは「セッションを立てること」だけ**——モデルの使用量を消費するのは
そこだけで、マージやラベルを止める理由は無い。**走っているセッションには触らない。**

置き場は**専用の issue のチェックボックス**（[#1515](https://github.com/gooyyu1/UnmappedIsland/issues/1515)）。
指示はスマホから来るので、**1タップで切り替わることが条件**になる。読むのは `## 手綱` 節の中だけで、
**行の文字列で見分ける**。

```
- [x] 投入する（これを外すと下は全部止まる）
  - [x] 新しいタスク
  - [x] レビュー
  - [x] 直しの再開
  - [x] その他のエージェント（棚卸し・傾向分析）
```

**チェックが「流す」。** 外れているとき、および**読めなかったとき**は止まる。読めないときに止まる側へ
倒すのは、**溢れるより止まるほうが軽い**から——止まっていることは見えるが、余分に立ったセッションは
矛盾した結論を生む（1.5）。

種類を分けるのは、**上限が近いときに「新しいタスクだけ止めて、走っているものは終わらせる」**が要る
から。仕組みは1つ（種類ごとに1ビット）で、種類はそのパラメータ。

読むのは [`brake.sh`](../scripts/agent/brake.sh)。**節の中を見出しの語で引く**——字下げでは見分けない
（人が編集する場所なので崩れる）。

これは**自前の規約**なので、`policies.md`「基盤が既に持っている状態を使う」に反する形になる。それでも
採るのは、一時停止に当たる状態を GitHub が持っておらず、かつ**読む側が1つ（デーモン）・書く側が1つ
（ユーザー）で、読めないときは止まる側へ倒す**ため、規約が揺れても壊れる先が安全側に限られるから。

### 2.5 使用量による自動の手綱【確定】

**上限が近づいたら自動で止め、明けたら自動で戻る**（出どころ: ユーザーの指示・2026-09-04）。
使用量は `GET https://api.anthropic.com/api/oauth/usage` から引ける（OAuthのアクセストークンだけで
通る。**モデルは要らない**）。使うのは次の部分。

```json
{ "five_hour": { "utilization": 47.0, "resets_at": "...", "locked_reason": null },
  "seven_day": { "utilization": 11.0, "resets_at": "...", "locked_reason": null } }
```

**流すかどうかは、手綱（人間）と余力（自動）の AND。** デーモンは**手綱の issue を書き換えない**
——2つの書き手が同じビットを取り合うと、人が入れたチェックを機械が外す形になる。別々に持って
掛け合わせる。

**しきい値は、`limits[].severity` のような基盤の出す段階には乗せない**（出どころ: ユーザーの指示・
2026-09-04）。基盤の段階は「どれだけ使ったか」を粗く言うだけで、**こちらが知りたい「あと1本投入して
よいか」には答えない**。要るのは残量そのものではなく**残量と1本あたりの消費の比較**なので、
**1本がどれだけ食うかを自分で計測して持つ。**

止める条件は種類ごとに次。

```
残り余力（= 100 - utilization） < その種類の1本あたりの平均消費 × 安全率
```

`locked_reason` が付いているときは、計測に関わらず全部止める（既に立てられない）。

引くのは [`usage.sh`](../scripts/agent/usage.sh)（読むだけ）。**比較のほうはまだ入っていない**
——1本あたりの消費の計測が溜まってから `may-dispatch.sh` へ足す。

**段は結果として付く。** 消費の大きい種類ほど早く止まるので、**上限が近づくと重い仕事から順に落ち、
軽いものが最後まで流れる**。「新しいタスクだけ止めてレビューは流す」という欲しい振る舞いは、種類ごと
にしきい値を書き分けなくても消費の差から出る。

**自動復帰に特別な処理は要らない。** 毎周引いて AND するだけなので、`resets_at` を過ぎて
`utilization` が下がった時点でそのまま流れが戻る。**「制限中だった」という状態を持たない**ので、
デーモンが途中で落ちても復帰の判断は狂わない（1.1）。

#### 1本あたりの消費をどう測るか

**セッション単位の消費は API から引けない**（2.8）。引けるのは全体の `utilization` だけなので、
**デーモンが毎周それを引いて、走っている本数で割り当てる。**

- 毎周、前回からの `utilization` の増分を、**そのとき動いていたセッション**（`status_bucket` が
  `..._WORKING`）で等分して積む。**手が空いているセッションには積まない**——占有は続いていても
  （1.2）、その周は食っていない。待っている本数で割ると、待つほど消費したことになる。
- **ユーザー自身の対話も分母に入る。** ブリッジの Claude Code もCCRのセッションなので一覧に載り、
  動いていれば `..._WORKING` が立つ。**別枠で1を足すと二重に数える。**
- **1本も動いていない周の増分は、誰にも積まない。** 一覧に載らないところが食ったぶんなので、投入した
  セッションのせいにすると過大に出る。
- セッションが畳まれた時点で、積み上がった値がそのセッションの消費。**種類ごとに平均を取る。**
- 計測が溜まるまでは既定値を使う。**既定は大きめに置く**——小さすぎると上限に当たって中途半端な
  セッションが残るが、大きすぎても投入が遅れるだけで済む。

蓄積した計測はデーモンの手元のファイルに置く（リポジトリへは入れない。毎周のコミットになるため）。
**これは過去の記録なのでデーモンが死んでも嘘にならず、消えない場所に置いてよい**（1.1）。

### 2.6 止まったセッションを起こす

制限で止まったセッションを起こす仕事は、**制限専用の機能にしない。** 止まったセッションを起こすのは
デーモンの通常の仕事で、制限が明けたときはそれが一斉に効くだけ。

- 対象は「畳まれておらず、**今は動いておらず**（`status_bucket` が `..._WORKING` でない）、担当して
  いる対象がまだ終わっていない」セッション。**`updated_at` は使わない**（1.2）ので、「古いから」では
  なく「手が空いているのに仕事が残っている」で選ぶ。制限で止まったものはこの条件に自然に入る。
- **仕事が終わったかは GitHub の側で見る**（1.1 の事実）。`task-<番号>` なら issue が閉じたか、
  `review-<番号>` ならそのPRに結論のラベルが付いたか。**セッションの側の状態では決められない**
  ——手が空いていることは、終わったことではない（1.2）。
- 起こすのは `send_message`。**同じセッションを継続させるので、二重に仕事をすることは無い**
  （新しく立てるのとは違い、1.4 の重複には当たらない）。
- **モデルの切り替えを要するときは起こせない。** `send_message` で `/model` を送ってもモデルは
  変わらない（実測: 2026-08-30、PR #1482 のレビューセッション）。Opus の障害などモデルを変えて
  再開したい場合は、人の手が要る（未決）。

### 2.7 消えるもの

司令塔のモデルセッション、`handover.sh`、[`commander-prompt.md`](commander-prompt.md)、
[`board.sh`](../scripts/agent/board.sh) の引き継ぎ向けの部分。**判断が無いので文脈が溜まらず、
引き継ぎという概念自体が無くなる。**

### 2.8 根拠（2026-09-04 に実測）

- **使用量は API から引ける。** `GET https://api.anthropic.com/api/oauth/usage` に OAuth の
  アクセストークンを付けて 200。`five_hour` / `seven_day` の `utilization`・`resets_at`・
  `locked_reason` と、`limits[]` の `kind` / `percent` / `severity` / `is_active` が返る。
  → 2.5 が成り立つ。
- **`resets_at` は、枠が同じかの判定には使えない**（2026-09-05 に実測）。同じ枠のまま、続けて呼ぶ
  たびに `07:19:59.015` 〜 `07:20:00.994` と揺れる。**揺れの中心がきりのよい境界に乗るので、どの
  粒度で丸めても境界をまたぐ。** → 枠が明けたことは `utilization` の下がりで見る
  （[`usage-attribute.mjs`](../scripts/agent/usage-attribute.mjs)）。
- **ただしセッション単位の消費は引けない。** `list_sessions` にトークンの項目は無く、`get_session` の
  `external_metadata.context_usage`（`used_tokens` / `max_tokens`）は**コンテキスト窓の埋まり具合**で
  あって累計の消費ではない。→ 2.5 の割り当てが必要になる。
- **CCRの資格情報は8時間で切れ、更新するのは Claude Code 本体。** `~/.claude/.credentials.json` の
  `accessToken` は 15:58 JST 発行・23:58 JST 期限。[`ccr-meta.sh`](ccr-meta.sh) は**読み直すだけで
  更新はしない**。つまり**今の仕組みが回っているのは、司令塔がモデルのセッションだからでもある**
  ——素の bash デーモンへ置き換えると、最後の更新から8時間で全部止まる。`refreshToken` は 09-20 まで
  有効なのでデーモン自身が更新する道はあるが、**同じファイルを Claude Code と取り合う**ので採らない。
  → **ブリッジで Claude Code が走っていることが、デーモンの前提。**
- **GitHub Actions は CCR の資格情報を持たない。** secret に置いても `refreshToken` が16日で切れ、
  入れ直しが人手に戻る（`policies.md`「人間に回す部分は最小に」）。→ 全部を Actions へ寄せる案は却下。
- **クラウドのCCRセッションは `api.github.com` へ届かない**（403 が返り、GitHub まで到達していない）。
- **`GITHUB_TOKEN` によるプッシュは他のワークフローを起こさない。** → マージには PAT。

## 3. 移行の順序【仮決め】

**今は盤面が止まっている**（2026-09-04 時点。畳まれていないセッションは1本だけで、それも手番を
終えている）。司令塔が走っていないので、**入れ替えの排他が要らない——「切り替え」ではなく
「立ち上げ」になる。**

段を切る基準は2つ。**各段の終わりで盤面が前より壊れていないこと**と、**戻せること**。

| 段 | やること | 危なさ | |
| --- | --- | --- | --- |
| 0 | 手綱の issue を1つ作る（2.4） | 無し | 済（[#1515](https://github.com/gooyyu1/UnmappedIsland/issues/1515)） |
| 1 | 占有と使用量を**読むだけ**の道具を作り、計測を貯め始める | 無し | 道具は済（[`usage-record.sh`](../scripts/agent/usage-record.sh)）。**呼び手が段4** |
| 2 | 投入スクリプトへ占有の判定を入れる（1.4） | 小 | 済 |

### 3.1 各段の理由

**段1を最初に置くのは、2.5 の安全率と既定値がここでしか決まらないから。** 計測は盤面を動かさなくても
貯まり始める（ユーザー自身の対話でも `utilization` は動くので、まず**デーモン以外の消費**が分かる）。
種類ごとの1本あたりは段4が動き出してから積まれるので、**貯め始めを早くするほど段5までに揃う。**

**ただし、計測を貯めるには周期的な呼び手が要る。** 2.5 の割り当ては「前回からの増分を、そのとき
生きているセッションで等分する」形なので、一定の間隔で引き続けないと増分が置き換わらない。1回ぶんの
割り当て（[`usage-record.sh`](../scripts/agent/usage-record.sh)）は置けたが、**貯め始めはデーモン
（段4）か、それに代わる定時実行が要る。**

**段2だけで PR #1493 の事故は止まる**（1.5）。占有の判定が投入スクリプトの中に入れば、呼ぶ側が司令塔
でもデーモンでも人手でも二重には立たない。**誤って「在る」と判定しても投入が止まるだけ**なので、
安全側に倒れている。早い段に置く値打ちが大きい。

**段3でラベルだけ先に移すのは、段4のデーモンが読む対象を揃えるため。** 今 PR #1512 はレビューが3周
「直しが要る」を出しているのに `直し待ち` が付いていない——付けていたのが司令塔で、それが止まって
いるから。**盤面の見え方が正しくなってからでないと、デーモンの判定を確かめられない。**

段3は使い捨てのPR（[#1516](https://github.com/gooyyu1/UnmappedIsland/pull/1516)、確認後に閉じた）で
**4つとも実測した**（2026-09-05）——`[レビュー] 直しが要る` で `直し待ち` が付き、push で外れ、
`[レビュー] 通してよい` で `通してよい` が付き、結論の行でないコメントでは動かない。

**段4で並列度を1に絞るのは、作業領域の多次元ラベルがまだ無いから。** 1本しか走らなければ領域は
衝突しない。**つまり領域ラベルは「起動の前提」ではなく「並列度を上げるための前提」**で、移行を
止めない。

**段5（マージ）を最後にするのは、唯一戻せない操作だから。** ラベルが正しく付くことを段3・段4で
確かめてから移す。

**ただし段4を入れた時点で、マージはもうデーモンが打っている**（`MERGE` の手）。2.1 の分け目
（CCRの資格情報が要るか）では、マージは CCR を要さないので Actions 側だが、**移して得られるのは
「ブリッジのPCが落ちていてもマージが進む」ことだけ**で、その状況ではレビューの投入も直しの再開も
止まっている。**マージだけが進んでも盤面は回らない**ので、段5は要否から保留する（仮決め。覆すなら
「ブリッジが落ちている間もマージだけは進んでほしい」と決まったとき）。

**段6（消すこと）を最後にするのは、戻せる先を残しておくため。** デーモンが回り始めて問題が出たとき、
司令塔の道具が消えていると戻れない。

### 3.2 移行を止めない、と判断したもの

**`## ユーザーへ` の受け皿と、#656 の口は、段4のブロッカーではない。** 司令塔が居なくなると読み手が
消えるが、**読まれないまま PR 本文に残るだけで盤面は止まらない。** 滞留は困るので受け皿は要るが、
それは段7以降でよい。**滞留していることが見えるようにはしておく。**

### 3.3 段4の前に確かめること（済）

**畳まれたセッションへ直しを頼めるか** → **頼める**（2026-09-05 に実測。1.5）。`unarchive_session`
→ `send_message` で、畳む前の文脈を保ったまま返事をする。投入の種類「直しの再開」は、書いた本人の
セッションを起こす形でよい。

## 4. レビューが何で止めるか【確定】

### 4.1 実測（2026-09-05）

直近18本のPRで、**差し戻しゼロが12本。** 周回は6本に集中している——#1493 と #1492 が5回、#1512 が
4回、#1497 が3回、#1508・#1507 が2回。

**その21回の「直しが要る」の理由を読むと、コードの挙動の問題は1件も無い。** すべてが
**ドキュメント・スキーマ・コメントの記述が現物と合っていない**という指摘だった。

### 4.2 周回が終わらない理由

**規則はもう在る。** [`review-criteria.md`](review-criteria.md) の末尾は「止めるのは、直さずに
マージすると壊れるものだけ」、[`review-prompt.md`](review-prompt.md) も同じ趣旨。**書き足しても
効かない。** 効いていない理由は3つ。

1. **観点の一覧が、ブロックとスメルを区別せず同格に並んでいる。** 7項目の箇条書きに印が無く、
   「止めるのは壊れるものだけ」はその下に1行あるだけ。読み手は一覧をチェックリストとして使うので、
   **項目に挙がっている＝止める理由**として読む。**一覧の形そのものが判断を作っている。**
2. **機械で見られるものをレビュアーに見せている。** 「PR本文に要る節」は正規表現で、「担当の範囲」は
   issue の担当リストと差分の突き合わせで分かる。人が見る限り往復に乗る。
3. **周回そのものが指摘を生産している。** 差分が変われば見る対象が変わり、軽微な不一致は**どの差分にも
   見つかる**。「1周で出し切れていない」のではなく、**出し切れる集合ではない。** だから往復回数の
   上限は対症療法で、ブロックの定義を絞ることだけが根治。

### 4.3 ブロックの定義【確定】

判定は一文で書ける。**この差分を入れると、入れる前より嘘が増えるか。**

1. **壊れている** — issue の現象が直っていない / 退行が入った / 実装が正しくない。**不要になった
   コードが残っているのもここ**（4.6 のとおり一部は CI が先に止める）
2. **この差分が嘘を増やす** — 新しく書いた記述が現物と合わない、差分が既存の記述を嘘にした、
   PR本文と差分が食い違う
3. **確定を覆している** — `【確定】` と「本書は全体が確定です」の射程に反する
4. **原因が浅い** — ただし**「その直しでは同じ不具合がまた出る」と具体的に言えるときだけ。**
   言えなければスメル
5. **`## 見た目` が無い** — `src/game/**` か `src/assets/**` を触ったのに、画面の画像も「不要」＋
   理由もPR本文に無い。**PR本文の節で止めるのはこれだけ**——入った後で誰も見返さないので、
   **後から補えるものが差分に無い**

**4だけ条件を付けたのは、ここが唯一「判断」だから。** 絞らないと今の状態に戻る。

**明示的にスメルへ落とすもの**——書かないと元に戻るので、名指しで書く。

- **「同じ誤りの兄弟が1箇所残っている」。** 片方を直した差分は、**嘘が1つ減っている。** 増えていない
  ものを止める理由にしない。**これが今いちばん周回を作っている**（#1492 の5周はほぼこれ）
- **元から在ったずれ**（差分が触っていない場所の記述が現物と合っていない）
- 名前・構造・重複・改善提案・ドキュメント間の言葉の違い
- **担当外のファイルを触っていること。** 並列度1（3節・段4）では衝突が起きない。並列度を上げる段で、
  **機械のチェックとして**復活させる

### 4.4 スメルの置き場【確定】

PRコメントに **`[スメル] ` の行頭**で残す。**ラベルは付けない**（1.3）。マージ後もコメントは残るので、
後から拾うエージェントがそのまま読める。**拾う側はまだ未決。**

### 4.5 2周目以降は、前の周の指摘が消えたかだけを見る【確定】

**新しいブロックとして挙げてよいのは、前の周のレビュー以降に入った差分に起因するものだけ。**
それ以外の場所から新しく見つけたものは、前の周で見えていたはずのもの＝見落としなので、スメルへ回す。
**これで指摘の供給が構造的に尽きる。**

### 4.6 3周してもブロックが残ったら人へ上げる

絞った後は1周で終わるのが普通になる想定なので、**3周まで行くこと自体が「機械では畳めていない」印。**
**この3という数だけは根拠が無い**——実績を見て動かす。上げ方は #656 と同じ「断定文＋チェック1つ」。

### 4.7 一次レビューも同じ観点に絞る

今のサブエージェント一次レビューが空振りするのは、**外のレビュアーが今回どの軽微を拾うかが決まって
いない**からで、当てようがない。4.3 の一覧に絞れば対象が有限になり、手前で拾えるようになる。
`## 自己点検` も短くなる。

### 4.8 「不要になった旧コード」を lint で拾えるか

**半分は既に拾っている。** `eslint.config.js` の `@typescript-eslint/no-unused-vars`（ファイル内の
未使用）と `@typescript-eslint/no-unnecessary-condition`（**型の上で常に成り立つ条件**＝修正で意味を
失った分岐）。

**拾えないのは3つ。** export されていてどこからも参照されないもの（eslint はファイル単位。`knip` を
足せば拾える）・型の上ではあり得るが実行時にはもう起きない分岐・**動くし型も通る「回避策・特別扱い」**
（`CLAUDE.md` 4節の本体はここ）。

**`knip` の追加は今は入れない。** 筋は通るが、4.1 のとおり**この観点で1本も止まっていない。**

### 4.9 直す先

- [`review-criteria.md`](review-criteria.md)（済） — 一覧を**ブロック**と**スメル**の2つの見出しに
  割る（印を付けるだけでは足りない。4.2 の 1）
- [`review-prompt.md`](review-prompt.md)（済） — 結論の語彙、`[スメル]` の書式、4.5 の規則
- [`../CLAUDE.md`](../CLAUDE.md)（済） — 一次レビューの節から観点の写しを外し、
  `review-criteria.md` を指すだけにした
- **段3の Actions** — 「PR本文に要る節」と「担当外」を引き取り、レビューの観点から落とす（4.2 の 2）

## 未決

**決める順序はこちらで決めてよい**（ユーザーの発言・2026-09-05）。着手前に方針だけ述べる。

- **積まれたPRを `main` の上へ載せ直す手。** [`merge-and-close.sh`](../scripts/agent/merge-and-close.sh)
  が下のPRのマージ後に base を張り替えるが、**それが防ぐのは自動クローズだけ。** squash マージでは
  下のコミットが `main` の履歴に入らず merge-base が動かないので、**上のPRの差分には下のぶんが混ざった
  まま**で、CIも古い base で得た緑のまま（base の変更では再実行されない）。しかも張り替えの後は
  base が `main` になるので [`board-move.mjs`](../scripts/agent/board-move.mjs) は普通に捌きにかかり、
  **混ざった差分がレビューへ出て、古い緑のままマージ候補になる。** 積まれている間だけ手が止まるので、
  **危ないのは下が入った後のほう。** 載せ直しをデーモンにやらせるか、積むこと自体を止めるか、人が
  やると決めるか。

- **作業領域の多次元ラベル。** 今の [`parallel-work.md`](parallel-work.md) 2節「所有権の地図」は
  6分割の一次元。棚卸し係が予め付ける形にする。
- **スメルを拾う側。** 残す先は決まった（4.4。PRコメントの `[スメル] `）が、**誰がいつ拾うかは
  未決。** 直近10PRを読んで傾向を見るエージェントと、その上でさらに長期の検討課題を拾う段。
  `## ユーザーへ` を廃止した後の行き先も同じ話。
- **人間への入力の口。** issue #656 のチェック方式を、マージの許可と仕様の確定とで分けるか。
- **自動の手綱（2.5）の安全率と、計測が溜まるまでの既定値。** どちらも実際の消費を見ないと決まらない。
  デーモンを動かして計測を貯めるのが先。
- **モデルを変えて再開したいとき（2.6）、デーモンから人へ届ける口。** `send_message` ではモデルが
  変わらないので人の手が要るが、デーモンには人へ知らせる経路が無い。
- **2.2 の「`check_suite` … CIの結果をラベルへ」は要るか。** 段3では入れなかった。CIの結果は
  `statusCheckRollup` でいつでも引ける事実なので、ラベルにすると**同じ事実の2つ目の写し**になり、
  食い違ったときにどちらが正か決まらない。段5（マージ）を起こす合図としては `check_suite` を使うが、
  そのときもラベルは要らない、という読み。**2.2 は確定なので、こちらで消さずに置く。**
- **周回数をどこで数えるか。** 4.5・4.6 は「前の周」と「3周」を要るものにしているが、**周回数を
  どう持つかは決めていない。** PRコメントの `[レビュー]` を数えれば出るので状態は要らないはずだが、
  未確認。
- **コンフリクトを解いただけの push に、レビューをもう1本立てるか。**
  [`parallel-work.md`](parallel-work.md)「PR の型」は立てないと決めている（ユーザーの指示・
