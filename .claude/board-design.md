# 盤面の設計

盤面を回す仕組みを、**機械的な処理だけで回る形**へ作り直す。ここは**決まったことを積む場所**——
決まった項目から順に節を足し、まだ決まっていないものは末尾の「未決」に並べる。実装が追いついた
節は、[`parallel-work.md`](parallel-work.md)・各プロンプト・`scripts/agent/**` の側を書き換えて
合わせる。**この文書と実装が食い違ったら、この文書が正。**

**`【確定】` が掛かるのは方針・方式だけで、実装の細部には掛からない**（[`DocumentStyle.md`](../docs/DocumentStyle.md)
6.1節）。実測の節と、そこから導いた「どの値をどう見るか」は印の外に置く——**測り直せば書き換わる側**
なので、覆すのに人間の判断は要らない。印は節の見出しに付き、**下位節には及ばない**ので、抱えている
節には付けずに確定した子だけに付ける。

向かう先（出どころ: ユーザーの指示・2026-09-04。錠の項目だけ 2026-09-06 の指示で絞り直した）。

- **中心は機械的な処理だけに絞る。** 判断が要るものは非同期の別エージェントへ切り離す。盤面を回す
  ことが、自動スクリプトだけで完結する状態を目指す。
- **同時に1本しか走れない資源の衝突は、投入のときに考えるのではなく、予め付けた錠**（`area:` の
  ラベル）**で避ける。** ファイルの衝突は投入では見ない——ぶつかったら直させ、**どこでぶつかったかを
  控えて**、錠を足すべき資源をそこから決める（[`parallel-work.md`](parallel-work.md) 2節）。
- **ワーカー・レビュアーからの申し送りを中心が読んで総合判断することをやめる。** 急がない懸念
  （アーキテクチャスメル・長期の検討課題）は残す場所を決めておき、後段のエージェントがまとめて拾う。

## 1. 状態の持ち方

**状態は、自前の規約で表さず、載っている基盤（GitHub・CCR）が既に持っているものを使う。** 自前の
規約は読む側と書く側の両方を自分で持つことになり、揺れれば黙って外れる。基盤に無い状態をどうしても
自前で持つときは、**規約が揺れたときに壊れる先が安全側に限られること**を確かめてから決める
（2.4 の手綱がこの形）。

### 1.1 事実と占有を分ける【確定】

分ける基準は「**持ち主が死んだとき、その状態は嘘になるか**」。

| | 事実 | 占有 |
|---|---|---|
| 例 | PRの存在・コミットのSHAと時刻・レビューの結論・issue の open/closed・`Closes` の紐付け | 「今このissueを誰かが作業している」「今このPRを誰かがレビューしている」 |
| 持ち主が死んだら | 真のまま | **嘘になる** |
| 置き場 | GitHub。消えてよい理由が無いので、消えない場所でよい | **セッションそのもの**。消えれば占有も消える |

**偽になるべき状態を、自分では消えない場所に書かない。**

`レビュー中`・`作業中` のラベルが破綻するのは、異常終了を防げないからではなく、**占有を事実の
置き場に書いたから**。ラベルは持ち主と無関係に生き続けるので、落ちたセッションのぶんが残り、
掃除役を足すことになる——それは嘘を後から拭く仕事を増やしているだけ。**異常終了は防げないので、
防ぐのではなく「落ちたら勝手に消える表し方」を選ぶ。**

### 1.2 セッションへの問いは2つある

走っているセッションへ訊きたいことは2つあり、それぞれ別の場所で使う。

#### 1.2.1 「居るか」と「手が動いているか」を、1つの占有へ畳まない【確定】

**2つの問いを1つの「占有」へ畳んではいけない。**

| 問い | 使う場所 |
|---|---|
| **その仕事に、生きたセッションが居るか**（投入済みか） | 盤面と、新しいタスクを立てる直前 |
| **今、手が動いているか**（二重に走らせない） | レビュー・直しの再開を立てる直前。1.4 の不変条件 |

**片方だけで書くと、必ずどちらかが壊れる。**

- 生死だけで排他すると、**判定を書き終えたレビューが占有し続け、再レビューが永久に止まる。**
  レビューは差分ごとに使い捨てで、次の差分のレビューは別の仕事。
- 手が動いているかだけで「投入済み」を読むと、**PRを出して手が空いたセッションの上へ2本目を立てる。**
  **手が空いていることは、終わったことではない**——仕事はまだそのセッションの手元にあり、次の指示が
  来れば同じ文脈で続きを書く。

**畳まれたセッションは「居ない」と読む。** 文脈ごと再開できる（1.5 で実測）が、**畳むのは
「この仕事は終わった」と判断した側の明示の操作**だから（担当の仕事がその手を離れたとき・次の
レビューを立てるとき）。

**どの問いで絞るかは呼び手が決める**——条件を一覧を出す側へ持つと、どの呼び手にも合わない定義が
1つできる。

止まったまま固まったセッションは、畳むまで「居る」と読まれ続ける。**それでよい**——時間で自動的に
剥がすと、生きているセッションの上へ二重投入する側に倒れる。止まっていることは盤面の側で見える
（2.4 の根拠と同じ）。

#### 1.2.2 2つの問いを、どこから引くか

1.2.1 から導いたもので、覆すのに人間の判断は要らない。

`task-<issue番号>` / `review-<PR番号>` のタグを持つセッションを `list_sessions` から引く。
盤面（[`board-move.mjs`](../scripts/agent/board-move.mjs)）と新しいタスクを立てる直前が前者を
`occupancy.sh --live` で、レビュー・直しの再開を立てる直前が後者を `occupancy.sh --busy` で引く。
**どの値がこの2つに答えるかは 1.6**——そちらは実測で動く。

畳まれたセッションを起こすのは `unarchive_session` → `send_message`。再レビューで前のセッションを
起こさずに新しく立てることは [`dispatch-review.sh`](../scripts/agent/dispatch-review.sh) が持つ。

一覧を出す [`live-sessions.sh`](../scripts/agent/live-sessions.sh) は**畳まれていないもの全部を、
判定に要る値を添えて**返す。

### 1.3 ラベルには結論だけを置く【確定】

| ラベル | 事実 | 効き目（これだけ） |
|---|---|---|
| `直し待ち` | そのPRに直しが要る | 書いた本人へ差し戻す |
| `通してよい` | レビューが通した | マージする |
| `収束せず` | レビューの往復では決まらなかった | **レビューを出さない** |
| `判断待ち` | 人の判断を待っている | **人が外すまで、その先へ進めない** |
| `却下` | 人がPRを止めている印を外した＝このままでは通せない（2.13.1） | 書いた本人へ差し戻す |
| `急ぎ` | 先に配ってほしい | **投入する順が先になる**（2.18） |

どれも**真であることが、誰かが生きていることに依存しない**。`レビュー中`・`作業中` は置かない。

**出どころ**: ユーザーの指示・2026-09-05（1つのラベルに効き目を1つだけ持たせる）

**1つのラベルに効き目を1つだけ持たせる。** 以前は
`判断待ち` が「マージを止める」「レビューを止める」「差し戻しも止める」を兼ねており、**人の判断と
関わらないコンフリクトの解消まで人待ちになった**（#1546）。割り方は 2.13。

**`判断待ち` はPRにも issue にも付く。** 効き目は1つ（人が外すまで進めない）で、**その先が母集団で
決まる**——PRなら次はマージ、issue なら次は投入。事実のほうも1つなので、ラベルを分けない。

**`直し待ち` を出すのはレビューだけではない。** 積まれたPRの base を GitHub が `main` へ張り替えた
ときも、後片付けが付ける（2.10.5）——張り替わっても差分とCIは載せ直すまで古いままなので、通す前に
書いた本人の手が要る。**ラベルが持つ事実は同じ**（直しが要る）なので、分けない。

**`直し待ち` と `却下` は、盤面から見た効き目が同じでも別のラベル。** 分け目は**起こされた側が
やること**——前者はレビューの指摘に答える作業、後者はユーザーが何を通さなかったのかを読んで、
そこに乗って書いた部分をまとめてやり直す作業で、読む場所も直す範囲も違う。渡す文面も分けてある
（[`resume-prompt.md`](resume-prompt.md)）。

**`直し待ち` だけでは、「直している最中」と「誰も居ない」が区別できない。** ラベルは事実
（直しが要る）しか持たないので、これは正しい——**区別は 1.2 のセッションの側にある**。読む側が
両方を引かないと、直している最中のPRを止まっていると読む。

### 1.4 二重投入は、投入する側が自分で止める

同じ差分へ2本を走らせない責任を、どこが持つか。

#### 1.4.1 不変条件は、投入する側が自分で持つ【確定】

**不変条件「同じ差分へ走るセッションは1本」は、投入するスクリプト自身が持つ。** 立てる直前に
1.2.1 の**「今、手が動いているか」**を引き、動いていれば**立てずに終わる**。

**盤面の側が同じ手を2回出しても、2本にはならない。** 正しさは呼び手に依存しない。

残る競合は「2本が同時に、引いて→無い→立てる」を通る短い窓。**投入の経路をロックで1本にする**
ことで閉じる。

#### 1.4.2 どのスクリプトが引き、どれが答えるか

1.4.1 から導いたもので、覆すのに人間の判断は要らない。

引くのは `dispatch-review.sh` / `dispatch-task.sh` で、既に走っていることは終了コードで返す。
判定は [`occupancy.sh`](../scripts/agent/occupancy.sh)、**立ててよいかを答える口**は
[`may-dispatch.sh`](../scripts/agent/may-dispatch.sh)（手綱もここで見る）。呼び手が条件を並べずに
1つ訊くだけで済む形にしてある。

### 1.5 根拠（2026-09-04 に実測）

**異常終了は実在する。** セッション `01Wcy9XLj85X`（タグ `review-1493`、09-03T14:57 作成・15:00
更新）は `status_bucket = SESSION_STATUS_BUCKET_FAILED`。3分で落ちている。

**二重投入も実在する。** PR #1493 に、09-03T15:58 の**同じ分**に立ったレビューのセッションが2本
（`01SE1TqFmnRh` / `019gWmVuTtDE`）。結果はPRのコメントに残っていて、**食い違っている**。

```
16:04:59  [レビュー] 直しが要る
16:05:38  [レビュー] 通してよい
16:06:22  [レビュー] 直しが要る
```

83秒に3つ。**二重投入の害は「無駄」ではなく、矛盾した結論のどれを拾うかが運任せになること。**
機械が最初に見つけた「通してよい」を拾ってマージしていたら、他の2本が落とした差分が `main` へ
入っていた。

**本数では見分けられない。** PR #1512 も同じ日に3本立っているが、こちらは正当な再レビュー
（commit 13:25 → 判定 13:31 → commit 13:40 → 判定 13:45 → commit 13:54 → 判定 14:00）。

**原因は「印が無いこと」ではない。** 黙らせる判定は見張りの側にあり、`dispatch-review.sh` には
無かった。当時のあちらは前のレビューを畳んでから立てていたが、これは排他ではないので、
**2本が同時に「畳んで立てる」を通ると2本とも生き残る**。不変条件を、それを作る側ではなく呼び出し側が
肩代わりしていた（`CLAUDE.md`「自分のことは自分でする」）。ラベルを足しても、判定が投入の外にある
限り同じ競合が起きる。

**畳んだセッションも文脈ごと再開できる（2026-09-05）。** 使い捨てのセッションを1本立てて畳み、
`unarchive_session` → `send_message` を通したところ、**畳む前の会話を覚えたまま返事をした**。
「直しの再開」を、書いた本人のセッションを起こして頼めるという根拠（3.3）。

**`list_sessions` の `tags` での絞り込みは、この呼び出し元からは使えない**（指定すると異常終了する。
ツールの説明にも OAuth の呼び出し元だけと書いてある）。`limit:100` で取って**手元で絞る**。
占有しているセッションは定義上いちばん新しいので、100件で足りる。

### 1.6 どの値で見るか

1.2 の2つの問いに、`list_sessions` のどの値が答えるか。**ここは実測で動く**ので印を付けない
——値の意味が違っていたら、この節を測り直して書き換える。

| 問い | 判定 |
|---|---|
| 生きたセッションが居るか | `session_status != SESSION_STATUS_ARCHIVED` |
| 今、手が動いているか | `session_status == SESSION_STATUS_RUNNING` |
| そのとき消費していたか | `session_status == SESSION_STATUS_RUNNING` |

**トップレベルの `status` は常に `null` なので使えない。** 直近100件の分布（2026-09-05）は
`session_status` が `ARCHIVED` 98 / `IDLE` 1 / `RUNNING` 1、`status_bucket` が `..._COMPLETED` 86 /
`..._FAILED` 13 / `..._WORKING` 1。

**手が動いているかを言うのは `session_status`。`status_bucket` では言えない。** 手が空いても
`..._WORKING` のまま固まることがある——2026-09-05、`task-1180` のセッション
（`01C7GHexVobbLne6d74ihmBV`）が `IDLE` + `..._WORKING` で1時間半動かず、その間
[PR #1524](https://github.com/gooyyu1/UnmappedIsland/pull/1524) のレビューが1周も出なかった。
**bucket で読むと、そうなったPRのレビューが永久に止まる。**

**`..._BLOCKED` も「手が動いている」ではない**（2026-09-05 に実測）。`status_bucket` は
`post_turn_summary` から決まる——**手番が終わって初めて書かれる値**なので、どれも「処理中」を
意味しない。`..._BLOCKED` に当たるのは `status_category == need_input`、つまり**手番を終えて人へ
問いを返した**セッションで、これは手が空いている側。実測したのは `task-1338` のセッション
（`014vvHyjQd2g7byJ56yrzFc7`）で、`IDLE` + `..._BLOCKED` + `status_detail: "PR #1541 ready; 3 new
issues (#1534–#1536) need go-ahead"`。**busy として読んだせいで、
[PR #1541](https://github.com/gooyyu1/UnmappedIsland/pull/1541) のレビューが2時間出なかった。**
`..._FAILED` は数えない（落ちたセッションの上へは立て直してよい。1.5 の `01Wcy9XLj85X`）。

**`..._COMPLETED` は「終わった」ではなく「今は手が空いている」**（2026-09-05 に実測。畳まれて
いない `IDLE` の1本がこの値だった）。だから 1.2 の「投入済みか」には答えない。

**`updated_at` はどの問いにも使わない。** 実測（2026-09-05）で、**走っているセッションでも
`updated_at` は動かない**——`SESSION_STATUS_RUNNING` のセッションの `updated_at` が、実際には走り
続けている1日前の時刻で止まっていた。**「古いから止まっている」は書けない。**

### 1.7 一覧を引く回数には上限がある

**`list_sessions` は1時間あたり1000回で頭打ちになる。** 超えると JSON の代わりに
`list_sessions is limited to 1000 calls per account per hour; retry in about N seconds` が返る
（2026-09-06 に実測）。**引く回数は、盤面が回る速さの天井そのもの**なので、1周あたり何回引くかを
設計の値として扱う。ここも実測で動くので印を付けない。

**壊れ方は「だんだん止まる」。** 1回の走査に要る回数は**これまでに作ったセッションの総数**に比例
するので、日が経つほど上限へ当たりやすくなる。当たった周は一覧が引けず、盤面はその周を捨てる——
**レビューも投入も1件も出ないまま、ログには「セッションの一覧を引けなかった」だけが並ぶ**
（2026-09-06、[PR #1573](https://github.com/gooyyu1/UnmappedIsland/pull/1573) /
[#1574](https://github.com/gooyyu1/UnmappedIsland/pull/1574) のレビューが立たなかった。当時
セッションは約600件・履歴8日ぶんで、1回の走査に6回。1周に4箇所が別々に引き、30秒間隔だったので
毎時2400回に達していた）。

掛け算の両側を落とす。

- **1周に1回だけ引く。** 引いた結果を [`board-round.mjs`](../scripts/agent/board-round.mjs) が
  ファイルへ置き、叩くスクリプトへは環境変数（`LIVE_SESSIONS_TSV`）で在り処だけを渡す。要る側は
  1周に4つある（盤面・使用量の割り当て・占有の判定・起こす相手の確認）が、**同じ周の答えは1つ**。
  投入の直前に引き直さないことは 1.4 の排他を弱めない——投入の経路はデーモン1本だから（2.3）。
- **繰るのは、生きたセッションが尽きるまで。** 生きたセッションが1件も無いページが続いたら止める
  （[`live-sessions.mjs`](../scripts/agent/live-sessions.mjs)）。実測（2026-09-06）では、生きて
  いた3本すべてが1ページ目——**畳まれていないものは新しい側に固まる**。

**取りこぼす側の危険は残る。** 畳まれたセッションが続いた向こうに生きたものが居ると見つからず、
盤面はそのタグを空きと読んで**二重に立てる**（1.5）。だから止める枚数は減らす向きに倒さない。

**引けなかったときは、道具が言った理由をそのまま出す。** 上限も認証切れも、呼び手には「引けな
かった」しか残らないので、**ログだけでは直しようが無くなる**。

## 2. 機械ループの実行基盤

**何かの完了を待つ間隔は、その遅れを誰が待つかで決める。** 人が待っているなら細かく（秒の単位）、
**遅れがそのまま次の仕事の滞りになるときも同じく細かく**。誰も待たず、遅れても滞らないものだけ、
落ち着いた間隔でよい。高いのはモデルのターンで、シェルの実行回数ではない。

**無人で回る仕組みで先に要るのは、落ちたことを検知して知らせる仕組みではなく、意図的に止められる
手綱**（2.4）。止められない仕組みは、止めたいときに個別に潰して回ることになる。**この盤面では、
知らせる側はそもそも置いていない**——落ちたことは走っているセッションが増えないことで見えるから
（2.3.3）。

### 2.1 分け目は「CCRの資格情報が要るか」【確定】

置き場を決める軸は「PCが要るか」ではなく「**その処理は CCR の資格情報を要るか**」（根拠は 2.6）。
この軸は、1節で分けた事実／占有とちょうど一致する。

| | 動かすもの | 置き場 |
|---|---|---|
| 事実 | PR・コミット・レビューの結論・ラベル・マージ | **GitHub Actions** |
| 占有 | セッションの投入・生死の確認・畳み | **ブリッジの常駐デーモン**（モデル不要） |

**効きどころは、デーモンが止まったときの壊れ方。** 投入できないことは盤面を壊さず、**進みが止まる
だけ**になる。投入待ちのものは GitHub 側にラベルとして残り、復帰したデーモンがそのまま拾う。
セッションの起動には元々ブリッジが要るので、これは追加の弱点ではない。

### 2.2 GitHub Actions が持つもの

#### 2.2.1 どのイベントで何を打つか

イベント駆動を主とし、cron は取りこぼしの拾い直しに使う。

- `pull_request` の `synchronize` … `直し待ち` を外す
- `issue_comment` … レビューの結論の行（`[レビュー]` で始まる1行目。2.13.4）からラベルを付ける
- `unlabeled` … 人がPRを止めている印を外したことを `却下` へ訳す（2.13.1）。**人が外したのか、
  push で機械が外したのかは sender で見分ける**——機械（`GITHUB_TOKEN`）は `Bot`
- マージ

#### 2.2.2 CIの結果はラベルにしない【確定】

**出どころ**: ユーザーの指示・2026-09-06。

CIの結果はGitHubへ訊けばいつでも引ける事実なので、ラベルにすると**同じ事実の2つ目の写し**になり、
食い違ったときにどちらが正か決まらない。**マージを起こす合図としてCIの完了を使うのは別の話**
——それでもラベルは要らない（段5。要否は 3.1 で保留）。

#### 2.2.3 マージには PAT を使う【確定】

**出どころ**: ユーザーの指示・2026-09-04。

`GITHUB_TOKEN` によるプッシュは他のワークフローを起こさないので、そのままでは公開サイトの
デプロイが動かず**サイトが更新されなくなる**。

### 2.3 ブリッジのデーモンが持つもの

`list_sessions` で占有を引き（1.2）、投入すべきものへセッションを立て、終わったものを畳む。投入の
種類は**新しいタスク**・**レビュー**・**直しの再開**・**その他のエージェント**（2.17 の周期で起きる
係）で、**手綱の側ではこれがさらに入れ子になる**（2.4）。

**ロック（1.4）は、この形で構造として満たされる。** 投入の経路がデーモン1プロセスに限られるので、
投入ごとの排他は要らない。要るのは**デーモンが二重に起動しないこと**だけで、起動時の `flock` 1つで済む。

#### 2.3.1 引けなくなっても、デーモンは止まらない

盤面を続けて引けなくなったら、待つ間隔を落として回り続ける（[`daemon.sh`](../scripts/agent/daemon.sh)
の `RETRY_INTERVAL`）。**止めない理由は、いちばん多い原因を自分では直せないこと**——アクセストークンは
数時間で切れ、切れている間は `list_sessions` が 401 を返すが、**貼り直すのは Claude Code 本体**で、
デーモンにも [`ccr-meta.sh`](ccr-meta.sh)（毎回 `~/.claude/.credentials.json` を読み直す）にもできない。
放っておけば直るものなので、止まらずに待つほうが速い。

**止まると、直っても盤面が動かない。** 立て直すのは起こす係（2.19）なので、切れていた時間ではなく
**次の点検までの時間**が止まる長さになる（2026-09-06 00:27Z に5回続けて 401 で落ちて止まり、
当時の手で立てた点検が拾うまで10分止まった）。意図して止めるための手綱は `stop` の側にある
——**落ちる側で兼ねない。**

#### 2.3.2 走る版を入れ替えるのも、デーモン自身

**回っている bash は、最初に読んだ版のまま。** 後片付けのたびに本体が `main` へ進む（`SYNCED`）ので、
隣の道具は次の周から新しい版で動くのに、[`daemon.sh`](../scripts/agent/daemon.sh) だけが古いまま残る
——**プロセスが一度しか読まないのはこの1本**で、他は毎周読み直される。

**走るのは複製で、リポジトリの1本ではない。** bash はスクリプトを読み進めながら実行するので、走行中に
中身が入れ替わると次に読む位置が別の中身を指す（コメント1行の挿入でも起きる）。周の終わりに複製元と
見比べ、変わっていたら `exec` で自分を入れ替える——PIDが残るので、錠も心拍もそのまま渡る。
**「違ったら終了して起こす係が立て直す」形は採らない**（出どころ: ユーザーの指示・2026-09-06）
——デーモンは単純になるが、新しい版が入るのが次の点検まで遅れる。

**立てるときは、本体を `origin/main` へ寄せてから**（`start`）。落ちた跡から起こすのは起こす係（2.19）で、
打つのは `start` だけなので、ここで寄せないと落ちた時点の版が次のマージまで回り続ける。**寄せるのは
`start` が持ち、起こす係には持たせない**（出どころ: ユーザーの指示・2026-09-06）——同じ更新をする仕組みを
2つ置くと、どちらが進めたのかが読めなくなる。本体に未コミットの変更があるときは触らず（`DIRTY` と
同じ判定）、**寄せられなくても立てる**——古い版で回ることより、盤面が動かないことのほうが重い。

**本体を進める者は、依存も入れ直す。** 作業ツリーは本体の `node_modules` を共有するので、進めた側が
入れ直さないと、共有しているのに版が食い違う（`parallel-work.md`「本体のチェックアウトは、マージ済みの
PRを見つけるたびに追随させる」）。`start` が跨ぐのは後片付けの外で `main` が動いたぶんなので、
後片付けの周が打ったかどうかとは別に見る。

#### 2.3.3 落ちたことを検知して知らせる仕組みは置かない【確定】

**出どころ**: ユーザーの指示・2026-09-04。

走っているセッションが増えないことで、盤面の側から見えるため。

### 2.4 投入の手綱

#### 2.4.1 止められるのは投入だけ【確定】

**出どころ**: ユーザーの指示・2026-09-04（止められること）／ユーザーの発言・2026-09-05
「通してよい、ならマージして良いです」（マージは分けない）。

**人間の都合で投入を止められること**が要る（使用量の5時間上限が近いときなど）。**手綱が掛かるのは
「セッションを立てること」だけ**——モデルの使用量を消費するのはそこだけで、マージやラベルを止める
理由は無い。**走っているセッションには触らない。**

**分けるのはレビューを立てるところまでで、マージは分けない。** `通してよい` はレビューが書いた事実
なので、PRの由来はマージしてよいかに関わらない。

#### 2.4.2 どこへ置き、どう読むか

置き場は**専用の issue のチェックボックス**（[#1515](https://github.com/gooyyu1/UnmappedIsland/issues/1515)）。
指示はスマホから来るので、**1タップで切り替わることが条件**になる。読むのは `## 手綱` 節の中だけで、
**行の文字列で見分ける**。

```
- [x] 投入する（これを外すと下は全部止まる）
  - [x] 新しいタスク
  - [x] レビュー
    - [x] task を持たないPRも読む
  - [x] 直しの再開
  - [x] その他のエージェント（周期で起きる係）
```

**チェックが「流す」。** 外れているとき、および**読めなかったとき**は止まる。読めないときに止まる側へ
倒すのは、**溢れるより止まるほうが軽い**から——止まっていることは見えるが、余分に立ったセッションは
矛盾した結論を生む（1.5）。

種類を分けるのは、**上限が近いときに「新しいタスクだけ止めて、走っているものは終わらせる」**が要る
から。仕組みは1つ（種類ごとに1ビット）で、種類はそのパラメータ。

**種類は入れ子になる。** `Closes` の先に `kind:task` の issue が無いPR——人と直接話した結果のPR——を
読ませるかは、レビュー全体とは別に切り替えたい（デーモンが配った仕事ではないので、**その仕事の当事者
でないレビュアーが設計判断を通す**ことになる。2026-09-05 の PR #1526 が実例）。種類から引くのは1つの
見出しではなく**根から自分までの鎖**で、どれか1つでも外れていれば止まる。**仕組みは増えず、鎖の長さが
パラメータになる。**

読むのは [`brake.sh`](../scripts/agent/brake.sh)。**節の中を見出しの語で引く**——字下げでは見分けない
（人が編集する場所なので崩れる）。**どの鎖を訊くかを決めるのは投入するスクリプト自身**
（[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh) が `Closes` 先のラベルを見る）で、
盤面（[`board-move.mjs`](../scripts/agent/board-move.mjs)）は種類を知らない——「立ててよいか」は
投入する側が持つ不変条件だから（1.4）。手綱で止まった周は、その手が打てずに次の手へ進む。

これは**自前の規約**なので、1節の「基盤が既に持っている状態を使う」に反する形になる。それでも
採るのは、一時停止に当たる状態を GitHub が持っておらず、かつ**読む側が1つ（デーモン）・書く側が1つ
（ユーザー）で、読めないときは止まる側へ倒す**ため、規約が揺れても壊れる先が安全側に限られるから。

### 2.5 使用量による自動の手綱

#### 2.5.1 余力で自動的に止め、明けたら自動的に戻す【確定】

**出どころ**: ユーザーの指示・2026-09-04。

**上限が近づいたら自動で止め、明けたら自動で戻る。**

**しきい値は、基盤の出す段階には乗せない。** 基盤の段階は「どれだけ
使ったか」を粗く言うだけで、**こちらが知りたい「あと1本投入してよいか」には答えない**。要るのは
残量そのものではなく**残量と1本あたりの消費の比較**。

#### 2.5.2 どう引いて、どう比べるか

使用量は `GET https://api.anthropic.com/api/oauth/usage` から引ける（OAuthのアクセストークンだけで
通る。**モデルは要らない**）。使うのは次の部分。

```json
{ "five_hour": { "utilization": 47.0, "resets_at": "...", "locked_reason": null },
  "seven_day": { "utilization": 11.0, "resets_at": "...", "locked_reason": null } }
```

止める条件は種類ごとに次。

```
残り余力（= 100 - utilization） < その種類の1本あたりの平均消費 × 安全率
```

`locked_reason` が付いているときは、計測に関わらず全部止める（既に立てられない）。

**段は結果として付く。** 消費の大きい種類ほど早く止まるので、**上限が近づくと重い仕事から順に落ち、
軽いものが最後まで流れる**。「新しいタスクだけ止めてレビューは流す」という欲しい振る舞いは、種類ごと
にしきい値を書き分けなくても消費の差から出る。

**流すかどうかは、手綱（人間）と余力（自動）の AND。** デーモンは**手綱の issue を書き換えない**
——2つの書き手が同じビットを取り合うと、人が入れたチェックを機械が外す形になる。別々に持って
掛け合わせる。

**自動復帰に特別な処理は要らない。** 毎周引いて AND するだけなので、枠が明けた時点でそのまま流れが
戻る。**「制限中だった」という状態を持たない**ので、デーモンが途中で落ちても復帰の判断は狂わない（1.1）。

**この口も叩ける間隔に上限がある。** 続けて叩くと2回目から `429 rate_limit_error` が返り、通るのは
**2分に1回ほど**（2026-09-06 に実測）。周ごと（35秒）に叩いていたので、**ログの半分が
「使用量を引けなかった」で埋まり、本物の失敗が見えなくなっていた**（[issue #1562](https://github.com/gooyyu1/UnmappedIsland/issues/1562)）。
何秒に1回なら通るかは口の性質なので、間隔を持つのは [`usage.sh`](../scripts/agent/usage.sh) の側。
**間隔が空いていない周は「今は読む番ではない」として終了コード2で返し、呼び手は何も言わずに
見送る**——失敗（1）と分けないと、待つだけの周まで異常として並ぶ。**粗くしても総和は変わらない**
ので、詰める理由は無い（2.5.3）。

引くのは [`usage.sh`](../scripts/agent/usage.sh)（読むだけ）。**比較のほうはまだ入っていない**
——1本あたりの消費の計測が溜まってから `may-dispatch.sh` へ足す。

**`resets_at` は使わない**（2.8）。枠が変わったことは `utilization` の下がりで見る。

**同じ意味なのに呼ぶたび揺れる値は、許容幅を置いて受けるのではなく、判定から外す。** 許容幅を置くと、
正しさが揺れ幅の観測に依存し続ける。外して失う正しさは、**いつ・どれだけ狂うか**を見積もってから
決める——丸めても、揺れの中心がきりのよい境界に乗る。

#### 2.5.3 1本あたりの消費をどう測るか

2.5.1 が比べる相手を1本あたりの消費と決めているので、**それを自分で測って持つことになる。** 状態は
基盤のものを使う（1節）が、しきい値は別の話として扱う。

**セッション単位の消費は API から引けない**（2.8）。引けるのは全体の `utilization` だけなので、
**デーモンが毎周それを引いて、走っている本数で割り当てる。**

- 毎周、前回からの `utilization` の増分を、**そのとき動いていたセッション**（1.6）で等分して積む。
  **手が空いているセッションには積まない**——占有は続いていても（1.2）、その周は食っていない。
  待っている本数で割ると、待つほど消費したことになる。
- **ユーザー自身の対話も分母に入る。** ブリッジの Claude Code もCCRのセッションなので一覧に載り、
  動いていればそう見える。**別枠で1を足すと二重に数える。**
- **1本も動いていない周の増分は、誰にも積まない。** 一覧に載らないところが食ったぶんなので、投入した
  セッションのせいにすると過大に出る。
- セッションが畳まれた時点で、積み上がった値がそのセッションの消費。**種類ごとに平均を取る。**
- 計測が溜まるまでは既定値を使う。**既定は大きめに置く**——小さすぎると上限に当たって中途半端な
  セッションが残るが、大きすぎても投入が遅れるだけで済む。

蓄積した計測はデーモンの手元のファイルに置く（リポジトリへは入れない。毎周のコミットになるため）。
**これは過去の記録なのでデーモンが死んでも嘘にならず、消えない場所に置いてよい**（1.1）。

### 2.6 止まったセッションを起こす

制限で止まったセッションを起こす仕事は、**制限専用の機能にしない。** 止まったセッションを起こすのは
デーモンの通常の仕事で、制限が明けたときはそれが一斉に効くだけ。

#### 2.6.1 自動化の外にあるのは、モデルを変えて再開する操作だけ【確定】

**出どころ**: ユーザーの指示・2026-09-06。

**モデルの切り替えを要するときは起こせない**ので、Opus の障害などモデルを変えて再開したい場合は
人の手が要る。**自動化の対象外なのはその操作そのものだけ**——動かないことの検知と人への引き渡しは
2.15.3 が担う。

#### 2.6.2 誰を、どうやって起こすか

- 対象は「畳まれておらず、**今は動いておらず**（1.6）、担当している対象がまだ終わっていない」
  セッション。**`updated_at` は使わない**（1.6）ので、「古いから」ではなく「手が空いているのに仕事が
  残っている」で選ぶ。制限で止まったものはこの条件に自然に入る。
- **仕事が終わったかは GitHub の側で見る**（1.1 の事実）。`task-<番号>` ならその issue がまだ
  そのセッションの仕事か（2.10.2）、`review-<番号>` ならそのPRに判定のコメントが在るか（2.10.3）。
  **セッションの側の状態では決められない**
  ——手が空いていることは、終わったことではない（1.2）。
- 起こすのは `send_message`。**同じセッションを継続させるので、二重に仕事をすることは無い**
  （新しく立てるのとは違い、1.4 の重複には当たらない）。
- **`send_message` で `/model` を送ってもモデルは変わらない**（実測: 2026-08-30、PR #1482 の
  レビューセッション）。2.6.1 が人の手に残るのはこのため。

### 2.7 中心にモデルのセッションを置かない【確定】

盤面を回す手前に、判断を担うモデルのセッションを置かない。**判断が無いので文脈が溜まらず、
引き継ぎという概念自体が無くなる**——引き継ぐための道具も、渡す本文も要らない。

**判断の要るものは、非同期の別エージェントへ切り離す**（2.17）。中心が賢くなるほど、そこは
引き継ぎ・文脈・可用性の単一障害点になる。

### 2.8 根拠（2026-09-04 に実測）

- **使用量は API から引ける。** `GET https://api.anthropic.com/api/oauth/usage` に OAuth の
  アクセストークンを付けて 200。`five_hour` / `seven_day` の `utilization`・`resets_at`・
  `locked_reason` と、`limits[]` の `kind` / `percent` / `severity` / `is_active` が返る。
  → 2.5.1 が成り立つ。
- **`resets_at` は、枠が同じかの判定には使えない**（2026-09-05 に実測）。同じ枠のまま、続けて呼ぶ
  たびに `07:19:59.015` 〜 `07:20:00.994` と揺れる。**揺れの中心がきりのよい境界に乗るので、どの
  粒度で丸めても境界をまたぐ。** → 枠が明けたことは `utilization` の下がりで見る
  （[`usage-attribute.mjs`](../scripts/agent/usage-attribute.mjs)）。
- **ただしセッション単位の消費は引けない。** `list_sessions` にトークンの項目は無く、`get_session` の
  `external_metadata.context_usage`（`used_tokens` / `max_tokens`）は**コンテキスト窓の埋まり具合**で
  あって累計の消費ではない。→ 2.5.3 の割り当てが必要になる。
- **CCRの資格情報は8時間で切れ、更新するのは Claude Code 本体。** `~/.claude/.credentials.json` の
  `accessToken` は 15:58 JST 発行・23:58 JST 期限。[`ccr-meta.sh`](ccr-meta.sh) は**読み直すだけで
  更新はしない**。つまり**デーモンが回り続けられるのは、同じPCで Claude Code が走っているから
  でもある**——素の bash だけにすると、最後の更新から8時間で全部止まる。`refreshToken` は 09-20 まで
  有効なのでデーモン自身が更新する道はあるが、**同じファイルを Claude Code と取り合う**ので採らない。
  → **ブリッジで Claude Code が走っていることが、デーモンの前提。**
- **GitHub Actions は CCR の資格情報を持たない。** secret に置いても `refreshToken` が16日で切れ、
  入れ直しが人手に戻る（`CLAUDE.md`「人間に回す部分は、最小にして自己完結させる」）。→ 全部を
  Actions へ寄せる案は却下。
- **クラウドのCCRセッションは `api.github.com` へ届かない**（403 が返り、GitHub まで到達していない）。
- **`GITHUB_TOKEN` によるプッシュは他のワークフローを起こさない。** → マージには PAT。

### 2.9 セッションのタイトル

#### 2.9.1 頭の語だけで種類が分かる形にする【確定】

**出どころ**: ユーザーの指示・2026-09-05（頭の語と、下の表の形）／ユーザーの指示・2026-09-06
（この番号が要るのは題だけ）。

一覧で読むのは人間で、タグ（`task-1180`）は機械の見分けなので人には読みにくい。

| 頭 | 何をするセッションか | 形 |
|---|---|---|
| 作業 | `kind:task` の issue 1件を片付ける | `作業 #<issue> <issue の題>` |
| レビュー | PRの差分を1回読む | `レビュー #<PR>:<何回目> <PR の題>` |
| 相談 | ユーザーが頼んで立てる、盤面の外の1本 | `相談 <相談内容>` |
| 棚卸 | 未整理の issue を分類し、投入できる形へ翻訳する | `棚卸 <対象>` |
| 発掘 | 配れる `goal:game` が無いとき（2.18.1）、完成の定義に照らして残りを数える | `発掘 <対象>` |

**「何回目」が要るのは題だけで、レビューのセッション自身が何周目かを知る必要は無い。**

#### 2.9.2 表に無い題と、番号の出し方

2.9.1 から導いたもので、覆すのに人間の判断は要らない。

**題の番号を他が当てにしていないのは、境界も勘定も別のところから出ているから**——4.5（前の周の指摘
だけを見る）は前の周が名乗った版で境界を引き（4.5.2）、4.6（3周で人へ上げる）は
[`board-labels.yml`](../.github/workflows/board-labels.yml) が同じコメントを数える。

**題を組み立てるのは投入する側**（[`dispatch-session.mjs`](../scripts/agent/dispatch-session.mjs) が
共通の形を持つ）。表の「相談」だけは、立てる人が自分で付ける。

**周期で起きる係の題は、渡すプロンプトの `題:` の行が持つ**（2.17）。投入する側は係の名前しか
知らないので、頭の語をそちらへ持たせると表が2つに割れる。

**「何回目」は数えて出す。状態を持たない。** そのPRに既に付いている**結論のコメント**を数えて +1。
判定はコメントとして GitHub に残る事実なので、持ち主が死んでも嘘にならない（1.1）。**見分け方は
[`board-labels.yml`](../.github/workflows/board-labels.yml) の `verdict` と同じ**——1行目が結論の文
そのもの。緩めると、ラベルが付かなかったコメントで番号だけが進む。
**判定を書かずに落ちたレビューは数に入らない**ので、次の1本が同じ番号を名乗る——「何本立てたか」
ではなく「**何個目の判定になるはずか**」を指す。

### 2.10 マージした手に、後を繋がない

#### 2.10.1 条件は issue、探すのはワーカーの側から【確定】

**出どころ**: ユーザーの指示・2026-09-05。

- 畳んでよいかは**担当の issue の側**で決まる。**PRをマージしたかでは決めない**——マージと
  ワーカーを畳むことは別の問いで、繋ぐと、人が画面からマージしたときに畳む手が一度も走らない。
  **issue の何を見れば「もう仕事ではない」と言えるかは 2.10.2**（印の外。導出なので測り直せる）。
- 探すのは**手が空いているワーカーの側から**、そのタグが指す issue の状態を引く。閉じた issue の側から
  探さない——閉じた issue は増える一方で、そのほとんどに畳む相手は居ない。

#### 2.10.2 どう引くか

**「もう仕事ではない」と言える形は、閉じたことだけではない。** 閉じた issue はマージか取り下げで
決着しており、`判断待ち` が付いた issue は人の手番へ移っている（2.15.3）。**走らせる先が食い違った
issue**（2.16.2）も、そこはこのワーカーの居場所ではない。**どれも畳む。畳んだ理由が読めるように、
指紋は形ごとに分ける。**

盤面は開いている issue の一覧を既に持つ（2.3）ので、**そこに載っていない `task-<番号>` だけ**を
`gh issue view` で引き直す。打つ数は生きたワーカーの数までで、その大半は一覧の側で当たる。

畳むのは [`archive-session.sh`](../scripts/agent/archive-session.sh) で、**畳んでよいかの最終判定は
あちらが持つ**（仕事の単位を持たないタグのものや、素性を引けなかったものは畳まない）。畳まなかった
（`KEPT`）は**同じ指紋のあいだ変わらない答え**なので、指紋を残して次の周からは打たない。

**判定の根拠は、あちらが自分で引ける事実だけにする。** ブリッジで立てたセッションは
`claude remote-control` が生きている間しか安全に畳めないと見て、**それを知っている呼び手に旗
（`--force-bridge`）で言わせていた**が、旗を渡す唯一の呼び手が消えたとき、
出るのは `KEPT` だけだった——**例外が外れないまま回り続けていることに、誰も気づけない。**
ブリッジのワーカーは仕事が終わっても枠を握ったまま残り、並列度が1なので次の task が1つも入らない
（issue #1558）。今はブリッジも同じ条件で畳み、**worktree を外せるかどうかは打った結果で分かる**
——掴まれていれば `git worktree remove` が断り、`DIRTY` として残る。

#### 2.10.3 レビューのセッションは、この鍵では引けない

レビューは issue を持たないので、`review-<PR番号>` のタグで引く。**合図は「この1本が判定を書いたか」**
——レビューは使い回さないので（[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh)）、書いた
時点でもう誰も起こさない。**手が止まっていることはその合図ではない**（1.2）。**そのPRがこの後どう
流れるかも見ない**——見ると、閉じないPR（`収束せず`・`直し待ち` のまま）のレビューが永久に残る。

**畳むのは盤面の手にする。** マージや次の投入のついでに掃いていたときは、**それが起きないPRの
ぶんが残った**——2026-08-30 に16本溜まり、2026-09-05 には人が画面からマージした #1549 のレビューが
残った。ワーカーで 2.10.1 が避けた誤り（畳むことを別の出来事に繋ぐ）と同じもの。

**判定を書き終えていれば、空くのを待たずに畳む。** 「走り終わった」と「道具の承認を待っている」を
見分けるために空いたままの長さを見る（2.15.3 の窓）が、**その窓が要るのは終わったかを他に訊けない
ときだけ。** レビューには訊く先がある——**そのPRに、この周が投入した版（台帳の指紋）を名乗った判定の
コメントが在るか**（2.9。見分け方は [`review-verdicts.mjs`](../scripts/agent/review-verdicts.mjs) が
1箇所で持つ）。**版で照合するので、前の差分へ書かれた判定を今の判定と読み違えない。**

**結論のラベルでは見ない。** ラベルを付けるのは [`board-labels.yml`](../.github/workflows/board-labels.yml)
なので、**付く前は書き終えたことを言えず、著者が push すると外れる**ので書き終えた後にも言えなくなる
（2.6）。**開いていないPRのレビューも終わり**——マージされたからではなく、判定を書いても置く先が無い。
周期の係（2.17）には訊く先が無いので、あちらは窓だけで測る。

**畳むのが先で、ラベルは後から付く。** その隙間のPRは「読み手が居ないのに結論のラベルも無い」形に
なるので、**次の1本を立てる側（2.12.4）も同じコメントを訊く。** 訊かないと、判定の付いた差分へ
もう1本立つ。

**待たせると枠が空かない。** 判定を書き終えたレビューを窓のぶん残していたときは、次の周期の係も
次のレビューも、その間ずっと立たなかった（2026-09-06、PR #1603 のレビューが14分残った）。

**窓が満ちても、畳む前に1回だけ起こす。** 畳めば次の周に新しい1本が立つ（2.12.4）が、**読んだ
ところは畳んだ時点で消える**ので、その1本は差分を読み直すところから始まる。続きを書かせるほうが
安いので、先に `RESUME … review-stall` を打つ（文面は [`resume-prompt.md`](resume-prompt.md) の
`## review-stall`）。**畳むのは、空いたままが窓の2つぶんに達してから**——合図が届くには時間が要る
（2.15.3 と同じ）。**動き出せば空いた時刻の覚えは消える**ので（[`board-round.mjs`](../scripts/agent/board-round.mjs)
の `trackIdle`）、そこからまた空いたときは2つぶんを数え直す。

**二度は起こさない。** 指紋は `review-stall:<PR番号>` で、**`stall:` で始めてはいけない**
——`trackIdle` は `stall:` で始まる覚えを動き出した時点で捨てる（ワーカーは再び空けばもう一度
起こす側なので。2.15.3）ので、始めるとレビューも起こし直しになる。**レビューに二度目が無いのは、
起こしても書かないなら読み直したほうが速いから。**

**読んだ差分がもう頭でなければ、起こさずに畳む。** 書けるのは前の差分への判定だが、ラベルを付ける
側は判定の1行目しか読まない（[`board-labels.yml`](../.github/workflows/board-labels.yml)）ので、
それが**今の頭へ `通してよい` として付く**——押された後のコミットを誰も読まないままマージされうる。
畳めば、次の周に今の差分の1本が立つ（2.12.4）。

**起こしても書かなければ、畳んで次の1本へ回す。** ワーカーの `RETURN` に当たる出口は持たない
——PRへ `判断待ち` を付けると「人が外すまでマージしない」という別の効き目が生まれる（2.13.2）。
**周期の係は起こさずに畳む**——渡す文面が無く、書かせたい出力もそもそも無い。

#### 2.10.4 後片付けも、マージした手からは切り離す

**ユーザーはPRをGitHubの画面からマージする。コマンドは打たない**（出どころ: ユーザーの指示・
2026-09-07）。だから**マージと同じ手で後片付けをすると、その回はどれも走らない**——2.10.1 が
ワーカーを畳む手で避けたのと同じ誤りで、避け方も同じ。**マージ済みのPRを見つけたら打つ**
（[`board-move.mjs`](../scripts/agent/board-move.mjs) の `TIDY`、打つ先は
[`tidy-merged-pr.sh`](../scripts/agent/tidy-merged-pr.sh)）ので、誰が入れても同じ1回を通る。

残りは [`merge-pr.sh`](../scripts/agent/merge-pr.sh) が持つ——関門（2.13.3）とマージだけ。

**相手はマージ済みPRの一覧で、窓は 48時間**（`board-read.mjs` の `MERGED_WINDOW_HOURS`）。
**1回だけにするのは台帳の覚え**（`tidy:<PR番号>`）で、**覚えを失っても壊れない**——打ち直しても
同じ結果になる形にしてある（下の 2.10.5）。**デーモンが窓より長く止まっていた間に入ったPRは
後片付けが走らない**ので、立て直すときに本体だけ [`daemon.sh`](../scripts/agent/daemon.sh) が寄せる。

#### 2.10.5 GitHub が肩代わりするもの

**ブランチの削除も、上に積まれたPRの base の張り替えも、盤面は打たない。** どちらもGitHub自身が
マージの時点で済ませる（2026-09-10 に、使い捨てのPRを素の squash でマージして確認した——
`delete_branch_on_merge` が真なのでブランチは数秒で消え、積まれていたPRには
`automatic_base_change_succeeded` が付いて base が下のPRの base へ移り、開いたまま残った）。
**画面からのマージでも同じ**なので、打ち直す先はもう無い。

**肩代わりされないのは、張り替わったPRを書いた本人へ差し戻すこと。** squash マージでは下のPRの
コミットが `main` の履歴に入らないので、**張り替わっても差分には下のぶんが混ざったまま**で、CIも
古い base で得た緑のまま。`直し待ち` を付けて理由をコメントで残すところまでが後片付けの仕事
（2.13.2 の `直し待ち` の出どころの1つ）。

**探すのは「そのブランチを base にした開いたPR」ではない。** 張り替えるのがGitHubなので、後片付け
が走る頃には base はもう `main` へ移っている。**張り替えの記録**（`oldBase`）がこのPRのブランチを
指しているものを引く。**押し返された後は差し戻さない**——記録は載せ直しても消えないので、
張り替えより後に押された先頭コミットが在るなら、もう本人が動いた後。

**`Closes #N` が閉じたかの確認は残す。** 閉じるのはGitHubだが、**閉じ損ねを見ている者が他に居ない。**

### 2.11 差し戻す相手をどう引くか

#### 2.11.1 セッションは自分で名乗り、コミットに残す【確定】

**出どころ**: ユーザーの指示・2026-09-05。

- **PRを出すセッションは、自分のIDを名乗る。** 本文の末尾にセッションのURLを置き、**コミットにも
  トレーラとして入れる**（綴りと引き方は 2.11.2）。どのセッションから出すPRにも掛かる（クラウドの
  ワーカーだけの慣習にしない）。**手元のブリッジも同じ形。**
- **差し戻す相手はトレーラで引く。** 本文は書き直した拍子に落ちるが、トレーラは残る。
- **`Closes` では引かない。** あれは**そのPRでどの issue が閉じるか**の印であって、誰が書いたかを
  指していない。同じ issue に複数のセッションが関わることも、issue を持たないPRもある。

#### 2.11.2 どう引くか

綴りは `Claude-Session: https://claude.ai/code/session_<ID>`。**手元のブリッジのIDもこの形で入る**
——作業ツリーの `bridge-cse_<ID>` と `session_<ID>` は接頭辞が違うだけの同じIDで、`list_sessions` にも
`environment_kind: bridge` として並ぶ（2026-09-05 に実測）。

盤面はPRごとに、**トレーラを持つ最後のコミット**を見る（手が変われば新しいほうが今の書き手）。
`gh api graphql` で末尾の何本かだけを指名して1回で引く——`gh pr list --json commits` は
PRごとに全コミットを取りに行き、GraphQL のノード数の上限を超えて何も返らない。

**引けなかった周は空にして進む。** 差し戻す相手が分からないだけで、他の手は打てる。

**名乗っていないPRは差し戻せない。** 盤面は覚え書きを残すだけで手を出さない——**規則の破れなので、
直すのは人**。覚え書きは「名乗っていない」と「畳まれている」を書き分ける（手を入れるべき側が違う）。

#### 2.11.3 引けない名乗りは機械で止める

[`tests.yml`](../.github/workflows/tests.yml) の `claimed` が、**盤面が引くのと同じ1つ**——トレーラを
持つ最後のコミットのID——を見て、**無いときも、実在のIDの形になっていないときも**CIを赤くする
（形そのものは `claimed` が持つ）。`bridge-cse_<ID>` から `cse_` を落とし損ねた `session_cse_…` は
この形に当たらない——在るかどうかだけを見ていた頃に通り抜け、PRに付いた却下が作者へ届かないまま
盤面が止まった（2026-09-11、PR #1922）。**促すだけにしないのは、書き忘れが既に実害を出しているから**
（[`policies.md`](policies.md)「仕組みの作り方」）。赤いPRは盤面がレビューへもマージへも出さないので、
**そこで止まる**——名乗り直して push すれば緑になって再開する。

**中身の誤りを見るジョブとは分ける。** 名乗り忘れは中身の話ではないので、直し方も直す人も別。

### 2.12 レビューへ回す前に、機械で弾く

#### 2.12.1 機械で判定できることは、レビュアーへ見せない【確定】

**出どころ**: ユーザーの指示・2026-09-05。

- **機械で判定できることは、レビュアーのセッションを1本使う手前で盤面が弾く。**
- **弾いたものは、[`review-criteria.md`](review-criteria.md) の観点からも消す。** 両方に置かない
  ——盤面が先に差し戻すので、レビュアーが読む番には既に直っている。
- 弾かれたPRは、他の差し戻しと同じ経路で書いた本人へ返る（2.11・2.6）。

#### 2.12.2 コンフリクトは3値で見る

`mergeable` は `MERGEABLE` / `CONFLICTING` / `UNKNOWN` の3値で、**`main` が動くたびに開いているPRが
全部 `UNKNOWN` へ落ち**、GitHub が計算し直すまでそのままになる。

**レビューへ出す条件は「`MERGEABLE` であること」。** `CONFLICTING` だけを弾く形にすると、
`UNKNOWN` の隙間に当たった周がコンフリクトしたままレビューへ出す——#1538 で実際に出ている
（枝は動いていないのに、コンフリクトの覚え書きが1周だけ消えた周でレビューへ出た。レビュアーの
1つめの指摘がそれになった）。`UNKNOWN` は次の周まで待つだけでよい。

#### 2.12.3 `## 見た目` の欠け

`src/game/**`・`src/assets/**` を触ったPRに `## 見た目` 節が要る（`CLAUDE.md`「PR本文に置く節」）。
**差分の置き場も本文も機械で読める**ので、盤面が見て差し戻す。節はあるが中身が空のものも同じ扱い。

**本文の節のうち、これだけを見る。** 他の節の欠けは入った後からでも補えるが、画面は誰も見返さない
ので**後から補えるものが差分に残らない**（4.3）。

#### 2.12.4 出したことは、読まれたことではない

同じ差分を二度レビューへ出さないための指紋（`taken['review:<PR>']`）が言えるのは、**その差分を
出したところまで。** 読み終えたかは言えない。**指紋の有無だけで次を止めると、判定を書かずに終わった
レビューがそのPRを永久に止める**——結論のラベルは付かず、指紋は残り続けるので、人が台帳を触るか
新しいコミットが載るまで誰も読みに来ない（issue #1569。2026-09-06 に PR #1573 が2度これで止まった）。

**先に訊くのは、判定のコメントが在るか**（2.10.3 と同じ照合）。在れば読み終わっていて、結論の
ラベルが付くのを待っているだけ。**読み手が居るかより先に訊く**——書き終えたレビューは畳まれてから
ラベルが付くまでの間、「居ないのにラベルも無い」形になる。

**書かれていないなら、読んでいる最中かを読み手が居るかで見る。** `review-<PR>` のタグを持つ
セッションが一覧に在れば読んでいる最中（手が止まっていても、道具の承認待ちかもしれない。1.6）。
**居なくなっていれば、その読みは終わっている**——判定が無いまま終わったのだから、もう一度出す。
畳まれた理由（盤面が畳んだ・人が畳んだ・落ちた）を問わないので、消え方ごとに条件を足さずに済む。

**繰り返し失敗する形は止めない。** 判定を書けないレビューが続けば同じPRへ何度も出ることになるが、
1本は畳まれるまで（2.10.3 の窓と、その手前の1回の起こし）残るので、出し直しはその間隔より速く
ならない。**止まったまま
気づかれないより、ログに繰り返しが出るほうがよい。**

### 2.13 人の手番と、そこからの出口

#### 2.13.1 ラベルを外す＝動いてもらう、自分で終わらせる＝閉じるかマージする【確定】

**出どころ**: ユーザーの指示・2026-09-07（issue #1707）。**覚えることを1つにする。**

| | ラベルを外す | 自分で終わらせる |
|---|---|---|
| issue の `判断待ち` | 答えを書いて外す → 配られる | **閉じる** |
| PRを止めている印（`判断待ち`・`収束せず`・`通してよい`） | 直してほしいことを書いて外す → **書いた本人へ差し戻る** | **画面からマージする** |

- **承認のためのラベルは無い。承認は画面からのマージそのもの。** 通してよいならマージすればよい
  だけで、そのためにラベルを1つ付けさせる理由が無い。`通してよい` はレビューが書いた事実であって、
  ユーザーの承認を表す道具ではない（1.3）。
- **打つ操作も無い。** 機械の関門（2.13.3）はデーモンのマージを止めるためのもので、**人が画面から
  入れるなら、その判断は定義上もう済んでいる**。マージの経路に、関門を越える引数は無い。
- **付けたのがレビュアーか機械かを、ユーザーが見分ける必要が無い**（2.13.3・2.13.4）。どちらでも
  することは同じ2つ。
- **`却下` を人が付けることも無くなった。** 外れたことを機械が `却下` へ訳す（2.2.1。**外れている
  状態では書けない**——外れていることと、最初から付いていないことが同じに見える。1.1）。
  **理由は写さない**——ユーザーが外す前に書いたコメントが、そのまま差し戻しの文面になる
  （[`resume-prompt.md`](resume-prompt.md)）。
- **人が外したのか、push で機械が外したのかを分ける。** 分けないと、**直して push した本人がその
  push で差し戻される**輪になる。見分け方は 2.2.1。
- **人の手番に入る印を、判断の要らないところへ付けない。** 外す作業が要るぶん、付けた数だけタップが
  増える。

**以前の形は「出口は付けるだけ」だった**（出どころ: ユーザーの指示・2026-09-05）。**人が外す作業を
作らない**ために入口の印は機械が始末していたが、**issue の `判断待ち` だけは前から「外す」が出口**
だったので、PRと issue で同じラベルの外し方が違う意味を持ち、**ユーザーが手順を覚えられなかった。**

#### 2.13.2 効き目を1つずつに割る

| 入口 | 何を止めるか | 出口 |
|---|---|---|
| `判断待ち`（PR） | **マージだけ。** 差し戻しもレビューも止めない | 2.13.1（外す＝差し戻し／画面からマージ） |
| `判断待ち`（issue） | **投入だけ**（2.15） | ラベルを外す。**答えの置き場は入口で決まる**——返却で付いたものはコメントへ、周期の係が付けたものは本文のチェックへ（2.17.2） |
| `収束せず` | **レビューだけ。** 差し戻しもマージも止めない | 2.13.1 |

**どちらの下でも差し戻しは出る。** コンフリクトもCIの赤も人の判断と関わらないので、返事を待つ
理由が無い。`収束せず` を付けるときに `直し待ち` を一緒に外すのは、**人が答える前に次の周が
走らないようにする**ため——止めるのはレビューの1つだけ、を保つ。

**外す先が1つずつなのは、止めている理由が1つずつだから。** `判断待ち` と `収束せず` が並んだPRで
片方だけ外しても `却下` は付く——差し戻しは止まらないので、残ったほうは次の差分で外れる。

#### 2.13.3 機械が付けるPRの `判断待ち` は導出される事実

**issue の側は違う**（2.15）——返したことを知っているのはワーカーだけなので、あちらは宣言で付く。
ここはPRの話。`needs-user-review.sh` が差分から出すので、[`merge-pr.sh`](../scripts/agent/merge-pr.sh)
が**マージを試みるたびに付け直す**。だから push で外してよい（1.1）。副作用として、`通してよい` が
付いたままの push では**盤面がマージを1回試みて `HELD` で跳ね返され、そこで付き直る**——ログに
`HELD` が1行増えるが、状態を溜めずに毎回導出する側を採る。

**人が外したときも、同じ形で付き直りうる**——`却下` が付くまでの窓に周が1つ入ると、そこで打った
`MERGE` が `HELD` で跳ね返る（2.13.5）。**入らないことは変わらない**ので、「外して待っても入らない」
という以前の落とし穴は、外すことが承認ではなくなったことで消えている。

**機械が出すのは `【確定】` の印の増減だけ。** ここは誤検知が構造的に無い——印は「覆すには人間の
判断が要る」の宣言そのものなので、ユーザー以外がそれを増やしたこと自体が、定義上ユーザーの判断を
要する。**残りは 2.13.4。**

#### 2.13.4 人の判断が要るかは、レビュアーが判定する

**差分を読まないと決められないことを、差分を読まない機械が決めない。** 宣言文法・スキーマ・
ゲームコンセプト・確定節に抵触するかは、差分を読むレビュアーが判定する
（[`review-criteria.md`](review-criteria.md)「人の判断へ回す」）。**止める観点ではない**——結論は
`通してよい` のままで、変わるのは「人へ回すか」だけ。判定の3つ目の形がこれ。

```
[レビュー] 通してよい（人の判断が要る）
```

[`board-labels.yml`](../.github/workflows/board-labels.yml) が `通してよい` と `判断待ち` を付け、
マージだけが止まる（2.13.2）。**何を判断してほしいかはコメントの本体に書かせる**ので、ユーザーは
リポジトリを開かずに答えられる。**答え方は機械が付けたものと同じ**——通すなら画面からマージ、
通さないならラベルを外す（2.13.1）。

**ファイルの線で引いていたときは、止めた理由とPR本文の `## 仮決め` の中身が一致しなかった。**
スキーマの `description` を変えただけの差分と文法を足した差分が同じに見えるので、通すかを決める側は
「何を判断すればよいのか」を読み取れない。**区別できるのは差分を読む者だけ。**

**このラベルは機械が付け直さない。** 2.13.3 と違って、**次の周のレビューが同じことを言わなければ
付かない。** 出どころが違っても、ユーザーがすることは 2.13.1 の2つで同じ。**ラベルが外れても
マージが止まったままなのは、盤面が判定のコメントから読み直すから**（2.13.5）。

**周ごとに判定は変わりうる。** レビューは周ごとに別セッションで、2周目以降は前の周以降の差分だけを
見る（4.5.1）。1周目が「人の判断が要る」と言い、2周目が言わなければ、push でラベルが外れたまま
通る——**これは正しい振る舞い。** 差分が変われば、人へ回す理由も無くなりうる。

**この形も1周として数える**（4.6）。数え方から漏らすと、3周で人へ上げる勘定が狂う。**判定の
見分け方を持つのは [`review-verdicts.mjs`](../scripts/agent/review-verdicts.mjs)** と、node を持ち
込めない Actions の側（`board-labels.yml`）の2つで、**揃っていることが要る**（2.9）。

#### 2.13.5 外れた瞬間と、`却下` が付く瞬間はずれる

**人がラベルを外してから [`board-labels.yml`](../.github/workflows/board-labels.yml) が `却下` を
付けるまでには、Actions のキューとランナーの起動ぶんの間がある。** 一方デーモンは既定30秒ごとに
盤面を引き直す（[`daemon.sh`](../scripts/agent/daemon.sh)）ので、**この窓に周が1つ入るのは例外では
ない。** 窓の中の盤面には、そのPRが「止める印が何も無いPR」に見える。

**だから盤面は、結論をラベルだけで読まない。** レビューの判定はコメントに残り、そこには読んだ版が
書いてある（[`review-prompt.md`](review-prompt.md)）——**今の版への判定が在るなら、人がラベルを
外していても判定は消えていない。** ラベルは 1.1 の「外れている状態は書けない」に当たるが、
**コメントは外されない側**なので、そちらから読む（[`board-move.mjs`](../scripts/agent/board-move.mjs)
の `verdictOn`）。

- **今の版の判定が `通してよい（人の判断が要る）` なら、マージを出さない**（2.13.4）。ここをラベル
  だけで見ていると、**差し戻すつもりで外した操作がそのままマージになる**——取り消せない。
- **今の版への判定が在れば、レビューを出さない。** ラベルだけで見ていると、読み終えた差分へ
  もう1本立つ（`収束せず` や `通してよい` を外した窓がこれ）。

**読んだ版の名乗りは書き忘れうる**（`review-prompt.md`）ので、**どの版のものか言えない判定を数えるか
は、訊く側の倒れる先で決める。** 止める側は数える——数えないと、**名乗りを書き忘れた周だけ、人へ
回した判定が消えて取り消せないマージになる**（ラベルを付ける側は1行目しか読まないので、名乗りが
無くても `判断待ち` は付く）。読まれたかを見る側は数えない——数えると、押した後の差分が二度と
読まれない。**同じ「名乗りが無い」を、両方が安全な側へ倒す。**

**マージを出す条件は `通してよい` のラベルのまま。** 判定から導出し直すと、**マージを止めるために
外した `通してよい` が効かなくなる**——導出してよいのは「止める側」だけ。

**機械の関門（2.13.3）だけは、窓に入った周が `MERGE` を打ちうる。** 打っても
[`merge-pr.sh`](../scripts/agent/merge-pr.sh) が `HELD` で跳ね返すので**マージはされない**が、
そこで `判断待ち` が付き直る。**差し戻しは `却下` が付いた次の周に届く**ので止まりはしない
——関門の判定は差分を丸ごと読む仕事なので、盤面が毎周やり直す形にはできない。

### 2.14 `main` が赤い間の差し戻し

#### 2.14.1 `main` が赤い間は差し戻さない【確定】

**出どころ**: ユーザーの指示・2026-09-05。

`main` が赤いと、それを取り込んだPRは**作業者が何をしても緑にならない**。押し返されるたびに新しい手
として通るので、**直せないものを直させ続ける輪**になる。2026-09-05 に `main` の試験が Linux でだけ
落ち、手綱で止めるまで実際にそうなった。

**盤面は `main` の先頭のCIを見て、赤なら差し戻しを止める。**

#### 2.14.2 止める範囲

**2.14.1 の輪が回るのは、差し戻しの指紋が `headRefOid` だから。**

引くのは `gh api repos/{owner}/{repo}/commits/main/check-runs`。語彙をPRの `statusCheckRollup` に
合わせて渡すので、色を決める判定は1つで足りる。

- **止めるのは `mend` だけ。** `reject`（人が差し戻した）と `look`（画面の証跡）は**出た理由が
  `main` の色と関わらない**ので出す——緑になるのを待っても手の中身は変わらず、押し返されても印は
  付き直らない（どちらも push で外れる）ので、輪にならない。
- **止めるのは、赤と分かったときだけ。** 走っている最中まで含めると、`main` へ push が入るたびに
  差し戻しが数分止まる。
- **`main` が赤い間、盤面は元から進まない。** レビューもマージも緑を条件にしているので、ここで
  失うのは「直せない直しを頼む手」だけ。

### 2.15 仕事を人へ返す

#### 2.15.1 タスクのセッションは、人へ問いかけない【確定】

**出どころ**: ユーザーの指示・2026-09-05。

**ユーザーは task のセッションを見ない。** 問いを投げた側は答えを待って止まり、枠を握ったまま
無限に待つ。決まっていない箇所は仮決めして進むのが既定なので（[`policies.md`](policies.md)）、
**問いかけずに済まないのは、仮決めそのものができないときだけ。** そのときは**仕事を issue へ
返して終わる**——待つのではなく、手放す。

#### 2.15.2 返すのは issue のコメントの1行目

`task-1376` は問いかけてはおらず、issue へ正しく報告して終わっていた。**欠けていたのは、返した
ことを機械が読める形と、盤面が枠を取り返す道。** 起こす手（`stall`）は指紋が issue 番号だけなので
1回しか出ず、その後の受け皿が無かった。

**判定はPRの有無では行わない。** PRが出ていないことは「忙しい」とも読める——書き始めたばかりの
セッションと、詰まって止まったセッションを、外から見て区別できない。**返したことは、返した本人に
しか言えない。**

形はレビューの結論と同じで、**issue のコメントの1行目**。

```
[返却] <なぜ返すか。1行>

（詳細）
```

**1行目は前方一致で見る。** レビューの結論は選択肢が閉じているので綴りちょうどで見分けられるが、
返す理由は閉じていない——残りがそのまま要約になる。読むのは
[`board-labels.yml`](../.github/workflows/board-labels.yml) で、付けるのは `判断待ち`（1.3）。

**分類（`kind:`）は動かさない。** 軸が違ううえ（2.17.1）、外すと戻すのに2タップ要り、外した issue は
未整理として棚卸しへ戻る。人は `判断待ち` を1つ外せば列へ戻せる（2.13.1）。**配らない判定を持つのは投入する側**
（1.4、[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh)）で、盤面の側にあるのはその写し。

**ルールを守らないワーカーは居る。** それはレビュアーについても同じことなので、受け入れる
（出どころ: ユーザーの指示・2026-09-05）。守らなかったぶんは次の 2.15.3 が拾う。

#### 2.15.3 起こしても動かないものは、盤面が返す

宣言も無いまま止まったセッションは、**1回起こして、それでも何も出てこなければ盤面が返す**。

- 入口は「**手が空いたままで**、担当の issue が開いていて、PRが出ていない」（2.6）。
- **「手が空いている」ことそのものは停滞ではない。** ワーカーは手番の切れ目ごとに空き、下請けの
  レビューを待つ間も空いて見える（1.6）。**空いたまま `STALL_MINUTES` 続いて初めて**起こす。
- 起こした後も、**同じ長さの窓をもう1つ空けてから返す。** 起こされたセッションが動き出すには時間が
  要るので、次の周（既定30秒）で見限ると、届いた合図が効く前に必ず返すことになる。
- **動き出したら、空いた時刻の覚えも「起こしたが動かなかった」の記録も捨てる**
  （[`board-round.mjs`](../scripts/agent/board-round.mjs) の `trackIdle`）。動いた時点でどちらも嘘に
  なり、残すと**次に空いた瞬間に、起こす手順を飛ばして人へ返す**。
- **覚えが無いときは何もしない。** 台帳が消えた直後もそう見えるので、動かない側へ倒す——ここで打つ
  手はどちらも取り返しが付かない。
- 手は `RESUME … stall` → `RETURN`。**セッションが持つ指紋の枠は1つ**なので、
  `stall:<番号>` → `returned:<番号>` と進めば、どちらの手も二度は出ない。

**この節は 2026-09-06 に書き直した。** それまでは「空いている」を1度見ただけで起こし、その次の周
（35秒後）に返していたので、**下請けのレビューを待っていたワーカーが、押し切る寸前に人へ返されて
畳まれた**（issue #1506。最後の要約は `subagent code review running (2m); staging ready to push`）。

**レビューを畳む側（2.10.3）も、判定がまだ無い間は同じ窓を通る。** 「走り終わった」と「道具の
承認を待っている」は `list_sessions` から同じ形に見えるので（1.6）、30秒で畳むと**判定を書く前の
レビューが消え、そのPRが永久に止まる**（[PR #1573](https://github.com/gooyyu1/UnmappedIsland/pull/1573)
が実際に止まった。要約は `Waiting on permission: Bash`。[issue #1569](https://github.com/gooyyu1/UnmappedIsland/issues/1569)）。
**判定を書き終えたら窓は要らない**——終わったことがPRのコメントから言えるので、そちらで畳む（2.10.3）。
**窓が満ちた後も、レビューは畳む前に1回だけ起こす**（2.10.3）。返す先が無いので、ワーカーの
`RETURN` に当たる段は持たない。
- **盤面もコメントで返す。** ラベルを直に付けない——返る道が2つに割れると、片方だけが直った
  ときに気づけない。理由の行には「起こしても手が動かなかった」と書くので、**人には宣言が
  無かったことも伝わる。**
- 返された issue を担当していたワーカーは、次の周に畳まれる（2.10。指紋は `returned:<番号>`）。

### 2.16 どこで走らせるかは、issue に書いてある

**投入先はクラウドとブリッジで、既定はクラウド。** `env:<値>` のラベルが付いていれば、そこが
指す先へ投入する（`env:bridge` → [`dispatch-task.sh`](../scripts/agent/dispatch-task.sh) の
`--bridge`）。

**触れる範囲では分けない。** クラウドのセッションも `.claude/**` を書き換えられる（2.16.3 のモードで
承認が要らなくなる）ので、**どこまで触ってよいかは、どちらで走っても同じ。**
`env:bridge` が要るのは、**クラウドではできない仕事**——手元の画面やローカルにしか無いものを使う
——と、走ってみて承認で詰まった仕事（2.16.2）。**GitHub を触ることは理由にならない**——既存 issue の
本文もラベルも、クラウドから用意された道具で書き換えられる（2026-09-06 に実測。`gh` と生の REST は
確かに無いが、MCP の道具は通る）。

**だから渡す指示も投入先で変えない。** 受け取る側は自分がどちらで走っているかを知らないので、
場所で切った制約を混ぜると、当たらないほうへも渡る（`.claude/**` を触るなと書いた行が、そこを直す
ために立てたブリッジのセッションへ届き、**着手した時点で仕事をせずに返した**）。
[`dispatch-prompt.md`](dispatch-prompt.md) は1つの文面だけを持つ。

**投入先で変わるのは、`source_url` と承認モード**（2.16.3）だけ。

#### 2.16.1 知らない `env:` は配らない

**盤面が宛先を知っている値の一覧は [`board-move.mjs`](../scripts/agent/board-move.mjs) にある**
（`DISPATCH_TO`）。**GitHub にラベルが在るかとは別**——人は盤面の知らない `env:*` を作れるので、
ラベルの存在では「配ってよい」を言えない。

知らない値と、`env:` が重ねて付いた issue は**配らずに覚え書きを出す**。既定のクラウドへ落とすと、
**そこでしかできないから宛先を書いた仕事が黙って別の場所で走り、指定が無視されたことが誰にも
残らない。**

#### 2.16.2 クラウドのセッションは、自分をブリッジへ回せる

**気づけるのは走ってみた側だけ**——承認で拒否されて進めない、そのPCでしか確かめられない、と
分かるのは作業を始めた後になる。issue へ `[ブリッジ] <なぜブリッジが要るか。1行で>` をコメントすると、
[`board-labels.yml`](../.github/workflows/board-labels.yml) が `env:bridge` を付ける。

**ラベルを直に付けさせない。** 付けるだけならクラウドからも通るが、**ラベルは事実しか持たない**
（1.3）ので、**なぜブリッジが要るのかがどこにも残らない。** 名乗らせれば理由が issue に残る。
訳す形は 2.15.2 と同じ。

**配り直すのは盤面。** ラベルが付いただけでは、担当していたワーカーが `task-<番号>` を持ったまま
生きているので、issue は配る側の一覧に戻らない。**クラウドで走っているワーカーの担当が、クラウド
以外を要求するようになったら畳む**（2.10.2。指紋は `moved:<番号>`）——空いた枠へ、次の周が正しい先で
立て直す。

**逆向き（ブリッジのワーカー）は動かさない。** `env:` の付かない issue をブリッジで走らせる形は
実在する（手元からの投入）ので、**既定の `cloud` との食い違いがそのまま当たり**、手元で
走っているワーカーが片端から畳まれてクラウドへ立て直される。

**知らないことを「違う」として読まない。** 環境を引けなかったセッション（`-`）と、配り直す先が
無い issue（知らない `env:` ・`env:` の重なり）は動かさない。**畳んだところで次の周は投入で
止まる**ので、枠を空ける意味が無い。

**PRを出した後のワーカーも動かさない。** 配り直しても投入する側が既に開いているPRを見て止めるが、
**畳んだぶん、そのPRの直しを頼む相手が居なくなる**（2.11）。ここが `closed` や `returned` と違うのは、
**あちらは仕事が終わっている**——直しを頼む先が要らない。

#### 2.16.3 承認モードは環境が決める

**出どころ**: ユーザーの指示・2026-09-06。**投入する側は選ばない。** どちらへ立てるかを決めれば
一緒に決まるので、置き場は環境IDと同じ [`ccr-env.sh`](../scripts/agent/ccr-env.sh)。

**渡さなければ、投入先ごとに違うモードで立つ。** 書けるのは観測だけで、**そうなる理由は突き止めて
いない**——`.claude/settings.json`（`defaultMode: bypassPermissions`）はリポジトリに追跡されていて
クラウドの箱にも入るので、設定ファイルの有無では説明が付かない。

| 投入先 | `permission_mode` | 渡さないと何が起きるか |
|---|---|---|
| クラウド | `auto` | `.claude/**` を**読むだけ**の `bash` が「機微なファイルの編集」と判定されて承認を待ち、**その承認は降りない** |
| ブリッジ | **渡さない** | `.claude/**` の読み書きが承認なしで通る（2026-09-06 に実測。`permission_denials` が空） |

**実効モードは `get_session` から読めない。** 渡さなかったセッションは、手番を回した後も
`permission_mode` が `null` のまま返る。確かめるなら実際に何かを叩かせて `permission_denials` を
見る——**手番を一度も回していないセッションは、渡していても手動に見える。**

**`bypassPermissions` だけは明示できない。** この経路には呼び元のセッションが無く、
`requires a CCR parent session` で撥ねられる。撥ねられるのはこの値だけで、以前の
「`permission_mode` は渡さない」は1件の失敗を全部の値へ広げたものだった（2026-09-06 に叩き直して
確かめた）。渡さなかった間はクラウドのセッションもこの表の上段のまま走っており、2026-09-05 に
PR #1567 のレビューが判定を書く前にこれで止まった。

**明示すると `config:headless-lineage` のタグが自動で付く。** 盤面がタグを見るのはどれも部分集合の
照合（`task-` / `review-` / `chore-` で始まるものが在るか）なので、混ざっても判定は変わらない。

### 2.17 周期で起きる係

人が投入しなくても、仕事があれば間隔を空けて自分で立つセッション（出どころ: ユーザーの指示・
2026-09-06）。**どの係が居るかは表**（[`board-move.mjs`](../scripts/agent/board-move.mjs) の
`CYCLES`）**が持つ**ので、ここには書き写さない。

**デーモンを起こす係だけは、この枠に載せない**（2.19）——表を回すのがデーモン自身なので、載せると
落ちたときに立たない。

**特別な手を係ごとに作らない。** 盤面が持つのは表1つ（[`board-move.mjs`](../scripts/agent/board-move.mjs)
の `CYCLES`）と手1つ（`CHORE`）で、係を足すときに書くのは**表の1行と渡すプロンプト**だけ。

| 持つもの | 何を決めるか |
|---|---|
| `due` | 今この係に仕事があるか（**渡すのは盤面ごと**——仕事の在り処は係で違う）。**無ければ間隔が満ちても立てない** |
| `hours` | 前に立ててから空ける間隔 |
| `env` | 投入先（2.16 の `env:` と同じ値） |
| `prompt` | 渡す本文の在り処 |

**係は錠（`area:`）を取らない。** 資源を取り合うのは担当の issue を持つセッションどうしだけで、
**間隔で立つ係をその取り合いに混ぜない**——待たされる先が、まさにその係に見てほしい詰まりである
ことがある（2.21.3 が実例）。**取らせたい係が出てきたら、そのときに `locks` を戻す**——今は
持つ係が居ないので、仕組みごと落としてある。

**PRを出す係が居ても、作業者の枠（3.1 の上限。どちらも）には数えない。** 間隔を空けて立つ係の、
記録だけの差分なので、マージの列を詰まらせない。数えると、書く側の並列度がその分だけ黙って下がる。

**ただし、PRを出した係は、そのPRが開いている間は畳まない。** 畳むと**指摘とコンフリクトを直す相手が
消える**——差し戻す先はコミットのトレーラで引く1本だけ（2.11）。**次の周期はそれでも立つ**
（下の「終わっているか」で見るため）ので、直しを待つ1本が周期を塞ぐことはない。

**次の1本を止めるのは「生きているか」ではなく「終わっているか」**——走っているか、手が止まってから
`STALL_MINUTES` に届いていないか（1.6・2.10.3 と同じ窓）。**畳む手が出るのは次の周**なので、
生きているかで見ると、終わった1本が畳まれるまでのあいだ次の周期を塞ぐ。

**引き金は件数ではなく時間**（出どころ: ユーザーの指示・2026-09-06）。まとめて捌きたいので溜めたい
が、**1件のまま来ない日が続くと放置される**。件数のしきい値は「そこまでは残ってよい」を宣言する
ことになり、滞留を仕様にしてしまう（2.18）。

**前に立てた時刻は台帳（`taken.json`）の `cycle:<名>` に控える。** 盤面の何かに紐づく指紋ではない
ので、[`board-round.mjs`](../scripts/agent/board-round.mjs) の掃除からは外れる。**デーモンを別のPCへ
移すと覚えごと消える**ので、移した直後は係が一斉に立つ。

#### 2.17.1 分類は `kind:` の1軸で、配ってよいかとは別【確定】

**出どころ**: ユーザーの指示・2026-09-06。

**棚卸しが出す結論は `kind:` のラベル1つ**——1セッションで片付く作業単位（`kind:task`）か、投入する
先が無い常設の盤（値は 2.17.5）か。**未整理とは、open で `kind:` を1つも持たないこと。**

**「もうやる必要が無い」は分類ではない。** それは *task ではなくなった* のではなく *task だが、
もう要らないと思う、と人へ返した* 状態なので、置き場は**配ってよいかの軸**（`判断待ち`。2.15）。

**`kind:` を付けるのも、順序を張るかどうかを決めるのも棚卸し。`判断待ち` は付けない。**（順序を
どう表すかは 2.17.3。）

#### 2.17.2 答えが要る係は、チェックボックスの issue で受ける

**価値観を畳む係**（[`policy-cycle-prompt.md`](policy-cycle-prompt.md)）の成果は、
[`policies.md`](policies.md) をはじめとする方針の文書へ入り、**以後の全セッションの既定になる。**
どれを既定へ上げるか・どう一般化するかはユーザーにしか決められないが、**周期の係には訊く先が
無い**（2.15.1）。

そこで**答えを issue のチェックで受ける**（出どころ: ユーザーの指示・2026-09-06）。

| 誰が | 何をするか |
|---|---|
| 周期の係 | 候補を並べた issue を1本、`判断待ち` を付けて起票する。リポジトリは書き換えない |
| ユーザー | 通す候補にチェックを付け、`判断待ち` を外す |
| 配られた task | チェックの付いた候補だけを反映し、出どころの履歴を `archive/` へ移す |

**出す係と反映する task を1本に混ぜない。** 混ぜると、諾否を待つ間セッションが止まる。分ければ
前者は候補を出すまで、後者はチェックを読んで書くだけで、**どちらも仕事が1つに絞れる。**

**この口は、答えが要る周期の係が共通で使う。** 掘り起こす係（[`dig-prompt.md`](dig-prompt.md)）が
「やるかどうかから訊くもの」を出す先も同じで、**確定待ちの盤（#656）へは積まない**——既にある
issue の本文を書き換えるのは棚卸しだけ（2.17.1）で、周期の係が書くのは自分で立てた issue に限る。

**チェックの付かなかった候補も `archive/` へ落とす**（見送った印を付けて。
[`policy-review` skill](skills/policy-review/SKILL.md) 手順4）。落とさないと、次の周が同じ候補を
もう一度出す。

**仕事の在り処はリポジトリの中**（`.claude/decisions/` のうち `archive/` に入っていないもの）で、
issue にもPRにも現れない。**盤面が GitHub と CCR の外を見るのは、ここと分析の記録（2.17.4）の
2箇所だけ**（[`board-read.mjs`](../scripts/agent/board-read.mjs)）。

**二重に起票させない手は2つ要る。** 間隔（`hours`）だけだと、**答えが返らないまま間隔が満ちた週に
2本目が立つ**——候補が2つ並ぶと、どちらを反映しても残りが嘘になる。もう1つは係自身が持つ
——立った直後に、自分が前に出した issue が開いていないかを題で探し、在れば何もせずに終える。
**盤面には持たせられない**（見るのは題で、盤面が引く issue の項目に題は無い）。

#### 2.17.3 分類をどう表し、どう付けるか

2.17.1 から導いたもので、覆すのに人間の判断は要らない。

- **未整理を、分類の値を数え上げた否定の列挙では表さない。** 出口が増えるたびに条件を
  書き換えることになり、書き忘れた出口の issue が毎周また拾われる。**整理済みの印を分類とは別に足す形も
  採らない**——2つのラベルが暗黙に一致すべき規約になり、片方だけ付いた issue が作れる。
- **常設の盤は、本文を機械がどう扱うかで値が分かれる**（下の 2.17.5）。
- **無効と読んだ issue にも `kind:task` を付ける。** そのうえで `[返却]` のコメントを1つ置き、
  そこから先は 2.15.2 と同じ道を通る。
- **`判断待ち` を付けないのは、分類が済んだ issue をそのまま配れる状態にするため**（2.13.1）。
- **`blockedBy` を張るかどうかは棚卸しが判断するが、推定はしない**——材料は、立てたセッションが
  本文へ書いた申告だけ（[`parallel-work.md`](parallel-work.md)「順序は issue の本文で申告し、
  棚卸しが決める」）。未整理の issue は必ずここを通るので、**分類と同じ1周で決められる。**
- **`判断待ち` を自分で付ける係が居る**（2.17.2・2.22.3）。付けるのは**自分が今から立てる issue** に
  対してだけで、既に在る issue へ付ける道は返却のコメント（2.15）とユーザー自身の手のまま。
- **棚卸しもクラウドで立つ**（2.16。出どころ: ユーザーの指示・2026-09-06）。分類も、本文の書き換えも、
  用意された道具で通る。**ブリッジはユーザーのPCを占める枠**なので、要らない仕事を置くと並列度が
  その分だけ下がる。
- **順序（`blockedBy`）だけは、棚卸しがコメントで名乗り、[`board-labels.yml`](../.github/workflows/board-labels.yml)
  が張る**（2.16.2 と同じ経路。1行目が `[順序] #<先に要るほう> の後`）。**クラウドのセッションには
  依存の API を叩く道具が無い**うえ、経路を1つにしておけば**どこで走っても同じ手**になる（2.16）。
  **張るかどうかの判断は棚卸しに残る**——ワークフローは決まったことを打つだけで、申告を自分で
  読みには行かない。
  名乗りの経路へ「コメントに書かれた綴りをラベルにする」を足さないのは別の話で、**選択肢が
  閉じていること**があの経路の安全そのものだから。`[順序]` が渡すのは issue の番号で、実在しなければ
  GitHub が拒む——綴りが増えるわけではない。

#### 2.17.4 分析は二段。一次は過去の回で傾向を探さない

**出どころ**: ユーザーの指示・2026-09-07。

**一次**（[`analysis-prompt.md`](analysis-prompt.md)）は**その回の帯だけ**を読み、その帯の中で
繰り返し現れた形を書く。**二次**（[`analysis-trend-prompt.md`](analysis-trend-prompt.md)）は
**一次が書いた記録だけ**を横断して読み、複数の回に現れている形に根本対策を打つか決める。

**分ける理由は、回をまたぐ数を一次が畳んでしまわないこと。** 一次は1つの帯しか見ないので、その形が
何回の帯にまたがって出たかを原理的に知らない。**同じ形が別々の回に独立して現れたこと自体が、根本
対策を打つべきかの根拠**なので、一次に過去へ足しに行かせると、その回数が消える。**重複は無駄では
なく、二次の入力。**

導いたもの（覆すのに人間の判断は要らない）。

- **禁じているのは、過去の回で傾向を探すこと。** **その回の帯のスメルが過去の記録の行を名指して
  いたら、一次はそのファイルを開いて現物と突き合わせる**——一次のPRにもスメルは付くので、確かめる手が
  他に無いこの形は帯が回るたびに現れる（#1830・#1838）。開かずに切れば、確かめていない指摘を issue へ
  写すだけの係になる。**開いた範囲は記録の `## 開いた過去の記録` に残す**——その回の帯に出ていない形が
  混ざっていないかを、回を数える二次が確かめられる。**過去の記録そのものは直さない**（当時の観測で、
  書き換える先ではない）ので、手を打つなら issue で、直す先はその記録を書かせた定めのほう。
- **形の見出しを回どうしで揃えさせない。** 同じ形かの判定は二次が読んで下すので、見出しの一致では
  引かない。揃える責任を一次に負わせると、結局は過去の `## 傾向` を読ませることになる。**記録そのものの節**
  （`## 読んだ範囲` など）は別で、どの回も同じ名前で置く——回をまたいで読む側が名前で引く。
- **書く先を分ける。** 一次は `.claude/analysis/<日付>.md`、二次は `.claude/analysis/summary/<日付>.md`。
  二次は一次のファイルを書き換えない——同じファイルを両方が書くと、どちらの観測かが読めなくなる。
- **二次の出口は issue と記録の2つだけ。** 方針の文書（[`policies.md`](policies.md) など）へ畳むのは
  価値観を畳む係（[`policy-cycle-prompt.md`](policy-cycle-prompt.md)）の仕事で、役が重なる。
- **二次の `due` は「二次が最後に書いた日付より後の一次の記録が在るか」。** 一次のファイルに処理済み
  の印を持たせない——持たせると、一次に二次の都合が入る。日付はどちらのファイル名も先頭に持つので、
  文字列の大小がそのまま前後になる（[`board-read.mjs`](../scripts/agent/board-read.mjs)）。
- **帯が連続しているかを見るのも二次。** 一次は自分の回の帯しか見ないので、**前の回との間にPRが
  落ちたことは、回を並べて見る側にしか分からない**（落ちた帯のスメルには 👀 が付かず、誰も読んで
  いない）。一次から過去を読む力を外した以上、この役は二次が持つほかない。

#### 2.17.5 常設の盤は、本文を機械がどう扱うかで分ける

**出どころ**: ユーザーの指示・2026-09-07（[`decisions/`](decisions/2026-09-07-rename-the-label-whose-name-hides-what-machines-read.md)）。

> ただ、kind:meta ラベルでは機械がチェックボックスを読んでいるとは想像できないので、kind:meta の
> リネームとセットだと思います

**常設の盤の本文には、機械が読むものと読まないものがある。** ユーザーの答えを拾う側
（[`checked-items.sh`](../scripts/agent/checked-items.sh)）は、**どれを拾ってよいかを分類の値だけで
決める**ので、兼ねさせると、投入の手綱（2.4）のような**下ろす者の居ないチェック**が `## 確定待ち` に
居座り、盤面の書き出し先（2.20）に至っては**デーモンが自分の書いたものをユーザーの答えとして読む。**

| 値 | 本文のチェック | 機械 |
|---|---|---|
| `kind:ask` | 人が付ける**答え**。拾われたら項目ごと消える | `checked-items.sh` が拾い、`## 確定待ち` に出す |
| `kind:switch` | 人が付ける**設定**。誰も下ろさない | [`brake.sh`](../scripts/agent/brake.sh) が毎周読む |
| `kind:board` | 機械は本文を読まない | 書くほうはある（`kind:board` の #1714 を 2.20 が書き換える） |

**分け目は「誰が書き、誰が読むか」**——2.20 が投入の手綱と盤面を別の issue にしたのと同じ軸で、
分類のラベルもそこで割る。**兼ねさせない理由は、拾う側が名前で見分けられないこと。** 拾うか拾わない
かを issue の番号で持てば、盤が1つ増えるたびに、書き足し忘れたものが既定で拾われる側へ落ちる。

**ラベルの名前が、機械の扱いをそのまま名乗る。** 名乗らない名前は、**拾っていることを誰も想像
できない**ぶん、壊れても壊れたことが見えない。

### 2.18 順位は印1つで、効き目は配る順だけ

配る順は古い番号からで、**急ぐものを先に出す手が無かった**（出どころ: ユーザーの指示・2026-09-06）。
無いと、急ぎの1件は人が手で運ぶことになる——**急ぐものは1件ではない**ので、そのたびに運ぶ手が要る。

**`急ぎ` の付いた `kind:task` が先に投入される**（1.3）。**効くのはそこだけ。** 枠
（[`board-move.mjs`](../scripts/agent/board-move.mjs) の `HELD_TASKS`・`ACTIVE_WORKERS`）は増えず、
錠（`area:`）も手綱も越えない。**`判断待ち` の issue は `急ぎ` でも配らない**——順を変えることと、配ってよいかを変える
ことは別（1.3 の「1つのラベルに効き目を1つだけ」）。

**順位を数で持たない。** `急ぎ` を**付けすぎても壊れない**——全部に付けば「古いものから」に戻る
だけで、**壊れる先が安全側に限られる**。数値の順位は、付ける側が他の issue の順位を知っていないと
決められず、知らないまま付けた値どうしが黙って競る。

**付けるのはユーザーと棚卸し**（`area:` と同じ。棚卸しへ渡す条件は
[`triage-prompt.md`](triage-prompt.md)）。**剥がす作業は要らない**——急いだ issue は
片付いて閉じるので、印は issue ごと消える。

**溜まると困るものを合図として出すときは、件数のしきい値を置かず、1件でも出す。** 抑えるのは
ここの順位でやる。しきい値は「そこまでは残ってよい」と宣言することになり、**滞留を仕様にしてしまう。**

#### 2.18.1 向かう先は、立てた本人が名乗る

**盤面が飢えているかは、在庫の数ではなく組成で見る**（出どころ: ユーザーの指示・2026-09-11）。

掘り起こす係（2.17・[`dig-prompt.md`](dig-prompt.md)）の出番は「**配れる task が尽きた周**」だった。
ところが**スメルを拾う係（4.4）の入力は、PRが出るたびに生える**——作れば作るほど入力が増えるので、
整備の issue が毎日積まれ、**在庫は二度と尽きない。** 掘り起こす係は立てられなくなり、完成の定義に
照らした残りは誰にも数えられないまま止まった。**仕組みの排気がタンクを満たし、ゲージは満タンを
指し続ける。**

2026-09-11 時点で、配れる `kind:task` 46件のうち**完成の定義へ向かうものは7件**だった。

**そこで、向かう先を状態の側へ置く**（[`policies.md`](policies.md)「仕組みの作り方」——動く前に
見るべき区別を、状態の側へ足す）。`goal:` のラベル1つで、**立てた本人が起票のときに付ける**
——向かう先を知っているのは立てた側だけで、後から残った状態を見ても引けない
（同[「理由の持たせ方」](policies.md)——起こした側にその場で名乗らせる）。

| 印 | 何へ向かうか |
|---|---|
| `goal:game` | 完成の定義を1つ埋める（世界の中身・遊びの仕組み・画面） |
| `goal:upkeep` | 作る仕組みと記述を整える（盤面の道具・参照のずれ・置き場の直し） |

**分類（`kind:`）とは別の軸**（2.17.1 は棚卸しが出す結論の話で、ここは立てた側が名乗る出どころの印
——`origin:agent` と同じ段）。**棚卸しは付け直さない。**

**印が無いときの既定は、立てた側で分ける。**

- **`origin:agent` が付いている → 整備。** 仕組みが自分で作った仕事が、**名乗らないだけで**前へ
  進める仕事の前に出られては、この軸を置いた意味が無い。付け忘れの倒れる先を安全側にする。
- **付いていない（人が立てた） → 完成へ近づける仕事。** ラベルはスマホから付かないうえ、人が
  わざわざ立てるのは前へ進めたいものだから。

**この既定は、棚卸しを1回通ると効かなくなる。** (c) の分解で立つ子には `origin:agent` が付くので、
**元が人の issue でも、子は「機械が立てたもの」に見える**——そのままでは、人の仕事が分解された瞬間に
整備へ落ちる。**だから分解する側が、元の向かう先を決めて子へ書き写す**（[`triage-prompt.md`](triage-prompt.md)
「付けるラベル」の表。**分解は向かう先を変えない**）。既定が効いているうちに、決まった値を明示へ
変えるのがあの表の役目。

**効かせる先は2つで、両方要る。**

1. **掘り起こす係の `due`** — 「配れる `goal:game` が尽きた周」。
2. **配る順**（2.18） — `急ぎ` の次、古い順の前。**掘り起こしたものは必ず最新**なので、古い順だけで
   並べると、掘り起こした先から整備の在庫の最後尾へ回る。**`due` だけを直しても、配られるまでに
   整備の在庫を全部捌くことになり、詰まりは動かない。**

**`急ぎ` はこの軸より強い**（2.18 の「効き目は配る順だけ」をこの軸の上でも保つ）——盤面そのものが
止まる整備は `急ぎ` で越える。

どちらも [`board-move.mjs`](../scripts/agent/board-move.mjs) の `advancesGame` が持ち、
[`boardMove.test.ts`](../tests/scripts/boardMove.test.ts) が**両方の効き目を別々に**見ている。

### 2.19 デーモンを起こす係は、デーモンの外から立てる

**デーモンが落ちると、盤面は1ミリも動かない**（[`parallel-work.md`](parallel-work.md)「盤面を回す
仕組みを止めたままにしない」）。落ちたことを知らせる仕組みは置かないと決めてある（2.3.3）ので、
**起こす者を1つ置く**（出どころ: ユーザーの指示・2026-09-06）。**打つのは `daemon.sh start` の1行
だけ**で、盤面もリポジトリも issue もPRも触らない。

**置き場はこのPCのタスクスケジューラ**（出どころ: ユーザーの指示・2026-09-11）。登録は
[`daemon-wake-task.sh`](../scripts/agent/daemon-wake-task.sh)（2.19.1）。**2.17 の枠には載せない**
——`CYCLES` を回すのはデーモン自身なので、そこへ載せると**デーモンが死んだときに係が立たない**
（見張れるのは「生きているが詰まっている」だけで、「落ちたら起こす」が抜ける）。

**起こす口は、ログオンと毎時。** 再起動の直後と、落ちた跡とで、拾う相手が違う。**間隔は1時間**
（出どころ: ユーザーの指示・2026-09-06）。

**投入の手綱（2.4）には載せない**（出どころ: ユーザーの指示・2026-09-06）。止めたいのは投入で
あって、起こすことではない。載せると、**止めたまま落ちても誰も気づかない**状態が作れる。

**セッションを立てない。** 打つ手に判断が1つも要らないので、モデルの居場所が無い——**係が食う使用量
は無く**（2.5.3 の割り当てに現れない）、走った跡の作業ツリーも残らない。

**盤面が健全かを見る仕事は、この係の外**（2.21）。健全かの判定にも、直すところにも判断が要るので、
この係の**判断が1つも要らない**という土台に乗らない。**二重に手を出さないのは、手番が背反だから**
——この係が手を出すのはデーモンが居ないときだけで、盤面を見回る係が立つのは居るときだけ。

**版の入れ替えは持たない。** 走っているデーモンを新しい `main` へ載せ替えるのはデーモン自身で、
落ちた跡から起こすときに寄せるのも `start` の側（2.3.2）。係が `stop` を打つと、そのあいだ盤面が
止まる。

**知らせる先は持たない。** 2.3.3 が「落ちたことを検知して知らせる仕組みは置かない」と決めているのと
同じ理由で、**この係は知らせるのではなく直す。** **人へ告げる仕組みをここへ足さない**——足すと、
判断も副作用も無いという土台が消える。**機械に直せない値の死を告げるのは別の係**（2.22）。

#### 2.19.1 登録は冪等な1本のスクリプトで、人が一度だけ打つ

置き場は [`daemon-wake-task.sh`](../scripts/agent/daemon-wake-task.sh)。**何度打っても1本のまま**
——探す鍵はタスクの名前で、名前を持つのもあちら。

**最初の1回は、この仕組みを入れた側が打つ。** 自分を立てる仕組みを自分では立てられないので、そこ
だけは外から始まる。**タスクは再起動を跨いで残る**ので、打ち直すのは登録の中身を変えたときだけ。

**条件をここへ書かない。** 二重に立たないこと・落ちた跡の錠を取り上げること・本体を `origin/main`
へ寄せることは、全部 `daemon.sh` が持っている（2.3.2・「二重に起こさない」）。係が持つのは
**打つ間隔だけ。**

#### 2.19.2 クラウドの cron には置かない

CCR の Routine は**デーモンに依らずに立つ**が、**投入先の環境が登録のときに決まり、後から替えられ
ない**（`update_trigger` が替えられるのは名前・間隔・止め起こし・本文だけ）。そして**ブリッジの環境
はPCの再起動で作り直される**（[`ccr-env.sh`](../scripts/agent/ccr-env.sh)「ブリッジのIDは、開き直す
たびに変わる」）ので、再起動を跨いだ Routine は**存在しない環境へ発火し続ける。**

**自分では直らない。** Routine を直せるのは Routine で立った係だけで、その係を立てるのが当の
Routine だから——2026-09-11、消えた環境を指したまま丸一日発火せず、その間デーモンも止まったまま
だった。タスクスケジューラには**指す先が無い**ので、この穴が無い。

#### 2.19.3 ログオンしている間しか走らない

タスクは**ログオンしている利用者の権限で走る**ので、誰もログオンしていない間は起きない。そして
**起きていないことを知らせる者は原理的に居ない**——この口座から動かせるものが全部このPCの上にあり、
外から見ている者が1つも無いため。**ここだけは人の目が要る。**

デーモンの死は係が拾うが、**係そのものの死を拾う者は居ない。** 見張りを足しても同じ場所へ戻る
（足した見張りもこのPCで走る）ので、ここは仕組みで塞がない。

### 2.20 盤面は、人が読める issue へ周期で書き出す

盤面を見るには [`board.sh`](../scripts/agent/board.sh) を手元で叩くしかなく、**セッションを立て
られる場所に居る人しか見られなかった**（出どころ: ユーザーの指示・
[#1597](https://github.com/gooyyu1/UnmappedIsland/issues/1597)）。指示はスマホから来るので、
**叩けない間、盤面が動いているかどうかは誰にも見えない。**

そこで、デーモンが**常設の issue**（[#1714](https://github.com/gooyyu1/UnmappedIsland/issues/1714)）
**の本文を、周期で丸ごと書き換える。**

| 誰が | 何をするか |
|---|---|
| デーモン | 間隔が満ちた周に1回、本文を丸ごと書き換える（[`board-publish.mjs`](../scripts/agent/board-publish.mjs)） |
| 人 | 読むだけ。**書いても次の更新で消える** |

**間隔は5分**（`PUBLISH_INTERVAL` で差し替えられる）。周（既定30秒）と同じ速さで書かないのは、
**読むのが人だから**——読み切れない速さで書き換わるうえ、issue の編集履歴がそれで埋まる。

**投入の手綱（2.4）とは別の issue にする。** あちらは人だけが書いて機械が読み、こちらは逆
（機械だけが書いて人が読む）。1つにすると、機械の書き込みが人のチェックを消す。

**並べる形を持つのは [`board.mjs`](../scripts/agent/board.mjs)** で、突き合わせは端末へ出すのと
**同じ1箇所**。出口ごとに組み直すと、片方だけが古い読み方のまま残る。出るのは、**人の手番で
止まっているもの**・**配ってよいかで数えた件数**・**`投入済み` の1件ごとの表**（issue の番号・題・
状態・PR）。

**`判断待ち` が付いたものは、番号と題で出す**（2.13）。**届く先がここしか無い**からで、ラベルを
付けるのは機械かレビュアーであり、**PRを出すのも issue を返すのも人と同じアカウント**なので
GitHub の通知は鳴らない。端末の盤面にはラベルの列が出るが、**叩けない人が読めるのは本文だけ。**
出さないでいると、人待ちの1件が錠（`area:`）を握ったまま、同じ錠の task が全部止まる。

**セッションの一覧は、その周に引いたものを使う**（1.7。[`board-round.mjs`](../scripts/agent/board-round.mjs)
が置く `live-sessions.tsv` を渡す）。書き出す側に引き直させない理由は2つ——**引く回数がそのまま
盤面の回る速さの天井に効く**ことと、**issue に出る表とその周に打った手の根拠が別の一覧になる**こと。
1ページだけ引いて済ませるのも同じ理由で採らない（**盤面が「居ない」と言う相手をデーモンは掴んで
いる**形になり、読んだ人は投入してよいと読む）。

**だから、一覧を渡すのは盤面を引けた周だけ。** 引けなかった周は一覧そのものが無く、前の周の写しを
渡せば古い顔ぶれが今の表として載る。**書き出しそのものは引けなかった周も行う**（2.21）——引けない
間は誰もセッションを立てられず、直せるのは人だけなので、**止まっていることが読む人へ届く先はここ
しか無い。** そのぶん本文は組み直されるので、**一覧を根拠にした行は落として組む**（下の 2.20.2）。

**状態はラベルの写しではない**（出どころ: ユーザーの指示・#1597）。セッションのタグ
（`task-<番号>` / `review-<PR番号>`）と、PRのCI・マージ可否から**その周に見えているものを出す**
——ラベルは人と `board-labels.yml` が後から付けるので、走っているかどうかを言えない（2.10.3 と
同じ理由）。語彙は [`board.mjs`](../scripts/agent/board.mjs) の冒頭が持つ。

#### 2.20.1 写しを持ってよいのは、いつ時点かを一緒に書くから

**写しを持つと古くなったことに誰も気づけない**（[`parallel-work.md`](parallel-work.md) 5節）。
ここはその例外で、条件は2つ。

- **最終更新の時刻を本文へ一緒に書く。** 止まったデーモンの写しは、時刻が伸びないことで**それ自身
  が「動いていない」を告げる**——読む人が確かめたいのがまさにそれなので、写しであることが害になら
  ない側へ倒れる。
- **機械はここを読み返さない。** 手を決める材料は毎周 GitHub と CCR から引き直すので、古い写しが
  手を決めることはない。**これを支えているのは分類のラベル**（2.17.5）——チェックを拾う側は
  `kind:ask` だけを見るので、`kind:board` のここは、本文にチェックの形が出ても拾われない。

**1.1 が禁じているのは、消えない場所へ置いた占有を*事実として読む*こと**（`レビュー中` のラベルが
破綻したのはそれ）。ここに出る `作業中` は**その時刻に見えていたもの**で、読む先も人だけなので、
掃除役が要る形にはならない。

#### 2.20.2 書けなかった周は、ログへ1行残して次へ進む

**周は止めない。** 古くなるのは読む先だけで、打つ手には関わらない——ここで諦める側へ倒すと、
GitHubが数分沈むたびに盤面ごと止まる。

- **叩いた時刻は、成否によらず控える。** 失敗のたびに次の周で叩き直すと、沈んでいる間じゅう周と
  同じ速さで打ち続けることになる。遅れて困るのは読む人だけなので、周期のぶんは待ってよい。
- **issue とPRを引けなかったら、書き込まない。** 欠けた盤面で上書きすると、**在るはずのものが消えた
  盤面**が残る。古いままなら、読む側は最終更新の時刻で気づける。
- **セッションの一覧を引けなかった周は、断りを本文へ出したうえで、一覧を根拠にした行を落とす。**
  出す先がログしか無いと、**読んでいる人は当てにならない表を正しいものとして読む**（ログを読める
  のは、手元で叩ける人だけ）。**断りだけでは足りない**——空の一覧で組むと投入済みの task が
  `着手可`・`担当無し` に化けるので、**断りが在っても表のほうが読まれる。**
- **盤面を引けていないことも、同じ理由で本文へ出す**（2.21）。断りは表の読み方の注釈だが、こちらは
  **読んだ人に手を打ってもらうための行**なので、いちばん上に置く。**見回りが届いているか**（2.21.4）
  も同じ——**係が黙って立たなくなったことは、他のどこにも出ない。**

### 2.21 デーモンは生きているが、盤面が進んでいない

**心拍は「回っているか」しか言わない**（2.19）。空回りしている周とやることが無い周が同じ顔をするので、
**デーモンが生きたまま盤面が止まっている状態を見る者が居なかった**——2026-09-11、CCRの資格情報が切れて
盤面を引けない周が1時間45分続き、投入もレビューもマージも全部止まったまま誰にも拾われなかった
（[#1710](https://github.com/gooyyu1/UnmappedIsland/issues/1710)）。

**同じ日、今度は盤面が引けているのに手が1つも打たれない形で、2時間11分止まった**
（[#1939](https://github.com/gooyyu1/UnmappedIsland/issues/1939)）。錠で全部の task が待たされ、
差し戻す相手が畳まれていた周で、覚え書きだけが毎周出続けていた。**沈黙を破ったのは人**（新しいPRが
出て、レビューの手が打てた）。**この2件が、下の形を決めている。**

#### 2.21.1 誰に見えて、誰が打てるかで割る

**ユーザーから来ているのは「分けるかを検討せよ」まで**（2026-09-07。「監視係と分けたほうが良いかも
そのissue側でしっかり検討させてください」「両者が同一か連携が取れたほうが良いかもしれません」）。
**下の割り方は、それを受けてこちらが決めたもの**で、確定の宣言は付かない——覆す提案を出してよい。

| 盤面の状態 | 見える者 | 打てる者 |
|---|---|---|
| デーモンが落ちている | 起こす係（心拍。2.19） | 起こす係（`daemon.sh start`） |
| 生きているが、盤面を引けない | デーモン自身 | **居ない**——CCRが落ちているのでセッションが立たない。直せるのは人 |
| 引けているのに、手が打てない | 盤面を見回る係（**デーモン自身には判定できない**。2.21.2） | 同じ係（下の 2.21.3） |

**三者は分ける。** 見えるものも打てる手も背反で、**混ぜると片方の壊れ方がもう片方を巻き込む。**

**引けない理由が値の死なら、その値を名指しで人へ告げる者が居る**（2.22）。**打てる者が居ないことは
変わらない**——告げるのは、直せる唯一の相手（人）に、直す先を渡すため。

**二重に手を出さないのは、錠ではなく手番の形で言える。**

- **起こす係が手を出すのは、デーモンが居ないときだけ**——走っていれば `daemon.sh start` は
  「既に走っている」と答えて何もしない（2.19）。
- **盤面を見回る係が立つのは、デーモンが居るときだけ**——立てるのがデーモン自身（`CYCLES`）なので、
  落ちていれば誰も立てない。**立ったこと自体が「デーモンは生きている」の証拠**になっている。

**退けた案。**

- **同一（起こす係に詰まりの点検も兼ねさせる）。** 起こす係は**モデルを持たない**（2.19）ので、
  兼ねるにはセッションを立てる口を作り直すことになる。そのうえ**デーモンが死んでいる周にも詰まりの
  調査が回る**——判断の要らない点検と要る調査が同じ手番に乗り、承認や分類器で止められた周に心拍の
  点検まで巻き込まれる（PR #1705 で実際に起きた形）。**起こす係の外から立てる形も同じ**で、
  デーモンの生死を見ずに立つので、落ちている周に両方が同じ原因へ手を出す。
- **連携（起こす係が詰まりの係を立て、錠で調停する）。** 錠は**同じ資源を書く相手どうし**を待たせる
  道具で、`daemon.sh start` は錠を取らない（取るのはデーモン本体）。起こす係に錠を持たせると、
  **デーモンが死んでいる間じゅう起こす係が待たされる**——起こすことそのものが止まる。
- **常駐をもう1つ置く。** 置き場は結局このPCなので 2.19.3 と同じ場所へ戻るうえ、常駐は `IDLE` が
  「終わった」と「止まっている」を区別しない（1.6）。周期の係なら、立って終わるので死活が読める。

#### 2.21.2 立つ条件は、間隔が満ちたことだけ

**係を印で絞らない。** 絞る条件は**既に知っている壊れ方の一覧**でしかなく、次に来る形はそのどれにも
掛からない。**係は間隔ごとに必ず立ち**、健全なら「異常なし」を記録して終わる
（[`board-move.mjs`](../scripts/agent/board-move.mjs) の `CYCLES` の `patrol` の `due` が常に真）。

**絞っていた形が、実際に取りこぼした。** 印が立つのは「転んだ手が在った周」だけだったので、
**手が1つも出ない周**——錠で全部が待たされる・差し戻す相手を引けない——には決して掛からず、
`played` が空のまま毎周消されていた（#1939）。**条件を1つ足せば今回の形は拾えるが、それは一覧を
1つ伸ばしただけ**で、次の未知の形では同じことが起きる。

**渡すのは、壊れ方の一覧ではなく正常の定義**（[`patrol-prompt.md`](patrol-prompt.md)）。
**未知の壊れ方も、成り立たなくなった不変条件のどれかに必ず現れる**ので、係が毎回「どれが成り立って
いないか・なぜか・自分で直せるか」を答える形にする。**足りない不変条件は、気づいた係が自分で
プロンプトへ書き足す**——一覧を人が保守する形にすると、そこがまた「既知の一覧」になる。

**費用は、間隔ごとにセッションが1本立つこと。** 健全な回は短く終わる（記録を読む・ログの尻を見る・
1行書く）。**取りこぼしの重さと並べて、間隔を1時間と置いた**（仮決め）——詰まっている間、盤面は
1ミリも動かないので、**気づくのが遅れた分がそのまま全部の作業の止まっている時間**になる。
**投入の手綱（2.4）と自動の手綱（2.5）は、この係にも効く**ので、止めている間の費用は増えない。

**退けた案。**

- **印に「手が0の周が続いた」を足す。** 今回の形は拾えるが、**拾えるのは今回の形だけ。** 上のとおり。
- **印を「盤面の見え方が前の周と同じなら立てる」まで広げる。** 一覧の伸ばし方としては筋が良いが、
  **判定を機械が持つ限り、何をもって「同じ」とするかを機械が決める**ことになる——盤面は自分の
  異常を自分で判定できない（2.21.1 の表）。**同じに見えることが異常かどうかは、そのとき何が起きて
  いるかで変わる**ので、そこが判断の要る仕事。係へ渡す。
- **常駐で見張る。** 2.21.1 の「常駐をもう1つ置く」と同じ場所へ落ちる。

**印（[`board-state.mjs`](../scripts/agent/board-state.mjs) の `UNREADABLE`）に残したのは、
盤面を引けなかった周だけ。** 読むのは人で、打てる手は無い（2.21.1）。**引けている周の不調は、
もう印に立てない**——見るのは係で、材料は `~/daemon.log`（打てた手・打てなかった手とその理由・
覚え書き）と前回の観測（2.21.4）。**「打てなかった」のうち答えが返っている分**（人が手綱で止めた手・
`ARCHIVE` の `KEPT`）**は、ログの行にそう書く**——直す相手が居ないので、係が毎回そこを調べに行かない
ように。**見分けるのは、止めた側の名乗り**（[`brake.sh`](../scripts/agent/brake.sh) が `STOP` の
ときだけ終了コード3で終わり、投入のスクリプトがそれをそのまま返す）。**後から状態を見て推し量らない**
（[`policies.md`](policies.md)「理由の持たせ方」）。

#### 2.21.3 引けない周は人へ、引ける周は係へ

**引けない周に、デーモンが打てる手は無い。** CCRが落ちていればセッションは1本も立たず、
`~/.claude/.credentials.json` を貼り直せるのは Claude Code 本体だけ（2.3.1）。**だから届け先は人**で、
経路は `gh`——別の資格情報で動くので、CCRが落ちていても issue は書ける。

**書き出し**（2.20）は**盤面が引けていないこと**しか言えない。写すのは盤面の姿そのもので、引けなけ
れば写すものが無いため。**どの値が死んでいて、どう直すのかを名指すのは 2.22 の1本**。**この2本より
先は増やさない**——増やすなら、2.3.3 と同じ問いに答えてから。

**引ける周は、盤面を見回る係**（[`patrol-prompt.md`](patrol-prompt.md)）。健全かを判定するところにも、
原因を探して直すところにも判断が要るので、モデルが要る。

| 持つもの | 値 | なぜ |
|---|---|---|
| `env` | `bridge` | 何が転んだかが残っているのは `~/daemon.log` と `~/.claude/board-state` だけ |
| `hours` | 1 | 健全な回にも立つので、**費用と、気づくまでの遅れの釣り合い**（2.21.2） |
| `urgent` | 立てる | **この係だけ、手の並びの先頭に置く**（下） |

**錠を取らない。** `area:daemon` を要求していたが、**その錠を握っている task のセッションが止まって
いるのが詰まりの典型**なので、**詰まっているときほど立てない**形になっていた（#1939 の当日も、
`area:daemon` は task のセッションが握っていた）。**毎回立つ係が錠を持つと、もう一方の害も出る**
——間隔ごとに `area:daemon` の task が投入されなくなる。**錠を持つ係はこれで1つも居なくなったので、
周期の係の側の仕組みごと落とした**（2.17）。

**代わりに、書き換える手前で係が自分で見る**（[`patrol-prompt.md`](patrol-prompt.md)）。
並んで走る相手とぶつかっても、**この係の直しは `main` へ直接入り、相手のPRは `mend` で直させる**
ので、戻せないものは残らない。**錠が守っていたのは並列に書くことだけで、立つこと自体ではない。**

**退けた案。**

- **錠は持たせたまま、この係だけ取り合いを無視する。** 立てる側（盤面）に「この係は例外」と書く
  ことになり、**錠の意味が係ごとに変わる**。錠を持たないと言い切るほうが、読む側に例外が残らない。
- **`area:daemon` を握る task が居る周は、立てるが報告だけさせる。** 立ってから自分で見るのと結果は
  同じで、**判定を盤面側へ持つぶんだけ、盤面が知らないこと**（相手が何を書き換えている最中か）**を
  盤面が判定する**ことになる。

**周期の係は最後尾でよいが、この係だけは先頭。** 最後尾に置ける根拠は「間隔が満ちている限り次の周
でも同じ手が出るので、いつか手番が回る」ことで、**打てる手が在る周にも立つ係にはそれが言えない**
——転ばずに打てる手が毎周1つでも在れば、**1周1手の切り上げに毎回先を越されて永久に立たない**
（投入だけが通らない盤面で、マージやレビューは通り続ける形がこれ）。先頭へ置いて押しのけるのは、
間隔ごとに1周ぶん。

**直しは `main` へ直接入れる**（出どころ: ユーザーの指示・2026-09-06。
[`decisions/2026-09-06-daemon-watchdog-commits-straight-to-main.md`](decisions/2026-09-06-daemon-watchdog-commits-straight-to-main.md)）
——PRにすると、盤面が詰まっている間はマージされないので直しが届かない。

**承認モードは上げなくてよい**（2026-09-11 に実測）。ブリッジへ `permission_mode` を渡さずに立てた
セッション（`create_session` に `environment_id`・`title`・`prompt`・`tags` だけを渡す。
[`ccr-env.sh`](../scripts/agent/ccr-env.sh) と同じ形）で、`.claude/**` を読む `bash`・編集ツールの
`Write`・`git commit`・`git reset --hard` を順に打たせたところ、**6つとも承認を求められずに通った**
（`session_01QUBbYuVFUiV9fpzaBwKNPQ`。手番の要約は `approval mode check: all 6 commands ran without
prompts`）。**この係は投入の道具（`dispatch-chore.sh --bridge`）で立つ**ので、同じ経路に乗る。

#### 2.21.4 前回の観測は、係が自分で残す

**進んでいないことは、1枚の写真には写らない。** 前回の自分が見たものと突き合わせて初めて「同じものが
同じ場所で止まったままだ」と言える。**原因を知らなくても停滞は言える**のがこの形の要点で、未知の
壊れ方を拾う力はここから来る——#1939 の2時間も、**盤面の見た目は毎周まったく同じだった。**

**置き場は `~/.claude/board-state/patrol.jsonl`**（1行1件のJSON。追記）。**書くのは係のセッションで、
形を持つのも係のプロンプト**（[`patrol-prompt.md`](patrol-prompt.md)）
——盤面はこの記録を読んで手を決めない。**機械が読むのは `at`・`verdict`・`summary` だけ**
（[`board-state.mjs`](../scripts/agent/board-state.mjs) の `readLastPatrol`）で、突き合わせに使う
`board` の中身は係どうしの取り決め。

**リポジトリへは置かない。** 間隔ごとに1件増えるので、**コミットが記録で埋まる。** デーモンと同じ
PCの外へ出す必要も無い——読むのは次の回の係で、そちらも同じPCで走る（2.21.3 の `env`）。

**古い行を落とす者は置かない**（ぶつかった実績の帳面 `conflicts.jsonl` と同じ、追記だけの帳面）。読むのは最後の
1行と、係が突き合わせに使う末尾の数行だけなので、**落とすなら「どこから先は捨ててよいか」を誰かが
決めることになる**——それは記録の使い道が固まってからの話。

**走ったこと自体は、人へ届く場所へ出す。** 記録がこのPCにしか無いと、**「異常なし」と「係が立たな
かった」を人が区別できない**（#1939 の2時間は後者だった）。**常設の issue の本文**（2.20）へ最後の
1行を出し、**しばらく更新されていなければ断りにする**（[`board.mjs`](../scripts/agent/board.mjs)
の `patrolNote`）。**間隔そのものでは鳴らさない**——1回ぶんの立ち遅れ（手綱で止まっている・投入が
転んだ・係が長く走っている）は毎日出るので、それで鳴ると読む人がこの行を読まなくなる。**どれだけ
過ぎたら鳴らすかは実装が持つ**（同 `STALE_PATROL_HOURS`。係の間隔から出すので、間隔を変えても
付いてくる）。**記録が無い周・読めない周も同じ断り**——人から見れば、走らなかったのと読めない
のは同じだけ危ない。

#### 2.21.5 畳むのは、既に在る手

**周期の係なので、畳む手は盤面が持っている**（2.17。手が空いたままが続けば `ARCHIVE`）。Routine で
立てる形を採らなかったぶん、ここに新しい仕組みは要らない。

### 2.22 盤面が動くのに要る値は、死んでも誰も言わない

CCRの環境ID（[`ccr-env.sh`](../scripts/agent/ccr-env.sh)）と、CCR・`gh` の資格情報。**どれが死んでも、
分かるのは投入や盤面の読みが落ちたときだけ**で、その失敗は `NOTE` として `~/daemon.log` へ出るだけ
だった（「未決」）。**値の生死を見回る者を置く**
（[`check-values.mjs`](../scripts/agent/check-values.mjs)。出どころ: ユーザーの指示・2026-09-06。
「設定する」は自動化できないので、**確かめて報告する**ところまでを機械が持つ）。

**何をどう確かめるかはあちらが持つ**ので、ここには書き写さない。ここに置くのは、コードを読んでも
出てこない決めごとだけ。

#### 2.22.1 置き場はデーモンの中で、1周の外

**周期の係（2.17）には載せられない。** 係を立てるかを決めるのは1周の中なので、**`gh` が死ぬと
その1周が引けず、いちばん告げてほしい死のときに告げる者が立たない。** 盤面を書き出す手（2.20）と
同じ層——**引けなかった周も走る**ところに置く。

**デーモンを起こす係（2.19）にも載せない。** あの係が安全なのは**判断も副作用も1つも無い**からで、
issue を書く手をそこへ足すと、その土台が消える。**デーモンが落ちている間は見回らない**が、落ちた跡は
毎時あの係が起こすので、止まるのは高々1周ぶん。**誰もログオンしていない間は走らない**のは 2.19.3 と
同じ場所へ落ちる。

#### 2.22.2 死んだと言うまで、死に続けるのを待つ

**CCRのアクセストークンは数時間で切れ、放っておくと直る**（[`daemon.sh`](../scripts/agent/daemon.sh)
「止めないのは」）。落ちた1回をそのまま死と読むと、**直る途中のものを毎回告げる**ことになり、告げた
ものが誰にも読まれなくなる。**同じ値が死んだまま猶予（`VALUE_GRACE_HOURS`）を越えてから告げる。**

**猶予の長さは仮決め**（6時間。日をまたぐ前に届き、トークンの切れ間より長い）。**短くしすぎると
偽の報せが増え、長くしすぎると盤面が止まったままの時間が延びる**ので、実際に鳴った回数を見てから
詰める。

**確かめられなかったことは、死んだことではない。** CCRへ届かない周は、環境IDが一覧に居るかを確かめ
ようがない。そこで「居ない」と読むと、トークンが切れただけの周に環境IDまで死んだことになる。**死とも
生とも数えず、それまで数えていた長さもそのまま残す。**

#### 2.22.3 告げ先は issue 1本だけ

**告げるのは題で引く issue 1本だけ。** 開いていれば本文を丸ごと書き換え、無ければ立てる——**鍵が題
なので、同じ死が続いても2本目にならない**（2.17.2「二重に起票させない手は2つ要る」と違って、間隔の
側の手が要らないのはこのため）。**死んでいる値も、確かめられなかった値も1つも残っていない周だけ
閉じる**ので、次の死は新しい1本になる。**「告げることが無い」で閉じない**——猶予に届いていない死も、
確かめられなかった死も、告げることは無いが生き返ってはいない。

**「引けなかった」を「無い」と読まない。** 開いている issue の一覧が転んだ周は、**何も書かずに次の
周へ回す**——そこで立てると、題で畳む鍵がその周だけ効かず2本目が立つ。告げるのが1周ぶん遅れるほうが
軽い。

**直せるのは人の手だけなので、`判断待ち` を付けて配らない**（2.17.3 の「自分で付ける係」に並ぶ）。
**本文には直し方まで入れる**——読む人はスマホから読むので、リポジトリを開かないと分からない報せは
届かないのと同じ。

**`gh` の死だけは告げられない。** 告げる手（`gh issue create`）がその値そのものなので、死んだ周には
打てない。`~/daemon.log` へは残すが、**定期的に読む者が居ない**ので告げたことにはならない——
ここは 2.19.3 と同じ場所（人の目）へ落ちる。

**電話は口ではない。** CCRの Routine の完了通知（`create_trigger` の `notifications`）はAPIが
受け付け、立てて押すところまで動くが、**押しても届かない**（2026-09-11、実際に1回押してユーザーへ
確認。「通知は届いていないようです」）。**APIが受け付けたことを、届いたことと読まない。**

**残っている口はCCRのセッションだけ。** `gh` が死んでいるのは**このPCの資格情報**なので、クラウド
で立てたセッションは自分の `gh` で同じ issue を書ける。**この差分では持たない**——告げ先が2つに
増えると、題で1本に畳む鍵（上）を両方が別々に引くことになるので、そこの決め方から要る。

#### 2.22.4 2.19「知らせる先は持たない」との違い

あちらは**デーモンの死**についての決めごとで、理由は「知らせるのではなく直す」（2.3.3）。
**値の死は機械に直せない**——設定を打ち直せるのは人だけなので、同じ理由がそのままは効かない。
**直せるものは直し、直せないものだけ告げる**、が両方に通る形。

## 3. 移行の順序【仮決め】

**今は盤面が止まっている**（2026-09-04 時点。畳まれていないセッションは1本だけで、それも手番を
終えている）。盤面を回すものが何も走っていないので、**入れ替えの排他が要らない——「切り替え」では
なく「立ち上げ」になる。**

段を切る基準は2つ。**各段の終わりで盤面が前より壊れていないこと**と、**戻せること**。

| 段 | やること | 危なさ | |
| --- | --- | --- | --- |
| 0 | 手綱の issue を1つ作る（2.4） | 無し | 済（[#1515](https://github.com/gooyyu1/UnmappedIsland/issues/1515)） |
| 1 | 占有と使用量を**読むだけ**の道具を作り、計測を貯め始める | 無し | 道具は済（[`usage-record.sh`](../scripts/agent/usage-record.sh)）。**呼び手が段4** |
| 2 | 投入スクリプトへ占有の判定を入れる（1.4） | 小 | 済 |
| 3 | ラベルの付け外しを Actions へ移す（2.2） | 小 | 済（[`board-labels.yml`](../.github/workflows/board-labels.yml)。下で実測） |
| 4 | デーモンを立てる。**ただし本数の上限つき** | 中 | 済（[`daemon.sh`](../scripts/agent/daemon.sh)＋[`board-move.mjs`](../scripts/agent/board-move.mjs)） |
| 5 | マージを Actions へ移す（PAT） | 大 | **要否を保留**（下） |
| 6 | 引き継ぎ向けの道具の後片付け | 小 | 済 |

### 3.1 各段の理由

**段1を最初に置くのは、2.5.2 の安全率と既定値がここでしか決まらないから。** 計測は盤面を動かさなくても
貯まり始める（ユーザー自身の対話でも `utilization` は動くので、まず**デーモン以外の消費**が分かる）。
種類ごとの1本あたりは段4が動き出してから積まれるので、**貯め始めを早くするほど段5までに揃う。**

**ただし、計測を貯めるには周期的な呼び手が要る。** 2.5.3 の割り当ては「前回からの増分を、そのとき
生きているセッションで等分する」形なので、一定の間隔で引き続けないと増分が置き換わらない。1回ぶんの
割り当て（[`usage-record.sh`](../scripts/agent/usage-record.sh)）は置けたが、**貯め始めはデーモン
（段4）か、それに代わる定時実行が要る。**

**段2だけで PR #1493 の事故は止まる**（1.5）。占有の判定が投入スクリプトの中に入れば、呼ぶ側が
デーモンでも人手でも二重には立たない。**誤って「在る」と判定しても投入が止まるだけ**なので、
安全側に倒れている。早い段に置く値打ちが大きい。

**段3でラベルだけ先に移すのは、段4のデーモンが読む対象を揃えるため。** 決めた時点（2026-09-04）の
PR #1512 はレビューが3周「直しが要る」を出しているのに `直し待ち` が付いていなかった——付けるのが
人の手作業で、それが止まっていたから。**盤面の見え方が正しくなってからでないと、デーモンの判定を
確かめられない。**

段3は使い捨てのPR（[#1516](https://github.com/gooyyu1/UnmappedIsland/pull/1516)、確認後に閉じた）で
**4つとも実測した**（2026-09-05）——`[レビュー] 直しが要る` で `直し待ち` が付き、push で外れ、
`[レビュー] 通してよい` で `通してよい` が付き、結論の行でないコメントでは動かない。

**段4で並列度を1に絞ったのは、衝突を見る仕組みが盤面に無かったから。** **つまりそれは「起動の前提」
ではなく「並列度を上げるための前提」**で、移行を止めなかった。今は**錠**（`area:` のラベル。
[`parallel-work.md`](parallel-work.md) 2節）と**本数の上限**が
[`board-move.mjs`](../scripts/agent/board-move.mjs) に入っている。

**ファイルの衝突は投入では見ない。** 盤面にできるのは投入を遅らせることだけで、**重なりを知らせても
受け取った側は触る先を変えない。** ぶつかったら `mend` で直させ、**どこで・何とぶつかったかを
帳面へ控える**（`board-round.mjs`。錠を足すべき資源をそこから決める）。

**本数の上限は、使用量の集計が入っても外さない**（出どころ: ユーザーの指示・2026-09-06）——残量だけを
見て決めると、余力のある周に一度に何本も立つ。

**上限は2つある**——**同時に抱えてよいタスクの数**（`HELD_TASKS`）と、**同時に手が動いてよい作業者の
数**（`ACTIVE_WORKERS`）。投入するのは、どちらの枠も空いているときだけ（値と出どころは
[`board-move.mjs`](../scripts/agent/board-move.mjs) の定義に置く）。

**1つの数で兼ねない。** 抱えている側が数えるのは担当 issue を持ったまま生きているセッションで、
**PRを出して人の判断を待っているだけのセッションも入り続ける**——担当はマージまで閉じない。兼ねると、
**待っているPRが上限まで溜まった時点で、手が1本も動いていなくても新しい task が1件も配られなくなる。**

**「手が動いている」は、走っていることだけでは数えない。** `SESSION_STATUS_RUNNING` は手番の切れ目
ごとに落ちる（1.6）ので、**立てた直後のまだ走り出していないセッション**も、下請けのレビューを待つ間も
空いて見える。そのまま数えると、**枠が空いて見えた周にもう1本立って、動く数が上限を越える。** 空いた
ままが停滞の境目（`STALL_MINUTES`。2.15.3）に届くまでは動いている側で数える——**PRをまだ出して
いないセッションは、越えたところで起こす手か返す手が出る**ので、**動いていないと読む線と、止まった
として打つ線が1本で揃う。**

**PRを出して待っているセッションには、越えても手が出ない**（2.15.3 の入口が「PRが出ていない」で
切ってある）。**止まっているのではなく、続きがレビューとマージの側にある**からで、越えた時点で
空くのは `ACTIVE_WORKERS` の側だけ——担当は上のとおりマージまで閉じないので、`HELD_TASKS` は
握ったまま。**枠を2つに分けてあるのはここ**で、1つで兼ねると、この状態が上限を埋める。

**待たせている覚え書きには、どちらの枠で止まったかを書く**（`board-move.mjs` の `NOTE`）。詰まりを人が
見つけるための行なので、枠の名前と、その枠を握っているセッションの名前の両方が要る。

**段5（マージ）を最後にするのは、唯一戻せない操作だから。** ラベルが正しく付くことを段3・段4で
確かめてから移す。

**ただし段4を入れた時点で、マージはもうデーモンが打っている**（`MERGE` の手）。2.1 の分け目
（CCRの資格情報が要るか）では、マージは CCR を要さないので Actions 側だが、**移して得られるのは
「ブリッジのPCが落ちていてもマージが進む」ことだけ**で、その状況ではレビューの投入も直しの再開も
止まっている。**マージだけが進んでも盤面は回らない**ので、段5は要否から保留する（仮決め。覆すなら
「ブリッジが落ちている間もマージだけは進んでほしい」と決まったとき）。

**段6（消すこと）を最後にするのは、戻せる先を残しておくため。** デーモンが回り始めて問題が出たとき、
引き継ぎ向けの道具が消えていると戻れない。

### 3.2 移行を止めない、と判断したもの

**PRから人へこぼれるものの受け皿と、#656 の口は、段4のブロッカーではない。** 申し送りを読む役が
居なくなるが、**読まれないまま PR 本文に残るだけで盤面は止まらない。**

**受け皿は「作る」ではなく「無くす」で決着した**（出どころ: ユーザーの指示・2026-09-06）。
`## ユーザーへ` は節ごと廃止し、行き先を issue と `[スメル]` へ割り振る（#1612）。**申し送りを
読む役を新しく置かない**——誰も読まない節が残るくらいなら、書く先を対応される場所へ移す。

### 3.3 段4の前に確かめること（済）

**畳まれたセッションへ直しを頼めるか** → **頼める**（2026-09-05 に実測。1.5）。`unarchive_session`
→ `send_message` で、畳む前の文脈を保ったまま返事をする。投入の種類「直しの再開」は、書いた本人の
セッションを起こす形でよい。

## 4. レビューが何で止めるか

### 4.1 実測（2026-09-05）

直近18本のPRで、**差し戻しゼロが12本。** 周回は6本に集中している——#1493 と #1492 が5回、#1512 が
4回、#1497 が3回、#1508・#1507 が2回。

**その21回の「直しが要る」の理由を読むと、コードの挙動の問題は1件も無い。** すべてが
**ドキュメント・スキーマ・コメントの記述が現物と合っていない**という指摘だった。

### 4.2 周回が終わらない理由

**規則はもう在る。** [`review-criteria.md`](review-criteria.md) の末尾は「止めるのは、直さずに
マージすると壊れるものだけ」、[`review-prompt.md`](review-prompt.md) も同じ趣旨。**書き足しても
効かない。** 効いていない理由は3つ。

1. **観点の一覧が、ブロックとスメルを区別せず同格に並んでいる。** 7項目の箇条書きに印が無く、
   「止めるのは壊れるものだけ」はその下に1行あるだけ。読み手は一覧をチェックリストとして使うので、
   **項目に挙がっている＝止める理由**として読む。**一覧の形そのものが判断を作っている。**
2. **機械で見られるものをレビュアーに見せている。** 「PR本文に要る節」は正規表現で分かる。人が見る
   限り往復に乗る。
3. **周回そのものが指摘を生産している。** 差分が変われば見る対象が変わり、軽微な不一致は**どの差分にも
   見つかる**。「1周で出し切れていない」のではなく、**出し切れる集合ではない。** だから往復回数の
   上限は対症療法で、ブロックの定義を絞ることだけが根治。

### 4.3 ブロックの定義

判定は一文で書ける。**この差分を入れると、入れる前より嘘が増えるか。**

1. **壊れている** — issue の現象が直っていない / 退行が入った / 実装が正しくない。**不要になった
   コードが残っているのもここ**（4.8 のとおり一部は CI が先に止める）
2. **この差分が嘘を増やす** — 新しく書いた記述が現物と合わない、差分が既存の記述を嘘にした。
   **PR本文で止めてよい範囲は 4.3.1**
3. **確定を覆している** — `【確定】` と「本書は全体が確定です」の射程に反する
4. **原因が浅い** — ただし**「その直しでは同じ不具合がまた出る」と具体的に言えるときだけ。**
   言えなければスメル

**4だけ条件を付けたのは、ここが唯一「判断」だから。** 絞らないと今の状態に戻る。

**機械で判定できるものは、ここに置かない**（2.12）。`## 見た目` の欠けはブロックの理由だったが、
レビュアーへ回す手前で盤面が見るようになったので、この一覧からは出ていった。

**明示的にスメルへ落とすもの**——書かないと元に戻るので、名指しで書く。

- **「同じ誤りの兄弟が1箇所残っている」。** 片方を直した差分は、**嘘が1つ減っている。** 増えていない
  ものを止める理由にしない。**これが今いちばん周回を作っている**（#1492 の5周はほぼこれ）
- **元から在ったずれ**（差分が触っていない場所の記述が現物と合っていない）
- 名前・構造・重複・改善提案・ドキュメント間の言葉の違い

#### 4.3.1 PR本文で止めるのは、読み方を間違えるときだけ【確定】

**出どころ**: ユーザーの指示・2026-09-05。

**PR本文で止めるのは、本文を信じると差分の読み方を間違えるときだけ。** 数値や件数のずれはスメル。

### 4.4 スメルの置き場

#### 4.4.1 PRコメントの行頭に残す【確定】

PRコメントの**行頭に印を置いて**残す。**ラベルは付けない**（1.3）。マージ後もコメントは残るので、
後から拾うエージェントがそのまま読める。**拾うのは分析係**（2.17 の周期で起きる係）。

#### 4.4.2 どう拾うか

上から導いたもので、覆すのに人間の判断は要らない。

- **行頭の印は `[スメル] `。** レビューが書くのも、タスクのセッションが書くのも同じ綴りで、
  **拾う側はこの行頭で読む**（[`analysis-prompt.md`](analysis-prompt.md)）。

- **読むのはマージ済みのPRだけ。** 開いているPRのコメントは、次の周のレビューや直しで消えることが
  あり、拾うと二重になる。
- **窓は本数ではなく期間で持ち、係の間隔より広く取る**（[`board-read.mjs`](../scripts/agent/board-read.mjs)
  の `MERGED_WINDOW_HOURS`）。本数は1本あたりに掛かる時間が変われば覆う期間も変わるので、間隔ぶんに
  入る本数を下回った瞬間、**拾われないまま窓から出るスメル**が出る——30本で1日を覆うつもりだった
  ものが15時間ぶんしかなく、#1659〜#1740 が一度も読まれずに落ちた（2026-09-07 に実測。#1787）。
  **同じ幅を盤面と係の両方が使う**（[`analysis-prompt.md`](analysis-prompt.md)「読む範囲」）——狭いほうが実質の
  窓になるので、係の側が狭いと、盤面が見つけた未読が印の付かないまま毎日空振りを生む。
- **絞るのはマージされた時刻。** `gh pr list` が並べるのは作成日で、**長く開いていたPR**（`判断待ち`
  で人の手番へ移ったものなど）**は、マージされる頃には作成日で数えた窓の外に居る。**
- **窓から落ちた帯は、1回きりの掃き寄せで拾う**（前例は
  [`.claude/analysis/2026-09-06-backfill.md`](analysis/2026-09-06-backfill.md)）。落ちたことに
  気づくのは二次（2.17.4）で、帯を名指しして issue を切る。**日々の係の窓を広げて拾わせない**
  ——落ちた帯は何日ぶんにもなるので、その日の帯と混ぜると、どちらも薄く読むことになる。
- **読んだ印はコメントに付く 👀。** 自前の台帳を作らない（1節）ので、
  立てるかを決める盤面と、拾うか飛ばすかを決める分析係が同じものを見る。**粒度はコメント**
  ——1つのコメントに `[スメル] ` の行が複数入るが、**マージ後のコメントは増えない**ので成立する。
- 渡す本文は [`analysis-prompt.md`](analysis-prompt.md)。出力は**新しい issue**（`kind:` は付けない
  ——分類は棚卸し）と、**1回1ファイルの記録**（`.claude/analysis/<日付>.md`）。記録が
  `.claude/decisions/` へ行かないのは、あそこが**ユーザー本人の発言だけ**の場所だから
  （`CLAUDE.md`「出どころは、ユーザー本人の発言だけ」）。
- **この係が見るのは自分の帯だけで、過去の回の記録で傾向を探さない**（2.17.4）。回をまたいで同じ形を
  探すのは二次の係（[`analysis-trend-prompt.md`](analysis-trend-prompt.md)）。**自分の帯のスメルが
  過去の記録の行を名指したときに開いて確かめるのは、この禁止の外**（同）。

### 4.5 2周目以降は、前の周の指摘が消えたかだけを見る

#### 4.5.1 新しく止めてよいのは、前の周以降の差分だけ【確定】

**新しいブロックとして挙げてよいのは、前の周のレビュー以降に入った差分に起因するものだけ。**
それ以外の場所から新しく見つけたものは、前の周で見えていたはずのもの＝見落としなので、スメルへ回す。
**これで指摘の供給が構造的に尽きる。**

#### 4.5.2 境界は、前の周が名乗った版

レビュアーは判定コメントの2行目に `読んだ版: <SHA>` を書く（`review-prompt.md`「読んだ版」）。次の周は
[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh) がそれを指示へ埋め、**`git diff <前の版>...HEAD`
だけ**を読ませる。境界をモデルの推定に任せると、差分が変わるたびに線が動く。

**盤面の指紋（`taken['review:<PR>']`）では引かない。** あちらは投入するたびに動くので、判定を書かずに
落ちた周のぶんだけ進み、次の1本が読んでいない範囲を「前の周が見た」ことにしてしまう。何周目かの数と
同じコメントから出せば、その食い違いが起きない。**名乗り忘れは全体を読み直す側へ倒す**——狭める側へ
倒すと、誰も読んでいない差分ができる。

**セッションは使い回さない**（出どころ: ユーザーの指示・2026-09-05）。2周目は前の周の指摘を**今の
観点の一覧で読み直す**仕事を含むので、自分の結論を文脈に持っている読み手には向かない。継続に要る
ものはPRのコメントに全部載っている。

### 4.6 3周目でブロックが残ったら人へ上げる

絞った後は1周で終わるのが普通になる想定なので、**3周まで行くこと自体が「機械では畳めていない」印。**
**この3という数だけは根拠が無い**——実績を見て動かす。上げ方は #656 と同じ「断定文＋チェック1つ」。

**上限を持つのは機械の側だけ。** 3周目の判定が `直しが要る` なら
[`board-labels.yml`](../.github/workflows/board-labels.yml) が `収束せず` を付け（`直し待ち` は
一緒に外す）、盤面はそのPRへレビューを出さなくなる（`board-move.mjs`）。人が読むのは、そのPRに
残っているレビューのコメント。出口は 2.13.1——通すなら画面からマージ、書き直させるなら直してほしい
ことを書いて `収束せず` を外す。

**数えるのは結論のコメントで、判定の形は問わない**——`通してよい（人の判断が要る）`（2.13.4）の周も
1周。漏らすと、この勘定が狂う。

**周回は数え直さない。** 数えるのは結論のコメントの総数なので、人が1回答えて1周進むと、
止まる理由が残っていれば次の「直しが要る」でふたたび `収束せず` が付いて人へ戻る。
**人が1回答えるごとに1周**、という形。

**レビュアーには上限を伝えない**（出どころ: ユーザーの指示・2026-09-05）。渡されたPRを読むことが
仕事で、何周目で止まるかは関係が無い。上限を指示側に持たせていたときは、**書き忘れれば誰も止めず**、
実際に [PR #1527](https://github.com/gooyyu1/UnmappedIsland/pull/1527) で4周目が走った——
**指示に書くほど、機械が持つべき不変条件を模型に肩代わりさせることになる。**

### 4.7 一次レビューも同じ観点に絞る

今のサブエージェント一次レビューが空振りするのは、**外のレビュアーが今回どの軽微を拾うかが決まって
いない**からで、当てようがない。4.3 の一覧に絞れば対象が有限になり、手前で拾えるようになる。
`## 自己点検` も短くなる。

### 4.8 「不要になった旧コード」を lint で拾えるか

**半分は既に拾っている。** `eslint.config.js` の `@typescript-eslint/no-unused-vars`（ファイル内の
未使用）と `@typescript-eslint/no-unnecessary-condition`（**型の上で常に成り立つ条件**＝修正で意味を
失った分岐）。

**拾えないのは3つ。** export されていてどこからも参照されないもの（eslint はファイル単位。`knip` を
足せば拾える）・型の上ではあり得るが実行時にはもう起きない分岐・**動くし型も通る「回避策・特別扱い」**
（`CLAUDE.md` 4節の本体はここ）。

**`knip` の追加は今は入れない。** 筋は通るが、4.1 のとおり**この観点で1本も止まっていない。**

## 未決

**決める順序はこちらで決めてよい**（ユーザーの発言・2026-09-05）。着手前に方針だけ述べる。

- **`area:art`・`area:daemon` の他に、どの資源へ錠が要るか**（付けるのは棚卸しとユーザー、で決まった。
  [`parallel-work.md`](parallel-work.md) 2節）。帳面（`conflicts.jsonl`）が溜まってから決める。
  **溜まったものを誰がいつ読むかは未決**——
  `NOTE` と同じで、今は読む者が居ない。**本数の上限は外さない**（3.1）ので、ここには残らない。
- **配れない理由が、誰にも届かない。** `NOTE` は `~/daemon.log` へ出るだけで、定期的に読む者が
  居ない（`board-round.mjs`）。錠を取り合って待っている issue も、知らない `env:` の issue も、
  ここで黙って滞留する。**滞留していることが見える形が要る。** **ラベルを外すことが人の唯一の
  動かし方になった**（2.13.1）ぶん、ここは重くなった——**書いたセッションが畳まれている／名乗って
  いないPRでは、外しても覚え書きが1行出るだけで、外した本人には何も返らない**（2.11）。
  **判定が書かれているのに結論のラベルが付かなかったPRも同じ**（2.13.5）——マージにもレビューにも
  進まないまま、毎周1行だけが出る。
- **二次の記録（`.claude/analysis/summary/<日付>.md`）を、さらに畳む先が要るか**（2.17.4）。一次の
  記録を畳む先は二次で決まったが、**その二次の出力が溜まったときに何が要るかは、溜まってから決める。**
- **自動の手綱（2.5.2）の安全率と、計測が溜まるまでの既定値。** どちらも実際の消費を見ないと決まらない。
  デーモンを動かして計測を貯めるのが先。
- **打てた手より後ろに並んでいた手が転んでいても、機械は見ていない**（2.21.2）。1周1手で切り上げる
  ので、**先に打てる手が絶えない限り、後ろの手はいつまでも試されない**（盤面を見回る係だけは、
  先頭へ置いて外してある。2.21.3）。**見回る係は毎回立つので、`~/daemon.log` から気づける**——
  機械の側にも要るかは、係が実際に取りこぼしてから決める。
