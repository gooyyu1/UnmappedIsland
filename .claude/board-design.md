# 盤面の設計

司令塔の仕組みを、**機械的な処理だけで回る形**へ作り直す。ここは**決まったことを積む場所**——
決まった項目から順に節を足し、まだ決まっていないものは末尾の「未決」に並べる。実装が追いついた
節は、[`parallel-work.md`](parallel-work.md)・各プロンプト・`scripts/agent/**` の側を書き換えて
合わせる。**この文書と実装が食い違ったら、この文書が正。**

向かう先は3つ（出どころ: ユーザーの指示・2026-09-04）。

- **中心は機械的な処理だけに絞る。** 判断が要るものは非同期の別エージェントへ切り離す。今の司令塔が
  やっていることが、自動スクリプトだけで完結する状態を目指す。
- **作業領域の衝突は、投入のときに考えるのではなく、予め棚卸し係が付けたラベルで避ける。**
  領域は一次元ではなく複数次元。
- **ワーカー・レビュアーからの申し送りを中心が読んで総合判断することをやめる。** 急がない懸念
  （アーキテクチャスメル・長期の検討課題）は残す場所を決めておき、後段のエージェントがまとめて拾う。

## 1. 状態の持ち方【確定】

### 1.1 事実と占有を分ける

分ける基準は「**持ち主が死んだとき、その状態は嘘になるか**」。

| | 事実 | 占有 |
|---|---|---|
| 例 | PRの存在・コミットのSHAと時刻・レビューの結論・issue の open/closed・`Closes` の紐付け | 「今このissueを誰かが作業している」「今このPRを誰かがレビューしている」 |
| 持ち主が死んだら | 真のまま | **嘘になる** |
| 置き場 | GitHub。消えてよい理由が無いので、消えない場所でよい | **セッションそのもの**。消えれば占有も消える |

**偽になるべき状態を、自分では消えない場所に書かない。**

`レビュー中`・`作業中` のラベルが破綻するのは、異常終了を防げないからではなく、**占有を事実の
置き場に書いたから**。ラベルは持ち主と無関係に生き続けるので、落ちたセッションのぶんが残り、
掃除役を足すことになる——それは嘘を後から拭く仕事を増やしているだけ。**異常終了は防げないので、
防ぐのではなく「落ちたら勝手に消える表し方」を選ぶ。**

### 1.2 占有は、タグの付いた生きているセッション

`task-<issue番号>` / `review-<PR番号>` のタグを持つセッションが生きていることが占有。生死は
`list_sessions` から引く。**トップレベルの `status` は常に `null` なので使えない**——見るのは
`session_status`・`status_bucket`・`updated_at` の3つ。

| 見るもの | 判定 |
|---|---|
| `session_status` が `SESSION_STATUS_ARCHIVED` | 占有していない |
| `status_bucket` が `SESSION_STATUS_BUCKET_COMPLETED` / `..._FAILED` | その手番は終わっている → 占有していない |
| 上のどれでもなく `updated_at` が新しい | **占有している** |
| 上のどれでもなく `updated_at` が古い | 止まっている → 占有を解いて投入し直してよい |

判定を**「走行中を表す値と一致するか」ではなく「終わっていないこと」**で書くのは、走行中の値の
名前をまだ実測していないため（末尾の未決）。この形なら名前が何であっても正しく動く。

**時間で切るのは最後の1行だけ。** 「返事が無くなった」は他に測りようが無い。それ以外を時刻の比較で
決めないのは、[`watch-prs.sh`](../scripts/agent/watch-prs.sh) の「手番は、時刻の窓ではなく状態で
見る」と同じ。

### 1.3 ラベルには結論だけを置く

- `直し待ち` … レビューが「直しが要る」を出した
- `通してよい` … レビューが通した
- `判断待ち` … 人間の返事が要る

どれも**真であることが、誰かが生きていることに依存しない**。`レビュー中`・`作業中` は置かない。

### 1.4 二重投入は、投入する側が自分で止める

**不変条件「1つの対象に走るセッションは1本」は、投入するスクリプト自身が持つ。**
`dispatch-review.sh` / `dispatch-task.sh` が、立てる前に対象の生きたセッションを 1.2 の判定で引き、
在れば**立てずに終わる**（既に走っていることを終了コードで返す）。

見張り（`watch-prs.sh`）側の黙らせ判定は、合図の数を減らす最適化として残ってよいが、**正しさは
もう見張りに依存しない**——見張りが2回出しても2本にはならない。

残る競合は「2本が同時に、引いて→無い→立てる」を通る数百ミリ秒の窓。**投入の経路をロックで1本に
する**ことで閉じる。

## 根拠（2026-09-04 に実測）

**異常終了は実在する。** セッション `01Wcy9XLj85X`（タグ `review-1493`、09-03T14:57 作成・15:00
更新）は `status_bucket = SESSION_STATUS_BUCKET_FAILED`。3分で落ちている。

**二重投入も実在する。** PR #1493 に、09-03T15:58 の**同じ分**に立ったレビューのセッションが2本
（`01SE1TqFmnRh` / `019gWmVuTtDE`）。結果はPRのコメントに残っていて、**食い違っている**。

```
16:04:59  [レビュー] 直しが要る
16:05:38  [レビュー] 通してよい
16:06:22  [レビュー] 直しが要る
```

83秒に3つ。**二重投入の害は「無駄」ではなく、矛盾した結論のどれを拾うかが運任せになること。**
機械が最初に見つけた「通してよい」を拾ってマージしていたら、他の2本が落とした差分が `main` へ
入っていた。

**本数では見分けられない。** PR #1512 も同じ日に3本立っているが、こちらは正当な再レビュー
（commit 13:25 → 判定 13:31 → commit 13:40 → 判定 13:45 → commit 13:54 → 判定 14:00）。

**原因は「印が無いこと」ではない。** 黙らせる判定は `watch-prs.sh` にあり、`dispatch-review.sh`
には無い。あちらは前のレビューを `archive-reviews.sh` で畳んでから立てるが、これは排他ではないので、
**2本が同時に「畳んで立てる」を通ると2本とも生き残る**。不変条件を、それを作る側ではなく呼び出し側が
肩代わりしていた（`CLAUDE.md`「自分のことは自分でする」）。ラベルを足しても、判定が投入の外にある
限り同じ競合が起きる。

## 未決

決める順序はユーザーが決める。着手前にどれを扱うか確認する。

- **走行中のセッションの `session_status` / `status_bucket` の値**（未実測）。1.2 はこれを知らなくても
  成り立つ形で書いてあるが、実測できたら表へ足す。
- **作業領域の多次元ラベル。** 今の [`parallel-work.md`](parallel-work.md) 2節「所有権の地図」は
  6分割の一次元。棚卸し係が予め付ける形にする。
- **必須でない懸念の受け皿。** `## 司令塔へ` を廃止した後、レビュアーの懸念・アーキテクチャスメルを
  どこへ残し、誰が拾うか。直近10PRを読んで傾向を見るエージェント、その上でさらに長期の検討課題を
  拾う段。
- **人間への入力の口。** issue #656 のチェック方式を、マージの許可と仕様の確定とで分けるか。
- **機械ループの実行基盤。** 司令塔をモデルのセッションから外せるか（`ccr-meta.sh` はモデルを要さない
  ので、bash のデーモンだけでセッションの作成・送信・畳みができる）。外すなら #732・`handover.sh`・
  [`commander-prompt.md`](commander-prompt.md) が不要になる。
- **収束しないPRの扱い。** PR #1493 は「5周目の指摘を処置して push」まで行っている。無人で回す以上、
  何周しても終わらないPRが延々回る。周回数を状態として持ち、しきい値で `判断待ち` へ倒すか。
- **移行の順序。**
