# 並列作業の進め方

多数のエージェントで同時に開発を進めるための取り決め。**このファイルは進め方だけを持つ。**
確定度の印は [`docs/DocumentStyle.md`](../docs/DocumentStyle.md) 6節、確認の積み方と
「担当外は触らない」は [`CLAUDE.md`](../CLAUDE.md) が持つので、ここでは繰り返さない。

## 1. 分かれ目は「書くかどうか」

| 作業 | 走らせ方 |
| --- | --- |
| 読むだけ（調査・分類・棚卸し） | **同じセッションのサブエージェント** |
| 書く（実装・PR） | **別セッション。1タスク = 1 issue = 1ブランチ = 1PR** |

書く作業を別セッションにするのは、次の3つが順に効くため。

1. **作業ツリーが物理的に分かれる。** 同じセッションのサブエージェントは同じチェックアウトを
   共有するので、並列で書くと整形の PostToolUse フックや git の状態を互いに壊す。
2. **統合機構が既にある。** 1セッション = 1ブランチ = 1PR は今の運用そのままで、追加の仕組みが
   要らない。1セッションから複数ブランチを作ると、この運用から外れる。
3. **SessionStart フックが確実に掛かる。** `inject-policies.sh` が価値観を流し込むのはセッション
   単位。サブエージェントに同じ文脈が入る保証は無く、価値観の記録が空振りしうる。

読むだけの作業を同じセッションに置くのは、衝突が起きず、結果が1箇所へ集まり、**ユーザーの手数が
ゼロ**だから。

## 2. 所有権の地図

**1タスクの編集が1領域に収まること**が、並列に流せる条件。収まらないものは分けるか、直列にする。
この6分割は定義位置レビュー（`review/placement/`）の調査で実証済み。行数は `.ts` の実測。

| 領域 | 範囲 | 行 |
| --- | --- | --: |
| 1 | `src/domain` 直下 | 7,261 |
| 2 | `src/domain/generation`・`wrappers` ＋ `src/loader` | 5,655 |
| 3 | カード・レーン ＋ `src/ui` ＋ `src/art` | 4,284 |
| 4 | ウィンドウ（`src/game/ui` の `*Window`・`*Pane`） | 約 3,000 |
| 5 | `src/game` 直下 ＋ `view` ＋ `looks` | 8,320 |
| 6 | `src/analysis` ＋ `src/codex-viewer` ＋ ほか | 7,722 |

**`src/game` は層ではない。** [`docs/engine/Layers.md`](../docs/engine/Layers.md) 4節のとおり
映し・意匠・部品・組み立ての4層にまたがり、この地図では3・4・5に割れる。

### 縦のスライスは、この地図では割れない

機能追加は層をまたぐので、上の横割りには乗らない。縦を割る基準は**文法を足すかどうか**で、
判定材料は**各設計文書の概要に既に書いてある**（`DocumentStyle.md` 2節が「新設した文法は何か。
新設ゼロならそれを明記する」を要求している）。

- **文法を足す** → `GameElementDefinition.md` と `loader`・`domain` という単一の hub を通るので、
  何本流しても直列寄り。**まとめて1本にする。**
- **宣言だけで書ける** → 専用の YAML と専用の設計文書だけを触るので、**互いに衝突しない。**

## 3. タスク issue の型

1タスク = 1 issue。ユーザーはその URL を新しいセッションへ貼るだけで指示が済む。

```markdown
## T-4 雨で溜まる水を「数えられない経路」として立てる

- **担当**: `src/analysis/balanceTables.ts` / `tests/diagnostics/balanceStatsReport.test.ts` /
  `docs/diagnostics/BalanceStats.md`
- **完了**: 4つのコマンド ＋ `npm run stats:balance` の出力に `### 数えられない経路` が現れ、
  `water_liquid` が「島全体で入手経路が無いもの」から消えること
- **拠り所**: `BalanceStats.md` の「この表が数えていないもの」節（暫定）
```

- **「触ってはいけないファイル」は書かない。** 担当の列挙で補集合が決まる。
- **「止まる条件」も書かない。** 既定は仮決めして進むことで、例外は確定節に反する変更が要るとき
  だけ。`【確定】` の印がその条件を既に表している。
- ブランチ名はセッションごとに自動で割り当たるので指定しない。

## 4. 段の分け方

探索を並列させない。**同じ発見を N 回繰り返し、出力が揃わなくなる。**

1. **段0 — 未実装9件の要否判断**（ユーザー／issue #656）。骨格待ちのものは保留する。
2. **段1 — コンテンツの骨格を決める**（ユーザー＋1体）。系統が何本・各系統が何段・終盤に何が要る
   か・アーティファクトが何種類か。**個々のレシピは決めない**（仮決めでよい）。
3. **段2 — 文法追加をまとめて1本**（直列）。骨格が決まっているので、本当に要る文法だけを入れる。
4. **段3 — コンテンツの幅出し（並列の本命）＋ 宣言だけの機能**。
5. **段4 — 統合と計測**。他のタスクと同じものを別名で作っていないかを見る（既存のテストは
   これを見ていない）。`npm run stats:balance` で日数が成立するかを測る。

段1を段2より前に置くのが肝。**骨格が決まると、文法追加のうちどれが本当に要るかが決まる。**

### コンテンツを後回しにしない理由

`npm run stats:balance` が「1日を賄う最小労働 624分（1440分の43.4%）」と出している。残りの56.6%に
することが無ければ100〜200日は成立せず、生存コストを上げて日数を伸ばすのは
[`DesignPrinciples.md`](../docs/concept/DesignPrinciples.md) の「時間経過に任せる区間を作らない」と
衝突する。**コンテンツ不足は仕組みの未検証と同じもので、後に回すほど手戻りが大きい。**

コンテンツの幅出しは、仕組みの実装よりスウォームに向いている——触るファイルが YAML 24本に分散し、
完了条件を `stats:balance` が定義だけから計算し、系統どうしが干渉せず、量がある。

## 5. 次にやること

1. `create_session` が使えるか確かめる。使えれば、書く作業のセッションもエージェントが立てられる。
   使えなければユーザーが立てる（issue の URL を貼るだけ）。
2. 水の件のタスク issue を2本立てる。
   - 雨で溜まる経路を `untimed` として立て、`### 数えられない経路` に出す（仮定ゼロ）。
     いま `water_liquid` は「入手経路が無いもの＝内容の穴」へ落ちていて、`BalanceStats.md` の
     「1節の『数えられない経路』へ分けてある」という注記と食い違っている。
   - 待ち生産表へ「容器1種ごと・季節ごとに1日返す水（蒸発差引後）」を足す。降雨は
     `ClimateSystemStats.md` に実測済み、蒸発は `LiquidContainerSystem.md` 6節に定義値があるので、
     置く仮定は容器の数だけ。**単一の平均は出さない**——序盤と後半の差が本質で、平均は存在しない
     中間の状態を測ることになる。
3. 段0（未実装9件の要否判断）を issue #656 へ積む。9件それぞれに「実装する／しない／骨格待ち」を
   リポジトリを開かずに判断できる形で書く。
