# 並列作業の進め方

多数のエージェントで同時に開発を進めるための取り決め。**このファイルは進め方だけを持つ。**
確定度の印は [`docs/DocumentStyle.md`](../docs/DocumentStyle.md) 6節、確認の積み方は
[`CLAUDE.md`](../CLAUDE.md) が持つので、ここでは繰り返さない。

**人間向けの全体像は [`docs/ParallelAgents.md`](../docs/ParallelAgents.md)。** 誰が何をして人間はどこで
決めるのかを図で示す。**規則を書くのはこちらだけ**で、あちらは全体像だけを持つ（同じ説明を二度書かない）。

## 1. 分かれ目は「どこかに書くか」

| その役が書く先 | 走らせ方 | 例 |
| --- | --- | --- |
| **どこにも書かない**（結論を親へ返すだけ） | **同じセッションのサブエージェント** | PRを出す前の自己レビュー |
| **どこかに書く**（作業ツリーのファイル・PR・コメント・issue） | **別セッション。1タスク = 1 issue = 1ブランチ = 1PR** | 作業者、レビュアー、棚卸し役、掘り起こし役 |

**「読むだけならサブエージェント」ではない。** レビュアーも棚卸し役も読む仕事だが、どちらも別
セッション——**書いたものが記録として残り、それが次を動かす合図になる**（判定のラベル・`## 未整理`）。
合図を読むのはデーモンで、**書いた側が生きている必要はない**ので、親と運命を共にするサブエージェント
には置けない。

どこかに書く作業を別セッションにするのは、次の3つが順に効くため。**1と2が効くのはファイルへ書く役
（作業者・相談役）で、3は書く先によらない。** GitHubへ書く役（レビュアー・棚卸し役・掘り起こし役）を
別セッションにする理由は、上の段落にある記録と合図のほう。

1. **作業ツリーが物理的に分かれる。** 同じセッションのサブエージェントは同じチェックアウトを
   共有するので、並列で書くと整形の PostToolUse フックや git の状態を互いに壊す。
2. **統合機構が既にある。** 1セッション = 1ブランチ = 1PR は今の運用そのままで、追加の仕組みが
   要らない。1セッションから複数ブランチを作ると、この運用から外れる。
3. **SessionStart フックが確実に掛かる。** `inject-policies.sh` が価値観を流し込むのはセッション
   単位。サブエージェントに同じ文脈が入る保証は無く、価値観の記録が空振りしうる。

どこにも書かない作業を同じセッションに置くのは、衝突が起きず、**読んだ量が子の文脈に留まって親へは
結論だけが返り**、ユーザーの手数がゼロだから。

### PRを出す前の自己レビューは、サブエージェント

**PRを作る前に、これから出す差分をサブエージェントへ読ませる。** 手順は `CLAUDE.md`「PRを出す前に、
サブエージェントへ一次レビューさせる」が持つ。渡す観点は [`review-criteria.md`](review-criteria.md)
——**外のレビュアーが読むのと同じ一覧**。

**通るのは、誰が出すPRかによらない。** 作業セッションも相談役もユーザー自身も同じで、免除は無い。手順を
`CLAUDE.md` に置いてあるのはそのためで、`dispatch-prompt.md` にだけ書くと作業セッションのPRしか
通らない。結果は `## 自己点検` 節へ書く（形は `CLAUDE.md`「PR本文に置く節」）。

**これで外のレビューが要らなくなるわけではない。** サブエージェントは親と同じチェックアウトに
居るので、**素通しした結果は誰にも記録されない**——止める権限を持てるのは、GitHubへ書く別セッション
だけ。手前の1本は往復の回数を削るためのもので、往復そのものを置き換えるものではない。

### GitHubへ書く作業をどこへ立てるか

実行元ごとに、確実に起動する隔離先を選ぶ。

| 実行元 | 立てる先 |
| --- | --- |
| Claude | **クラウド優先**。画像の生成（ComfyUI）だけ**ブリッジ環境へ投入する** |
| Copilot | **ローカルworktree**。クラウドは使わない |

Claude はローカルの枠を画像生成のために空ける。Copilot のクラウド起動は失敗する経路であり、隔離は
ローカルworktreeで確保できる。実装・ドキュメント・画面の動作確認もこの原則に従う。

**画像生成も「投入する」。気づいた側が自分で抱え込まない。** ここでの「ローカル」は**投入先の環境の
名前**であって、そのセッション自身が作業することではない。**この読み違いを一度やっている**
（2026-08-28、「絵の生成は ComfyUI 依存なのでタスクとして投入できない」とユーザーへ報告した。
実際にはブリッジ環境へ投入すれば済む話だった）。**タスクとして出せないものは無い。**

`create_session` は既定で**呼び出し元と同じ環境**に立つので、環境を選ぶには `environment_id` を
渡す。IDは `bash .claude/ccr-meta.sh list_environments <<<'{}'` の `kind` が `bridge` のもの。

```bash
bash .claude/ccr-meta.sh list_environments <<<'{}'   # kind が bridge のIDを取る
# args.json に "environment_id": "env_..." を足してから立てる（他は普段どおり）
bash .claude/ccr-meta.sh create_session < args.json
```

セッションはエージェントが立てられるので、ユーザーの手数は「issue に答える」だけ。**`permission_mode`
は立てる先から決まる**ので、[`ccr-env.sh`](../scripts/agent/ccr-env.sh) から取る——ブリッジへは渡さず、
クラウドへは `auto`。**省いてクラウドへ立てると、`.claude/**` を読むだけで降りない承認を待つ。**

**`title` は定型に従う**（[`board-design.md`](board-design.md) 2.9 の表）。一覧を読むのは人間で、
タグは機械の見分けなので読めない。手で立てる1本——ユーザーに頼まれて立てる盤面の外のもの——は
`相談 <相談内容>`。

#### 立てる・確かめる・畳むは [`ccr-meta.sh`](./ccr-meta.sh)

**入口はこれ1つ。** `mcp__ccr_meta__*` は**起動時のヘッダを掴んだまま**で、走っている最中に
トークンが切れると、登録を直しても**そのセッションからは二度と使えなかった**（2026-08-25 に2回
起きた）。登録は道具の一覧に残っているが、呼ぶと
[`hooks/deny-ccr-meta-mcp.sh`](hooks/deny-ccr-meta-mcp.sh) が拒否してここへ案内する。

```bash
bash .claude/ccr-meta.sh create_session < args.json
bash .claude/ccr-check-prompt.sh <セッションID> <送った指示のファイル>
bash .claude/ccr-meta.sh archive_session <<<'{"session_id": "cse_..."}'
```

**ただし投入は [`dispatch-task.sh`](../scripts/agent/dispatch-task.sh) から呼ぶ。** 上の3行は入口の説明で、
投入のたびに手で組むものではない——引数の組み立て・立てた中身の確認・照合まで含めて1回で済む。

```bash
bash scripts/agent/dispatch-task.sh 1029 "$LOCALAPPDATA/Temp/ui-1029.md"
bash scripts/agent/dispatch-task.sh 1029 <指示ファイル> --bridge   # 画像生成など
DRY_RUN=1 bash scripts/agent/dispatch-task.sh 1029 <指示ファイル>  # 渡す引数を見るだけ
```

**盤面が配るときは、投入先を issue の `env:` から決める**（[`board-design.md`](board-design.md)
2.16）。手で叩くときだけ、上のように直に指定する。

**引数は標準入力で渡す**（argvではない）。**呼ぶたびに `~/.claude/.credentials.json` から読み直す**ので
切れない。**道具も引数も普段と同じで、23個すべてが使える**——MCPサーバもただのHTTPで、しかも
ステートレスに応じるため、`tools/call` を1発投げるだけでよい。

**指示の本文は [`dispatch-prompt.md`](./dispatch-prompt.md) を写して作る。** 手で書き起こすと落ちる
（2026-08-27 に「PRを見張らない」が3本すべてから抜けた）。

**立てた直後に [`ccr-check-prompt.sh`](./ccr-check-prompt.sh) を通す。** 指示が化けても壊れても
セッションは普通に動き出すので、**動いている様子は判断材料にならない**（2026-08-25 に、丸ごと化けた
指示で20分走らせた）。届いた本文と送ったファイルを文字列で突き合わせて、一致だけを信じる。

**RESTを逆算しない**（`/v1/code/sessions` を直に叩く道もある）。形が違ううえ
（`sources` は入れ子ではなく平ら）、**`DELETE` は畳まずに消す**——同じ意味の操作を2通り持つ理由が無い。

`RemoteTrigger` でも立てられるが、**トリガー発火の実行はセッション一覧に出ない**——ユーザーが進み
具合を見に行けないので、上を先に使う。

### 盤面を回す仕組みを止めたままにしない

**指示なしで盤面を回し続けるのは [`daemon.sh`](../scripts/agent/daemon.sh)。** レビューの投入・
直しの再開・マージ・新しいタスクの投入は、**モデルのセッションが1本も起きていなくても進む**。
**これが止まっている間、盤面は1ミリも動かない。**

**デーモンは自分では終わらない。** 盤面を続けて引けなくなっても、待つ間隔を落として回り続ける
（認証切れも通信断も自分では直せず、放っておくと直るので）。**止まるのは `stop` で撃たれたとき・
走らせているPCが落ちたとき・入れ替わった先が壊れていたときだけ。**

**それでも止まったら、監視係が起こす**（[`board-design.md`](board-design.md) 2.19）。CCRの Routine が
1時間ごとにブリッジへ立てるセッションが、心拍を見て `start` を打つ。**人が気づく必要があるのは1つ
だけ**——`claude remote-control` が上がっていないと Routine も発火せず、**上がっていないことを
知らせる者は原理的に居ない**（同 2.19.4）。

```
bash scripts/agent/daemon.sh start     # 背景で立てる。ログは ~/daemon.log へ追記
bash scripts/agent/daemon.sh status    # 生死だけを見る（生きていれば0）
bash scripts/agent/daemon.sh stop
bash scripts/agent/daemon.sh restart   # 直接 push した版や環境変数を、すぐ効かせるとき
```

**走っているかを確かめてから `start` を打ってよい。** 二本目は自分で引き返す（`daemon.sh`「二重に
起こさない」）。**プロセスを探して撃たない**——`stop` が錠に置かれたPIDを撃つ（同「止めるのも
自分の仕事」）。

**`main` へ入れた `daemon.sh` は、マージを打った次の周から効く。** マージの周で本体が `main` へ進み、
その周の終わりにデーモンが気づいて新しい版で回り直す（同「走るのは複製」）。**直接 push しただけでは
本体は進まない**ので、マージを待たずに効かせたいなら `restart`。

**ユーザーからの依頼が来ても、これより先に着手しない。** 依頼が数分遅れることは目に見えるが、
**盤面が止まっていることは誰にも見えない**。2026-08-30 に前身の見張りを止めたまま `CLAUDE.md` の
手入れをして、再開時に26件（レビュー待ち6本・直しが戻ったPR1本・マージできるPR1本・配れる task
18件）が一度に出た。

**打った手はログに残る。** `tail ~/daemon.log` が、いつ何を打ったか・打てなかった理由
（`覚え書き:` の行）をそのまま見せる。

**止めるのは手綱の issue のチェックを外すこと。** [`brake.sh`](../scripts/agent/brake.sh) を毎回
読むので、外れている間はその種類の手だけが打たれない。**デーモン自体は止めない**——止めると
レビューもマージも一緒に止まる。止める場面は6節「ユーザーが投入を止めると告げたら、入口だけを
一律に止める」。

**ユーザーがマージを止めるには、`通してよい` を外すか `却下` を付ける。** PRの作者が全部
ユーザー自身になるためGitHubは Request changes を出させず、**コメントを書いてもデーモンは読まない**
（読むのはラベルだけ）。

### 直列に並べたタスクを、誰も待たない

**前段が終わるのを待つ仕組みは要らない。** デーモンは毎周 `blockedBy` ごと盤面を引き直すので、
**塞がっている間はその issue が候補に出ないだけ**で、空いた周に自然と出てくる（下の
「配れる `kind:task` は、盤面から毎周引き直す」）。待つ側を用意すると、**待っている最中に前段が
取り下げで閉じた場合に誰も気づかない**。

なお、issue はセッションが閉じるものではない（[`CLAUDE.md`](../CLAUDE.md)「タスクの issue を渡された
とき」）。閉じさせていた頃は、**まだ main に何も入っていない時点で「完了」の合図が出ていた**
——実測で8件中6件が、PRのマージより最大21分早く閉じられていた。

### 長く回るセッションの文脈は、放っておくと1応答50万トークンになる

**無人で回り続けることは目的なので、抑えるのは動きの量ではなく1回あたりの単価**
（6節「無人で進むことは、目的であってコストではない」）。

2026-08-26 に5時間の上限へ当たったときの実測——**960応答で読み込み531M**、1応答あたり**平均553k・
最悪923k**。出力は1応答あたり983トークンしかない。**書いた量ではなく、読み直した量で消えている。**

手は2つで、どちらも効く。

- **`~/.claude/settings.json` の `autoCompactWindow`**（10万〜100万の整数、単位はトークン）。
  1M文脈のモデルでは既定が実質100万なので、**50万を超えてから畳まれていた**。状態は文脈ではなく
  盤面（ラベル・issue・デーモンのログ）に在るので、狭めて失うものがほぼ無い。
  **200000 を入れてある。**

  **これ以上は下げられない。** 20万未満を入れると判定が `window < 200000` で打ち切られ、
  **自動コンパクションが丸ごと止まる**——畳まれないまま上限まで伸びるので、締めたつもりで逆を
  向く。20万は有効なまま取れる最小値ちょうど。実効の発火点は、ここから出力枠の予約2万と
  バッファ2割を引いた**14.4万トークン**。
- **Bashを1回にまとめる。** 文脈を膨らませていた首位は Bash で、**688回・15万トークン**。ただし
  1回あたりは220トークンで、**巨大な出力が数個あるのではなく小さいものが688個**だった。
  `gh pr view` と `git log` を別々に打つのをやめるだけで、回数も総量も減る。

  **決まりきった並びはスクリプトへ畳んである。** 1サイクル10〜14回だったものが5〜7回になる。

  | 何をするとき | 打つもの |
  |---|---|
  | 盤面を見る | [`board.sh`](../scripts/agent/board.sh)（開いているPR・`kind:task` の issue・畳んでいないセッションを1つの表に） |
  | 投入する | [`dispatch-task.sh`](../scripts/agent/dispatch-task.sh)（`<issue番号>` と指示ファイル） |
  | マージして片付ける | [`merge-and-close.sh`](../scripts/agent/merge-and-close.sh)（`<PR番号>`） |

  **投入とマージはもう [`daemon.sh`](../scripts/agent/daemon.sh) が打っている。** 手で打つのは、
  デーモンが手を出さないものを捌くときだけ。

  **畳んだのは往復だけではない。** 手で叩くと省かれていた確認——`blockedBy`・`tags`・投入前の
  issue の `state`——が、必ず通るようになっている。判断が要るのは**合図をどう捌くか決めるところ**と
  **指示文を書くところ**の2つだけで、そこは畳んでいない。

**PRを読むときは全文を入れない。** 下の「PR の型」の表に挙げた節と、チェックの結果と、触った
ファイルの数で足りる。

```
gh pr view <番号> --json body --jq .body | tr -d '\r' |
  awk '/^## /{ p = /^## (仮決め|見た目|ユーザーの指示)$/ } p'
```

**`tr -d '\r'` を省かない。** 節の名前を `$` で留めているので、CRが乗った本文ではどの節とも一致せず
**何も出ない**（盤面の道具も同じ用途では落としている。[`brake.sh`](../scripts/agent/brake.sh)）。

**文脈へ入れたものの費用は「その大きさ×残りのターン数」**で、1回の読み込みでは終わらない。

### 投入する直前に、その issue が開いているかを見る

[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh) は、題を引くのと同じ `gh issue view` で `state` も
見て、開いていなければ立てずに終わる。**前に一覧で見たときの状態は当てにならない**——ユーザーは
issue をいつでも閉じる（取り下げ・却下・別のPRが `Closes` で閉じた）。

閉じた issue へ立てると、セッションは指示どおり「仕事は無い」と判断して即終了する。**立てる手が
1つ無駄になるだけでなく、そのタグのセッションが居ることになる**ので、盤面はその issue を投入済みと
読み続ける。2026-08-25 に、却下されて閉じた issue へその16分後にセッションを立てた。

**立てた後にユーザーが閉じることもある。** そちらは
[`board-move.mjs`](../scripts/agent/board-move.mjs) の側で消える——閉じた issue は盤面に出てこない
ので、`stall` の手も出ない。残ったセッションは下の「終わったセッションは、issue を鍵にして畳む」で
畳む。

### 終わったセッションは、issue を鍵にして畳む

仕事をしたセッションは、[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh) が付ける
`task-<番号>` のタグで引く（盤面が `stall` の相手を引くのと同じタグ）。**PRが出たかは見ない**
——PRをマージしたかとワーカーを畳んでよいかは別の問いで、繋ぐと人が画面からマージしたときに畳む手が
走らない（[`board-design.md`](board-design.md) 2.10）。畳む条件は次のとおり。

- **その issue が、もうそのセッションの仕事ではない。** 閉じているなら、閉じるのはマージのときなので
  入ったか取り下げられたかのどちらかで、いずれも仕事は終わっている。開いていても `判断待ち` が
  付いているなら、人の手番へ移っている（[`board-design.md`](board-design.md) 2.15.3）。
- **自分が立てたセッション。** **ユーザーが立てたものには触らない**——走っている作業を止めること
  になる。あちらは `task-` のタグを持たないので `KEPT` に落ちる。**ブリッジで立てたものも同じ
  条件で畳む**——違うのはこのPCに worktree を持つことだけで、それは畳んだ後に何を片付けるかの話
  （[`archive-session.sh`](../scripts/agent/archive-session.sh)）。
- **素性を引けなかったものも `KEPT`。** `get_session` が引けないと全部のキーが空に落ち、何も持たない
  ものとして扱われる。**知らないことを「違う」として読まない**——畳んで消えたコメントも、消した
  worktree も戻せないので、引けなかったものは残す。

**状態で判定しない。** 走行中かどうかは分かる（`session_status`。見方は
[`board-design.md`](board-design.md) 1.6。盤面の `stall` も同じ見方で走行中を除いている）が、
**知りたいのは「仕事が終わったか」で、それは待機中の中身**にある。
待機中には「レビューを書き終えた」も「こちらからの追加指示を待っている」も落ちるので、
区別が付かない。「完了してから一定時間」も同じ理由で使えない。**畳んでよいかは、上のような外から
見える出来事で決める。**

**走行中を除くのは、これとは別の問い。** `archive_session` はコンテナを解放するので、判定を書いて
いる最中のセッションを畳むと、そのコメントは出ないまま消える。**除くのは渡す側**——盤面は手が
動いているセッションに手を出さない（[`board-design.md`](board-design.md) 1.2）。畳む側で除くと
`KEPT` が返り、盤面はそれを**安定した答え**として指紋に残すので、走行中がたまたま重なった1回で、
その相手が二度と畳まれなくなる。

畳んだセッションは戻せる（unarchive）ので、猶予は置かない。

#### レビューのセッションは、判定を書いたかを見て畳む

レビューは issue を持たないので、上の鍵では引けない。手掛かりは
[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh) が付ける `review-<PR番号>` のタグだけ。
**合図はそのPRに判定のコメントが在るかで、そのPRがこの後どう流れるかは見ない**——レビューは
使い回さないので、書いた時点でもう誰も起こさない。**手が止まっていることは合図ではない**
——書かないまま空いたままのレビューは、畳む前に1回だけ起こす（[`board-design.md`](board-design.md) 2.10.3）。

**畳むのは盤面が打つ手。** マージや次の投入のついでに掃いていた頃は、**それが起きないPRのぶんが
残った**（2026-08-30 に16本、2026-09-05 に人が画面からマージした #1549 のぶん）。上の `task-` と
同じ誤りで、直し方も同じ——畳むことを別の出来事に繋がず、盤面が毎周見る。

**ブリッジで立てたレビューも、素性を引けなかったものも、扱いは上の `task-` と同じ。**

#### 配れる `kind:task` は、盤面から毎周引き直す

[`board-move.mjs`](../scripts/agent/board-move.mjs) は、**`kind:task` の付いた open な issue のうち、
open な `blockedBy` が無く、open なPRが `Closes` で指していないもの**を `TASK <番号>` として出す。
落ちる3つは、どれも**投入する先が無いか、既に誰かの手元にある**もの——`kind:task` の無い issue
（確認の置き場・ユーザーの答え待ち・まだ棚卸しが見ていないもの）は仕事の単位ではなく、依存が
残っているものは投入しても着手できず、PRの出ているものはそのセッションが持っている。

**古い番号から配る。** `gh issue list` は新しい順に返るので、そのまま使うと古い issue が永久に
後回しになる。**先に配ってほしいものには `急ぎ` を付ける**（[`board-design.md`](board-design.md)
2.18。効き目は順だけで、投入の上限も錠も越えない）。

**投入していい本数には上限がある**（[`board-design.md`](board-design.md) 3.1。**何が並べてよいかは
2節**）。投入済みかどうかは `dispatch-task.sh` が付ける `task-<番号>` のタグで読むので、
番号を数え上げて渡す必要は無い。

**投入したくない issue は、手綱のチェックを外して全部止めるか、`判断待ち` を付ける**（分類の
`kind:task` は外さない。[`board-design.md`](board-design.md) 2.17.1）。
盤面の側に「この番号だけ黙らせる」口は無い——番号の一覧を人が持ち回ることになり、
**渡し忘れがそのまま二重投入になる**。

#### まとめて掃除する形にはしない

**「気づいたときにまとめて畳む」をやめる理由は、遅れが仕事と無関係にばらつくこと。** 実測（2026-08-25）
では issue が閉じてから畳むまでが2分・23分・30分で、**差を作っていたのは仕事の中身ではなく「次に
別の用事で起こされた時刻」だった**。盤面が毎周見れば、そのばらつきごと消える。

**一定時間ごとに自分を起こして掃除する形は採らない**（`send_later`）。自動承認ができないので、掃除
1回ごとにユーザーのタップが要る——放っておいても壊れないものに、それは高すぎる。

### 本体のチェックアウトは、マージのたびに追随させる

作業ツリーは `<repo>/.claude/worktrees/` に置かれる。**リポジトリの中なので、Node も npm も親を
遡って本体の `node_modules` を共有する。** 作業ツリーごとに `npm install` を打つ必要は無い。

**共有先が古いと、共有しているのに版が食い違う。** 誰も本体では作業しないので、放っておくと本体は
古いままになる。落ち方は `Cannot find module` ではなく、**古い版が解決されて一部だけ壊れる**——本体が
`ajv` 8 を持たず eslint 由来の 6 だけ在ったとき、`require` は通ったままテストが1本落ちた。踏んだ側は
自分の変更を疑う。

そこで [`merge-and-close.sh`](../scripts/agent/merge-and-close.sh) が、マージと同じ1回で本体を
`origin/main` へ進める（`SYNCED`）。`package-lock.json` が動いたときだけ `npm install` も打つ
（`INSTALLED`）。**本体はブランチを持たない（detached HEAD）**——`main` は同時に2箇所へチェックアウト
できず、本体が握ると作業ツリーが作れなくなる。detached は「固定」ではなく、指す先を毎回新しい `main`
へ付け替える形。本体に未コミットの変更があるときは触らず `DIRTY` を出す（未追跡は見ない）。

**作業ツリーの側は直さない。** [`session-start.sh`](hooks/session-start.sh) は、自分の
`package-lock.json` と共有先に実際に入っている木を突き合わせて、足りなければ名指しで促すだけ。
ここで `npm install` を打つと250MBの複製ができて共有が終わるうえ、**共有先を読んでいる他のセッションの
足元が揺れる。**

### PRが出ないまま手が空いたセッションは、1回だけ起こす

**待機中（IDLE）は「終わった」と「止まった」の区別が付かない。** 利用制限・権限の確認待ち・失敗で、
セッションはPRを出さないまま待機中になる。GitHub の側には何も現れないので、ラベルにも issue にも
出ない。

2026-08-28 に、投入した4本（#915・#932・#953・#936）が同じ分に止まり、**3時間そのままだった**。
気づいたのは、別の用事で `list_sessions` を打ったとき——PRを5秒ごとに見張っていたが、
一度も知らせていない。

[`board-move.mjs`](../scripts/agent/board-move.mjs) は、**手が動いておらず、その `task-<番号>` を
`Closes` で指す open なPRも無い**セッションへ `RESUME <ID> stall <番号>` を出す。渡す文は
[`resume-prompt.md`](resume-prompt.md) の `## stall`。

- **判定は「PRを出したか」だけ。** セッションの状態では、書き終えて報告した IDLE と途中で落ちた
  IDLE が区別できない。突き合わせるのは **`Closes #<番号>` と `task-<番号>` タグの対応**。PR本文の
  脚注に入るセッションのIDだけでは足りない（本文を書き直したPRで脚注ごと落ちる。2026-08-29 の
  #1177・#1178）。枝の名前でも引けない——ブリッジのセッションの `current_branches` は worktree の
  ローカル枝で、push する枝とは別物。
- **起こすのは1回だけ。** 指紋が `stall:<番号>` なので、一度打てば同じ手はもう出ない
  （[`board-design.md`](board-design.md) 1.1）。起きても動かないセッションを毎周叩き続けない。
  **それでも動かなければ、次の周に盤面がその仕事を人へ返す**（[`board-design.md`](board-design.md) 2.15.3）。
- **人の判断を待つセッションは残さない。** 待つ側は答えが来るまで枠を握るので、**待たずに仕事を
  返して畳む**（[`board-design.md`](board-design.md) 2.15）。答えが出たら、返した issue から
  `判断待ち` を外せば、新しいセッションが答え込みで読み直す。

### ユーザーの答えは、まだ機械が拾わない

確認の置き場（#656）は**タップ1つで答えられる形**にしてあるので、**答えはコメントではなく本文の
チェックボックスに付く**。コメントだけを見張っていると、タップは誰にも届かない——ユーザーからは
「タップしたのに何も起きない」、拾う側からは「何も来ていない」としか見えず、**両者は区別が付かない**。
最小の入力を用意した意味が、そこで丸ごと消える。

判定は [`checked-items.sh`](../scripts/agent/checked-items.sh) が1箇所で持ち、
[`board.sh`](../scripts/agent/board.sh) の `## 確定待ち` がそれを出す。**チェックは出来事ではなく
状態**なので、いつ付いたかに関わらず、一覧から下りるまで出続ける。

**デーモンはこれを読まない。** 拾うのは判断の要る仕事で、**届ける口はまだ無い**
（[`board-design.md`](board-design.md) 3.3 の未決）。今は [`board.sh`](../scripts/agent/board.sh) を
見に来た者が拾うほかない。

- **黙る条件は、項目を一覧から下ろすこと。** 拾った側が答えの行き先を `## 下ろした項目` へ書いて
  項目を消すと、`[x]` の箇条書きでなくなるのでそこで黙る。**`【確定】` の印は待たない**——印を付けるのは
  答えを受けた issue の担当者なので、待つと下ろした後も一覧に残る。
- 片付け方は下の「束ねる関門は、ゲートの issue を1件立てる」のとおり。

## 2. 同時に走らせてよいか

**止めたい理由ごとに、別の仕組みが持つ。**

| 止めたい理由 | 持つ仕組み |
| --- | --- |
| **同時に1本しか動かせない資源** | **錠**（`area:` のラベル）。`area:art`（GPUを専有する画像生成）・`area:daemon`（動かしながら書き換えられないデーモン）から始める |
| **順序に理由がある** | **`blockedBy`** |

**同じファイルを2本が書くことは止めない**（出どころ: ユーザーの指示・2026-09-06）。ぶつかったら
コンフリクトとして出るので、盤面が `mend` で直させる。**止めない代わりに、ぶつかった実績を控える**
（下の「ぶつかった実績は控える」）。

**層で切った所有権の地図も持たない**（出どころ: ユーザーの指示・2026-09-06）。効くのはファイルの
衝突にだけで、**文書には効かない**——文書は主題で並ぶので、層で切った担当とは軸が直交する。

**錠は地図ではない。** 付けるのは「同時に1本しか走れない実体」だけで、ゲームのコードには原則
付けない。**意味の上で干渉するもの**（同時に足すと解析の期待値が互いにずれる、など）を錠にするかは、
**実際にコンフリクトが観察されてから決める**（出どころ: ユーザーの指示・2026-09-06）——起きていない
衝突のために並列度を下げない。

**付けるのは棚卸しとユーザー。デーモンには付けさせない**——どの資源が1本しか使えないかを
知っているのは人で、盤面はラベルを読むだけ。棚卸しが分類するときに、担当から明らかなものを付ける
（[`triage-prompt.md`](triage-prompt.md)）。

**錠は [`board-move.mjs`](../scripts/agent/board-move.mjs) が投入の前に見る。** 走っている
セッションの担当 issue と同じ錠を持つ issue は出さない。**素性を引けなかった相手の後ろでも出さない**
——同じ錠を持っていないことを確かめられないので、資源を2本で取り合う形が通ってしまう。

**本数の上限も別に置いてある**（抱えている数と手が動いている数の2つ。
[`board-design.md`](board-design.md) 3.1）。錠を持たない issue はいくらでも並ぶので、
**手綱はそこにしか無い。**

### ぶつかった実績は控える

同じファイルを2本が書くことを止めない代わりに、**実際にぶつかった組を帳面へ残す**。`area:` の錠を
足すべき資源を、**起きた衝突から決める**ため（上の「錠は地図ではない」）。

[`board-round.mjs`](../scripts/agent/board-round.mjs) が周ごとに、コンフリクトしているPRを
`~/.claude/board-state/conflicts.jsonl` へ1行1件で書く。中身は
[`describe-conflict.sh`](../scripts/agent/describe-conflict.sh) が出す**衝突したファイル**と、
**分岐点から後にそのファイルを `main` へ入れたPR**。押し返されるまで同じ差分は一度しか書かない。

**投入するとき、重なっている相手を名指ししない。** 盤面が書けるのはファイル名だけで、**受け取った側は
それを見ても触る先を変えない**ので、知らせても作業が変わらない。ぶつかれば git が相手を教える
（出どころ: ユーザーの指示・2026-09-06）。

### 縦に割る基準は、文法を足すかどうか

機能追加は層をまたぐ。縦を割る基準は**文法を足すかどうか**で、判定材料は**各設計文書の概要に既に
書いてある**（`DocumentStyle.md` 2節が「新設した文法は何か。新設ゼロならそれを明記する」を
要求している）。

- **文法を足す** → `GameElementDefinition.md` と `loader`・`domain` という単一の hub を通るので、
  何本流しても直列寄り。**まとめて1本にする。**
- **宣言だけで書ける** → 専用の YAML と専用の設計文書だけを触るので、**互いに衝突しない。**

### 同じ宣言が全部へ並ぶなら、担当は配る側（trait）

**yaml の担当は、値を書くファイルではなく、宣言を配るファイル。** 「全部の土地が持つ性質を足す」
task の `## 担当` に `locations.yaml` だけを挙げると、そこの11件へ同じ宣言が並ぶうえ、`location` を
名乗る `voyage.yaml` の17件が丸ごと落ちる。正しい直し方（`core.yaml` の `location` trait の `props`
へ1行）は**そこに挙がっていない**。issue #1412 がこれで、中心の仕事が手がかりの外にあった。

判定は「その宣言は、種類の全部に並ぶか」の1点。並ぶなら trait の側（`core.yaml`）を担当に入れる。

### 同じファイルを触ることは、依存ではない

**「順序に理由がある」と「同じファイルを触る」は別のもので、後者を依存（`blockedBy`）に書いては
いけない。** 衝突するかどうかは**今どのセッションが走っているかで変わる**ので、issue に書いた
時点の事実にならない。書けば嘘の順序を固定することになる。それに、立てた側は他に何が走るかを
原理的に知らない。

**投入の瞬間にも見ない**（上の2節）。重なりの度合いを見ずに直列へ落とすと、鎖が伸びた分がそのまま
遅れになる——2026-09-06 に数えたところ、担当を宣言した `kind:task` のうち**同時に開いていた組の
4分の1が重なっていた**（4452組のうち1085組）。**最も多いのは `docs/engine/GameElementDefinition.md`**
（184組）で、hub を触るものが直列に落ちる。

代わりに、**push の直前に `main` を取り込み直して4つのコマンドを通す**ことを投入の文面に入れる。

### 生成物が古くなるのは workflow が直す。マージする側は何もしない

`stats/balance.yaml` のような生成物は、**gitの上では衝突しないのに意味の上では古くなる**。2本目は
1本目が入る前の定義から作られているので、行が離れていれば `MERGEABLE CLEAN` のまま入り、**鮮度検査
（[`tests/support/generatedReport.ts`](../tests/support/generatedReport.ts) の
`describeReportFreshness`）が `main` で落ちる**（2026-08-28 に #1004・#1005 で実際に起きた。
#1004 が足した `pick` のぶん3項目が、#1005 の持っていた表から欠けていた）。

[`.github/workflows/regenerate-stats.yml`](../.github/workflows/regenerate-stats.yml) が
`main` への push のたびに `stats/` を作り直し、差分が出たら直接 push し直す。**マージした後に
することは無い。**

**残る赤が1本ある。** 直したコミットを push しても、その前のマージコミットに付いた `tests.yml` の
赤は消えない（`GITHUB_TOKEN` の push は新しい run を起こさないので、ループもしない代わりに
過去の run も塗り替えない）。**`main` の最新が緑なら直っている**ので、履歴の赤は追わなくてよい。

**手で作り直すとき**（workflow が壊れている・気候表を触るときなど）、**Windows の bash からは
`npm run stats:balance` が通らない**——npm がスクリプトを cmd.exe へ渡すので `RUN_BALANCE_STATS=1` の
前置が解釈されない。`RUN_BALANCE_STATS=1 npx vitest run
tests/diagnostics/balanceStatsReport.test.ts` を直に呼ぶ（気候表は `RUN_CLIMATE_STATS` と
`tests/diagnostics/climateStatsReport.test.ts`）。

## 3. タスク issue の型

1タスク = 1 issue。ユーザーはその URL を新しいセッションへ貼るだけで指示が済む。

題は「何をどうする」の1文。本文は次の形。

```markdown
雨で溜まる水が、`## 数えられない経路` に出ない。（現象の説明。長さは自由）

## 担当

`src/analysis/balanceTables.ts` / `tests/diagnostics/balanceStatsReport.test.ts` /
`docs/diagnostics/BalanceStats.md`

## 完了の条件

- `npm run stats:balance` の出力に `### 数えられない経路` が現れ、`water_liquid` が
  「島全体で入手経路が無いもの」から消える
- `npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` が通る

## 拠り所

`BalanceStats.md` の「この表が数えていないもの」節（暫定）
```

**節名を固定するのは、読む側が名前で引くから。** 投入されたセッションは
[`dispatch-prompt.md`](./dispatch-prompt.md) で「`## 担当` は調べ始める場所の手がかり」と言われ、
レビューは [`review-prompt.md`](./review-prompt.md) で「完了の条件はそちらに書いてある」と言われる。
**節名が揺れると、どちらも探す先を失う。**

- **必ず置く**: `## 担当`・`## 完了の条件`。**`## 担当` は調べ始める場所の手がかり**で、触ってよい
  範囲ではない（下の「`## 担当` は調べ始める場所の手がかり」）。
- **任意**: `## 拠り所`、ユーザーが決めたことがあるなら `## 決まっていること`、どう直すかを渡すなら
  `## 案`（次節）、先に片付いていないと着手できない issue があるなら `## 順序`（下の「順序は issue の
  本文で申告し、棚卸しが決める」）。
- **これ以外の節名は自由。** 現象の説明・調べた結果は好きに割ってよい。**直し方はどこへでもなく
  `## 案` へ**（次節）。**引かれるのは上に挙げた節だけ。**
- **`## 完了` と書かない**（`## 完了の条件` に揃える）。**引く側は節名で探す**ので、揺れた分は
  そのまま読み落としになる。
- **`## 完了の条件` に、どうやるかを書かない。** 書くのは**何が達成されていれば終わりか**と、
  **それをどう確かめるか**だけ。**手順を混ぜると覆せなくなる**——受け取ったセッションは完了を
  この節で判定し、レビューは範囲をこの節で判定するので、ここへ入った手段は決まっていることと
  同じ重さで効く。
- **`## 触らないもの` は書かない。** 触ってよい範囲を切らないので、書く先が無い。**他のセッションとの
  重なりも書かない**——issue 本文へ書くと、重なりが解けた後も残って嘘になる（投入の補足へも書かない。
  上の「ぶつかった実績は控える」）。
- **「止まる条件」も書かない。** 既定は仮決めして進むことで、例外は確定の宣言に反する変更が要ると
  きだけ。宣言（節の `【確定】` と、文書単位の `**本書は全体が確定です。**`）がその条件を既に表している。
- ブランチ名はセッションごとに自動で割り当たるので指定しない。
- **`## 完了の条件` が実装と食い違っていたら、疑うのは issue のほう。** 書いた側は全部のファイルを
  見ていない。条件に合わせて文書を直すと、**文書だけが実装から離れる**。食い違いは新しい issue に
  する。

### 自分で立てた issue には `origin:agent` を付ける

人とエージェントは**同じアカウントで書き込む**ので、立てたのがどちらかを GitHub の側からは
見分けられない。**印を付けるのはエージェントの側だけ**（出どころ: ユーザーの指示・2026-09-06）——
セッションが自分で issue を立てるときに `origin:agent` を一緒に付ける。**起票のときに渡すこと**
——後から付け直す道はある（[`board-design.md`](board-design.md) 2.16）が、**別の手が要る形にすると、
付け忘れた issue が「人が立てた」として数えられる。** 気づける者は居ない。

**人が立てた issue には何も付かない。** 印が無いことが「人が立てた」を表すので、人の側の手数は
増えない。`origin:human` は要らない。

**この軸は数えるためのもので、盤面は読まない。** 配る順にも錠にも効かない。

### 実現案を書くなら、ユーザーが決めたことと分けて書く

issue が渡すのは**起票の時点で分かっていること**——ユーザーの発言・`【確定】` の節・自分で測った
結果・再現手順。**それを読んでどう取り込むかは、受け取る側の仕事**（出どころ: ユーザーの指示・
2026-09-07）。

**どう直すかを書くのは構わない**——**セッションのほうが文脈は薄い**ので、既に調べが付いている形を
伝えないと、同じことを調べ直させることになる。ただし**渡すのは案であって、やり方の指示ではない。**
壊れるのは書くことではなく、**出どころを混ぜること**と、**覆せない節へ入れること。**

`拠り所` の後に、2つの節へ割る。

```markdown
## 決まっていること

- 荷が重くて移動が遅くなる分は、**積ではなく加算**で表す（ユーザー 2026-08-28）
- 移動の所要時間は `travel_minutes`（`docs/engine/GameElementDefinition.md` 11.3 節【確定】）

## 案

- `duration` に `plus` を足して、`{prop: travel_minutes, plus: {subject: agent, prop: travel_delay}}`
- 遅れは +10 分／+25 分の2段
```

- **`## 決まっていること` は1件ずつ出どころを添える。** ユーザーの発言・`【確定】` の節・既存の
  テスト・自分で測った結果のどれか。**出どころが書けないものは、決まっていることではない。**
- **`## 案` は覆してよい。** ただし覆すと決めたセッションは、**実装せずに issue を人へ返す**
  （投入の指示に書いてある。[`dispatch-prompt.md`](./dispatch-prompt.md)）。**この
  「返す」は暫定**——進ませたほうが速いなら、運用が回ってから変える。
- **節が無い issue は、全部が「案」**として読まれる。決まっていることがあるなら必ず書く。
- **2つの節は独立していること。** 案を覆すと決まっていることまで崩れるなら、置き場が違う。#1412 は
  「顕在化は60日目」を決まっていることへ、「段の数・境目・速さ」を案へ置いたが、**境目を動かせば
  顕在化の日は必ず動く**ので、セッションは案を覆せない。決まっていることへ書くのは**案から導かれた
  数値ではなく、その数値を決めている制約のほう**。制約の形に書き直せないなら、それは案ではない。
- **案を、必ず置く2節（`## 担当`・`## 完了の条件`）へ入れない。** 受け取ったセッションは完了を
  `## 完了の条件` で判定し、レビューは範囲をそこで判定するので、**入れた手段は決まっていることと
  同じ重さで効き、覆せなくなる。`## 担当` は調べ始める場所の手がかり**で、どう直すかの指定ではない。
- **どの係がその仕事を引き取るかも実現方法。** ユーザーの発言から引けないなら `## 案` へ置く。
  **既に在る係へ仕事を足すときは、`## 担当` にその係の本文（`.claude/*-prompt.md`）が挙がっている
  だけでは、引き取り手が決まっているのかどうかが読めない**ので、案なら案だと本文で言う。

混ぜると何が起きるかの実例。どちらも `【確定】` の節にエージェントの仮決めが混ざったのと同じ
構造（[`policies.md`](./policies.md)「確定の印を付ける範囲」）。

- **#1180 — 節を割らずに混ぜた。** ユーザーが決めたのは「積ではなく加算」だけだったのに、issue は
  `plus` という綴りも `travel_delay` という名前も +10/+25 という数値も同じ声で並べ、さらに「この点を
  理由に積へ戻さないこと」と逃げ道まで塞いだ。**セッションは全部を決定事項として受け取り、yaml の
  文法を仮決めのまま書き換えにかかった。**
- **#1609 — 案を、必ず置く2節へ入れた。** ユーザーが決めたのは「ブリッジのセッションを手で畳むのを
  やめたい」まで（#1601 の E17）で、**どの係が引き取るかは言っていない。** issue は監視係と決め打ち、
  `## 担当` に `.claude/watch-prompt.md` を挙げ、`## 完了の条件` を「**監視係が**1周走ると畳まれる」と
  書いた。ユーザーがコメントで止めるまで（「監視係の仕事を増やし過ぎ」「終わったタスクセッションを
  たたむのはデーモンの仕事です」）、**引き取り手は決定事項として渡っていた。**

### 投入する前に、棚卸しが分類する

ユーザーが立てる issue は自分の言葉で書かれていて、担当も完了条件も無い。**型を覚えることは判断では
ないので、書式を人間の側へ要求しない**。型を要求すると、思いついたことを書き留める速さが落ちる。
翻訳は仕組みの側が引き取る。

そのまま投入すると、**どこまでやれば終わりかが宣言されていない**まま差分が返ってくる。受け取った
セッションは完了を自分で決めるしかなく、レビューはそれが妥当かを判定できない。

- 対象は**未整理**——open で `kind:` のラベルを1つも持たない issue
  （[`board-design.md`](board-design.md) 2.17.1）。
- **未整理の全件をまとめて1セッションに渡す。** 1件ずつ配ると、**この係にしかできない仕事が全部
  落ちる**——別々に立った issue が同じ原因であること（#1042・#1043・#1044 はどれもカードの移動
  アニメーションの話だった）、張るべき順序、重複。どれも複数を並べて見た者にしか見えない。
  **1件だけを見る仕事なら、ワーカーにさせればよい**（出どころ: ユーザーの指示・2026-09-06）。
- **クラウドで走らせる**（出どころ: ユーザーの指示・2026-09-06）。番号を保ったまま本文を書き換える
  のが棚卸しの中心だが、**それも用意された道具で通る**（`gh` と生の REST は無い。
  [`board-design.md`](board-design.md) 2.16）。**ブリッジはユーザーのPCを占める枠**なので、
  要らない仕事を置くと並列度がその分だけ下がる。
- 渡す本文は [`triage-prompt.md`](./triage-prompt.md)。出口は**そのまま／翻訳／分解／束ねる／返却**で、
  書き換えたときは原文を `## 元の報告` として消さずに残させる。
- **`kind:task` を付けるのは棚卸し。** **`判断待ち` は付けない**——分類が済んだ issue はそのまま
  配られる（[`board-design.md`](board-design.md) 2.17.1）。**順序（`blockedBy`）を張るかどうかを
  決めるのも棚卸し**——本文の申告を読んで決める（下の「順序は issue の本文で申告し、棚卸しが決める」）。

**起こすのはデーモン**（[`board-design.md`](board-design.md) 2.17）。未整理が1件でもあれば一日一回
立つ。**引き金がどこにも無かった間、2026-08-30 の時点で15件が滞留していた**——`board.sh` を打った
者の目にしか入らず、**セッションが issue を立てるたびに未整理は増える**。

### `## 担当` は調べ始める場所の手がかり

**触ってよい範囲ではない**（出どころ: ユーザーの指示・2026-09-07）。直すのに必要だと判断した
ファイルは、挙がっていなくても変更してよい。**囲いを置くと、囲いを越えたかどうかの判定と申告が
要り、そこが一次レビューの指摘を生む側に回っていた。**

**触ったファイルの一覧でPRの範囲を測らない。** どこまでやれば終わりかを持つのは `## 完了の条件`
だけ。

分け目は、**その直しが今の issue の仕事かどうか**。

- **自分の変更が他の記述・コードを事実でなくしたなら、必ず同じPRで直す。** 判定は「**自分の差分が
  この行を嘘にしたか**」の一点。**後回しにすると嘘が1つ増える**ので、issue へ回さない。
  かつては担当外というだけでこれが issue に化けていた——2026-08-28 の1日で4件あり（#994・#998・
  #1000・#993）、うち2件は2〜3行で、2行のために issue 1件・セッション1本・PR1本・マージ1回が
  要っていた。
- **「ついでに気づいた」「直したほうがよさそう」は、今の issue の仕事ではない**ので、直さずに新しい
  issue を立てる（下の「PRの中で終わらないことは、issue かスメルへ出す」）。

**生成物は作り直す**（`stats/balance.yaml` は `npm run stats:balance`、`stats/climate.yaml` は
`npm run stats:climate`）。鮮度検査があるので、作り直さなければCIが落ちる。手で書き換えることは
許さない——**作り直すのであって直すのではない。**

### 順序は issue の本文で申告し、棚卸しが決める

**先に片付いていないと着手できない issue があるなら、GitHub の依存（`blockedBy`）で結ぶ。** 本文に
「#123 の後」と書いても機械は読めず、[`board-move.mjs`](../scripts/agent/board-move.mjs) はそれを
ready として配る。**判断する側と張れる側が別なので、間を申告でつなぐ。**

- **順序の理由を持つのは issue を立てた本人。** なぜその順序かを知っているのは、その問題を見つけた
  側だけ。後から本文だけを見る者は推測することになり、推測は必ず取りこぼす。
  **だが、張るかどうかを決めるのは棚卸し**（出どころ: ユーザーの指示・2026-09-06）——理由が
  「同じファイルを触る」なら張らない（下）ので、**セッションが自分で張ると、その判断を通らない。**
  そもそも**クラウドのセッションからは張れない**——issue の作成も本文の書き換えも用意された道具で
  通るが、**依存の API だけはその一覧に無い**（`gh` も生の REST も無い。`curl` は
  `{"message":"GitHub access is not enabled for this session. An org admin must connect the Claude
  GitHub App for this organization."}` を返す。2026-08-27 に3セッションが実際に踏んだ）。

  そこで**セッションは、立てた issue の本文へ `## 順序` 節を置いて申告する**。1行1件で、
  **先に要るほうの番号と、なぜ後でないと着手できないかを添える。**

  ```markdown
  ## 順序

  - #1234 の後（宣言を読む側がこの issue で、書く側が #1234。読む側だけ先に入れても動かない）
  ```

  **申告の先を issue にするのは、PRの本文が読み返されないから**（次節）——順序を待っているのは
  issue の側なので、そこに在れば消えない。
- **決めるのは棚卸し**（[`triage-prompt.md`](./triage-prompt.md)）。分類のために全件の本文を読む係で、
  未整理の issue は必ずここを通るので、申告が読まれないまま配られることはない。

  **張る手はワークフローが持つ。** 棚卸しは待つ側の issue へ次の形のコメントを1つ置き、
  [`board-labels.yml`](../.github/workflows/board-labels.yml) が `blockedBy` を張る
  （[`board-design.md`](board-design.md) 2.17.3）。**どこで走っていても同じ手で張れて、なぜその
  順序かも issue に残る。**

  ```
  [順序] #<先に要るほう> の後（<なぜ後でないと着手できないか>）
  ```
- **棚卸しは推定しない。** 申告の無いものに順序を作らない——判断の材料は申告に添えられた理由だけで、
  本文の外に無い。
- **「同じファイルを触る」は依存ではない。** 申告する側は理由があるものだけを書き、棚卸しは理由が
  これなら張らない。理由が無いのに結ぶと、**嘘の順序が固定される**（衝突の扱いは2節）。
- **迷ったら張らない。** 張り忘れ（早すぎる着手）はPRの段階で気づけて、やり直しはリベース1回で
  済む。**過剰に張ると鎖が伸びた分だけ黙って遅くなり、誤りに誰も気づかない。**
- 循環は GitHub が 422 で拒む（実測）ので、静かに全停止することはない——張りに行ったワークフローが
  赤くなる。

### PRの中で終わらないことは、issue かスメルへ出す

**PRの本文は、マージの後は誰も読み返さない。** 申し送りの節を置いて滞留をラベルで見せてもみたが、
下ろす者が居らず18件が付いたまま残った（2026-09-06 の実測）。**読む役を新しく置くのではなく、
書く先を対応される場所へ移す**（出どころ: ユーザーの指示・2026-09-06。
[`board-design.md`](board-design.md) 3.2）。**射程はマージの後に手を動かす者が要るものだけ**
——`## 仮決め`・`## ユーザーの指示` はマージの前に読まれるので、今までどおり本文へ書かせる（下の
「PR の型」）。行き先は2つだけ。

- **やる必要があること → issue を立てさせる。** issue が在れば棚卸しが分類し、盤面が配る。範囲外だと
  判断したものも、仕組みそのものへの直し（`.claude/**`・`scripts/agent/**`・`CLAUDE.md`）も同じ。
  **分類（`kind:`）は付けさせない**——付けるのは棚卸しで、付いていない
  issue はそちらへ回る（[`board-design.md`](board-design.md) 2.17.1）。**番号をPR本文へ書き写させない**
  ——写しは、読む者が居なければ何も起こさない。順序が要るなら、その issue の本文の `## 順序` 節へ
  申告させる（前節）。
- **issue を立てるほどではない気づき → `[スメル] ` で始まる行としてPRへコメントさせる。**
  レビュアーが書くのと同じ形（[`board-design.md`](board-design.md) 4.4）で、マージ後に分析係が拾う
  （下の「マージ済みのスメルは、分析係が拾う」）。

**分け目は、やる必要があるかどうか。** issue を立てたということは、やる必要があるという判断が既に
済んでいるということなので、**必ず対応される場所に置く**。

### 束ねる関門は、ゲートの issue を1件立てる

**N 件が済むまで M 件を止めたい**とき、M 件それぞれに N 本を張らない。「〜が確定していること」だけを
書いた issue を1件立て、N 件をその `blockedBy` に、M 件をその後ろに置く。辺は N×M ではなく N+M で
済み、**後から1件足すときに張る辺は1本**になる。

数ではなく、**張り忘れたときにどちらへ倒れるか**が理由。関門が1点なら、足したものは既定で止まる側に
落ちる。個別に張る形では、足したものは既定で素通りする。

ユーザーの確定を待つゲートは、**チェックを付けるのも閉じるのもユーザー（#656）**。
#656 の入力の形は変えない——チェック1つで答えられることが、あの issue の条件だから。付いたことは
`board.sh` の `## 確定待ち` に出る（1節）。

### PR の型 — 仮決めと自己点検を、書いた本人が申告する

PR本文の先頭に `## 仮決め` 節を置く。**「なし」と書くのも仕事のうち**——書かせないと、仮決めが
無かったのか書き忘れたのかが区別できない。あるなら、決めた内容・代わりの案・覆すと何が変わるかを
3行以内で。

**`## 自己点検` 節も、PRの出どころにかかわらず全部が置く。** 書くのは手前の一次レビュー（1節）の結果で、
**中身の形は `CLAUDE.md`「PR本文に置く節」が持つ**。ここも「なし」と同じ理屈で、書かせないと通して
いないのか書き忘れたのかが区別できない。**読むのはレビュアー**（[`review-criteria.md`](review-criteria.md)）。

**差分の中身を読むのは、下の関門（機械）とレビューのセッション。** ユーザーが読むのは、下の表で
読む相手にユーザーが挙がっている節だけ。

**`## 仮決め` と `## 見た目` の読み手からユーザーを落としてある。** 人の判断が要るかを判定するのは
レビュアーで、**何を判断してほしいかも判定のコメントへ書く**（[`board-design.md`](board-design.md)
2.13.4）ので、**ユーザーが読む先はそのコメント**。**節が要らなくなったわけではない**——
決めきれなかった問いを書く場所は今もここで（下の「決めきれなかった問いも、この節に書かせる」）、
**読んだレビュアーが人へ回す。**

PR本文の節は次のとおり。**必ず置くのは `## 仮決め` と `## 自己点検`**（`Closes` は issue を持つPR
だけ）で、残りは無ければ節ごと省く。

**節は表の綴りちょうどで書く。** 節を読む側はどこも名前を `$` で留める（盤面が `## 見た目` の
有無を見る形。[`board-move.mjs`](../scripts/agent/board-move.mjs)）ので、
`## 仮決め（3周目）` のように語を足すと**その節だけ誰にも届かない**。周回番号や
補足は、節の中へ書く。

| 節 | 中身 | 読む相手 |
| --- | --- | --- |
| `Closes #<番号>` | 先頭に。番号だけの参照では閉じない（**issue を持たないPRには無い**） | GitHub |
| `## 仮決め` | 決めていない箇所をどう決めたか（**無いなら「なし」**） | レビュー |
| `## 自己点検` | この節の本文のとおり | レビュー |
| `## 見た目` | 画面が変わるなら画像（変わらないなら「不要」と理由） | レビュー |
| `## ユーザーの指示` | 作業中にユーザー本人から届いた指示と、その反映 | レビュー |

**`## ユーザーの指示` が要るのは、レビューがそれを見ていないから。** ユーザーは走っているセッションへ
直接 `send_message` を送れる。書かせないと、issue の完了条件から外れた理由が本文のどこにも
無いまま、**レビューには「範囲外へ伸びたPR」としか見えない**——差し戻すと、ユーザーの指示を取り消す
ことになる。デーモンが送ったものは書かせない（`[デーモン]` で始まる）。

| PRの状態 | 扱い |
| --- | --- |
| `needs-user-review.sh` が該当を出す（`【確定】` の印が動いた） | **機械にはマージできない。** `merge-and-close.sh` が `判断待ち` を付けて `HELD` で止める。**ラベルを外すだけでは越えられない**（次の周に付き直す）——越えるのは `merge-and-close.sh <PR> --user-ok` だけ |
| レビューが `[レビュー] 通してよい（人の判断が要る）` を出す | `通してよい` と `判断待ち` が付き、**マージだけが止まる**。**ラベルを1つ外せば通る**（機械は付け直さない。[`board-design.md`](board-design.md) 2.13.4） |
| 差分が画像だけ | **そのままマージする**（下の「絵は素通しに固定する」） |
| それ以外 | **レビューのセッションを1本立てる**（下の「差分を読むのはレビューのセッション」） |

**外のレビューは、どんな周でも1本立てる。周を飛ばす道は無い**（出どころ: ユーザーの指示・
2026-09-07）。書いた側の一次レビュー（サブエージェント）も外を置き換えない。

**コンフリクトを解いただけに見える周も立てる。** コンフリクトとは機械が結果を出せない場所のことで、
**解いた字面は誰も読んでいないもの**として必ず新しく現れる。**しかも解き方だけとは限らない**
——実測（2026-09-06。`main` の取り込みが先頭に載っているPRを新しいほうから23本取り、`git merge-tree`
の出す木と突き合わせた）で、機械では解けずに人が解いていた2本はどちらも解き方以外が動いていた:
#1651 は取り込みで生成物 `stats/balance.yaml` の数が動き（`days: 0.58 → 0.57` ほか）、#1700 は同じ
段落への両側の書き換えが**どちらの版にも無い文**へ畳まれていた。**通せば、誰も読んでいない中身が
レビューを経ずにマージへ入る。**

**「仮決めあり」だけでは止める理由にならない。** 実測（2026-08-29）で、直近25本のうち `## 仮決め` に
中身のあったPRは22本、`判断待ち` が付いたのは0本だった。22/25 を止めれば**タップを1回増やすだけの
関門**になり、本当に判断が要るものが埋もれる。

**線を引くのは、機械とレビュアーで分かれる。** 機械
（[`needs-user-review.sh`](../scripts/agent/needs-user-review.sh)）が引くのは**確定の宣言の増減**
だけ——節の `【確定】` と、文書まるごとを土台と宣言する形（`**本書は全体が確定です。**`）を同じ1つの
印として数える。**残りは差分を読むレビュアーが引く**（宣言文法・スキーマ・ゲームコンセプト・確定節に
抵触するか。[`review-criteria.md`](review-criteria.md)「人の判断へ回す」）——触ったファイルは機械で
分かるが、**何が変わったか**は差分を読まないと言えない。

線の引き方も、書く側が持つ。

- **素通し**: 正しい挙動が仕様や既存テストから一意に決まる不具合修正、生成物の再生成、**絵の追加**、
  `【確定】` 節の値をそのまま書く宣言。
- **判断待ち**: しきい値や配分の値を自分で選んだ、名前がそのまま仕様になる、条件の有無を選んだ、
  設計文書に無い挙動を足した。

**「リポジトリを見れば一意に決まる」ものは、仮決めに見えても判断ではない。** 渡した issue が
間違った数値や前提を書いていて、書いた側がそれを正した申告がこれにあたる（2026-08-26・PR #870 で、
issue が「見出しに付いた `【確定】` は18個」と書いたのは数え間違いで、実際は16個だった）。
2026-08-25・PR #770 の申告3件も「試験の種類の決まりに禁じられていて選択の余地が無かった」
「穴が塞げていない（#768 へ）」「表の前提が書けていない（#769 へ）」で、**どれも判断ではなかった**。
**この見分けは、リポジトリを開いて確かめないと付かない**——だからレビューのセッションがやる。
ユーザーが引き受けると、PRの本数だけ差分を読むことになる。

**見つけた不具合を、仮決めに変えない。** 別の仕事に属する不具合が自分の成果に影響したとき、**その影響を
含んだまま「入れるか止めるか」を仮決めとして出さない**——直し方が仕様から一意に決まるなら、それは
判断ではない。**自分のPRを止めて、不具合の issue を先に流させる**（その issue の本文へ順序を申告
させ、棚卸しが張るかどうかを決める）。実測（2026-08-25）で、収支表の再生成が別の仕事に属する解析の不具合で表を1つ落とし、それを仮決めと
して出したことがある——**ユーザーが答えるまで、直ると分かっている不具合が main に居座る**形になる。

#### 決めきれなかった問いも、この節に書かせる

`## 仮決め` に書くのは「こう決めた」だけではない。**決めたが自信が無い点・別の答えがありうると
思った点も、同じ節に並べさせる。**

**セッションからユーザーへ届ける口は無い**（起こす道具は禁止してある。下の節）ので、**問いを残す場所は
PRの本文しか無い。** ここに書かれなければ、その問いは誰の目にも触れずに消える——実測（2026-08-25）
で、#741 のセッションは「日暮れ後に手元を取り戻すのに窯まで要求してよいか」を最後の要約に書いて
終わったが、PRの `## 仮決め` に無かったため**ユーザーへ届かないまま入った。**

**双方向の会話で埋めようとしない。** セッション側から届ける手段が無い以上、聞きに行く時機は読む側が
決めることになり、**その時機が来なかったせいで消えた**のが上の実例。既に必ず読まれる場所（`## 仮決め`）
へ書かせるほうが、確実で安い。デーモンからの `send_message` は、こちらに用があるとき——CIが赤い・
レビューが差し戻した——にだけ使う。

**絵は素通しに固定する。** 見た目はPRで覆すものではない——作り直したくなったら新しい issue にする
ほうが、ユーザーの手数が少ない。

#### 見た目が変わるPRには、画面を貼らせる

**見た目の可否は文章からは判定できない。** 貼らせなければ、判断のたびにユーザーがブランチを引いて
動かすことになる。人間に残すのは判断だけ、というのは**その判断に要る材料を揃えて渡すところまで**を
含む（[`CLAUDE.md`](../CLAUDE.md)「PR本文に置く節」の `## 見た目`）。

- `src/game/**` か `src/assets/**` を触ったPRは、本文に `## 見た目` 節が要る。中身は画像か、
  「不要」＋理由の1行。**節ごと無いPRは、レビューへ回る手前で盤面が差し戻す**（要否を決めるのは
  書いた側で、必ず言わせるのが読む側の役目。差分の置き場も本文も機械で読めるので、レビュアーの
  セッションを1本使わない。[`board-design.md`](board-design.md) 2.12）。
- 貼り方は [`push-screenshot.sh`](../scripts/agent/push-screenshot.sh)。画像は `screenshots`
  ブランチへ置く——`main` に入れると証跡が資料に混ざって公開サイトにも出るし、PRブランチへ入れると
  マージ後に枝が消えて**画像が壊れた記録だけが残る**。
- **前後を並べるなら、URLに `?seed=` を付けさせる。** 付ければ別々の実行でも島も開始時刻も同じに
  なる。**付けずに撮った2枚の差は変更由来とは限らない**ので、並べても何も言っていない
  （`skills/run/SKILL.md`）。

鎖の途中が人の手番（`判断待ち`・`収束せず`）に入ると**その先が止まる**。止まっている間は鎖の外を
先に流す。督促はしない。

### 差分を読むのはレビューのセッション

`bash scripts/agent/dispatch-review.sh <PR番号>` で1本立てる。指示は
[`review-prompt.md`](./review-prompt.md)、補足は無い（見どころはPRごとに変わらない）。**結果はPRの
コメントとして返り**、その1行目を [`board-labels.yml`](../.github/workflows/board-labels.yml) が
`通してよい`／`直し待ち` のラベルへ変える。**盤面が読むのはラベルだけ**なので、レビューのセッションを
覚えておく必要が無い。

**ラベルは push で自分から消える**（`pull_request: synchronize`）。判定は「その差分についてのもの」で、
差分が変われば偽になる——**消える側を機械に持たせてあるので、時刻の比較は要らない**
（[`board-design.md`](board-design.md) 1.1）。

**同じ判定が2度続いたら、中身を読む前に投稿の事故を疑う。** 再レビューの結論が前回とバイト単位で
同じなら、それは判定ではない——レビューのセッションは原稿をファイルへ書いてから
`gh pr comment --body-file` で出すので、置き場を取り違えると**前回の残骸がそのまま投稿される**
（`CLAUDE.md`「`/tmp` は2つある」）。PR #1229 と PR #1191 で1件ずつ起きた。**疑ったら、そのPRの
head を自分で見て、前回指摘した箇所が直っているかを確かめる。**

**盤面が読むのはコメントの1行目だけ。** 途中の指摘は直す側が読み、`[スメル] ` の行はマージ後に
分析係が拾う（下の節）。

| 1行目 | デーモンがすること |
| --- | --- |
| `[レビュー] 通してよい` | マージする。並んでいる `[スメル] ` の行は**何もしない**——コメントに残したまま、マージ後に分析係が拾う（下の「マージ済みのスメルは、分析係が拾う」） |
| `[レビュー] 通してよい（人の判断が要る）` | `判断待ち` が付き、**ユーザーが外すまでマージしない**（[`board-design.md`](board-design.md) 2.13.4）。それ以外は上と同じ |
| `[レビュー] 直しが要る` | **元を書いたセッション**を `send_message` で起こして直させる |

- **レビューのセッションは直さない。** 直すのは元を書いた側——文脈を持っているのはそちらで、
  レビュー側が push すると、同じPRを2つのセッションが握ることになる。
- **再レビューは、前のレビューを起こさずに新しく立てる。** 直す側とは逆で、ここは使い回さない。
  直しは「指摘された行を直す」ではなく「原則として受け取って兄弟も直す」（`CLAUDE.md` 5節）なので、
  **2回目のヘッドは1回目とは別物**になる。自分の出した判定を自分で再判定すると「言ったことが
  直っているか」だけを見る方向に寄り、**直しが新しく壊したものが誰にも読まれない**——2026-08-29 の
  PR #1191 で、2回目のレビューが前回の3件を確かめたうえで前回は見ていなかった箇所の嘘を見つけた。
  読み直しの費用（PR全体をもう一度読む）は、この読み直しそのものなので削れない。
- **PRの本数だけ立つ。** 絞ると「どれを読むか」の判定が盤面を回す側に戻ってきて、それには差分が要る。
  唯一の例外は差分が画像だけのPRで、これはファイル一覧だけで分かる（下の「絵は素通しに固定する」）。
- **タグは `review-<PR番号>`。** `task` で始めると `stall` の対象になり、PRを出さないレビューの
  セッションが「止まっている」として起こされる。
- **出し忘れは起きない。** 盤面は**判定のラベルが付いていない緑のPR**を毎周レビューへ出すので、
  誰も順番を覚えておく必要が無い。**同じ差分へ2回出すことも無い**——打った手は
  `headRefOid` を指紋として控えてあり、push で指紋が変わるまで同じ手は出ない
  （[`board-design.md`](board-design.md) 1.1）。

### マージ済みのスメルは、分析係が拾う

PRのコメントには `[スメル] ` の行が2つの口から入る——レビュアーが止める理由に数えなかったもの
（[`review-criteria.md`](review-criteria.md)「止めないもの」）と、PRを書いた側が issue を立てるほどでは
ないと見たもの（上の「PRの中で終わらないことは、issue かスメルへ出す」）。**どちらもそのPRでは
何もしない**——手を打つ値打ちがあるかは、1本のPRの中では決まらないから。

**拾うのは一次の分析係**（[`board-design.md`](board-design.md) 4.4・2.17）。読まれていないスメルが
1件でもあれば一日一回立ち、手を打つべきものは issue を切り、**切るほどではないが繰り返し現れている
形**は `.claude/analysis/<日付>.md` へ1回1ファイルで残す。渡す本文は
[`analysis-prompt.md`](analysis-prompt.md)。

**この係が見るのはその回の帯だけで、過去の回の記録は読まない**（[`board-design.md`](board-design.md)
2.17.4）。**回をまたいで同じ形が出ているかを見るのは二次の係**
（[`analysis-trend-prompt.md`](analysis-trend-prompt.md)）で、そちらの入力は一次が書いた記録だけ、
書く先は `.claude/analysis/summary/<日付>.md`。**同じ形を一次が毎回書くのは無駄ではない**——何回の帯に
独立して現れたかが、二次にとっての根拠そのもの。

- **読むのはマージ済みのPRだけ。** 開いているPRのコメントは、次の周のレビューや直しで消えることが
  あり、拾うと二重になる。
- **読んだ印はコメントに付く 👀**（自前の台帳を作らない）。**付けるのは最後**——先に付けて途中で
  落ちると、拾われないままのスメルが黙って消える。逆順なら、落ちても次の周が拾い直すだけで済む。
- **切る issue に `kind:` は付けない。** 分類するのは棚卸し（上の「投入する前に、棚卸しが分類する」）。
- **記録はPRとして出す。** リポジトリのファイルなので、他の書くセッションと同じ道を通る——ただし
  **書くセッションの枠には数えない**（間隔を空けて立つ係の、記録だけの差分で、マージの列を
  詰まらせない）。
  **そのPRが開いている間、この係のセッションは畳まれない**（差し戻す先が消えるため）。

### 却下はラベルで出す

**PRの作者はすべてユーザー自身になる**——セッションがユーザーの資格情報で push するため。GitHubは
自分が作者のPRに Approve も Request changes も出させないので、**レビュー機能は使えない。**

**既定はマージ。** 判定が `通してよい` で緑になれば、デーモンがそのまま入れる。**止めるには手を
動かす必要がある。**

| ユーザーがすること | 何が起きるか |
| --- | --- |
| **承認** → 何もしない | 緑になった時点でマージされる |
| **承認**（レビュアーが `判断待ち` を付けている） → **ラベルを外す** | 次の周でマージされる（[`board-design.md`](board-design.md) 2.13.4） |
| **承認**（機械が `判断待ち` を付けている） → `merge-and-close.sh <PR> --user-ok` | その場でマージされる。**ラベルを外すだけでは越えられない**（同 2.13.3） |
| **却下** → `却下` を付ける | デーモンが書いた本人を起こし、通らなかった仮決めを取り下げさせる。理由はコメントに書けばよい |

- **コメントだけでは止まらない。** デーモンが読むのはラベルだけで、**コメントは読まない**。
  理由を書くのはコメントでよいが、**止める意思はラベルで表す**。
- **コメントは理由まで書かれていなくてよい。** 「−5 で」だけで足りる。足りなければ、起こされた
  セッションがPRのコメントで訊く（[`resume-prompt.md`](resume-prompt.md) の `## reject`）。
- **ユーザーがセッションと直接話すこともある。** それは速いので止めない。

**`判断待ち` が付いていても、`却下` の差し戻しは止まらない**（[`board-design.md`](board-design.md)
2.13.2）——止めているのはマージだけ。どちらの印も、直しが push された時点で機械が外す。

**外す作業があるのは、レビュアーが付けた `判断待ち` だけ**（上の表。外すこと自体が承認で、それが
1タップ。2.13.4）。機械が付けたほうは外しても次の周に付き直るので、人が触る意味が無い。

**沈黙を「死んだ」と読まない。** 応答が無いセッションを見限って同じ仕事を自分で書く前に、
**そのブランチが push されていないかを見る。**

```bash
git ls-remote --heads origin 'claude/issue-<番号>*'
```

これは `gh` も MCP も要らず、**セッションの状態が引けない状況でも使える**——2026-08-25 に、2時間
応答の無いセッションを死んだと判断し、MCPも切れていて確かめられないまま同じ検査を書いて先に
入れた（PR #772）。**セッションは生きていて、その直後に PR #773 を出した。** 向こうのほうが良い
出来だったので、こちらを消して統合し直すことになった。**枝が在れば生きている。**

**差し戻したら `直し待ち` を付ける。** 付いていないPRは「まだレビューしていない」と読まれるので、
付け忘れると**直しを待っている間にレビューが立つ**。付け外しは
[`board-labels.yml`](../.github/workflows/board-labels.yml) がやる（`[レビュー] 直しが要る` で付き、
push で外れる）ので、手で付けるのは人が差し戻すときだけ。

**ボット用のアカウントでPRを出させて本物のレビュー機能を使う案は採らない。** Approve /
Request changes が使えるようになっても、**却下時に結局コメントを書く**ので手数は減らず、増えるのは
GitHub App の管理だけになる。

### `main` の赤を直したら、開いている全PRへ取り込ませる

**`gh run rerun` では直らない。** GitHubはPRのチェックを**そのPRが作られた時点の merge ref** で
走らせるので、再実行しても `main` の修正は入らず、同じ赤がもう一度出る。
`gh pr update-branch <番号>` でPRのブランチへ `main` を取り込ませると、新しい merge ref で走り直す。

**掛けるのは、赤を直したPRをマージした直後に、開いている全PRへ一律。** 心当たりのあるものだけを
1本ずつ拾うと取り残す——2026-08-28 に `main` の赤を #928 で直したあと、#927・#930 へは掛けて
**#918 だけ漏らし、担当セッションが何もしていないのに赤のまま止まった**（気づいたのはユーザー）。

```bash
for n in $(gh pr list --state open --json number --jq '.[].number'); do gh pr update-branch "$n"; done
```

**PRの赤は、まずそのPRの変更が原因かを見る。** 上の取り残しは、`判断待ち` が付いていたせいで
「ユーザーの手元にある」と読み、CIを見ていなかったのが元。**ラベルは持ち主を表すだけで、
赤の理由ではない。**

### 走っているセッションへ仕事を足したら、PR本文への反映まで見る

**そのセッションが既に見ている範囲へ完全に収まる小さな仕事は、新しいセッションを立てずに、既に
開いているセッションへ `send_message` で渡してよい。** コメント1文の削除のために1セッションぶんの文脈を積むほうが高い。

**ただし本文は追いつかない。** 渡した仕事は `Closes` にも変更の説明にも載らないことがある——
2026-08-28 に #939（コメント1文の削除）を #914 のセッションへ渡したら、**コードは正しく入ったのに
`Closes #939` が抜け、「そのファイルは無変更」という記述が残ったまま**PRが出た。本文を書き終えた後に
仕事が増えたのだから、追いつかないほうが自然。

**PRが出たら、渡したぶんが本文に載っているかを必ず見る。** 載っていなければ本文だけを直させる
（`直し待ち` を付けて `send_message`）。代わりに書き換えない——**次も同じ場所で漏れる。**

### PRを出したら、そのセッションの仕事は終わり

**タスクのセッションに自分のPRを見張らせない。** `send_later`・`delete_trigger`（自分を起こすための
予約と、その取り消し）と `subscribe_pr_activity` は**自動承認ができない**ので、見張らせた分がそのまま
ユーザーのタップになる。見張るのは
[`daemon.sh`](../scripts/agent/daemon.sh) の仕事。

**禁止は2箇所に置いてある。** どちらも消さないこと——2026-08-27 に、この節にしか無かったせいで
3セッションが見張りを始めた。

- [`CLAUDE.md`](../CLAUDE.md)「タスクの issue を渡されたとき」。**セッションが必ず読むのはこちら。**
  この節だけに書いても、指したファイルを読むとは限らない。
- [`dispatch-prompt.md`](./dispatch-prompt.md) の指示のひな形。投入のたびに本文へ入る。

**「マージされるまで完了ではない」と並べて書く。** 分けて書くと、責任だけが残って手段が
禁止された状態に読め、**セッションは自分で見張るほうへ倒れる**（実際に倒れた）。直しの依頼は
向こうから来る、までを1つの文にする。

[`daemon.sh`](../scripts/agent/daemon.sh) が毎周1手だけ打つ。順は
[`board-move.mjs`](../scripts/agent/board-move.mjs) が決める。

- **判定のラベルが無く、緑** → `dispatch-review.sh <番号>`。マージの前に必ずここを通る。
- **`通してよい` があり、緑で、コンフリクトも無い** → `merge-and-close.sh`。issue が閉じたことの
  確認と、書いたセッションを畳むところまで同じ1回で済む。
- **`直し待ち`・CIが赤・コンフリクト** → **そのPRの `task-<番号>` のセッションを起こして直させる**
  （[`resume-session.sh`](../scripts/agent/resume-session.sh)。渡す文は
  [`resume-prompt.md`](resume-prompt.md) の `## mend`）。**起こすほうが既定**——PRの文脈を持って
  いるのはそのセッションで、新しく立てると読み直しから始まる。

  **止まった（IDLE・切断）クラウドセッションは、これで起きる**（2026-08-25 実測: 送信から応答まで
  8秒、$0.32）。コンテナは作り直され、文脈は残ったまま続く。だから**セッション側に見張らせる必要が
  無い**——クラウドには `gh` が無く、未認証のGitHub APIは60回/時なので、そもそも同じ間隔では回せない。

  **`priority: now` で割り込ませる。** `next` はターンの区切りまで待つので、**仕上げに入っている
  セッションには届かない**（2026-08-26 に、差し戻しが間に合わず不具合が4本へ広がった）。
- **`却下` がある** → 起こして、通らなかった仮決めを取り下げさせる（`## reject`）。
- **画面が変わるのに `## 見た目` が無い** → 起こして、撮って貼らせる（`## look`）。

**人の手番の印は、差し戻しを止めない。** PRの `判断待ち` が止めるのはマージ、`収束せず` が止めるのは
レビューで、どちらもコンフリクトやCIの赤の解消を待たせる理由が無い（[`board-design.md`](board-design.md) 2.13）。

**コンフリクトも差し戻す。** 以前は盤面を回す側が自分で `main` を取り込んで解消していたが、**デーモンには
解消できない**（判断が要る）。取り込みは書いた本人にもできるので、赤と同じ `mend` に畳んである
——**この3つは起こされた側がやることが同じ**（PRを見て直す）なので束ねてよい。逆に `reject` と
`look` を分けてあるのは、やることが違うから（1.3）。

**同じPRを毎周叩かない。** 指紋は `<種類>:<PR番号>:<headRefOid>` で、**push があるまで同じ手は
出ない**（[`board-design.md`](board-design.md) 1.1）。`直し待ち` のラベルで黙らせる必要が無いので、
「今それが誰の手元にあるか」と「誰の手元にあろうと進めない」を混ぜずに済む。

### 価値観の記録 — 出どころがユーザー本人でないなら、記録しない

**価値観の出どころはユーザー本人の発言だけ**（[CLAUDE.md](../CLAUDE.md)「価値観の記録」）。
エージェントが書いた issue や指令から汲み取ったものは、ユーザーの価値観ではない。**エージェントが
枠組みを書き、セッションがそれを言い直し、別のエージェントが転記する**と、自分の考えがユーザーの
名前で全セッションへ配られる（2026-08-26 に8件がこの経路で入り、消した）。

**指示に「価値観の記録は行わない」と明記する。** `.claude/decisions/` へ書かないだけでなく、
PR本文へ「記録してほしい価値観」として書くこともしない。**唯一の例外は、ユーザー本人から直接
メッセージを受け取ったとき**——そのときだけ `## ユーザーの指示` へ**原文をそのまま**引用する。
ユーザーは、原文が添えられているものだけを転記し、言い換えない。

**盤面からタスクセッションへ向けて書く文は、すべて `[デーモン]` で始める。** `create_session` の
prompt・`send_message` の本文・PRへのコメントの全部。GitHubへは**ユーザーと同じアカウントで**
書き込むので、印が無いと受け取る側から区別できない。

**止めているのは承認ではなく出どころ。** `.claude/**` の残りは、どこで走っていても書き換えてよい
（`CLAUDE.md`「タスクの issue を渡されたとき」）。`decisions/` だけが別扱い。

## 4. 段の分け方

探索を並列させない。**同じ発見を N 回繰り返し、出力が揃わなくなる。**

段は頭の中で数える印ではなく、**ゲートの issue として置く**（3節）。「段2が済んだ」を頭の中で
持つと、それを見落とした投入が素通りする。ゲートが開いていれば、後ろは機械が止める。

1. **段0 — 未実装9件の要否判断**（ユーザー／issue #656）。骨格待ちのものは保留する。
2. **段1 — コンテンツの骨格を決める**（ユーザー＋1体）。系統が何本・各系統が何段・終盤に何が要る
   か・アーティファクトが何種類か。**個々のレシピは決めない**（仮決めでよい）。
3. **段2 — 文法追加をまとめて1本**（直列）。骨格が決まっているので、本当に要る文法だけを入れる。
4. **段3 — コンテンツの幅出し（並列の本命）＋ 宣言だけの機能**。
5. **段4 — 統合と計測**。他のタスクと同じものを別名で作っていないかを見る（既存のテストは
   これを見ていない）。`npm run stats:balance` で日数が成立するかを測る。

段1を段2より前に置くのが肝。**骨格が決まると、文法追加のうちどれが本当に要るかが決まる。**

**段の全部をあらかじめゲートにしない。** 先の段の issue はまだ書けていないので、置いても中身の無い
関門が並ぶだけになる。ゲートを立てるのは、**その後ろに置きたい issue が実際に現れたとき**。

### ready を配るところまでは機械が持つ

`TASK` に出るものは、依存の上では**今すぐ着手してよい**。

- **資源の衝突は錠で避ける**（2節）。走っている issue と `area:` を取り合わないかは
  [`board-move.mjs`](../scripts/agent/board-move.mjs) が見る。
- **次の段のゲートを閉じるかどうかだけが、人に残る。** 段を進めてよいという判断は渡さない。

**印から issue の文面を起こす作業を、盤面を見る手番の中でやらない。** `【未実装】` を数えて issue に
起こすような一度きりで読み込みの重い仕事は、別セッションへ出す——**文脈へ入れたものの費用は「その
大きさ×残りのターン数」**（1節）で、長く回るセッションだけが払う費用が高い。**出す先は下の発掘係。**

### 配れる task が尽きたら、発掘係が数える

**配れる `kind:task` が無くなった周に、発掘係が一日一回立つ**（[`board-design.md`](board-design.md)
2.17。渡す本文は [`dig-prompt.md`](dig-prompt.md)）。数えるのは**完成の定義に載っているものから、
既に issue になっているものを引いた残り**で、**「仕事を探せ」とは言わない**——そう言われた側は必ず
何か見つけるので、出力の質が観点の質と同じになる。

- **数えるのは、残りの作業量を答えられるものだけ**——`未決事項`・`今後の検討課題` の節、`【未実装】`
  の印、`stats/balance.yaml` の収支の穴（[`policies.md`](policies.md)「未実装のものの扱い」）。
  「無くても完成を宣言できるもの」は [`Someday.md`](../docs/Someday.md) に分けてある。
- **出口は分かれる。** やると決まっているもの（収支の穴と、**段0を通った** `【未実装】`。下の
  「承認の要る未実装を、勝手に流さない」）は**そのまま issue**。やるかどうかから訊くもの
  （`未決事項` と、段0を通っていない `【未実装】`。下の「未決は「やるかどうか」から訊く」）は
  **`判断待ち` を付けたチェックの一覧を1本**（[`board-design.md`](board-design.md) 2.17.2）。
  全部を訊く側へ回すと、立てても配れるものが1件も増えない。
- **「残り0件」は失敗ではなく、正しい報告。** 見つからなければ issue を立てずに終わる。
- **リポジトリへは1行も書かず、PRも出さない。書くのは自分で立てる issue だけ。** 掘り起こすのは
  材料で、手を動かすのは配られたワーカー（報告と反映を同じ役に持たせない）。

### コンテンツを後回しにしない理由

`npm run stats:balance` が「1日を賄う最小労働 624分（1440分の43.4%）」と出している。残りの56.6%に
することが無ければ100〜200日は成立せず、生存コストを上げて日数を伸ばすのは
[`DesignPrinciples.md`](../docs/concept/DesignPrinciples.md) の「時間経過に任せる区間を作らない」と
衝突する。**コンテンツ不足は仕組みの未検証と同じもので、後に回すほど手戻りが大きい。**

コンテンツの幅出しは、仕組みの実装よりスウォームに向いている——触るファイルが YAML 24本に分散し、
完了条件を `stats:balance` が定義だけから計算し、系統どうしが干渉せず、量がある。

## 5. 現在地と、何を投入してよいか

**今どこまで進んでいるかは、リポジトリのどこにも書かない。** [`board.sh`](../scripts/agent/board.sh) が
GitHubから毎回引き直す——走っているセッション・PRとそのラベル・配れる `kind:task`・`blockedBy` の
鎖は、全部あちらに在る事実で、写しを持てば**古くなったことに誰も気づけない**
（[`board-design.md`](board-design.md) 1節）。済んだ段だけは取り決めなので同ファイル3節が持つ。

**唯一の写しは、デーモンが常設の issue へ周期で書き出す盤面**（同 2.20）。**スマホから読むための
ものだけ**で、機械は読み返さず、古くなったことは本文の最終更新の時刻で分かる。

このファイルが持つのは進め方だけで、動くのは取り決めが変わるときだけ。**状態を混ぜない**——1日に
何度も動く情報をファイルに置くと、更新のたびにコミットとPRが要り、履歴が写しで埋まる。

### 盤面を回す仕組みの手入れは `main` へ直接 push する

`.claude/` 配下（このファイル・[`policies.md`](./policies.md)・フック）と
[`scripts/agent/`](../scripts/agent)（盤面を回す道具・シェルの検査）、`.github/extensions/`（Copilot CLI の
フック）の変更は、PRを作らずに `main` へ直接 push してよい。`main` に保護は掛かっておらず、
**PRにしてもユーザーのタップを1回増やすだけ**だから。

**CIは `.claude/` を触った push でも走る**（#840 で `tests.yml` の `paths` を外した。`.claude/**` は
`eslint .`・`prettier --check .`・`exports.test.ts` の実際の入力）。**赤くなるのは push した後**なので、
直接 push する前に手元で4つのコマンドを通しておくこと。それが面倒な変更は、PRにしてよい。

**この経路でも、一次レビュー（1節）は同じように通す。** PRを作らないぶん、外のレビュアーが読む機会が
そもそも無いので、**素通しすると誰の目にも触れないまま `main` へ入る。** 結果を書く `## 自己点検` の
節が無いので、指摘とその扱いはコミットメッセージの本文へ1〜2行で残す。**ただし
`.claude/decisions/` への記録だけは立てない**（出どころ: ユーザーの指示・2026-09-07）——レビューの
観点はこの配下を見ないと決めてあり（[`review-criteria.md`](./review-criteria.md)「見ないもの」）、
通しても返るものが無い。

**ルートの [`CLAUDE.md`](../CLAUDE.md) も同じ扱い。** 進め方の取り決めそのもので、`.claude/` 配下と
同じ性質——**タスクのセッションも必要なら直しに来るが、重なりを避ける必要は無い**（同じファイルを
2本が書くことは止めない。2節）。

**盤面のスクリプトの試験（`tests/scripts/mergeAndClose.test.ts` のような、`scripts/agent/` の
1本に張り付いた試験）も同じ扱い。** 分けると、スクリプトだけが先に `main` へ入って CI が赤くなる。

`src/` `docs/` `tests/` を触る変更は今までどおりPR。CIが要り、他のセッションと触る先が重なりうる。

### エージェントを選ばない道具は `.claude/` に置かない

[`daemon.sh`](../scripts/agent/daemon.sh) と [`board-move.mjs`](../scripts/agent/board-move.mjs) は
`gh`・`jq`・`node` だけで動き、どのエージェントが起動しても同じに振る舞う（**エージェントが1本も
起きていなくても動く**）ので `scripts/agent/` に置く。`.claude/` に残すのは、**Claude Code が形式を
決めているもの**——フック・`settings.json`・`launch.json`・メタMCPの入口（`ccr-meta.sh`）と、
セッションへ渡す指示のひな形だけ。

`.claude/skills/` は例外で、動かさない。**Copilot CLI もこの場所を読む**ので、移すと両方から見えなくなる。

### 承認の要る未実装を、勝手に流さない

**未実装として置かれているものは、段0（要否の判断）を通ってから実装する**
（[`policies.md`](./policies.md)「未実装のものの扱い」）。設計文書に書いてあることを順に実装すると、
断らなかっただけのものが仕様になる。

判断の材料は印で付いている。`【確定】`＋段0の仕分け済みなら流してよく（#706・#707 がこれ）、
#656 に未チェックで載っているものは待つ。**仮決めして進む既定はこれと衝突しない**——仮決めが
効くのは「決まっていないから止まる」場面で、ここは**既に訊いてあって答えが来ていない**場面。

**ただし、待つことは唯一の道ではない。** 明るさの「大きいほうを採る」合成は、答えが来る前に
**問いのほうが消えた**——値の設計を作り直して加算だけで書けるようにしたため、文法が要らなくなった。
関門に当たったら、答えを待つのと並べて**要求そのものを畳めないか**を疑う
（[`DesignPrinciples.md`](../docs/concept/DesignPrinciples.md)「宣言の表現力は、定義がプログラムに
なる手前で止める」の、正しさの不足より仕組みが増えるほうが重い、が根拠）。

## 6. 盤面を回すときの判断

**ここに在るのは、盤面を回す側（デーモン・issue を配る側・レビューを立てる側）だけが要る判断。**
どのセッションも要る判断は [`policies.md`](./policies.md) が持ち、そちらは全セッションへ注入される。

### 無人で進むことは、目的であってコストではない

人が居ない時間に消費が集中していると分かっても、**無人での自動進行を絞らない。下げるのは1回
あたりの単価**（文脈の大きさ・往復の回数）。人が居ない間も仕事が進むことはこの仕組みが目指して
いる形そのもので、**進む量を減らして帳尻を合わせるのは目的のほうを削っている。** 派生した issue を
無人のまま投入し続けることも止める理由にならない——**仕事が仕事を生むのは正常な動作。**

### ユーザーが投入を止めると告げたら、入口だけを一律に止める

理由（使用上限が近い・仕組みを変えたい等）で対応を変えず、告げられた通り、次の指示があるまで
**新規タスクの投入だけを止めて、開始済みの完了を優先する。** 理由が違っても実害は同じ形を取る
——走っている途中のタスクが**本人の意図とずれた前提のまま**進む。**絞るのは入口だけで、レビュー・
マージ・差し戻しは止めない**（あれは開始済みを完了させる手）。

**引き金はユーザーの発言だけ。** 理由の是非や残量を自分で判定せず、告げられていない間は止めない。
再開も同じくユーザーの発言を待つ——期限が明確な理由でも、告げられるまでは止めたままにする。
止め方は手綱の issue のチェックを外すこと（`## 手綱` の「新しいタスク」）。

### 仕組みの変更は、本人の具体案が届くまで着手しない

`.claude/**`・`scripts/agent/**`・`CLAUDE.md` について、ユーザーが構想を告げたが具体案がまだ本人の
中にしかないとき、**自分の見立てで着手しない。** ここを推測で動かすと、本人の構想と食い違った土台の
上に本人の案を継ぎ足すことになる。案が届く前に催促もしない——判断はユーザー本人の手番。

### 成果の点検は、受け取る側ではなく作った側にやらせる

受け取る側は**全部を受け取る**ので、1本あたりが軽くても本数だけ積もる——**コンテキストが埋まって
後の判断が痩せ、点検が終わるまで全体が待つ。** 作った側は1本しか持っておらず、**何を調べたかを
知っているのも作った側だけ**なので、同じ点検が安く深くできる。受け取る側が読まねばならないなら、
**読む役を別に立てて、返させるのは結論だけにする。**

### 一次レビューは、外のレビューを置き換えない

出す前のサブエージェントが「通してよい」を出しても、別セッションのレビューは立てる。サブエージェントは
書いた本人が立て、同じチェックアウトと同じ前提の上に居るので、**信用の置き所である「独立した文脈で
読まれたこと」がそこには無い。** 一次レビューの値打ちは往復を減らすことであって、外の判定を代行する
ことではない。

**周を飛ばす道は無い**（上の「PR の型」）。コンフリクトを解いただけに見える周も、外を1本立てる。

### 別セッションの範囲外の変更は、取り決め違反と決めつけない

渡した issue の `## 完了の条件` から外れた変更が混じっていたら、差し戻す前に**ユーザーがその
セッションと直接話した結果ではないか**を確かめる。成果物からは、指示が issue から来たのかユーザー
から来たのかが見えない——**取り決めを根拠に差し戻すと、ユーザー自身の判断を取り消すことになる。**

### 未決は「やるかどうか」から訊く

`docs/**` の未決事項を、残りの作業として task へ落とさない。**未決は「まだ決めていないこと」であって
「やると決めたこと」ではない**ので、そのまま task にすると乗り気でないものが実装されて戻ってくる。
訊き方は、有力な案が1つなら採否、複数あるなら選択、そのレベルにも達していないなら**「入れない」を
選択肢に並べる**（[#656](https://github.com/gooyyu1/UnmappedIsland/issues/656) の使い方）。

### 別の仕事に属する不具合は、自分の成果を止めて先に流す

作業中に別の仕事の不具合を見つけ、直せないまま自分の成果にその影響が出るとき、影響を含んだものを
「仮決め」として出して判断を仰がない。**明らかな不具合の直し方は仕様から一意に決まる**ので、訊いても
答えは決まっている。**判断の要らないものを判断待ちへ混ぜると、本当に判断が要るものが埋もれる。**

### 仮決めの申告には、可否ではなく足りない判断根拠を訊く

`## 仮決め` が付いたPRを受け取ったとき、その可否をそのまま訊かない。**どのポリシーが足りなくて
自分では決められないのか**を特定して、それを訊く。可否だけを貰っても次に同じ形で止まる——**貯める
のは判断ではなく判断根拠**で、返ってきたものは記録に入って次から効く。**足りないものを言語化
できないなら、それは自分で判断できるということ。**

### 待ちを終える条件は「やることが無いこと」

待ちの道具が見る範囲を「投入したものの決着」に限らず、「やることが残っているか」まで広げる。
前者は、投入した全部が判断待ちで止まった瞬間に**何も起こらなくなる**——手が空いたことも、その間に
積まれた新しい仕事も、誰の目にも触れない。

### 判断の要る論点を含むタスクも、仮決めさせて投入する

答えが出るまで握って止めない。**仮決めして進む既定は、作業する側だけでなく配る側にも掛かる。**
配る側が握って止めると、待っていることが誰の目にも見えない。

### 消せない記録が誤って付いたら、入れ物ごと作り直す

**提出済みのレビューは消せない。** GitHubの削除APIは下書き（PENDING）専用で、残る手は dismiss だけ
——これは記録を消すのではなく**タイムラインに1件足す**。差分もブランチも無傷なので、**同じブランチ
からPRを立て直せば、失うのはPRの番号とコメントの並びだけ。** 入れ物が安いなら、汚れた入れ物を
弁解しながら使い続けない。
