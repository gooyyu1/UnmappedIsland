# 並列作業の進め方

多数のエージェントで同時に開発を進めるための取り決め。**このファイルは進め方だけを持つ。**
確定度の印は [`docs/DocumentStyle.md`](../docs/DocumentStyle.md) 6節、確認の積み方と
「担当外は触らない」は [`CLAUDE.md`](../CLAUDE.md) が持つので、ここでは繰り返さない。

**人間向けの全体像は [`docs/ParallelAgents.md`](../docs/ParallelAgents.md)。** 誰が何をして人間はどこで
決めるのかを図で示す。**規則を書くのはこちらだけ**で、あちらは全体像だけを持つ（同じ説明を二度書かない）。

## 1. 分かれ目は「どこかに書くか」

| その役が書く先 | 走らせ方 | 例 |
| --- | --- | --- |
| **どこにも書かない**（結論を親へ返すだけ） | **同じセッションのサブエージェント** | 掘り起こし役、PRを出す前の自己レビュー |
| **どこかに書く**（作業ツリーのファイル・PR・コメント・issue） | **別セッション。1タスク = 1 issue = 1ブランチ = 1PR** | 作業者、レビュアー、棚卸し役 |

**「読むだけならサブエージェント」ではない。** レビュアーも棚卸し役も読む仕事だが、どちらも別
セッション——**書いたものが記録として残り、それが次を動かす合図になる**（`REVIEWED`・`## 未整理`）。
司令塔は自動コンパクションを跨いで何時間も回り続けるので、**親と運命を共にするサブエージェントには
置けない。**

どこかに書く作業を別セッションにするのは、次の3つが順に効くため。**1と2が効くのはファイルへ書く役
（作業者・相談役）で、3は書く先によらない。** GitHubへ書く役（レビュアー・棚卸し役）を別セッションに
する理由は、上の段落にある記録と合図のほう。

1. **作業ツリーが物理的に分かれる。** 同じセッションのサブエージェントは同じチェックアウトを
   共有するので、並列で書くと整形の PostToolUse フックや git の状態を互いに壊す。
2. **統合機構が既にある。** 1セッション = 1ブランチ = 1PR は今の運用そのままで、追加の仕組みが
   要らない。1セッションから複数ブランチを作ると、この運用から外れる。
3. **SessionStart フックが確実に掛かる。** `inject-policies.sh` が価値観を流し込むのはセッション
   単位。サブエージェントに同じ文脈が入る保証は無く、価値観の記録が空振りしうる。

どこにも書かない作業を同じセッションに置くのは、衝突が起きず、**読んだ量が子の文脈に留まって親へは
結論だけが返り**、ユーザーの手数がゼロだから。

### PRを出す前の自己レビューは、サブエージェント

**作業セッションは、PRを作る前に、これから出す差分をサブエージェントへ読ませる**
（[`dispatch-prompt.md`](dispatch-prompt.md)）。渡す観点は
[`review-criteria.md`](review-criteria.md)——**外のレビュアーが読むのと同じ一覧**。

**手順を通るのは作業セッションのPRだけ。** 手順が居るのは `dispatch-prompt.md` で、司令塔と相談役は
そこを通らない。**だが `## 自己点検` の節は全部のPRが置く**（下の「### PR の型」）——通らない側は
「手順を持たない」と書く。外のレビュアーは、手前を通ったかどうかをこの名乗りで**振り分ける**
（[`review-prompt.md`](review-prompt.md)）。

分けているのは差分の大きさではなく**渡すもの**で、外のレビュアーと同じ3つ（差分・issue・PR本文の
原稿）だけを渡し、**本人にしかない事情は渡さない。** 渡すと書いた本人の仮説をなぞるだけになり、
手前を通した意味が無くなる。

**これで外のレビューが要らなくなるわけではない。** サブエージェントは親と同じチェックアウトに
居るので、**素通しした結果は誰にも記録されない**——止める権限を持てるのは、GitHubへ書く別セッション
だけ。手前の1本は往復の回数を削るためのもので、往復そのものを置き換えるものではない。

### GitHubへ書く作業をどこへ立てるか

実行元ごとに、確実に起動する隔離先を選ぶ。

| 実行元 | 立てる先 |
| --- | --- |
| Claude | **クラウド優先**。画像の生成（ComfyUI）だけ**ブリッジ環境へ投入する** |
| Copilot | **ローカルworktree**。クラウドは使わない |

Claude はローカルの枠を画像生成のために空ける。Copilot のクラウド起動は失敗する経路であり、隔離は
ローカルworktreeで確保できる。実装・ドキュメント・画面の動作確認もこの原則に従う。

**画像生成も「投入する」。司令塔が自分で抱え込まない。** ここでの「ローカル」は**投入先の環境の
名前**であって、そのセッション自身が作業することではない。**この読み違いを一度やっている**
（2026-08-28、「絵の生成は ComfyUI 依存なのでタスクとして投入できない」とユーザーへ報告した。
実際にはブリッジ環境へ投入すれば済む話だった）。**タスクとして出せないものは無い。**

`create_session` は既定で**呼び出し元と同じ環境**に立つので、環境を選ぶには `environment_id` を
渡す。IDは `bash .claude/ccr-meta.sh list_environments <<<'{}'` の `kind` が `bridge` のもの。

```bash
bash .claude/ccr-meta.sh list_environments <<<'{}'   # kind が bridge のIDを取る
# args.json に "environment_id": "env_..." を足してから立てる（他は普段どおり）
bash .claude/ccr-meta.sh create_session < args.json
```

セッションはエージェントが立てられるので、ユーザーの手数は「issue に答える」だけ。ローカルから
呼ぶときは `permission_mode` を渡せないため、既定のまま作る。

#### 立てる・確かめる・畳むは [`ccr-meta.sh`](./ccr-meta.sh)

**`mcp__ccr_meta__*` の登録は消した**（`~/.claude.json`）ので、入口はこれ1つ。あれは**起動時のヘッダを
掴んだまま**で、走っている最中にトークンが切れると、登録を直しても**そのセッションからは二度と
使えなかった**（2026-08-25 に2回起きた）。

```bash
bash .claude/ccr-meta.sh create_session < args.json
bash .claude/ccr-check-prompt.sh <セッションID> <送った指示のファイル>
bash .claude/ccr-meta.sh archive_session <<<'{"session_id": "cse_..."}'
```

**ただし投入は [`dispatch-task.sh`](../scripts/agent/dispatch-task.sh) から呼ぶ。** 上の3行は入口の説明で、
投入のたびに手で組むものではない——引数の組み立て・立てた中身の確認・照合まで含めて1回で済む。

```bash
bash scripts/agent/dispatch-task.sh 1029 "$LOCALAPPDATA/Temp/ui-1029.md"
bash scripts/agent/dispatch-task.sh 1029 <指示ファイル> --bridge   # 画像生成など
DRY_RUN=1 bash scripts/agent/dispatch-task.sh 1029 <指示ファイル>  # 渡す引数を見るだけ
```

**引数は標準入力で渡す**（argvではない）。**呼ぶたびに `~/.claude/.credentials.json` から読み直す**ので
切れない。**道具も引数も普段と同じで、23個すべてが使える**——MCPサーバもただのHTTPで、しかも
ステートレスに応じるため、`tools/call` を1発投げるだけでよい。

**指示の本文は [`dispatch-prompt.md`](./dispatch-prompt.md) を写して作る。** 手で書き起こすと落ちる
（2026-08-27 に「PRを見張らない」が3本すべてから抜けた）。

**立てた直後に [`ccr-check-prompt.sh`](./ccr-check-prompt.sh) を通す。** 指示が化けても壊れても
セッションは普通に動き出すので、**動いている様子は判断材料にならない**（2026-08-25 に、丸ごと化けた
指示で20分走らせた）。届いた本文と送ったファイルを文字列で突き合わせて、一致だけを信じる。

**RESTを逆算しない**（`/v1/code/sessions` を直に叩く道もある）。形が違ううえ
（`sources` は入れ子ではなく平ら）、**`DELETE` は畳まずに消す**——同じ意味の操作を2通り持つ理由が無い。

`RemoteTrigger` でも立てられるが、**トリガー発火の実行はセッション一覧に出ない**——ユーザーが進み
具合を見に行けないので、上を先に使う。

### 前のタスクの完了は、シェルで待つ

直列に並べたタスクは、[`wait-for-issues.sh`](../scripts/agent/wait-for-issues.sh) をバックグラウンドで起動して
待つ。完了した瞬間に1回だけ起きて次を投入できる。

```bash
bash scripts/agent/wait-for-issues.sh 662
```

**間隔を空けて浮くものは無い。** 高いのはモデルのターンであって `gh` の呼び出しではないので、
既定の5秒のまま詰めて回す。空けた分はそのまま次のタスクの着手が遅れるだけになる。

**待つのは「その issue を閉じる PR がマージされたか」。** ここが訊いているのは仕事が終わったかでは
なく、**前のタスクの変更が main に入ったか**なので、それを直接表すマージを見る。取り下げで閉じた
issue は、終わってはいるが main には何も入っていない。

なお、issue はセッションが閉じるものではない（[`CLAUDE.md`](../CLAUDE.md)「タスクの issue を渡された
とき」）。閉じさせていた頃は、**まだ main に何も入っていない時点で「完了」の合図が出ていた**
——実測で8件中6件が、PRのマージより最大21分早く閉じられていた。

### 司令塔の文脈は、放っておくと1応答50万トークンになる

**無人で回り続けることは目的なので、抑えるのは動きの量ではなく1回あたりの単価**
（[`policies.md`](./policies.md)「無人で進むことは、目的であってコストではない」）。

2026-08-26 に5時間の上限へ当たったときの実測——**960応答で読み込み531M**、1応答あたり**平均553k・
最悪923k**。出力は1応答あたり983トークンしかない。**書いた量ではなく、読み直した量で消えている。**

手は2つで、どちらも効く。

- **`~/.claude/settings.json` の `autoCompactWindow`**（10万〜100万の整数、単位はトークン）。
  1M文脈のモデルでは既定が実質100万なので、**50万を超えてから畳まれていた**。司令塔は状態を
  文脈ではなく #732 に持つので、狭めて失うものがほぼ無い。**200000 を入れてある。**

  **これ以上は下げられない。** 20万未満を入れると判定が `window < 200000` で打ち切られ、
  **自動コンパクションが丸ごと止まる**——畳まれないまま上限まで伸びるので、締めたつもりで逆を
  向く。20万は有効なまま取れる最小値ちょうど。実効の発火点は、ここから出力枠の予約2万と
  バッファ2割を引いた**14.4万トークン**。
- **Bashを1回にまとめる。** 文脈を膨らませていた首位は Bash で、**688回・15万トークン**。ただし
  1回あたりは220トークンで、**巨大な出力が数個あるのではなく小さいものが688個**だった。
  `gh pr view` と `git log` を別々に打つのをやめるだけで、回数も総量も減る。

  **決まりきった並びはスクリプトへ畳んである。** 1サイクル10〜14回だったものが5〜7回になる。

  | 何をするとき | 打つもの |
  |---|---|
  | 盤面を見る | [`board.sh`](../scripts/agent/board.sh)（開いているPR・`task` issue・畳んでいないセッションを1つの表に） |
  | 投入する | [`dispatch-task.sh`](../scripts/agent/dispatch-task.sh)（`<issue番号>` と指示ファイル） |
  | 決着を待つ | [`watch-prs.sh`](../scripts/agent/watch-prs.sh)（`GREEN` にはPRの題・本文・ファイル一覧が付いてくる） |
  | マージして片付ける | [`merge-and-close.sh`](../scripts/agent/merge-and-close.sh)（`<PR番号>`） |

  **畳んだのは往復だけではない。** 手で叩くと省かれていた確認——`blockedBy`・`tags`・投入前の
  issue の `state`——が、必ず通るようになっている。判断が要るのは**合図をどう捌くか決めるところ**と
  **指示文を書くところ**の2つだけで、そこは畳んでいない。

**PRを読むときは全文を入れない。** 司令塔宛ての節（下の「PR の型」の表で読む相手に司令塔が
挙がっているもの）と、チェックの結果と、触ったファイルの数で足りる。

```
gh pr view <番号> --json body --jq .body | tr -d '\r' |
  awk '/^## /{ p = /^## (仮決め|担当外へ入った直し|見た目|司令塔へ|ユーザーの指示)$/ } p'
```

**`tr -d '\r'` を省かない。** 節の名前を `$` で留めているので、CRが乗った本文では5節とも一致せず
**何も出ない**（司令塔の道具も同じ用途では通している。
[`merge-and-close.sh`](../scripts/agent/merge-and-close.sh)・
[`watch-prs.sh`](../scripts/agent/watch-prs.sh)）。

**司令塔の文脈へ入れたものの費用は「その大きさ×残りのターン数」**で、1回の読み込みでは終わらない。

### 投入する直前に、その issue が開いているかを見る

[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh) は、題を引くのと同じ `gh issue view` で `state` も
見て、開いていなければ立てずに終わる。**前に一覧で見たときの状態は当てにならない**——ユーザーは
issue をいつでも閉じる（取り下げ・却下・別のPRが `Closes` で閉じた）。

閉じた issue へ立てると、セッションは指示どおり「仕事は無い」と判断して即終了する。ここまでは
正しいが、**PRが出ないので [`watch-prs.sh`](../scripts/agent/watch-prs.sh) には何も届かない**——PRだけを見張って
いるからで、タイムアウトまで空待ちになる。2026-08-25 に、却下されて閉じた issue へその16分後に
セッションを立て、120分の空待ちに入りかけた。

**そのため、待ちに入るときは投入した issue の番号も渡す。**

```bash
bash scripts/agent/watch-prs.sh --issues 746,751 --timeout-minutes 120
```

issue が閉じた時点で `GONE <番号>` が出る。**PRの決着と、PRが出ないまま終わったことの両方が、
1つの待ちで拾える。**

### 終わったセッションは、issue を鍵にして畳む

**PRが出たものは [`merge-and-close.sh`](../scripts/agent/merge-and-close.sh) が畳む。** PR本文の脚注
（`https://claude.ai/code/session_...`）がそのPRを書いたセッションなので、マージと同じ1回で片付く。
タグより脚注が確実で、**同じ issue へ2回投入したときに古いほうを畳んでしまうことが無い。**

以下は**PRが出ないまま終わったセッション**の畳み方。[`dispatch-task.sh`](../scripts/agent/dispatch-task.sh)
が付ける `task-<番号>` のタグで引く（`watch-prs.sh` の `STALLED` が見ているのと同じタグ）。畳む条件は2つ。

- **その issue が閉じている。** 閉じるのはマージのときなので、閉じた＝入ったか取り下げられたかの
  どちらかで、いずれもそのセッションの仕事は終わっている。
- **自分が立てたクラウドのセッション。** **ユーザーが立てたものとブリッジのものには触らない。**
  前者は走っている作業を止めることになり、後者は `claude remote-control` が落ちている間に畳むと
  worktree がロックされたまま残る。タグはクラウドとブリッジで同じなので、`--bridge` で投入した
  ものは `environment_id`（[`ccr-env.sh`](../scripts/agent/ccr-env.sh) の `BRIDGE_ENV`）で除き、
  `KEPT` として出す。ユーザーが立てたものは `task-` のタグを持たないので、同じ `KEPT` に落ちる。
- **素性を引けなかったものも `KEPT`。** `get_session` が引けないと、走行中かもブリッジかも分からない。
  **知らないことを「違う」として読まない**——畳んで消えたコメントも、ロックされたまま残る worktree も
  戻せないので、引けなかったものは残す。マージ後の `KEPT` は渡す出来事がもう無いので、司令塔が
  引き直して手で畳む。

**状態で判定しない。** 走行中かどうかは分かる（`status_bucket` が
`SESSION_STATUS_BUCKET_WORKING`。[`watch-prs.sh`](../scripts/agent/watch-prs.sh) の `STALLED` は
これで走行中を除いている）が、**知りたいのは「仕事が終わったか」で、それは待機中の中身**にある。
待機中には「レビューを書き終えた」も「こちらからの追加指示を待っている」も落ちるので、
区別が付かない。「完了してから一定時間」も同じ理由で使えない。**畳んでよいかは、上の2つのような
外から見える出来事で決める。**

**走行中を除くのは、これとは別の問い。** `archive_session` はコンテナを解放するので、判定を書いて
いる最中のセッションを畳むと、そのコメントは出ないまま消える。「今走っているか」は上のとおり
判定できるので、[`archive-session.sh`](../scripts/agent/archive-session.sh) が畳む直前に見て除ける。

**ただし除けば `KEPT` として残るだけで、誰かがもう一度渡さない限り二度と畳まれない。** だから守るのは
**その出力を読む相手がまだ居るとき**だけで、それは**PRがまだ開いているレビュー**（下の節）に限る。
上の `task-` のセッションは issue が閉じた＝マージ済みで、走行中でも畳む——判定を書き終えても読む相手が
無く、渡す出来事も二度と起きない。守るかどうかは呼び手が `--keep-working` で渡す。

畳んだセッションは戻せる（unarchive）ので、猶予は置かない。

#### レビューのセッションは、残っているものを全部まとめて畳む

レビューは issue を持たずPRも出さないので、上の2つのどちらでも引けない。手掛かりは
[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh) が付ける `review-<PR番号>` のタグだけで、
[`archive-reviews.sh`](../scripts/agent/archive-reviews.sh) がそれで引いて畳む。**司令塔が打つ道具では
なく**、「もう起こされない」と確定する2つの瞬間に、それぞれの道具の中から呼ばれる。

- `dispatch-review.sh` が**次を立てる直前**。レビューは使い回さない設計なので、次を立てる時点で前の
  分は終わっている。
- `merge-and-close.sh` が**マージした後**。PRが閉じれば、最後の1本も読む相手が無くなる。

**呼ばれた側が掃くのは、その瞬間のPR1本ぶんではなく、残っている `review-*` 全部。** 畳んでよい理由は
PRごとに違わない（どのレビューも使い回さないので、走り終わった時点で誰も起こさない）一方、**1本ずつに
絞ると、上の2つがこの先どちらも起きないPRのぶんが永久に残る**——`判断待ち` でユーザーの手番に入った
PRと、`直し待ち` のまま戻ってこないPRがそれで、2026-08-30 に16本溜まっていた。全部を見るなら、
そういうPRのレビューも、他の何かが1件マージされたついでに片付く。

**走行中を守るかはPRごとに決める。** 開いているPRのレビューは守り（`KEPT`。次の投入かマージで渡し
直される）、閉じた・マージ済みのPRのレビューは走行中でも畳む——判定を書き終えても読む相手が無く、
渡す出来事も二度と起きないから。開いているPRの一覧を引けなかったときは、全部を開いている側として
扱う（畳んで消えた判定は戻せないが、守って残ったものは手で畳める）。

**ブリッジで立てたレビューと、素性を引けなかったものを除くのは、上の `task-` と同じ。** タグは
クラウドとブリッジで同じなので、`environment_id` で見て `KEPT` として出す。

投入もマージもしばらく起きないときは、`bash scripts/agent/archive-reviews.sh` を手で叩いてよい
（引数は無い）。

#### 待ちを終える条件は「やることが無いこと」

**投入したものの決着だけを待つと、全部が `判断待ち` で止まった瞬間に何も起こらなくなる。** 手が
空いたことも、その間にセッションが立てた issue も、誰の目にも触れない。

[`watch-prs.sh`](../scripts/agent/watch-prs.sh) は、**`task` ラベルの付いた open な issue のうち、open な
`blockedBy` が無く、`task-<番号>` のセッションも立っておらず、open なPRが `Closes` で指しておらず、
`--issues` にも無いもの**を `TASK <番号>` として出す。出さない4つは、どれも**投入する先が無いか、
既に誰かの手元にある**もの——`task` の無い issue（確認の置き場・ユーザーの答え待ち）は仕事の単位では
なく、依存が残っているものは投入しても着手できず、投入済みのものとPRの出ているものは、そのセッションが
持っている。

**`--issues` に渡すのは、「こちらが把握している `task`」のうち投入していないもの**——投入したものは
`dispatch-task.sh` が付ける `task-<番号>` のタグで機械が知るので、渡さなくてよい。渡すのは、
**意図して置いてある `task`**（仮決めの範囲に含まれるもの）だけ。`task` の無い issue は判定の側で
落ちるので、`TASK` を黙らせる目的では渡さなくてよい。#732 を渡すのはコメントを拾うため
（「承認はマージ、却下はコメント」節）。

拾うかどうかは受け取った側が決める。**判断の材料は、その issue を生んだPRの `## 仮決め` にある**
——そこで「この issue を立てて、直さずに出した」と申告されているなら、**その扱い自体がユーザーの
判断待ち**なので拾わない。申告に含まれていなければ、鎖の外の仕事として流してよい。

#### 畳む引き金は `GONE`

**条件が揃っても、それを見に行かなければ畳めない。** [`watch-prs.sh`](../scripts/agent/watch-prs.sh) の `GONE <番号>`
は「その issue が閉じた」——**上の1つ目の条件そのもの**なので、これを合図にする。

- **`--issues` には、投入した issue を全部渡す。** PRが出ないまま終わったものを拾う用途（`GONE` の
  もう一つの読み方）と同じ引数で、掃除の合図も来る。
- **`GONE` を受けたら、`task-<番号>` のタグを持つセッションを畳む。** PRが出ていたなら
  `merge-and-close.sh` が既に畳んでいるので、残るのはPRを出さないまま終わったものだけ。
  **走行中でも畳む**——issue が閉じた時点でその仕事は終わっており、**ここが渡す最後の機会**
  （上の `task-` のセッションと同じ。守っても、次に渡す出来事がもう起きない）。

**「気づいたときにまとめて畳む」をやめる理由は、遅れが仕事と無関係にばらつくこと。** 実測（2026-08-25）
では issue が閉じてから畳むまでが2分・23分・30分で、**差を作っていたのは仕事の中身ではなく「次に
別の用事で起こされた時刻」だった**。`GONE` に結び付ければ見張りの間隔（既定5秒）まで縮む。

**一定時間ごとに自分を起こして掃除する形は採らない**（`send_later`）。自動承認ができないので、掃除
1回ごとにユーザーのタップが要る——放っておいても壊れないものに、それは高すぎる。

### 本体のチェックアウトは、マージのたびに追随させる

作業ツリーは `<repo>/.claude/worktrees/` に置かれる。**リポジトリの中なので、Node も npm も親を
遡って本体の `node_modules` を共有する。** 作業ツリーごとに `npm install` を打つ必要は無い。

**共有先が古いと、共有しているのに版が食い違う。** 誰も本体では作業しないので、放っておくと本体は
古いままになる。落ち方は `Cannot find module` ではなく、**古い版が解決されて一部だけ壊れる**——本体が
`ajv` 8 を持たず eslint 由来の 6 だけ在ったとき、`require` は通ったままテストが1本落ちた。踏んだ側は
自分の変更を疑う。

そこで [`merge-and-close.sh`](../scripts/agent/merge-and-close.sh) が、マージと同じ1回で本体を
`origin/main` へ進める（`SYNCED`）。`package-lock.json` が動いたときだけ `npm install` も打つ
（`INSTALLED`）。**本体はブランチを持たない（detached HEAD）**——`main` は同時に2箇所へチェックアウト
できず、本体が握ると作業ツリーが作れなくなる。detached は「固定」ではなく、指す先を毎回新しい `main`
へ付け替える形。本体に未コミットの変更があるときは触らず `DIRTY` を出す（未追跡は見ない）。

**作業ツリーの側は直さない。** [`session-start.sh`](hooks/session-start.sh) は、自分の
`package-lock.json` と共有先に実際に入っている木を突き合わせて、足りなければ名指しで促すだけ。
ここで `npm install` を打つと250MBの複製ができて共有が終わるうえ、**共有先を読んでいる他のセッションの
足元が揺れる。**

### 止まったセッションを起こす引き金は `STALLED`

**待機中（IDLE）は「終わった」と「止まった」の区別が付かない。** 利用制限・権限の確認待ち・失敗で、
セッションはPRを出さないまま待機中になる。GitHub の側には何も現れないので、上のどの行も出ない。

2026-08-28 に、投入した4本（#915・#932・#953・#936）が同じ分に止まり、**3時間そのままだった**。
気づいたのは司令塔が別の用事で `list_sessions` を打ったとき——見張りは5秒ごとに回っていたが、
一度も知らせていない。

[`watch-prs.sh`](../scripts/agent/watch-prs.sh) は `list_sessions` も引いて、**動いておらず、自分の
IDを載せた open なPRも無い** `task` のセッションを `STALLED <セッションID> <題>` として出す。

- **判定は「PRを出したか」だけ。** セッションの状態では、書き終えて報告した IDLE と途中で落ちた
  IDLE が区別できない。突き合わせる手掛かりは2つ——**PR本文の脚注に入るセッションのID**と、
  **`Closes #<番号>` と `task-<番号>` タグの対応**。脚注だけでは足りない（本文を書き直したPRで
  脚注ごと落ちる。2026-08-29 の #1177・#1178）。枝の名前では引けない——ブリッジのセッションの
  `current_branches` は worktree のローカル枝で、push する枝とは別物。
- **マージ済みで畳み忘れたセッションも同じ行に出る。** どちらも司令塔が手を入れるべき状態なので
  種類を分けていない。**受け取ったら `list_events` を見て、起こすのか畳むのかを決める。**
- 引く間隔はPRより粗い（`--session-interval` 秒、既定60）。`.claude/ccr-meta.sh` が使えない環境では
  **標準エラーへ `SESSIONS-OFF` を出して**以降はPRと issue だけを見る。

**起こすときは、止まっている間に `main` へ入ったものを添える。** 再開したセッションは自分が寝て
いたことを知らないので、古い `main` の上で続きを書く。

**意図して止めたセッションは、タグを `held-<番号>` へ付け替える**（`set_session_tags` で `task-<番号>`
を外す）。ユーザーの判断待ちで進ませていないセッションは、PRを出さないまま何時間も待機中に居る
——`STALLED` は毎周それを出し、**見張りはその行でその場で終わる**ので、待ちの仕組みが丸ごと止まる。
`STALLED` が見ているのは `task` で始まるタグだけなので、外せば黙る。**答えが返ったら `task-<番号>` へ
戻してから起こす**（戻し忘れると、以後そのセッションが止まっても誰も気づけない）。

### ユーザーの答えを拾う引き金は `CHECKED`

確認の置き場（#656）は**タップ1つで答えられる形**にしてあるので、**答えはコメントではなく本文の
チェックボックスに付く**。コメントだけを見張っていると、タップは誰にも届かない——ユーザーからは
「タップしたのに何も起きない」、司令塔からは「何も来ていない」としか見えず、**両者は区別が付かない**。
最小の入力を用意した意味が、そこで丸ごと消える。

[`watch-prs.sh`](../scripts/agent/watch-prs.sh) は、`--issues` に渡した issue の本文でチェックの付いて
いる項目を `CHECKED <番号> <項目>` として出す。**チェックは出来事ではなく状態**なので、いつ付いたかに
関わらず、一覧から下りるまで毎周出る。判定は [`checked-items.sh`](../scripts/agent/checked-items.sh) が
1箇所で持ち、[`board.sh`](../scripts/agent/board.sh) の `## 確定待ち` も同じものを使う。

- **`--issues` に #656 を入れておく。** 入れないと本文は見られない。
- **黙る条件は、項目を一覧から下ろすこと。** 拾った司令塔が答えの行き先を `## 下ろした項目` へ書いて
  項目を消すと、`[x]` の箇条書きでなくなるのでそこで黙る。**`【確定】` の印は待たない**——印を付けるのは
  答えを受けた issue の担当者なので、待つと手番が終わったのに一覧が残り、見張りが毎周それで起きて
  他の待ちに使えなくなる。
- 片付け方は下の「束ねる関門は、ゲートの issue を1件立てる」のとおり。

## 2. 所有権の地図

**1タスクの編集が1領域に収まること**が、並列に流せる条件。収まらないものは分けるか、直列にする。
この6分割は定義位置レビュー（`review/placement/`）の調査で実証済み。行数は `.ts` の実測。

| 領域 | 範囲 | 行 |
| --- | --- | --: |
| 1 | `src/domain` 直下 | 7,261 |
| 2 | `src/domain/generation`・`wrappers` ＋ `src/loader` | 5,655 |
| 3 | カード・レーン ＋ `src/ui` ＋ `src/art` | 4,284 |
| 4 | ウィンドウ（`src/game/ui` の `*Window`・`*Pane`） | 約 3,000 |
| 5 | `src/game` 直下 ＋ `view` ＋ `looks` | 8,320 |
| 6 | `src/analysis` ＋ `src/codex-viewer` ＋ ほか | 7,722 |

**`src/game` は層ではない。** [`docs/CodeStructure.md`](../docs/CodeStructure.md) 1節のとおり
映し・意匠・部品の3層に加え、層ではない組み立てと層の外にまたがり、この地図では3・4・5に割れる。

### 縦のスライスは、この地図では割れない

機能追加は層をまたぐので、上の横割りには乗らない。縦を割る基準は**文法を足すかどうか**で、
判定材料は**各設計文書の概要に既に書いてある**（`DocumentStyle.md` 2節が「新設した文法は何か。
新設ゼロならそれを明記する」を要求している）。

- **文法を足す** → `GameElementDefinition.md` と `loader`・`domain` という単一の hub を通るので、
  何本流しても直列寄り。**まとめて1本にする。**
- **宣言だけで書ける** → 専用の YAML と専用の設計文書だけを触るので、**互いに衝突しない。**

### 1ファイル重なることは、直列にする理由にはしない

担当が1つ重なっても、**変える箇所が別なら並列に流す**。触らない箇所を指示で名指しすればよい
（#673 と #722 は同じ `WorldVocabulary.ts` を触るが、一方は明るさのプロパティの登録、他方は表の鍵の
置き場だった）。重なりの度合いを見ずに直列へ落とすと、鎖が伸びた分がそのまま遅れになる。

名指しに加えて、**push の直前に `main` を取り込み直して4つのコマンドを通す**ことを指示に入れる。

### 資源の衝突は、依存ではなく投入の瞬間に見る

**「順序に理由がある」と「同じファイルを触る」は別のもので、後者を依存（`blockedBy`）に書いては
いけない。** 衝突するかどうかは**今どのセッションが走っているかで変わる**ので、issue に書いた
時点の事実にならない。書けば嘘の順序を固定することになる。それに、立てた側は他に何が走るかを
原理的に知らない。

司令塔が投入の直前に見る。**判断ではなく計算になる**——タスク issue の型が `担当` の列挙を義務付け、
`CLAUDE.md` が「担当に挙がっていないファイルは触らない」と禁じているので、**宣言に拘束力がある**。
見るのは走っている issue の `担当` との**集合の交わり**だけで、本文は読まなくてよい。

- **交わりが空なら、そのまま投入する。**
- **空でなければ、そこだけ上の節のとおり中身を見る。** 重なりのコストは壊れることではなくリベース
  1回なので、**重なり＝止める**にはしない。

**走っている集合は、セッションの状態ではなく枝から引く**（`git branch -r`）。応答が無いことは
死んだことを意味しない——2026-08-25 に、2時間応答の無いセッションを死んだと判断し、確かめる経路も
落ちていたため同じ検査を書いて先に入れた。**セッションは生きていて、その直後にPRを出した**
（#772・#773 の重複）。**枝が在れば生きている。**

### 生成物が古くなるのは workflow が直す。司令塔は何もしない

`stats/balance.yaml` のような生成物は、**gitの上では衝突しないのに意味の上では古くなる**。2本目は
1本目が入る前の定義から作られているので、行が離れていれば `MERGEABLE CLEAN` のまま入り、**鮮度検査
（[`tests/support/generatedReport.ts`](../tests/support/generatedReport.ts) の
`describeReportFreshness`）が `main` で落ちる**（2026-08-28 に #1004・#1005 で実際に起きた。
#1004 が足した `pick` のぶん3項目が、#1005 の持っていた表から欠けていた）。

[`.github/workflows/regenerate-stats.yml`](../.github/workflows/regenerate-stats.yml) が
`main` への push のたびに `stats/` を作り直し、差分が出たら直接 push し直す。**マージした後に
司令塔がすることは無い。**

**残る赤が1本ある。** 直したコミットを push しても、その前のマージコミットに付いた `tests.yml` の
赤は消えない（`GITHUB_TOKEN` の push は新しい run を起こさないので、ループもしない代わりに
過去の run も塗り替えない）。**`main` の最新が緑なら直っている**ので、履歴の赤は追わなくてよい。

**手で作り直すとき**（workflow が壊れている・気候表を触るときなど）、**Windows の bash からは
`npm run stats:balance` が通らない**——npm がスクリプトを cmd.exe へ渡すので `RUN_BALANCE_STATS=1` の
前置が解釈されない。`RUN_BALANCE_STATS=1 npx vitest run
tests/diagnostics/balanceStatsReport.test.ts` を直に呼ぶ（気候表は `RUN_CLIMATE_STATS` と
`tests/diagnostics/climateStatsReport.test.ts`）。

## 3. タスク issue の型

1タスク = 1 issue。ユーザーはその URL を新しいセッションへ貼るだけで指示が済む。

題は「何をどうする」の1文。本文は次の形。

```markdown
雨で溜まる水が、`## 数えられない経路` に出ない。（現象の説明。長さは自由）

## 担当

`src/analysis/balanceTables.ts` / `tests/diagnostics/balanceStatsReport.test.ts` /
`docs/diagnostics/BalanceStats.md`

## 完了の条件

- `npm run stats:balance` の出力に `### 数えられない経路` が現れ、`water_liquid` が
  「島全体で入手経路が無いもの」から消える
- `npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` が通る

## 拠り所

`BalanceStats.md` の「この表が数えていないもの」節（暫定）
```

**節名を固定するのは、読む側が名前で引くから。** 投入されたセッションは
[`dispatch-prompt.md`](./dispatch-prompt.md) で「issue の『担当』に挙がっていないファイルは触るな」と
言われ、レビューは [`review-prompt.md`](./review-prompt.md) で「担当の範囲と完了条件はそちらに
書いてある」と言われる。**節名が揺れると、どちらも探す先を失う。**

- **必ず置く**: `## 担当`・`## 完了の条件`。
- **任意**: `## 拠り所`、ユーザーが決めたことがあるなら `## 決まっていること` と `## 司令塔の案`
  （次節）。
- **これ以外の節名は自由。** 現象の説明・調べた結果・直し方の案は好きに割ってよい。**引かれるのは
  上の4つだけ。**
- **`## 完了` と書かない**（`## 完了の条件` に揃える）。**引く側は節名で探す**ので、揺れた分は
  そのまま読み落としになる。
- **`## 触らないもの` は書かない。** `## 担当` の列挙で補集合が決まる。重なりが心配なら、**投入時の
  補足**でどのファイルのどこを他のセッションが掴んでいるかを名指しする（`dispatch-task.sh` の
  第2引数）。issue 本文へ書くと、重なりが解けた後も残って嘘になる。
- **「止まる条件」も書かない。** 既定は仮決めして進むことで、例外は確定節に反する変更が要るとき
  だけ。`【確定】` の印がその条件を既に表している。
- ブランチ名はセッションごとに自動で割り当たるので指定しない。
- **`## 完了の条件` が実装と食い違っていたら、疑うのは issue のほう。** 書いた側は全部のファイルを
  見ていない。条件に合わせて文書を直すと、**文書だけが実装から離れる**。担当の範囲だけ直し、
  食い違いは新しい issue にする。

### 実現案を書くなら、ユーザーが決めたことと分けて書く

司令塔が「どう直すか」を書くのは構わない——**セッションのほうが文脈は薄い**ので、担当の割り方や
既に決まっている形を伝えないと、同じことを調べ直させることになる。壊れるのは書くことではなく、
**出どころを混ぜること。**

`拠り所` の後に、2つの節へ割る。

```markdown
## 決まっていること

- 荷が重くて移動が遅くなる分は、**積ではなく加算**で表す（ユーザー 2026-08-28）
- 移動の所要時間は `travel_minutes`（`docs/engine/GameElementDefinition.md` 11.3 節【確定】）

## 司令塔の案

- `duration` に `plus` を足して、`{prop: travel_minutes, plus: {subject: agent, prop: travel_delay}}`
- 遅れは +10 分／+25 分の2段
```

- **`## 決まっていること` は1件ずつ出どころを添える。** ユーザーの発言・`【確定】` の節・既存の
  テストのどれか。**出どころが書けないものは、決まっていることではない。**
- **`## 司令塔の案` は覆してよい。** ただし覆すと決めたセッションは、**実装せずに報告して止まる**
  （投入の指示に書いてある。[`dispatch-prompt.md`](./dispatch-prompt.md)）。**この「止める」は暫定**
  ——進ませたほうが速いなら、運用が回ってから変える。
- **節が無い issue は、全部が「司令塔の案」**として読まれる。決まっていることがあるなら必ず書く。

混ぜると何が起きるかの実例が #1180。ユーザーが決めたのは「積ではなく加算」の1点だけだったのに、
司令塔は `plus` という綴りも `travel_delay` という名前も +10/+25 という数値も同じ声で並べ、さらに
「この点を理由に積へ戻さないこと」と逃げ道まで塞いだ。**セッションは全部を決定事項として受け取り、
yaml の文法を仮決めのまま書き換えにかかった。** `【確定】` の節に司令塔の仮決めが混ざったのと
同じ構造で、これが2度目（[`policies.md`](./policies.md)「確定の印を付ける範囲」）。

### 人間が立てた issue は、投入する前に棚卸しで task へ翻訳する

ユーザーが立てる issue は自分の言葉で書かれていて、担当も完了条件も無い。**型を覚えることは判断では
ないので、書式を人間の側へ要求しない**（[`policies.md`](./policies.md)「人間が立てた issue の
受け取り方」）。翻訳は仕組みの側が引き取る。

そのまま `task` を付けて投入すると、**PRの範囲が宣言されていない**まま差分が返ってくる。司令塔は
範囲外へ伸びたかを機械的に判定できず、全部が判断待ちに落ちる（担当が守っているのは衝突ではなく
範囲が読めること。上の節）。

- 対象は `board.sh` の `## 未整理`（`task` も `meta` も付いていない open な issue）。
- **未整理の全件をまとめて1セッションに渡す。** 1件ずつ配ると、**別々に立った issue が同じ原因で
  あることに誰も気づけない**——#1042・#1043・#1044 はどれもカードの移動アニメーションの話で、
  1件ずつ翻訳すると同じファイルを触る `task` が3本立って衝突する。
- **ブリッジ（`--bridge`）で走らせる。** クラウドのセッションは GitHub の REST が丸ごと塞がって
  いて**既存 issue の本文を書き換えられない**（新規作成は用意された道具で通る）。番号を保ったまま
  書き換えるのが棚卸しの中心なので、クラウドでは仕事にならない。
- 渡す本文は [`triage-prompt.md`](./triage-prompt.md) をそのまま写す。出口は
  **そのまま／分解／束ねる**の3つで、原文は `## 元の報告` として消さずに残させる。
- **`task` ラベルを付けるのは司令塔。** 棚卸しの側には付けさせない——順序（`blockedBy`）を張る前に
  付くと、依存のある issue が `TASK` として先に配られる。報告を読み、辺を張ってから付ける。

棚卸しは**PRを出さない仕事**なので、投入も見張りも普通の issue と同じ道具で足りる。棚卸しを追う
issue を1件立てて `meta` を付け（未整理として二重に数えないため）、`dispatch-task.sh` でその番号へ
投入する。終わればセッションは `STALLED` として届くので、報告を読んでから畳む。

### 担当外へ出てよいのは、自分が嘘にしたものを直すとき

**自分の変更がその記述・コードを事実でなくしたなら、担当外でも同じPRで直す。** 判定は「**自分の
差分がこの行を嘘にしたか**」の一点で、「ついでに気づいた」「直したほうがよさそう」は入らない
（それは今までどおり新しい issue）。入れたぶんは **PR本文の `## 担当外へ入った直し` 節に、1件ずつ
「何が嘘になったから直したか」を書く。**

開ける理由は速度。**手続きが実装の10倍を超えていた**——2026-08-28 の1日で、担当外というだけで
issue に化けた直しが4件あり（#994・#998・#1000・#993）、うち2件は2〜3行だった。2行のために
issue 1件・セッション1本・PR1本・マージ1回が要っていた。

**全面自由にはしない。** 担当が守っているのは衝突ではなく（衝突のコストはリベース1回。2節）、
**PRの範囲が読めること**。範囲が宣言されているから、司令塔は触ったファイルの一覧と
`## 担当外へ入った直し` で「範囲外へ伸びていないか」を判定でき、判断待ちへ落とさずに済む。無制限にすると1PRが膨らんで判定できないPRが増え、
**結局ユーザーの手が要る回数が増える**——速度のために開けたはずが逆を向く。

**生成物は、担当に挙がっていなくても作り直してよい**（`stats/balance.yaml` は `npm run stats:balance`、
`stats/climate.yaml` は `npm run stats:climate`）。鮮度検査があるので、作り直さなければCIが落ちる。
手で書き換えることは許さない——**作り直すのであって直すのではない。**

### 順序は本文ではなく `blockedBy` に書く

**先に片付いていないと着手できない issue があるなら、GitHub の依存（`blockedBy`）で結ぶ。** 本文に
「#123 の後」と書いても機械は読めず、[`watch-prs.sh`](../scripts/agent/watch-prs.sh) はそれを ready として配る。

```bash
gh api --method POST repos/gooyyu1/UnmappedIsland/issues/<この issue>/dependencies/blocked_by \
  -F issue_id="$(gh api repos/gooyyu1/UnmappedIsland/issues/<先に要るほう> --jq .id)"
```

渡すのは**REST の数値 ID**（`--jq .id`）で、`I_kwDO...` の node ID では通らない。

- **張るのは司令塔だが、決めるのは issue を立てた本人。** なぜその順序かを知っているのは、その問題を
  見つけた側だけ。全体を見る専任は本文から推測することになり、推測は必ず取りこぼす。
  **クラウドのセッションからは張れない**——GitHub の REST が丸ごと塞がっており、`gh` でも `curl` でも
  `{"message":"GitHub access is not enabled for this session. An org admin must connect the Claude
  GitHub App for this organization."}` が返る（2026-08-27 に3セッションが実際に踏んだ）。issue やPRの
  作成は用意された道具で通るが、**依存の API はその道具の一覧に無い。**

  そこで**セッションには `## 司令塔へ` 節に「#A は #B の後」と書かせ、司令塔が張る**（次節）。
  判断は見つけた側に残り、手だけがこちらへ来る。**このとき本文の他の場所へ書かせない**——散文に
  紛れると司令塔が読まず、`watch-prs.sh` はその issue を ready として配る。
- **迷ったら張らない。** 張り忘れ（早すぎる着手）はPRの段階で気づけて、やり直しはリベース1回で
  済む。**過剰に張ると鎖が伸びた分だけ黙って遅くなり、誤りに誰も気づかない。**
- **「同じファイルを触る」は依存ではない。** 順序に理由があるものだけを書く。理由が無いのに
  結ぶと、**嘘の順序が固定される**（衝突の扱いは2節）。
- 循環は GitHub が 422 で拒む（実測）ので、自由に張らせても静かに全停止することはない。

### 司令塔に手を動かしてほしいことは、`## 司令塔へ` の1節に集める

**PRの中では終わらず、司令塔が何かをしないと終わらないもの**は、PR本文（レビューならコメント）の
`## 司令塔へ` 節へ書かせる。無ければ節ごと省く——**`## 仮決め` と違い、「なし」とは書かせない。**
入るのは3つ。

- **立てた issue の番号。** 範囲外だと判断して立てたもの。司令塔が投入する。
- **順序。** 「#A は #B の後」。司令塔が `blockedBy` を張る（前節）。
- **仕組みそのものへの直しの依頼。** `.claude/**` の全部（ひな形・`parallel-work.md`・`policies.md`
  ほか）・`scripts/agent/**`・`CLAUDE.md`。司令塔が #732 へ積む。**セッションには直させない**——
  担当外で、司令塔と他のセッションが同時に触るうえ、**`.claude/**` はクラウドセッションからの
  書き込みが必ずユーザー承認を求められ、そこで止まる**（`policies.md` も例外ではない。
  [`policies.md`](./policies.md)「配るか、司令塔が自分で書くか」）。

**1つの節に畳むのは、行き先ごとに節を割ると、どれにも当てはまらないものが地の文へ落ちるから。**
落ちたものは誰も読まない。**「司令塔が手を動かすか」の一点で括れば、当てはまらないものは無い。**

宛先の違いは司令塔が読んで振り分ける——**振り分けは司令塔の仕事で、書く側の仕事ではない。**

#### 下ろすまで黙らない（`RELAY`）

**節があっても、司令塔が読み落とせば同じ。** PR #1240 は7件を回してきたが、拾えたのは6件だった
——マージのときに司令塔が手で読む一発勝負しか無く、落ちた1件は誰にも気づかれなかった。

そこで `CHECKED` と同じ形にする。**下ろすまで毎周出る。**

- [`merge-and-close.sh`](../scripts/agent/merge-and-close.sh) がマージのときに**PR本文と `[レビュー]`
  のコメントの両方**を見て、`## 司令塔へ` に中身があれば `司令塔へ` ラベルを付ける。**書く口が2つ
  あるので、読む口も2つ要る。**
- **「なし」と書かれた節では印を置かない。** 取り違えて書かれるたびに `RELAY` が空振りし、**見張りは
  合図が1件でも出た時点で終わる**ので、手でラベルを外すまで他の待ちに使えなくなる。規約は上の
  「無ければ節ごと省く」のままで、機械の側でも取り違えを吸収する。
- [`watch-prs.sh`](../scripts/agent/watch-prs.sh) が、そのラベルの付いたマージ済みPRを毎周
  `RELAY <番号>` として出す。
- 司令塔は中身を下ろして（issue を立てる・`blockedBy` を張る・#732 へ積む）、**ラベルを外す。**

**ラベルで持つのは、引くのが安いから。** マージ済みPRは本数が多く、本文を毎周読むと窓を切ることに
なる——切った窓から出たものは永久に出なくなり、「下ろすまで黙らない」が成り立たない。

### 束ねる関門は、ゲートの issue を1件立てる

**N 件が済むまで M 件を止めたい**とき、M 件それぞれに N 本を張らない。「〜が確定していること」だけを
書いた issue を1件立て、N 件をその `blockedBy` に、M 件をその後ろに置く。辺は N×M ではなく N+M で
済み、**後から1件足すときに張る辺は1本**になる。

数ではなく、**張り忘れたときにどちらへ倒れるか**が理由。関門が1点なら、足したものは既定で止まる側に
落ちる。個別に張る形では、足したものは既定で素通りする。

ユーザーの確定を待つゲートは、**チェックを付けるのはユーザー（#656）だが、閉じるのは司令塔**。
#656 の入力の形は変えない——チェック1つで答えられることが、あの issue の条件だから。付いたことは
見張りの `CHECKED` で届く（1節）。

### PR の型 — 仮決めと自己点検を、書いた本人が申告する

PR本文の先頭に `## 仮決め` 節を置く。**「なし」と書くのも仕事のうち**——書かせないと、仮決めが
無かったのか書き忘れたのかが区別できない。あるなら、決めた内容・代わりの案・覆すと何が変わるかを
3行以内で。

**`## 自己点検` 節も、PRの出どころにかかわらず全部が置く。** 作業セッションはサブエージェントの
指摘と、それぞれをどうしたかを書き、**「同じ誤りの兄弟」については使った検索語をそのまま書く**
（1節「PRを出す前の自己レビューは、サブエージェント」）。検索語まで書かせるのは、探し方が甘かった
のか本当に無かったのかを、レビュアーが見分けられるようにするため。
**その手順を持たない司令塔と相談役は、「手順を持たない」とだけ書く**——ここも「なし」と同じ理屈で、
書かせないと通していないのか書き忘れたのかが区別できない。**読むのはレビュアー**
（[`review-criteria.md`](review-criteria.md)）で、名乗りで振り分ける。

**司令塔は差分を読まない。** 読むのは下の表で読む相手に司令塔が挙がっている節と、PRが触った
ファイルの**一覧**だけ。差分の中身を読むのは、下の関門（機械）とレビューのセッション（人手では
ない）で、司令塔がやるのは下の表のとおりに動くことだけ。

PR本文の節は次のとおり。**必ず置くのは `## 仮決め` と `## 自己点検`**（`Closes` は issue を持つPR
だけ）で、残りは無ければ節ごと省く。

**司令塔が読む5節（`## 仮決め`・`## 担当外へ入った直し`・`## 見た目`・`## 司令塔へ`・
`## ユーザーの指示`）は、表の綴りちょうどで書く。** 司令塔は節の名前を `$` で留めて抜き出す
（1節「司令塔の文脈は、放っておくと1応答50万トークンになる」の `awk`）ので、
`## 担当外へ入った直し（3周目）` のように語を足すと**その節だけ司令塔に届かない**。周回番号や
補足は、節の中へ書く。

| 節 | 中身 | 読む相手 |
| --- | --- | --- |
| `Closes #<番号>` | 先頭に。番号だけの参照では閉じない（**issue を持たないPRには無い**） | GitHub |
| `## 仮決め` | 決めていない箇所をどう決めたか（**無いなら「なし」**） | 司令塔 |
| `## 自己点検` | この節の本文のとおり | レビュー |
| `## 担当外へ入った直し` | 自分の差分が嘘にしたので直したもの | レビュー・司令塔 |
| `## 見た目` | 画面が変わるなら画像（変わらないなら「不要」と理由） | 司令塔・ユーザー |
| `## 司令塔へ` | 司令塔が手を動かさないと終わらないもの（前節） | 司令塔 |
| `## ユーザーの指示` | 作業中にユーザー本人から届いた指示と、その反映 | 司令塔 |

**`## ユーザーの指示` が要るのは、司令塔がそれを見ていないから。** ユーザーは走っているセッションへ
直接 `send_message` を送れる。書かせないと、issue の担当や完了条件から外れた理由が本文のどこにも
無いまま、**司令塔には「範囲外へ伸びたPR」としか見えない**——差し戻すと、ユーザーの指示を取り消す
ことになる。司令塔自身が送ったものは書かせない（見ているので）。

| PRの状態 | 扱い |
| --- | --- |
| `## 仮決め` 節が無い | 受け取らない。そのセッションに書かせる |
| `needs-user-review.sh` が該当を出す | **司令塔にはマージできない。** `merge-and-close.sh` が `判断待ち` を付けて `HELD` で止める。#732 の先頭へ「あなた待ち」として1行で出す |
| 差分が画像だけ | **そのままマージする**（下の「絵は素通しに固定する」） |
| それ以外 | **レビューのセッションを1本立てる**（`bash scripts/agent/dispatch-review.sh <PR番号>`）。結果はコメントで届く |

**外のレビューは、どんな周でも1本立てる。書いた側の一次レビュー（サブエージェント）は外を
置き換えない。例外は1つだけ**——直前の周で外のレビューが `通してよい` を出しており、**その後に
入った差分がリベースのコンフリクト解決だけ**のとき。この条件では外が読んだ中身とマージする中身が
同じで、一次レビューが見るのは解き方だけになる。ここへ外をもう1本立てるのは、費用と時間に見合わない
（出どころ: ユーザーの指示・2026-08-30）。

レビューが `[レビュー] 通してよい` と書いたらマージする（気になった点だけが並んでいるときも同じ。
それは issue にする）。`[レビュー] 直しが要る` なら、**元を書いたセッションを `send_message` で
起こして直させる**——レビューのセッションは直さない。

**「仮決めあり」だけでは止める理由にならない。** 実測（2026-08-29）で、直近25本のうち `## 仮決め` に
中身のあったPRは22本、`判断待ち` が付いたのは0本だった。22/25 を止めれば**タップを1回増やすだけの
関門**になり、本当に判断が要るものが埋もれる。**止める線は機械が引く**
（[`needs-user-review.sh`](../scripts/agent/needs-user-review.sh)＝宣言文法・スキーマ・`【確定】` の
印。同じ25本のうち5本が掛かり、倍率がゲームへ入った3本すべてが入る）。

**線はパスで引くが、`.ts` は注釈しか変わっていないなら止めない。** 文法のファイルでも、実行される
行が1つも変わっていなければ yaml に書ける形は変わりようがない。止めても、ユーザーの手元に届くのは
「通してよいか」の一言だけで判断の中身が無い——2026-08-30 に `判断待ち` の10本のうち2本
（#1330・#1312）がこれで、どちらも doc コメントの書き換えだけだった。`.md`・`.json` は全体が宣言
そのものなので、文面の書き換えでも止まる。

線の引き方も、書く側が持つ。

- **素通し**: 正しい挙動が仕様や既存テストから一意に決まる不具合修正、生成物の再生成、**絵の追加**、
  `【確定】` 節の値をそのまま書く宣言。
- **判断待ち**: しきい値や配分の値を自分で選んだ、名前がそのまま仕様になる、条件の有無を選んだ、
  設計文書に無い挙動を足した。

**「リポジトリを見れば一意に決まる」ものは、仮決めに見えても判断ではない。** 渡した issue が
間違った数値や前提を書いていて、書いた側がそれを正した申告がこれにあたる（2026-08-26・PR #870 で、
issue が「見出しに付いた `【確定】` は18個」と書いたのは司令塔の数え間違いで、実際は16個だった）。
2026-08-25・PR #770 の申告3件も「試験の種類の決まりに禁じられていて選択の余地が無かった」
「穴が塞げていない（#768 へ）」「表の前提が書けていない（#769 へ）」で、**どれも司令塔が先に
受けていた**。**この見分けは、リポジトリを開いて確かめないと付かない**——だからレビューの
セッションがやる。司令塔が引き受けると、PRの本数だけ差分を読むことになる。

**見つけた不具合を、仮決めに変えない。** 担当外の不具合が自分の成果に影響したとき、**その影響を
含んだまま「入れるか止めるか」を仮決めとして出さない**——直し方が仕様から一意に決まるなら、それは
判断ではない。**自分のPRを止めて、不具合の issue を先に流させる**（司令塔へ報告し、司令塔が投入順を
決める）。実測（2026-08-25）で、収支表の再生成が担当外の解析の不具合で表を1つ落とし、それを仮決めと
して出したことがある——**ユーザーが答えるまで、直ると分かっている不具合が main に居座る**形になる。

#### 決めきれなかった問いも、この節に書かせる

`## 仮決め` に書くのは「こう決めた」だけではない。**決めたが自信が無い点・別の答えがありうると
思った点も、同じ節に並べさせる。**

**セッションは司令塔を起こせない**（起こす道具は禁止してある。下の節）ので、**問いを残す場所は
PRの本文しか無い。** ここに書かれなければ、その問いは誰の目にも触れずに消える——実測（2026-08-25）
で、#741 のセッションは「日暮れ後に手元を取り戻すのに窯まで要求してよいか」を最後の要約に書いて
終わったが、PRの `## 仮決め` に無かったため**ユーザーへ届かないまま入った。**

**双方向の会話で埋めようとしない。** セッション側から届ける手段が無い以上、聞きに行く時機は司令塔が
決めることになり、**その時機が来なかったせいで消えた**のが上の実例。既に必ず読まれる場所（`## 仮決め`）
へ書かせるほうが、確実で安い。司令塔からの `send_message` は、こちらに用があるとき——CIが赤い・
ユーザーが却下した・仮決めの根拠を確かめたい——にだけ使う。

**絵は素通しに固定する。** 見た目はPRで覆すものではない——作り直したくなったら新しい issue にする
ほうが、ユーザーの手数が少ない。

#### 見た目が変わるPRには、画面を貼らせる

**見た目の可否は文章からは判定できない。** 貼らせなければ、判断のたびにユーザーがブランチを引いて
動かすことになる。人間に残すのは判断だけ、というのは**その判断に要る材料を揃えて渡すところまで**を
含む（[`policies.md`](./policies.md)「見た目が変わるPRの示し方」）。

- `src/game/**` か `src/assets/**` を触ったPRは、本文に `## 見た目` 節が要る。中身は画像か、
  「不要」＋理由の1行。**節ごと無いPRは差し戻す**（要否を決めるのは書いた側で、必ず言わせるのが
  こちらの役目）。
- 貼り方は [`push-screenshot.sh`](../scripts/agent/push-screenshot.sh)。画像は `screenshots`
  ブランチへ置く——`main` に入れると証跡が資料に混ざって公開サイトにも出るし、PRブランチへ入れると
  マージ後に枝が消えて**画像が壊れた記録だけが残る**。
- **前後を並べるなら、URLに `?seed=` を付けさせる。** 付ければ別々の実行でも島も開始時刻も同じに
  なる。**付けずに撮った2枚の差は変更由来とは限らない**ので、並べても何も言っていない
  （`skills/run/SKILL.md`）。

鎖の途中が `判断待ち` になると**その先が止まる**。止まっている間は鎖の外を先に流す。督促はしない。

### 差分を読むのは、司令塔ではなくレビューのセッション

`bash scripts/agent/dispatch-review.sh <PR番号>` で1本立てる。指示は
[`review-prompt.md`](./review-prompt.md)、補足は無い（見どころはPRごとに変わらない）。**結果はPRの
コメントとして返る**ので、司令塔は `watch-prs.sh` の `REVIEWED <番号> <結論>` で受け取るだけでよく、
レビューのセッションを覚えておく必要が無い。

**`REVIEWED` は時刻ではなく状態で出る**（最後の `[レビュー]` コメントが最後のコミットより新しい）。
見張りを立て直しても、まだ動いていない結論はそのつど出直す——起動時刻と比べていたときは、
立て直した谷間に出た結論が誰にも届かなかった（2026-08-29 の PR #1183・#1182 で2時間）。
**黙らせるのは司令塔が動いたときだけ**で、マージするか、`直し待ち`・`判断待ち` を付けると止まる。

**同じ判定が2度続いたら、中身を読む前に投稿の事故を疑う。** 再レビューの結論が前回とバイト単位で
同じなら、それは判定ではない——レビューのセッションは原稿をファイルへ書いてから
`gh pr comment --body-file` で出すので、置き場を取り違えると**前回の残骸がそのまま投稿される**
（`CLAUDE.md`「`/tmp` は2つある」）。PR #1229 と PR #1191 で1件ずつ起きた。**疑ったら、そのPRの
head を自分で見て、前回指摘した箇所が直っているかを確かめる。**

**司令塔が読むのは、コメントの1行目と `## 司令塔へ` 節だけ**（前節）。途中の指摘は直す側が読む。

| 1行目 | 司令塔がすること |
| --- | --- |
| `[レビュー] 通してよい` | マージする。並んでいる「気になった点」は issue にする |
| `[レビュー] 直しが要る` | **元を書いたセッション**を `send_message` で起こして直させる |

- **レビューのセッションは直さない。** 直すのは元を書いた側——文脈を持っているのはそちらで、
  レビュー側が push すると、同じPRを2つのセッションが握ることになる。
- **再レビューは、前のレビューを起こさずに新しく立てる。** 直す側とは逆で、ここは使い回さない。
  直しは「指摘された行を直す」ではなく「原則として受け取って兄弟も直す」（`CLAUDE.md` 5節）なので、
  **2回目のヘッドは1回目とは別物**になる。自分の出した判定を自分で再判定すると「言ったことが
  直っているか」だけを見る方向に寄り、**直しが新しく壊したものが誰にも読まれない**——2026-08-29 の
  PR #1191 で、2回目のレビューが前回の3件を確かめたうえで前回は見ていなかった箇所の嘘を見つけた。
  読み直しの費用（PR全体をもう一度読む）は、この読み直しそのものなので削れない。
- **PRの本数だけ立つ。** 絞ると「どれを読むか」の判定が司令塔に戻ってきて、それには差分が要る。
  唯一の例外は差分が画像だけのPRで、これはファイル一覧だけで分かる（下の「絵は素通しに固定する」）。
- **タグは `review-<PR番号>`。** `task` で始めると `STALLED` の対象になり、PRを出さないレビューの
  セッションが毎周「止まっている」として出続ける。
- **レビューへ出したPRは、`watch-prs.sh` の番号指定から外す。** 緑のまま置くので、入れておくと
  `GREEN` が毎周出て見張りがその場で終わる。`REVIEWED` は番号指定と関係なく開いている全PRから
  拾うので、外してもレビューの結果は届く。
- **出し忘れは `UNREVIEWED <番号>` が拾う。** 番号から外すということは、そのPRの `GREEN`・`RED`・
  `CONFLICT` を全部消すということでもある。司令塔は普段 `0` を渡すので、**新しく出たPRはどの行にも
  現れない**——2026-08-29 に #1195・#1198 が誰にも拾われないまま残った。`UNREVIEWED` は番号指定と
  関係なく出て、`dispatch-review.sh` が `review-<番号>` のセッションを立てた時点で黙る。だから
  **司令塔がレビューへ出す順番を覚えておく必要は無い**——出していないPRは毎周そう言ってくる。

### 承認はマージ、却下はコメント

**PRの作者はすべてユーザー自身になる**——セッションがユーザーの資格情報で push するため。GitHubは
自分が作者のPRに Approve も Request changes も出させないので、**レビュー機能は使えない。**

| ユーザーがすること | 司令塔がすること |
| --- | --- |
| **承認** → そのままマージ | 何もしない |
| **却下** → **PR か #732 のどちらか、いま開いているほうにコメントを1つ** | 拾って、書いたセッションを `send_message` で起こす。直った後のCIとラベルの付け替えも司令塔 |

- **どちらに書いてもよい**ことが肝。#732 を読んでいる最中に「#760 の暗さは −5 で」と書けるほうが、
  PRを開き直すより手数が少ない。[`watch-prs.sh`](../scripts/agent/watch-prs.sh) に `--issues 732,<投入した番号>` を
  渡して、両方を1つの待ちで拾う。
- **コメントは理由まで書かれていなくてよい。** 「−5 で」だけで足りる。足りなければ司令塔が訊く。
- **ユーザーがセッションと直接話すこともある。** それは速いので止めない——ただし司令塔には見えない
  ので、`判断待ち` が付いたまま止まる。だから**コメントの見張りが要る**。

**却下されたら、書いたセッションを起こして直させる**（RED のときと同じ）。新しいセッションを立てる
のは、畳んだ後か応答が無いときだけ。直って CI が緑になったら、`## 仮決め` を読み直して `判断待ち`
を外すか付け直す。

**沈黙を「死んだ」と読まない。** 応答が無いセッションを見限って同じ仕事を自分で書く前に、
**そのブランチが push されていないかを見る。**

```bash
git ls-remote --heads origin 'claude/issue-<番号>*'
```

これは `gh` も MCP も要らず、**セッションの状態が引けない状況でも使える**——2026-08-25 に、2時間
応答の無いセッションを死んだと判断し、MCPも切れていて確かめられないまま同じ検査を書いて先に
入れた（PR #772）。**セッションは生きていて、その直後に PR #773 を出した。** 向こうのほうが良い
出来だったので、こちらを消して統合し直すことになった。**枝が在れば生きている。**

**差し戻したら `直し待ち` を付ける。** [`watch-prs.sh`](../scripts/agent/watch-prs.sh) はこのラベルの付いたPRを
報告しない。付け忘れると、**緑のまま直しを待っている間ずっと同じ行で起こされる**（2026-08-25 に
PR #771 で実際に空振りした）。直しが上がったら外して、いつもどおり振り分ける。

**ボット用のアカウントでPRを出させて本物のレビュー機能を使う案は採らない。** Approve /
Request changes が使えるようになっても、**却下時に結局コメントを書く**ので手数は減らず、増えるのは
GitHub App の管理だけになる。

### `main` の赤を直したら、開いている全PRへ取り込ませる

**`gh run rerun` では直らない。** GitHubはPRのチェックを**そのPRが作られた時点の merge ref** で
走らせるので、再実行しても `main` の修正は入らず、同じ赤がもう一度出る。
`gh pr update-branch <番号>` でPRのブランチへ `main` を取り込ませると、新しい merge ref で走り直す。

**掛けるのは、赤を直したPRをマージした直後に、開いている全PRへ一律。** 心当たりのあるものだけを
1本ずつ拾うと取り残す——2026-08-28 に `main` の赤を #928 で直したあと、#927・#930 へは掛けて
**#918 だけ漏らし、担当セッションが何もしていないのに赤のまま止まった**（気づいたのはユーザー）。

```bash
for n in $(gh pr list --state open --json number --jq '.[].number'); do gh pr update-branch "$n"; done
```

**PRの赤は、まずそのPRの変更が原因かを見る。** 上の取り残しは、`判断待ち` が付いていたせいで
「ユーザーの手元にある」と読み、CIを見ていなかったのが元。**ラベルは持ち主を表すだけで、
赤の理由ではない。**

### 走っているセッションへ仕事を足したら、PR本文への反映まで見る

**担当に完全に含まれる小さな仕事は、新しいセッションを立てずに、既に開いているセッションへ
`send_message` で渡してよい。** コメント1文の削除のために1セッションぶんの文脈を積むほうが高い。

**ただし本文は追いつかない。** 渡した仕事は `Closes` にも変更の説明にも載らないことがある——
2026-08-28 に #939（コメント1文の削除）を #914 のセッションへ渡したら、**コードは正しく入ったのに
`Closes #939` が抜け、「そのファイルは無変更」という記述が残ったまま**PRが出た。本文を書き終えた後に
仕事が増えたのだから、追いつかないほうが自然。

**PRが出たら、渡したぶんが本文に載っているかを必ず見る。** 載っていなければ本文だけを直させる
（`直し待ち` を付けて `send_message`）。司令塔が代わりに書き換えない——**次も同じ場所で漏れる。**

### PRを出したら、そのセッションの仕事は終わり

**タスクのセッションに自分のPRを見張らせない。** `send_later`・`delete_trigger`（自分を起こすための
予約と、その取り消し）と `subscribe_pr_activity` は**自動承認ができない**ので、見張らせた分がそのまま
ユーザーのタップになる。待つのはシェルで待てる司令塔の仕事
（[`watch-prs.sh`](../scripts/agent/watch-prs.sh)）。

**禁止は2箇所に置いてある。** どちらも消さないこと——2026-08-27 に、この節にしか無かったせいで
3セッションが見張りを始めた。

- [`CLAUDE.md`](../CLAUDE.md)「タスクの issue を渡されたとき」。**セッションが必ず読むのはこちら。**
  この節だけに書いても、指したファイルを読むとは限らない。
- [`dispatch-prompt.md`](./dispatch-prompt.md) の指示のひな形。投入のたびに本文へ入る。

**「マージされるまで完了ではない」と並べて書く。** 分けて書くと、責任だけが残って手段が
禁止された状態に読め、**セッションは自分で見張るほうへ倒れる**（実際に倒れた）。直しの依頼は
向こうから来る、までを1つの文にする。

司令塔は `watch-prs.sh` をバックグラウンドで起動して決着を待ち、

- **UNREVIEWED** → `dispatch-review.sh <番号>` を走らせる。マージの前に必ずここを通る。
- **GREEN かつ `判断待ち` 無し** → `merge-and-close.sh` に渡す。issue が閉じたことの確認と、
  書いたセッションを畳むところまで同じ1回で済む。
- **RED** → **そのPRを出したセッションを `send_message` で起こして直させる。** 畳んだ後・応答が
  無い場合だけ、同じ issue で新しいセッションを立てる。**起こすほうが既定**——PRの文脈を持って
  いるのはそのセッションで、新しく立てると読み直しから始まる。

  **止まった（IDLE・切断）クラウドセッションは、これで起きる**（2026-08-25 実測: 送信から応答まで
  8秒、$0.32）。コンテナは作り直され、文脈は残ったまま続く。だから**セッション側に見張らせる必要が
  無い**——クラウドには `gh` が無く、未認証のGitHub APIは60回/時なので、そもそも同じ間隔では回せない。
- **GREEN かつ `判断待ち` あり** → 触らず、#732 の「あなた待ち」へ出す。
- **STALLED** → `list_events` でそのセッションの最後を見て、**書き終わっていないなら `send_message` で
  起こし、担当の issue が閉じているなら畳む**（上の「止まったセッションを起こす引き金は `STALLED`」）。
- **CONFLICT** → **司令塔が `main` を取り込んで解消し、push する**
  （`gh pr checkout <番号> && git merge origin/main`。解消したら4つのコマンドを通してから push）。

**CONFLICT だけは差し戻さない。** RED を書いたセッションへ返すのは、直すのに要る文脈をそちらが
持っているから。コンフリクトを直すのに要るのは `main` の側の変更で、それは司令塔の手元にある。

差し戻すと、直るまで**毎周この行で起こされる**。`直し待ち` は効かない——見張りはコンフリクトを
ラベルより先に見る（「今それが誰の手元にあるか」と「誰の手元にあろうと進めない」は直交するので、
前者で後者を隠さない）。だから CONFLICT は、受け取った側がその場で消すまで鳴り続ける行として扱う。

**どちらを採るかで挙動が変わる衝突だけは、司令塔が決めない。** `直し待ち` を付けて `send_message` で
起こす。それだけで黙る——見張りは `直し待ち` のPRのコンフリクトを出さず、`FIXED` を待つ。

**見張りの引数（番号）でコンフリクトを黙らせることはできない。** 番号が掛かるのは `GREEN`・`RED` の
2つだけで、`CONFLICT` は渡した番号に関わらず毎周出る。逆に**番号を絞ってもコンフリクトは埋もれない**
——2026-08-30 まではここも絞りに入っており、司令塔が `0` を渡す既定の使い方では、`判断待ち` の
#1272・#1361 が衝突したまま一度も報告されなかった。

### 価値観の記録 — 出どころがユーザー本人でないなら、記録しない

**価値観の出どころはユーザー本人の発言だけ**（[CLAUDE.md](../CLAUDE.md)「価値観の記録」）。司令塔が
書いた issue や指令から汲み取ったものは、ユーザーの価値観ではない。**司令塔が枠組みを書き、セッションが
それを言い直し、司令塔が転記する**と、自分の考えがユーザーの名前で全セッションへ配られる
（2026-08-26 に8件がこの経路で入り、消した）。

**指示に「価値観の記録は行わない」と明記する。** `.claude/policies.md` へ書かないだけでなく、
PR本文へ「記録してほしい価値観」として書くこともしない。**唯一の例外は、ユーザー本人から直接
メッセージを受け取ったとき**——そのときだけ `## 仮決め` へ「ユーザー発言」として**原文をそのまま**
引用する。司令塔は、原文が添えられているものだけを転記し、言い換えない。

**司令塔がタスクセッションへ向けて書く文は、すべて `[司令塔]` で始める。** `create_session` の
prompt・`send_message` の本文・PRへのコメントの全部。GitHubへは**ユーザーと同じアカウントで**
書き込むので、印が無いと受け取る側から区別できない。

書かせない理由は出どころだけではない。**`policies.md` の編集は「機微なファイル」として許可を
求められ、そこで止まる**（2026-08-26 に3つのセッションが同時に `REQUIRES_ACTION` で停止した。
`bypassPermissions` は [`ccr-meta.sh`](./ccr-meta.sh) の経路では渡せない）。**並列で走る全員が
同じ1ファイルを触るので、書けたとしても衝突する。**

止まったセッションは `send_message` の `priority: now` で起きる。**割り込ませないと、仕上げに
入っているセッションには届かない**（`next` はターンの区切りまで待つ——2026-08-26 に、差し戻しが
間に合わず不具合が4本へ広がった）。

## 4. 段の分け方

探索を並列させない。**同じ発見を N 回繰り返し、出力が揃わなくなる。**

段は司令塔が数える印ではなく、**ゲートの issue として置く**（3節）。「段2が済んだ」を頭の中や
#732 の本文で持つと、それを見落とした投入が素通りする。ゲートが開いていれば、後ろは機械が止める。

1. **段0 — 未実装9件の要否判断**（ユーザー／issue #656）。骨格待ちのものは保留する。
2. **段1 — コンテンツの骨格を決める**（ユーザー＋1体）。系統が何本・各系統が何段・終盤に何が要る
   か・アーティファクトが何種類か。**個々のレシピは決めない**（仮決めでよい）。
3. **段2 — 文法追加をまとめて1本**（直列）。骨格が決まっているので、本当に要る文法だけを入れる。
4. **段3 — コンテンツの幅出し（並列の本命）＋ 宣言だけの機能**。
5. **段4 — 統合と計測**。他のタスクと同じものを別名で作っていないかを見る（既存のテストは
   これを見ていない）。`npm run stats:balance` で日数が成立するかを測る。

段1を段2より前に置くのが肝。**骨格が決まると、文法追加のうちどれが本当に要るかが決まる。**

**段の全部をあらかじめゲートにしない。** 先の段の issue はまだ書けていないので、置いても中身の無い
関門が並ぶだけになる。ゲートを立てるのは、**その後ろに置きたい issue が実際に現れたとき**。

### 司令塔がやるのは、ready を配ることだけ

`TASK` に出るものは、依存の上では**今すぐ着手してよい**。残る仕事は2つに減る。

- **資源の衝突を見る**（2節）。走っている `担当` との交わりだけ。
- **次の段のゲートを閉じるかどうかを決める。** 段を進めてよいという判断は、ここに残す。

**印から issue の文面を起こす作業は、司令塔がやらない。** `【未実装】` を数えて issue に起こすような
一度きりで読み込みの重い仕事は、別セッションへ出す——**司令塔の文脈へ入れたものの費用は「その
大きさ×残りのターン数」**（1節）で、司令塔だけが払う費用が高い。判断（どの段へ進んでよいか）は
渡さない。

### コンテンツを後回しにしない理由

`npm run stats:balance` が「1日を賄う最小労働 624分（1440分の43.4%）」と出している。残りの56.6%に
することが無ければ100〜200日は成立せず、生存コストを上げて日数を伸ばすのは
[`DesignPrinciples.md`](../docs/concept/DesignPrinciples.md) の「時間経過に任せる区間を作らない」と
衝突する。**コンテンツ不足は仕組みの未検証と同じもので、後に回すほど手戻りが大きい。**

コンテンツの幅出しは、仕組みの実装よりスウォームに向いている——触るファイルが YAML 24本に分散し、
完了条件を `stats:balance` が定義だけから計算し、系統どうしが干渉せず、量がある。

## 5. 現在地と、何を投入してよいか

**今どこまで進んでいるかは、このファイルではなく
[issue #732](https://github.com/gooyyu1/UnmappedIsland/issues/732)（司令塔）が持つ。** 直列の鎖・走って
いるもの・投入していないものとその理由・済んだ段は、すべてあちら。新しい司令塔セッションには、この
ファイルではなく **#732 のURLを貼れば足りる**。

このファイルが持つのは進め方だけで、動くのは取り決めが変わるときだけ。**状態を混ぜない**——1日に
何度も動く情報をファイルに置くと、更新のたびにコミットとPRが要り、履歴が写しで埋まる。

### 司令塔の手入れは `main` へ直接 push する

`.claude/` 配下（このファイル・[`policies.md`](./policies.md)・フック）と
[`scripts/agent/`](../scripts/agent)（見張り・待ち・シェルの検査）、`.github/extensions/`（Copilot CLI の
フック）の変更は、PRを作らずに `main` へ直接 push してよい。`main` に保護は掛かっておらず、
**PRにしてもユーザーのタップを1回増やすだけ**だから。

**CIは `.claude/` を触った push でも走る**（#840 で `tests.yml` の `paths` を外した。`.claude/**` は
`eslint .`・`prettier --check .`・`exports.test.ts` の実際の入力）。**赤くなるのは push した後**なので、
直接 push する前に手元で4つのコマンドを通しておくこと。それが面倒な変更は、PRにしてよい。

**ルートの [`CLAUDE.md`](../CLAUDE.md) も同じ扱い。** 進め方の取り決めそのもので、タスクの担当に
挙がることが無いので重ならない。

**司令塔のスクリプトの試験（`tests/scripts/mergeAndClose.test.ts` のような、`scripts/agent/` の
1本に張り付いた試験）も同じ扱い。** 分けると、スクリプトだけが先に `main` へ入って CI が赤くなる。

`src/` `docs/` `tests/` を触る変更は今までどおりPR。CIが要り、他のセッションと担当が重なりうる。

### エージェントを選ばない道具は `.claude/` に置かない

[`watch-prs.sh`](../scripts/agent/watch-prs.sh) と
[`wait-for-issues.sh`](../scripts/agent/wait-for-issues.sh) は `gh` と `jq` だけで動き、どのエージェントが
起動しても同じに振る舞うので `scripts/agent/` に置く。`.claude/` に残すのは、**Claude Code が形式を
決めているもの**——フック・`settings.json`・`launch.json`・メタMCPの入口（`ccr-meta.sh`）だけ。

`.claude/skills/` は例外で、動かさない。**Copilot CLI もこの場所を読む**ので、移すと両方から見えなくなる。

### 承認の要る未実装を、勝手に流さない

**未実装として置かれているものは、段0（要否の判断）を通ってから実装する**
（[`policies.md`](./policies.md)「未実装のものの扱い」）。設計文書に書いてあることを順に実装すると、
断らなかっただけのものが仕様になる。

判断の材料は印で付いている。`【確定】`＋段0の仕分け済みなら流してよく（#706・#707 がこれ）、
#656 に未チェックで載っているものは待つ。**仮決めして進む既定はこれと衝突しない**——仮決めが
効くのは「決まっていないから止まる」場面で、ここは**既に訊いてあって答えが来ていない**場面。

**ただし、待つことは唯一の道ではない。** 明るさの「大きいほうを採る」合成は、答えが来る前に
**問いのほうが消えた**——値の設計を作り直して加算だけで書けるようにしたため、文法が要らなくなった。
関門に当たったら、答えを待つのと並べて**要求そのものを畳めないか**を疑う
（[`policies.md`](./policies.md)「仕組みの作り方」の、正しさの不足より仕組みが増えるほうが重い、が根拠）。
