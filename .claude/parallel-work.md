# 並列作業の進め方

多数のエージェントで同時に開発を進めるための取り決め。**このファイルは進め方だけを持つ。**
確定度の印は [`docs/DocumentStyle.md`](../docs/DocumentStyle.md) 6節、確認の積み方と
「担当外は触らない」は [`CLAUDE.md`](../CLAUDE.md) が持つので、ここでは繰り返さない。

**人間向けの全体像は [`docs/ParallelAgents.md`](../docs/ParallelAgents.md)。** 誰が何をして人間はどこで
決めるのかを図で示す。**規則を書くのはこちらだけ**で、あちらは全体像だけを持つ（同じ説明を二度書かない）。

## 1. 分かれ目は「書くかどうか」

| 作業 | 走らせ方 |
| --- | --- |
| 読むだけ（調査・分類・棚卸し） | **同じセッションのサブエージェント** |
| 書く（実装・PR） | **別セッション。1タスク = 1 issue = 1ブランチ = 1PR** |

書く作業を別セッションにするのは、次の3つが順に効くため。

1. **作業ツリーが物理的に分かれる。** 同じセッションのサブエージェントは同じチェックアウトを
   共有するので、並列で書くと整形の PostToolUse フックや git の状態を互いに壊す。
2. **統合機構が既にある。** 1セッション = 1ブランチ = 1PR は今の運用そのままで、追加の仕組みが
   要らない。1セッションから複数ブランチを作ると、この運用から外れる。
3. **SessionStart フックが確実に掛かる。** `inject-policies.sh` が価値観を流し込むのはセッション
   単位。サブエージェントに同じ文脈が入る保証は無く、価値観の記録が空振りしうる。

読むだけの作業を同じセッションに置くのは、衝突が起きず、結果が1箇所へ集まり、**ユーザーの手数が
ゼロ**だから。

### 書く作業をどこへ立てるか

実行元ごとに、確実に起動する隔離先を選ぶ。

| 実行元 | 立てる先 |
| --- | --- |
| Claude | **クラウド優先**。画像の生成（ComfyUI）だけローカル |
| Copilot | **ローカルworktree**。クラウドは使わない |

Claude はローカルの枠を画像生成のために空ける。Copilot のクラウド起動は失敗する経路であり、隔離は
ローカルworktreeで確保できる。実装・ドキュメント・画面の動作確認もこの原則に従う。

セッションはエージェントが立てられるので、ユーザーの手数は「issue に答える」だけ。ローカルから
呼ぶときは `permission_mode` を渡せないため、既定のまま作る。

#### 立てる・確かめる・畳むは [`ccr-meta.sh`](./ccr-meta.sh)

**`mcp__ccr_meta__*` の登録は消した**（`~/.claude.json`）ので、入口はこれ1つ。あれは**起動時のヘッダを
掴んだまま**で、走っている最中にトークンが切れると、登録を直しても**そのセッションからは二度と
使えなかった**（2026-08-25 に2回起きた）。

```bash
bash .claude/ccr-meta.sh create_session < args.json
bash .claude/ccr-check-prompt.sh <セッションID> <送った指示のファイル>
bash .claude/ccr-meta.sh archive_session <<<'{"session_id": "cse_..."}'
```

**引数は標準入力で渡す**（argvではない）。**呼ぶたびに `~/.claude/.credentials.json` から読み直す**ので
切れない。**道具も引数も普段と同じで、23個すべてが使える**——MCPサーバもただのHTTPで、しかも
ステートレスに応じるため、`tools/call` を1発投げるだけでよい。

**指示の本文は [`dispatch-prompt.md`](./dispatch-prompt.md) を写して作る。** 手で書き起こすと落ちる
（2026-08-27 に「PRを見張らない」が3本すべてから抜けた）。

**立てた直後に [`ccr-check-prompt.sh`](./ccr-check-prompt.sh) を通す。** 指示が化けても壊れても
セッションは普通に動き出すので、**動いている様子は判断材料にならない**（2026-08-25 に、丸ごと化けた
指示で20分走らせた）。届いた本文と送ったファイルを文字列で突き合わせて、一致だけを信じる。

**RESTを逆算しない**（`/v1/code/sessions` を直に叩く道もある）。形が違ううえ
（`sources` は入れ子ではなく平ら）、**`DELETE` は畳まずに消す**——同じ意味の操作を2通り持つ理由が無い。

`RemoteTrigger` でも立てられるが、**トリガー発火の実行はセッション一覧に出ない**——ユーザーが進み
具合を見に行けないので、上を先に使う。

### 前のタスクの完了は、シェルで待つ

直列に並べたタスクは、[`wait-for-issues.sh`](../scripts/agent/wait-for-issues.sh) をバックグラウンドで起動して
待つ。完了した瞬間に1回だけ起きて次を投入できる。

```bash
bash scripts/agent/wait-for-issues.sh 662
```

**間隔を空けて浮くものは無い。** 高いのはモデルのターンであって `gh` の呼び出しではないので、
既定の5秒のまま詰めて回す。空けた分はそのまま次のタスクの着手が遅れるだけになる。

**待つのは「その issue を閉じる PR がマージされたか」。** ここが訊いているのは仕事が終わったかでは
なく、**前のタスクの変更が main に入ったか**なので、それを直接表すマージを見る。取り下げで閉じた
issue は、終わってはいるが main には何も入っていない。

なお、issue はセッションが閉じるものではない（[`CLAUDE.md`](../CLAUDE.md)「タスクの issue を渡された
とき」）。閉じさせていた頃は、**まだ main に何も入っていない時点で「完了」の合図が出ていた**
——実測で8件中6件が、PRのマージより最大21分早く閉じられていた。

### 司令塔の文脈は、放っておくと1応答50万トークンになる

**無人で回り続けることは目的なので、抑えるのは動きの量ではなく1回あたりの単価**
（[`policies.md`](./policies.md)「無人で進むことは、目的であってコストではない」）。

2026-08-26 に5時間の上限へ当たったときの実測——**960応答で読み込み531M**、1応答あたり**平均553k・
最悪923k**。出力は1応答あたり983トークンしかない。**書いた量ではなく、読み直した量で消えている。**

手は2つで、どちらも効く。

- **`~/.claude/settings.json` の `autoCompactWindow`**（10万〜100万の整数、単位はトークン）。
  1M文脈のモデルでは既定が実質100万なので、**50万を超えてから畳まれていた**。司令塔は状態を
  文脈ではなく #732 に持つので、狭めて失うものがほぼ無い。**200000 を入れてある。**

  **これ以上は下げられない。** 20万未満を入れると判定が `window < 200000` で打ち切られ、
  **自動コンパクションが丸ごと止まる**——畳まれないまま上限まで伸びるので、締めたつもりで逆を
  向く。20万は有効なまま取れる最小値ちょうど。実効の発火点は、ここから出力枠の予約2万と
  バッファ2割を引いた**14.4万トークン**。
- **Bashを1回にまとめる。** 文脈を膨らませていた首位は Bash で、**688回・15万トークン**。ただし
  1回あたりは220トークンで、**巨大な出力が数個あるのではなく小さいものが688個**だった。
  `gh pr view` と `git log` を別々に打つのをやめるだけで、回数も総量も減る。

**PRを読むときは全文を入れない。** `## 仮決め` の節と、チェックの結果と、触ったファイルの数で足りる
（`gh pr view <番号> --json body --jq .body | sed -n '/^## 仮決め/,/^## /p'`）。**司令塔の文脈へ入れた
ものの費用は「その大きさ×残りのターン数」**で、1回の読み込みでは終わらない。

### 投入する直前に、その issue が開いているかを見る

**セッションを立てる直前に `gh issue view <番号> --json state` を打つ。** 前に一覧で見たときの状態は
当てにならない——ユーザーは issue をいつでも閉じる（取り下げ・却下・別のPRが `Closes` で閉じた）。

閉じた issue へ立てると、セッションは指示どおり「仕事は無い」と判断して即終了する。ここまでは
正しいが、**PRが出ないので [`watch-prs.sh`](../scripts/agent/watch-prs.sh) には何も届かない**——PRだけを見張って
いるからで、タイムアウトまで空待ちになる。2026-08-25 に、却下されて閉じた issue へその16分後に
セッションを立て、120分の空待ちに入りかけた。

**そのため、待ちに入るときは投入した issue の番号も渡す。**

```bash
bash scripts/agent/watch-prs.sh --issues 746,751 --timeout-minutes 120
```

issue が閉じた時点で `GONE <番号>` が出る。**PRの決着と、PRが出ないまま終わったことの両方が、
1つの待ちで拾える。**

### 終わったセッションは、issue を鍵にして畳む

セッションを立てるときに `issue-<番号>` のタグを付ける。**指示のキーが issue なのだから、後片付けも
issue で引く。** 畳む条件は3つ。

- **その issue が閉じている。** 閉じるのはマージのときなので、閉じた＝入ったか取り下げられたかの
  どちらかで、いずれもそのセッションの仕事は終わっている。
- **セッションが待機中（IDLE）。** マージの瞬間にまだ何かしていることがある。
- **自分が立てたクラウドのセッション**（タグ `parallel-work` が目印）。**ユーザーが立てたものと
  ブリッジのものには触らない。** 前者は走っている作業を止めることになり、後者は
  `claude remote-control` が落ちている間に畳むと worktree がロックされたまま残る。

**「完了してから一定時間」では畳まない。** 待機中であることは「終わった」を意味しない——レビュー
待ちも、こちらからの追加指示待ちも同じ待機中で、**時間では区別が付かない**。

畳んだセッションは戻せる（unarchive）ので、猶予は置かない。

#### 待ちを終える条件は「やることが無いこと」

**投入したものの決着だけを待つと、全部が `判断待ち` で止まった瞬間に何も起こらなくなる。** 手が
空いたことも、その間にセッションが立てた issue も、誰の目にも触れない。

[`watch-prs.sh`](../scripts/agent/watch-prs.sh) は、**`task` ラベルの付いた open な issue のうち、open な
`blockedBy` が無く、open なPRが `Closes` で指しておらず、`--issues` にも無いもの**を `TASK <番号>`
として出す。出さない3つは、どれも**投入する先が無いか、既に誰かの手元にある**もの——`task` の無い
issue（確認の置き場・ユーザーの答え待ち）は仕事の単位ではなく、依存が残っているものは投入しても
着手できず、PRの出ているものは書いたセッションが持っている。

**`--issues` に渡すのは、残る「こちらが把握している `task`」の全部**——投入したものに加えて、
**意図して置いてある `task`**（仮決めの範囲に含まれるもの）も渡す。渡さないと毎周起こされる。
`task` の無い issue は判定の側で落ちるので、`TASK` を黙らせる目的では渡さなくてよい。#732 を渡すのは
コメントを拾うため（「承認はマージ、却下はコメント」節）。

拾うかどうかは受け取った側が決める。**判断の材料は、その issue を生んだPRの `## 仮決め` にある**
——そこで「この issue を立てて、直さずに出した」と申告されているなら、**その扱い自体がユーザーの
判断待ち**なので拾わない。申告に含まれていなければ、鎖の外の仕事として流してよい。

#### 畳む引き金は `GONE`

**条件が揃っても、それを見に行かなければ畳めない。** [`watch-prs.sh`](../scripts/agent/watch-prs.sh) の `GONE <番号>`
は「その issue が閉じた」——**上の1つ目の条件そのもの**なので、これを合図にする。

- **`--issues` には、投入した issue を全部渡す。** PRが出ないまま終わったものを拾う用途（`GONE` の
  もう一つの読み方）と同じ引数で、掃除の合図も来る。
- **`GONE` を受けたら、`issue-<番号>` のタグを持つセッションを畳む。** 待機中でなければ畳まず、次の
  起床で拾い直す。

**「気づいたときにまとめて畳む」をやめる理由は、遅れが仕事と無関係にばらつくこと。** 実測（2026-08-25）
では issue が閉じてから畳むまでが2分・23分・30分で、**差を作っていたのは仕事の中身ではなく「次に
別の用事で起こされた時刻」だった**。`GONE` に結び付ければ見張りの間隔（既定5秒）まで縮む。

**一定時間ごとに自分を起こして掃除する形は採らない**（`send_later`）。自動承認ができないので、掃除
1回ごとにユーザーのタップが要る——放っておいても壊れないものに、それは高すぎる。

### ユーザーの答えを拾う引き金は `CHECKED`

確認の置き場（#656）は**タップ1つで答えられる形**にしてあるので、**答えはコメントではなく本文の
チェックボックスに付く**。コメントだけを見張っていると、タップは誰にも届かない——ユーザーからは
「タップしたのに何も起きない」、司令塔からは「何も来ていない」としか見えず、**両者は区別が付かない**。
最小の入力を用意した意味が、そこで丸ごと消える。

[`watch-prs.sh`](../scripts/agent/watch-prs.sh) は、`--issues` に渡した issue の本文で**起動より後に**
チェックが付いた項目を `CHECKED <番号> <項目>` として出す。

- **`--issues` に #656 を入れておく。** 入れないと本文は見られない。
- **出るのは起動時からの増分だけ。** 起動時に付いていた `[x]` まで出すと、見張りは起きるたびに
  その場で終わり、何も見張れなくなる。**既に付いている項目の掃除は、拾った側の仕事**——`CHECKED` を
  受けたら、その周に出たものだけでなく #656 の `[x]` を全部見て片付ける。
- 片付け方は下の「束ねる関門は、ゲートの issue を1件立てる」のとおりで、該当節へ `【確定】` を付け、
  #656 の一覧から消す。

## 2. 所有権の地図

**1タスクの編集が1領域に収まること**が、並列に流せる条件。収まらないものは分けるか、直列にする。
この6分割は定義位置レビュー（`review/placement/`）の調査で実証済み。行数は `.ts` の実測。

| 領域 | 範囲 | 行 |
| --- | --- | --: |
| 1 | `src/domain` 直下 | 7,261 |
| 2 | `src/domain/generation`・`wrappers` ＋ `src/loader` | 5,655 |
| 3 | カード・レーン ＋ `src/ui` ＋ `src/art` | 4,284 |
| 4 | ウィンドウ（`src/game/ui` の `*Window`・`*Pane`） | 約 3,000 |
| 5 | `src/game` 直下 ＋ `view` ＋ `looks` | 8,320 |
| 6 | `src/analysis` ＋ `src/codex-viewer` ＋ ほか | 7,722 |

**`src/game` は層ではない。** [`docs/engine/Layers.md`](../docs/engine/Layers.md) 4節のとおり
映し・意匠・部品・組み立ての4層にまたがり、この地図では3・4・5に割れる。

### 縦のスライスは、この地図では割れない

機能追加は層をまたぐので、上の横割りには乗らない。縦を割る基準は**文法を足すかどうか**で、
判定材料は**各設計文書の概要に既に書いてある**（`DocumentStyle.md` 2節が「新設した文法は何か。
新設ゼロならそれを明記する」を要求している）。

- **文法を足す** → `GameElementDefinition.md` と `loader`・`domain` という単一の hub を通るので、
  何本流しても直列寄り。**まとめて1本にする。**
- **宣言だけで書ける** → 専用の YAML と専用の設計文書だけを触るので、**互いに衝突しない。**

### 1ファイル重なることは、直列にする理由にはしない

担当が1つ重なっても、**変える箇所が別なら並列に流す**。触らない箇所を指示で名指しすればよい
（#673 と #722 は同じ `WorldVocabulary.ts` を触るが、一方は明るさのプロパティの登録、他方は表の鍵の
置き場だった）。重なりの度合いを見ずに直列へ落とすと、鎖が伸びた分がそのまま遅れになる。

名指しに加えて、**push の直前に `main` を取り込み直して4つのコマンドを通す**ことを指示に入れる。

### 資源の衝突は、依存ではなく投入の瞬間に見る

**「順序に理由がある」と「同じファイルを触る」は別のもので、後者を依存（`blockedBy`）に書いては
いけない。** 衝突するかどうかは**今どのセッションが走っているかで変わる**ので、issue に書いた
時点の事実にならない。書けば嘘の順序を固定することになる。それに、立てた側は他に何が走るかを
原理的に知らない。

司令塔が投入の直前に見る。**判断ではなく計算になる**——タスク issue の型が `担当` の列挙を義務付け、
`CLAUDE.md` が「担当に挙がっていないファイルは触らない」と禁じているので、**宣言に拘束力がある**。
見るのは走っている issue の `担当` との**集合の交わり**だけで、本文は読まなくてよい。

- **交わりが空なら、そのまま投入する。**
- **空でなければ、そこだけ上の節のとおり中身を見る。** 重なりのコストは壊れることではなくリベース
  1回なので、**重なり＝止める**にはしない。

**走っている集合は、セッションの状態ではなく枝から引く**（`git branch -r`）。応答が無いことは
死んだことを意味しない——2026-08-25 に、2時間応答の無いセッションを死んだと判断し、確かめる経路も
落ちていたため同じ検査を書いて先に入れた。**セッションは生きていて、その直後にPRを出した**
（#772・#773 の重複）。**枝が在れば生きている。**

## 3. タスク issue の型

1タスク = 1 issue。ユーザーはその URL を新しいセッションへ貼るだけで指示が済む。

```markdown
## T-4 雨で溜まる水を「数えられない経路」として立てる

- **担当**: `src/analysis/balanceTables.ts` / `tests/diagnostics/balanceStatsReport.test.ts` /
  `docs/diagnostics/BalanceStats.md`
- **完了**: 4つのコマンド ＋ `npm run stats:balance` の出力に `### 数えられない経路` が現れ、
  `water_liquid` が「島全体で入手経路が無いもの」から消えること
- **拠り所**: `BalanceStats.md` の「この表が数えていないもの」節（暫定）
```

- **「触ってはいけないファイル」は書かない。** 担当の列挙で補集合が決まる。
- **「止まる条件」も書かない。** 既定は仮決めして進むことで、例外は確定節に反する変更が要るとき
  だけ。`【確定】` の印がその条件を既に表している。
- ブランチ名はセッションごとに自動で割り当たるので指定しない。
- **「完了」が実装と食い違っていたら、疑うのは issue のほう。** 書いた側は全部のファイルを見て
  いない。条件に合わせて文書を直すと、**文書だけが実装から離れる**。担当の範囲だけ直し、食い違いは
  新しい issue にする。

### 順序は本文ではなく `blockedBy` に書く

**先に片付いていないと着手できない issue があるなら、GitHub の依存（`blockedBy`）で結ぶ。** 本文に
「#123 の後」と書いても機械は読めず、[`watch-prs.sh`](../scripts/agent/watch-prs.sh) はそれを ready として配る。

```bash
gh api --method POST repos/gooyyu1/UnmappedIsland/issues/<この issue>/dependencies/blocked_by \
  -F issue_id="$(gh api repos/gooyyu1/UnmappedIsland/issues/<先に要るほう> --jq .id)"
```

渡すのは**REST の数値 ID**（`--jq .id`）で、`I_kwDO...` の node ID では通らない。

- **張るのは issue を立てた本人。** なぜその順序かを知っているのは、その問題を見つけた側だけ。
  全体を見る専任は本文から推測することになり、推測は必ず取りこぼす。
- **迷ったら張らない。** 張り忘れ（早すぎる着手）はPRの段階で気づけて、やり直しはリベース1回で
  済む。**過剰に張ると鎖が伸びた分だけ黙って遅くなり、誤りに誰も気づかない。**
- **「同じファイルを触る」は依存ではない。** 順序に理由があるものだけを書く。理由が無いのに
  結ぶと、**嘘の順序が固定される**（衝突の扱いは2節）。
- 循環は GitHub が 422 で拒む（実測）ので、自由に張らせても静かに全停止することはない。

### 束ねる関門は、ゲートの issue を1件立てる

**N 件が済むまで M 件を止めたい**とき、M 件それぞれに N 本を張らない。「〜が確定していること」だけを
書いた issue を1件立て、N 件をその `blockedBy` に、M 件をその後ろに置く。辺は N×M ではなく N+M で
済み、**後から1件足すときに張る辺は1本**になる。

数ではなく、**張り忘れたときにどちらへ倒れるか**が理由。関門が1点なら、足したものは既定で止まる側に
落ちる。個別に張る形では、足したものは既定で素通りする。

ユーザーの確定を待つゲートは、**チェックを付けるのはユーザー（#656）だが、閉じるのは司令塔**。
#656 の入力の形は変えない——チェック1つで答えられることが、あの issue の条件だから。付いたことは
見張りの `CHECKED` で届く（1節）。

### PR の型 — 仮決めの有無を、書いた本人が申告する

PR本文の先頭に `## 仮決め` 節を置く。**「なし」と書くのも仕事のうち**——書かせないと、仮決めが
無かったのか書き忘れたのかが区別できない。あるなら、決めた内容・代わりの案・覆すと何が変わるかを
3行以内で。

**司令塔はこの節だけを見て振り分ける。差分を読み直して判定しない。** 仮決めをしたのは書いた側で、
判定の材料もそちらにしか無い。司令塔がやるのは、申告を `判断待ち` ラベルへ写すことと、下の表の
とおりに動くことだけ。

| `## 仮決め` の中身 | 扱い |
| --- | --- |
| 「なし」＋ CIが緑 | **司令塔がマージする**（`gh pr merge <番号> --merge --delete-branch`）。ユーザーは通らない |
| 仮決めあり | **マージしない。** `判断待ち` を付け、#732 の先頭へ「あなた待ち」として1行で出す |
| 節が無い | 受け取らない。そのセッションに書かせる |

線の引き方も、書く側が持つ。

- **素通し**: 正しい挙動が仕様や既存テストから一意に決まる不具合修正、生成物の再生成、**絵の追加**、
  `【確定】` 節の値をそのまま書く宣言。
- **判断待ち**: しきい値や配分の値を自分で選んだ、名前がそのまま仕様になる、条件の有無を選んだ、
  設計文書に無い挙動を足した。

**申告に仮決めがあっても、中身が全部「既に司令塔が受けた後続 issue へ回したもの」なら素通しする。**
表の2行目は「ユーザーの判断が動くなら止める」という意味で、**申告の有無そのものではない。** 判断が
1つも動かないPRを判断待ちへ置くと、**タップを1回増やすだけの関門**になり、本当に判断が要るものが
埋もれる。素通しにした理由はPRへコメントで残し、#732 にも1行で出す——**関門を外すのであって、
見えなくするのではない。**

**issue の側の事実誤りの訂正も、判断は動かない。** 渡した issue が間違った数値や前提を書いていて、
書いた側がそれを正した申告は、**リポジトリを見れば答えが一意に決まる**ので素通しする。司令塔は
その数を自分で数え直してから入れる。実測（2026-08-26・PR #870）で、issue が「見出しに付いた
`【確定】` は18個」と書いたのは司令塔の数え間違いで、実際は16個だった——訂正は検査が裏を取っている。

実測（2026-08-25・PR #770）で、申告された3件は「試験の種類の決まりに禁じられていて選択の余地が
無かった」「穴が塞げていない（#768 へ）」「表の前提が書けていない（#769 へ）」で、**どれも司令塔が
先に受けていた**。制約だと言われた1件は、`testKinds.test.ts` を開いて実在を確かめてから素通しした。

**見つけた不具合を、仮決めに変えない。** 担当外の不具合が自分の成果に影響したとき、**その影響を
含んだまま「入れるか止めるか」を仮決めとして出さない**——直し方が仕様から一意に決まるなら、それは
判断ではない。**自分のPRを止めて、不具合の issue を先に流させる**（司令塔へ報告し、司令塔が投入順を
決める）。実測（2026-08-25）で、収支表の再生成が担当外の解析の不具合で表を1つ落とし、それを仮決めと
して出したことがある——**ユーザーが答えるまで、直ると分かっている不具合が main に居座る**形になる。

#### 決めきれなかった問いも、この節に書かせる

`## 仮決め` に書くのは「こう決めた」だけではない。**決めたが自信が無い点・別の答えがありうると
思った点も、同じ節に並べさせる。**

**セッションは司令塔を起こせない**（起こす道具は禁止してある。下の節）ので、**問いを残す場所は
PRの本文しか無い。** ここに書かれなければ、その問いは誰の目にも触れずに消える——実測（2026-08-25）
で、#741 のセッションは「日暮れ後に手元を取り戻すのに窯まで要求してよいか」を最後の要約に書いて
終わったが、PRの `## 仮決め` に無かったため**ユーザーへ届かないまま入った。**

**双方向の会話で埋めようとしない。** セッション側から届ける手段が無い以上、聞きに行く時機は司令塔が
決めることになり、**その時機が来なかったせいで消えた**のが上の実例。既に必ず読まれる場所（`## 仮決め`）
へ書かせるほうが、確実で安い。司令塔からの `send_message` は、こちらに用があるとき——CIが赤い・
ユーザーが却下した・仮決めの根拠を確かめたい——にだけ使う。

**絵は素通しに固定する。** 見た目はPRで覆すものではない——作り直したくなったら新しい issue にする
ほうが、ユーザーの手数が少ない。

鎖の途中が `判断待ち` になると**その先が止まる**。止まっている間は鎖の外を先に流す。督促はしない。

### 承認はマージ、却下はコメント

**PRの作者はすべてユーザー自身になる**——セッションがユーザーの資格情報で push するため。GitHubは
自分が作者のPRに Approve も Request changes も出させないので、**レビュー機能は使えない。**

| ユーザーがすること | 司令塔がすること |
| --- | --- |
| **承認** → そのままマージ | 何もしない |
| **却下** → **PR か #732 のどちらか、いま開いているほうにコメントを1つ** | 拾って、書いたセッションを `send_message` で起こす。直った後のCIとラベルの付け替えも司令塔 |

- **どちらに書いてもよい**ことが肝。#732 を読んでいる最中に「#760 の暗さは −5 で」と書けるほうが、
  PRを開き直すより手数が少ない。[`watch-prs.sh`](../scripts/agent/watch-prs.sh) に `--issues 732,<投入した番号>` を
  渡して、両方を1つの待ちで拾う。
- **コメントは理由まで書かれていなくてよい。** 「−5 で」だけで足りる。足りなければ司令塔が訊く。
- **ユーザーがセッションと直接話すこともある。** それは速いので止めない——ただし司令塔には見えない
  ので、`判断待ち` が付いたまま止まる。だから**コメントの見張りが要る**。

**却下されたら、書いたセッションを起こして直させる**（RED のときと同じ）。新しいセッションを立てる
のは、畳んだ後か応答が無いときだけ。直って CI が緑になったら、`## 仮決め` を読み直して `判断待ち`
を外すか付け直す。

**沈黙を「死んだ」と読まない。** 応答が無いセッションを見限って同じ仕事を自分で書く前に、
**そのブランチが push されていないかを見る。**

```bash
git ls-remote --heads origin 'claude/issue-<番号>*'
```

これは `gh` も MCP も要らず、**セッションの状態が引けない状況でも使える**——2026-08-25 に、2時間
応答の無いセッションを死んだと判断し、MCPも切れていて確かめられないまま同じ検査を書いて先に
入れた（PR #772）。**セッションは生きていて、その直後に PR #773 を出した。** 向こうのほうが良い
出来だったので、こちらを消して統合し直すことになった。**枝が在れば生きている。**

**差し戻したら `直し待ち` を付ける。** [`watch-prs.sh`](../scripts/agent/watch-prs.sh) はこのラベルの付いたPRを
報告しない。付け忘れると、**緑のまま直しを待っている間ずっと同じ行で起こされる**（2026-08-25 に
PR #771 で実際に空振りした）。直しが上がったら外して、いつもどおり振り分ける。

**ボット用のアカウントでPRを出させて本物のレビュー機能を使う案は採らない。** Approve /
Request changes が使えるようになっても、**却下時に結局コメントを書く**ので手数は減らず、増えるのは
GitHub App の管理だけになる。

### PRを出したら、そのセッションの仕事は終わり

**タスクのセッションに自分のPRを見張らせない。** `send_later`・`delete_trigger`（自分を起こすための
予約と、その取り消し）と `subscribe_pr_activity` は**自動承認ができない**ので、見張らせた分がそのまま
ユーザーのタップになる。待つのはシェルで待てる司令塔の仕事
（[`watch-prs.sh`](../scripts/agent/watch-prs.sh)）。

**禁止は2箇所に置いてある。** どちらも消さないこと——2026-08-27 に、この節にしか無かったせいで
3セッションが見張りを始めた。

- [`CLAUDE.md`](../CLAUDE.md)「タスクの issue を渡されたとき」。**セッションが必ず読むのはこちら。**
  この節だけに書いても、指したファイルを読むとは限らない。
- [`dispatch-prompt.md`](./dispatch-prompt.md) の指示のひな形。投入のたびに本文へ入る。

**「マージされるまで完了ではない」と並べて書く。** 分けて書くと、責任だけが残って手段が
禁止された状態に読め、**セッションは自分で見張るほうへ倒れる**（実際に倒れた）。直しの依頼は
向こうから来る、までを1つの文にする。

司令塔は `watch-prs.sh` をバックグラウンドで起動して決着を待ち、

- **GREEN かつ `判断待ち` 無し** → マージする。
- **RED** → **そのPRを出したセッションを `send_message` で起こして直させる。** 畳んだ後・応答が
  無い場合だけ、同じ issue で新しいセッションを立てる。**起こすほうが既定**——PRの文脈を持って
  いるのはそのセッションで、新しく立てると読み直しから始まる。

  **止まった（IDLE・切断）クラウドセッションは、これで起きる**（2026-08-25 実測: 送信から応答まで
  8秒、$0.32）。コンテナは作り直され、文脈は残ったまま続く。だから**セッション側に見張らせる必要が
  無い**——クラウドには `gh` が無く、未認証のGitHub APIは60回/時なので、そもそも同じ間隔では回せない。
- **GREEN かつ `判断待ち` あり** → 触らず、#732 の「あなた待ち」へ出す。
- **CONFLICT** → **司令塔が `main` を取り込んで解消し、push する**
  （`gh pr checkout <番号> && git merge origin/main`。解消したら4つのコマンドを通してから push）。

**CONFLICT だけは差し戻さない。** RED を書いたセッションへ返すのは、直すのに要る文脈をそちらが
持っているから。コンフリクトを直すのに要るのは `main` の側の変更で、それは司令塔の手元にある。

差し戻すと、直るまで**毎周この行で起こされる**。`直し待ち` は効かない——見張りはコンフリクトを
ラベルより先に見る（「今それが誰の手元にあるか」と「誰の手元にあろうと進めない」は直交するので、
前者で後者を隠さない）。だから CONFLICT は、受け取った側がその場で消すまで鳴り続ける行として扱う。

**どちらを採るかで挙動が変わる衝突だけは、司令塔が決めない。** `直し待ち` を付けて `send_message` で
起こし、直るまではそのPRを見張りの引数から外す（残りのPRの番号を並べて回す。番号を渡すと
GREEN・RED・CONFLICT がその範囲に絞られる）。

### 価値観の記録 — 出どころがユーザー本人でないなら、記録しない

**価値観の出どころはユーザー本人の発言だけ**（[CLAUDE.md](../CLAUDE.md)「価値観の記録」）。司令塔が
書いた issue や指令から汲み取ったものは、ユーザーの価値観ではない。**司令塔が枠組みを書き、セッションが
それを言い直し、司令塔が転記する**と、自分の考えがユーザーの名前で全セッションへ配られる
（2026-08-26 に8件がこの経路で入り、消した）。

**指示に「価値観の記録は行わない」と明記する。** `.claude/policies.md` へ書かないだけでなく、
PR本文へ「記録してほしい価値観」として書くこともしない。**唯一の例外は、ユーザー本人から直接
メッセージを受け取ったとき**——そのときだけ `## 仮決め` へ「ユーザー発言」として**原文をそのまま**
引用する。司令塔は、原文が添えられているものだけを転記し、言い換えない。

**司令塔がタスクセッションへ向けて書く文は、すべて `[司令塔]` で始める。** `create_session` の
prompt・`send_message` の本文・PRへのコメントの全部。GitHubへは**ユーザーと同じアカウントで**
書き込むので、印が無いと受け取る側から区別できない。

書かせない理由は出どころだけではない。**`policies.md` の編集は「機微なファイル」として許可を
求められ、そこで止まる**（2026-08-26 に3つのセッションが同時に `REQUIRES_ACTION` で停止した。
`bypassPermissions` は [`ccr-meta.sh`](./ccr-meta.sh) の経路では渡せない）。**並列で走る全員が
同じ1ファイルを触るので、書けたとしても衝突する。**

止まったセッションは `send_message` の `priority: now` で起きる。**割り込ませないと、仕上げに
入っているセッションには届かない**（`next` はターンの区切りまで待つ——2026-08-26 に、差し戻しが
間に合わず不具合が4本へ広がった）。

## 4. 段の分け方

探索を並列させない。**同じ発見を N 回繰り返し、出力が揃わなくなる。**

段は司令塔が数える印ではなく、**ゲートの issue として置く**（3節）。「段2が済んだ」を頭の中や
#732 の本文で持つと、それを見落とした投入が素通りする。ゲートが開いていれば、後ろは機械が止める。

1. **段0 — 未実装9件の要否判断**（ユーザー／issue #656）。骨格待ちのものは保留する。
2. **段1 — コンテンツの骨格を決める**（ユーザー＋1体）。系統が何本・各系統が何段・終盤に何が要る
   か・アーティファクトが何種類か。**個々のレシピは決めない**（仮決めでよい）。
3. **段2 — 文法追加をまとめて1本**（直列）。骨格が決まっているので、本当に要る文法だけを入れる。
4. **段3 — コンテンツの幅出し（並列の本命）＋ 宣言だけの機能**。
5. **段4 — 統合と計測**。他のタスクと同じものを別名で作っていないかを見る（既存のテストは
   これを見ていない）。`npm run stats:balance` で日数が成立するかを測る。

段1を段2より前に置くのが肝。**骨格が決まると、文法追加のうちどれが本当に要るかが決まる。**

**段の全部をあらかじめゲートにしない。** 先の段の issue はまだ書けていないので、置いても中身の無い
関門が並ぶだけになる。ゲートを立てるのは、**その後ろに置きたい issue が実際に現れたとき**。

### 司令塔がやるのは、ready を配ることだけ

`TASK` に出るものは、依存の上では**今すぐ着手してよい**。残る仕事は2つに減る。

- **資源の衝突を見る**（2節）。走っている `担当` との交わりだけ。
- **次の段のゲートを閉じるかどうかを決める。** 段を進めてよいという判断は、ここに残す。

**印から issue の文面を起こす作業は、司令塔がやらない。** `【未実装】` を数えて issue に起こすような
一度きりで読み込みの重い仕事は、別セッションへ出す——**司令塔の文脈へ入れたものの費用は「その
大きさ×残りのターン数」**（1節）で、司令塔だけが払う費用が高い。判断（どの段へ進んでよいか）は
渡さない。

### コンテンツを後回しにしない理由

`npm run stats:balance` が「1日を賄う最小労働 624分（1440分の43.4%）」と出している。残りの56.6%に
することが無ければ100〜200日は成立せず、生存コストを上げて日数を伸ばすのは
[`DesignPrinciples.md`](../docs/concept/DesignPrinciples.md) の「時間経過に任せる区間を作らない」と
衝突する。**コンテンツ不足は仕組みの未検証と同じもので、後に回すほど手戻りが大きい。**

コンテンツの幅出しは、仕組みの実装よりスウォームに向いている——触るファイルが YAML 24本に分散し、
完了条件を `stats:balance` が定義だけから計算し、系統どうしが干渉せず、量がある。

## 5. 現在地と、何を投入してよいか

**今どこまで進んでいるかは、このファイルではなく
[issue #732](https://github.com/gooyyu1/UnmappedIsland/issues/732)（司令塔）が持つ。** 直列の鎖・走って
いるもの・投入していないものとその理由・済んだ段は、すべてあちら。新しい司令塔セッションには、この
ファイルではなく **#732 のURLを貼れば足りる**。

このファイルが持つのは進め方だけで、動くのは取り決めが変わるときだけ。**状態を混ぜない**——1日に
何度も動く情報をファイルに置くと、更新のたびにコミットとPRが要り、履歴が写しで埋まる。

### 司令塔の手入れは `main` へ直接 push する

`.claude/` 配下（このファイル・[`policies.md`](./policies.md)・フック）と
[`scripts/agent/`](../scripts/agent)（見張り・待ち・シェルの検査）、`.github/extensions/`（Copilot CLI の
フック）の変更は、PRを作らずに `main` へ直接 push してよい。`main` に保護は掛かっておらず、
**PRにしてもユーザーのタップを1回増やすだけ**だから。

**CIは `.claude/` を触った push でも走る**（#840 で `tests.yml` の `paths` を外した。`.claude/**` は
`eslint .`・`prettier --check .`・`exports.test.ts` の実際の入力）。**赤くなるのは push した後**なので、
直接 push する前に手元で4つのコマンドを通しておくこと。それが面倒な変更は、PRにしてよい。

`src/` `docs/` `tests/` を触る変更は今までどおりPR。CIが要り、他のセッションと担当が重なりうる。

### エージェントを選ばない道具は `.claude/` に置かない

[`watch-prs.sh`](../scripts/agent/watch-prs.sh) と
[`wait-for-issues.sh`](../scripts/agent/wait-for-issues.sh) は `gh` と `jq` だけで動き、どのエージェントが
起動しても同じに振る舞うので `scripts/agent/` に置く。`.claude/` に残すのは、**Claude Code が形式を
決めているもの**——フック・`settings.json`・`launch.json`・メタMCPの入口（`ccr-meta.sh`）だけ。

`.claude/skills/` は例外で、動かさない。**Copilot CLI もこの場所を読む**ので、移すと両方から見えなくなる。

### 承認の要る未実装を、勝手に流さない

**未実装として置かれているものは、段0（要否の判断）を通ってから実装する**
（[`policies.md`](./policies.md)「未実装のものの扱い」）。設計文書に書いてあることを順に実装すると、
断らなかっただけのものが仕様になる。

判断の材料は印で付いている。`【確定】`＋段0の仕分け済みなら流してよく（#706・#707 がこれ）、
#656 に未チェックで載っているものは待つ。**仮決めして進む既定はこれと衝突しない**——仮決めが
効くのは「決まっていないから止まる」場面で、ここは**既に訊いてあって答えが来ていない**場面。

**ただし、待つことは唯一の道ではない。** 明るさの「大きいほうを採る」合成は、答えが来る前に
**問いのほうが消えた**——値の設計を作り直して加算だけで書けるようにしたため、文法が要らなくなった。
関門に当たったら、答えを待つのと並べて**要求そのものを畳めないか**を疑う
（[`policies.md`](./policies.md)「仕組みの作り方」の、正しさの不足より仕組みが増えるほうが重い、が根拠）。
