# 並列作業の進め方

多数のエージェントで同時に開発を進めるための取り決め。**このファイルは進め方だけを持つ。**
確定度の印は [`docs/DocumentStyle.md`](../docs/DocumentStyle.md) 6節、確認の積み方と
「担当外は触らない」は [`CLAUDE.md`](../CLAUDE.md) が持つので、ここでは繰り返さない。

## 1. 分かれ目は「書くかどうか」

| 作業 | 走らせ方 |
| --- | --- |
| 読むだけ（調査・分類・棚卸し） | **同じセッションのサブエージェント** |
| 書く（実装・PR） | **別セッション。1タスク = 1 issue = 1ブランチ = 1PR** |

書く作業を別セッションにするのは、次の3つが順に効くため。

1. **作業ツリーが物理的に分かれる。** 同じセッションのサブエージェントは同じチェックアウトを
   共有するので、並列で書くと整形の PostToolUse フックや git の状態を互いに壊す。
2. **統合機構が既にある。** 1セッション = 1ブランチ = 1PR は今の運用そのままで、追加の仕組みが
   要らない。1セッションから複数ブランチを作ると、この運用から外れる。
3. **SessionStart フックが確実に掛かる。** `inject-policies.sh` が価値観を流し込むのはセッション
   単位。サブエージェントに同じ文脈が入る保証は無く、価値観の記録が空振りしうる。

読むだけの作業を同じセッションに置くのは、衝突が起きず、結果が1箇所へ集まり、**ユーザーの手数が
ゼロ**だから。

### 書く作業をどこへ立てるか — ローカルは画像生成のために空けておく

別セッションはローカル（このPC）にもクラウドにも立てられる。**既定はクラウド。** ローカルへ
立てるのは、このPCにしか無いものを使う作業だけ。

| 作業 | 立てる先 |
| --- | --- |
| 画像の生成（ComfyUI） | **ローカル** |
| それ以外（実装・ドキュメント・調査結果の反映・**画面の動作確認**） | **クラウド** |

**画面の確認はクラウドでできる。** [`run` skill](./skills/run/SKILL.md) はヘッドレスブラウザを
そのまま使えるので、UIの変更もクラウドへ投げる（ローカルでしか動かないのは、この skill の
Windows 向けの読み替えのほうであって、確認そのものではない）。

理由は、**ローカルで同時に走らせられる数が、画像生成の重さで決まる**こと。ComfyUIはこのPCの
GPUを占有するので、ローカルの枠を実装で埋めると、画像を1枚作るのに実装の終わりを待つことに
なる。クラウドは枠がPCの資源と無関係に増える。

クラウドへ立てるときは `source_url` を渡さないとリポジトリの無い箱で起動する、`gh` が無い、
といった差があるので、指示の書き方はローカルのメモ（`ccr-session-environments`）に従う。

セッションはエージェントが立てられる（`mcp__ccr_meta__create_session`）ので、ユーザーの手数は
「issue に答える」だけ。**ただしローカルから呼ぶときは `permission_mode` を渡せない**（CCRの親
セッションが要る）ので、既定のまま作る。

### 前のタスクの完了は、シェルで待つ

直列に並べたタスクは、[`wait-for-issues.sh`](./wait-for-issues.sh) をバックグラウンドで起動して
待つ。完了した瞬間に1回だけ起きて次を投入できる。

```bash
bash .claude/wait-for-issues.sh 662
```

**間隔を空けて浮くものは無い。** 高いのはモデルのターンであって `gh` の呼び出しではないので、
既定の5秒のまま詰めて回す。空けた分はそのまま次のタスクの着手が遅れるだけになる。

**待つのは「その issue を閉じる PR がマージされたか」。** ここが訊いているのは仕事が終わったかでは
なく、**前のタスクの変更が main に入ったか**なので、それを直接表すマージを見る。取り下げで閉じた
issue は、終わってはいるが main には何も入っていない。

なお、issue はセッションが閉じるものではない（[`CLAUDE.md`](../CLAUDE.md)「タスクの issue を渡された
とき」）。閉じさせていた頃は、**まだ main に何も入っていない時点で「完了」の合図が出ていた**
——実測で8件中6件が、PRのマージより最大21分早く閉じられていた。

### 終わったセッションは、issue を鍵にして畳む

セッションを立てるときに `issue-<番号>` のタグを付ける。**指示のキーが issue なのだから、後片付けも
issue で引く。** 畳む条件は3つ。

- **その issue が閉じている。** 閉じるのはマージのときなので、閉じた＝入ったか取り下げられたかの
  どちらかで、いずれもそのセッションの仕事は終わっている。
- **セッションが待機中（IDLE）。** マージの瞬間にまだ何かしていることがある。
- **自分が立てたクラウドのセッション**（タグ `parallel-work` が目印）。**ユーザーが立てたものと
  ブリッジのものには触らない。** 前者は走っている作業を止めることになり、後者は
  `claude remote-control` が落ちている間に畳むと worktree がロックされたまま残る。

**「完了してから一定時間」では畳まない。** 待機中であることは「終わった」を意味しない——レビュー
待ちも、こちらからの追加指示待ちも同じ待機中で、**時間では区別が付かない**。

畳んだセッションは戻せる（unarchive）ので、猶予は置かない。

## 2. 所有権の地図

**1タスクの編集が1領域に収まること**が、並列に流せる条件。収まらないものは分けるか、直列にする。
この6分割は定義位置レビュー（`review/placement/`）の調査で実証済み。行数は `.ts` の実測。

| 領域 | 範囲 | 行 |
| --- | --- | --: |
| 1 | `src/domain` 直下 | 7,261 |
| 2 | `src/domain/generation`・`wrappers` ＋ `src/loader` | 5,655 |
| 3 | カード・レーン ＋ `src/ui` ＋ `src/art` | 4,284 |
| 4 | ウィンドウ（`src/game/ui` の `*Window`・`*Pane`） | 約 3,000 |
| 5 | `src/game` 直下 ＋ `view` ＋ `looks` | 8,320 |
| 6 | `src/analysis` ＋ `src/codex-viewer` ＋ ほか | 7,722 |

**`src/game` は層ではない。** [`docs/engine/Layers.md`](../docs/engine/Layers.md) 4節のとおり
映し・意匠・部品・組み立ての4層にまたがり、この地図では3・4・5に割れる。

### 縦のスライスは、この地図では割れない

機能追加は層をまたぐので、上の横割りには乗らない。縦を割る基準は**文法を足すかどうか**で、
判定材料は**各設計文書の概要に既に書いてある**（`DocumentStyle.md` 2節が「新設した文法は何か。
新設ゼロならそれを明記する」を要求している）。

- **文法を足す** → `GameElementDefinition.md` と `loader`・`domain` という単一の hub を通るので、
  何本流しても直列寄り。**まとめて1本にする。**
- **宣言だけで書ける** → 専用の YAML と専用の設計文書だけを触るので、**互いに衝突しない。**

### 1ファイル重なることは、直列にする理由にはしない

担当が1つ重なっても、**変える箇所が別なら並列に流す**。触らない箇所を指示で名指しすればよい
（#673 と #722 は同じ `WorldVocabulary.ts` を触るが、一方は `sunlight` の登録、他方は表の鍵の置き場
だった）。重なりの度合いを見ずに直列へ落とすと、鎖が伸びた分がそのまま遅れになる。

名指しに加えて、**push の直前に `main` を取り込み直して4つのコマンドを通す**ことを指示に入れる。

## 3. タスク issue の型

1タスク = 1 issue。ユーザーはその URL を新しいセッションへ貼るだけで指示が済む。

```markdown
## T-4 雨で溜まる水を「数えられない経路」として立てる

- **担当**: `src/analysis/balanceTables.ts` / `tests/diagnostics/balanceStatsReport.test.ts` /
  `docs/diagnostics/BalanceStats.md`
- **完了**: 4つのコマンド ＋ `npm run stats:balance` の出力に `### 数えられない経路` が現れ、
  `water_liquid` が「島全体で入手経路が無いもの」から消えること
- **拠り所**: `BalanceStats.md` の「この表が数えていないもの」節（暫定）
```

- **「触ってはいけないファイル」は書かない。** 担当の列挙で補集合が決まる。
- **「止まる条件」も書かない。** 既定は仮決めして進むことで、例外は確定節に反する変更が要るとき
  だけ。`【確定】` の印がその条件を既に表している。
- ブランチ名はセッションごとに自動で割り当たるので指定しない。

### PR の型 — 仮決めの有無を、書いた本人が申告する

PR本文の先頭に `## 仮決め` 節を置く。**「なし」と書くのも仕事のうち**——書かせないと、仮決めが
無かったのか書き忘れたのかが区別できない。あるなら、決めた内容・代わりの案・覆すと何が変わるかを
3行以内で。

**司令塔はこの節だけを見て振り分ける。差分を読み直して判定しない。** 仮決めをしたのは書いた側で、
判定の材料もそちらにしか無い。司令塔がやるのは、申告を `判断待ち` ラベルへ写すことと、下の表の
とおりに動くことだけ。

| `## 仮決め` の中身 | 扱い |
| --- | --- |
| 「なし」＋ CIが緑 | **司令塔がマージする**（`gh pr merge <番号> --merge --delete-branch`）。ユーザーは通らない |
| 仮決めあり | **マージしない。** `判断待ち` を付け、#732 の先頭へ「あなた待ち」として1行で出す |
| 節が無い | 受け取らない。そのセッションに書かせる |

線の引き方も、書く側が持つ。

- **素通し**: 正しい挙動が仕様や既存テストから一意に決まる不具合修正、生成物の再生成、**絵の追加**、
  `【確定】` 節の値をそのまま書く宣言。
- **判断待ち**: しきい値や配分の値を自分で選んだ、名前がそのまま仕様になる、条件の有無を選んだ、
  設計文書に無い挙動を足した。

**絵は素通しに固定する。** 見た目はPRで覆すものではない——作り直したくなったら新しい issue にする
ほうが、ユーザーの手数が少ない。

鎖の途中が `判断待ち` になると**その先が止まる**。止まっている間は鎖の外を先に流す。督促はしない。

### PRを出したら、そのセッションの仕事は終わり

**タスクのセッションに自分のPRを見張らせない。** 指示には「PRを作ったら報告して終わり。CIの結果も
レビューも見張らない」と明記し、次を**使わせない**。

- `send_later` と `delete_trigger`（自分を起こすための予約と、その取り消し）
- `subscribe_pr_activity`

この2つは**自動承認ができない**ので、見張らせた分がそのままユーザーのタップになる。待つのは
シェルで待てる司令塔の仕事（[`watch-prs.sh`](./watch-prs.sh)）。

司令塔は `watch-prs.sh` をバックグラウンドで起動して決着を待ち、

- **GREEN かつ `判断待ち` 無し** → マージする。
- **RED** → **そのPRを出したセッションを `send_message` で起こして直させる。** 畳んだ後・応答が
  無い場合だけ、同じ issue で新しいセッションを立てる。**起こすほうが既定**——PRの文脈を持って
  いるのはそのセッションで、新しく立てると読み直しから始まる。

  **止まった（IDLE・切断）クラウドセッションは、これで起きる**（2026-08-25 実測: 送信から応答まで
  8秒、$0.32）。コンテナは作り直され、文脈は残ったまま続く。だから**セッション側に見張らせる必要が
  無い**——クラウドには `gh` が無く、未認証のGitHub APIは60回/時なので、そもそも同じ間隔では回せない。
- **GREEN かつ `判断待ち` あり** → 触らず、#732 の「あなた待ち」へ出す。

## 4. 段の分け方

探索を並列させない。**同じ発見を N 回繰り返し、出力が揃わなくなる。**

1. **段0 — 未実装9件の要否判断**（ユーザー／issue #656）。骨格待ちのものは保留する。
2. **段1 — コンテンツの骨格を決める**（ユーザー＋1体）。系統が何本・各系統が何段・終盤に何が要る
   か・アーティファクトが何種類か。**個々のレシピは決めない**（仮決めでよい）。
3. **段2 — 文法追加をまとめて1本**（直列）。骨格が決まっているので、本当に要る文法だけを入れる。
4. **段3 — コンテンツの幅出し（並列の本命）＋ 宣言だけの機能**。
5. **段4 — 統合と計測**。他のタスクと同じものを別名で作っていないかを見る（既存のテストは
   これを見ていない）。`npm run stats:balance` で日数が成立するかを測る。

段1を段2より前に置くのが肝。**骨格が決まると、文法追加のうちどれが本当に要るかが決まる。**

### コンテンツを後回しにしない理由

`npm run stats:balance` が「1日を賄う最小労働 624分（1440分の43.4%）」と出している。残りの56.6%に
することが無ければ100〜200日は成立せず、生存コストを上げて日数を伸ばすのは
[`DesignPrinciples.md`](../docs/concept/DesignPrinciples.md) の「時間経過に任せる区間を作らない」と
衝突する。**コンテンツ不足は仕組みの未検証と同じもので、後に回すほど手戻りが大きい。**

コンテンツの幅出しは、仕組みの実装よりスウォームに向いている——触るファイルが YAML 24本に分散し、
完了条件を `stats:balance` が定義だけから計算し、系統どうしが干渉せず、量がある。

## 5. 現在地と、何を投入してよいか

**今どこまで進んでいるかは、このファイルではなく
[issue #732](https://github.com/gooyyu1/UnmappedIsland/issues/732)（司令塔）が持つ。** 直列の鎖・走って
いるもの・投入していないものとその理由・済んだ段は、すべてあちら。新しい司令塔セッションには、この
ファイルではなく **#732 のURLを貼れば足りる**。

このファイルが持つのは進め方だけで、動くのは取り決めが変わるときだけ。**状態を混ぜない**——1日に
何度も動く情報をファイルに置くと、更新のたびにコミットとPRが要り、履歴が写しで埋まる。

### 司令塔の手入れは `main` へ直接 push する

`.claude/` 配下（このファイル・[`policies.md`](./policies.md)・フック）の変更は、PRを作らずに `main`
へ直接 push してよい。`main` に保護は掛かっておらず、CI（`tests.yml`）の `paths` は `src/` `tests/`
`scripts/` などで **`.claude/` を見ていない**ので、PRにしても走るものが無い。**ユーザーのタップを1回
増やすだけになる。**

`src/` `docs/` `tests/` を触る変更は今までどおりPR。CIが要り、他のセッションと担当が重なりうる。

### 承認の要る未実装を、勝手に流さない

**未実装として置かれているものは、段0（要否の判断）を通ってから実装する**
（[`policies.md`](./policies.md)「未実装のものの扱い」）。設計文書に書いてあることを順に実装すると、
断らなかっただけのものが仕様になる。

判断の材料は印で付いている。`【確定】`＋段0の仕分け済みなら流してよく（#706・#707 がこれ）、
#656 に未チェックで載っているものは待つ。**仮決めして進む既定はこれと衝突しない**——仮決めが
効くのは「決まっていないから止まる」場面で、ここは**既に訊いてあって答えが来ていない**場面。

**ただし、待つことは唯一の道ではない。** 明るさの「大きいほうを採る」合成は、答えが来る前に
**問いのほうが消えた**——値の設計を作り直して加算だけで書けるようにしたため、文法が要らなくなった。
関門に当たったら、答えを待つのと並べて**要求そのものを畳めないか**を疑う
（[`policies.md`](./policies.md)「仕組みの作り方」の、正しさの不足より仕組みが増えるほうが重い、が根拠）。
