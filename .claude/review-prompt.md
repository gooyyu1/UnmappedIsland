# PRのレビューを1本投入するときの指示

司令塔が `create_session` へ渡す本文。**組み立てるのは
[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh)** で、下の ``` の中を読んで `<番号>` を
埋める。補足は無い——レビューの見どころはPRごとに変わらないので、司令塔が書き足すものは無い。

## なぜ司令塔ではなくセッションが読むのか

**司令塔は多数のPRを受け取るので、差分を読むほどコンテキストが埋まり、後の判断が痩せる。**
実測（2026-08-29）で、直近25本のうち `## 仮決め` に中身のあったPRは22本、`判断待ち` が付いたのは
0本だった。読み切れていない。読むこと自体はセッション1つを立てれば済み、**司令塔が受け取るのは
「通してよい」か「直しが要る」かと、コメントの `## 司令塔へ` 節**でよい（下の「書き方」）。
理由の数行を読むのは直す側。

**機械で引ける線は [`needs-user-review.sh`](../scripts/agent/needs-user-review.sh) が引く。**
こちらが見るのは、機械に引けないほうだけ。

## 結果はPRのコメントとして残す

司令塔へ `send_message` で返させない。**コメントなら `watch-prs.sh` の `REVIEWED` が拾う**ので、
司令塔は今までどおり見張るだけでよく、レビューのためにセッションを覚えておく必要が無い。
直しは元のセッションを起こしてやらせる（レビューのセッションは直さない）。

**``` の行は目印として使っている。** 消すと投入が止まる。

---

```
[司令塔] https://github.com/gooyyu1/UnmappedIsland/pull/<番号>

このPR1本を読んで、**通してよいかを判定する**のがこのセッションの仕事です。実装はしません。

まず `CLAUDE.md` と `.claude/parallel-work.md` を読んでください。

## やること

1. `gh pr view <番号>` で本文を、`gh pr diff <番号>` で差分を読む。本文の `Closes #N` が指す issue も
   `gh issue view N` で読む（**担当の範囲と完了条件はそちらに書いてあります**）。
2. 下の観点で見て、**問題があった箇所だけ**を挙げる。
3. `gh pr comment <番号> --body-file <ファイル>` で結果を書く。**これが唯一の出力です。**
   原稿の置き場は `CLAUDE.md`「`/tmp` は2つある」に従う——**編集ツールの `/tmp` と bash の `/tmp` は
   別の場所**で、取り違えると**前のレビューが残した原稿がそのまま投稿されます**（2件起きています）。
   投稿したら `gh pr view <番号> --json comments -q '.comments|last|.body'` を実行し、
   **出てきたものが自分の書いた判定かを確かめる。**

## 見る観点

`CLAUDE.md`「修正作業の進め方」「調査とレビューの進め方」がそのまま項目です。

- **原因の深さ**（2節）。症状の出ている行を止めただけになっていないか。不変条件を、それを持つべき
  クラスではなく呼び出し側が肩代わりしていないか（「自分のことは自分でする」）。
- **同じ誤りの兄弟**（3節）。**申告を鵜呑みにせず、自分でも grep して確かめる。** 本文の
  `## 自己点検` に書かれた検索語が、その原因を拾うのに十分だったかを見ること。
- **不要になった旧コード**（4節）。この変更で意味を失った分岐・回避策・特別扱いが残っていないか。
- **名前と中身が、今の機能の現実と一致しているか**。挙動を保つリファクタは古い意味を忠実に移すので、
  機能が変わった箇所に不具合が残ります。暗黙の位置規約、つじつま合わせの計算も見る。
- **担当の範囲**。差分のファイルが issue の「担当」に無いのに、本文の `## 担当外へ入った直し` にも
  挙がっていないもの。**他のタスクが同時に走っているので、これは衝突になります。**
- **PR本文に要る節**。`Closes #<issue番号>`（**issue を持つPRだけ**。番号だけの参照では閉じない）・
  `## 仮決め`（無いなら「なし」と書いてあること）・`## 自己点検`・見た目が変わるなら `## 見た目`。
  **`## 司令塔へ`・`## ユーザーの指示`・`## 担当外へ入った直し` は無ければ省く節**なので、
  無いこと自体は問題ではありません。見るのは**中身が本文の他の場所へ紛れていないか**——
  「別に issue を立てた」「#A は #B の後」「ひな形を直したほうがよい」が地の文に書かれていたら、
  **司令塔はそこを読まないので届きません**。`## 司令塔へ` へ移すよう指摘してください。
- **本文と差分が食い違っていないか**（6節）。実在しないコードの引用、途中で変えた方針が本文に
  残っているもの。

**見ないもの**: 整形とlint（CIの4つが見ています）。テストの再実行も要りません。

## 書き方

**1行目は次のどちらかだけを書く。** 司令塔はここだけを見て振り分けます。

    [レビュー] 通してよい
    [レビュー] 直しが要る

2行目以降に、**問題のあった箇所だけ**を1件1項目で書く。1件ずつ `ファイル:行番号` を挙げ、
**何が問題か**と**なぜ問題か**（どの原則・どの節に反するか）を書く。直し方は書かなくてよい——
直すのは元を書いたセッションで、そちらのほうが文脈を持っています。

**問題が無ければ、1行目だけで終えてよい。** 「確認しました」の列挙は書かないこと。

判断が付かないものは `[レビュー] 直しが要る` にはせず、**通してよいと書いたうえで「気になった点」
として挙げる**。止めるのは、直さずにマージすると壊れるものだけです。

**このPRの外の話は、コメントの末尾に `## 司令塔へ` 節を作ってそこへ書く**（無ければ節ごと省く。
**`## 仮決め` と違い、「なし」とは書きません**）。
このPRを通すかどうかとは別に、**司令塔が手を動かさないと終わらないもの**が入ります。

- **範囲外だと思ったもの**（issue にするかは司令塔が決めます）。
- **仕組みそのものへの直しの依頼。** ひな形・司令塔の道具・運用の文書について気づいたこと。

地の文に混ぜないでください。**司令塔が読むのは1行目の判定とこの節**で、途中の指摘は直す側が読みます。

## やらないこと

- **PRのブランチへ push しない。マージしない。閉じない。ラベルも触らない。**
- **新しい issue を立てない。** 上の `## 司令塔へ` に書けば司令塔が立てます。
- **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。
- コメントを書いたら報告して終わりです。返事も直しも見張らないでください。
