# PRのレビューを1本投入するときの指示

司令塔が `create_session` へ渡す本文。**組み立てるのは
[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh)** で、下の ``` の中を読んで `<番号>` を
埋める。補足は無い——レビューの見どころはPRごとに変わらないので、司令塔が書き足すものは無い。

## なぜ司令塔ではなくセッションが読むのか

**司令塔は多数のPRを受け取るので、差分を読むほどコンテキストが埋まり、後の判断が痩せる。**
実測（2026-08-29）で、直近25本のうち `## 仮決め` に中身のあったPRは22本、`判断待ち` が付いたのは
0本だった。読み切れていない。読むこと自体はセッション1つを立てれば済み、**司令塔が受け取るのは
「通してよい」か「直しが要る」かと、コメントの `## 司令塔へ` 節**でよい（下の「書き方」）。
理由の数行を読むのは直す側。

**機械で引ける線は [`needs-user-review.sh`](../scripts/agent/needs-user-review.sh) が引く。**
こちらが見るのは、機械に引けないほうだけ。

## 結果はPRのコメントとして残す

司令塔へ `send_message` で返させない。**1行目の判定は
[`board-labels.yml`](../.github/workflows/board-labels.yml) が `通してよい`／`直し待ち` のラベルへ
変える**ので、盤面を回す側はラベルだけを見ればよく、レビューのためにセッションを覚えておく必要が
無い。直しは元のセッションを起こしてやらせる（レビューのセッションは直さない）。

**``` の行は目印として使っている。** 消すと投入が止まる。

---

```
[司令塔] https://github.com/gooyyu1/UnmappedIsland/pull/<番号>

このPR1本を読んで、**通してよいかを判定する**のがこのセッションの仕事です。実装はしません。

まず `CLAUDE.md` と `.claude/parallel-work.md` を読んでください。

## やること

**読み書きの手段は、`gh` があるかで分かれます。** まず `command -v gh` を打ってください。
**クラウドのセッションには入っていません**——無いほうが普通です。無いときは GitHub の MCP で
同じことをします（PRの本文・差分を読む道具と、issue へコメントを書く道具）。

1. **PR本文と差分を読む。** `gh` があるなら `gh pr view <番号>` と `gh pr diff <番号>`。無いなら
   MCP で同じものを取る。本文の `Closes #N` が指す issue も読む（`gh issue view N` / MCP）——
   **担当の範囲と完了条件はそちらに書いてあります**。**`Closes` が無いPRもあります**（司令塔自身の
   PRと、人間が立てた相談役のPR）——範囲の出どころが本文だけになるので、`Closes` が無いこと自体は
   挙げないでください。
2. **これまでのレビューコメントを読む**（`gh pr view <番号> --json comments` / MCP）。
   **2周目以降は、見るものが変わります**——下の「2周目以降」。
3. 下の観点で見て、**問題があった箇所だけ**を挙げる。
4. **判定をPRへコメントで書く。これが唯一の出力です。**
   - `gh` があるとき: `gh pr comment <番号> --body-file <ファイル>`。原稿の置き場は
     `CLAUDE.md`「`/tmp` は2つある」に従う——**編集ツールの `/tmp` と bash の `/tmp` は別の場所**で、
     取り違えると**前のレビューが残した原稿がそのまま投稿されます**（2件起きています）。
   - `gh` が無いとき: MCP へ本文を直接渡す。**原稿のファイルを作らないので、この取り違えは
     起きません。**

   **どちらの経路でも、投稿したあとに最後のコメントを読み直し、出てきたものが自分の書いた判定かを
   確かめる**（`gh pr view <番号> --json comments -q '.comments|last|.body'`、または MCP で
   コメント一覧の末尾）。

## 見る観点

**観点の一覧は、必ず `main` の版を読んでください。挙げ方もそちらです。**

    git fetch origin main && git show origin/main:.claude/review-criteria.md

**作業ディレクトリの `.claude/review-criteria.md` を読まないこと。** このセッションはPRのブランチで
起動するので、そこに在るのは**そのPRが切られた時点の版**です。観点は絞られる方向へ動くので、古い版を
読むと**もう止めないことになったもので止めます**。`gh` が無くてもこれは `git` だけで通ります。

**同じファイルを、PRを書いた側も手前で読んでいます。** **誰が出すPRでも**、PRを作る前に
サブエージェントへ差分を渡して読ませることになっています（`CLAUDE.md`「PRを出す前に、サブエージェント
へ一次レビューさせる」）。その結果が本文の `## 自己点検` です。

**`## 自己点検` は、どこを見るかの手がかりとして読んでください。** 素通しされた理由のほうに、
残っている問題があります。**ただし `## 自己点検` 自体の不備——書き方・挙げた検索語の十分さ・
節が無いこと——は、それだけでは止める理由になりません**（入れても嘘は増えないので、スメルです）。
**止めるのは、そこを手がかりに見つけた現物の問題のほう。**

## 2周目以降

**過去のレビューコメントに `[レビュー] 直しが要る` があるなら、2周目以降です。**

**新しく止める理由として挙げてよいのは、前の周のレビュー以降に入った差分に起因するものだけ。**
それ以外の場所から新しく見つけたものは、前の周で見えていたはずのもの——つまり前の周の見落としなので、
スメルへ回してください。**これをやらないと、差分が変わるたびに新しい指摘が生まれて終わりません。**

**前の周の指摘も、そのまま引き継がないでください。** `review-criteria.md`「止めるのは4つだけ」に
当たるかを**今の一覧で読み直す**。当たらないものは、直っていなくても止める理由から外して
`[スメル] ` へ回します。**前の周が違う一覧で読まれていることがあります。**

**`[レビュー] 直しが要る` が既に3回あるのに、まだ止める理由が残っているなら**、機械では畳めて
いません。判定は `[レビュー] 直しが要る` のまま、**1行目の直後に `## 判断待ち` 節を作り、
何と何がぶつかっていて人に何を決めてほしいかを、リポジトリを開かずに読める形で3行以内に**
書いてください。

## 書き方

**1行目は次のどちらかだけを書く。** ここだけがラベルへ変わり、盤面はそのラベルで動きます。

    [レビュー] 通してよい
    [レビュー] 直しが要る

2行目以降は `.claude/review-criteria.md`「挙げ方」のとおり。

**止める理由に数えないものは、`[スメル] ` で始まる行として書きます。** 判断が付かないもの、
範囲外だと思ったもの、名前や構造の気づき、`## 自己点検` の書き方——`review-criteria.md`
「止めないもの」に当たるものは全部この形。**後から拾う仕組みがこの語形で読む**ので、崩さないこと。
`[レビュー] 通してよい` の周にも書けます。

**仕組みそのものへの直しの依頼**（ひな形・司令塔の道具・運用の文書について気づいたこと）だけは、
コメントの末尾に `## 司令塔へ` 節を作ってそこへ書く（無ければ節ごと省く。**`## 仮決め` と違い、
「なし」とは書きません**）。**節名は `## 司令塔へ` ちょうどで書く**——司令塔は節の名前を `$` で
留めて抜き出すので、`## 司令塔へ（2周目）` のように語を足すと**その節だけ届きません**。周回番号や
補足は節の中へ書いてください。

地の文に混ぜないでください。**司令塔が読むのは1行目の判定とこの節**で、途中の指摘は直す側が読みます。

## やらないこと

- **PRのブランチへ push しない。マージしない。閉じない。ラベルも触らない。**
- **新しい issue を立てない。** 上の `## 司令塔へ` に書けば司令塔が立てます。
- **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。
- コメントを書いたら報告して終わりです。返事も直しも見張らないでください。
