# PRのレビューを1本投入するときの指示

`create_session` へ渡す本文。**組み立てるのは
[`dispatch-review.sh`](../scripts/agent/dispatch-review.sh)** で、下の ``` の中を読んで `<番号>` と
`<前の版>` を埋める。補足はそれだけ——レビューの見どころはPRごとに変わらないので、書き足すものは無い。


**書くのは、レビュアーが読むために要ることだけ。** 盤面の都合（何周で止まるか・ラベルがどう動くか・
その後どこへ流れるか）は書かない。**レビュアーの仕事は渡されたPRを読むことだけ**で、周回の上限は
機械の側が持っている（`board-design.md` 4.6）。

## なぜPRごとに1本立てるのか

**差分を読むほどコンテキストが埋まる**ので、盤面を回す側が全部のPRを読むと後の判断が痩せる。
実測（2026-08-29）で、直近25本のうち `## 仮決め` に中身のあったPRは22本、`判断待ち` が付いたのは
0本だった。読み切れていない。読むこと自体はセッション1つを立てれば済み、**盤面へ返るのは判定の
1行から起こしたラベルだけ**でよい（下の「結果は…」）。理由の数行を読むのは直す側。

**機械で引ける線は [`needs-user-review.sh`](../scripts/agent/needs-user-review.sh) が引く。**
こちらが見るのは、機械に引けないほうだけ。

## 結果はPRのコメントとして残す

`send_message` で誰かへ返させない。**1行目の判定は
[`board-labels.yml`](../.github/workflows/board-labels.yml) が `通してよい`／`直し待ち`／`判断待ち` の
ラベルへ変える**ので、投入した側は返事を待たず、レビューのためにセッションを覚えておく必要も無い。
直しは元のセッションを起こしてやらせる（レビューのセッションは直さない）。

**盤面はこのコメントそのものも読む。** そのレビューが書き終えたかを、2行目の版で引く
（`board-design.md` 2.10.3）。書式を外したコメントは、判定としても「書き終えた」としても数えない。

## 読んだ版

レビュアーは判定コメントの2行目に `読んだ版: <SHA>` を書く。**次の周が読む差分の範囲は、この行から
決まる**——`<前の版>` に埋まって届き、2周目以降は `git diff <前の版>...HEAD` だけを読む
（`board-design.md` 4.5.2）。

**盤面が持っている指紋では引かない。** あちらは投入するたびに動くので、判定を書かずに落ちた周の
ぶんだけ進み、次の1本が読んでいない範囲を「前の周が見た」ことにしてしまう。何周目かの数と同じ
コメントから出せば、その食い違いが起きない。**名乗り忘れは `なし`**——PR全体を読み直す側へ倒す。

**``` の行は目印として使っている。** 消すと投入が止まる。

---

```
[デーモン] https://github.com/gooyyu1/UnmappedIsland/pull/<番号>

このPR1本を読んで、**通してよいかを判定する**のがこのセッションの仕事です。実装はしません。

まず `CLAUDE.md` と `.claude/parallel-work.md` を読んでください。

## やること

**道具は `.claude/github-access.md`「PR を読む・書く」に従ってください。** 差分のように `git` だけで
取れるものは、そちらのほうが速く確実です。

1. **PR本文と差分を読む。**

   **読む差分の範囲は、前の周が読んだ版で決まります。** それは `<前の版>` です。

   - **`なし`** … 1周目。**PR全体**の差分（`git diff main...HEAD`）。
   - **SHA** … 2周目以降。**`git diff <前の版>...HEAD` だけ**を読む。ここに出ないものは前の周が
     見ています——見落としていたとしても、それは下の「2周目以降」で止める理由から外れます。
     **その版が手元に無いとき**（作り直された枝）は `git diff` が失敗するので、1周目と同じく
     PR全体を読んでください。

   本文の `Closes #N` が指す issue も読む（道具は `.claude/github-access.md`「issue を読む・書く」）
   ——**完了の条件はそちらに書いてあります**。**`Closes` が無いPRもあります**（ユーザー自身の
   PRと、人間が立てた相談役のPR）——範囲の出どころが本文だけになるので、`Closes` が無いこと自体は
   挙げないでください。
2. **これまでのレビューコメントを読む。**
   **2周目以降は、見るものが変わります**——下の「2周目以降」。
3. 下の観点で見て、**問題があった箇所だけ**を挙げる。
4. **判定をPRへコメントで書く。これが唯一の出力です。**

   **置いたあとにコメントを読み直し、末尾に出てきたものが自分の書いた判定かを確かめてください。**
   原稿をファイルで渡す経路では、**前のレビューが残した原稿がそのまま投稿されたこと**が実際に
   起きています（`CLAUDE.md`「`/tmp` は2つある」）。

## 見る観点

**観点の一覧は、必ず `main` の版を読んでください。挙げ方もそちらです。**

    git fetch origin main && MSYS2_ARG_CONV_EXCL='*' git show origin/main:.claude/review-criteria.md

**`MSYS2_ARG_CONV_EXCL='*'` を落とさないこと。** ブリッジ（Windows）の bash では、この引数が
パスの並びと読まれて `origin\main;.claude\review-criteria.md` に化け、**観点を1つも読めないまま**
レビューが始まります（実測 2026-09-06）。クラウドでは付いていても害がありません。

**作業ディレクトリの `.claude/review-criteria.md` を読まないこと。** このセッションはPRのブランチで
起動するので、そこに在るのは**そのPRが切られた時点の版**です。観点は絞られる方向へ動くので、古い版を
読むと**もう止めないことになったもので止めます**。`gh` が無くてもこれは `git` だけで通ります。

**同じ観点を、PRを書いた側も手前で通しています**——その結果が本文の `## 自己点検` です。
**どこを見るかの手がかりとして読んでください。** 素通しされた理由のほうに、残っている問題が
あります。**ただし `## 自己点検` 自体の不備は、それだけでは止める理由になりません**（入れても嘘は
増えないので、スメルです）。**止めるのは、そこを手がかりに見つけた現物の問題のほう。**

## 2周目以降

**`<前の版>` が `なし` でなければ、2周目以降です。**

**新しく止める理由として挙げてよいのは、`git diff <前の版>...HEAD` に出る変更に起因するものだけ。**
それ以外の場所から新しく見つけたものは、前の周で見えていたはずのもの——つまり前の周の見落としなので、
スメルへ回してください。**これをやらないと、差分が変わるたびに新しい指摘が生まれて終わりません。**

**前の周の指摘も、そのまま引き継がないでください。** `review-criteria.md`「止めるのは、下に挙げたものだけ」に
当たるかを**今の一覧で読み直す**。当たらないものは、直っていなくても止める理由から外して
`[スメル] ` へ回します。**前の周が違う一覧で読まれていることがあります。**

## 書き方

**1行目は次のどれかだけを書く。** この行だけが機械に読まれます。**綴りちょうどで**——括弧も全角。

    [レビュー] 通してよい
    [レビュー] 通してよい（人の判断が要る）
    [レビュー] 直しが要る

**真ん中は、通したうえでユーザーへ回す形**（`review-criteria.md`「人の判断へ回す」）。止める理由が
無いことは1つめと同じで、違うのは**マージの前にユーザーが1つ答える**ところだけです。**何を判断して
ほしいかを、3行目以降の本体に書いてください**——**リポジトリを開かずに答えられるだけの文脈を
添える**こと。書かなければ、受け取ったユーザーは差分を開くところから始めることになります。

**2行目には、自分が読んだ版を名乗る。** `git rev-parse HEAD` の値をそのまま書く。

    読んだ版: 0a0926ded0a5ce9345f91a1006e7b13cce93afcd

**次の周が読む範囲は、この行から決まります**（上の1番の `<前の版>`）。書き忘れると次の周がPR全体を
読み直し、前の周が見送ったものまで新しい指摘として挙がります。**著者がレビュー中に push していても、
書くのは自分の作業ツリーの `HEAD`**——名乗るのは「今のPRの先頭」ではなく「自分が実際に読んだ版」。

3行目以降は `.claude/review-criteria.md`「挙げ方」のとおり。

**止める理由に数えないものは、`[スメル] ` で始まる行として書きます。**
`review-criteria.md`「止めないもの」に当たるものは全部この形。**後から拾う仕組みがこの語形で読む**
ので、崩さないこと。`[レビュー] 通してよい` の周にも書けます。

**仕組みそのものへの直しの依頼**（ひな形・盤面の道具・運用の文書について気づいたこと）も、同じ
`[スメル] ` の行として書きます。**地の文に混ぜないでください**——拾う仕組みが読むのはこの語形だけで、
散文に紛れたものは誰にも届きません。

## やらないこと

- **PRのブランチへ push しない。マージしない。閉じない。ラベルも触らない。**
- **新しい issue を立てない。** 上の `[スメル] ` に書けば、後で拾う分析係が立てます。
- **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。
- コメントを書いたら報告して終わりです。返事も直しも見張らないでください。
