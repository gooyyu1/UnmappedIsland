# 掘り起こしのプロンプト

**完成の定義に照らして、まだ issue になっていない残りを数える**係の本文。投入するのは盤面
（[`board-move.mjs`](../scripts/agent/board-move.mjs) の `CYCLES`）で、**配れる `kind:task` が
無くなった周**に一日一回立つ。渡し方は [`dispatch-chore.sh`](../scripts/agent/dispatch-chore.sh)。

**「仕事を探せ」とは言わない**（[`docs/ParallelAgents.md`](../docs/ParallelAgents.md)「⛏️ 掘り起こし役
— 探すのではなく、数える」）。そう言われたエージェントは必ず何か見つけるので、出力の質が観点の質と
同じになり、観点を毎回考える人が要ることになる。**機械が起こす係なので、その人は居ない。**

**クラウドで走る。** リポジトリへは1行も書かず、PRも出さない——**書くのは新しい issue だけ**で、
既存の issue には手を触れない。**やるかどうかから訊くものも、チェックの一覧を1本立てて受ける**
（[`board-design.md`](board-design.md) 2.17.2。周期の係には訊く先が無いので、答えは issue の
チェックで受け取る）。

題は下の `題:` の行が持つ（[`board-design.md`](board-design.md) 2.9）。

題: 発掘 完成の定義の残り

---

````
[デーモン] 配れる `kind:task` が尽きました。完成の定義に照らして、残りを数えてください。

まず `CLAUDE.md` と `.claude/parallel-work.md` を読んでください。

**探すのではなく、数える仕事です。**

> **完成の定義に載っているもの － 既に issue になっているもの ＝ 掘り起こすもの。**

**「残り0件」は失敗ではなく、正しい報告です。** 定義に照らした穴は有限なので、残りは減っていきます。
**足りないぶんを埋めるために、定義に載っていないものを持ってこないでください**——「面白さが足りない」
の類は人間と話す役（相談役）の領分で、この係には見つかりません。

## GitHub を触る道具

**道具は `.claude/github-access.md`「issue を読む・書く」に従ってください。**

この係が引くのは**開いている issue**で、既に issue になっているものを数えるために使うので、
**打ち切らずに全部**引いてください——**引く数を渡さないと30件で切れます。**
立てるときのラベルは `origin:agent`——ユーザーへ訊く issue には `判断待ち` も足します。

`origin:agent` は、人が立てた issue と見分けるための印です（`.claude/parallel-work.md`「自分で立てた
issue には `origin:agent` を付ける」）。**起票のときに一緒に渡してください**（後から付け直さずに
済みます）。**`kind:` は付けないでください**（分類するのは棚卸しです。`.claude/board-design.md`
2.17.1）。

## 数える先

**残りの作業量を答えられるものだけ**を数えます（`.claude/policies.md`「未実装のものの扱い」）。

- **`未決事項`・`今後の検討課題` の節**（`docs/**`）
- **`【未実装】` の印**（`docs/**`・`src/**`）
- **収支の穴。** `stats/balance.yaml` の `chain_gaps`（島のどこにも入手経路が無いものと、それが
  塞いでいる経路）と、`daily_minimum` が1日を賄えていない土地。読み方は
  `docs/diagnostics/BalanceStats.md`。

**`stats/balance.yaml` は読むだけにしてください。** `npm run stats:balance` は表を作り直して書き出す
ので、走らせるとチェックアウトが汚れます。表は `main` への push のたびに workflow が作り直すため、
**生成済みのものが常に最新です。**

**`docs/Someday.md` に在るものは数えません。** あれは「無くても完成を宣言できるもの」を分けた置き場
なので、残りの作業量には入りません。

## 既に issue になっているものを引く

**開いている issue を全部読んでから、差を取ってください。** 題だけで突き合わせると、言い回しの違う
同じ仕事が二重に立ちます。**閉じた issue も、同じ題材が最近閉じていないかは見てください**——直った
ばかりのものをもう一度立てることになります。

**この係が前の周に立てた issue は、まだ `kind:` が付いていません**（分類は棚卸しが一日二回やるので、
半日ほど未整理のまま残ります）。**未整理のものも「既に issue になっているもの」です。** ここを飛ばすと、
盤面が空いている間じゅう毎日同じ issue が積み上がります。

## 出口を振り分ける

**全部を訊く側へ回さないでください。** 配れるものが1件も増えず、この係を起こしても盤面が動きません。

### やると決まっているもの → 新しい issue

- **収支の穴。** 定義の穴なので、埋めるかどうかを訊くまでもありません。
- **段0（要否の判断）を通った `【未実装】`。** 印の付いた節が `【確定】` を持つもの・確定待ち
  （[#656](https://github.com/gooyyu1/UnmappedIsland/issues/656)）でチェックが付いて下ろされたもの
  （`.claude/parallel-work.md`「承認の要る未実装を、勝手に流さない」）。

書き方は次のとおり。

- 本文は `.claude/parallel-work.md` 3節の**タスク issue の型**に従う（`## 担当`・`## 完了の条件`は
  必ず置く）。**この型で書くのは、棚卸しを通ってそのまま配られるから**です。
- **1セッションで片付く大きさに割ってください。** 「未実装をすべて実装する」は仕事ではありません。
- **どこを読めば始められるかを書く。** 印が付いているファイルと節を、`## 担当` に挙げます。

### やるかどうかから訊くもの → チェックの一覧を1本立てる

- **`未決事項`・`今後の検討課題` の節。** **未決は「まだ決めていないこと」であって「やると決めた
  こと」ではない**ので、そのまま配ると乗り気でないものが実装されて戻ってきます
  （`.claude/parallel-work.md`「未決は「やるかどうか」から訊く」）。
- **段0を通っていない `【未実装】`。** 書いてあることを順に実装すると、**断らなかっただけのものが
  仕様になります**（同「承認の要る未実装を、勝手に流さない」）。要否が印から読み取れないものは、
  こちらへ回してください。

**周期の係が答えを受け取る口は、チェックボックスの issue です**（`.claude/board-design.md` 2.17.2）。
**ユーザーはこのセッションを見ない**ので、訊いて待つことはできません。

- **`判断待ち` と `origin:agent` を付けて、1本だけ立てる。** 題は
  `発掘: やるかどうかを訊く（<日付>）` の形（例: `発掘: やるかどうかを訊く（2026-09-13）`）。
  **`判断待ち` が付いている間は誰にも配られない**ので、答えが埋まる前に実装されることはありません。
- **先に、前の周のものが残っていないか見てください。** 題が `発掘: やるかどうかを訊く` で始まる
  open の issue が1本でもあれば、**訊く側はこの周は何もしません**（やると決まっているものの起票は
  そのまま進めます）。2本並ぶと、どちらを反映しても残りが嘘になります。**題を言い換えないこと**
  ——次の周はこの綴りで前の周を探します。
- **1項目1チェックボックスで、断定文で書く。** 「どうしますか」は書けません——太字の1文が、その
  まま仕様書へ書ける文になっていること。有力な案が1つなら採否、複数あるなら子チェックで選択、
  そのレベルにも達していないなら**「入れない」を選択肢に並べます**。
- **リポジトリを開かずに答えられるだけの文脈を添える。** ユーザーはスマホから読みます。節への
  リンクは確かめたいとき用で、**リンクを開かないと判断できない項目は出さないでください。**
- **1画面で答えきれる数に絞る。** 入りきらないぶんは次の周へ回してください（この issue が閉じた
  後の周が、また数え直します）。
- 本文は `.claude/parallel-work.md` 3節の**タスク issue の型**に従い（`## 担当`・`## 完了の条件`）、
  `## 完了の条件` には**チェックの付いた項目だけを反映すること**を書きます——付いた項目は、その節を
  「やると決まった」形へ書き直し、実装が要るなら issue を立てる。**付かなかった項目には手を
  付けない**（暫定のままが既定です）。

## 順番

1. **数える先を全部読む**（上の「数える先」）。**先に全部読んでから**振り分けてください。
2. **開いている issue を全部読み、差を取る。**
3. **やると決まっているものを issue にする。** 1件ずつ立てます。
4. **やるかどうかから訊くものを、チェックの一覧1本にして立てる。**
5. **報告する。** 数えた残りの件数・立てた issue の番号を書いてください。
   **残り0件ならそう書いて終わりです**——issue は立てません。

## 守ること

- **リポジトリを1行も書き換えないこと。PRも作りません。** コードも文書も読むだけです。見つけた
  穴を自分で埋めないでください——**埋めるのは、配られたワーカーの仕事**です（報告と反映を同じ役に
  持たせない）。
- **既存の issue とPRを触らないこと。** 本文もラベルもコメントも、自分が今から立てるもの以外へは
  付けません（**既にある issue を書き換えるのは棚卸しの仕事**です）。
- **`kind:` のラベルを付けないこと。** 分類は棚卸しがやります。
- **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** 自動承認ができず、
  呼んだ分がそのままユーザーの手作業になります。
- 決まっていない箇所は仮決めして進み、立てた issue の中に書いてください。

応答は日本語で。
````
