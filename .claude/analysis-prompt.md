# 分析のプロンプト

**PRのコメントに残ったスメル**——`[スメル] ` で始まる行
（[`board-design.md`](board-design.md) 4.4）——を拾い、手を打つべきものは issue へ、そこまでではないが
繰り返し現れている形は記録へ落とす係の本文。投入するのは盤面
（[`board-move.mjs`](../scripts/agent/board-move.mjs) の `CYCLES`）で、読まれていないスメルが1件でも
あれば一日一回立つ。渡し方は [`dispatch-chore.sh`](../scripts/agent/dispatch-chore.sh)。

**クラウドで走る。** 既存 issue の本文は書き換えない——切るのは新しい issue で、記録は自分のPRに
載せるので、クラウドに用意された道具でどちらも通る。

**マージ済みのPRだけを読む。** 開いているPRのコメントは、次の周のレビューや直しで消えることが
あり、拾うと二重になる。

**全件をまとめて1セッションに渡す。** 1件ずつ配ると、この係にしかできない仕事が落ちる——**同じ形が
何本のPRに出ているか**は、並べて見た者にしか見えない。1件だけを見て直せるものなら、そもそも
書いた側が直しているか、レビュアーが止めている。

題は下の `題:` の行が持つ（`board-design.md` 2.9）。

題: 分析 PRのスメル

---

````
[デーモン] マージ済みPRに残ったスメルを拾います。

まず `CLAUDE.md` と `.claude/parallel-work.md` を読んでください。

**スメル**は、PRのコメントに `[スメル] ` で始まる行として残された指摘です。書き手は2種類あります
——**レビュアー**が止める理由に数えなかったもの（`.claude/review-criteria.md`「止めないもの」）と、
**PRを書いた側**が issue を立てるほどではないと見たもの（`.claude/parallel-work.md`「PRの中で
終わらないことは、issue かスメルへ出す」）。どちらも**そのPRでは手を打たないが、気づいたこと**で、
**拾う者は他に居ません。**

## 読む範囲

**マージ済みのPRだけ。** 開いているPRのコメントは、次の周のレビューや直しで消えることがあり、
拾うと二重になります。

**読んだコメントには 👀 が付いています。** これが処理済みの印なので、**付いていないコメントだけ**が
今回の対象です。

**さかのぼる本数は、盤面の窓を覆ってください**——`scripts/agent/board-read.mjs` の `MERGED_LIMIT`
が、盤面が「立てろ」を決めるときに見ているマージ済みPRの本数です。**下回ると、盤面が見つけた未読の
スメルが係の窓の外に落ち**、印が付かないので**毎日立って毎日同じ空振りを繰り返します。** 多く読む
ぶんには構いません。

**道具は `gh` があるかで分かれます。** まず `command -v gh` を打ってください。**クラウドの
セッションには入っていません**——無いほうが普通です。無いときは GitHub の MCP で同じことをします。

- `gh` があるとき: `gh pr list --state merged --limit <MERGED_LIMIT> --json number` でPRの番号を
  引き、そのそれぞれへ
  `gh api repos/{owner}/{repo}/issues/<PR番号>/comments --jq '.[] | {id, body, reactions}'`。
- 無いとき: `search_pull_requests`（`query: "repo:gooyyu1/UnmappedIsland is:pr is:merged"`・
  `sort: created`・`order: desc`・`perPage: <MERGED_LIMIT>`）でマージ済みのPRを引き、そのそれぞれへ
  `pull_request_read`（`method: get_comments`）。**`list_pull_requests` では取れません**——
  `state: closed` は**マージされずに閉じたPRも返し**、応答の `merged` は常に偽なので、マージ済み
  だけを取る手がありません。

**どちらの経路でも、コメントの `id`（数値）と `reactions` を控えてください。** `id` は次の周へ印を
付けるのに要ります。`reactions.eyes` が1以上なら 👀 が付いています。

`[スメル] ` を含むコメントでも、**👀 が付いていれば前の周が読み終えたもの**です。飛ばしてください。

## やること

1. **対象のコメントを全部読む。** 1件ずつ片付けず、**先に全部読んでから**手を付けてください。
   同じ形が何本のPRに出ているかは、並べて見た者にしか見えません——それがこの係の仕事の中心です。
2. **手を打つべきものは issue を切る。** `kind:` のラベルは付けないでください（分類するのは棚卸し
   です。`.claude/board-design.md` 2.17.1）。**1件のスメルが1件の issue とは限りません**——同じ原因の
   ものは1件にまとめ、本文に出どころのPRを並べてください。issue の型は
   `.claude/parallel-work.md` 3節。
3. **切るほどではないが、繰り返し現れている形は記録に残す。** 書き方は下の「記録」。
4. 記録をコミットしてPRを出す（下の「PR」）。
5. **最後に、読んだコメントへ 👀 を付ける。** 対象にしたコメントは、issue を切ったかどうかに
   関わらず**全部**に付けます。**付け忘れたコメントは次の周でまた拾われます。**
   - `gh` があるとき:
     `gh api -X POST repos/{owner}/{repo}/issues/comments/<コメントの id>/reactions -f content=eyes`
   - 無いとき: `add_issue_comment` に `issue_number`（そのPRの番号）・`comment_id`（コメントの
     `id`）・`reaction: "eyes"` を渡す。**`body` は渡さないでください**——返信ではなく印です。
   **順番を入れ替えないでください。** 先に印を付けて途中で落ちると、拾われないままのスメルが黙って
   消えます。この順なら、落ちても次の周がもう一度拾うだけで済みます。

## 記録

`.claude/analysis/<日付>.md`（`YYYY-MM-DD`）へ、**1回につき1ファイル。** `docs/` ではなく `.claude/`
に置くのは、公開サイトに載る設計文書ではなく**開発の運びの記録**だからです。

置く節は次の3つ。

- **`## 読んだ範囲`** — どのPRのコメントを読んだか。
- **`## 切った issue`** — 番号と、何を見て切ったか1行ずつ。切らなかったなら「なし」。
- **`## 傾向`** — 繰り返し現れている形と、その根拠（どのPRに何度出たか）。

**同じ傾向を毎回書き直さないこと。** 前の回のファイル（`ls .claude/analysis/`）に既に在る傾向は、
**そのファイルの節へ観測を足し**、今回のファイルには足した先を1行書くだけにします。書き直すと、
回が増えるほど読む量が線形に増えます。

**1回きりの気づきは傾向ではありません。** 手を打つなら issue、打たないなら書かない——ここに全部を
書き写すと、次に読む者が繰り返しているものを見つけられなくなります。

## PR

- 本文に置く節は `CLAUDE.md`「PR本文に置く節」に従う。**`Closes` は書きません**（この係は issue を
  渡されていません）。`## 見た目` は「不要」と理由の1行で足ります。
- **立てた issue の番号は記録の `## 切った issue` にだけ書き、PR本文へは書き写さないでください。**
  切るのはこの係の仕事で、分類は棚卸しが拾います——ユーザーの手は要りません。**仕組みそのものへの
  直しの依頼**（ひな形・盤面の道具・運用の文書）も、やる必要があるなら同じように issue にします。
- **push の前にサブエージェントを1本立てて、これから出す差分をレビューさせてください。** 手順は
  `CLAUDE.md`「PRを出す前に、サブエージェントへ一次レビューさせる」——**開いて読んでから通して
  ください。**
- そのうえで `npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` の4つを通す。
- **PRを作ったら報告して終わりです。CIの結果もレビューも見張らないでください。**
  **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。直しが要れば、盤面が `send_message` で
  このセッションを起こします。

## 守ること

- **コードは1行も変えないこと。** 成果は、新しい issue と `.claude/analysis/` の記録だけです。
  スメルを自分で直さないでください——直す値打ちがあるなら issue にします。
- **既存の issue とPRの本文・ラベルを触らないこと。** 付けるのは 👀 だけです。
- **PRのコメントへ返信しないこと。**
- 決まっていない箇所は仮決めして進み、PR本文の `## 仮決め` に書いてください。
````
