# 分析のプロンプト（一次）

**PRのコメントに残ったスメル**——`[スメル] ` で始まる行
（[`board-design.md`](board-design.md) 4.4）——を拾い、手を打つべきものは issue へ、そこまでではないが
繰り返し現れている形は記録へ落とす係の本文。投入するのは盤面
（[`board-move.mjs`](../scripts/agent/board-move.mjs) の `CYCLES`）で、読まれていないスメルが1件でも
あれば一日一回立つ。渡し方は [`dispatch-chore.sh`](../scripts/agent/dispatch-chore.sh)。

**この係が見るのは、その回の帯だけ。過去の回の分析は読まない**（出どころ: ユーザーの指示・
2026-09-07。[`board-design.md`](board-design.md) 2.17.4）。**回をまたいで同じ形を探すのは二次の係**
（[`analysis-trend-prompt.md`](analysis-trend-prompt.md)）で、そちらの入力はこの係が書いたファイル。
**同じ形を毎回書くのは無駄ではない**——何回の帯に独立して現れたかが、二次にとっての根拠そのもの。

**クラウドで走る。** 既存 issue の本文は書き換えない——切るのは新しい issue で、記録は自分のPRに
載せるので、クラウドに用意された道具でどちらも通る。

**マージ済みのPRだけを読む。** 開いているPRのコメントは、次の周のレビューや直しで消えることが
あり、拾うと二重になる。

**全件をまとめて1セッションに渡す。** 1件ずつ配ると、この係にしかできない仕事が落ちる——**同じ形が
何本のPRに出ているか**は、並べて見た者にしか見えない。1件だけを見て直せるものなら、そもそも
書いた側が直しているか、レビュアーが止めている。

題は下の `題:` の行が持つ（`board-design.md` 2.9）。

題: 分析 PRのスメル

---

````
[デーモン] マージ済みPRに残ったスメルを拾います。

まず `CLAUDE.md` と `.claude/parallel-work.md` を読んでください。

**スメル**は、PRのコメントに `[スメル] ` で始まる行として残された指摘です。書き手は2種類あります
——**レビュアー**が止める理由に数えなかったもの（`.claude/review-criteria.md`「止めないもの」）と、
**PRを書いた側**が issue を立てるほどではないと見たもの（`.claude/parallel-work.md`「PRの中で
終わらないことは、issue かスメルへ出す」）。どちらも**そのPRでは手を打たないが、気づいたこと**で、
**拾う者は他に居ません。**

## 読む範囲

**マージ済みのPRだけ。** 開いているPRのコメントは、次の周のレビューや直しで消えることがあり、
拾うと二重になります。

**読んだコメントには 👀 が付いています。** これが処理済みの印なので、**付いていないコメントだけ**が
今回の対象です。

**さかのぼるのは本数ではなく期間です**——`scripts/agent/board-read.mjs` の `MERGED_WINDOW_HOURS`
が、盤面が「立てろ」を決めるときに見ている幅（時間）で、**そこから今までにマージされたPRを
全部**読んでください。**盤面の窓を下回ると、盤面が見つけた未読のスメルが係の窓の外に落ち**、印が
付かないので**毎日立って毎日同じ空振りを繰り返します。** 多く読むぶんには構いません。

**絞るのはマージされた時刻で、作成日ではありません。** 長く開いていたPR（`判断待ち` で人の手番へ
移ったものなど）は、作成日で数えると、マージされる頃には窓の外に居ます。

**道具は `.claude/github-access.md`「PR を読む・書く」に従ってください。** マージ済みのPRを引き、
そのそれぞれのコメントを読みます。`<窓の始まり>` は「今から `MERGED_WINDOW_HOURS` 時間前」を
`2026-09-05T12:00:00Z` の形で書いたもの、`<上限>` は `scripts/agent/board-read.mjs` の
`CAPS.mergedPrs`（盤面が使うのと同じ値）です。

**栓に当たったら、窓を取り切れていません。** 引けた本数が `CAPS.mergedPrs` に達していたら、
**記録の `## 読んだ範囲` にそう書いてください**——黙って切ると、切られたぶんは誰にも見えないまま
消えます。

**コメントの `id`（数値）と `reactions` を控えてください。** `id` は次の周へ印を付けるのに要ります。
`reactions.eyes` が1以上なら 👀 が付いています。

`[スメル] ` を含むコメントでも、**👀 が付いていれば前の周が読み終えたもの**です。飛ばしてください。

## やること

1. **対象のコメントを全部読む。** 1件ずつ片付けず、**先に全部読んでから**手を付けてください。
   同じ形が何本のPRに出ているかは、並べて見た者にしか見えません——それがこの係の仕事の中心です。
2. **手を打つべきものは issue を切る**（道具は `.claude/github-access.md`「issue を読む・書く」）。
   `kind:` のラベルは付けないでください（分類するのは棚卸しです。`.claude/board-design.md`
   2.17.1）。**`origin:agent` と `goal:` は、起票のときに一緒に渡してください**——立てた本人しか
   付けられない印です（`.claude/parallel-work.md`「自分で立てた issue には `origin:agent` を
   付ける」・`.claude/board-design.md` 2.18.1）。後から付け直す道はありますが、**別の手が要る形に
   すると、付け忘れた issue が「人が立てた」として数えられます。**
   **1件のスメルが1件の issue とは限りません**——同じ原因のものは1件にまとめ、本文に
   出どころのPRを並べてください。issue の型は `.claude/parallel-work.md` 3節。

   **`goal:` は、その issue が何へ向かうかで選びます**——`goal:game` は完成の定義を1つ埋めるもの
   （世界の中身・遊びの仕組み・画面）、`goal:upkeep` は作る仕組みと記述を整えるもの。**この係が
   切るものはたいてい `goal:upkeep`** ですが、スメルがゲームの中身を指しているなら `goal:game` です。
   **迷ったら `goal:upkeep`。** 整備を前へ出す誤りのほうが高くつきます。

   **箇所を数え上げる issue を立てないでください。** 同じ形が2本以上のPRに出ているなら、切るのは
   **その形1本**で、`## 完了の条件` は**箇所の一覧ではなく「その形がリポジトリから無くなったこと」**
   にします。名指しした箇所は `## 担当`（調べ始める場所）へ置いてください。
   **同じ形の issue が既に開いていないかを、先に確かめてください**——開いていれば2本目を立てず、
   見つけた箇所をその issue へのコメントで足します。
   **箇所で切ると、1つの形が issue の数だけセッションを食い、そのどれもが形を消しません**
   （実際にそうなった例は `.claude/parallel-work.md` 3節）。
3. **切るほどではないが、繰り返し現れている形は記録に残す。** 書き方は下の「記録」。
4. 記録をコミットしてPRを出す（下の「PR」）。
5. **最後に、読んだコメントへ 👀 を付ける。** 対象にしたコメントは、issue を切ったかどうかに
   関わらず**全部**に付けます。**付け忘れたコメントは次の周でまた拾われます。**
   **順番を入れ替えないでください。** 先に印を付けて途中で落ちると、拾われないままのスメルが黙って
   消えます。この順なら、落ちても次の周がもう一度拾うだけで済みます。

## 記録

`.claude/analysis/<日付>.md`（`YYYY-MM-DD`）へ、**1回につき1ファイル。** `docs/` ではなく `.claude/`
に置くのは、公開サイトに載る設計文書ではなく**開発の運びの記録**だからです。

置く節は次のとおり。

- **`## 読んだ範囲`** — どのPRのコメントを読んだか。
- **`## 切った issue`** — 番号と、何を見て切ったか1行ずつ。**1件も切らなかったなら「なし」。**
- **`## 落としたもの`** — **読んだスメルのうち、issue にしなかったもの**と、落とした理由。**全部を
  issue にしたなら「なし」。**
- **`## 傾向`** — **今回の帯の中で**繰り返し現れている形と、その根拠（どのPRに何度出たか）。

**落としたものを書くのは、印を付けた時点でそのスメルが二度と拾われないからです。** 👀 は issue に
したかどうかに関わらず読んだコメント全部へ付ける決まりなので、ここに書かなければ、**落としたこと
自体がどこにも残りません。** 1件ずつ並べる必要はなく、**落とした理由が同じものは1行にまとめて**、
出どころのPRを添えてください。

**過去の回のファイルを読まないでください。** 触るのも書くのも今回のファイルだけです。**同じ形が
前の回にも書かれていることは構いません**——**何回の帯に独立して現れたかが、二次の係
（[`analysis-trend-prompt.md`](analysis-trend-prompt.md)）の根拠そのもの**なので、こちらで畳むと
その回数が消えます。過去に当たろうとすると、回が増えるほど読む量が線形に増えもします。

**`## 傾向` の中の見出しを、過去の回と揃える必要もありません。** 回をまたいで同じ形かどうかを
判定するのは二次の仕事で、その判定は見出しの一致では行いません。**自分が見た形を、自分の言葉で
書いてください。**

**1回きりの気づきは傾向ではありません。** 今回の帯で1本のPRにしか出ていない形は、手を打つなら
issue、打たないなら `## 落としたもの` へ——`## 傾向` に全部を書き写すと、繰り返しているものが
埋もれます。

## PR

- 本文に置く節は `CLAUDE.md`「PR本文に置く節」に従う。**`Closes` は書きません**（この係は issue を
  渡されていません）。`## 見た目` は「不要」と理由の1行で足ります。
- **立てた issue の番号は記録の `## 切った issue` にだけ書き、PR本文へは書き写さないでください。**
  切るのはこの係の仕事で、分類は棚卸しが拾います——ユーザーの手は要りません。**仕組みそのものへの
  直しの依頼**（ひな形・盤面の道具・運用の文書）も、やる必要があるなら同じように issue にします。
- **push の前にサブエージェントを1本立てて、これから出す差分をレビューさせてください。** 手順は
  `CLAUDE.md`「PRを出す前に、サブエージェントへ一次レビューさせる」——**開いて読んでから通して
  ください。**
- そのうえで `npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` の4つを通す。
- **PRを作ったら報告して終わりです。CIの結果もレビューも見張らないでください。**
  **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。直しが要れば、盤面が `send_message` で
  このセッションを起こします。

## 守ること

- **コードは1行も変えないこと。** 成果は、新しい issue と `.claude/analysis/` の記録だけです。
  スメルを自分で直さないでください——直す値打ちがあるなら issue にします。
- **既存の issue とPRの本文・ラベルを触らないこと。** 付けるのは 👀 だけです。
- **PRのコメントへ返信しないこと。**
- 決まっていない箇所は仮決めして進み、PR本文の `## 仮決め` に書いてください。
````
