# 火システム設計

## 概要

炉を組み、燃料をくべ、火を保ち、その熱を他の物へ渡す仕組みの設計ドキュメントです。「どんな加熱方法が
どう組み立てられ、何に使えるか」までを決めます。

**個別の料理レシピは決めません。** 料理の大半は、既存の `recipes`（[`RecipeSystem.md`](./RecipeSystem.md)）で
未加熱の物を組み立て、最後に火で加熱して完成します。本書が決めるのはその最後の一手の**受け渡し口**
（7 節）だけで、何と何を組み合わせると何になるかは扱いません。火起こし具・燃料になる物の一覧は
[`SurvivalItems.md`](../world/SurvivalItems.md)、火スキルの段は [`Skills.md`](../world/Skills.md) が持ちます。
天気・気温は [`ClimateSystem.md`](./ClimateSystem.md) が、雨から守る `sheltered` は
[`ContainerSystem.md`](./ContainerSystem.md) 6 節が持ちます。

**新設する文法はありません。** 火は炉のプロパティ（1 節）、くべる操作は `transfer`（2 節）、火の育ちと
衰え・燃焼・加熱は `add`（2.2 節・7 節）、炉の段上げは `on_max`（5 節）で、いずれも
[`GameElementDefinition.md`](./GameElementDefinition.md) の既存語彙です。本書が導入するのは語彙の名前
だけです。

| 種別 | 名前 |
|---|---|
| タグ | `hearth`（炉）・`fuel`（燃料）・`tinder`（火口）・`roastable`（直火に入れられる物）・`cookware`（火にかける器） |
| スロット | `fire`（火にかけているもの） |
| プロパティ | `fuel`（くべた薪。燃料の側では「くべると増える量」）・`heat`（火力。一番下の段が種火）・`stones`（積んだ石）・`heat_soak`（石の蓄熱）・`cooking_progress`（加熱の進み） |
| 型 | `campfire`（焚き火）・`three_stone_hearth`（三石のかまど）・`stone_hearth`（石囲いの炉）・`fire_drill`（火起こし具）・`burning_tinder`（火種）・`hot_stone`（焼け石） |

定義は `src/assets/world-codex/fire.yaml`（燃料になる物と火口は `locations.yaml`・`coconut.yaml`・
`fiber.yaml`、焼ける物は `animals.yaml`）、検証は `tests/world-codex/fireYaml.test.ts` です。

本ドキュメントは検討結果であり、確定仕様書ではありません。**本書の設計は 9 節を除いて実装済み**で、
未実装の節（9.1・9.2）は見出しにラベルを付けています。数値はいずれも目安で、`tick` = 15 分・
1 日 = 96 tick（[`DurabilitySystem.md`](./DurabilitySystem.md) 1 節）を前提とします。未決事項は
11 節に整理しています。

## 1. 火は炉のプロパティで、「火」という物は作らない

**燃えていることは炉のプロパティで表し、火そのものを表すオブジェクトは置きません。** 単独では存在
できない物は、抱えている側のプロパティにするのが既定です——液体が容器の変種になっている
（[`LiquidContainerSystem.md`](./LiquidContainerSystem.md) 1 節）のと同じで、火は炉から取り出せず、
分けられず、別の炉へ移せません。独立させても得るものがなく、カードが 1 枚増えるだけです。

炉は `hearth` タグを持つ設置物（`fixture`）で、**スロットは `fire`（火にかけているもの）1 つだけ**です。
直火で焼く物も、焼く石も、火にかけた器も、すべてここへ入ります（枠が受け入れる型は 1.1 節）。

**燃料はここへ入りません。** くべた薪は物として炉の中に居続けるのではなく、`fuel`（くべた薪の量）へ
溶けて消えます（2 節）。

### 1.1 器の場所は、スロットではなく枠で分ける

**器を置ける炉と置けない炉の差は、`cells`（`GameElementDefinition.md` 7.2 節）の並びが持ちます。**

```yaml
# 三石のかまど
slots:
  fire:
    cells:
      - {accept: {tag: roastable}}  # 火の中。直火で焼く物・焼く石
      - {accept: {tag: roastable}}
      - {accept: {tag: cookware}}   # 石の上。器だけが載る
```

焚き火はこの最後の枠を持たず、石囲いの炉は 2 つ持ちます（6 節）。器を支えているのが炎ではなく石だと
いうことは、**枠があるかどうか**で表せます。枠は宣言順ではなく型の合う枠へ埋まる（同 7.2 節）ので、
焼く物を重ねれば火の中へ、器を重ねれば石の上へ、条件を書かずに入ります。

**火の中の枠は `roastable` を持つ型だけを受け入れます。** 持ち物なら何でも投げ込める枠にすると、
炉が「物を捨てる場所」になり、火にかけたものだけが持つはずの `cooking_progress`（7 節）と枠の意味が
噛み合いません。持つのは丸焼きの鎖（生肉 → 焼けた肉 → 焦げた塊、ネズミの死体 → 丸焼き、
タロイモ・ヤシガニ → 焼いたもの → 焦げた塊）で、鎖の終わりの焦げた塊も、置き換わった先が火の中の
枠に残れるように持ちます（7.2 節）。焼け石（9 節）を実装するときは、石がこのタグを得ます。

**この鎖は「焼くとおいしい」ではなく「焼かないと食べられない」も表します。** タロイモとヤシガニは
生では食べ物のタグを持たず、焼いて初めて食べられます（`src/assets/world-codex/foods.yaml`）。
生でも食べられる肉と同じ仕組みに乗るのは、違いが**生の側が `eat` を持つかどうか**の 1 点だけだからです。

スロットを 2 つに分けないのは、**画面が 1 つの対象につき 1 つの並びしか出せない**ためです。カードを
押したときに開くスロットは `visible_slots` が名指しする決まりで（同 7.11 節）、これは画面の
都合というより、「押せば開く」「重ねれば入る」の行き先が 1 つに定まっていることそのものです。2 つ目の
スロットを足すと、どちらを開きどちらへ入れるかを画面側が決めることになり、その規則が YAML の外へ出ます。

## 2. 燃料は数える物で、くべると炉の `fuel` へ溶ける

**燃料は塊で数える物です。** 小枝も薪も、粘土や石と同じように 1 個・2 個で存在し、量として分割は
しません（中身入りの容器とは違う扱い。[`LiquidContainerSystem.md`](./LiquidContainerSystem.md) 1 節）。
炉へくべると、その物が持つ `fuel` が炉の `fuel` へ移り、**燃料そのものは残らず消えます**。

```yaml
# 炉の側が宣言する
interactions:
  add_fuel:
    trigger: {drag: {tag: fuel}}
    duration: 1
    allow_multiple: true     # 束ねた薪はまとめてくべられる（GameElementDefinition.md 12.4節）
    transfer:
      amount: 999            # 入るだけ入れる
      from: dragged
      from_prop: fuel
      to_prop: fuel
    destroy: dragged         # 入りきらなかった分は失われる
```

**満杯の炉を拒む条件は書きません。** 移送先の `fuel` は `range` を持つので、あと何本くべられるかは
その残りから決まります（同 12.4 節）。残りが 0 なら組み合わせは候補にならず、薪だけ失う結果になりません
——**上限は `range` が既に言っている**ので、同じ値を条件としてもう一度書く必要はありません。

```yaml
# 燃料の側が宣言する
props:
  fuel:
    value: 20                # 太い枝1本ぶん
```

`transfer`（`GameElementDefinition.md` 9.5 節）を使うのは、**`add` だと炉の種類 × 燃料の種類の数だけ
固定値を書くことになる**ためです。移す量は燃料の側が 1 箇所で持ち、炉はそれを受けるだけになります。

**`destroy: dragged` を併記して、中途半端に残った薪を作りません。** 効果は書いた順に適用される
（`GameElementDefinition.md` 9.7 節）ので、`transfer` の後に `destroy` を書いて、移した後に消します。
これを書かないと「燃料としては僅かしか残っていないが、他の用途には普通に 1 個として使える枝」という
説明のつかない物が生まれます。入りきらなかった分は失われますが、満杯を拒む条件があるので、失うのは
高々 1 個ぶんです。

### 2.1 燃料を枠へ置かない理由

くべた薪を `fire` の枠に置き続ける形も書けますが、採りません。

- **1 つの枠には同じ型しか積めない**（同 7.6 節）ので、枠の数がそのまま同時に燃やせる燃料の種類数に
  なります。小枝と太い枝と皮を一緒にくべる、という当たり前のことが枠の都合で縛られます。
- **燃えている炉から薪を取り出せてしまいます。** 半分燃えた薪も型は同じままなので、見た目に区別が
  つかないうえ、炉から出した瞬間に燃えるのが止まります。
- **枠が燃料に食われます。** `fire` の枠は焼く物と焼く石のためのもので、薪が入ると小さい炉ほど
  何も焼けなくなります。

炉のプロパティへ溶かせば 3 つとも消えます。**くべた薪は炉の中に「在る」ものではなく、火が「食べて
しまった」もの**だからです。

### 2.2 火力は、薪を食って育ち、薪が尽きると衰える

**炉が持つ数は `fuel`（薪）と `heat`（火力）の 2 つだけで、どちらも `add` で動く実体値です。**
`modify` は使いません——火は「今の状態から計算される値」ではなく、**育ったり衰えたりする量**だからです
（[`ClimateSystem.md`](./ClimateSystem.md) 1 節の数値積分と同じ考え方）。

- **薪があれば、火力は育つ。** ただし `heat` が 0 より大きいとき、つまり火がついているときだけです。
- **火力が高いほど、薪を速く食う。** 薪が尽きれば、その火力に応じた速さで衰えていく。

```yaml
# 炉のfuelのstagesが宣言する（薪が火を育てる）
- name: some
  min: 10
  passives:
    - conditions:
        - {prop: heat, gt: 0}      # 消えている炉は、薪を積んでも育たない
      add:
        self:
          heat: 6
```

```yaml
# 炉のheatのstagesが宣言する（火が薪を食い、薪が尽きたら衰える）
- name: flame
  min: 20
  passives:
    - add:
        self: {fuel: -1.5}
    - conditions: [{prop: fuel, in_stage: none}]
      add:
        self: {heat: -6}
```

| `fuel`（薪） | 段 | 火力の育ち |
|---|---|---|
| 0 | `none` | 育たず、衰えていく |
| 1〜9 | `few` | +2/tick |
| 10〜39 | `some` | +6/tick |
| 40〜 | `many` | +16/tick |

**育ちと衰えは同時に効かせません。** `add` は登録順に値を書き換えながら適用されるため、同じ
tick に正負が混ざると、段の境目で「育って次の段へ入り、その段の冷めを即座に払って戻る」が起きて、
火がそこから育たなくなります。育ちは薪がある間、衰えは薪が尽きている間だけにして、打ち消しを断ちます。
この打ち消しは段を細かく刻めば**狙った高さの平衡点**にもできますが、火には平衡が要りません
（[`DesignNotes.md`](./DesignNotes.md) tick毎のaddの平衡点節）。

**火の大きさを決めるのは、上限と時間の競争です。** 薪があるかぎり火力はその炉の上限（`heat` の
`range.max`、6 節）まで上がりますが、**上がるより先に薪が尽きれば、そこまでしか大きくなりません**。
小枝 1 本では熾火のうちに燃え尽き、太い枝を並べて初めて炎になります。上限の中でどこへ届くかは、
別の宣言ではなく薪の量と時間が決めます。

**薪を組んだだけの炉は `heat` が 0 のままです。** 育ちが「火がついている」でゲートされているので、
積んだ薪は減りも育ちもせず、着火（3.1 節）した瞬間から食われ始めます。

### 2.3 火力の段

`heat` は段（`stages`、`GameElementDefinition.md` 6.4 節）を持ち、**段が加熱の速さ・薪の減り・薪が尽きた後の衰えを決めます**。数値の
境目を条件の側にも書くと、境目が 2 箇所に散るためです。

| 段 | `heat` | 状態 | 加熱の速さ | `fuel` の減り | 薪が尽きた後の衰え |
|---|---|---|---|---|---|
| `out` | 0 | 消えている | — | — | — |
| `ember` | 1〜4 | 種火 | **できない** | -0.1/tick | 炉ごと（3 節） |
| `coals` | 5〜19 | 熾火 | 1/tick | -0.5/tick | -2/tick |
| `flame` | 20〜59 | 炎 | 3/tick | -1.5/tick | -6/tick |
| `blaze` | 60〜 | 高温 | 5/tick | -4/tick | -6/tick |

**焼く・煮るに段の下限は設けません。** 熾火の上でも湯は沸きます——むしろ煮炊きは熾火のほうが安定
するので、鍋を炎に載せる必要はありません。炎が速いだけで、できることが増えるわけではないためです。
**段を下限として要求するものは1つもありません。** 土器の焼成（`src/assets/world-codex/pottery.yaml`）も
下限を持たず、熾火からでも進みます——覆い焼きの炉が `blaze` まで上がるので、結果として速く焼き上がる
だけです。**焼き上がりが成功するかは、`heat` ではなく焼かれる側が持つ水の残りが決めます**——濡れた器を
炎に入れれば割れますが、それは炉が拒むのではなく、器の側の賭けに負けるということです。昇温の途中も
進むことは、現実の「あぶり焚き」（水を抜きながら焼く）にあたります。

燃料 1 つが持つ `fuel` の目安は次のとおりです。

| 燃料 | `fuel` |
|---|---|
| 小枝 | 3 |
| ヤシの実の皮 | 2 |
| 太い枝 | 20 |

**`fuel` と `heat` の上限はどちらも炉が持ちます**（6 節）。焚き火にどれだけ薪を積んでも `blaze` に
届かないのは、開いた焚き火の火力がそこで頭打ちになるからで、段の側に別の禁止を書く必要はありません。

## 3. 種火は、火力の一番下の段

**種火を別のプロパティにはしません。** `heat` の `ember` の段（1〜4）がそれです。**料理には使えないが、
薪をくべれば育つ火力**——種火とはそういうものだからです。

| `heat` | 意味 |
|---|---|
| 0（`out`） | 死んでいる。薪を足しても何も起きず、着火が要る |
| 1〜4（`ember`） | 種火。料理はできないが、薪を足せば育つ |
| 5 以上 | 料理ができる |

**「料理ができるほど熱い」なら「再着火が要らない」のは自明です。** 2 つを別のプロパティで持つと、
この当たり前の含意を守るために両者を同期させ続けることになります。1 本の数直線の上下として持てば、
含意は順序そのものになって守る必要が消えます。

**`ember` の段だけ、冷める速さが炉ごとに違います。** 灰をかぶって空気を絞られた火がどれだけもつかが、
炉の差そのものだからです（6 節）。

```yaml
# 焚き火の側が宣言する。段のpassivesではなく炉のpassivesに置くのは、traitが配るstagesを
# 炉ごとに部分的に差し替えられないため。
passives:
  - conditions:
      - {prop: heat, in_stage: ember}
      - {prop: fuel, in_stage: none}   # 薪が載っていれば、火は衰える側ではなく育つ側
    add:
      self: {heat: -2}   # 1〜4を2 tick(30分)で通り抜けて死ぬ。石囲いの炉は-0.125（8時間）
```

**種火が残っているあいだに薪を足せば、道具なしで火が戻ります。** 火起こし具を使わずに済むことが、
炉を常設する唯一にして最大の利得です。焚き火が「使い捨て」なのは組み方のせいではなく、種火が短時間で
死ぬからで、石で囲った炉が常設になるのは種火が翌朝まで生きるからです。

**画面にもこの形がそのまま出ます。** `fuel` は「あとどれだけ燃え続けられるか」なのでバー
（`gauge` タグ、[`CardView.md`](../ui/CardView.md) 8.1 節）、`heat` は「今この炉で何ができるか」なので
シンボル 1 つです。種火と熾火が排他なのは、同じ数直線の隣り合う段だからで、画面側に排他の規則を書く
必要はありません。

### 3.1 着火は、火種を炉へ運ぶ

**火起こしと着火を分けます。** 火起こし具（`fire_drill`）を火口（`tinder`）へ重ねて火をつけ、できた
**火種**（`burning_tinder`）を炉へ重ねると、炉に種火が立ちます。

**火種と種火は別のものです。** 火種は持ち運べる物（`burning_tinder`）で、炉へ運ぶために存在します。
種火は炉に残る最小の火力（`heat` の `ember` の段、3 節）で、物ではありません。火種を炉へ落とすことは、
運んできた火を炉の種火へ置き換える操作です。

```yaml
# 火口の側が宣言する。成否は天気とスキルの段が重みを動かす
interactions:
  light:
    trigger: {drag: {object: fire_drill}}
    duration: 30
    pick:
      - weight: {prop: ignition_chance}
        destroy: self
        spawn: {object: burning_tinder}
        signal: lit
      - weight: 40           # 外した回は火口だけが無駄になる
        destroy: self
        signal: not_lit
```

**成否は `signal`（`GameElementDefinition.md` 9.8 節）が告げます。** 火口はどちらの回も同じように
消えるので、レーンの上では 30 分かけて札が 1 枚減っただけに見え、外した回が「何も起きなかった」と
区別できません。火種が生まれたかどうかを札の増減から読ませず、起きたことを火口の札の上へ出します。

```yaml
# 炉の側が宣言する
interactions:
  ignite:
    trigger: {drag: {object: burning_tinder}}
    conditions:
      - {reason: no_fuel, prop: fuel, gt: 0}
    destroy: dragged
    set: {self: {heat: 1}}      # 種火の段のいちばん下から始まる
```

**着火が置くのは種火 1 つぶんだけです。** そこから先は薪が育てます（2.2 節）——火種を落としてすぐ煮炊きが
できるわけではなく、炎になるまで数十分かかります。着火の強さを炉ごとに書き分ける必要もありません。

**火種は短命です。** 1 tick で燃え尽きて消えるので、火起こしをした場所で使うしかありません。火種を
持って土地を移動することはできず、炉のある場所で起こすことになります。

### 3.2 火口になるのは繊維状のものだけ

**枝には直接火をつけられません。** 摩擦で得られるのは米粒ほどの熾で、それを受け止めて炎に育てられるのは
**ほぐした繊維・綿状のものだけ**です。細い小枝でも太すぎて火は移りません。火口 → 焚き付け → 薪という
順に太くしていくのが、道具のない火起こしの実際です。

| 火口 | 手に入れ方 |
|---|---|
| 枯れ草 | 拾う（**道具が要らない**） |
| ヤシの実の皮 | 熟した実の皮をほぐす（刃物が要る、`coconut.yaml`） |
| 植物繊維 | 掻き取る（刃物が要る、`fiber.yaml`） |

**道具の要らない火口を 1 つ残すことが要件です。** 火口が刃物を要る物ばかりだと、火が石器の後ろへ回って
しまい、「きりもみ式が道具も紐も要求しない」ことで保証されている火スキルの立ち上がり
（[`SurvivalItems.md`](../world/SurvivalItems.md) 1.1 節）が崩れます。乾いた土地でだけ拾える枯れ草が
その役です。

**火がついた後は、素材の違いを見ません。** どの火口から起こしても `burning_tinder` 1 種類になります。
火種にできることは炉へ移すことだけで、そこに枯れ草とコイアの差を持たせても、増えるのは型の数だけ
だからです。

**火口は燃料にもなります。** ヤシの実の皮は火口にも薪にもなりますが、**組み合わせる相手が違うので迷いは
起きません**——火起こし具と合わせれば火口、炉と合わせれば燃料です。

### 3.3 火起こしの宣言は、火口の側に置く

ドラッグ型の操作は素材の側に宣言する（`GameElementDefinition.md` 12.3 節）ので、火起こし具ではなく
火口が `light` を持ちます。宣言は 1 つで、火起こし具を火口へ重ねても火口を火起こし具へ重ねても同じ
`light` が実行されます——成否の `pick` を 2 箇所へ書く必要はありません。

## 4. 薪の消費を火力の段に置ける理由

**`heat` が温度ではなく火力だからです。** 火力とは単位時間あたりに出る熱のことで、それは**そのあいだに
食っている薪の量そのもの**です。2 つは同じ現象の表と裏で、「熱いほど速く燃える」のではなく「速く
燃えているから熱い」——因果は後者の向きです。だから消費を `heat` の段に書くのは別の概念での代用ではなく、
定義をそのまま書いていることになります。

もし `heat` を温度として定義したら、この置き方は誤りになります。火が消えた直後のまだ熱い炉が薪を食い
続けてしまうためで、そのときは「燃えているか」を別に持つ必要が出ます。

**火が生きているかを別に持たないのも、同じ理由です。** 火力が 0 より大きいことがそのまま「燃えている」で、
その一番下が種火です（3 節）。薪の消費・加熱・冷めのすべてを `heat` の段に並べられるのは、この 1 つの
定義から出ています。

**炉ごとの差は、火力と薪の上限、そして種火の衰えだけです**（6 節）。薪の減りと加熱の速さはどの炉でも
同じ表（2.3 節）に従い、燃料の側は、くべるとどれだけ増えるか（2 節）だけを持ちます。

## 5. 石は火の中ではなく、火のまわりに積む

**石を炉へ運ぶと `stones` が 1 増え、必要数に達した瞬間に次の段の炉へ置き換わります。**

```yaml
# 焚き火の側が宣言する
interactions:
  add_stone:
    trigger: {drag: {object: stone}}
    destroy: dragged
    add: {self: {stones: 1}}
props:
  stones:
    value: 0
    range: {min: 0, max: 2}
    on_max:
      spawn: {object: three_stone_hearth}
      destroy: self
```

`range.max` を必要数に置き、そこへ届いた瞬間に反応させるのは、耐久値 0 での自壊と同じ形です
（`GameElementDefinition.md` 6.3 節）。段上げは箱のレシピにしません。地面に石を運んで積むだけの作業で、材料を箱へ入れて待つ
形にする理由がないためです。

置き換えなので、段を上げると火は消えます（炉を組み直しているため）。

### 5.1 石は既存の `stone` をそのまま使い、炉は一人用の大きさになる

**専用の大きな石は導入しません。** 既存の `stone`（1kg・手に持てる大きさ、`locations.yaml`）を運んで積みます。
石囲いの炉まで組んでも石は 11 個・11kg で、持てる量（33kg）の 3 分の 1 に収まるので、運搬そのものが
関門にはなりません。

その結果、炉は一般に想起されるかまどよりだいぶ小ぶりな、**一人分の器が 1 つ載る大きさ**になります。
これは制約ではなく、この島に居るのが 1 人だという事実の現れです。

三石が器を持ち上げる高さも 10cm 弱なので、器の下に入るのは炎ではなく熾火です。2 節が焼く・煮るに段の
下限を設けないのは、この寸法とも噛み合っています。

石囲いの炉の種火が翌朝まで生きるのも、この大きさで成立します。種火が長く保つ主因は灰に埋めて空気の
流れを絞ることで、石が担うのは風防と輻射だからです。石の熱容量に頼る設計なら、この大きさでは足りません。

## 6. 炉の段

| 段 | 炉 | 作り方 | 火の中の枠 | 器の枠 | `fuel` の上限 | `heat` の上限 | 種火の衰え | 種火が保つ時間 |
|---|---|---|---|---|---|---|---|---|
| 1 | 焚き火 | 小枝 3 本 | 2 | なし | 30 | 30（炎まで） | -2/tick | 30 分 |
| 2 | 三石のかまど | 焚き火 ＋ 石 3 | 2 | 1 | 30 | 30（炎まで） | -1/tick | 1 時間 |
| 3 | 石囲いの炉 | 三石のかまど ＋ 石 8 | 3 | 2 | 120 | 100（高温まで） | -0.125/tick | 8 時間 |

種火が保つ時間は、`ember` の段の幅（1〜4、2.3 節）を衰える速さで割ったものです。

どちらの枠も同じ `fire` スロットの `cells` に並びます（1.1 節）。枠は焼く物と焼く石のためのもので、
薪は枠を使いません（2.1 節）。

段ごとに増えるものは 1 つずつです。

- **焚き火 → 三石のかまど**: 器を載せる場所ができます。三石が支点になって初めて器を火にかけられる、
  という現実そのままで、器を持たないうちに作っても何も変わりません。
- **三石のかまど → 石囲いの炉**: 種火が翌朝まで生きます。加えて火力の上限が上がって `blaze` に届き、
  積める薪も 4 倍になり、火床が広いので熾火を掻き分けて器を 2 つ置けます。

**梯子の中で `blaze` に届くのは石囲いの炉だけ**ですが、それは段に禁止を書いた結果ではなく、
`heat` の上限が 30 と 100 で違うことの帰結です（2.3 節）。

**土器を焼く炉は、この梯子の外にあります。** 覆い焼きの炉（`src/assets/world-codex/pottery.yaml`）は
粘土から直接築く使い捨ての設備で、石囲いの炉と同じ `heat` の上限を持ちますが、`fire` スロットが土器
しか受けません。逆に石囲いの炉は土器を受けません。**どちらで何が焼けるかは、火力ではなく枠が決めて
います**——焚き火が器を載せられず、三石で `cookware` が増えるのと同じ足し方で、焼成のために新しい
仕組みを持ち込まずに済みます。

**器を持たない段階でも煮炊きはできます。** 焼け石を水へ落とす方法（9 節）は容器に耐火性を要求しない
ので、炉の段ではなく石と時間だけで成立します。三石のかまどが効くのは甕を得てからで、この順序は
仕様ではなく「ヤシの殻を直火にかけると焦げる」という事実から出ています。

## 7. 加熱の受け渡しは、子のcooking_progressへのadd

**炉は、火の中にある子の `cooking_progress` を毎 tick 進めます。量は `heat` の段が決めます。**
料理側が書くのは「未加熱の物が `cooking_progress` を持ち、上限に達したら焼き上がりへ置き換わる」だけで、
炉のことも火のことも知りません。

```yaml
# 炉のheatのstagesが宣言する（4節の薪の減りと同じブロックに並ぶ）
- name: flame
  min: 20
  passives:
    - add:
        self:
          fuel: -1.5
        child:
          cooking_progress: 3
```

```yaml
# 料理側（本書の対象外）が宣言する
cooking_progress:
  value: 0
  range: {min: 0, max: 24}
  on_max:
    spawn: {object: roasted_meat}
    destroy: self
```

これが火と料理の境界です。本書は「熱がどこからどれだけ来るか」までを決め、「何分でどうなるか」は
料理側の `range.max` が持ちます。

**焼き上がるまでの残り時間は、火にかかっている間だけ札の上に出ます**（[`CardView.md`](../ui/CardView.md)
15 節）。出すかどうかを決めるのはこの `add` が今効いているかどうかで、画面側は炉のことを知りません。

**器の中身は、器が自分で加熱します。** 炉の子は器であって、中身は器の子（炉から見れば孫）です。
炉が孫まで手を伸ばすのではなく、器が「炉の上にいるあいだ、自分の中身を加熱する」を自分で持ちます。

```yaml
# 器の側が宣言する
passives:
  - conditions:
      - {subject: ancestor, prop: heat, in_stage: coals}
    add:
      child:
        cooking_progress: 1
  - conditions:
      - {subject: ancestor, prop: heat, in_stage: flame}
    add:
      child:
        cooking_progress: 3
```

器は段ごとに 1 ブロックを並べます（`GameElementDefinition.md` 8.5 節）。炉の側と同じ速さを 2 箇所に
書くことになるので、値の出所は 2.3 節の表 1 つに保ちます。

祖先に `heat` が無ければ条件は偽になる（`GameElementDefinition.md` 14.1 節）ので、**器が炉から降りていることを表す条件は要りません**。
「炉に載っているか」を別に問うと、載っている場所の名前が器の側にも書かれることになります。

### 7.1 直火で焼く物は、そのまま火の中へ入れる

**串のような、焼くためだけの中間の物は挟みません。** 肉はそのまま火の中の枠へ入れます。灰に埋めて
焼くのは実在する最も原始的な焼き方で、道具を何も持たない段階と噛み合います。

串を挟むと、型と工程が 1 つずつ増えるのに**プレイヤーの選択は増えません**。串の材料になる小枝は
いくらでも拾えるので、持っているなら必ず刺すことになるからです。

**見張る理由は、串ではなく焼きすぎが作ります。** `cooking_progress` の上限で焼き上がりへ置き換わった後、
その焼き上がり自身がまた `cooking_progress` を持てば、放っておくと焦げます。串が担うはずだった「火の
そばに居る理由」は、料理側の型が 2 段重なるだけで出ます。

**一度に焼ける量は枠の数が決めます。** 焚き火の枠は 2 つで、石囲いの炉でも 3 つです。薪は枠を
使わない（2.1 節）ので、この数はそのまま「火のそばに並べられる物の数」になります。

串を後から入れるなら、中間素材としてではなく、**1 つの枠に何本も刺せる道具**として入れます。器と
同じ形（`cookware` の枠に入り、自分の子を加熱する）で書けるので、この節の構造は変わりません。

### 7.2 焼き上がりも進行度を持ち、同じ仕組みで焦げる

**進行度を持つのは食料自身で、炉は進めるだけです。** 生肉は自分の `cooking_progress` を進め、上限へ
届いたら自分を破棄して焼けた肉を生みます。焼けた肉も同じ形の `cooking_progress` を持つので、火から
出さずに放っておくと焦げた塊へ変わります。**焦げた塊は進行度を持たず、そこで鎖が終わります。**

生 → 焼き → 焦げ を成り立たせているのは、`spawn` の 3 つの既定の振る舞いです
（`GameElementDefinition.md` 9.4 節）。

- **`into` を書かないので、同じ枠へ置き換わります。** 焼けた肉は火の中に残り、そのまま焼かれ続けます。
  置き換わる先も枠の受け入れを通るので、**鎖に並ぶ型はすべて `roastable` を持ちます**（1.1 節）。
  持たない型が生まれると、その枠には入れずに土地のアイテムへこぼれます。
- **`destroy` を `spawn` より先に書く**ので、位置が空いてから生まれます。
- **生まれた側のプロパティは自分の型の初期値から始まります。** 進行度は引き継がれないので、**焦げるまでの
  猶予は焼けた肉自身の `range.max` が持ちます**。生から焼きより短くすれば、「目を離すと焦げる」が出ます。

**火から出せば進行は止まり、戻りません。** 加熱の `add` が効かなくなるだけなので、半分焼けた肉を
持ち歩き、後で火へ戻せば続きから焼けます。食べ物が冷めて生に戻ることはないので、これが正しい振る舞いです。

**進行度が違っても、同じ型は 1 つのスタックにまとまります**（[`SlotSystem.md`](./SlotSystem.md) 5 節。
まとまる条件は型だけで、プロパティの値は見ません）。同じ炉の中では全員が同じ速さで進むので
順序は崩れず、`stack_order`（同 6 節）に `cooking_progress` を `ascending: false` で置けば、**一番進んだ
ものがスタックの手前に出ます**。焼き上がった 1 個は別の型になるので、そこで自然にスタックが分かれます。

## 8. 雨は火力を削る

**雨天で野ざらしの炉は `heat` が余分に減ります。** 消火を判定する専用の仕組みは持たず、火が死ぬ経路を
3 節と同じ 1 本に保ちます。

```yaml
# 炉の側が宣言する
passives:
  - conditions:
      - {subject: ancestor, prop: sheltered, eq: 0}
      - {subject: ancestor, prop: weather, in: [light_rain, heavy_rain, storm]}
    add:
      self:
        heat: -4
```

種火の冷める速さが炉ごとに違う（6 節）ため、同じ雨でも焚き火は一降りで死に、石囲いの炉は生き延びます。屋根の
下に置けば `sheltered` が 1 になって雨の効果自体が消えます（`ContainerSystem.md` 6 節）。

風は独立したプロパティを持ちません。風を切る効果は石囲いの炉の燃料消費（6 節）に、嵐の強風はこの節の
`heat` の減少に畳んであります。

## 9. 火が与えるもの【確定】

**焼け石を先に実装し、暖と明かりは後へ回します。** どちらも火の連鎖の外にあるので、順に足せます。
焼け石は器が実装済みなので単独で載りますが、暖と明かりは気候の作り替えを伴います（9.2）。

### 9.1 焼け石は、炉から取り出せる唯一の産物【未実装: heat_soak】

**炉に入れた石は熱を溜め、`hot_stone` に置き換わります。** 石は火の中の枠へ入るために `roastable`
（1.1 節）を得ます。`fire` スロットへ入れた石は `heat_soak` を溜め、上限に達すると `hot_stone` へ
置き換わります。炉から出した焼け石は `heat_soak` が減り、0 で普通の石に戻ります。水を張った器へ
落とせば、器に耐火性がなくても中身が沸きます（[`SurvivalItems.md`](../world/SurvivalItems.md) 4 節）。

### 9.2 暖と明かりは、気候の作り替えとセット【未実装: 暖と明かり】

**`ambient_temperature`・`sunlight` は今のところ土地ではなく世界（時刻・天気）のプロパティなので、
このまま炉から寄与させると炉ひとつで島全体が暖まります。** 土地がこの2つを持つ形にする変更が先に要ります。

熱以外に炉が周囲へ与えるものは、いずれも `ancestor`（`GameElementDefinition.md` 8.6 節）への `modify` で
表します。炉が土地に置かれていても小屋の中にあっても、そのプロパティを定義している祖先へ自然に届きます。

- **暖**: `ambient_temperature` を上げます。夜と雨季の冷えに効きます。
- **明かり**: `sunlight` を上げます。夜でも手元の作業ができます。

## 10. 火スキルとの分担

**炉は「今どれだけ燃えているか」を、火スキルは「火を扱えるか」を持ちます**（`Skills.md` 2.2 節）。同じ「低・中・高」
でも見ているものが違います。

| | 決めるもの | 表し方 |
|---|---|---|
| 炉の `heat` の段 | 今この炉で何ができるか | 薪が育て、火が冷ます釣り合い（2.2 節） |
| 火スキルの段 | 着火が成功するか、種火を保てるか、高温を出せるか | 着火の `pick` の重み、着火の解放条件 |

スキルの段が効くのは火起こしの `pick` の重み（3.1 節）だけです。**火がついた後の火力にスキルは
効きません**——熟練者の焚き火が同じ薪でより熱くなることはないためです。「高温を出せる」は、炉を
石で囲めるようになること（5 節）として現れます。

## 11. 未決事項・今後の検討課題

- 着火の成否（3.1 節）に天気とスキルの段が効いていない。今は火口ごとの固定の重みだけで、雨の日でも
  同じ確率で火がつく
- 火が燃え移ること（延焼）。現状は炉の外へ火が出る経路を持たない
- 煙。燻製による保存、虫除け、遠くから見えることのいずれを表すか
- 濡れた燃料。雨ざらしの薪が火起こしを妨げるか、燃料の `fuel` を減らす形で表すか
- 炉そのものの劣化。雨で崩れるか、放置しても残り続けるか
- `fuel` のバーと `heat` のシンボルを、カードのどこに出すか
- 器の枠（1.1 節）に「ここは器を置く枠」と見せるかどうか。空き枠へ受け入れる型を薄く敷く仕組み
  （`EmptyCard`）は既にあるが、枠ごとの受け入れ型を画面へ渡しているのは製作中オブジェクトの材料欄
  だけで、普通の入れ物は `SlotDef` の枠ごとの `accept` を見ていない。受け入れがタグの場合に何の絵を
  出すかも決まっていない
- 焼け石の `heat_soak` の減り方が、器の中と外で変わるか（湯へ落とせば急に冷める）
- 段上げで火が消えること（5 節）を、種火だけ引き継ぐ形に変えるかどうか
- 燃料の投入・取り出しにかかる時間（`put_in`、`GameElementDefinition.md` 7.10 節）を持たせるか
- 恒久的な窯を上位の焼成設備として足すか。現実の順序は「覆い焼き → そこでレンガを焼く → 恒久窯」
  なので、足すならこの順序ごと足すことになる（`src/assets/world-codex/pottery.yaml`）。窯にするなら、
  5.1 節が退けた大きな石を導入する最初の理由にもなる
