# セーブデータ管理

[スタート画面・セーブ選択画面](../ui/StartScreen.md)のモックを作る過程で、単なる画面設計を
超えてセーブデータの持ち方自体に関わる決定が必要になったため、ここに集約する。
画面構成そのものは [StartScreen.md](../ui/StartScreen.md) を参照。

## 保存先

ブラウザの `localStorage` を採用する。本作はサーバーを持たないブラウザ単体のゲームであり
（`package.json` の依存に見るとおり Phaser + Vite の静的ビルドのみ）、複数端末間の同期や
クラウド保存は現時点でスコープ外（詳細は「スコープ外」節）。

- キーは `unmapped-island:save:{slotIndex}`（`slotIndex` は `0`〜`3`）。スロット数は4固定のため、
  スロット一覧を得るための別キー（インデックス／サマリー一覧）は持たない。4つのキーを
  直接読み、値が存在しない（`null`）スロットを空きスロットとして扱う。
- 一覧表示専用のサマリーをスロット本体と別に持たない。持ってしまうと「セーブ本体を更新したら
  サマリーも更新する」という手順を呼び出し側が覚える必要が生じ、
  [CLAUDE.md のカプセル化方針](../../CLAUDE.md)が禁じる状態になる。スロット一覧画面は
  4件のセーブ本体を直接読んで表示に必要な項目（後述）を取り出すだけで十分に軽量なため、
  サマリーの複製を持つ動機がない。

## セーブデータのスキーマ

セーブデータ本体は概ね次の項目を持つ JSON とする（実際のワールド状態のスキーマは別途検討）。

| フィールド | 型 | 内容 |
|---|---|---|
| `schemaVersion` | number | セーブデータの形式バージョン。将来のフィールド追加・変更をマイグレーションで吸収するための起点（マイグレーション処理自体は本ドキュメントの対象外）。 |
| `islandName` | string | 新規ゲーム作成時に入力した島の名前。1〜20文字。 |
| `seed` | number | 乱数シード。地形生成が消費する `Pcg32` の実装（`seed >>> 0`）に合わせ、`0` 以上 `2^32 - 1` 以下の符号なし32bit整数の範囲で扱う（詳細は後述）。 |
| `characterId` | string | 選択したキャラクターを識別するID。現状のドメインモデルは1種類のキャラクター（シングルトン）しか持たないため、当面は固定値になる（詳細は後述）。 |
| `createdAt` | number | 作成日時（UNIX時間・ミリ秒）。 |
| `elapsedDays` | number | 生存日数。ワールドの経過ゲーム内時間から求まる値で、セーブスロット一覧の表示のためだけに
別途複製した値ではなく、セーブ本体（ワールド状態）が持つ経過時間をそのまま読む。 |
| `pinnedStatuses` | string[] | ユーザが固定表示にしたステータス（プロパティの識別子）。安全域でもステータスエリアへ出し続ける（[`ScreenLayout.md`](../ui/ScreenLayout.md) ステータスエリア節）。プレイ中に切り替えるたびスロットへ書き戻す。 |

`elapsedDays` を「表示専用の複製」にしないのは、上記のサマリー非保持の方針と同じ理由による
（更新のたびに複数箇所を同期させる手順を呼び出し側に持たせない）。

`pinnedStatuses` は形式バージョン 2 で足したフィールドで、それを持たない形式バージョン 1 のセーブは
「固定表示なし」として読む（欠けたフィールドの補完は読み出しの1か所、`SaveData.toSaveData` に集める）。

## 新規ゲーム作成時の入力とランダム生成

- **島の名前**: 自由入力（1〜20文字、空文字は不可）。ランダムボタンは形容語＋名詞の2語を
  組み合わせて生成する（例: 「霧深い」＋「孤島」）。一意性は保証しない
  （スロットごとの識別は名前ではなく `slotIndex` で行うため、島名の重複を禁止する理由がない）。
- **乱数シード**: 数字のみの自由入力、またはランダムボタンで生成する。`NewGame.start`
  （`src/domain/generation/NewGame.ts`）はすでに `seed: number` を受け取り、地形生成
  （`TerrainGenerator.generate` → `Pcg32`）が「同じシード→同じ島」を決定的に再現する。
  `Pcg32` のコンストラクタは `seed >>> 0` で符号なし32bit値として消費するため、シードの
  値域は `0` 以上 `2^32 - 1`（4294967295）以下として扱う。`WorldSession.rng`（pick抽選・
  初期値ロール用）にも同じシードから作った決定的な実装（`seededRng`、
  `src/domain/runtime/Rng.ts`）を渡すため、開始状態は地形レイアウトを含めてシードだけで決まる。
  地形生成とは別インスタンスの `Pcg32` を使うので、pick抽選の消費順序は地形に影響しない。
- **キャラクター選択**: `characters.yaml` の `character` object_def は `singleton: true`
  （常に1体だけ存在する前提）であり、現状のドメインモデルには複数キャラクターから選ぶ仕組みが
  まだ存在しない。本モックのキャラクター選択は、複数キャラクターに対応する将来のドメインモデルを
  見越した画面上の入り口であり、実際に選択肢を出し分けるにはキャラクター定義自体を
  シングルトンから複数選択可能な形へ拡張する作業が別途必要になる（本ドキュメントの対象外）。

## ワールド状態の保存

ワールド状態（`WorldObject` のツリー）そのものを保存する仕組みはまだ無い。プレイ画面
（`src/game/PlayScene.ts`）は、新規作成でも既存スロットを開いた場合でも、セーブデータの
`seed` から世界を作り直して表示する。上記のとおり開始状態はシードだけで決まるため、
同じスロットを開き直せば常に同じ島・同じ漂着地になる（進行の保存は今後の課題）。

## テスト用シナリオ

決まった開始状態からすぐ動作を試すための仕組み。タイトル画面の「テスト用シナリオ」から選ぶと、
セーブ選択を飛ばしてその状態でプレイ画面に入る。セーブスロットは使わず、書き戻しもしない。

シナリオは `src/scenarios/<名前>.yaml` に置く。コード側への登録は要らず、一覧は
`import.meta.glob` がビルド時に作る（`public/` 配下では実行時に名前を列挙できないため、
`src/` に置いてバンドルへ含める）。同梱シナリオが1つも無ければ、タイトル画面のボタンも出ない。

ワールド状態を保存する仕組みが無い（前節）ため、シナリオは状態そのものではなく
**シードと、その後に行う配置の手順**を持つ。つまり「シードで世界を作り直し、object_defを
生成してスロットへ入れる」だけで、保存側の課題（インスタンスIDの参照、passiveの再登録、
乱数の位置）を一切踏まない。将来ロードを実装するときは、この配置手順をそのまま使える。

```yaml
title: 編み籠と石            # 一覧に出す表示名（省略するとシナリオ名がそのまま出る）
seed: 3
player:
  hand: [woven_basket]      # キャラクターのhandスロットへ、並べた順に入れる
  equipment: []             # 同じ名前が並んだ数だけ作られる
  props:
    satiety: 1200           # プロパティの上書き（実体値）
location:
  type: jungle              # 開始地点にする土地のobject_def（省略すると通常の漂着地）
  items: [stone x100, thick_branch]     # `x個数` で同じものをまとめて指定できる（1〜1000）
  fixtures: []
```

地形の種類はシードだけでは選べない（漂着地は砂浜優先で決まる）ため、特定の土地から試したい
シナリオは `location.type` で開始地点を指定する。その土地がシードの島に無ければエラーにする。

配置は通常のスロット移動（`WorldObject.moveToSlot`）そのもので、シナリオ専用の抜け道は
持たない。受け入れられない指定（手持ちの上限超過、綴り違いのobject_def）はその場でエラーに
する——黙って落とすと、試したかった状態と違う状態でゲームが始まってしまうため。
同梱シナリオが実際に適用できることは `tests/scenario/scenario.test.ts` が担保する。選択画面が
読み込みの失敗を扱わないのは、これが根拠。

読み込みは `src/scenario/Scenario.ts`、選択画面は `src/game/ScenarioSelectScene.ts`。

## スロットの空き・削除

- 空き判定はキーの不在（`localStorage.getItem` が `null`）のみで行い、別途「空きフラグ」は持たない。
- 削除は該当スロットのキーを消すだけで、他スロットに影響しない。
- 削除は確認操作を必須とする（画面設計は [StartScreen.md](../ui/StartScreen.md) 参照）。
  誤タップで進行データを失う事故を防ぐための最低限の防御であり、取り消し（アンドゥ）は
  スコープ外（「スコープ外」節）。

## スコープ外

- クラウド同期・複数端末間の共有
- セーブデータの暗号化・改ざん防止（ローカル単体プレイのみを想定するため）
- 削除の取り消し（アンドゥ）
- スキーマバージョン間のマイグレーション処理そのものの実装（`schemaVersion` フィールドの用意まで）
