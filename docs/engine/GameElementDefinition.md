# WorldCodex YAML 文法リファレンス

## 1. 位置づけ

本ドキュメントは、`WorldCodex`（ゲーム内のあらゆる要素を定義する YAML）の**文法そのもの**を体系的にまとめた、唯一の
リファレンスです。`traits`・`object_defs`・`props`・`stages`・`slots`・`interactions`・`trigger`・`recipes`・`passives`・`active`・
`modify`・`add`・`destroy`・`spawn`・`move`・`pick`・`duration`・`conditions` など、YAML 上のキーワードの意味と
書き方はすべてここに集約します。

本書が定めるのは**文法**だけです。その文法で**具体的なゲーム内容をどう表現するか**は、以下の別ドキュメントを
参照してください。

- [`RecipeSystem.md`](./RecipeSystem.md) — アイテムの製作
- [`SlotSystem.md`](./SlotSystem.md) — スロットの実行時実装（固定位置・受け入れ判定・スタック）
- [`ContainerSystem.md`](./ContainerSystem.md) — コンテナの容量・重さ・保護
- [`LiquidContainerSystem.md`](./LiquidContainerSystem.md) — 液体容器（量・飲用・注ぎ移し・蒸発・降雨）
- [`ActionSystem.md`](./ActionSystem.md) — 操作の実行時の設計（`interactions` の実行時の仕組み）
- [`ClimateSystem.md`](./ClimateSystem.md) — 季節・天候
- [`TerrainGeneration.md`](./TerrainGeneration.md) — 島の地形生成（軸・LocationTypeマッチング・パスネットワーク生成のアルゴリズム）
- [`ExplorationSystem.md`](./ExplorationSystem.md) — 生成された土地の構造と挙動（スロット・探索・道の発見と移動）

形式的なスキーマ定義（[JSON Schema](https://json-schema.org/)）は [`WorldCodex.schema.json`](./WorldCodex.schema.json)
（メタ情報は [`WorldCodexSchema.md`](./WorldCodexSchema.md)）を参照してください。機械的な検証はスキーマ側が担います。

本書は確定した文法のみを記述します。未決定の論点は 17 節にまとめています。

**次の 1 つは実装より先行しています**（実装と他の文書はまだ追いついていません）。

- **`weight`・`duration` から積を落としたこと**（10.2 節・11.3 節）。**`times:` は実装・スキーマ・実データに
  まだ在ります**（`src/loader/parseActiveEffects.ts`・`docs/engine/WorldCodex.schema.json`・
  `src/assets/world-codex/locations.yaml`）。10.2 節の「この二択より豊かな書き方はありません」は決まった文法の
  話で、**残っている `times:` はデータの誤りではなく残作業**です。

## 2. 設計原則

- **統一的な実行エンジン**: あらゆる概念を共通の枠組み・単一の汎用エンジンで表現し、概念ごとの専用ロジックを増やしません。
- **tick 駆動**: 時間経過にともなう変化は、すべて tick ごとの独立変数への加減算（`add`）で表現します。
- **範囲による状態決定**: 数値プロパティの値域から状態（`stages`）を決定する仕組みを型定義レベルで共通化します。
- **宣言は、その組み合わせを知っている側に書く**: 影響を与える側とは限りません。ナイフは自分が何を切れるかを
  知らず、材料は自分が切れることを知っているので、宣言は材料に置きます（12.3 節）。世界は自分の下に何がぶら下がるかを
  知らないので、明るさは土地の側が `base`（6.5 節）で見に行きます。**押す（`modify`）か引く（`base`・参照）かは、
  知識がどちら側に在るかで決まる従属物**です。どちらも相手を知らないときは、両方が知っている共通の親のプロパティを
  経由します（焚き火とキャラクタは互いを知らず、どちらも場を知っているので `ambient_temperature` があります）。
  **ただし操作の瞬間だけ在る関係（11.5 節）は経由しません**——環境へ写すと、関係が終わっても残り、同じ立場の者が
  複数居れば重なります。
- **可逆な寄与を合成する器は 1 つだけ**: 値を合わせる場所は `modify`（8.3 節）と `base`（6.5 節）で、どちらも
  加算です。`weight`（10.2 節）・`duration`（11.3 節）のような「その場で決まる数値」は**リテラルか参照 1 つ**しか
  取れず、式を書けません。器を増やすと、`range`（6.3 節）も段（6.4 節）も付いてこない 2 つ目の合成先ができます。
- **数えるものはオブジェクト、量はプロパティ**: 1つずつ数えて1つずつ手を加えられるもの（傷・道具）は
  `object_def` にし、合計しか意味を持たないもの（痛み・意識）は `props` にします。判定の基準と境界の例は
  [`InjurySystem.md`](./InjurySystem.md) 4 節。
- **ハードコードしない／ファイル追加だけで拡張できる**: 挙動は YAML 定義に置き、パック作成者がファイル追加だけで新要素を
  導入・上書きできるようにします。

## 3. ファイル構造とロード

### 3.1 ルート構造

ファイル全体が 1 つの `WorldCodex` を表します。専用のルートキーは置かず、`object_defs`・`traits` と、
プロパティのカテゴリを宣言する `property_tags`（6.7 節）をトップレベルキーとして持ちます。

ほかに、画面の都合だけを持つルートキーが 2 つあります。`recipe_categories` は、レシピ一覧の棚に使う
タグ（4.1 節）を**優先順位の順に**並べた列で、意味は [`Windows.md`](../ui/Windows.md) 9.2 節が持ちます。
`card_filters` は、フィルターバーのボタンを**並べる順に**挙げた列で、要素は `id`（そのままアイコンの
名前）と、絵がまだ無いときに置く絵文字 `icon`、そのボタンが指すタグの列 `tags` を持ちます。意味は
[`ScreenLayout.md`](../ui/ScreenLayout.md) 8.1.3 節が持ちます。**どちらも分類のための語彙を新設せず、
既にあるタグを指すだけです。**
その世界の約束を書く `required_props`（4.2 節）と、製作中オブジェクトが完成品から引き継ぐタグを挙げる
`in_progress_tags`（[`RecipeSystem.md`](./RecipeSystem.md) 5 節）もルートキーです。
地形生成の `axes`・`location_types`・`generation_scopes` は
[`TerrainGeneration.md`](./TerrainGeneration.md) が持ちます。

### 3.2 命名規則

- 構造キーワード（`props`、`traits`、`interactions` など）・型名・プロパティ名は、すべて **snake_case** で統一します。
- 識別子（型名・プロパティ名・トレイト名・アクション名・スロット名・タグ名に共通）は次の正規表現に従います。

  ```
  ^[a-z][a-z0-9_]*$
  ```

### 3.3 ロードとバリデーション

- YAML ファイルは所定のディレクトリ以下のすべてのファイルが自動的に読み込まれます。ゲーム本体の定義とアセットパックの定義は
  別々に管理します（[`AssetPack.md`](./AssetPack.md)）。
- マッピングキーの重複は、ローダーの**厳格モード**でエラーにします（多くの YAML パーサは重複キーを後勝ちで
  黙って上書きするため）。
- ロード後に別途**バリデーションステップ**を設けます。
- 同じ ID を持つ定義が複数のファイルに存在する場合、ファイル・ディレクトリ・読み込みのタイミングを問わず
  **常にエラー**とします（意図しない上書き事故の防止のため、後勝ちの上書き規則は持ちません）。アセットパックによる
  既存定義の意図的な差し替えは、専用の patch 文法で表現します（3.4節）。

### 3.4 patch_object_defs（既存の型への変更）

既に読み込まれた `object_def` を変更する唯一の口です。主に使うのはアセットパック
（[`AssetPack.md`](./AssetPack.md)）で、同梱の土地の探索結果に自分のアイテムを足す、といった
変更を書きます。同梱のYAMLでも同じ文法が使えます。

トップレベルの `patch_object_defs` に、**操作を1つずつ並べます**。

```yaml
patch_object_defs:
  - append: sandy_beach.actions.explore.pick
    value:
      weight: 2
      spawn: {object: healing_potion, into: self}
```

**動詞がパスの読み方を決めます。**

| 動詞 | パスが指すもの | 前提 | 材料 |
|---|---|---|---|
| `add` | 新しく作る**キー** | そのキーが**無い** | `value` |
| `append` | **配列** | その配列が**ある** | `value`（要素1つ） |
| `set` | 既にある値、または配列の要素 | **ある** | `value`（配列の要素なら `where` も） |
| `remove` | 既にあるキー、または配列の要素 | **ある** | （配列の要素なら `where`） |

`add` と `append` を分けているのは、1つの動詞にまとめると**配列名の打ち間違いが「新しいキーの
作成」として通ってしまう**からです（`...explore.picks` は `explore` に存在しないキーなので、
`add` としては成立してしまう）。分けておけば、その場で「配列がありません」と言えます。

パスはドット区切りで、先頭が `object_def` の識別子です。識別子に `.` は入らない（3.2節）ので
曖昧になりません。

### 3.4.1 配列の要素は、位置ではなく中身で指す

`set` と `remove` が配列の要素を指すときは `where` を書きます。**当てはまる要素が0個でも2個以上でも
エラー**です。

```yaml
patch_object_defs:
  - remove: sandy_beach.actions.explore.pick
    where: {spawn: {object: woven_basket, into: self}}
```

添字（`pick[2]`）を使わないのは、別のパックが1つ足しただけで同じ添字が別の要素を指すうえ、
それが黙って成功するからです。`where` は**書いたキーだけを見る部分一致**で、書いていないキーは
何であってもかまいません（配列だけは、書いたとおりの並びと個数を求めます）。

配列の要素の**一部だけ**を変えることはできません。要素を丸ごと書き直します。

### 3.4.2 適用の順序と、失敗したとき

- 適用は**すべてのファイルを読み終えてから**、読み込み順に行います。当たる先が揃っている必要が
  あるためです。trait の合成（5節）より前なので、`traits` の一覧そのものも変更できます。
- **同じ場所を2つのpatchが差し替えることはできません。先に読んだ方が残ります。** 後勝ちにすると、
  読み込み順という見えない要因で結果が変わり、勝った側も自分が上書きしたことを知りません。
- 前提が満たされない操作（消そうとしたものが無い、足そうとしたキーが既にある等）は、**同梱の
  YAMLならロードエラー**、**アセットパックならその1操作だけを捨てて記録**します
  （[`AssetPack.md`](./AssetPack.md) 6.1節）。
- `object_def` そのものの新設と削除はできません。新しい型は `object_defs` に書きます。削除を許すと、
  他の定義から参照されている型が消え、壊れ方が patch から遠い場所に出ます。

### 3.5 ロード時に生成される型

**エンジンがロード時に生成する型は、いくつかの軸の値の組で決まり、識別子はその組から組み立てた結果です。**
著者もパック作成者もこの識別子を書かず、効果からも名指ししません（9.9 節）。

生成器は 2 つあります。**製作中オブジェクト**（13 節、[`RecipeSystem.md`](./RecipeSystem.md) 1 節）は
素の型が完成品・軸が `recipe` で、著者は何も書きません。**変種**（`variation_axes`、3.5.1 節）は
型自身が軸を宣言し、その軸の値ごとに型が生まれます——中身入りの容器
（[`LiquidContainerSystem.md`](./LiquidContainerSystem.md)）がこれにあたります。

- **軸を決めるのは生成器です。** 軸の名前も、どの組に型が存在するかも、生成する側（レシピなら 13 節の
  宣言を読む側）が決めます。エンジンが持つのは `軸の値の組 ↔ 生成された型` の対応だけで、軸の名前が
  何を意味するかは知りません。
- **組み立てなかった座標は、その型が無いということです。** そこを指す操作は解決に失敗し、実行できなく
  なります（9.9 節）。「この入れ物にはこれを入れられない」を、条件ではなく型の有無で表せます。
- 地形生成の `axes`（16 節）とは別の話です。あちらは土地の性質を表す座標で、こちらは型の生成規則です。

表は `WorldCodex.generatedTypes` が持ち、**両方向に引けます**——生成型からその座標へも、座標からそこに
居る型へも。**どの軸かで扱いを分けません**——作りかけも中身入りも「素の型の変種」で、違うのは軸の
名前と、その名前に紐づく書式（[`Localization.md`](./Localization.md) variation_names節）だけです。

### 3.5.1 variation_axes（変種を並べる軸）

**`variation_axes` は、その型の変種がどの軸で並ぶかを宣言します。** 軸の名前は著者が付け、値に
なれる型は `of`（`accept`・`with` と同じ型指定、4.1 節）が選びます。

```yaml
object_defs:
  jar:
    traits: [liquid_container, narrow_open_container]
    variation_axes:
      content: {of: {tag: liquid}}
```

**変種は「素の型に、軸の値の型が持つ `traits` を配ったもの」です。** props・tags・actions・
combinations・passives の合成は trait の mixin（5 節）がそのまま行うので、生成に固有の合成規則は
ありません。**軸の値になれるのは `traits` だけを宣言した型**で、自前のメンバーを持つ型を指すと
ロードエラーになります——配る仕組みが mixin そのものである以上、mixin に載らない宣言は配れません。

**宣言は `of` だけです。** 変種が素の型と何が違うかは、配られた trait だけが決めます——**この仕組みは
何を配っているのかを知りません**。素の型ごとに違う数値（容器ごとの容量）も、素の型が自分の `props` と
して持てば変種へそのまま引き継がれます。

**素の型へ戻る道も宣言の側にあります。** 量が尽きたら空へ戻る、という規則は `on_min`（6.3 節）へ
`become: {<軸>: none}` を書いて表します——**「何かが尽きたら変種が変わる」を仕組みの側が想定しては
いけません**。

`variation_axes` と `recipes` は変種へ写しません。**変種の変種は作らず**、作れるのは素の型のほうです
（空の容器を作ってから中身を入れる）。

## 4. object_defs（型定義）

型定義は `object_defs` の下に、識別子を**キーとして**表現します（値ではありません）。

```yaml
object_defs:
  stone:
    props:
      weight:
        value: 1000
```

### 4.1 tags

`tags` に文字列の配列を書くと、その `object_def` にタグを付けられます。`traits`（5節）も同じ `tags` フィールドを
持て、その trait を参照するあらゆる `object_def` へタグが合成されます。tags は単純な集合なので、trait 間・
trait と object_def 自身の間で同じタグが重複しても衝突エラーにはなりません。

```yaml
traits:
  location:
    tags: [location]
object_defs:
  forest:
    traits: [location]   # traitのtagsが合成され、locationタグを持つ
  beach:
    tags: [location]     # locationトレイトを一切参照しなくても、直接同じタグを宣言できる
```

ここでいうタグは `object_def` に付くもので、プロパティに付けるタグ（6.7 節）とは別の名前空間です。

**「どの型が当てはまるか」を書く場所——枠の `accept`（7.2 節）と重ねる操作の相手の指定（12.1 節）——は、
`{tag: ...}` と `{object: ...}` の二択で同じ形をしています。** タグで指せばそのタグを持つあらゆる型
（パック追加分も含む）が、`object_defs` の id で指せばまさにその型だけが当てはまります。**trait 名では
どちらの形でもマッチングしません**（trait は合成後に消える存在であり、外部から参照すべきではないため）。
`beach` の例のように trait を経由せず直接 `tags` を書いても、同じタグを共有していれば同じ扱いを受けます。

どちらで書くかは、**後から仲間が増える余地があるか**で決めます。刃物・燃料のように「その役ができる物」の
集まりならタグ、火種（`burning_tinder`）のように種類を増やす予定がその型そのものに無いなら id です。
id で書けば、そのためだけの単発タグを新設せずに済みます。

### 4.2 required_props（タグが要求するプロパティ）

ルートキー `required_props` は、**タグ名 → そのタグを持つ型が宣言していなければならないプロパティ名の列**です。
1 つでも欠けている型があればロード時エラーになります。

```yaml
required_props:
  item: [weight]      # 持ち歩ける物は必ず重さを名乗る
  character: [load]   # 担ぐ者は必ず負荷を受け取る口を持つ
```

**タグは「その物が何であるか」を言うので、名乗った以上そこに要る値は揃っているはず**——という、
その世界の約束をそのまま書きます。エンジンは何が要るかを知らず、要求を 1 つも書かない世界も成立します。

宣言漏れが静かに効く値ほど、ここへ書く価値があります。重さを書き忘れた道具は 0g として無限に持ち運べ、
負荷を書き忘れたキャラクタは何を担いでも平気になります——どちらもエラーにはならず、ただ遊びが壊れます。

同じタグを複数のファイルが書けます（パックが自分のタグの約束を足す）。後から現れた宣言は上書きではなく
合流し、要求は増える方向にだけ動きます。

### 4.3 art（1枚の絵を複数の型で共有する）

型は **`art`** で「カードに出す絵の名前」を名乗れます。値は `src/assets/objects/<この値>.png` を指し
（[`CardView.md`](../ui/CardView.md) 5 節）、**宣言しなければ型の識別子そのもの**です。

```yaml
traits:
  sea_route:
    art: sea_route      # この trait を持つ16本の航路が、1枚の sea_route.png を共有する
```

**同じ絵しか持ちようがない型の群れのためのものです。** 16 本の航路（[`Voyage.md`](../world/Voyage.md)
3 節）は行き先の 1 行しか違わないので、行き先の数だけ絵を描いても同じ絵が 16 枚並ぶだけになります。

- **名乗るのは型の側です。** 「この絵はどの型のものか」をコードや絵の側の一覧で持つと、絵を 1 枚足す
  たびに登録が要ります。型が自分の絵の名前を言えば、規約はファイル名だけで済みます（`objectArt.ts`）。
- `stack_order`（7.6 節）・`art_by_stage`（6.4 節）と同じ規約で、**trait 側の宣言も参照できます**
  （自分自身の指定を優先し、無ければちょうど 1 つの trait の指定を使う）。共有したい群れは trait で
  括られていることが多いので、実際に書くのは trait 側の 1 行だけになります。
- 絵の名前は object_def の識別子と同じ命名規則（3.2 節）に従います。**識別子と衝突してかまいません**
  ——ある型の絵を別の型が名指しで借りる形になるだけです。

## 5. traits（mixin）

複数の `object_def` で共有するプロパティ・アクション等を `traits` として定義します。

- **多重継承は禁止**: trait が他の trait を参照することはできません（1 階層のみ）。
- **プロパティ衝突はエラー**: 複数の trait が同名プロパティを宣言していた場合、暗黙の優先順位で解決せずエラーとします。
- **値の扱い**:
  - trait 側で `value` を持たないプロパティ = object_def 側で値を与えることが必須
  - trait 側で `value` を持つプロパティ = デフォルト値。object_def 側で省略可、上書きも可
  - object_def 側で一部属性（例: `value`）だけを上書きした場合、残りの属性（`unit` など）は trait 側の値を引き継ぐ
  - 例外として `props` の `tags`（6.7 節）だけは上書きせず足し合わせる

```yaml
traits:
  perishable:
    props:
      shelf_life:      # valueなし→継承先で必須
        unit: days
      decay_rate:
        value: {min: 1, max: 3}

object_defs:
  apple:
    traits: [perishable]
    props:
      shelf_life:
        value: 7
```

`props`（6 節）以外にも、`interactions`・`recipes`・`slots`・`passives`・`tags`（4.1 節）を trait 経由で
まとめて配布できます。`value` を持たないプロパティは、5 節のルール通り空のマッピング（`{}`）として表現します。

## 6. props（プロパティ）

数値プロパティの値は**有限の数値**で、`value`/`range`/`stages`/`modify`/`add`/`transfer` など、
数値を扱うすべての場所で**小数を書けます**（値域は 32bit 整数の幅、精度は倍精度）。細かい傾きを
「1 単位を何分割するか」で表す必要はありません——`-0.35/tick` と直接書けます。

**ただし小数を持てるのは連続量だけです。** 数えるもの（`tick` や残り時間のようにプロパティ自身が刻みを
持つもの）と、シンボル型（6.6 節）は整数で書きます。エンジンは `stages` の `eq` を完全一致で判定するため、
**「最小の刻みが 1」であることに依存した書き方は、整数で書くプロパティにだけ使えます**。

### 6.0 数値のスケール規約

数値プロパティは次の 2 クラスのいずれかに属し、書かれている数値の読み方はクラスで決まります。

| クラス | 基準 | 値の読み方 | 例 |
|---|---|---|---|
| **時間を数えるもの** | **1 = 1 tick** | 値がそのまま tick 数 | `tick`・`satiety`・`hydration`・`body_fat`・`wakefulness`・各栄養・`severity`・`durability`・`atmospheric_moisture`・`season_remaining`・`thermal_level` |
| **現実の単位に載るもの** | **1 = 1mL / 1 = 1g / 1 = 1g/mL / 1 = 1℃** | 値がそのまま実単位 | `volume`・`weight`・`density`・`ambient_temperature` |

**境界が「人や物の状態か、物の物理量か」と一致します。** 人の状態はすべて「基準のレートで何 tick 保つか」
として読め、物の物理量だけが現実の単位に載ります。

```yaml
# 満腹は1日（96 tick）で空になる
satiety:
  value: 96
  range: {min: 0, max: 96}
  passives:
    - add: {self: {satiety: -1}}   # 基準レート = 1/tick
```

時間を数えるクラスでは、`range.max` が「基準レートで何 tick 保つか」を直接表します。「基準レート」が何かは
プロパティごとに宣言側が決めます（`satiety` なら消費、`atmospheric_moisture` なら雨季の上昇）。基準から外れる
レート（雨季以外の季節、素材ごとの劣化速度）は小数で書きます。

物理量のクラスは、単位が互いに噛み合っている点が要です。`weight = volume × density` が換算定数なしで
成立します（[`ContainerSystem.md`](./ContainerSystem.md) 1 節）。**この 2 つのクラスの間の換算は、
必要な場所が宣言として持ちます**——飲用が水分へどれだけ寄与するかは `transfer` の `amount`/`to_amount`
（9.5 節）が持ち、エンジンは換算率を知りません。

比率として読むものは、どちらのクラスにも属しません（`load_rate` は率、`pick` の `weight` は
正規化される相対値、`*_weight` は天気候補の相対重み）。

### 6.1 固定値

最も単純な形は、`value` に固定値を 1 つ持つだけの形です（4 節の `stone.props.weight` を参照）。

### 6.2 範囲値（生成時に1回ロール）

固定値の代わりに `{min, max}` の範囲を `value` に持たせると、**インスタンスの生成（spawn）時に 1 回だけ、
範囲内の一様乱数で初期値をロール**します。以後は固定値と同じ扱いで、tick ごとの再ロールは行いません
（`PropertyDef.rollInitialValue` 参照）。

```yaml
props:
  max_durability:
    value: {min: 80, max: 120}   # 個体ごとに生成時1回だけロールされる
```

### 6.3 range / on_max / on_min（周回・上下限）

上限・下限に達したら折り返す（あるいは繰り上げる）プロパティは、`range`（取りうる上下限）と、`on_max`
（上限到達時の挙動）・`on_min`（下限到達時の挙動、`on_max` の下限側の鏡像）を持たせます。`value` の
`{min, max}`（6.2 節、生成時に 1 回ロールする初期値の範囲）とは別の仕組みです。

**`on_max`/`on_min` は、値が境界に達した瞬間に発火します**（`>= range.max` / `<= range.min`）。境界は
「そこに居てはいけない値」ではなく「そこに着いたら何かが起きる値」で、**尽きた・満ちたことそのものへの
反応**をここに書きます。`transfer`（9.5 節）は `range.min` を「出せる量の床」と見るので、在庫を出し切る
操作は下限を割りません——「注ぎ切った」「飲み干した」に反応できるのは、境界そのもので発火するからです。

`on_max`/`on_min` の中身は `active`（9 節）と同じ型の内容で、`pick`（10 節）も他の動詞と
並べて書けます。**発火するのは時間の側なので、この場所には操作者が居ません**——対象に指せるのは
`self`・`parent`・`ancestor` で、操作の関係の役（`agent`/`instrument`/`patient`）はロード時にエラーになります
（11.5 節「役を書ける場所」）。

#### 実体値と実効値、そして `range` が誰の端か

プロパティの値には2つの読み方があります。

- **実体値**: 書き込みで**不可逆に**積み上がったもの。動かすのは `set`/`add`（9 節）と、`passives` の
  `add` による毎 tick の積分（8.4 節）だけです。
- **実効値**: 実体値に**可逆な**寄与——`modify`（8.3 節）・`base`（6.5 節）・入れ物の中身から受ける
  `weight`/`load`——を重ね、`range` で切ったもの。段（6.4 節）・ゲージ・`conditions`（14 節）が読むのは
  こちらです。

**`on_max`/`on_min` が見るのは実体値です。** 端のイベントは「不可逆に動いた値が端に着いた瞬間」への
反応なので、可逆な寄与では起こりません。

**エンジンは実体値をクランプしません。** 値を範囲へ戻しているのは既定の `on_max`/`on_min`
（自分自身を境界へ `set` する）であって、暗黙の丸めではありません。だから著者がそれを上書きすれば、
実体値は範囲の外へ出られます——`on_min: {}` と書くと範囲外の値をそのまま許容できるのはこのためです。

`become`（9.9 節）で型が変わり、運んだ値が**新しい型の `range` に収まらない**場合も丸めません。
読むときに実効値の側で切られるからです。その場では `on_max`/`on_min` は起きません（器が変わっただけで、
値は動いていないため）——**次にその値へ書き込みが起きたときに、新しい型の宣言に従って発火します**。

**実効値が実体値と食い違いうるプロパティには、`on_max`/`on_min` を書けません**（ロード時エラー）。
`modify` の対象になっている・`base` を持つ・`weight`/`load` である、のいずれかが当てはまる場合です。
書けてしまうと「ゲージは満ちているのに何も起きない」「まだ空でないのに尽きる」が起こりえますが、
**そのときに何が正しいかをまだ決めていません**。

- どちらも、`range` が定義されていて著者が明示的に書かなかった場合、**自分自身を境界値（`on_max` なら
  `range.max`、`on_min` なら `range.min`）へ `set` する**既定の内容が自動的に補われます。`range` を書く
  だけで上下限のクランプになり、明示するのは繰り上げ・繰り下げのような特別な挙動が要る場合だけです。
- **空のmappingを書く（`on_min: {}`）と、「宣言だけして何もしない」**、つまり既定のクランプを打ち消して
  範囲外の値をそのまま許容する、という意味になります。
- **周期を持つ量は、折り返す先ではなく折り返す点を `max` に書きます。** 1 日 24 時間の `hour` は
  `{min: 0, max: 24}` で、24 に達した瞬間 `on_max` が 0 へ戻します。見た目には 23 の次が 0 ですが、
  「一瞬 24 になってから戻る」のが実際の動きです。

```yaml
props:
  minute_of_day:
    value: 0
    range: {min: 0, max: 1440}
    on_max:
      add:
        self:
          minute_of_day: -1440   # 1440に達したら自分を1440引いて0に戻す
          day: 1                 # 同時にdayへ+1する
  # on_minを省略しているため、下限(0)に達した場合は既定の
  # `set: {self: {minute_of_day: 0}}` が自動的に適用される（単純なクランプ）。

  hp:
    value: 100
    range: {min: 0, max: 100}
    # on_max/on_minをどちらも省略しているため、単純に[0, 100]へクランプされるだけの
    # プロパティになる（毎tick再計算するmodify/addの結果が範囲をはみ出した場合の後始末）。
```

- `range` は `on_max`/`on_min` を使う場合に必須です。`range` 自体を省略すると（`day` のように上限・
  下限なく積み上げ続けたい場合）、`on_max`/`on_min` の仕組み自体を持ちません。
- `add` に書けるプロパティは、自分自身（折り返し）に限らず、同じ object_def 内の他のプロパティ
  （繰り上げ・繰り下げ先）も指定できます。存在しないプロパティ名は `add` の通常の規約と同様に黙って無視されます。
- 自分自身の折り返し・繰り下げには `set`（9.2 節）ではなく `add` を使ってください。1 tick で `range` の幅を
  複数回分飛び越えることがあり、`set` で固定値へ代入するとその超過分を失いますが、`add` なら差分を保ったまま
  反映されます。
- 補正の適用自体が再び判定を呼ぶため、補正が値を境界の内側へ戻す限り、連鎖は同じ tick 内で完全に解決されます。
  1 tick で `range` の幅を複数回分飛び越えた場合も、繰り上げ・繰り下げ先自身がさらに範囲外へ出る連鎖
  （分→時→日）も、`props` の宣言順に関わらず持ち越しなく解決されます（`tests/domain/rangeEvents.test.ts` 参照）。
- 補正が値を境界の内側へ戻さない場合（空宣言や、値を書き換えない内容だけを書いた場合）、値が境界に居る間は
  判定のたびに繰り返し適用されます。`destroy` は冪等なので安全で、`spawn` を伴う場合は同じイベント内で
  `destroy` と組み合わせるのが基本形です（破棄後は tick の対象でなくなるため、2 回目以降の実行は起こりません）。
  自分を破棄しない `spawn` を境界で繰り返させないための口が、次の `conditions` です。

#### `conditions`（どういうときに走るか）

`on_max`/`on_min` は `conditions`（14 節）を持てます。**満たす回だけが著者の書いた内容へ、満たさない回は
既定のクランプ**（自分自身を境界へ `set`）**へ倒れます**——`on_max` を書くとクランプが消えるのは、著者が
境界での振る舞いを引き受けたからで、条件を満たさない回は引き受けていないためです。値は境界に張り付いた
ままになり、書き込みは何度でも続けられます。

**「一度だけ起こす」を、呼ぶ側ではなく起こす側に書くための口です。** 境界に居る値は書き込みのたびに
イベントを呼び直すので、これが無いと「もう起こした」を呼ぶ側（そこへ書き込むアクションの `conditions`）が
覚えることになり、**そのアクション自体が打ち切られます**。海区の見張りが航路を1本だけ湧かせる例が
これで（[`Voyage.md`](../world/Voyage.md) 3.5 節）、条件が見るのは印ではなく**湧かせた物そのもの**です。

```yaml
props:
  exploration_progress:
    value: 0
    range: {min: 0, max: 3}
    on_max:
      conditions:
        - not: {slot: fixtures, matches: {object: route_to_kelp_belt}}   # まだ湧かせていない
      spawn: {object: route_to_kelp_belt, into: self}
```

```yaml
props:
  durability:
    value: 100
    range: {min: 0, max: 100}
    passives:
      - add:
          self:
            durability: -1
    on_min:
      destroy: self   # 0に達した瞬間に自壊する
```

### 6.4 stages（段階）

数値プロパティは `stages` を持つことができ、現在値がどの段階にあるかによって、有効になる `passives`（8 節）が
切り替わります。

- 段階の区間定義は **`min`（下限）のみ**を指定します。上限は次の段階の `min` によって自動的に決まります
  （半開区間、`[min, 次のminより手前]`）。この方式により、区間の隙間や重複が構造的に発生しません。
- 最下段の段階は `min: null`（または省略）とし、それより下の残り全ての値を拾います。
- **シンボル型プロパティ（6.6 節）の場合は `min` を書きません**（書いた場合はロード時エラー。シンボル値の
  大小関係に意味が無いため）。代わりに、**段階の `name` 自体がそのまま比較対象の値になります**（値が
  `name` と完全一致する場合だけその段階になる、シンボル名同士の比較）。

  ```yaml
  props:
    weather:
      value: clear
      stages:
        - name: storm
        - name: clear
          passives:
            - modify:
                self:
                  ambient_brightness: -2
  ```

  数値型の「最下段（min省略）＝フォールバック」という概念は、シンボル型には存在しません。`stages` に
  書かなかった値は単に「該当する段階が無い」となり、`resolveStage` は `undefined` を返します。呼び出し側
  （`WhenOwnStage` ゲートを含む）は必ず `undefined` チェックを行います（`WorldObject.isInStage` 参照）。
  複数のシンボル値を1つの段階名にまとめたい場合は、`stages` ではなく利用側の `conditions` の `in`
  （14.1 節）で表現します。`stages` は1つのプロパティ自身の値と段階名を1対1で対応させる仕組みです。
- 現在値に基づいて常に一意に段階を決定します。ヒステリシス（上昇時・下降時で閾値をずらす仕組み）は採用しません。
- ステージの `passives` はレベルトリガー（そのステージにいる間ずっと有効）のみです。ステージ切替の瞬間だけ発火する
  edge-triggered な仕組み（`on_enter`/`on_exit` 的なもの）は導入していません（17 節）。「下限に達した瞬間」は
  `on_min`（6.3 節）で表現します。
- ステージは `name`/`min` という固有の属性を持つため、ステージ自体を配列の要素にはできません。`passives:` は
  `name`/`min` と対等な兄弟キーとして、専用にネストしたキーのまま持ちます（他のレベルの `passives:` と同じく
  常に配列です、8 節）。
- ステージの `passives` ブロックには `conditions` も併記できます。この場合、「現在値がこの段階の区間内に
  あること」（`WhenOwnStage`）と `conditions` の両方を満たす間だけ有効になります（AND、8.2 節）。
- ステージは **`alert`** で「その段階にいる間、値がどの域にあると見なすか」を宣言できます。値は
  `safe`（安全域）・`watch`（留意域）・`caution`（要注意域）・`danger`（危険域）・`fatal`（致命的域）の
  いずれかで、省略時は `safe` です。UI はこの宣言だけを見てステータスの見せ方（非表示・表示・明滅）を
  決めます（[`StatusArea.md`](../ui/StatusArea.md)）。`watch` と `caution` は
  今のところ同じ見せ方（出すだけ）ですが、深刻さの違いを段の側で表しておくことで、見せ方を分けたく
  なったときに YAML を書き直さずに済みます。`fatal` は**放置すると死に至る**プロパティ（水分など）に
  だけ付けます。UI は `alert` から**バーの塗りの色**（深刻さで緑から茶へ）と、**どちら向きが悪化か**
  （段を下から上へ見て深刻さが単調に上がるなら、増える側が悪い）を導きます
  （[`StatusArea.md`](../ui/StatusArea.md)）。
- **`range` を持つプロパティでは、`alert` の深刻さは下から上へ単調でなければなりません**（ロード時
  エラー）。体温のように上下どちらの端も悪い量はバーの向きを決められないため、片側だけの度合い
  （熱中症・低体温症）を別のプロパティとして持たせます。`range` を持たない（＝バーにならない）
  プロパティにはこの制約はありません。
- ステージは **`art`** で「その段階にいる間カードに出す絵」を接尾辞として宣言できます
  （値は `src/assets/objects/<型の絵の名前（4.3 節）>_<この値>.png` を指す、
  [`CardView.md`](../ui/CardView.md) 5.1 節）。**同じ個体のまま姿だけが変わる状態**——気を失った動物、
  火のついた炉——を、型を差し替えずに表すためのものです。宣言した絵をまだ用意していない場合は、その型
  自身の絵のままになります（絵を描くのと文法を宣言するのを別々の時に行えます）。
  - `art` を宣言できるのは、その object_def が **`art_by_stage`** で名指ししたプロパティの段だけです
    （object_def 直下の兄弟キー、値はプロパティ名）。1つの object_def につき `art_by_stage` は高々1つで、
    他のプロパティの段が `art` を宣言するとロードエラーになります——**1オブジェクト1絵の原則**を、
    2つのプロパティが同時に絵を主張する曖昧さごと構造で防ぐためです。`art_by_stage` は
    `stack_order`（7.6節）と同じ規約で、trait 側の宣言も参照できます（自分自身の指定を優先し、
    無ければちょうど1つの trait の指定を使う）。
  - **複数の段が同じ `art` 値を宣言してかまいません。** 料理のできる火力の3段（`coals`〜`blaze`、
    `FireSystem.md` 3節）がすべて同じ「ついている」絵を指す、という使い方はここで賄います。段を
    割った意味の粒度と、絵を割る粒度を一致させる必要はありません。
- ステージは **`situation`** で「その段階にいる間、キャラクター表示エリアに出す状況アイコン」を絵の
  識別子として宣言できます（値は `src/assets/icons/<この値>.png` を指す、
  [`ScreenLayout.md`](../ui/ScreenLayout.md) 4.1.1 節）。**宣言した段にいる間だけ出て、宣言しない段では
  出ません**——「出すか」と「どの絵か」を1つの宣言に畳んであるので、片方だけ書いて黙って出なくなることが
  ありません。`art` と違い、名乗れるプロパティを object_def が絞る宣言はありません（画面はプロパティの
  意味を知らずに並べるため）。**複数の段が同じ識別子を宣言してかまいません**（`art` と同じ理由。手元の
  明るさの `pitch_dark` と `dim` はどちらも「手元が暗い」の一言に尽きるので、同じ絵を指します）。

```yaml
props:
  progress:
    stages:
      - name: none
        min: 0
      - name: mild
        min: 20
        alert: caution
        passives:
          - add:
              parent:
                temperature: 1
      - name: feverish
        min: 50
        alert: danger
        passives:
          - add:
              parent:
                temperature: 2
                hydration: -1
```

### 6.5 base（値の土台）

`base` を書くと、**そこが指すプロパティの実効値を土台にして、自分の値をその上へ加算**します
（`GetEffectiveValue`、可逆）。土台が辿り着けなければ寄与は 0 で、自分の値だけが残ります。

土台の指し方は `{subject, prop}` で、`conditions`（14.1 節）・`weight`（10.2 節）・`duration`
（11.3 節）と同じ参照です。`subject` を省くと `self`、`prop` を省くと**同名**のプロパティを指します。

```yaml
props:
  # 祖先の同名（propを省略）
  ambient_brightness: {value: -9, base: {subject: ancestor}}
  # 自分の別のプロパティ
  hand_brightness: {value: 0, base: {subject: self, prop: ambient_brightness}}
  # 祖先の、別名のプロパティ
  looking_brightness: {value: 0, base: {subject: ancestor, prop: ambient_brightness}}
```

- **読むのは土台の実効値**です（相手の `range` でクランプ済み・`modify` 込み）。自分の側の `range` は、
  土台へ加算した後に効きます。
- **1 つのプロパティに `base` は 1 つだけ**です。土台が増えると、実効値がどこから来たのかが読めなく
  なります。
- **`subject: self` のとき `prop` は必須**です（省略すると自分自身が土台になるため、ロード時エラー）。
  `self` を辿って自分へ戻る循環も、同じ型の中で閉じるのでロード時に検出します。
- 宣言の置かれた場所が用意できる主語だけを書けます（14.1 節の表）。`props` は宣言元の個体に付いているので
  `self`・`parent`・`ancestor` がいつでも書け、**その個体が操作の参加者である間は `agent`・`instrument`・`patient`
  （11.5 節）も解決します**。関係が結ばれていない間は土台が辿り着かないので、寄与は 0 になり、自分の値だけが
  残ります。

`ancestor`（8.6 節と同じ探索）は、**自分の直接の親から遡り、`prop` が指すプロパティを定義している
最初の祖先**です。

- 直接の親（`parent`）固定でなく祖先を遡れるのは、直接の親がそのプロパティを持たない場合に対応するため
  です（例: アイテムの直接の親はプレイヤーだが、`ambient_temperature` は部屋が持つ）。途中の親が定義して
  いればそこで探索が止まるため、断熱容器のように「途中で値を変えて中継する」表現も、その容器自身が
  `range`・`modify` 等で自分の値を作ればそのまま実現できます。
- すべてのオブジェクトは唯一のシングルトンである world の子孫であるため（7.1 節）、途中に誰も定義していなければ
  必ず world まで遡ります。「本当に世界固有の概念かどうか」を著者が事前に区別する必要はありません。

```yaml
object_defs:
  room:
    props:
      ambient_temperature:
        value: 20
  food:
    props:
      ambient_temperature:
        value: -2                  # 自分のオフセット
        base: {subject: ancestor}  # 祖先(通常はroom)のambient_temperatureを土台にする
```

### 6.6 シンボル型の値

`value` に数値にも真偽値にもならない識別子（`^[a-z][a-z0-9_]*$`、
3.2 節と同じ命名規則）を書くと、その識別子を**シンボル名**として自動的に整数へ変換します。専用の宣言
（`symbol: true` 等）は不要で、`value` の書き方だけで区別できます。液体の種類のような「離散した状態」を、
enum 型等を新設せず既存の `props`/`conditions`/`set` の語彙だけで表現するための仕組みです。値の比較・代入は
9.2 節・14.1 節の通り、他の数値プロパティと全く同じように書けます。

```yaml
props:
  content:
    value: water   # 数値にも真偽値にもならないため、シンボル名として登録される
```

- シンボル名同士の大小関係（`lt`/`gt` 等）は、登録順に依存する恣意的なものであり意味を持ちません。
  シンボル型のプロパティは `eq`/`neq`/`in`/`not_in` で比較する用途を想定しています。
- `range`/`on_max`/`on_min`/`stages` はいずれも数値の大小関係を前提にした仕組みのため、
  シンボル型のプロパティと組み合わせても意味のある結果にはなりません。

### 6.7 tags（プロパティのカテゴリ）

プロパティは `tags` でカテゴリ分けできます。キャラクターのように多数のプロパティを持つ型を、UI が
「健康」「栄養」のようなまとまりに分けて見せるための仕組みです。

タグ名はトップレベルの `property_tags` で宣言し、`props` 側はそこで宣言した名前しか使えません
（未宣言の名前はロード時エラー。綴り間違いをその場で捕まえるため）。**宣言した順がそのまま UI での
表示順**になります。

```yaml
property_tags:
  status:
  health:
  nutrition:

object_defs:
  character:
    props:
      satiety:
        tags: [status, nutrition]
        value: 96
        range: {min: 0, max: 96}
```

- **`object_defs` のタグ（4.1 節）とは別の名前空間**です。枠の`accept`・`combinations.with`・
  `conditions` の `matches`（14.3・14.4 節）が `{tag: ...}` で見るのは 4.1 節のタグだけで、プロパティの
  タグは参照しません。
- 1 つのプロパティに複数のタグを付けられます（上の例の `satiety` は「常時ステータスエリアに出す」＝
  `status` であり、栄養カテゴリの一員でもあります）。
- **trait 経由のタグは合成されます**。`props` の他のフィールド（`value`・`range` など）は trait 側の
  指定を object_def 側が上書きしますが、`tags` だけは足し合わせます（5 節）。タグは集合であり、
  object_def 側がタグを1つ足しただけで trait 由来のカテゴリを失うのは事故になるためです。
- `property_tags` のエントリは今のところ中身を持ちません（`status:` のようにキーだけを書きます）。
  タブに出す表示名は他の識別子と同様 locale 側が持ちます（[`Localization.md`](./Localization.md)）。

### 6.8 gauge（カードにバーとして出す）

プロパティは `gauge` で、**自分をカードのバーとして出すか**と、**両端がどう見えるか**を宣言できます
（[`CardView.md`](../ui/CardView.md) 8 節）。

```yaml
props:
  durability:
    # 尽きると使えなくなる量。満タン側が good なので、減るほど赤へ寄る。
    gauge: {min: bad, max: good}
    value: 960
    range: {min: 0, max: 960}
  severity:
    # 残っている傷。増えるほど悪いので、耐久度とは両端が入れ替わる。
    gauge: {min: good, max: bad}
```

- **`min`/`max` は `range` の両端に居るときの見せ方**で、`good`（満ち足りている）・`bad`（尽きている・
  行き過ぎている）・`neutral`（良し悪しを言わない）の 3 つから選びます。**塗りの色はこの 2 つだけで
  決まる**ので、UI 側にプロパティ名の対応表は要りません。両端が同じなら値によらず 1 色になります
  （工程の進捗のように、0 を赤で急かしたくない量）。
- **`range` が必須です。** 割合が定義できなければバーとして描きようがないためで、`range` の無い
  プロパティに `gauge` を書くとロード時エラーになります。
- **どちらの端が危ないかは 1 か所にしか書けません。** `stages` の `alert` から導く向き
  （`alertDirection`、6.4 節）と `gauge` の向きが食い違っているとロード時エラーになります。
  増えた分の帯をどちら向きに出すかは `gauge` の側から決まります。
- **バーを出すか出さないかも、この宣言の有無だけで決まります。** 宣言していないプロパティは
  カードに出ません。**何本出るかも宣言の数で決まる**ので、UI 側は「いくつまで」を知りません。

### 6.9 型を指す値

`value` に `{object: <識別子>}` を書くと、その値は **`object_defs` の型を 1 つ指すもの**になります。実行時の
値は整数（その型のグローバル ID）で、シンボル型（6.6 節）と同じく**名前を整数へ畳んだ値**です。ロードした
時点で決まる定数なので、生成の順序にも世界の形にも依存しません。

```yaml
props:
  # この海区の、本土の側の隣（voyage.yaml）。
  zone_toward_mainland: {value: {object: kelp_belt}}
```

**引くのは行き先を型で指す口**——`move` の `to_object`・`spawn` の `into_object`（9.6 節・9.4 節）で、
`{prop: <名前>}` と書くとこの値を読みます。**探し方は型の名前をその場に書いたときとまったく同じ**なので、
違うのは名前をどこに書くかだけです。

```yaml
move: {subject: picked, to_object: {prop: zone_toward_mainland}}
```

- **指せるのは `singleton` の型だけです**（15 節）。`to_object` に直接書いたときと同じ制約で、複数在りうる
  型ではどの個体を指すのか決まらないためです。ロード時に検査します。
- **同じ行き先を 2 か所へ書き写さないための仕組みです。** 型の名前しか書けなかった頃は、同じ隣を
  「航路を立てる先」と「荒天が押し流す先」の両方へ手で書くしかありませんでした
  （[`Voyage.md`](../world/Voyage.md) 3.8 節）。
- **`range`/`on_max`/`on_min`/`stages` とは組み合わせても意味のある結果になりません**（シンボル型と同じ
  理由で、値の大小に意味が無いため）。
- **引く先がこの宣言を持たないプロパティならロード時エラーです。** 値は数のままなので、ただの数値
  プロパティを引く `to_object` は、実行時に無関係な型を引くか黙って何も起きないかのどちらかになります。
  型の名前を直接書いたときに `singleton` を要求するのと同じ、**書いた時点で分かる誤り**です。
- **その宣言を持つプロパティを、たまたま持っていないオブジェクトが引いたときは何も起こしません**
  （9.6 節の解決失敗と同じ扱い）。「片側の隣が無い端の海区」を、書き分けずに表せます。

## 7. slots（親子関係とコンテナ）

### 7.1 基本構造

- オブジェクト間の所属関係はツリー構造で表現します。1 つの子オブジェクトは必ず 1 つの親に属します。
- 親オブジェクトは複数の「スロット」（配列）を持ちます（例: `inventory`、`equip`、`fixtures`）。
- 子オブジェクトは逆引き用のキャッシュフィールドを持ちますが、正の情報源はあくまで親側のスロット配列です。
- スロット間の移動は `move_to_slot` という単一の汎用操作に集約します。親側スロット配列と子側の逆引きキャッシュの
  整合性は、この操作の中でのみ保証します。
- スロットに「種類タグ（kind）」は設けません。スロット名を直接参照します。
- すべてのオブジェクトは、唯一のシングルトンである `world`（15 節）を根とするこのツリーのどこかに、必ず所属します。
  **このツリーに繋がっていること自体が「世界に存在すること」を意味します**（別途の一覧管理はしません）。
  `destroy`（9.3 節）は親スロットからの切り離し、`spawn`（9.4 節）は生成とこのツリーへの接続として表現できるのは
  この前提のためです。

```yaml
object_defs:
  character:
    props:
      hp:
        value: 100
    slots:
      equip: {}
      inventory: {}
      injuries: {}
```

### 7.2 cells（枠ごとの要件）

**スロットは中身を直接持たず、枠（セル）の並びを持ちます。** 何が入るかも何個入るかも、スロット
全体ではなく枠ごとに決まります。

```yaml
object_defs:
  character:
    slots:
      inventory: {}                              # 制約なし・枠数も未定
      hand:
        cell_count: 6                            # 枠が6つ
        cell: {accept: {tag: item}}              # どの枠も同じ要件
  chair_in_progress:
    slots:
      materials:
        cells:                                   # 枠ごとに違う要件。並べた数がそのまま枠数
          - {accept: {object: board}, max: 1}
          - {accept: {object: stick}, max: 4}
```

- **`cell`**: すべての枠に共通する要件。`cell_count` と併せて書けば枠数が決まり、書かなければ
  枠数は決まりません（＝前詰め。[`SlotSystem.md`](./SlotSystem.md) 3 節）。
- **`cells`**: 枠ごとの要件を並べます。**並べた数がそのまま枠の数**なので `cell_count` は書けません。
  「板 1 枚と棒 4 本」のようなレシピの材料欄がこれで、何が何個必要かがそのまま枠の形になります。
- **`cell_count`**: 枠の数。`cells` と同時には指定できません。
- `cell` と `cells` はどちらか一方だけを書きます。どちらも書かなければ、どんな型でも無制限に積める枠が
  必要なだけ増えます。

枠の中身は 2 つのキーで決めます。

- **`accept`**: その枠が受け入れる型。`tag` か `object` のどちらか一方を指定します（両方またはどちらも
  なしはエラー）。省略すると型を問いません。
  書き方は重ねる操作の相手の指定（12.1 節）と同じ二択です（4.1 節）。
- **`max`**: その枠に積める同種の個数（省略で無制限）。**束ねられる型にだけ効きます**——
  `stackable: false` な型（道・かご、7.6 節）は同種でも束ならないので、1 枠には必ず 1 個しか入りません。

**枠は宣言順に埋まるのではなく、型の合う枠へ入ります。** 上の例で棒を先に入れれば、板の枠は空いたまま
棒の枠が埋まります。

**レシピが要求する個数はここには書きません**（13.1 節の `requires`）。枠は「置ける場所」であって
「作るのに要る量」ではないため、両方に数を書くと二重管理になります。

### 7.3 capacity（合計サイズの制約）

`capacity` を書くと、スロット内のアイテムの合計サイズ（各アイテムの `volume` プロパティの総和）が上限を超えないよう
制約できます。`move_to_slot` が「現在の中身のサイズ合計＋新しいアイテムのサイズ ≤ capacity」を検証し、超える場合は
移動を拒否します。

```yaml
slots:
  inventory:
    capacity: 50

props:
  volume:
    value: 3
```

### 7.4 weight / load（重さと負荷）

`weight`・`load`・`density`・`load_rate` は、エンジンが名前で直接参照する規約プロパティです
（内部設計は [`ContainerSystem.md`](./ContainerSystem.md)）。いずれも実効値として読むたびに導出されます。

**コードがYAMLの単語へ寄せている依存は `WorldVocabulary` に集めてあります。** ここに挙げた規約プロパティ
（`engine`）と、この世界のルールが名前で知っている単語（`world`。時間・天候・手持ちの枠・探索の進捗など）の
2つに分かれていて、**「この単語をYAMLから消したら何が壊れるか」を1箇所で読めます**。IDは`intern`で取る
（無ければ登録する）ので、誰も宣言していない単語は「そのIDを持つ物が1つも居ない」という形で自然に扱われ、
語彙の有無で分岐する場所はありません。

見せ方だけを決める単語（カードの枠色を選ぶタグ、覆いを出す段の名前など）は載せていません。あちらは
「この段なら覆いを出す」のように**結果と対でしか意味を持たない**ので、名前だけを引き剥がすと規則が
2箇所に割れます。

- **`weight`**: 物の重さ。自分の値に、**中身の `weight` をそのまま足します**（率はかけません）。中身入りの
  容器（[`LiquidContainerSystem.md`](./LiquidContainerSystem.md) 1 節）は `fill × density` が加わります
  （`density` は単位量あたりの重さ = g/mL、水は 1）。そりを台車に積めば、台車の重さはそりの重さをそのまま
  加えたものです。
- **`load`**: 担いだ人が感じる負荷。**直接の子**の `weight` に、その子の `load_rate`（担いだときに感じる
  割合）を掛けた分の合計です。持つのはキャラクターだけで、他のオブジェクトは定義しません。宣言しなければ
  素の重さがそのまま効き、`1` を超えれば実際より重く感じます（長物を素手で抱えるような場合）。**下限は
  見ません**——負の率も書いたとおりに効きますが、それは負の `modify` を書けるのと同じことで、端を持つのは
  受け取る側（`load` の `range`）です。

これらの伝播は、**エンジンが型に生やす `modify`**（8.3 節）として表されます。押し上げる当人が名乗る形で、
寄与の登録も影響の一覧も著者が書いた `modify` と同じ経路を通ります。著者に書かせないのは、この宣言に
自由度が 1 つも無いためです（詳細は [`ContainerSystem.md`](./ContainerSystem.md) 1 節）。**`fill` を宣言する型は
`weight` も宣言しなければなりません**——抱えている量の重さを載せる先が要るためで、無ければロード時エラーです。

率をスロットではなくアイテムが持つのは、同じ入れ物でも背負うか手に提げるかで体感が変わるからです。
どのスロットにいるかは `passives` の `in_slot`（14.2 節）で切り替えます。

```yaml
object_defs:
  sledge:
    props:
      weight: {value: 10000}
      load_rate:
        value: 1
        passives:
          - conditions: [{in_slot: hand}]
            modify: {self: {load_rate: -0.9}}   # 引きずるので体感は1割

  character:
    props:
      weight: {value: 70000}   # 自重。荷物は中身として上に乗る
      load: {value: 0}
```

石（`weight` 100）を載せたそり（自重 1000）を手で引くと、そりの `weight` は 1100、キャラクターの `weight` は
自重込みの 71100、`load` は 1100 × 0.1 = 110 になります。

### 7.5 装備の排他制御（covers / layer）【確定】

- 身につける枠には複数のアイテムを同時に格納できます。排他制御はスロットの数ではなく、アイテムが持つ属性で
  行います。
- アイテムは `covers`（覆う部位のタグの配列。例: `[torso]`）と `layer`（重ね着の階層。例: `base`、`outer`）を
  持ちます。**2 つは対でしか宣言できません**——片方だけでは競合を判定できない（部位の無い階層は誰とも
  重ならず、階層の無い部位はどの段で重なるかを言えない）ので、片方だけならロード時エラーです。
- 競合判定は、同じ `(covers要素, layer)` の組が、既に同じ枠に入っている他アイテムと重複する場合に
  装備不可とします。
- 競合解決は「ブロック型」です。競合するアイテムがある場合、プレイヤーが先に既存の装備を外す必要があります
  （自動退避は採用しません）。
- **この判定が効くのは身につける枠だけ**です。手持ちや地面では同じ衣類を何着でも並べられます。
  どの枠が身につける枠か（`equipment`）を知っているのは `WorldVocabulary`（7.4 節）で、枠の宣言からは
  導けません。

```yaml
object_defs:
  armor_leather:
    covers: [torso]
    layer: base
```

### 7.6 スタック表示

同種オブジェクトをまとめて1つの視覚的なまとまり（スタック）として表示するための設定です。世界の実体
（`slots`の中身が個々のオブジェクトの集まりであること）は変わりません。`Slot`は中身を`ObjectStack`
（1つのスタックにまとまるオブジェクトの集まり）の列として保持し、これが「表示上の並び順」の正の情報源です。
個々の`ObjectStack`の中は`stack_order`（無ければ挿入順）で並びます。スタックの区別を畳み込んだビュー
（`Slot.Contents`）も提供されますが、これは内部処理（タグ判定・重さ集計など）向けの派生ビューです。

**スロット側**（`slots`の各エントリに指定）: 枠の数（`cell_count` / `cells`）と枠ごとの `max`
（7.2節）。**枠数を決めると位置も安定します**——空いた枠を保持したまま前詰めせず、プレイヤーが手動で
入れ替えられます（例: プレイヤー手持ちの6枠）。枠数を決めなければ、空いた枠は詰められます
（[`SlotSystem.md`](./SlotSystem.md) 3節）。

```yaml
object_defs:
  character:
    slots:
      hand:
        cell_count: 6
        cell: {accept: {tag: item}}
      furnace_intake:
        cell_count: 2          # 燃料はstackable: falseなので、同じ燃料でも2つで2枠
```

**オブジェクト側**（`object_defs`の各エントリに指定）:

- **`stackable`**（既定`true`）: 同種と束ねてよい型か。`false`なら同じ型でも1個ずつ別の枠に並びます。
  束ねたくないのは、その個体を名指しで操作する必要があるとき——道は行き先が、かごは中身が個体ごとに
  違うので、束ねると代表のものしか触れなくなります。**入れ物ではなく物の性質**なので、スロットではなく
  こちらで宣言します（[`SlotSystem.md`](./SlotSystem.md) 4節）。

- **`stack_order`**: `{property, ascending}`。スタック内での並び順を、指定したプロパティの値で決めます。
  「手前に重ねたいものほどリストの末尾に並ぶ」という規約のもとで、`ascending: false`は値が小さいものほど
  末尾（劣化アイテムなら寿命が短いものほど手前に）、`ascending: true`は値が大きいものほど末尾を表します。
  省略時は並び順が未定義で、新規インスタンスは常にスタックの末尾（挿入順）へ追加されます。劣化する液体など、
  複数のプロパティが絡む並び順のパターンは今後の検討課題です（12.1節参照）。

```yaml
object_defs:
  wet_log:
    props:
      freshness:
        value: 100
    stack_order: {property: freshness, ascending: false}
```

- `stack_order`は、新規インスタンスがスタックへ加わる際の並び位置決定にのみ使います。一度並んだ後、値の変化に
  追従した再ソートは行いません。同種は同じ速度で変化する（`add`は`ObjectDef`ごとに一定量、8.4節）
  前提のもとで、挿入時点の相対順序がその後も保たれるためです。

**`spawn`（9.4節）との関係**: `into`を省略（`same_slot`）した置き換えは、`destroy`を`spawn`より先に書き
（9.3節・9.4節参照）、破棄されたオブジェクトが占めていた位置（一般のスロットではリストの位置、
枠数を決めたスロットでは固定番号）を新しいオブジェクトへそのまま引き継がせます。これにより、種類が
変わるアイテムが、周囲の並び順を崩したり新しい枠にはみ出したりせず、同じ位置で置き換わります。`destroy`を
伴わない場合（生き残ったまま増やす場合）は、新しいオブジェクトは自分の直後へ挿入されます。

1つの効果が複数のオブジェクトを生む場合（1つのクラフトで実と皮に分かれる場合など）、元の位置を引き継ぐのは
新しい枠を要る最初の1つで、以降は直前に置いたものの隣（下記の「自分の隣」と同じ規則）へ、宣言順に並びます。
合流できる既存スタックがあるものは枠を消費しないため、この並びには加わりません（元の位置は、枠を要る次の
1つのために空いたまま残ります）。

新しい型を挿入する必要があり（合流できる既存スタックが無く）、かつ自分自身の位置を再利用できない場合
（`destroy`しない、または`destroy`しても同種が残る場合）、挿入位置は「自分の隣」です。一般のスロットでは
単純に自分の直後へ挿入します。枠数を決めたスロットでは、**まず自分の固定番号+1の位置（右側）から
空いている番号を探し**、間にいる他の型をすべて+1して押し出してから割り込ませます。右側に空きが無ければ、
**自分の固定番号-1の位置（左側）から空いている番号を探し**、間にいる他の型をすべて-1して押し出してから
割り込ませます。いずれの方向も前詰めはせず、押し出された型同士の相対順序は変わりません（押し出しは型単位で
行うため、押し出される型がスタックであっても中身はバラけません）。どちらの方向にも空きが無い場合
（枠がすべて埋まっている場合）は配置に失敗し、起点自身の親へこぼれます（`fallback`が無いのと同じ扱い）。

例（`cell_count: 4`、`_`は空き番号）: `A(0) _(1) B(2) _(3)` の状態で `A` から `C` が生まれると（`destroy`
なし）、空いている1番へそのまま入り `A C B _` になります。続けて `A` から `D` が生まれると、空いている3番
までの間（`C`・`B`）を+1して押し出し、`A D C B` になります。さらに `A` から `E` が生まれても、4枠すべてが
埋まっているため配置に失敗し、起点自身の親へこぼれます。なお、生まれた側が元のスタックと合流できる型
（例: `A` から `A`）は、新しい固定番号を消費せず既存のスタックへそのまま加わるため、このあふれの心配は
ありません。

右側に空きが無い場合の例: `_(0) _(1) A(2) B(3)` の状態で `A` から `C` が生まれると、右側（3番以降）は`B`で
埋まっているため左側を探し、空いている1番へそのまま入って `_ C A B` になります。続けて `B` から `D` が
生まれると、右側（4番）はスロットの外なので左側を探し、空いている0番までの間（`C`・`A`）を-1して押し出し、
`C A D B` になります。

### 7.7 placement（誰がここへ物を入れてよいか）

**`placement`** は、そのスロットへ**誰が物を入れてよいか**を並べるスロットレベルのキーです。
省略すると両方（`[auto, manual]`）です。

| 値 | 意味 |
|---|---|
| `auto` | `spawn`（9.4 節）・`move`（9.6 節）の**宣言順走査**の宛先になる。エンジンが自分で選んでよい |
| `manual` | **プレイヤーが札を重ねて入れられる**（7.8 節） |

**2 つは同じ 1 つの規約（宣言順に探して最初に受け取れる枠へ入れる）の、入口の違いです。** どの枠が
その走査に参加するかを `placement` が決め、走査する枠の並びは `ObjectDef.placementSlotDefs` が
1 箇所で答えます。

```yaml
slots:
  hand:
    cell_count: 6
    cell: {accept: {tag: item}}
  equipment:
    cell: {accept: {tag: item}}
    placement: [manual]        # 手持ちがあふれても流れ込まない。着けるのは意図した操作だけ
  spoils:
    cell: {accept: {tag: item}}
    placement: [auto]          # くわえるのは獣自身。プレイヤーは物を渡せない
  undiscovered_fixtures:
    cell: {accept: {tag: fixture}}
    placement: []              # 生成が名指しで入れるだけ。誰にも選ばせない
```

枠の要件（7.2 節）・`capacity`（7.3 節）が「何をいくつ入れられるか」の制約であるのに対し、`placement` は
**入れる側が誰か**を表します。

- **`auto` を外すのは、上限の無いスロットが吸い込むのを止めるため**です。上限の無いスロットが宣言順の
  どこかにあると、それより後ろのスロットも、あふれた先である親も一切使われなくなります。
- **`manual` を外すのは、プレイヤーが持ちようのない物や、渡す道理の無いスロット**です。獣がくわえた物の
  枠がこれで、外からは見えても（7.11 節）渡すことはできません。
- 走査の対象外であることは、こぼれた先の親（9.4 節）でも変わりません。こぼれ落ちる先でも走査の決まりは
  同じで、どの段でも枠の宣言はそのまま効きます。

### 7.8 カードへ重ねた物の行き先

**カードへ重ねた物は、そのオブジェクトのスロットのうち、宣言順で最初に受け取れるものへ入ります**
（[`CardInteraction.md`](../ui/CardInteraction.md) 2 節）。受け取れるとは、`manual` を許していて
（7.7 節）、**今その物が実際に入る**、ということです——枠の要件（7.2 節）だけでなく、空きと容量まで
見ます。型が合うだけで選ぶと、手が塞がっているときに装備の枠が空いていても落とせなくなります。

**スロットがあるなら入れられる、が既定です。** 入れられて困るスロットが `placement` で自分から断ります。

**行き先は重ねる物で変わります。** 怪我の札は治療具だけを受け取り、かごは持ち物を受け取ります。同じ
カードでも、何を重ねたかで行き先が決まる（あるいは決まらない）ので、カードごとに 1 つの行き先を持つ
形では表せません。

**複数のスロットが受け取れるときは、宣言順で最初のものです。** 編み籠は `item` でも `fixture` でも
あるので、筏へ重ねると積荷（`items`）に入り、設置物の枠には落ちません。先の枠が埋まっていれば、
次に受け取れる枠が行き先になります。**この順序は自動配置の走査順
（7.7 節）と同じもの**で、`location` trait が `items` を先頭に置いているのはこぼれた物の行き先を
決めるためです。どこへ入るかは、落とす前に吹き出しが名乗ります（`put_in`、7.10 節）。

**中が見えるかとは別です**（`visible_slots`、7.11 節）。筏の積荷は外から見えませんが、札へ重ねれば
積めます——中を確かめるには乗り込む、という違いがそのまま操作の形になります。

**「押すと開くスロット」（7.11 節）とも「容量のバー」（7.12 節）とも別の宣言です。** かごのように
3 つとも一致する型が多いので、かつては 1 つのキー（`main_item_slot`）が兼ねていましたが、筏が
「重ねれば積めるが、中身は外から見えない」を持ち込んで破れました。

### 7.9 bound_to_owner（持ち主とともにしか在れない）

**`bound_to_owner: true`** は、その型のオブジェクトが**単独では存在できない**ことを宣言する
オブジェクトレベルのキーです（`stack_order` と同じ位置に書きます）。捻挫・液体・道がこれにあたります。

```yaml
object_defs:
  sprained_ankle:
    bound_to_owner: true      # 身体から離れた「捻挫」は無い
```

宣言すると2つのことが起きます。

- **他の持ち主へ移せない。** いったん親に付いたら、`move`（9.5 節）でもドラッグでも別の親へは
  移りません（生まれた直後の、まだ親を持たない状態での配置は通ります）。枠の`accept`（7.2 節）が
  「入れる側から見て、何を受け入れるか」を言うのに対し、こちらは「その物がどう存在するか」なので、
  こぼれ落ち（9.4 節）でも移りません——こぼれる代わりに、持ち主と一緒に世界から外れます。
- **親が消えれば道連れになる。** `destroy`（9.3 節）は中身をその親へこぼしますが、`bound_to_owner`
  な中身はこぼれず、一緒に世界から外れます。

**スロットではなくオブジェクトに書く**のは、これが**その物の性質**だからです。同じ「怪我スロット」でも、
入っている物が捻挫なら剥がせず、湿布（治療具）なら剥がせる、という違いはスロット側では言えません。
怪我が治って捻挫が消えるとき、当てていた包帯だけが本人の手元へこぼれ出るのがその現れです。

**プレイヤーが怪我を出し入れできないのは、この宣言の帰結です。** 取り出せないのは捻挫が
`bound_to_owner` だから、入れられないのは手元に怪我を持ちようがないから。スロット側に「書き込み禁止」
のような別の属性は要りません。

### 7.10 put_in（入れるのにかかる時間）

**`put_in: {duration: ...}`** を書くと、そのスロットへ物を入れるのにゲーム内時間がかかります（既定は一瞬）。
`duration` は操作のそれと同じ形（リテラルか `{subject, prop}` 参照、10.2 節）で、`self` が枠の
持ち主、`instrument` が入れる物、`agent` が入れている者です。**ここも操作の宣言なので `patient` は
書けません**——枠の持ち主が `patient` で、`self` と同じ物だからです（11.5 節「役を書ける場所」）。

```yaml
slots:
  treatment:
    cell_count: 1
    cell: {accept: {tag: treatment}, max: 1}
    put_in: {duration: 30}      # 包帯を当てるのに30分
```

**時間を課すのは入れる側だけ**で、出すのは常に一瞬です。当てるのに手間がかかっても外すのは一瞬、という
非対称の方が普通のためです。

**値段は枠が持ち、経路は持ちません。** プレイヤーが物を入れる操作はカードへ重ねる・レーンへ落とす・端の
矢印で送るの3通りありますが、どれも同じだけかかります。重ねる操作に `duration` を書いて同じことを
表そうとすると、**スロットへ直接落とす経路だけが無料**になり、同じことが経路で違う値段になります。

離す前に値段を見せるのは画面の責務です（[`CardInteraction.md`](../ui/CardInteraction.md) 2 節）。操作の呼び名と説明は `slot_texts` の `put_in`（[Localization.md](Localization.md)）に書きます。

### 7.11 visible_slots（外から中身が見えるスロット）

**`visible_slots`** は、その型の**中身が外から見えるスロットを、見せたい順に並べる**オブジェクトレベルの
キーです（`stack_order` と同じ位置に書きます）。並んだスロットは子ウィンドウのタブになります
（[`Windows.md`](../ui/Windows.md) 1.2 節）。

```yaml
traits:
  item_container:
    visible_slots: [contents]     # かごは中身が見える器。それがこの型の存在意義そのもの

object_defs:
  raft:
    traits: [location]
    visible_slots: [structure]    # 帆は外から見える。積荷は乗り込まないと分からない
```

- **既定は空**です。名乗らないスロットは外から覗けません。筏は土地と同じ `items`/`fixtures`/
  `characters` を持ちますが、外から覗ける場所にすると「開けば中身が並ぶ箱」になってしまいます。
- **真偽値をスロットへ書くのではなく、オブジェクトが名前を並べます。** `property_tags`（6.7 節）・
  `recipe_categories`（3.1 節）と同じ形です。この形だけが次の 3 つを満たします。
  - **綴り間違いをロード時に捕まえられます**（そのスロットを持たなければエラー）。スロット側の真偽値は、
    書き間違えても黙って無視されるだけです。
  - **表示順を宣言順から切り離せます。** スロットの宣言順は既に自動配置の走査順（7.7 節）が使っていて、
    `location` trait が `items` を先頭に置いているのはこぼれた物の行き先を決めるためです。ここに表示順まで
    載せると、無関係な 2 つの関心が 1 つの順序を取り合います。
  - **trait が配ったスロットでも、型ごとに見せるかを変えられます。**
- **trait と自分自身の宣言は足し合わせます**（`tags` と同じ、5 節）。trait 由来を先に、自分自身の宣言を
  後ろに並べ、同じスロットを 2 度書いても先に現れた位置を保ちます。**取り消しはできません**——trait が
  見せると決めたスロットを、参照する側が隠すことはできません。
- **画面に定位置を持つスロットは名乗りません。** 手持ちは常にレーンに出ているので、タブにも出すと
  同じ札が画面に 2 枚出ます（[`Windows.md`](../ui/Windows.md) 1.1 節）。キャラクタが名乗るのは
  装備と怪我だけです。

**「見える」と「入れられる」は別です。** 筏の積荷は名乗っていませんが、筏のカードへ重ねれば積めます
（7.8 節）。中を見るには乗り込む、という違いがそのまま操作の形になります。

### 7.12 storage（物を溜める入れ物）

**`storage: true`** は、その型を**物を溜める入れ物として使う**ことを宣言するオブジェクトレベルのキーです
（既定 `false`）。名乗った型は、上限（`capacity`、7.3 節）を持つスロットの詰まり具合をカードのバーに
出します（[`CardView.md`](../ui/CardView.md) 8 節）。

```yaml
traits:
  item_container:
    storage: true             # かご。中身の枠の詰まり具合をバーに出す

object_defs:
  raft:
    storage: true             # 筏。積荷の枠が上限を持つ
```

- **上限を持つスロットがあるだけでは出しません。** 液体の容器も `capacity` を持ちますが、量を持つのは
  中身の液体自身なので、中身のバーが受け持ちます（[`LiquidContainerSystem.md`](./LiquidContainerSystem.md)
  2 節）。「上限がある」と「物を溜める入れ物である」は別のことです。
- **上限を持つスロットが複数あるときは、最も詰まっているものを出します。** バーが答えるのは
  「あとどれだけ入るか」なので、先に一杯になる側を映します——合計で割ると、片方が満杯でも半分に
  見えてしまいます。
- trait と自分自身の宣言は OR で合成します（`tags` と同じ、5 節）。

### 7.13 resists（条件が成立する間、持ち主を持てない）

**`resists`** は、**その条件が成立している間はどの持ち主にも付けない**ことを宣言するオブジェクトレベルの
キーです（`stack_order` と同じ位置に書きます）。値は条件の並びで、書き方は `conditions`（14 節）と
同じ——暗黙の AND で、主語の既定は `self` です。宣言しなければ、いつでも誰の下へでも入れます。

```yaml
object_defs:
  wild_boar:
    tags: [item]
    resists: [{prop: wariness, gte: 1}]   # 荒ぶっている間は手にも台車にも入らない
```

7.9 節の `bound_to_owner` と対をなします。あちらが「今の持ち主から**離れられない**」を言うのに対し、
こちらは成立している間だけ「そもそも持ち主に**付けない**」を言います。

- **土地だけが持ち主になりません。** 土地（`location` タグ）の枠へは普通に置け、土地から土地への移動
  （自分で隣へ逃げる）も通ります。それ以外の親——手持ち・かご・台車・罠——へは移れません。
- **入れ物の中で成立したら、こぼれ出ます。** 台車に積んだ動物の警戒が上がれば、その瞬間に最も近い
  土地へ落ちます（`destroy` が中身を親へこぼすのと同じ扱い、9.3 節）。土地以外は受け取らなくなるので、
  行き先を名指しせずとも上へ遡るうちに土地が最初の受け取り手になります。
- **読むのは実効値です**（8.3 節）。外から与えられた寄与——罠の `modify` が警戒を打ち消すような——も
  そのまま効くので、掛かっている間は成立せず、取り出した瞬間に成立します。
- **生まれた直後（親を持たない間）の配置は通ります**（`bound_to_owner` と同じ免除、7.9 節）。罠が獲物を
  自分の `catch` へ生むのは、誰かが持ち主になろうとする移動ではありません。通すのは関門だけなので、
  拘束しない入れ物の中へ生まれた物は、付いた直後の判定でそのまま土地までこぼれ出ます。
- **判定が走るのは、値が動いたとき・tick のたび・親が変わったとき**です。tick を見るのは、実体値だけで
  なく寄与の掛かり方も時間で変わるためです。
- **枠ではなくオブジェクトに書く**のは、これがその物の性質だからです。同じ `hand` の枠でも、入れよう
  としている物が石なら入り、荒ぶるイノシシなら入らない、という違いは枠側では言えません（7.9 節と
  同じ理由）。
- trait と自分自身の宣言は、片方だけが持てます（`stack_order` と同じ、5 節）。並び全体が 1 つの条件木
  なので、連結すると書いた覚えのない合わせ技になります。

### 7.14 remove_slots（配られたスロットを落とす）

**`remove_slots`** は、混ぜ終わった `slots` から名指ししたスロットを落とします（`slots` と同じ位置に書く
オブジェクトレベルのキー）。**trait が配ったスロットを持たない型**を書くための唯一の口です。

```yaml
traits:
  location:
    slots:
      items: {cell: {accept: {tag: item}}}
      fixtures: {cell: {accept: {tag: fixture}}}
  sea_zone:
    remove_slots: [items]        # 海は物を置ける場所ではない

object_defs:
  coastal_waters:
    traits: [location, sea_zone] # itemsを持たない場所になる
```

- **落とすのは混ぜ終わってから**なので、**誰が配ったスロットでも落とせます**——`slots` に同名を書いて
  上書きする形（5 節）とは別物で、あちらは同名エントリが複数の trait にあればエラーになります。
- **trait にも書けます。** 落とすことが「その trait であること」の側の事実——海は物を置ける場所では
  ない——なら、混ぜ込まれる型ごとに書かせません。
- **落とす先が無ければロードエラー**です。綴り間違いも、もう配られていない名前も、通せば「落とした
  つもり」の宣言が残ります。同じ宣言の中で `slots` に書きながら `remove_slots` にも挙げるのもエラーです。
- 枠を作るかどうかは、**置いてほしい物ではなく置けてしまう物**で決まります。置けてはいけない物が
  あるなら、条件で弾くのではなく枠そのものを作りません
  （[`GameEndings.md`](../concept/GameEndings.md) 12.7 節）。

## 8. passives（持続する影響）

`passives` は、`self`/`parent`/`child` の関係とゲート（常時／`conditions`／プロパティの stage）に紐づいて
登録され、**その関係が続く限り評価され続ける**、持続する影響を表します。次の 3 つのレベルで定義でき、いずれも
同一の記法・実行原理を用います。

1. **オブジェクトレベル**（例: 防具そのものが持つ複数の恩恵の束）
2. **プロパティレベル**（例: アイテムの重量プロパティが持ち主の負荷に寄与する）
3. **プロパティのステージレベル**（6.4 節）

`passives` は常に配列です（`conditions`/`stages`/`cells`/`pick` と同じ規約で、要素が1つの場合も配列で書きます）。
配列の各要素が独立した1つのブロック（`conditions`/`modify`/`add`）で、複数のブロックを並べることで、
`conditions` ごとに異なる効果を与えられます（8.5 節）。

### 8.1 文法: 操作が上位、対象が下位

`passives` の各要素は、操作（`conditions`/`modify`/`add`）をキーとする辞書型です。`modify`/`add`
の中には、効果の対象を識別子とする対象キーの辞書がぶら下がります。**何を対象キーに書けるかは、場所ごとに
数え上げるのではなく、その宣言が置かれた場所が何を持つかで決まります**——一覧は 14.1 節の表（操作の関係の役は
11.5 節「役を書ける場所」）を見てください。ここは `child`（付いている子それぞれへ登録を配る）を対象に書ける
唯一の場所です。**`modify` の対象にできる範囲はさらに狭く、操作の関係の役では `agent` にしか押せません**
（`add` にこの制限はありません）。理由は 8.3 節。

```yaml
object_defs:
  armor_leather:
    covers: [torso]
    layer: base
    passives:
      - conditions:
          - {in_slot: equip}
        modify:
          parent:
            defense: 5
            speed: 3
            accuracy: 2
```

### 8.2 conditions（ゲート）

- `conditions`（14 節と同じ文法・木構造）が真である間、継続的に有効（レベルトリガー）です。1 つのブロック全体
  （`modify`/`add` に含まれるすべての対象）に対して、共通の `conditions` を 1 つだけ持ちます。
- `conditions` を省略すれば「常時（無条件）」を意味します。
- `self`/`parent` 対象の効果は、どちらも「このブロックを宣言したオブジェクト自身が今どのスロットに入っているか」
  という同じ実体を指すため、`conditions` の `subject` は省略（既定値 `self`）して書くのが自然です（例:
  `{in_slot: equip}` は「自分自身が親の `equip` スロットに入っている間」）。`child` は効果の**対象**
  （8.1 節）専用で、`subject` には書けません（ロード時エラー）——ゲートは1つの解決先を要求するのに対し、
  `child` は複数へ配るための対象だからです。

### 8.3 modify

条件が真である間だけ計算式に寄与する、**可逆的な**修飾子です。条件が偽になった瞬間に寄与は自動的に消えます。値
そのものを書き換えるのではなく、実効値を都度導出するための入力として扱います。

- 同一プロパティに対する複数の `modify` は単純加算で合成します。
- 合成結果の上限・下限（min/max）はプロパティ側の `range`（6.3 節）に持たせます。
- **`modify` の対象にしたプロパティには `on_max`/`on_min` を書けません**（6.3 節）。
- **操作の関係（11.5 節）を対象にできるのは `agent` だけ**です。押した寄与は相手の上で合計され、読んだ側は
  それが誰の寄与かを見分けられません。`agent` は 1 つの操作に 1 人しか居ませんが、`instrument`・`patient` は
  複数の操作に同時に就きうる（2 人が同じ道を歩く、同じ炉に薪をくべる）ので、混ざります。**「一意な参加者にだけ
  押せる」という 1 つの規則**で、役ごとの特例ではありません。
  - 共有されうる相手へ効かせたいことは、**受け手が引く形**で書けます。手当ての間だけ出血が止まるなら、傷の側が
    `conditions: [{subject: agent, ...}]` を付けて自分を `modify` します——`agent` が解決すること自体が
    「今、誰かに手当てされている」を意味します。2 人がかりでも止まるのは 1 回ぶんで、押す形より正しくなります。

### 8.4 add

条件が真である tick 毎に、対象プロパティの実体値へ直接・**不可逆**に加減算します（例: 出血中の血液量減少、耐久値の
毎 tick 減少）。`modify` と全く同じ登録・ゲートの仕組みを使い、違いは可逆か不可逆かだけです。

**`add` は操作の関係（11.5 節）の 3 つの役すべてを対象にできます。** 8.3 節が `agent` だけに絞られているのは、
可逆な寄与が実効値の上で合計され、誰の寄与かを見分けられなくなるためでした。`add` が積むのは実体値で、積まれた
結果は世界に起きた事実なので、後から「誰の操作の分か」を問う必要がありません——**2 人が同じ傷を手当てすれば
2 倍治るのが、`add` の意味そのもの**です。

**動詞が名乗るのは可逆性だけで、一度きりか tick 毎かは置き場所が決めます。** 同じ `add`（9.2 節）を
`interactions` の中に書けば実行の瞬間に 1 回、`passives` の中に書けば条件が真である tick 毎。`transfer`
（9.5 節）も同じ 1 語で両方に置けます。動詞にも「一度きり／継続」を持たせると、ブロックと動詞という
**必ず一致しなければならない 2 つの宣言**を書くことになり、一致しない組み合わせはロード時エラーにしか
なりません（つまり動詞側は情報を足していません）。

逆に `modify` は `passives` にしか置けません。**一度きりの可逆な寄与は成立しない**——誰がいつ戻すのかが
決まらないためです。この非対称は例外ではなく、動詞が可逆性を名乗っていることの帰結です。

継続の意味を持たない動詞（`set`・`destroy`・`spawn`・`move`・`signal`・`become`）は `active` にしか
置けません。毎 tick 壊し続ける物は最初の 1 回で居なくなります。

#### 8.4.1 passives の中の transfer

`transfer`（9.5 節）を `passives` に置くと、条件が真である tick 毎に走る輸送になります。文法は `active`
のものと同一で、対象に操作の関係の役（`agent`/`instrument`/`patient`、11.5 節）を書けるのは、その `passives`
を宣言した個体が今その操作の参加者である間だけです（`add` と同じ、8.4 節）。

```yaml
props:
  stomach:
    value: 0
    range: {min: 0, max: 32}
  digesting:
    value: 0
    range: {min: 0, max: 64}
passives:
  # 胃の中身が毎tick 1ずつ腸へ移る。空の胃からは動かない（出せる量しか動かないため、条件は要らない）
  - transfer: {from_prop: stomach, to_prop: digesting, amount: 1}
  # 腸から蓄えへ。to_amount がそのまま吸収率になる
  - transfer: {from_prop: digesting, to_prop: body_fat, amount: 1, to_amount: 1}
```

**`add` の対で書くのとは、2 つの点で違います。**

- **出せる量しか動きません。** 残り 1 の値から 3 を出そうとしても 1 しか動かず、`add` の対（出す側
  `-3`／受け取る側 `+3`）のように、片方が下限で止まっている間に相手だけが増えることがありません。
- **換算率が 1 箇所にあります。** `to_amount`（9.5 節）が「出した量に対して受け取る量」そのものなので、
  `add` の対のように**必ず一致すべき数値を 2 箇所に置く**必要がありません。

**輸送は宣言順に適用され、互いの結果を見ます**（`active` の命令と同じ、9 節）。上の例で 1 tick に
起きるのは「胃から 1 出る → 腸から 1 出る」の順で、腸へ届いた分はその tick のうちに蓄えへ抜けます。

そのため、**直列に繋いだ輸送の中間に在庫を持たせるのは、速度の差です**。上流を速くすればその差が
中間へ溜まり（`amount: 2` → `amount: 1` なら毎 tick 1 ずつ）、同じ速度なら中間は素通りになります。
エンジン側で「同じ tick では 1 段しか進ませない」ようにしても、稼げる遅れは 1 tick（15 分）だけで、
何時間もの緩衝は結局この差が作ることになります。**置き場所が変わっても動詞の意味は変わらない**、を
保つほうを選んでいます。

輸送は寄与として登録されません（2 つのプロパティを同時に動かす操作は、どちらか一方への寄与としては
表せないため）。宣言したオブジェクトの tick で走り、`from`/`to` はそのつど辿り直されます。

### 8.5 複数ブロック（conditions の使い分け）

同じ対象（例: `parent`）に対して、状況によって異なる効果を与えたい場合は、`passives` に複数のブロックを並べます。
典型例は、装備するスロットによってボーナス量を変えたい武器です。

```yaml
object_defs:
  sword:
    passives:
      - conditions:
          - {in_slot: main_hand}
        modify:
          parent:
            attack: 5
      - conditions:
          - {in_slot: off_hand}
        modify:
          parent:
            attack: 2
```

各ブロックは独立して登録・評価されます。同じ対象・同じプロパティに対して複数のブロックが同時に有効になった場合、
`modify` は 8.3 節の通り単純加算で合成され、`add` も有効な全ブロックの量がそれぞれ tick 毎に反映されます。

### 8.6 ancestor（祖先を辿る対象）

`ancestor` は、**このpassivesを宣言したオブジェクト自身の直接の親から遡り、対象プロパティを定義している
最初の祖先**を対象にします（見つからなければこの効果は何も起きません）。`parent`（1階層固定）と異なり、
途中の親がそのプロパティを持たない場合でも、さらに上の祖先へ自然に届きます。

典型例は、部屋に置かれた暖炉が、その部屋（自分の直接の親とは限らない）の気温を上げる効果です。

```yaml
object_defs:
  fireplace:
    passives:
      - conditions:
          - {prop: lit, eq: 1}
        modify:
          ancestor:
            ambient_temperature: 5
```

暖炉自身が `ambient_temperature` を持たない容器の中に置かれていても、その容器を素通りして、実際に定義している
祖先に効果が届きます。祖先を辿った先が後で移動した場合は再解決され、新しい祖先へ効果が自動的に切り替わります。

`ancestor` は conditions（14 節）の `subject` としても、`base`（6.5 節）の土台の指し先としても使われる、
共通の1つの祖先探索です。

## 9. active（一時的な命令）

`active` は、アクション・組み合わせ・確率分岐の結果が確定した瞬間に、**無条件で1回だけ**適用される命令を指す
概念です。持続する条件を表す `conditions`/ゲートは持たず、`passives`（8 節）のような登録の仕組みにも乗りません。

`active` という語自体は、YAML 上の専用キーとしては書きません。この節で説明する `set`・`add`・`destroy`・
`spawn`・`transfer`・`move`・`signal` を、それが書ける場所（9.7 節）の中に、
`trigger`/`conditions`/`weight` と対等な兄弟キーとして直接書きます。確率分岐の `pick`（10 節）も
これらと対等な兄弟キーで、**いくつでも並べて書け、書いた順に実行されます**（9.7 節）。

### 9.1 文法: 操作が上位、対象が下位

`set`・`add`・`destroy`・`spawn` という操作をキーとして直接書きます。`set`/`add` の中には、対象キーの辞書が
ぶら下がります。**何を対象キーに書けるかは、場所ごとに数え上げるのではなく、その宣言が置かれた場所が何を
持つかで決まります**——一覧は 14.1 節の表（操作の関係の役は 11.5 節「役を書ける場所」）を見てください。
`ancestor` を対象に書いた `set`/`add` は、その祖先（8.6 節）へ書き込みます。

```yaml
interactions:
  eat:
    trigger: menu
    add:
      agent:
        satiety: 10
    destroy: self
```

### 9.2 set / add

どちらも対象プロパティの実体値へ、その場で一度だけ不可逆に反映します。

- `set` は指定した**絶対値**をそのまま代入します。
- `add` は指定した量を既存の値へ**加減算**します。

**同じ `add` を `passives` の中に書けば、条件が真である tick 毎の加算になります**（8.4 節）。一度きりか
継続かを決めるのは動詞ではなく置き場所です。`set` は `active` にしか置けません（毎 tick 同じ値を代入し
続ける意味が無いため）。

`set`/`add` の値は、どちらも**リテラル**（数値・真偽値・シンボル名、6.6 節）だけです。他のプロパティを指す
`{subject, prop}` 参照は使えません（`conditions` の値参照・`weight`・`duration` とはここが異なります）。値の
算出を YAML へ持ち込むと定義ファイルがプログラム化していくためです。在庫に応じて動く量が変わる移送は、
専用の動詞である `transfer`（9.5 節）で表します。

**`set` だけは、値の位置に「その対象キーが名指す個体」を書けます**（`{subject: parent}`）。書き込まれるのは
その個体のインスタンスID（9.6 節）で、**実行時に決まった相手を覚える唯一の手段**です。覚えた相手は
`move` の `to_prop`・`spawn` の `into_prop` がそのまま引きます——筏は出航のときに自分が居た海岸を覚え、
島へ戻る航路はその個体へ帰します（[`Voyage.md`](../world/Voyage.md) 3.5 節）。

```yaml
set_sail:
  trigger: menu
  set: {self: {home_coast_id: {subject: parent}}}   # 押し出す前に、出た海岸を覚える
  move:
    - {subject: agent, to: self}
    - {subject: self, to_object: coastal_waters}
```

書けるのは**対象キーだけ**で、`prop` は書けません。`{subject, prop}` は「そのプロパティの実効値が指す個体」
——つまり値を読む形なので、上の規則のとおり値の位置には置けません。**リテラルとの見分けはスカラーか
マップか**で、値の位置ではスカラーが既にリテラルの綴りだからです（`parent` と書いてもシンボル名です）。

**個体は割れないので、収まらない分は捨てます。** カード1枚を消費する操作（食べる・飲み干す・くべる）は、
`add` が宣言した量をまるごと効かせます。受け取るプロパティの `range.max` を越えた分は `on_max`
（既定のクランプ、6.3 節）が捨てるだけで、**カードが食べかけで残ることはありません**。満腹まであと少しの
ときに大きな食料を食べれば、その差は失われます——「入る分だけ食べる」を書こうとすると、食べかけの
オブジェクトという状態を型ごとに用意することになります。

一部だけを使えるのは**中身入りの容器**（[`LiquidContainerSystem.md`](./LiquidContainerSystem.md) 1 節）
だけです。そちらは `transfer`（9.5 節）が「入る分だけ」動かし、余りを移し元へ残します。**この違いが個体と
量の境目そのもの**で、どちらとして表すかを決めれば、あふれた分の行方も決まります。

### 9.3 destroy

削除したい対象を直接指定します。単一の対象なら `destroy: self` のようにスカラーで、複数の対象を同時に削除する
なら `destroy: [self, instrument]` のようにリストで書きます。**対象は `move` の `subject` と同じ二択**で、
対象キー（**何を書けるかは、その宣言が置かれた場所が何を持つかで決まります**——一覧は 14.1 節の表、操作の
関係の役は 11.5 節「役を書ける場所」）のほかに、インスタンスIDを保持するプロパティ
（`destroy: {prop: smash_target}`、9.6 節）でも指せます。すべてのオブジェクトは必ずworldを根とするツリーに
所属するため（7.1 節）、`destroy` は「現在の親スロットから切り離す」こととして表現できます。繰り返し実行しても
安全（冪等）です。`spawn` と併記するときは `destroy` を先に書きます（9.4 節）。

**中身は道連れにならず、消える物の親へこぼれ出ます。** 壊れたかごの中の物は地面に散らばるのであって、
一緒に消えるわけではありません。ただし単独では在れない物（`bound_to_owner`、7.9 節）は例外で、
こぼれずに一緒に外れます——割れた器の水は残りません。こぼれた先がすでにその tick の中身を数え終えて
いれば、その物はそのtickの残りだけ動きません（1 tick の取りこぼしは、1日96 tickの刻みでは無視できます）。

#### 消し方に名前を添える（`reason`）

**どう消したのかは、消した宣言がその場で名乗ります。** 対象をマップで書くと `reason` を添えられ、
名前は消された側に残ります（`WorldObject.destroyedReason`）。

```yaml
hydration:
  range: {min: 0, max: 336}
  on_min:
    destroy: {subject: self, reason: dehydrated}   # 渇きで死んだ
```

マップの中身は `subject`（省略時は `self`）・`prop`・`reason` の3つで、`prop` を書けばその実効値が
インスタンスIDとして指す相手（`destroy: {prop: smash_target, reason: crushed}`）、書かなければ
`subject` そのものを指します。スカラーとリストの書き方はそのままで、リストの要素にもマップを置けます。
**空のマップ（`destroy: {}`）はロード時エラー**です——既定に任せれば動きますが、それは何も書かずに
`destroy: self` を得る抜け道で、書く理由がありません。

表示文言は locale の `destroy_reason_texts`（[`Localization.md`](./Localization.md)
destroy_reason_texts節）が持ちます。**段（6.4節）とも要件の `reason`（14.6節）とも別の名前空間**で、
同じ綴りを当てても構いませんが、揃っていることを当てにはしません。

**名乗らない消滅は、何も残しません。** 立ち去った獣（`stay_remaining` の `on_min`）と渇きで死んだ獣は、
残った値から見れば同じ「下限で消えた」ですが、名乗るかどうかで分かれます——**消えたことの意味を
知っているのは消した側だけ**なので、後から状態を見て推測しません
（[`VitalsSystem.md`](./VitalsSystem.md) 6 節）。識別子は表示のためだけに使い（`signal` の名前・要件の
`reason` と同じ扱い、9.8 節・14.6 節）、エンジンは名前の意味を知りません。

### 9.4 spawn

`{object, into}` を指定すると、新規オブジェクトを生成し、指定した場所へ配置します。`spawn` は常に **`self`
（この `active` を宣言したオブジェクト自身）が実行するもの**とみなすため、`set`/`add`/`destroy` のような対象
キーのラップを挟みません。

**種類が変わる演出は `destroy` → `spawn` の順に書きます**（`{destroy: self, spawn: {...}}`）。破棄によって
位置が空いてから配置することで、スタック表示（7.6節）における位置の引き継ぎが素直に実現できるためです。
ただし、これは**そう書けば入れ替わったように見せられる場合がある、という程度の規則**です。`destroy` で
そのセルが必ず空くとは限らず（他の物がスタックしている・そもそも `destroy` の対象が居ない）、位置の
引き継ぎは配置時のスロットの状態から決まります（7.6節）。**同じ個体のまま型を差し替えるのは
`become`（9.9 節）です。** `destroy` → `spawn` で立つのは別の個体なので、プロパティもスロットの中身も
引き継ぎません。

挿入先の**スロット名は書きません**。生成物を受け取るオブジェクト（配置先が指す起点）が持つスロットを
**宣言順に走査し、最初に配置できたスロットへ入れます**。著者はスロット名を知る必要がありません。走査の対象外に
できるスロット（`auto_placement`）については 7.7 節を参照してください。

**配置先**は `into` と `into_prop` と `into_object` の**どれか1つ**で指します。**個体を指す3通りは `move` の
移動先（`to`/`to_prop`/`to_object`、9.6 節）とまったく同じ**で、違うのはキーの綴りだけです。`into` だけは、
個体ではないもの——位置（`same_slot`）と走査（`child`）——も名乗れます。

- **省略、または`into: same_slot`**: `self`が今いる、まさにその場所（親と、`self`が現在占めているのと同じスロット）へ
  そのまま配置します。クラフト・腐敗など「同じ場所で別の物に置き換わる」場合に使う既定動作です。スロットの
  走査は行いません。`same_slot`は省略時と全く同じ意味を持つ、明示したい場合のためのキーワードです。
  引き継ぐのは**位置だけ**で、生まれたオブジェクトのプロパティは（配置先の指定によらず）自分の型が
  宣言した初期値（6.2節）から始まります。同じ名前のプロパティを置き換え元も持っていても、その値は移りません。
- **`into`（対象キーか`{subject, prop}`）**: その相手を起点に、持っているスロットを宣言順に走査します。
  **書ける役は宣言の置き場所で決まり、`move`の移動先（9.6 節）と同じ規則です**——その場所に居ない役を
  書くとロード時エラーになります（`on_max`/`on_min`に`agent`は居ないので、そこへ`into: agent`とは
  書けません）。どの置き場所から何を書けるかは 11.5 節「役を書ける場所」の表が唯一の一覧です。
  **実行時に相手へ辿り着けなかったとき**（`into_prop`の指すインスタンスが世界のどこにも居ない、など）は、
  他の対象解決の失敗（9.1 節）と同じく、生まれた物がどこにも置かれずに消えるだけです。
- **`into_prop`**: `self`が持つプロパティ名。その実効値をインスタンスIDとして解釈した個体へ入れます
  （`move`の`to_prop`と同じ）。**実行時に決まった相手へ置く**ための形で、相手を覚えるのは
  `set`（9.2 節）です。
- **`into_object`**: 行き先の型。世界の木を辿って**その型のインスタンス**へ入れます
  （`move`の`to_object`と同じ）。世界にただ1つ在る型（`singleton`、15 節）のためのものです。
- **`into: child`**: `self`の子を順に走査し、**最初に受け取れた子**のスロットへ入れます。走査の決め方は
  スロットに対するものと同じで、著者は「どの子か」も「どのスロットか」も書きません。同じ効果の
  `spawn`は配列の順に1つずつ生んで配置するため、**直前に生んだ子へ続けて物を入れる**のに使えます
  （罠が掛けた獲物へ怪我を渡す経路。[`TrapSystem.md`](./TrapSystem.md) 5.3 節）。受け取れる子が
  1つも無かった場合の伝播先は、`self`の親です。

```yaml
spawn: {object: rotten_wood}
destroy: self
```

```yaml
spawn: {object: item_coconut, into: agent}
```

**`count`（生む個数、省略時は1）** は、同じ宣言を並べるのと同じ意味です。1個ずつ順に生んで配置します
（「ヤシの実が2個見つかる」を、同じ行を2度書かずに書けるようにするためのものです）。

```yaml
spawn: {object: item_coconut, count: 2, into: self}
```

配置先が指す起点のどのスロットにも枠の要件・`capacity`が合わず配置できなかった場合、**`fallback`はYAML上に
存在せず**、その起点自身の親へこぼれます。**こぼれた先でも枠の宣言はそのまま効きます**——受け取ってもらえ
なければさらにその親、さらにその親…と遡り、**どこにも入らなければそのオブジェクトは世界から消えます**
（7.1 節。存在しなかったのと同じ扱いです）。たとえば上の`into: agent`の例は、収穫したアイテムをまず
プレイヤーの手持ちへ入れようとし、埋まっていればagentが今いる場所（`agent`の親）へ落ちる、という
「取得アイテムの置き場所」パターンになります。

**枠が受け入れないものを押し込むことはしません。** 器に入らない物は器の外——手に持てなければ足元へ、
足元にも置けなければ失われる、という順で落ちていくだけです。この落ち方は `destroy` のこぼし（9.3 節）とも
`become` が受け取れなかった中身（9.9 節）とも同じ1つの規則です。

### 9.5 transfer

`set`/`add` は固定の値・量しか書けないため、「在庫に応じて実際に動く量が変わる」移送（例: 容器に入っている
分だけ回復する水分補給）を表現できません。`transfer` は、`from` が指すプロパティの実体値のうち、実際に
出せる量（0未満にはならない量）と `amount` の小さい方だけを、`to` が指すプロパティへ移す専用の動詞です。

`add` と同じく、**`passives` の中に置けば tick 毎に走る輸送**になります（8.4.1 節）。以下の文法は
どちらの置き場所でも同じです。

```yaml
interactions:
  drink:
    trigger: menu
    transfer:
      amount: 2000
      from_prop: volume
      to: agent
      to_prop: hydration
```

- **`from`**（省略可、既定値 `self`）・**`to`**（省略可、既定値 `self`）: 参照ルート。
  `set`/`add` の対象キー（9.1 節）と同じで、何を書けるかは 14.1 節の表が決めます。
- **`from_prop`**・**`to_prop`**: それぞれ移送元・移送先のプロパティ名。
- **`amount`**: 一度に `from` から出すことを試みる量の上限。
- **`to_amount`**（省略可、既定値は `amount`）: `amount` の全量を出したときに `to` が増える量。
  **`from` と `to` の単位が違う移送の換算率**を、比として表します。省略すれば 1 対 1（同じ単位）です。
  実際に増える量は `実際に出した量 × to_amount / amount` で、`allow_overflow: false` のときの
  「収まる分まで」の判定は、`to` の残り容量を `from` の単位へ割り戻してから行います。
  **換算率をエンジンは知りません**——飲んだ水が体内の水分へどれだけ寄与するかは液体の性質なので、
  移送する側の宣言が持ちます（酒は同じ 1 口でも水より寄与が小さい）。0 以下は書けません。
- **`allow_overflow`**（省略可、既定値 `false`）: `to` の `range` に実際に収まる量までしか移動しません
  （収まらない分は `from` に残ります＝液体を無駄にしません）。`true` にすると、`from` の残量と `amount` だけで
  移動量が決まり、`to` の `range` を超えた分は `to` の `on_max`（未指定なら既定のクランプ、6.3 節）に
  委ねます（あふれた分は失われます）。
- **`linked_add`**（省略可）: `add`（9.1 節）と同じ構造で、実際に移動した量に比例してスケールされる
  追加の加減算を表します。各プロパティへの加減算量は `宣言値 × 実際に出した量 / amount` で確定します。
  固定の `add` では表現できない「飲んだ量に比例した副効果」（例: お茶の眠気改善）を表すために使います。

```yaml
interactions:
  drink:
    trigger: menu
    transfer:
      amount: 250            # 水を250mL出す
      to_amount: 10          # 飲みきると水分が10 tick分回復する
      from_prop: volume
      to: agent
      to_prop: hydration
      linked_add:
        agent:
          wakefulness: 2     # 実際に出した量に比例: 250 飲めば +2、125 飲めば +1
```

`from`/`from_prop`/`to`/`to_prop` をフラットな4フィールドにしているのは、`conditions`（14.1 節）の
`subject`/`prop` と同じ理由です（`from`・`to` それぞれ参照は常に1組であり、ネストする必要がないため）。
移送の端点は主語ではないので、`subject` ではなく方向を表す `from`/`to` がそのまま名前になります。

### 9.6 move

`set`/`add`/`destroy`/`spawn`/`transfer` は、対象の所属先（どの親のどのスロットに入っているか）そのものは
変更しません。`move` は、既に世界に存在するオブジェクトを、**別の場所（生成時に確定した特定のインスタンス）
の中へ移動させる**専用の動詞です。`transfer`（9.5 節）が連続量（プロパティの値）を移すのに対し、`move` は
オブジェクト自身の所属を移します。典型例は、土地と土地を繋ぐ道の移動アクション（`agent` を移動先の土地へ移す）です。

```yaml
interactions:
  travel:
    trigger: menu
    move:
      subject: agent
      to_prop: destination_id
```

- **動かす物**: `subject` と `subject_prop` の**どちらか一方**で指します（両方書く・どちらも書かないのは
  ロード時エラー）。
  - **`subject`**: オブジェクトそのものを指すので、指せるのは**その宣言が置かれた場所が用意できる相手**
    です（14.1 節。操作の関係の役は 11.5 節「役を書ける場所」）。`child` は「一度きりの命令に対してどれを
    動かすか」が決まらないため、どの場所でも指せません。`ancestor` は探すプロパティ名を伴わないため同様です。
  - **`subject_prop`**: `self` が持つプロパティ名。`to_prop` と同じく実効値をインスタンスIDとして解釈します
    ——**動かす物も行き先も、実行時に初めて確定する個体を指せます**（動物が足元の物をくわえる 1 手、
    [`HuntingSystem.md`](./HuntingSystem.md) 5 節）。
- **移動先**: `to` と `to_prop` と `to_object` の**どれか1つ**で指します（複数書く・どれも書かないのは
  ロード時エラー）。この三択は `spawn` の配置先（`into`/`into_prop`/`into_object`、9.4 節）と同じもので、
  違うのはキーの綴りだけです。
  - **`to`**: `subject` と同じく、その場所が用意できる相手を指せます（14.1 節）。行き先が定義時点で
    決まっている場合に使います。`parent` は、代表（7.6 節）へリダイレクトされた中身が、自分ではなく容器を
    行き先にしたい場合のためのものです（液体の注ぎ移し、`LiquidContainerSystem.md` 4 節）。指した相手が
    居ない場合は何も起きません。
  - **`to_prop`**: `self` が持つプロパティ名。その実効値を `WorldObject` のインスタンスID（生成時に発行される、
    実行時限りの識別子）として解釈し、移動先とみなします。書き込むのは生成器（地上の道の `destination_id`）か
    `set`（9.2 節。筏が出航した海岸を覚える）です。
  - **`to_object`**: 行き先の型。世界の木を辿って**その型のインスタンス**を探し、移動先とします。
    **世界にただ1つ在る型（`singleton`、15 節）のためのもの**で、海区・本土のように定義の時点で型は
    分かっているが、生成時のインスタンスIDは分からない行き先を指します
    （[`Voyage.md`](../world/Voyage.md) 4 節）。**`singleton` でない型を指すのはロード時エラー**です
    ——複数在りうる型では、どの個体へ着くかを世界の形が決めてしまうためです。
    **型の書き方は 2 通りで、探し方は同じです。** `object_defs` の識別子をそのまま書くか、型を値に持つ
    `self` のプロパティを `{prop: <名前>}` で引きます（6.9 節）。**リテラルと参照の見分けがスカラーか
    マップかなのは `set` の値（9.2 節）と同じ規約**で、同じ行き先を 2 か所へ書き写さずに済ませるための
    ものです。
- **移動先の枠**: `to_slot` に移動先のスロット名を書くと、**その枠だけ**を試します。省略した場合は
  宣言順で最初に受け取れる枠（`spawn` の `into` と同じ走査、7.7 節）です。行き先の型が同じものを
  受け取れる枠を複数持つとき、宣言順に頼らず狙った枠を指すために使います。

`move` は1つでも配列でも書けます（`destroy`・`transfer` と同じ）。**同じ一手で2つ動かす**——筏に乗り込んで
から、その筏ごと漕ぎ出す——のに使います。適用は書かれた順です。

```yaml
move:
  - {subject: agent, to: self}
  - {subject: self, to_object: coastal_waters}
```

プロパティが個体を `object_defs` の id（型）ではなくインスタンスIDで指すのは、典型例（生成された特定の道が
指す特定の移動先）が、**定義時点では決まらず、実行時に初めて確定する個体**を指す必要があるためです。実際の解決は、`self` から所属ツリーの根（`world`、15 節）まで遡り、そこから `InstanceId` が
一致する子孫を探すことで行います。解決できない場合（`to_prop` を持たない、該当インスタンスが世界のどこにも
存在しない）は、他の対象解決の失敗（9.1 節）と同じく、何も起きません。

`to: self` は、組み合わせた相手（`instrument`）を宣言している側の中へ入れる操作（液体を注ぎ移す等）を
書くための形です。

```yaml
traits:
  liquid_container:
    interactions:
      pour_in:
        trigger: {drag: {tag: liquid}}
        move: {subject: instrument, to: self}
```

**物を入れ物へしまうだけなら、これを書く必要はありません。** 受け取れるスロットを持つカード（
7.8 節）へ重ねたらそのスロットへ入る、という動きが画面側にあります
（[`CardInteraction.md`](../ui/CardInteraction.md) 2 節）。重ねる操作を書くのは、
入れる以上のこと（量として混ざる・時間がかかる・条件が要る）を起こしたいときだけです。

移動先が移動対象自身か、その中身である場合（入れ物を自分の中へ入れる）は、ツリーから切り離された輪が
できてしまうため、配置は必ず失敗します（7.1 節）。この判定は 枠の要件・`capacity` とは別の木構造の
不変条件なので、こぼれ落ち（9.4 節）の途中でも省かれません。

配置先の**スロット名は書きません**。`spawn` の `into`（9.4 節）と同様、移動先が持つスロットを宣言順に走査し、
最初に配置できたスロットへ入れます。ただし `spawn` と異なり、`move` には親へのこぼれ落ち（9.4 節）は
**ありません**。移動対象は今いる場所から動かないだけで済むので、配置に失敗した場合は単に元の場所に留まります。

`move` は `interactions`/`pick` の各候補のいずれでも書けます。`on_max`/`on_min`
（6.3 節）でも書けますが、そこに実行者は居ないので **操作の関係の役（11.5 節）を指す形だけがロード時エラー**に
なります（`self` と型・プロパティで書いた移動は成立します——距離が尽きた瞬間に本土へ着く、など)。

### 9.7 この節の操作が書ける場所と、実行される順

この節の操作は次のいずれかの位置に、専用のラップを挟まず直接書きます。持続する条件を表す `conditions`/ゲートを
持つ `passives` とは、書ける場所が構造上重ならないため、両者を混同する余地はありません。

- `interactions` の各エントリ（11 節・12 節）— `trigger`/`conditions`/`duration` と
  対等な兄弟キー
- `pick` の各候補（10 節）— `weight` と対等な兄弟キー
- `props` の `on_max`/`on_min`（6.3 節）— これらは専用のキーの直下にそのまま書きます

**同じ場所へいくつでも並べて書け、適用順は YAML に書かれた順です。** 動詞ごとの優先順位はありません
（`pick`（10 節）も、この節の動詞と対等に並べられる 1 つの操作です）。順序に意味がある組み合わせは、
その意味のとおりの順に書きます——同じプロパティへの `set` と `add`、置き換えの `destroy` と `spawn`
（9.4 節）などです。

```yaml
interactions:
  turn:
    trigger: menu
    add: {self: {fatigue: 1}}   # 分岐に関わらず必ず起こること
    pick:                       # 分岐する部分。共通処理を全候補へ複製しなくてよい
      - weight: 10
        spawn: {object: gore_wound, into: agent}
      - weight: 5
        destroy: self
```

### 9.8 signal（起きたことを告げる）

**世界の形を何も変えず、出来事が起きたことだけを観測する側へ渡します。** 値は出来事の識別子です。

```yaml
interactions:
  strike:
    trigger: {drag: {tag: weapon}}
    pick:
      - weight: 70
        spawn: {object: laceration, into: self}
        signal: hit
      - weight: 30
        signal: missed          # 世界は何も変わらないが、外したことは起きている
```

**誰の身に起きたかは、他の操作と同じ対象キー（9.1 節）で指せます。** 対象を省いた `signal: missed` は
`self` に起きたこととして告げます（宣言した型そのものに起きる場合が大半のため）。

```yaml
interactions:
  strike:
    trigger: {drag: {tag: weapon}}
    signal: {instrument: chipped}   # 殴った側（重ねた武器）に起きたこととして告げる
```

対象は対象キーだけで、`destroy`（9.3 節）のような `{subject, prop}` の形を持ちません。そのため、プロパティ名で
祖先を探す `ancestor` はここでは書けません（ロード時エラー）。

外した回に何も書かないと、その一手は「起きなかった手」と見分けが付きません。観測する側が読むのは
世界に起きた物の出入り（[`ActionSystem.md`](./ActionSystem.md) 7 節）なので、**出入りを伴わない出来事は、
起こした側が告げなければ誰にも届きません**。

- **プロパティのカウンタで代用しません。** 値は効果の入力であって通知路ではなく、増やせば後始末
  （0 へ戻す）が要り、増分は実効値の前後比較にしか現れません。
- **告げるのは出来事であって、見せ方ではありません。** どう見せるか（札の上の文字・音）は受け取った
  側が決めます（[`CardView.md`](../ui/CardView.md) 14 節）。
- 表示文言は locale の `signal_texts`（[`Localization.md`](./Localization.md) signal_texts節）が持ちます。
  要件の `reason`（14.6 節）と同じく、識別子は表示のためだけに使います。

### 9.9 become（同じ個体のまま型を差し替える）

**インスタンスをそのままに、型だけを別の型へ差し替えます。** 水を汲んだ甕が「水入りの甕」になる、
といった**同じ個体の作り変え**のための操作です。

`destroy` → `spawn`（9.4 節）では代用できません。あちらが引き継げるのは位置だけで、インスタンスは
別物になります——札は消えて出直し、プロパティの値も移らず、スロットの中身は親へこぼれます。

```yaml
interactions:
  collect_sap:
    trigger: {drag: {tag: liquid_container}}
    conditions:
      - {reason: not_empty, subject: instrument, prop: fill, eq: 0}
    duration: 4
    become: {subject: instrument, content: sap_liquid}
```

**行き先は識別子ではなく座標で指します**（3.5 節）。`subject` 以外のキーは軸の値で、**書かなかった軸は
変化前の自分から引き継ぎます**。上の例は「重ねられた容器を、中身が樹液の版にする」で、木の側はどの容器が
来るかを知りません。中身を空にするのは `become: {subject: self, content: none}` です。

**生成されていない素の型も、座標の一点です。** 書かなかった軸を引き継ぐという規則が成り立つには、
どの型もどこかの座標に居なければなりません——液体容器なら、手で書いた空の容器が `content: none` に
あたります。

- **`subject`** は `destroy`（9.3 節）と同じ形で指せて、省略すると `self` です。
- **行き先の座標に型が居ない組み合わせは、候補になりません**（12 節）。落とせるのに何も起きない操作を
  出さないためで、`conditions` の不成立と違って `reason`（14.6 節）は持ちません——成立していないのは
  条件ではなく行き先の型そのものだからです。
- 9.7 節のとおり、`active` を書ける位置に他の動詞と対等に並べます。

**「同じ物が姿を変える」すべてがこの操作ではありません。** 行き先は座標なので、**手で書いた別々の型の
あいだは行き来できません**——石と尖った石、ヤシの実と皮を剥いたヤシの実は、それぞれ独立した型なので、
移り変わりは `destroy` と `spawn` が担います（副産物が同時に生まれるのも、そちらなら書けます）。
1 つが 2 つに増える変化は、**個体が 1 つ続く**というこの操作の前提そのものに合いません。

#### 9.9.1 何を引き継ぎ、何を失うか

- **プロパティ**: 同じ名前のプロパティは値を引き継ぎます。新しい型にしか無いものは初期値から始まり
  （6.2 節の範囲値はここで振ります）、新しい型が持たないものは捨てます。`range`（6.3 節）が変わって
  引き継いだ値が外れる場合は**クランプするだけで、`on_max`/`on_min` は発火させません**
  ——器が変わったのは値の出来事ではないためです。
- **スロット**: 同じ名前のスロットが中身を引き取ります。**新しい型が受け取れなかった中身は、
  `destroy`（9.3 節）と同じ規則で親へこぼれます**（`bound_to_owner` な中身は移せる先が無いので、
  そこで失われます）。行き先のスロットが無い場合も、枠（7.2 節）や `capacity`（7.3 節）が足りない
  場合も同じ扱いです——**変わった先の型が持てない状態を作らない**、の 1 つで決まります。中身は
  宣言順に配るので、収まる分が残り、溢れた分が出ていきます。
- **個体の同一性**: インスタンスIDは変わりません。変わるのは型だけなので、**スタックの所属だけを
  判定し直します**（7.6 節）。

**スロットが合わないことを理由に、変化そのものを拒みはしません。** 拒むと、起きなかったことも
その理由も画面に出ません。こぼれるなら結果が見えますし、スロットの違う型へ意図して変えることもできます。

製作の完成——`progress` の `on_max` で作りかけが完成品になる——がこの操作です
（[`RecipeSystem.md`](./RecipeSystem.md) 1 節）。

## 10. pick（重み付き確率分岐）

`pick` は、`set`/`add`/`destroy`/`spawn`/`transfer`/`move`（9 節）を直接書ける場所であればどこでも、**それらと
対等な兄弟キーとして**書ける、重み付き候補のリストです（並べた場合の実行順は 9.7 節）。`passives`
（無条件／`conditions`／stage 内）には書けません。`passives` は「いつ振るか」という瞬間を持たない、
関係とゲートに基づく継続的な評価だからです。

### 10.1 基本構造

各候補は `weight` に加えて、`set`/`add`/`destroy`/`spawn`/`transfer`/`move`（9 節の文法そのまま）を `weight` と対等な
兄弟キーとして直接持ちます。候補が1つしかない場合は、重みの値に関わらず必ずそれが選ばれます。

```yaml
interactions:
  attack:
    trigger: menu
    pick:
      - weight: 50
        destroy: self
      - weight: 50
        destroy: agent
```

候補ごとに影響を受ける対象（`self`/`agent` など）そのものが異なるケースも、このように表現できます。`pick` の
入れ子は再帰的であり、候補の中にさらに別の `pick` を書くこともできます。

各候補に書ける内容は、一時的な命令（`set`/`add`/`destroy`/`spawn`/`transfer`/`move`）に限られます。`modify`
は関係が続く限り評価され続けることに意味がある仕組みのため、1回選ばれて終わる `pick` の候補に書く意味がありません
（`add`/`transfer` を書けば、`passives` の中と違って一度きり効きます、8.4 節）。

### 10.2 weight

`weight` は、専用の計算式（base値＋条件付き補正）を新設せず、以下のいずれかとして表現します。

- **リテラル定数**: 外部からの干渉を想定しない候補向け。
- **既存プロパティへの参照**（`{subject, prop}`、14 節の条件式の葉と同じ書き方。`subject`は省略可で既定値は
  `self`。書ける起点はその宣言が置かれた場所が決めます、14.1 節の表）: 外部から干渉させたい候補向け。参照先は
  通常の `props` として定義された値です。

**この二択より豊かな書き方はありません。** 式（積・和・条件付きの補正）を書ける場所を作らないのは、
可逆な寄与を合成する器を `modify`・`base` の 1 つに保つためです（2 節）。**参照が解決できなければ 0** で、
値が無いこととは区別しません（宣言はされているため）。

2 つの値を合わせたいときは、**合わせた結果を持つプロパティを 1 つ作り**、そこを参照します。土台を他の
オブジェクトから引くなら `base`（6.5 節）、条件で足し引きするなら `modify`（8.3 節）で、どちらも加算です。

```yaml
pick:
  - weight: {prop: accuracy}
    add:
      self: {hp: -10}
  - weight: {prop: evasion}
    destroy: instrument
```

外部からの干渉（「戦闘スキルが高いほど命中しやすい」等）は、`weight` 自体に専用の補正記法を用意するのではなく、
参照先のプロパティに対する通常の `modify` 効果として表現します。

### 10.3 among（周りの物から相手を選ぶ）

候補に `among` を書くと、**その候補が選ばれたときに、周りの物からさらに相手を1つ選んで**から効果を
当てます。選ばれた相手は `picked`（14.1 節の対象キー）で指します。

```yaml
- weight: {prop: snatch}
  among:
    subject: parent            # 候補を探す相手（省略時は self）
    slot: items                # そのスロットの中身が候補
    matches: {not: {tag: quarry}}   # 絞り込み（省略時は中身すべて）
    weight: {subject: picked, prop: volume}   # 候補ごとの重み（省略時は一律）
  move: {subject: picked, to: self}
```

集合の指し方（`subject` + `slot` + `matches`）は、条件の「そのスロットに当てはまる子が居るか」
（14.4 節）とまったく同じ形です。足しているのは**その中から1つ選ぶ**ことと、その重みだけ。

- **重みの参照は候補自身を指すので `{subject: picked, prop: ...}` と書きます。** `subject` の既定が
  `self` である規則（10.2 節）はここでも変わりません。
- 全部の重みが 0 なら先頭の候補が選ばれます（`pick` と同じ規約、10 節）。
- **候補が1つも無ければ、その `pick` の候補は抽選に出ません。** 「相手が居なければ起こらない」を
  条件や重みの打ち消しで書く必要がありません。全部の候補が外れれば、その `pick` は何も起こしません。

`picked` を指せるのは、`among` を書いた候補の中（重みと効果）だけです。それ以外の場所で指すと
ロード時エラーになります（14.1 節）。

## 11. interactions（操作）

操作（`eat`、`travel`、`chop` など）は、きっかけ（`trigger`）と条件（`conditions`）と実行結果
（`set`/`add`/`destroy`/`spawn`/`transfer`/`move`、または `pick`）、および実行にかかるゲーム内時間
（`duration`）を**1つの定義としてまとめて持ちます**。`object_defs`/`traits` の中に `interactions` として
配置します（トップレベル独立キーにはしません）。

**操作は1つの節・1つの名前空間です。** 押して起こすものも、時間が起こすものも、カードを重ねて起こす
ものも、違うのは**きっかけだけ**——条件・効果・所要時間の書き方は丸ごと同じです。同じカードに同名の
操作が2つ並ぶとプレイヤーが見分けられないので、名前は1つの節の中で一意になります。表示文字列も
1つの節へ書きます（[`Localization.md`](./Localization.md) 対応表の形式）。

```yaml
traits:
  eatable:
    interactions:
      eat:
        trigger: menu
        conditions:
          - {subject: agent, prop: satiety, lt: max}
        add:
          agent:
            satiety: 10
        destroy: self
```

### 11.1 trigger（きっかけ）

**何がこの操作を起こすか**を宣言します。必須です。

| 書き方 | 起こすもの | 画面のボタン |
| ------ | ---------- | ------------ |
| `trigger: menu` | プレイヤーが押したとき | 出る |
| `trigger: tick` | 時間が経ったとき | 出ない |
| `trigger: {drag: ...}` | そのカードを重ねたとき（12 節） | 出ない（相手が要るため） |

**画面に出すかは、きっかけから決まります。** ボタンとして並ぶのは `menu` だけです。

`tick` は、**プレイヤーが押す機会の無い操作**です。名前で指して実行される点だけが `menu` と同じに
なります（時間の経過が配る動物の 1 手、[`HuntingSystem.md`](./HuntingSystem.md) 5 節）。

**時間が配るのは手番で、動くのはその物自身です。** きっかけが違うだけで役は同じなので、`tick` の操作にも
`agent` が居ます（11.5 節）——動物の 1 手の `agent` は動物です。

### 11.2 conditions

`{object, prop, op, value}` の葉と `all`/`any`/`not` の複合ノードからなる条件木です（14 節）。トップレベルは
常に配列で、暗黙の `all`（AND）として扱われます。

### 11.3 duration（実行にかかるゲーム内時間）

`duration` は、この操作を実行するのにかかるゲーム内時間（分）です。`trigger`/`conditions`と対等な
兄弟キーとして直接書きます。省略すれば時間を消費しません（例: `eat`のような即座に終わる操作）。
きっかけによらず同じキーを同じ意味で持ちます。

```yaml
interactions:
  explore:
    duration: 30          # 探索は1回30分かかる
    ...
  travel:
    duration: {prop: travel_minutes}    # 道が持つ移動時間をそのまま使う
    ...
```

値は、`weight`（10.2 節）と同じ**リテラル数値**・**`{subject, prop}` 参照**の二択で、10.2 節と同じ解決規則を
共有します。操作の中なので `subject` には操作の関係の役も書けます——**どの役を書けるかは、きっかけによって
違います**（11.5 節「役を書ける場所」）。

**所要時間を持つ側と、それを伸ばす側が別のオブジェクトのときも、ここには式を書きません。** 参照先のプロパティが
`base`（6.5 節）で相手の値を土台にすれば、合成は既にそこで済んでいます——道は自分の長さに歩く人の遅れを継ぎ、
`duration` はその 1 つを読むだけです（11.5 節の例）。

条件（`conditions`）が不成立で操作自体が実行されなかった場合、`duration`は消費されません。時間の消費は
**実行結果が適用される前**に行われます（行動してから結果が出る順序であり、作ったもの・見つけたものが
自分の制作時間・探索時間ぶんのtickを浴びずに済むため）。

その経過中に、tick駆動の変化（劣化による`destroy`など）が`self`/`instrument`/`agent`を消してしまうことが
あります。その場合はその操作を**成立しなかったものとして打ち切り**、効果を適用しません（時間は経過した
ままです）。詳細は[`ActionSystem.md`](./ActionSystem.md) 6.1節。

### 11.4 active / pick

このアクションが実行された瞬間に、`set`/`add`/`destroy`/`spawn`/`transfer`/`move`/`signal`（9 節、`active` の
実体）と `pick`（10 節）が、書かれた順に1回ずつ適用されます（9.7 節）。`trigger`/`conditions`/`duration`と
対等な兄弟キーとして直接書き、専用の `active:` ラップは挟みません。1つも指定しなければ、条件成立時に
何も起きないアクションになります。

**`agent` は、その操作で動いている個体**です（11.5 節）。`parent`（木構造上の直接の格納先）とは独立した参照で、
プレイヤーが起こす操作（`menu`・`drag`）ではプレイヤーキャラクターを指します。

### 11.5 操作の関係（`agent`・`instrument`・`patient`）

操作は「**A が B で C を D する**」の形をしていて、参加者に 3 つの役があります。名前は格から採っています。

| 役 | 格 | 何を指すか |
| --- | --- | --- |
| `agent` | 〜**が** | その操作で動いている個体 |
| `instrument` | 〜**で** | 宣言が乗っていない側の参加者。運ばれてきて働きかけに使われる物 |
| `patient` | 〜**を** | 働きかけられる物。操作の宣言が乗っている側 |

**格は名前の出どころで、どの物がどの役に就くかを決めるのは「宣言がどちらに乗っているか」です。** だから
**どちらの名前も、格が言うほど狭くありません。**

- `instrument` は道具や触媒に限りません。塩と肉から塩漬け肉を作る組み合わせは宣言が肉に在るので、**塩は道具では
  ないが `instrument`** です（燃料・枠へ入れる物も同じ）。
- `patient` も、変化する物や働きかけられる物に限りません。道の `travel` は宣言が道に在るので**道が `patient`**
  ですが、道は変わらず、動くのは `agent` です。

**宣言をどちらに置くかを決めているのが 12.3 節**で、重ねる操作では「変化の本体に置く」——それが `patient` に
なります。相手を伴わない操作（`menu`・`tick`）では、宣言の置き場所がそのまま役を決めます。

- **すべての操作に `agent` が居ます。** きっかけが時間でも（`trigger: tick`、11.1 節）、時間が配るのは手番で、
  動くのはその物自身です（動物の 1 手）。居ないのは `on_max`/`on_min`（6.3 節）だけで、あれは操作ではなく
  値が端に着いた瞬間への反応です。
- **再帰的な操作では、`agent` と `patient` が同じ個体です。** 眠る・休む・動物の 1 手のような、自分に対する行動。
  宣言の中で書けるのは `self`（＝`patient`）と `agent` で、実行時には両方が同じ物を指します。
- **役は、画面での操作の仕方では決まりません。** 枠へ物を入れる操作はカードへ重ねる・レーンへ落とす・端の矢印で
  送るの 3 通りで起こせますが、どれでも入れる物が `instrument` です（7.10 節）。**きっかけの名前（`menu`・`drag`、
  11.1 節）が経路を指すのに対し、役はそれが何であるかを指します。**

#### 役を書ける場所

**宣言が置かれた場所で静的に決まります**（14.1 節の「書ける場所は宣言が置かれた場所で決まる」と同じ線）。
**この表が唯一の一覧で、14.1 節の表はここを指します。**

| 宣言の置き場所 | `agent` | `instrument` | `patient` |
| --- | --- | --- | --- |
| 参加者の `props`（`base`・`passives`） | ○ | ○ | ○ |
| `interactions`（`menu`・`tick`） | ○ | — | ✕ |
| `interactions`（`trigger: {drag: ...}`、12 節） | ○ | ○ | ✕ |
| `put_in`（7.10 節） | ○ | ○ | ✕ |
| レシピの解放条件・`crafting_conditions`（13.3・13.4 節） | ○ | — | — |
| `on_max`/`on_min`（6.3 節） | — | — | — |

- **✕ は「書くとロード時エラー」、— は「その場所に居ないので解決先を持たず、やはりロード時エラー」**です。
  区別が要るのは理由が違うからで、`patient` の ✕ は居ないからではありません。
- **`patient` が操作の宣言の中で書けないのは、役の定義そのものが「宣言が乗っている側」だから**です。
  どの操作でも必ず `self` と同じ物になり、同じ物に 2 つの名前が付くと、読む側は毎回どちらが正かを考えることに
  なります。`agent`・`instrument` の定義にはそれがないので書けます。
  - **`agent` が `self` と同じ物になる操作はあります**——自分に対する行動（眠る・動物の 1 手）です。
    `trigger: tick` は必ずそうなりますが、`menu` の眠るも同じで、**きっかけでは決まりません**。役の定義から
    決まる `patient` とは違い、**その操作が自分に向いているかで決まる**ので、名前を禁じる理由にはなりません
    （書けば `self` と同じ 1 つの物を指すだけです）。
- **参加者の `props` から 3 役とも書けるのは、そこに「宣言元がどの役に就くか」を静的に決めるものが無いから**です。
  実行時にたまたま宣言元自身へ解決することはありますが、それは `self` と同じ物を指す 1 つの参照であって、
  2 つの名前ではありません。
- **レシピの解放条件・`crafting_conditions` は操作ではありません。** 「誰にとって解放されているか」を問う判定
  なので、`agent` だけを問う側が渡します（13.3 節）。

**関係は世界に刻まれます。** 条件（`conditions`）の判定・所要時間（`duration`）の問い合わせ・効果の適用のすべてを、
関係を張った状態で行います。**押す前に見せる分数と、実際に進む分数が同じ数になる**のはこのためで、片方だけで
張ると見せた数と進む数がずれます。

**役を指せるのは参加者からだけです。** 参加していない物（担ぎ手の手の中の道具など）から役を指しても解決しません。

**不変条件: 同じ物が 2 つの操作の `agent` になることはありません**（動作主は一度に 1 つの動作しかできない）。
実行時に検査します。`instrument`・`patient` は複数の操作に同時に就けます——引くだけなら混ざらないためで、
押す側の制限は 8.3 節にあります。

**数えるのは、同時に張られている関係です。** 押す前に分数を見せるための問い合わせは、候補ごとに**1 つずつ
張って外す**ので重なりません（同じ土地から道が 2 本出ていても、2 本ぶんの関係が同時に在ることはない）。
重なるのは、実行中の操作が関係を張り続けている間に、同じ個体を `agent` とする別の操作が始まったときだけです。

**この不変条件から、時間がきっかけの操作は操作の切れ目でしか起きません。** 長い移動の最中にも tick は回るので、
そこで同じ個体の別の操作（眠気が限界に達しての強制睡眠など）が始まると、`agent` が 2 つの操作に就きます。
進行中の操作を中断して別の操作を始めさせる仕組みは 17 節の未決事項です。

荷が重いほど移動に時間がかかる、はこう書きます。

```yaml
object_defs:
  path:
    props:
      # 道の長さに、今歩いている人の遅れを継ぐ。誰も歩いていなければ60のまま
      travel_minutes:
        value: 60
        base: {subject: agent, prop: travel_delay}
    interactions:
      travel:
        trigger: menu
        duration: {prop: travel_minutes}

  character:
    props:
      # 歩みの遅れ（分）。素は0で、荷重や怪我など遅くするものが自分の段から押す
      travel_delay: {value: 0}
```

道が知っているのは「自分の所要時間は歩く人の遅れで伸びる」ことだけで、**遅れの内訳（荷・怪我・暗さ）は
知りません。** 遅くするものが増えても押す先は人の `travel_delay` なので、道の宣言は変わりません。

## 12. trigger: drag（カードを重ねる操作）

きっかけを `{drag: ...}` と書いた操作は、**変化の本体と言えるオブジェクト**に定義します（どちらへ
ドラッグしても成立するので、受け側かどうかで決めません。12.3 節）。`drag` の値が相手のカードに求める型
（4.1 節）で、宣言している側が `self`、相手が `instrument` になります。

```yaml
object_defs:
  wood:
    interactions:
      chop:
        trigger: {drag: {tag: axe_tool}}
        conditions:
          - {subject: instrument, prop: durability, gt: 0}
        add:
          instrument:
            durability: -1
        destroy: self
        spawn: {object: logs}
  logs: {}
  axe_tool:
    tags: [axe_tool]
    props:
      durability:
        value: 10
```

### 12.1 相手の指定

マッチング対象を、**枠の `accept`（7.2 節）と同じ `{tag: ...}` / `{object: ...}` の二択**で指定します
（両方またはどちらもなしはエラー。4.1 節）。

```yaml
interactions:
  chop:
    trigger: {drag: {tag: axe_tool}}          # そのタグを持つあらゆるカード
  ignite:
    trigger: {drag: {object: burning_tinder}} # その型そのものだけ
```

`{tag: ...}` は、そのタグを持つあらゆるカード（パック追加分・trait を介さず直接タグを宣言したカードも
含む）と一致します。`{object: ...}` はその型だけと一致し、**相手が 1 種類しか無い組み合わせのために
単発のタグを新設せずに済みます**。trait 名ではどちらの形でもマッチングしません（4.1 節）。

重ねる操作も `duration`（11.3 節）を持てます。`{subject, prop}` 参照では `instrument` も指せるため、
「使う道具側のプロパティが所要時間を決める」（切れ味の悪い刃物ほど時間がかかる、など）も書けます。

### 12.2 instrument

重ねる操作では、運ばれてきた側が `instrument`（11.5 節の役。「それで働きかける物」）になります。
`set`/`add`/`destroy`/`transfer`（9 節）の対象キー、および `conditions`/`weight`/`duration` の `subject`
（14 節・10.2 節・11.3 節）で指せます。

**画面でどちらの札を掴んだかによらず**、`self` は宣言している側、`instrument` は運ばれてきた側です（12.3 節）。
どちらを掴んだかは経路であって役ではないので、宣言の読み方は変わりません。

### 12.3 どちらのオブジェクトに書くか

**1 つの組み合わせは、片方のオブジェクトにだけ書きます。** 画面は、落とされた側の宣言を先に、
無ければ掴んだ側の宣言を見るので（[`CardInteraction.md`](../ui/CardInteraction.md) 2 節）、
**どちらの札をどちらへドラッグしても同じ 1 つの宣言が実行されます**。両側に書くと 2 つの宣言になり、
同じ内容である保証がありません。

書く先は、**素材の側**です。道具や触媒（刃物・火起こし具）の側ではありません。どちらが素材とも言えない
ときは、**変化の本体**——その組み合わせで姿を変えるほう——に書きます。塩と肉から塩漬け肉ができるなら、
肉に書きます。**これが 2 節の「知っている側に書く」の一例**で、ナイフは自分が何を切れるかを知りませんが、
材料は自分が切れることも焼けることも叩けることも知っています。**書く先が `patient`**（11.5 節）です。

```yaml
object_defs:
  # 槍の柄になる棒が本体。縄はそれを縛る側なので、宣言は棒にだけ置く。
  stick:
    interactions:
      craft_spear:
        trigger: {drag: {tag: rope}}
        destroy: [self, instrument]
        spawn: {object: spear}
  rope:
    tags: [rope]
```

上の例では、縄を棒へ重ねても棒を縄へ重ねても `craft_spear` が実行され、どちらの場合も `self` は棒、
`instrument` は縄です。

同じ相手に対して**両側が別々の組み合わせを宣言している**場合は、落とされた側の宣言が実行されます
（同 2 節）。「刃物を肉へ重ねたら切る」「肉を刃物へ重ねたら切る」のように向きで別の結果にしたいときだけ、
両側に書きます。

### 12.4 allow_multiple（まとめて重ねる）

**既定では、1 回のドロップで組み合わさるのは 1 枚だけです。** きっかけの中に `allow_multiple: true` を
書くと、束からまとめて運んできた枚数ぶんを続けて実行します。**きっかけの中に置くのは、重ねる操作
以外では意味を持たないから**です——外に出すと、書けてしまうが効かないキーができます。

```yaml
interactions:
  add_fuel:
    trigger: {drag: {tag: fuel}, allow_multiple: true}
    duration: 1
    transfer: {amount: 999, from: instrument, from_prop: fuel, to_prop: fuel}
    destroy: instrument
```

**何枚受け取れるかは宣言しません。** 効果が動かす器——値域（`range`）を持つプロパティ——の残りから
エンジンが数えます（炉の `fuel` が満ちるまで何本くべられるか）。プレイヤーが運んだ枚数と、器が
受け取れる枚数の小さいほうが実際の枚数です。

**器が満ちていれば、その組み合わせは候補になりません**（`allow_multiple` の有無によらず）。1 つも
入らないのに実行させると、`destroy: instrument` のように相手を消す効果が、何も入れないまま相手だけを
失わせます。**満杯を拒む条件を書く必要はありません**——上限は `range` が既に言っています。

**それでも許可を宣言させるのは、構造として受け取れることと、まとめて実行させてよいことが別だから**
です。`duration` の大きい操作をまとめて実行すると、プレイヤーが止める手段の無いまま何時間も進みます。
数えられるかはエンジンが答えられますが、それをしてよいかは書いた人にしか分かりません。

許可できるのは、**まとめた枚数の上限を決める器をちょうど 1 つ持つ効果**だけです。器を持たない・複数持つ・
`pick` を含む（引くたびに起きることが変わるので 2 回目が何をするか分からない）宣言に `allow_multiple` を
書くとロード時エラーになります。逆に、器を持つのに書かない宣言は咎めません——それが許可であることの
意味です。

枠へ入れる操作（7.8 節）はこの宣言を持ちません。効果も値段も枠の宣言で決まっていて、書いた人が
選べる余地が無いためです。

重ねる操作の実行時の設計（マッチングの解決、キーの衝突の扱いなど）は `ActionSystem.md` を参照してください。

## 13. recipes（レシピ）

レシピは、成果物の `object_defs` に、名前をキーとする辞書として埋め込みます。**`traits` には書けません**
（複数の型へ混ざる mixin では、どれが成果物か決まらないため。ロード時エラー）。

```yaml
object_defs:
  axe:
    recipes:
      basic:
        icon: axe_wip.png
        conditions:
          - {subject: agent, prop: skill_knapping, in_stage: basic}
        steps:
          - requires:
              - {object: wood, count: 2, consume: true}
              - {object: stone_knife, consume: false}
            duration: 30
          - requires:
              - {object: rope, count: 1, consume: true}
            duration: 10
```

### 13.1 steps / requires

- レシピは 1 つ以上の**工程（`steps`）**からなります。
- 各工程は 1 つ以上の**素材または道具**を要求します（`requires`）。素材（`consume: true`）は消費され、道具
  （`consume: false`）は消耗しますが消費はされません。
- 各工程には所要**時間（`duration`）**が定義されます。
- 最後の工程まで完了すると、目的のアイテムが生成されます。

**要求する相手は、型そのものでもタグでも指せます**（`{object: ...}` / `{tag: ...}` のいずれか一方。
枠の `accept`（7.2 節）・重ねる操作の相手の指定（12.1 節）と同じ形）。道具は「その用途に使える物」で
あって特定の型ではないので、刃物を `{tag: cutting_tool}` で求められます。

```yaml
recipes:
  sewn:
    steps:
      - requires:
          - {object: rawhide, count: 6, consume: true}
          - {tag: sewing_tool, consume: false}
        duration: 300
```

**1 つの物が 2 つの要求を同時には満たしません。** タグで書くと、1 つの物が複数の要求に当てはまり
えます（尖った石は `cutting_tool` にも `sharp_stone` にも当てはまる）。充足の判定も消費も、宣言順に
先に書いた要求から割り当てます。

`count`（要求する**個数**）は省略すると 1 です。かさ（`volume`、mL）とは別物なので、体積の語と
混ざらない名前にしています。`consume` は省略できません（素材か道具かに既定値を置くと、書き忘れが
どちらかとして黙って通るため）。

### 13.2 icon

完成品ごとのアイコン指定です。レシピから自動生成される製作中オブジェクトの型へ引き継がれます（詳細は
`RecipeSystem.md`）。

### 13.3 conditions（解放条件）

そのレシピを**知っているか**の条件です（14 節の条件木。設計は [`SkillSystem.md`](./SkillSystem.md) 4 節）。
省略すれば最初から作れます。素材が揃っているかは 13.1 節の `requires` が見るので、両者は別物です。

**解放条件を評価する時点では、成果物のインスタンスがまだ存在しません。** 宣言元の個体を起点とするルートが
指せないのはこのためです（`subject` に何を書けるかは 14.1 節の表が唯一の一覧）。

**ここは操作ではないので、11.5 節の関係はありません。** 「**誰にとって**解放されているか」を問う判定なので、
`agent` は問う側（一覧を出す画面）が渡します。操作の関係が結ばれていなくても解決する、唯一の `agent` です。

`interactions` の `conditions` と同じく、要素ごとに `reason`（14.6 節）を書けます。未解放の
レシピは解放条件とともに一覧へ出すため、可否と理由が同じ 1 回の評価から得られます。

### 13.4 crafting_conditions（工程を進めるのに要る条件）【確定】

ルートキー（`core.yaml`）で、**すべてのレシピの工程に一律で掛かる条件**です。書き方は `conditions`
（14 節）と同じで、要素ごとに `reason`（14.6 節）を持てます。

```yaml
# core.yaml
crafting_conditions:
  - reason: too_dark
    subject: agent
    prop: hand_brightness
    gte: 5
```

- **`subject` に使えるのは `agent` だけです**（13.3 節と同じ `ReferenceScope`）。工程を進める操作は
  レシピから自動生成される（`RecipeSystem.md` 4 節）ので、条件の書き手は成果物も作りかけも指せません。
- **レシピごとには書けません。** 「3 つ以上の物を組み合わせる複雑な作業」であることはレシピという形が
  既に言っているので、条件をレシピごとに書き分けると、条件の無いレシピが**そう決めたのか書き忘れたのか
  見分けられなく**なります。宣言が 1 つも無い世界では、どんな状況でも工程を進められます。
- 満たしていなければ、工程は進みません（`crafting.tryAdvanceCrafting`）。画面は同じ問いで「作業する」の
  可否と理由を出します。

`interactions` として宣言されている手作業は、この一律の条件には掛かりません——それぞれが自分の
`conditions` に書きます。

レシピの内部設計（製作中オブジェクトの自動生成、枠の要件との連携など）は `RecipeSystem.md` を参照してください。

## 14. conditions（条件式）

条件は、1つの主語について何かを判定する「葉」と、複数の条件を論理積・論理和・否定で束ねる
「複合ノード」からなる木構造です。トップレベルの `conditions:` は常に配列で、暗黙の `all`（論理積）として
扱われます（`passives`/`stages`/`cells`/`pick` と同じ、複数形キーは常に配列という規約、8 節）。

葉はどれも **誰を見るかを決めるキー（`subject`）・主語を絞るキー（`prop`／`slot`）と、演算子キー
（値が比較の相手）** でできています。`subject` は省略でき、既定値は `self` です。

| 主語 | 使える演算子キー | 節 |
|------|------------------|----|
| `prop`（`subject` のそのプロパティの実効値） | `lt`/`lte`/`gt`/`gte`/`eq`/`neq`/`in`/`not_in`/`in_stage` | 14.1 |
| `slot`（`subject` のそのスロットの中身） | `matches` | 14.3 |
| 無し（`subject` 自身） | `in_slot`（親の中での位置）／`matches`（`subject` 自身の型） | 14.2・14.4 |

**同じ `matches` でも、量化は主語が決めます。** `slot` があれば「その中身に当てはまるものが1つでもあるか」、
無ければ「`subject` 自身が当てはまるか」です（14.3 節・14.4 節）。

**演算子キーは1つの葉に複数書けます。** 同じマップ内の複数キーは配列と同じく暗黙の `all` なので、範囲は
`{prop: x, gte: 100, lt: 200}` と書けます。同じ `prop` を2度書いて片方だけ直す事故を避けるためで、矛盾した
組み合わせ（`{gte: 100, lt: 50}`）はロード時には捕まりません（`all` で分けて書いても同じことが書けるため）。
演算子キーが1つも無い葉はロード時エラーです。

### 14.1 葉: プロパティ比較・段判定

```yaml
conditions:
  - {subject: agent, prop: satiety, lt: 12}
  - {subject: agent, prop: load, in_stage: too_heavy}
```

- **`subject`**（省略可、既定値 `self`）: 参照ルート。**この葉が誰を見るか**を決めます。`self`（宣言した
  オブジェクト自身）・`parent`（その親）・`ancestor`（selfの直接の親から遡り、`prop`が指すプロパティを
  定義している最初の祖先。8.6 節と同じ探索ロジック）・`agent`/`instrument`/`patient`（操作の関係の 3 つの役、
  11.5 節）・`child`（付いている子それぞれ、8.1 節）のいずれか。
  `world`（15 節のシングルトン）は未対応（ロード時エラー、17 節）だが、`ancestor` は見つからなければ
  自然にworldまで遡るため、世界固有と思われる概念の参照は `ancestor`で代替できる。

  **どれを書けるかは、その宣言が置かれた場所が何を用意できるかで決まります**（一覧を場所ごとに
  覚える必要はありません）。

  | ルート | 書ける場所 |
  | ------ | ---------- |
  | `self` / `parent` | 宣言元の個体が居る場所（レシピの解放条件だけは、成果物がまだ無いので指せません） |
  | `ancestor` | 上に加えて、`prop` のようにプロパティ名を伴う場所（オブジェクトそのものを指す `in_slot`・`destroy`・`move` では指せません） |
  | `agent` / `instrument` / `patient` | 操作の関係が結ばれている間。**置き場所ごとの可否は 11.5 節「役を書ける場所」の表が唯一の一覧**で、ここには写しません——2 箇所に書くと必ず食い違います |
  | `picked` | `among` を書いた候補の中（10.3 節） |
  | `child` | `passives` の対象（付いている子ごとに登録を配る唯一の場所、8.1 節） |

  解決先を持たないルートを書くとロード時にエラーになり、**その場所に何が無いのか**が理由として出ます。
  書けたのに実行時は必ず空振りする、という書き方をここで塞いでいます。
- **`prop`**: 参照するプロパティ名。
- **比較演算子のキー**: `lt` / `lte` / `gt` / `gte` / `eq` / `neq` / `in` / `not_in`。値が比較の相手で、
  **リテラル**（数値・真偽値・シンボル名、6.6 節）か **`{subject, prop}` 参照**（`weight` の path 参照、
  10.2 節と同じ二択）のいずれか。参照は `lt`/`lte`/`gt`/`gte`/`eq`/`neq` でのみ使えます（`in`/`not_in` は
  複数値との比較のため、単一の参照とは噛み合わずロード時エラーになります。値は配列で書きます）。
- **`in_stage`**: 値はその `prop` の段（6.4 節）の名前で、実効値が今その段に該当していれば真です。
  段の境目を `stages` の `min` と条件の側へ二重に書かずに済みます。段の名前を宣言しているのは
  参照先のオブジェクトの `prop` なので、綴り間違いはロード時には捕まりません（常に偽になります）。

`not_in`/`neq` は `not` で包む形（14.5 節）と同じではありません。**参照が解決できない葉は偽**になるため、
`not` で包むと「解決できなかった」が真に反転します。「祖先に天候の概念が無ければ蒸発しない」のように、
分からないときに効かせたくない条件は否定形の演算子で書きます。

```yaml
conditions:
  - {prop: content, eq: {subject: instrument, prop: content}}   # 2つの動的な値同士を比較する
```

`subject`/`prop` をフラットな2フィールドにしているのは、対象1つ・プロパティ1つの単純な参照であり、
ネストする必要が無いためです。

`prop` が参照する値は、実体値（生の値）ではなく**実効値**（8.3 節の `modify` を加味した値）です。これにより、
`modify` だけで決まる派生プロパティ（例: 天候と時間から決まる日照）も、他の `conditions` から参照できます。
`value` が `{subject, prop}` 参照の場合も同様に実効値を読みます。ただし、あるプロパティの `modify` のゲートが、
直接・間接を問わず自分自身の実効値に依存する（循環参照）と、実行時に例外を送出します
（`PropertyValue.getEffectiveValue` 参照）。この種の循環はエンジン側では防げず、YAML の書き方で避ける必要が
あります。

### 14.2 葉: スロット位置判定

`subject` が指すオブジェクトが、今まさに親のどのスロットに入っているかを判定します（**外側から見た
位置**）。常に等価判定なので、スロット名そのものが値になります（否定したい場合は 14.5 節の `not` で包みます）。

```yaml
conditions:
  - {subject: self, in_slot: equip}
```

`in_slot` は `subject` 自身を主語とする演算子キーなので、`prop` を主語にした葉には書けません（ロード時
エラー）。プロパティ名とスロット名は別の名前空間であり、同じ識別子でも衝突しません。

`ancestor` は「`prop` が指すプロパティ名で祖先を探す」という仕組みのため、探すプロパティを持たない葉
（スロット位置判定・スロット中身判定・型判定）では `subject` に指定できません（14.1 節の表）。

### 14.3 葉: スロット中身判定

`subject` が持つ**そのスロット**の中に、`matches` に当てはまる子オブジェクトが1つでもあるかを判定します
（**内側から見た中身**、14.2 節のスロット位置判定とは向きが逆）。常に存在判定です。

```yaml
conditions:
  - {subject: self, slot: content, matches: {object: water_liquid}}
```

- **`slot`**: 判定対象の、`subject` が持つスロット名。
- **`matches`**: そのスロットの中身に求める型。枠の `accept`（7.2 節）と同じ `{tag: ...}` / `{object: ...}`
  の二択です（4.1 節）。

`slot` は 14.2 節の `in_slot` とは別フィールドです。`in_slot` は「`subject` が親の中でどこにいるか」、`slot` は
「`subject` 自身の中に何が入っているか」という、参照する木構造上の向きが逆であるため、キー名自体を分けて
区別しています。

液体容器のような「中身の種類によって取れる行動が変わる」ケースに使います。中身の種類は、容器の中の専用
スロットへ中身のオブジェクトを1つ置くことで表現します
（[`LiquidContainerSystem.md`](./LiquidContainerSystem.md) 参照）。種類が1つの型で足りるなら
`{object: ...}`、口の広い容器のように仲間が増える役割なら `{tag: ...}` で書きます（4.1 節）。

```yaml
object_defs:
  jar:
    slots:
      content:
        cell_count: 1
        cell: {accept: {tag: liquid}}
        capacity: 4800
    interactions:
      pour_out:
        trigger: menu
        conditions:
          - {slot: content, matches: {object: water_liquid}}
        destroy: self
```

### 14.4 葉: 型判定

`subject` が指すオブジェクト自身が、`matches` に当てはまるかを判定します（否定したい場合は 14.5 節の
`not` で包みます）。

```yaml
conditions:
  - {subject: instrument, matches: {tag: liquid}}      # instrumentがliquidタグを持つ
  - {subject: instrument, matches: {object: raw_meat}} # instrumentが生肉そのもの
```

**14.3 節と同じ `matches` で、違うのは主語だけです。** `slot` を書けば「その中に当てはまる**子**がいるか」、
書かなければ「`subject` **自身**が当てはまるか」になります。量化をキー名にも書くと、同じ指定の形に2つの
名前が付くことになるため、主語だけに担わせています。

### 14.5 複合ノード: all / any / not

複数の条件を組み合わせたい場合、`all`（論理積）・`any`（論理和）・`not`（否定）で入れ子にできます。

```yaml
conditions:
  - any:
      - {in_slot: main_hand}
      - {in_slot: off_hand}
```

トップレベルの配列自体が暗黙の `all` であるため、単純な AND 条件は複合ノードを使わず、葉を並べるだけで書けます。

### 14.6 reason（満たさなかったときに出す理由）

`interactions` の `conditions` の要素には、**満たさなかったときにプレイヤーへ出す理由**を
`reason`（識別子）で添えられます。文言は locale の `reason_texts` が持ちます
（[`Localization.md`](./Localization.md)）。

```yaml
interactions:
  travel:
    trigger: menu
    conditions:
      - {in_slot: fixtures}
      - reason: too_heavy
        not: {subject: agent, prop: load, in_stage: too_heavy}
```

UI は、実行できないアクションのボタンを押せない見た目にし、宣言順で**最初に満たしていない要素**の文言を
出します（[`Windows.md`](../ui/Windows.md) 4 節）。`reason` を持たない要素は理由を出しません
（未発見の道の `in_slot` のように、そもそもプレイヤーへ見せる必要が無い前提条件のためです）。

書けるのは `conditions:` の**要素**にだけで、入れ子の `all`/`any`/`not` の中には書けません。条件木の形から
文を組み立てる（否定・入れ子を自然な文へ直す）方法はどの言語でも一般には無いため、**判定の木は機械のもの、
説明は人のもの**として、要件1つ＝文1つで著者が書きます。`passives` のゲート（8.2 節）は
プレイヤーの操作ではないので持てません。

## 15. singleton（唯一のインスタンス）

「インスタンスが1つだけ存在すべき」という制約は、`object_defs` のエントリに `singleton: true` を追加することで
表現します。

```yaml
object_defs:
  world:
    singleton: true
    props:
      day:
        value: 1
      hour:
        value: 12
        range: {min: 0, max: 24}
        on_max:
          add:
            self:
              hour: -24
              day: 1
      minute:
        value: 0
        range: {min: 0, max: 60}
        on_max:
          add:
            self:
              minute: -60
              hour: 1
```

（実際の定義は `src/assets/world-codex/core.yaml` 参照。ここに挙げたのは日時だけで、累積 tick 数・
天候・季節なども同じ `world` が持つ。）

**「1つだけ存在すべき」は「世界を作った時点で在る」と読みます。** ただし湧かせるのは、`world` が直に
受け入れられる型だけです（`NewGame.spawnSingletonsAcceptedByWorld`）——海区・本土（[`Voyage.md`](../world/Voyage.md) 4 節）は
`world` の `locations` 枠に入るのでそこに在り、キャラクタも `singleton` ですが、`world` のどの枠にも入らない
（土地の `characters` 枠に入る物です）ので湧きません。何が最初から在るかを決めるのは枠の宣言だけで、
エンジンは型の名前を1つも知りません。これにより、型の名前で行き先を指す `move` の `to_object`（9.6 節）は
必ず解決できます。

日時・天候はオブジェクトから直接参照されるのではなく、**環境がオブジェクトに影響を与える**という位置づけです
（例: 明るさによって行動可否が変わる）。直接のプロパティ参照は 14 節の `conditions`（`subject: world`）で使います。

## 16. 本書の対象外

- **地形生成**（`axes`/`location_types`/`generation_scopes`）: 記法自体は本書と同じ「識別子をキーとする辞書」を
  採用し実装済みですが、フィールドの意味・軸空間マッチングのアルゴリズムは地形生成固有の内容であるため、
  本書には含めず [`TerrainGeneration.md`](./TerrainGeneration.md) に委ねます。地形生成によって作られた
  `Location` 自身の構造（スロット・探索・道の発見と移動）は [`ExplorationSystem.md`](./ExplorationSystem.md)
  を参照してください（そちらは本書の `slots`・`props`・`interactions`・`move`・`duration` の応用例です）。
- **`derived`（導出値）**: 「他の props から計算される値」という概念自体、採否がまだ決まっていません（17 節）。
- **表示文字列**: 画面に出す名前・説明文は WorldCodex に持たせません。`object_defs` のキーはあくまで
  識別子であり、表示名は言語ごとの対応表から引きます（[`Localization.md`](./Localization.md)）。

## 17. 今後の検討課題

- `derived`（導出値）の採否。採用する場合、`stages`（6.4 節、`min` による半開区間）とキー名・記法を統一するか
- ステージ切替の瞬間だけ発火する edge-triggered な仕組み（`on_enter`/`on_exit` 的なもの）の要否と記法。「下限に
  達した瞬間」は `on_min`（6.3 節）で解決済みだが、それ以外のステージ境界を跨いだ瞬間に発火したいケースが今後
  生じた場合の対応は未検討
- `day` の上限（無制限のまま加算し続けるか、年単位で wrap して `year` プロパティを持つか）
- `passives`/`active` の対象キーに `sibling`/`descendant` を追加するかどうか（`ancestor` は 8.6 節・6.5 節で
  対応済み）
- **進行中の操作を中断して、同じ個体に別の操作を始めさせる仕組み**。眠気が限界に達しての強制睡眠・体力切れでの
  強制休憩は `trigger: tick` と `conditions` で書けるが（`on_max`/`on_min` は `duration` を持てないので置き場所は
  `interactions`）、**長い移動の最中に始まると `agent` が 2 つの操作に就く**（11.5 節の不変条件）。中断の仕組みを
  入れないなら、強制睡眠は操作の切れ目でしか起きない——歩き終わってから倒れる。どちらにするかはゲームの判断
- **ゲーム内時間で重なる操作**（別々の `agent` が同時に動き、所要時間が重なる）を入れるとき、`patient` から見た
  関係が一意でなくなる（2 人が同じ道を歩けば、道から見て `agent` が 2 人）。そのときは問い合わせる側が関係を
  持ち回る形が要る。**書かれた YAML は変わらず、解決の仕組みだけが変わる**ので、重なる操作が入るまで導入しない。
  それまでは「同じ物が 2 つの操作の `agent` にならない」の実行時検査（11.5 節）が、破れた瞬間に止める
- `pick` の位置づけ（候補に `modify` を書けないことの扱い）
- `pick` の候補から「別のアクションを実行する」ための記法（エフェクトから能動的にアクションを発火する仕組み自体が
  まだない）
- **`conditions` から域（`alert`、6.4 節）を読めないこと**（14.1 節）。「安全域にある間だけ」を書くには
  安全域の段を `in_stage` で列挙して `any` で束ねることになり、段を 1 つ足すたびに条件の側も直す
  （[`VitalsSystem.md`](./VitalsSystem.md) 3.1 節）。閾値の二重書きよりはましだが、二重であることは
  変わらない
- action / combinations の比較演算子セット（14.1 節）の過不足、`between` 等の追加要否
- `subject`（14.1 節・10.2 節）の参照範囲: 現状の実装は `subject` が指すオブジェクト自身が直接持つ
  プロパティ・スロットのみに対応し、任意の階層数を指定するネストした参照（例: 「親の親」を明示的に指定）は
  未対応。「祖先を遡って該当プロパティを持つ最初のオブジェクトを探す」という用途は `ancestor`（8.6 節・6.5 節）
  で対応済み。`world` を `subject` にした参照（world シングルトンインスタンスの実行時追跡が未実装）も未対応
  （ロード時エラー）だが、`ancestor` は見つからなければ自然にworldまで遡るため、多くの場合これで代替できる
- `active`（9 節）の対象キー `child`: 一度きりの命令に対して「どの子か」の意味が確定していないため未対応
  （ロード時エラー）。passives の child 寄与（8 節、関係とゲートに基づく持続的な登録）とは性質が異なる
- `conditions`/`weight` の `value: max`/`value: min`（参照先プロパティの range の上限・下限を指す想定と思われる
  記法）は、規約が本書上どこにも明文化されていないため未対応（ロード時エラー）
- `weight` の合計が0（またはマイナス）になった場合のフォールバック候補の扱いは、宣言順で先頭の候補を選ぶ、と
  実装上決定した（YAML側にフォールバック候補を明示する記法は無い）
- `slots` が character 専有の概念か、コンテナ全般で使い回す汎用概念か
- 重ねる操作に関する未決事項一式（キーの衝突解決、パックによる拡張性など）は `ActionSystem.md` に整理
- レシピに関する未決事項一式は `RecipeSystem.md` に整理
- コンテナの容量・重さに関する未決事項一式は `ContainerSystem.md` に整理
