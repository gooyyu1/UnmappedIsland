# 明るさシステム設計

## 概要

**守備範囲**: 明るさをどう持ち、行動の可否をどう決めるか。単位（EV）・行動が見る2つの明るさ（手元・
視界）とそれを導く環境光・各項（時刻・天気・樹冠・地面の反射・光源）がどのオブジェクトのどのプロパティ
に載るか・行動ごとの要求をどこに書くかを決めます。

**境界**: 天気そのものの駆動は [`ClimateSystem.md`](./ClimateSystem.md)、土地と道は
[`ExplorationSystem.md`](./ExplorationSystem.md)、火の維持と燃料は [`FireSystem.md`](./FireSystem.md)。
**どの値をいくつにするか**（照度とEVの換算・しきい値・土地ごとの樹冠と反射・その結果1日に何時間
行動できるか）は [`ContentSkeleton.md`](../world/ContentSkeleton.md) 8.1節〜8.1.3節が持ち、本書は
繰り返しません。風雨で出歩けないことは明るさでは表さないので（同 8.1節）、それを何の値で表すかも
本書の外です。**火の暖房効果も本書の外です**——光源は明るさのプロパティにしか書かないので、暖まることは
別の値で作ります。

**実現方法**: どの値も普通の数値プロパティで、`props` の `value`（土地ごとの定数）・`range`（クランプ、
[`GameElementDefinition.md`](./GameElementDefinition.md) 6.3節）・`base`（6節）・`modify`（同 8.3節）・
`conditions`（同 14節）だけで組み立てます。計算式を持ち込む `derived`（同 17節）は使いません。ただし
**今の文法には足りないものが1つあり**——値の土台を明示できること（6節）——それを足すまでは書けません。

**在処**: 定義は `src/assets/world-codex/core.yaml`（world）・`locations.yaml`（土地）と各光源の型。
実装・検証はまだありません。

**確定度と実装状況**: **本書の設計はすべて未実装**で、記述は6節を除いて暫定です。6節の文法追加
（`base`）は #656 で採ると決まりました。`core.yaml` の `sunlight` からの移し替え（9節）と、
`GameElementDefinition.md` への文法の追記は別タスクです。

## 1. 明るさはEV（照度の2を底とする対数）で持つ

**明るさを表すプロパティはすべてEVスケール（`EV = log2(照度 / 2.5 lx)`）で持ちます。** 1段が2倍に
あたるので、樹冠が通す割合も天気の透過率も地面の反射率も、**掛け算ではなく足し算の項**になります。

**スケールを名乗るのは本節で、プロパティ名ではありません。** EV（Exposure Value）は本来カメラの露出
設定を表す量で、明るさそのものの単位ではないためです。名前が名乗るのは量のほう（`brightness`）で、
`ambient_temperature` が摂氏を名乗らないのと同じ扱いです。エンジンが持っているのは加算（`modify`・`base`）だけなので、この形でなければ
9桁に渡る照度を扱えません。値の由来と換算表は `ContentSkeleton.md` 8.1.1節にあります。

**光源が複数あるときも単純加算です。** 対数なので厳密には正しくありません（10 lx のランプ2つは 20 lx
＝1段の増加ですが、加算では2段になります）。**この誤差は引き受けて、代わりに光源の値を「暗闇から
何段持ち上げるか」で決めます**（同 8.1.1節）。しきい値との比較にしか使わない値なので、誤差が線を
跨がなければ結果は変わりません。乗算や「大きいほうを採る」といった合成をエンジンへ足すよりも、
**定義ファイルが加算だけで書けることを優先します。**

EVは連続量なので小数を書けます（`GameElementDefinition.md` 6節）が、いまの項はすべて整数です。

## 2. 要る明るさは2つ、それを導く環境光が1つ

**行動の可否を決めるのは2つだけです。**

| 概念 | プロパティ | 決めるもの |
| --- | --- | --- |
| 手元の明るさ | `hand_brightness` | 手元の細かい作業ができるか |
| 視界の明るさ | `looking_brightness` | 屋外で採れるか・土地の間を移動できるか |

**3つ目の `ambient_brightness` は、この2つを導くためだけに在ります**——その場を満たしている、**据え付けの光源が
入っていない**明るさです。据え付けの光が視界を明るくしないこと（3節）と、暗さの底（4節）が、この値の
存在理由です。

宣言は5つで、オブジェクトの木（world → 土地 → キャラクタ → 持ち物）を下りながら育ちます。

| オブジェクト | プロパティ | 土台（`base`） | 自分の `value` | 光源が届くか |
| --- | --- | --- | --- | :-: |
| world | `ambient_brightness` | — | 0（時刻と天気が `modify`） | — |
| 土地 | `ambient_brightness` | world の `ambient_brightness` | 樹冠＋地面の反射 | — |
| 土地 | `hand_brightness` | 自分の `ambient_brightness` | 0 | **据え付けの光源** |
| キャラクタ | `hand_brightness` | 土地の `hand_brightness` | 0 | **持っている光源** |
| キャラクタ | `looking_brightness` | 土地の **`ambient_brightness`** | 0 | **持っている光源** |

**土地は `looking_brightness` を持ちません。** これが「据え付けの光源は視界を明るくしない」の全部です（3節）。

```yaml
# core.yaml — 世界（樹冠も反射も無い場所の明るさ）
world:
  props:
    ambient_brightness:
      value: 0                       # hourのstagesが時刻を、weatherのstagesが天気をmodifyする
      range: {min: -6, max: 17}

# locations.yaml — 密林（樹冠 -7・反射 -2）
location_jungle:
  props:
    ambient_brightness:
      value: -9
      base: {subject: ancestor}      # worldのambient_brightnessが土台
      range: {min: -6, max: 17}
    hand_brightness:
      value: 0
      base: {subject: self, prop: ambient_brightness}       # クランプ済みの環境光が土台

# キャラクタ
character:
  props:
    hand_brightness:
      value: 0
      base: {subject: ancestor, prop: hand_brightness}      # 土地の手元（据え付けの光源を含む）
    looking_brightness:
      value: 0
      base: {subject: ancestor, prop: ambient_brightness}   # 土地の環境光だけ
```

## 3. 光源は、置かれた場所だけで届き先が決まる

**どの光源も同じ2行を書きます。** 種類による書き分けはありません。

```yaml
# 松明。キャンプファイヤーも獣脂のランプも、値が違うだけで同じ2行（火の状態の持ち方はFireSystem.md）
torch:
  passives:
    - conditions: [{prop: lit, eq: 1}]
      modify: {parent: {hand_brightness: 11, looking_brightness: 11}}
```

**親がその値を持っていなければ届きません。**

| 置き方 | `parent` | 手元 | 視界 |
| --- | --- | :-: | :-: |
| 手に持つ | キャラクタ | ○ | ○ |
| 地面や炉に据える | 土地 | ○ | **×**（土地は `looking_brightness` を持たない） |
| 袋にしまう | 袋 | × | × |

**キャンプファイヤーが視界を良くしないのは、それが動かせない設置物だからです。** 光源自身は「自分は
視界に効かない」と知りません。持ち歩けない明かりは道に付いてこないので、**焚き火のそばから夜の道へ
出発することはできません**——松明を地面へ刺した場合も同じで、刺した松明は歩き出した本人を照らしません。

同じ理由で、袋の中へしまった光が土地を照らすこともありません（袋はどちらの値も持たないため、
`modify` は黙って無視されます）。

## 4. 暗さには底がある

**`ambient_brightness` は `range` で −6 を下限とします。** これより暗い場所を区別しません。

底があるのは、**光源が持ち上げる段数を場所によらず一定にするため**です。底が無いと、密林の夜（−9）と
洞窟でランプの効き方が変わり、「1本で歩けるようになる」「作業できる明るさには11本要る」という段が
作れません（`ContentSkeleton.md` 8.1.1節）。

**−6 に現実の根拠はありません**——移動のしきい値（−5）の1段下、というゲーム側の都合です。上限の
**+17 のほうには根拠があり**、快晴の正午（+16）に最も明るい地面（砂浜 +1）を足した、**太陽光だけで
届く最大**です。

**底は光源より前に効きます。** `range` は同じプロパティの中では `modify` の後に効くので、底を持つ値
（`ambient_brightness`）と光源が入る値（`hand_brightness`・`looking_brightness`）を分けてあります。`base` が読むのは相手の
**実効値**なので、`hand_brightness` はクランプ済みの `ambient_brightness` を土台として受け取ります。**2節で土地が
2つの値を持つのは、この順序と、3節の据え付け光源の隔離との、独立した2つの理由からです**——どちらか
一方をやめても、もう一方が2つを要求します。

## 5. 行動ごとの要求は、操作の `conditions` に1行書く

**しきい値は2つで、行動によって見る値が違います。** 満たさなければその行動はできません——遅くなるので
はなく、線を引きます（[`DesignPrinciples.md`](../concept/DesignPrinciples.md) の「悪条件は、効率を
下げるのではなく、できる／できないの線で効かせる」節）。

| 行動のクラス | 見る値 | しきい値 | 書く場所 |
| --- | --- | --: | --- |
| 土地の間を移動する | `looking_brightness` | −5 | `path` の `travel`（`ExplorationSystem.md` 3節） |
| 屋外で採る・探索する | `looking_brightness` | +5 | 土地の `explore` と、各採取の操作 |
| 手元の細かい作業 | `hand_brightness` | +5 | 製作を進める操作（[`RecipeSystem.md`](./RecipeSystem.md)） |

```yaml
path:
  interactions:
    travel:
      conditions:
        - {in_slot: fixtures}
        - reason: too_dark
          subject: actor
          prop: looking_brightness
          gte: -5
```

- **主語は `actor` です。** 行動が見るのはキャラクタ側の2つで、キャラクタは操作を実行している本人だから
  です（`GameElementDefinition.md` 14.1節）。
- **`reason` を添えます**（同 14.6節）。暗くてできないことは、ボタンが押せないだけでは伝わりません。
- **明るさの条件を書かない操作は、暗さに依らずできる**という意味になります（食べる・飲む・眠る・火を
  くべる）。書き忘れと見分けが付かないので、見張り方を未決事項に挙げています。

**夜、焚き火のそばで作ることはできますが、採りには出られません。** しきい値は同じ +5 でも、作る側は
`hand_brightness`（据え付けの光源を含む）を、採る側は `looking_brightness`（含まない）を見るためです。

**移動できるかは、出発する土地の明るさで決めます。** 道は自分の明るさを持ちません——道の型が持って
いるのは行き先の識別子だけで（`ExplorationSystem.md` 3節）、条件から行き先の土地のプロパティは辿れない
ためです。`ContentSkeleton.md` 8.1.2節が未決としていた「道がどちらの明るさを採るか」への、本書側の答えが
これです。

## 6. 足りない文法: 値の土台を明示できること【確定】

**`inherit: true`（`GameElementDefinition.md` 6.5節）を廃し、土台を指せる `base` に置き換えます。**

```yaml
# 祖先の同名（propを省略）
ambient_brightness: {value: -9, base: {subject: ancestor}}
# 自分の別のプロパティ
hand_brightness: {value: 0, base: {subject: self, prop: ambient_brightness}}
# 祖先の、別名のプロパティ
looking_brightness: {value: 0, base: {subject: ancestor, prop: ambient_brightness}}
```

- **読むのは相手の実効値**（クランプ済み・`modify` 込み）で、自分の `value` はそこへ**加算**されます。
  どちらも今の `inherit` と同じ挙動で、**演算は1つも増えません**。
- **`{subject, prop}` は既存の語彙です。** `conditions`（14.1節）・`weight`（10.2節）・`duration`
  （11.3節）と共有で、`subject` 省略時の既定が `self` であることも、`ancestor` が 8.6節と同じ祖先探索
  であることも同じです。`prop` を省略すると同名を指します。
- **1つのプロパティに `base` は1つだけ**です。加算の相手が増えると、実効値がどこから来たのか読めなく
  なります。
- **`subject: self` のとき `prop` は必須**です（省略すると自分自身を指すため、ロード時エラー）。`self`
  を辿る循環は同じオブジェクトの中で閉じるので、ロード時に検出できます。

**`inherit: true` は残しません。** `base: {subject: ancestor}` と書けば同じで、同じことに書き方が2つ
あると、読む側が毎回どちらが正かを考えることになります。既存の使用は `traps.yaml` の2箇所だけです。

なぜ土台を指せる必要があるかというと、詰まるのは**1つの世界の値から、土地ごとに違う2つの組み合わせ
（樹冠と反射だけ／それに据え付けの光源を足したもの）を作る**ところです。継ぎ元が「祖先の同名」に
固定されている限り、2つ目の組み合わせには2本目の継承の道が要ります。却下した案は2つです。

- **世界の側に2系統持たせる**（world が両方を持ち、土地が別々に継ぐ）。時刻と天気の寄与が全部2箇所に
  書かれ、**暗黙に一致すべき数が11個増えます**。
- **行動ごとの「必要な明るさ」を土地が持つ**（しきい値 − 反射を土地のプロパティにする）。**今の文法
  だけで書けます**が、反射が土地ごとに行動クラスの数だけ複製され、加えて「砂浜では移動に要る明るさが
  低い」という、現実には無い意味の値になります——明るいのは地面であって、必要な明るさが変わるわけでは
  ありません。

## 7. 空を継がない場所は、光源だけで決まる

**洞窟は `base` を書きません。** 樹冠を −∞ にするのではなく、空から光が来ないことを「土台を持たない」で
表します。`value` は底そのもの（−6）です。

```yaml
location_cave:
  props:
    ambient_brightness:
      value: -6                      # baseが無い＝空から光が来ない
      range: {min: -6, max: 17}
    hand_brightness:
      value: 0
      base: {subject: self, prop: ambient_brightness}
```

これで**洞窟は昼でも真っ暗**になり、探索には必ず光源が要ります。屋根を持つ建物を作ったときも同じ形に
なります。

## 8. 段（`stages`）は環境光にだけ置く

**段を持つのは `ambient_brightness` だけで、行動の可否は段では判定しません。** 段は「今どのくらい明るいか」を
他の値や画面へ渡すための粗い区分で、境目は5節のしきい値に合わせた2つです——`pitch_dark`（−5未満）・
`dim`（−5〜+4）・`bright`（+5以上）。

境目をしきい値に合わせてあるのは、**プレイヤーの目に見える変化と、できることの変化が同じ瞬間に
起きるため**です。段の側を細かくしても、できることは変わりません。

## 9. `sunlight` を読んでいる3箇所は、移し替えが要る

**今の `sunlight`（抽象値0〜20）を消すと、それを読んでいる3箇所が同時に動きます。** どれも本書の
担当外なので、ここでは移し先だけを挙げます（実際の書き換えは別タスク）。

| 今の読み手 | 移し先 |
| --- | --- |
| 気温への寄与（`core.yaml` の `sunlight` の `stages`） | world の `ambient_brightness` の段（8節） |
| 空の色（`src/game/looks/skyTint.ts`） | world の `ambient_brightness`。夜が0へクランプされる前提も要見直し |
| 水の蒸発（`liquid_containers.yaml`、[`LiquidContainerSystem.md`](./LiquidContainerSystem.md)） | world の `ambient_brightness` |

**どれも world の側を見ます。** 土地の `ambient_brightness` には樹冠と地面の反射が入っているので、日射の
代わりにはなりません。

時刻の段（2節）も、太陽高度に合わせて切り直す必要があります。**今の `hour` の4段
（`core.yaml` の night/morning/day/evening）では刻みが粗すぎます。**

## 未決事項・今後の検討課題

- **明るさの条件の書き忘れをどう見張るか。** 書かなければ「暗くてもできる」になり、書き忘れと区別が
  付きません（5節）。操作の一覧を出して、明るさの条件を持たないものを並べる検査が要ります。
- **火の暖房効果をどの値で表すか。** 光源は明るさのプロパティにしか書かないので、**明るさは室温に
  影響しません**。焚き火で暖まることは別の値として、同じ物（キャンプファイヤー）がもう1行書く形に
  なります。
- **風雨で行動が止まることを、どの値で表すか**（`ContentSkeleton.md` 8.1節）。明るさとは別の値です。
- **樹冠と地面の反射が、定義の上では1つの `value` に潰れています。** 内訳は
  `ContentSkeleton.md` 8.1.2節の表が持ちます。分けて持ちたくなったら、反射のほうを土地の `passives`
  から自分の `ambient_brightness` へ `modify` する形にできます。
- **月齢を入れるか。** 今は満月固定です。入れると夜の空が月と星のどちらかになり、対数の加算では
  合成できない場面（1節）がもう1つ増えます。
- **暗くて何もできない時間の見せ方。** 押せないボタンと `reason` だけで足りるか、日が暮れる前に
  気付ける形が要るかは、[`Windows.md`](../ui/Windows.md) 側の話として未検討です。
- **移動の途中で暗くなる扱い。** いまは出発時の1回しか見ません（5節）。長い道を歩いている間に日が
  暮れる場合をどうするかは決めていません。
