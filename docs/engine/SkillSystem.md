# スキルシステム設計

## 概要

本ドキュメントは、レシピが**いつ作れるようになるか**を決める仕組みをまとめたものです。何を作れるかの定義
（`recipes` の文法）は [`GameElementDefinition.md`](./GameElementDefinition.md) 13 節、レシピが成立する
仕組みは [`RecipeSystem.md`](./RecipeSystem.md) の担当です。

[`ExplorationSystem.md`](./ExplorationSystem.md) と同じく、専用の新しい文法は導入せず、既存の
`props`/`stages`/`conditions`/`passives`/`actions` の応用として組みます（唯一の例外は 4 節）。

本ドキュメントは検討結果であり、確定仕様書ではありません。未決事項は 8 節に整理しています。

## 1. 「研究」という別概念を持たない

スキルは、領域ごとの習熟度を表す数値プロパティです。レシピの解放条件は、対応するスキルが一定の段に
達していることとして表します。「研究課題を明示的に選び、それが完了するまで待つ」という枠は設けません。

スキルは工程ではなく**領域**なので、素材チェーンと直交します。解放のゲートを素材チェーンに沿って置くと、
中間素材が 1 段増えるたびに解放待ちが直列に挟まり、進行が間延びします。

## 2. スキルはキャラクターのプロパティ

スキルはプレイヤーキャラクターの `props` として持たせます。`conditions` の `object: actor`
（14.1 節）から直接参照でき、`world` シングルトンを参照する迂回（同節、`object: world` は未対応）が
要りません。

```yaml
object_defs:
  player_character:
    props:
      skill_cordage:
        value: 0
        stages:
          - name: novice
            min: 0
          - name: basic
            min: 20
          - name: skilled
            min: 60
          - name: expert
            min: 180
```

## 3. 進捗の 3 経路

スキル値は、次の 3 つの経路から同じプロパティへ加算されます。仕組みは共通で、係数だけが違います。

| 経路 | 契機 | 量 |
| ---- | ---- | -- |
| 発見 | 探索で未知の物・場所に出会う（[`ExplorationSystem.md`](./ExplorationSystem.md)） | 小 |
| 実行 | 関連する行動・製作を行う | 中 |
| 集中 | 3.1 節の専用アクション | 大 |

発見と実行は、契機となる `actions`/`combinations` の効果として `actor` のスキルへ `add` します。
tick ごとの自然増加は持たせません（何もしていない時間に伸びると、プレイヤーの行動が進捗と無関係になるため）。

```yaml
actions:
  make_cord:
    duration: 30
    add:
      actor:
        skill_cordage: 2
```

### 3.1 集中（時間と集中資源を払って伸ばす）

発見と実行だけでは、**今できることしか伸びません**。生存の仕方が固定されると、そこから外れたスキルへ
移る経路が無くなります。集中は、今の暮らし方が自然に与えてくれないスキルへ投資する唯一の経路であり、
このシステムでプレイヤーが行う実質的な意思決定はここに集約されます。

対価はゲーム内時間（`duration`、11.3 節）だけにしません。時間だけだと、手が空いているときに実行するのが
常に正解になり、決定になりません。時間と併せて、生存と競合する資源（集中力・幸福度など。具体的な選択は
8 節）を消費させます。

## 4. 解放条件は段のしきい値

レシピの解放は、`recipes` のエントリに `conditions`（14 節）を書き、`actor` のスキル段を判定する形で
表します。

```yaml
object_defs:
  fishing_net:
    recipes:
      basic:
        conditions:
          - {object: actor, prop: skill_cordage, in_stage: skilled}
        steps: ...
```

`conditions` は既存の条件木をそのまま使いますが、**`recipes` のエントリがこのキーを持てること自体は
本システムで追加する必要があります**（13 節には現在ありません）。本システムが必要とする文法の追加は
これだけです。

条件を満たさないレシピは、解放条件とともに一覧に表示します（作れないものが見えないと、必要なレシピに
辿り着けないまま詰みます）。誘導のための表示条件と、実際に作れるかの可否条件は別に持ちます。

## 5. 表示: レベルと段内進捗

スキル値は指数的に増えるため（6 節）、生の値や最大値に対する割合をそのまま出すと、序盤が常にほぼ 0% に
見えます。UI へは次の 2 つに分けて出します。

- **レベル** — 現在いる段（`stages` の `name`）。段はしきい値ごとに 1 つなので、等間隔に並んで見えます。
- **段内進捗** — `(現在値 - 現在の段の min) ÷ (次の段の min - 現在の段の min)`。段が上がるたび 0 に戻ります。

対数を取った値は出しません。対数表示は指数的な鈍化を打ち消してしまい、「低い段の作業を繰り返しても
伸びが悪い」という、鈍化によって伝えたい情報そのものを隠します。段内進捗であれば、上の段ほどバーが
目に見えて進まなくなり、鈍化が体感として残ります。

どちらも `stages` の境界からの純粋な計算なので、UI 側で導出します。採否が未決の `derived`（17 節）は
必要としません。

## 6. 数値の置き方

**指数はしきい値（`stages` の `min`）側に置き、1 回あたりの獲得量は小さい整数に保ちます。** 獲得量を
指数にすると、YAML に 1 と 4096 が並んで行動間の相対的な重み付けが読めなくなります。

目安は 1 スキルあたり 4〜6 段、しきい値の比は 2.5〜3 程度です。

## 7. この仕組みが成立する前提

スキルは実際に行ったことから伸びるため、**生存の仕方が実質 1 通りしかないと、全員が同じスキルを同じ順で
伸ばします**。その場合、この仕組みは分岐を生まず、進行を演出するだけのものになります。

逆に、同じ生存課題に対して複数の方針が拮抗していれば、スキルの伸び方とレシピの解放順は、追加の記述なしに
分岐します。したがって、方針の拮抗はコンテンツ側の調整課題であると同時に、**本システムが機能するための
前提条件**です。マップがランダム生成であることは、方針ごとの有利不利を島の側へ分散できるため、この調整を
容易にします。

なお、低い段の作業の繰り返しで上位のレシピへ到達できてしまうかどうかは、しきい値だけでは決まりません
（指数的なしきい値は到達を遅くするだけで、防ぎはしません）。本作では時間が最も希少な資源であり、稼ぎに
費やした時間は生存に使えないため、当面は時間コストによる抑止だけを持たせます。実際に稼ぎが成立して
しまう場合は、その行動のコストがレシピ側で安すぎることを先に疑います。

## 8. 未決事項

- スキルの粒度と個数（領域の切り方。後から変更しにくいため、実装前に決める）
- 集中が消費する資源。専用の集中力プロパティを設けるか、既存の幸福度・眠気で払わせるか
- 集中アクションの置き場所（キャラクター自身の `actions` として持てるか）
- 発見によるスキル加算の契機を、型ごとに書くか、タグ（4.1 節）ごとに書くか。タグ側にすると、島の生成で
  どの植物が出ても条件を満たせるため、ランダム生成との相性が良い
- レシピ一覧で未解放のものを見せる際の、解放条件の表示粒度（どのスキルがどの段に必要か、をどこまで出すか）
- スキルが解放（二値）だけでなく、製作の速度・歩留まりへ連続的に影響するかどうか
- 方針間の均衡を検査する診断の形（[`../diagnostics/`](../diagnostics/README.md) に置く、レシピ DAG を辿った
  静的なコスト集計）
- 到達可能性の検査をテストとして持つ形（何も持たない状態から「今作れるもの」の閉包を取り、全レシピが
  到達可能かを確かめる）
