# コンテナの容量と重さ

## 概要

本ドキュメントは、`slots` の `weight_rate`（`GameElementDefinition.md` 7.4 節）を使って、重さの伝播・行動力への
影響をどう成立させるかをまとめたものです。`capacity`（合計サイズの制約、同 7.3 節）は `move_to_slot` が検証するだけの
単純な仕組みで、文法以上の設計判断を要しないため、重さについては伝播にのみ焦点を当てます。あわせて、入れ物が
中身を環境から守ることをどう表すか（4 節）を扱います。`capacity`/`weight_rate` 自体の文法、および
`RecipeSystem.md` の `accepts`（型・個数の制約）との関係は `GameElementDefinition.md` を参照してください。

実際にゲームへ登場させる入れ物の一覧と比較は [`../world/Containers.md`](../world/Containers.md) です。

本ドキュメントは検討結果であり、確定仕様書ではありません。未決事項は 4 節に整理しています。

## 1. 重さの伝播は move_to_slot の副作用として扱う

コンテナ自体の重さは、中に入っているアイテムの重さの影響を受けます（バックパックの中身が増えれば、バックパック
自体が重くなる）。これは計算式（`derived`）ではなく、既存の `move_to_slot`（唯一の汎用操作）に「アイテムが
スロットに出入りするたびに、そのアイテムの実効重量をスロットの持ち主の `weight` へ加減算する」という不変条件を
1つ持たせるだけで実現します。

温度・湿度（`ClimateSystem.md`）の「毎 tick 加減算する」方式とは異なり、**スロット移動という離散イベントの度に
1回だけ加減算する**方式です。新しいトリガー体系は追加しません。

入れ子（アイテム→バッグ→バックパック→装備）も、この仕組みが再帰的に働くことで自然にカスケードします。バッグ
自身の `weight` は、バッグの中身の出入りに応じて常に最新化されているため、バッグをバックパックに入れる瞬間は
「バッグの現在の `weight`」を1回伝播させるだけで済みます。

## 2. weight_rate は「身につけると軽い」も「軽減能力の高い箱」も同じ仕組みで説明する

「身につけると手荷物より軽い」も「台車は中身が増えても重さが増えにくい」も、どちらも `weight_rate`
（スロットごとの伝播率）で説明します。

```yaml
object_defs:
  character:
    slots:
      equip:
        weight_rate: 0.5    # 身につけると重さが半分に感じる
      inventory:
        weight_rate: 1.0    # 手荷物はそのまま
  cart:
    props:
      weight:
        value: 20
    slots:
      storage:
        weight_rate: 0.1    # 中身の重さの10%しか伝播しない
```

バックパックを背負うと軽く感じる、という現象も、`character.equip` と `backpack.storage` 両方の `weight_rate` が
効いた結果として説明できます。コンテナごとに専用の「軽減能力」という別概念は作りません。

## 3. 行動力への影響

キャラクターの合計重量（各スロットからの伝播の総和）を `weight` のようなプロパティとして持たせ、既存の `stages`
（`GameElementDefinition.md` 6.4 節）で「軽い/やや重い/かなり重い/動けない」のような段階に分けます。あとは
`move` アクションの条件・効果として、重量段階を通常通り参照するだけです。

```yaml
actions:
  move:
    conditions:
      - {path: actor.encumbrance_stage, op: neq, value: immobile}
```

移動時間の延長は各段階の `passive` の `modify`、疲労の増加は毎 tick 蓄積する `accumulate` で表現すればよく、
新しい仕組みは不要です。重さの伝播自体は、どのオブジェクトの `slots` でも同じように起きます。「行動力に影響する」
のはキャラクター自身の `weight` を読む `stages`/`actions` だけなので、地面に置かれた宝箱の重さが誰の行動力にも
影響しないのは自然な帰結です。

## 4. 環境からの保護は sheltered プロパティ1つで表す

蓋のある入れ物に入れた物が天候から守られることは、`sheltered`（0/1）というプロパティ1つで表します。
中身側の屋外劣化（`DurabilitySystem.md` 2 節）の `accumulate` を、次の条件でゲートするだけです。

```yaml
conditions:
  - {object: ancestor, prop: sheltered, value: 0}
```

要点は、**守る入れ物だけが `sheltered: 1` を定義し、守らない入れ物は定義しない**ことです（`world` が
`sheltered: 0` を定義して既定値を与えます）。`ancestor` は「そのプロパティを定義している最初の祖先」を
探すため（8.6 節）、定義しない入れ物は素通りされます。結果として、蓋のない籠を蓋つきの箱にしまえば籠の
中身まで守られ、その籠を地面に置けば `world` まで遡って `0` になる、という入れ子の振る舞いが、新しい
文法なしで正しく出ます。将来の屋根・小屋も同じプロパティを定義するだけで同じように働きます。

守れるのは天候による屋外劣化だけです。保存温度由来の腐敗は別の `accumulate` なので止まりません
（`DurabilitySystem.md` 3 節）。蓋つきの箱に生肉を入れても「屋外・晴れ・通常温度の2日」が「通常温度の
2.5日」に戻るだけで、保冷は別の軸のまま残ります。保護を強くしすぎない歯止めとして、この分離をそのまま
使います。

## 5. 未決事項・今後の検討課題

- 既に中に入っているアイテムの重さが後から変化した場合（例: 松明の燃料が減って軽くなる）、`move_to_slot` は
  出入りの瞬間にしか発火しないため、入れっぱなしのまま重さが変わってもコンテナ側の `weight` は自動的に追従
  しない。これを許容する仕様上の割り切りとするか、何らかの再伝播の仕組みを別途用意するか
- `size`/`capacity` が単純なスカラー数値で十分か、それとも将来的に形状（テトリス型インベントリ等）を考慮したいか
- `weight_rate` が 1.0 を超える（かえって重く感じる）ケースを想定する必要があるか
- `size`/`capacity`/`weight_rate` の具体的な数値・単位（本書のサンプルはあくまで説明用）
- 重さの伝播（1 節）と `RecipeSystem.md` の `accepts` から自動生成される `combinations`（材料投入）が、同じ
  `move_to_slot` イベントに対してどちらも副作用として発火する場合の実行順序
- 中身の入った入れ物が壊れたときの中身の扱い。`destroy` は親スロットからの切り離しなので（9.3 節）中身も
  一緒に消え、`move` が動かせるのは `actor`/`dragged` だけなので（9.6 節）中身を親へ吐き出す書き方が無い。
  「壊れるときに中身をどうするか」は入れ物自身の責務なので、エンジン側の不変条件として持たせるのが素直。
  それまでは `durability` を下限 0 で止めて `destroy` しない（ぼろぼろでも使える）ことで回避できる
- 入れ物ごとの「何種類入るか」は `contents` の `unit_capacity`（7.6 節）で決まるが、現在の
  `containers.yaml` は未指定（＝無制限）。入れ物の差別化はここが主な数値になる
- 入れ子（籠の中の籠）を禁じるのは自己包含だけなので、`size`/`weight` が定義されるまでは枠を無限に
  増やせる
