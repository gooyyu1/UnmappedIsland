# レシピシステム設計

## 概要

本ドキュメントは、`recipes`（`GameElementDefinition.md` 13 節）の文法を使って、2つ以上のアイテムを組み合わせて
新しいアイテムを作成する仕組み（道具の生成・建物の建築の両方に使う）をどう成立させるかをまとめたものです。
`recipes`/`steps`/`requires`/`icon` 自体の文法は `GameElementDefinition.md` 13 節を参照してください。

本ドキュメントは検討結果であり、確定仕様書ではありません。未決事項は 6 節に整理しています。

## 1. 製作中オブジェクトは、完成品とは別オブジェクト

「未完成の斧」は、斧自身とは**別の、製作中の状態専用オブジェクト**として扱います。製作中オブジェクトは
`progress` プロパティに、工程に対応する半開区間の `stages`（`GameElementDefinition.md` 6.4 節の
`progress`/`feverish` サンプルと同じパターン）を持ち、最終工程の効果として `spawn: {object: axe}` と
`destroy: self`（`into` 省略により、自分がいたスロットへ完成品を生成して自分自身を破棄する、同 9.4 節）を
発火させます。

製作中オブジェクトの型は、レシピの内容（工程数・各工程の要求・時間）から、決まった変換規則で自動的に導出します。
人間も MOD 作成者も、この型を直接書きません。アイコンなど完成品ごとに変えたい情報は、レシピ自身の `icon`
（`GameElementDefinition.md` 13.2 節）として著者が指定し、自動生成時にその情報を型へ引き継がせます。

## 2. 材料・道具の要求は専用スキーマ（steps / requires）

既存の `conditions`/`passive`/`active` には「工程ごとに異なる要求について在庫を確認し、指定数量だけ消費し、
足りなければ何もしない」という条件チェック＋消費の複合動作を表す語彙がないため、`steps`/`requires` という
専用のスキーマを設けています（`GameElementDefinition.md` 13.1 節）。

進捗は既存の `stages` をそのまま流用します。専用の進捗表現は設けません。

## 3. 「箱」は slots の枠をそのまま使う

ゲーム上、レシピは「箱」として表現します。必要な素材・道具を箱に入れてからボタンを押すと、素材が消費されて
進捗が進みます。この「箱」は、`slots` の枠（`cells`、`GameElementDefinition.md` 7.2 節）そのものです。
レシピ専用の新しいコンテナ概念は作りません。

```yaml
slots:
  materials:
    cells:
      - {accept: {object: wood}, max: 2}
      - {accept: {object: stone_knife}, max: 1}
```

**何が何個要るかが、そのまま枠の形になります。** 板の枠が1つ、棒の枠が1つ（4本まで）と並べば、
プレイヤーは箱を見るだけで必要なものが分かります。普通の箱（家具・コンテナ等）にも緩やかな制約はあるはず
なので、枠は普通の箱とレシピの箱を**同じ機構の厳しさの違い**として説明できます。

素材か道具か（`consume`）と、工程が実際に要求する量（`quantity`）は枠には書かず、`requires`（13.1 節）
だけが持ちます。枠は「置ける場所」であって「作るのに要る量」ではないためです。

**箱には必要量より多く入れられます。** 枠の `max` は場所の制約でしかないので、余分に入れておいても
工程は要求量だけ消費します。完成時に製作中オブジェクトが `destroy` されると、残った素材はその親へ
こぼれ出ます（`GameElementDefinition.md` 9.3 節）。

## 4. 投入操作は枠から自動生成される combinations

箱へのアイテム投入は、製作中オブジェクト（1 節）に対して、枠の `accept` から自動的に
`combinations`（`GameElementDefinition.md` 12 節）を生成する形で実現します。人間が書く代わりに、エンジンが
枠の宣言から生成します。

素材が揃っているかの確認・消費・進捗更新（`actions.work` 相当）は、通常の `actions` の `conditions`/`active`
として表現しますが、「スロットの中身をまとめて検査し、条件を満たせば該当分だけ消費する」という具体的な処理は、
レシピでしか使わない概念であるため、YAML の汎用語彙（`conditions`/`active`）を複雑化させず、プログラム側の
専用ロジックとして実装します。

## 5. 製作中オブジェクトは、完成品のタグを引き継ぐ

自動生成される製作中オブジェクトの型は、完成品の `tags`（`GameElementDefinition.md` 4.1 節）を引き継ぎます。
**枠の `accept` がタグで書かれている場所へ、その場で作れなくなるためです。**

住居の壁の枠（[`Dwellings.md`](../world/Dwellings.md) 1 節）は `{accept: {tag: wall}}` なので、壁をその場で
作るには、製作中の壁が `wall` タグを持っていなければ枠へ入りません。引き継がない場合は、枠の側が製作中
オブジェクトも受け入れるよう個別に書く必要があり、枠の宣言が「置ける物」以外の知識を持つことになります。

## 6. 未決事項・今後の検討課題

- 製作中オブジェクトの型の自動生成が、ゲーム起動時にエンジンがメモリ上で行う処理なのか、ビルド時の前処理ステップ
  なのか
- 素材と道具を同じスロットにまとめるか、別スロットに分けるか
- 普通の箱（家具・コンテナ等）が枠の宣言をどこまで再利用できるか（型・trait・サイズベースの緩い制約への拡張。
  普通のコンテナの合計サイズ制限・重さは `ContainerSystem.md` で別途検討）
- `steps.requires` の記法の詳細（`quantity` のデフォルト値、trait マッチングの可否など）
- 枠から自動生成される `combinations` で、複数の素材が同時にマッチしうる場合の優先順位
  （`ActionSystem.md` の既存の未決事項と関連）
- レシピの `icon`・完成品の `tags`（5 節）以外に、自動生成される型へ引き継ぐべき情報（名前、説明文など）の範囲
