SaveDataManagement

セーブデータ管理

スタート画面・セーブ選択画面のモックを作る過程で、単なる画面設計を 超えてセーブデータの持ち方自体に関わる決定が必要になったため、ここに集約する。 画面構成そのものは StartScreen.md を参照。

保存先

ブラウザの localStorage を採用する。本作はサーバーを持たないブラウザ単体のゲームであり （package.json の依存に見るとおり Phaser + Vite の静的ビルドのみ）、複数端末間の同期や クラウド保存は現時点でスコープ外（詳細は「スコープ外」節）。

  • キーは unmapped-island:save:{slotIndex}（slotIndex は 0〜3）。スロット数は4固定のため、 スロット一覧を得るための別キー（インデックス／サマリー一覧）は持たない。4つのキーを 直接読み、値が存在しない（null）スロットを空きスロットとして扱う。
  • 一覧表示専用のサマリーをスロット本体と別に持たない。持ってしまうと「セーブ本体を更新したら サマリーも更新する」という手順を呼び出し側が覚える必要が生じ、 CLAUDE.md のカプセル化方針が禁じる状態になる。スロット一覧画面は 4件のセーブ本体を直接読んで表示に必要な項目（後述）を取り出すだけで十分に軽量なため、 サマリーの複製を持つ動機がない。

セーブデータのスキーマ

セーブデータ本体は概ね次の項目を持つ JSON とする（実際のワールド状態のスキーマは別途検討）。

フィールド 型 内容
schemaVersion number セーブデータの形式バージョン。将来のフィールド追加・変更をマイグレーションで吸収するための起点（マイグレーション処理自体は本ドキュメントの対象外）。
islandName string 新規ゲーム作成時に入力した島の名前。1〜20文字。
seed number 乱数シード。地形生成が消費する Pcg32 の実装（seed >>> 0）に合わせ、0 以上 2^32 - 1 以下の符号なし32bit整数の範囲で扱う（詳細は後述）。
characterId string 選択したキャラクターを識別するID。現状のドメインモデルは1種類のキャラクター（シングルトン）しか持たないため、当面は固定値になる（詳細は後述）。
createdAt number 作成日時（UNIX時間・ミリ秒）。
elapsedDays number 生存日数。ワールドの経過ゲーム内時間から求まる値で、セーブスロット一覧の表示のためだけに
別途複製した値ではなく、セーブ本体（ワールド状態）が持つ経過時間をそのまま読む。

elapsedDays を「表示専用の複製」にしないのは、上記のサマリー非保持の方針と同じ理由による （更新のたびに複数箇所を同期させる手順を呼び出し側に持たせない）。

新規ゲーム作成時の入力とランダム生成

  • 島の名前: 自由入力（1〜20文字、空文字は不可）。ランダムボタンは形容語＋名詞の2語を 組み合わせて生成する（例: 「霧深い」＋「孤島」）。一意性は保証しない （スロットごとの識別は名前ではなく slotIndex で行うため、島名の重複を禁止する理由がない）。
  • 乱数シード: 数字のみの自由入力、またはランダムボタンで生成する。NewGame.start （src/domain/generation/NewGame.ts）はすでに seed: number を受け取り、地形生成 （TerrainGenerator.generate → Pcg32）が「同じシード→同じ島」を決定的に再現する。 Pcg32 のコンストラクタは seed >>> 0 で符号なし32bit値として消費するため、シードの 値域は 0 以上 2^32 - 1（4294967295）以下として扱う。ただし決定的なのは地形レイアウトのみで、 WorldSession.rng（pick抽選・初期値ロール用）は NewGame.start の rng 引数を省略すると 非決定的な既定実装（randomRng、src/domain/runtime/Rng.ts）になる。そのため「同じシード→ 完全に同じ開始状態の再現」まで保証するには、シードから作った決定的な Rng 実装を rng 引数へ別途渡す仕組みが必要になる（本ドキュメントの対象外。現状はマップ生成のみ再現される）。
  • キャラクター選択: characters.yaml の character object_def は singleton: true （常に1体だけ存在する前提）であり、現状のドメインモデルには複数キャラクターから選ぶ仕組みが まだ存在しない。本モックのキャラクター選択は、複数キャラクターに対応する将来のドメインモデルを 見越した画面上の入り口であり、実際に選択肢を出し分けるにはキャラクター定義自体を シングルトンから複数選択可能な形へ拡張する作業が別途必要になる（本ドキュメントの対象外）。

スロットの空き・削除

  • 空き判定はキーの不在（localStorage.getItem が null）のみで行い、別途「空きフラグ」は持たない。
  • 削除は該当スロットのキーを消すだけで、他スロットに影響しない。
  • 削除は確認操作を必須とする（画面設計は StartScreen.md 参照）。 誤タップで進行データを失う事故を防ぐための最低限の防御であり、取り消し（アンドゥ）は スコープ外（「スコープ外」節）。

スコープ外

  • クラウド同期・複数端末間の共有
  • セーブデータの暗号化・改ざん防止（ローカル単体プレイのみを想定するため）
  • 削除の取り消し（アンドゥ）
  • スキーマバージョン間のマイグレーション処理そのものの実装（schemaVersion フィールドの用意まで）
