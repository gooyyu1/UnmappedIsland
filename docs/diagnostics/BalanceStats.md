# アイテム収支レポートの読み方

数値は [`stats/balance.yaml`](../../stats/balance.yaml) にあります。
`tests/diagnostics/balanceStatsReport.test.ts` が、定義（`src/assets/world-codex/*.yaml`）だけから
計算した「時間あたりの収支」です。定義の数値を変えたら再生成します。

```
npm run stats:balance
```

同じ表はコーデックスビューアの「収支」ページでも見られます（アイコンつき）。**絵つきで読めるのは
そちら、数値を変えたときの差分を読めるのはこちら**です。

**この文書は手書きで、再生成しても書き換わりません。** 持つのは読み方——何を測ったか、どこに線を
引いたか、何を数えていないか——だけです。**測った数値そのものは1行も書きません**（書けば、再生成した
YAMLとずれます）。

## YAMLの節

**1つのレコードが違う量を並べて持つので、単位はキーの名前へ入れています**（`per_unit_minutes`・
`capacity_ml`・`day_percent` など）。時間はすべて労働時間で、待ち時間は含みません。

**`null` は「決まらない」ではなく、節ごとに意味が決まっています**——`device_count` と `days` は
その経路に当てはまらないこと、`build_minutes` は**その土地の値段が出ない**こと、
`object_costs.total_minutes` は総コストを出せないこと、`devices` の `lifetime_property` と
`lifetime_days` は朽ちないことを表します。

**「値段が付かない」と「入手経路が無い」は別のことです。** 総コストが出ないのは、島のどこにも
入手経路が無いからとは限らず、**手に入るが値段を付けられない**（出どころを辿ると朽ちない設備の
待ち生産に行き着き、按分できない。「待って得る生産の数え方」）こともあります。どちらかを答えるのは
`object_costs` の `obtainable_without_cost` と `prerequisites` の `object` で、
`total_minutes: null`・`minutes: null` は**値段が付かないことしか言っていません**。
**土地ごとの節（`devices`）はどちらも答えません**——`build_minutes: null` の理由は3つ（他の土地で
なら作れる・島のどこでも値段が付かない・入手経路が無い）あって、**どれも島全体の事実**なので、
土地ごとの行には持たせず `object_costs` のその型の行で読みます。

| 節 | 中身 |
| --- | --- |
| `meta` | 1日ぶんの必要量を取ったキャラクタと、tickと日の刻み |
| `excluded_locations` | 表が数えなかった土地（海区と、海区にしか湧かない土地）と、外した根拠のタグ |
| `daily_needs` | 値ごとの1日ぶんの必要量。何で埋まるか・尽きると死ぬか |
| `daily_minimum` | 土地ごとの、1日を賄う最小労働（貪欲解） |
| `daily_minimum_menu` | その献立の内訳 |
| `chain_routes` | 土地×値ごとの、素材から摂取までの経路と単位あたりの時間 |
| `chain_untimed_routes` | 時間を数えられない経路（労働0で値が返るもの） |
| `chain_gaps` | 島全体で入手経路が無いものと、それが塞いでいる経路（**空でもよい**——穴が無いのが望ましい） |
| `object_costs` | オブジェクト1つを手に入れるまでの総労働 |
| `devices` | 待ち生産（設備が時間をかけて返す分）の周期とレート |
| `rain_water` | 空けたまま置いた容器が1日に受ける水と失う水 |
| `consumption` | キャラクタが1日に動かす自分のプロパティの量 |
| `supply` | 何かを生むか値を動かす工程（海でしか手に入らないものを除く）の、所要時間と産出 |

**この表とYAMLが食い違うと `npm test` が赤くなります。** 表に挙げた節がYAMLに在って空でないことと、
表に無い節がYAMLに無いことの両方を、生成元のテストが見ます。

## 計測方法

- `pick` の分岐は `weight` から期待値を取る。入れ子の `pick` は確率の積まで畳んである。
- **候補が自分の重みの値を自分で減らしているなら、その値は「仕込んだ在庫」として読む。**
  塩田に張った海水も畑に撒いた株も、宣言された初期値は空——そこで重みを読むと全候補が0になり、
  「何も仕込んでいない回」だけが確率1になって、設備が何を返すかを一度も数えないことになる。
  **1回ぶん仕込んである**として数えるので、在庫を使う候補どうしは互角に並ぶ。
  減らさない重み（罠の掛かりやすさ・器に残った水・食べ物の傷み）は宣言値のまま。
- **1つの工程が複数の値を返す場合、所要時間は按分せず全額を各値に計上する。** 按分には
  水と満腹の交換レートが要るが、そのレートこそこの表が見つけようとしているもの。
  代わりに `deltas`（同時に返す値）を添えた——それらを縦に足すと二重計上になる。
- **道具（消費されない入力）の入手時間は単位あたりの時間に含めない。** 繰り返し使えるものを
  1個あたりへ按分するには「何回使うか」の仮定が要り、その仮定が数字を支配するため。
  代わりに `prerequisites`（前提）へ、1度だけ払う入手時間として別に並べる。
- 連鎖の起点は探索。土地ごとに得られる物が違うので、`chain_routes` は `place` で分かれる。
  ただし資源は土地をまたいで分かれている（木は砂浜、石は岩場）ので、渡り歩ける前提の
  **島全体**を先頭に置く——各資源を最も得やすい土地で得て、移動時間は数えない場合。

### 待って得る生産の数え方

罠のように、仕掛けてから時間が経つと産物が返るものは、**待っている間に他のことができる**。
そこで工程の時間を2本に分けて数える。

- **労働時間**: プレイヤーが払う分。他の行動と直接競合するのはこれだけで、`*_minutes` はすべてこちら。
- **周期**: 経過するだけの分。単位あたりの時間には**足さない**。

では待ち時間が無コストかというと、そうではない。**設備は待っている間も朽ちる**ので、
1周期で使い切る設備の割合（周期 ÷ 寿命）が、そのまま製作労働の按分になる——罠1回の判定は
「罠を作る労働の、周期÷寿命ぶん」を払っている。`chain_routes` の数字はこの按分を含む。

この数え方が成り立つのは**並列度に上限があるとき**だけ。いくらでも並べられて朽ちもしない
設備は、待つだけで無限に得られることになるので按分できず、`chain_routes` から外して `devices` へ回す。

### 隣の物に押されて起こる作り替え

焼くのも失血死も、**自分では動かない値を隣の物が動かす**。炉は火にかけた物の
`cooking_progress` を進め（`add: {child: ...}`）、刺さった傷は持ち主の `blood` を奪う
（`add: {parent: ...}`）。値が range の端へ届いた瞬間に、その型自身の `on_max`/
`on_min` が生肉を焼けた肉へ、獲物を死体へ置き換える。

どちらも「1回で終わる待ち生産」なので、労働0・経過時間ありの工程として `chain_routes` に載せ、
押し手（炉・傷）は**要る道具**として `prerequisites` に出す。誰が誰の隣に立てるかは、枠の
`accept` だけで判断する——炉の火の枠が `roastable` を受けるから、そこへ入る物は焼ける。

**押し手が止まるまでに動かせる総量**も数える。出血は傷の `bleeding` が尽きれば止まるので、
罠の傷ではネズミは死ぬがヤケイは死なない。届かない組み合わせはその工程を立てない。

この総量は**最も少なく見積もります**——止まるまでの長さは、押し手が同時に見ている値のうち最も早く
尽きるものを、最も速い減りで数えます。**生成時に1回引く初期値**（`GameElementDefinition.md` 6.2節、
`value: {min, max}`）も同じ向きに揃えて軽く出たほうを採るので、40〜100 で引かれる罠の傷の
`bleeding` はここでは 40 として数えます。重く出た個体でしか成立しない組み合わせは、この表に
出ません。

一撃で端まで押す効果も同じ引き金を引く。仕留めの一撃（`set: {self: {blood: 0}}`）は
血を空にするだけで、死体を生むのは `blood` の `on_min` ——工程の結果にこれを
畳まないと、イノシシの死体（失血死には届かない）の作り方がどこにも無くなる。
確率でしか消えない入力は、**その確率ぶんだけ**消費されるものとして数える。

### この表が数えていないもの

- **土地の間の移動時間。** 道ごとに違い、地形生成が個体へ書き込むため定義からは決まらない。
  設備を見回る時間もこれに含まれるので、必要設備数が多い経路ほど実際は不利になる。
- **餌の効果。** 餌は `modify`（実効値への可逆な寄与）で重みを押し上げるが、静的に読めるのは
  宣言値だけなので、罠のレートは**餌なし**の値。
- **雨で溜まる水を汲む労働。** 量を増やすのは `rain_filled_liquid` のtick毎の持続効果で、
  工程ではない。そのため水を汲む経路は労働0分になり、`chain_untimed_routes` へ分けてある。
  溜まる量そのものは `rain_water` に出す（労働ではなく、季節ごとの mL/日）。
- **採取ポイントの枯渇。** 同じ木から何度でも採れる前提で計算している。
- **炉の薪。** 焼くには火を保たなければならないが、そのぶんの薪は数えていない。炉は
  `prerequisites`（道具）としてだけ出る。
- **どの武器を重ねたか。** 一撃の当たり所の配分は武器が宣言する（`{subject: dragged}` の
  重み）ので、重ねる相手を決めないと配分が決まらない。ここでは**その値を最も高く宣言して
  いる型を重ねた**として読むため、配分は「分岐ごとに最も良い武器を選べる場合」のものになる
  ——1本の武器では出ない配分で、仕留めの確率は実際より低く出る。
- **実行時にしか決まらない条件。** 起こりえない工程は立てないが、偽と判定できるのは
  `subject: self` のプロパティが**その型の取りうる範囲**（`range`。端に達した瞬間に
  その型でなくなるなら、その端を除く）から外れる条件だけ。祖先の天候・重ねる相手・
  スロットの中身を見る条件は真偽を決めずに素通しするので、それだけで弾かれる操作は
  工程として残る。

### 何を「島の土地」と数えるか

土地ごとの表が答えるのは「**島**の1日が賄えるか」なので、数えるのは探索できる土地のうち**海でしか
手に入らないものではないもの**だけです。海区（`voyage.yaml`の島影の海・潮目・空の海）は探索でき、
寝られ、雨も貯まるので、集め方の条件（`location`タグ＋`exploration_progress`）をそのまま満たしますが、
島の土地ではないので分母に入れません。外した場所は `excluded_locations` に出ます。

**線は「海でしか手に入らない」で、`sea`タグだけでは引けません。** 小島（`offshore_islet`）は海区に
湧く設置物でありながら上陸して探索できる土地で、`sea`タグは持ちません（付けると筏の`disembark`が
通らなくなる）。湧き元を辿って、海区からしか生まれない型をまとめて外します——`excluded_locations`
の `tag` は、そうして辿り着いた根拠のタグです。

**工程の目録（`supply`）と総コスト（`object_costs`）からも、海でしか手に入らないものを外して
います。** 海区の見張りだけでなく、漁り場の漁も海藻も落ちます——生肉を30分で返す漁り場を残すと、
生肉の代表経路が海に決まり、入手経路が無い経路として落とされて、島で最も安い肉の経路
（イノシシ）が `chain_routes` から丸ごと消えます。筏と帆は島で作る物なので残ります。

### 何を「1日に要る量」と数えるか

`daily_needs` の出どころは `consumption`。**輸送で減る値は需要にしない**——
`carbohydrate`/`protein`/`lipid` はtick毎に体脂肪へ流れるが、あの速さは在庫がある間の流量で
あって、要る量ではない。体が実際に燃やすのは受け皿側の `body_fat` の減りだけで、三大栄養素は
そこへ注ぐ原資（DigestionSystem.md 3節）。流量を要求量として数えると、必要な何倍も食べさせる
ことになる。

**段で減る速さが変わる値は、初期値が入る段の速さを採る。** 体脂肪は段ごとに減り方が違うので、
全部を足すとどの段にも当てはまらない量になる。

`satiety` は胃のかさであってエネルギーではない（同2節）。尽きても死なず、食べれば同時に
埋まるので、献立では他の値を賄うついでに満たされることが多い。

## 連鎖表（`chain_routes`）

`daily_minutes` は1日ぶんを賄うのに要る労働、`day_percent` はそれが1日（`meta.minutes_per_day`）に
占める割合。`device_count` は、待ち生産の経路で1日ぶんを賄うのに同時に要る設備の数。

**`device_count` は `devices` の条件が成立し続けた場合の数です。** `devices` は経路が待つ設備を
上流から下流の順に並べたもので、`condition` は周期が進む条件（「待ち生産表」の同名の列と同じもの。
周期とレートはそちらが持つ）。条件が満たせなければ設備を何個並べても産物は0なので、**数だけでは
「置けば回る」としか読めません**——罠は `items枠にある かつ catch枠にquarryが無い` で、地面に置いて
掛かっていない間だけ進みます。経路は設備を何個でも通りうるので列は並びで、待ち生産を含まない
経路では空（`device_count` も `null`）。

**土地ごとの行は可否を判定しない。** 答えるのは「この土地を起点にすると単位あたり何分か」
だけで、ある経路が載らないのはできないからではなく**その `place` の対象ではない**から。
入手できるかどうかは `place: 島全体` でだけ判定し、島のどこにも経路が無いものは `chain_gaps` へ
まとめる。

**`imported: true` は、他の土地で用意した材料・道具が要る経路。** AとBの土地で集めた物を合わせて
作るのは普通の遊び方なので可否は分けないが、土地の間の移動時間を数えていない以上、この経路は
実際にはこの表より不利になる。

**時間を数えられない経路（労働0で値が返るもの）は `chain_untimed_routes` へ分けた。**
時間を数えられていないだけで、本当にタダなわけではない（雨で水が溜まるのはtick毎の持続効果で、
工程ではない）。同じ並びに0分として混ぜると、最安の手段に見えてしまう。

**`prerequisites` の `label` は要求の書き方（タグ指定なら `タグ → 実際に使う型`）、`object` は
実際に使う型。** `object: null` だけが「島のどこにも入手経路が無い」で、その道具が `chain_gaps` に
挙がり、経路は塞がる。`minutes: null` は値段が付かないことしか言わない——朽ちない設備の待ち生産で
しか得られない道具はここへ来るが、**穴ではないので経路は成立する**（道具の時間は単位あたりへ
按分しないので、時間も変わらない）。

`chain_gaps` は、島のどこを探しても作れも見つかりもしないもの。定義の穴で、これが
`blocked_route` の経路を塞いでいる。**空であることが望ましい状態**なので、この節だけは空でもよい。

## オブジェクトの総コスト（`object_costs`）

1つ手に入れるまでの労働を、素材の採集から数えたもの。組み立ての時間だけではない——筏は組む
だけなら短いが、丸太と縄を揃えるところから数えると桁が変わる。

`days` は、生存に要る労働を引いた残り（1日の余剰時間）で割った日数。**目標までに何日かかるか**が
これで出る。道具（`prerequisites`）の時間は総コストに含めない（#550のまま）。

- **`total_minutes: null`** は総コストを出せないもの。**2つある理由を分けるのが
  `obtainable_without_cost`** です。
- **`obtainable_without_cost: false`** は、島のどこにも作り方も見つけ方も無いもの。
  `missing`（足りない入力）がそのまま埋めるべき穴になり、`missing` が空なら作る工程そのものが無い。
- **`obtainable_without_cost: true`** は、**手に入るのに値段を付けられない**もの。出どころを辿ると
  朽ちない設備の待ち生産に行き着き、按分の分母（寿命）が無いので工程として数えられません
  （「待って得る生産の数え方」）。**その産物を材料に取る物も同じ側**——値段の付かなさは連鎖を
  下流へ伝わるので、**`devices` に行が在るのは設備が直に返す物だけ**です（塩には在り、塩から
  作る物には在りません）。工程の入力（設備・材料・道具）のどれかが揃わないなら立ちません
  ——値段が付かない理由が按分ではなく入手経路のほうにあるので、上の行として出ます。
- **`blocked_by_tool: true`** は、材料は揃うが要る道具に入手経路が無いもの。**総コストは出るが、
  実際には作れない**——道具の時間を総コストへ按分しない決まり（#550）の裏返し。無い道具は
  `prerequisites` の `object: null` の行で、`minutes: null` の行ではありません（値段が付かない
  だけの道具は作れなさの理由になりません）。

土地・キャラクタ・単独で存在できない物（怪我・道）・製作中オブジェクト・軸の値の型
（液体の種類。世界に現れるのは中身入りの容器という変種のほうで、`water_liquid` そのものの
インスタンスは作られない）は、手に入れるという言い方が成り立たないので対象外。

## 待ち生産表（`devices`）

仕掛けてから時間が経つと産物が返るもの。**`period_minutes` は単位あたりの労働時間には足していない**
（「待って得る生産の数え方」参照）ので、この節が代わりに周期とレートを出す。

**行が土地ごとに並ぶのは掛かる相手の重みが土地で変わるからで、「その土地に置けば働く」という意味では
ありません。** 周期を進めるのはtick毎の増減（`GameElementDefinition.md` 8.4節）で、それがゲート
（同8.2節）で縛られていれば、条件が成立しない限り1 tickも進みません。`condition` がそれです。

- **`condition`**: 周期が進む条件。`常時` は置くだけで進むもので、それ以外はゲートの中身を
  そのまま書き出したものです（識別子は定義のまま）。**その行の数字は、条件が成立し続けた場合の
  レート**——罠の判定は `items枠にある かつ catch枠にquarryが無い`、囲いの判定は
  `catch枠にquarryが無い`、ヤケイの繁殖は `catch枠にある かつ 親のfodder ≥ 1` で、
  囲い（`build_minutes` 2617分）と飼葉が要ることが行から読めます。否定は葉まで押し下げて
  書きます（`not: {slot: catch, matches: {tag: quarry}}` は「catch枠にquarryが無い」）。
- **`per_day`（個/日）**: 1日は24時間まるごと回る。眠っている間も進むのが待ち生産の取り柄。
- **`lifetime_property` / `lifetime_days`**: 設備を終わらせるプロパティと、それが尽きるまでの日数。
  条件つきの減りは**最小の1つだけが効くとして**数えている。罠の寿命は地面にある間の減りだけで
  割った値で、獲物が掛かっている間の減りは含まない——どの条件がいつ重なるかは定義からは決まらない
  ため。実際の寿命はこれより短く、下の2つはその分だけ設備に有利に出る。`null` は朽ちないこと。
- **`over_lifetime`（個）**: 設備1つが朽ちるまでに返す総数。これが並列度の上限を決める。
  **`lifetime_property` が `condition` と別の条件で減るなら、この積は同時には成立しない仮定の
  掛け算になります**——ヤケイの `stay_remaining` は地面に立っている間しか減らないので、囲いの中の
  ヤケイは立ち去らず、地面に立っているヤケイは増えません。
- **`build_minutes`**: 設備1つを作るまでの労働。**その土地を起点にした値段**で、`chain_routes` が
  周期へ按分しているのと同じ値です（`labor_minutes_per_unit` がその1個あたり）。
  **`null` の理由はこの節では言いません**——他の土地でなら作れる（罠の掛かる動物は土地が決めるので、
  ヤケイの湧かない土地ではヤケイの行がこれになりますが、島全体では値段が付きます）・島のどこでも
  値段が付かない・入手経路が無い、のどれもありえて、**どれも島全体の事実**だからです。**この節は
  可否を判定しません**（連鎖表と同じ、上の「土地ごとの行は可否を判定しない」）。理由は
  `object_costs` のその設備の行が答えます。
- **`labor_minutes_per_unit`**: 製作労働 ÷ 寿命の間に返す数。`chain_routes` に載るのはこの値。

## 雨で溜まる水（`rain_water`）

空けたまま置いた容器が、1日に受ける水と失う水（`LiquidContainerSystem.md` 6・7節）。
降雨も蒸発も気候の実測値から出している（`ClimateSystemStats.md`）。

**単一の平均は出さない。** 雨季とそれ以外では降る時間が1桁違い、平均するとどの季節にも
存在しない中間の状態を測ることになる。読みたいのは `net_ml_per_day` の符号——**雨だけで水を
賄えるのは雨季だけ**で、それ以外の季節は置いておくだけでは減る。

- **降雨も蒸発も、同じ1つの数え方で出している。** どちらも`fill`をtick毎に動かす持続効果で、
  違うのは符号だけ。器の居る場所の天候と明るさを時刻ごとに置き、そのとき条件が成立する増減を
  出現時間で加重して均している（**天候と時刻は独立とみなす近似**）。
- **明るさは開けた土地のもの。** 蒸発の上乗せは`ancestor.ambient_brightness`を見るので
  （`LiquidContainerSystem.md` 6節）、樹冠も反射もある土地では変わる。この節は
  `ambient_brightness`の`value`が0の土地に置いた容器の量。
- **雨よけの下かどうかは見ていない。** 水が増える宣言は、雨が降っていることに加えて
  「雨よけの下でないこと」（`{subject: ancestor, prop: sheltered}`）も課しているが、天候と
  明るさ以外の祖先の条件は真偽を決めずに素通しする（「この表が数えていないもの」）。
  これは**雨の当たる場所に置いた容器**の量で、屋根の下に置いた容器も同じだけ受ける前提。
- **段（`stage`）で縛られた増減は数に入らない。** その段だった時間は天候の出現時間からは
  決まらないため。今の定義に該当は無いが、**書き方をそちらへ変えるとその増分はこの節から
  黙って消える。**
- **蒸発は中身がある間しか効かない。** 空になった容器は素の型へ戻って蒸発も止まるので、
  `evaporation_ml_per_day` は満杯を保った場合の上限。実際の減りはこれより小さい。
- **容量を超えた分は捨てられる。** 雨季のヤシの器は `capacity_ml` に対して桁違いの雨を受けるので、
  汲み替えなければそのほとんどが失われる。`net_ml_per_day` はその損失を含まない。

## 消費表（`consumption`）

キャラクタが自分のプロパティをtick毎にどれだけ動かすか（`passives` の `add` と `transfer`）。
`per_day` は1日ぶん（`per_tick` × `meta.ticks_per_day`）。個体差は `character` の行に出る。
**`daily_needs` の出どころ**。

## 供給表（`supply`）

何かを生むか、値を動かす工程すべて（**海区が宣言するものを除く**、「何を「島の土地」と数えるか」）。
`spawns` は1回の実行あたりの期待個数。各オブジェクトのページにも同じ宣言があるので、ここは横断して
見比べるための一覧。

`unresolved_references: true` は、所要時間か分岐の重みが**定義だけでは決まらない**工程（相手の
持ち物を見る `{subject: dragged, prop: ...}` 参照など）。解けない重みは0として扱うので、その行の
期待値は残った候補へ寄っている——例えば `strike` の当たり方は武器が決めるため、ここでは出せない。

`kind: periodic` は時間で回る工程（罠の判定）。労働は0で、`elapsed_minutes` だけが経過する。
`actor_deltas`／`self_deltas` の増減は宣言された上限で、実際に動く量は在庫と空きで目減りする。
