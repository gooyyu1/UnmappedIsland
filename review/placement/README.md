# 定義位置レビュー

`src` 配下の宣言（ファイル・クラス・関数・変数・定数・型・フィールド）が、**そこに居るのが適切か**を
棚卸ししたもの。目的は不要機能の削除ではなく、**定義位置の再整理**。

対象は `main` の `cb01b89` 時点。TypeScript は 229ファイル / 約37,200行 / 宣言 4,178件。

## 判定基準

| 判定 | 意味 |
| ---- | ---- |
| 1 | 一般概念として、そこにあるのが妥当（オブジェクトがプロパティを持つ、など） |
| 2 | 概念的に自明ではないが、プログラムである以上は必要（オブジェクトがIDを持つ、など） |
| 3 | 意味論的にはそこである必要はないが、利用者が近くにいるので置かれている |
| 4 | 意味論的には他所が自然だが、実装上の別の何かを守るためにそこに居る |
| 5 | 意味論的にも利用方法的にも、そこにあるのは不適切 |

**4 が最も価値のある発見**。「何を守るために歪んでいるのか」が特定できれば、守っているものごと直せる。
判定4には**阻害要因**（何を守るためにそこに居るのか）を必ず添えている。添えられないものは 4 ではなく
3 か 5 に倒した。

「契約を定義しているから」「責務として関係があるから」は、そこに置くべき理由として採用していない。
関係があることと、そこに置くべきことは別。

## 3つの層

同じ「そこに居る」でも打ち手が違うため、各指摘がどの層の話かを明示している。

- **配置** — ディレクトリ／ファイルの位置。判定は [`docs/engine/Layers.md`](../../docs/engine/Layers.md)
  の4層（世界・映し・意匠・部品）を基準にした。
- **所属** — クラス／モジュールへの所属。
- **可視性** — `public` / `export` である必要があるか。クラス外から呼ばれていない `public` は、
  内部を開けてしまっている＝判定4の兆候として扱う。

## 進め方

1. TypeScript Compiler API で全宣言を機械抽出し、名前・シグネチャ・可視性・参照状況の一覧を作った。
   探索ではなく**与えられた一覧の採点**にすることで、漏れを無くし、担当間で出力を揃えている。
2. 領域ごとに分けて採点した。判定は**まず名前とシグネチャだけ**で行い、実装本体を読むのは名前から
   中身が類推できないときだけ。読まないと分からなかったものには「名前不一致」を立てている。
3. 判定4・5は全件を再判定した。
4. 判定3は、5段階の採点とは別に**もう一段深い問い**で見直した。「A の private ヘルパーだが、主語は
   実は B（B の機能が足りないから A が代わりに書いている）」という形を、全 private ヘルパーに問うた
   （[`Helpers.md`](./Helpers.md)）。
5. 担当範囲に閉じると見えないもの（同じ概念の分散、名前の衝突、テスト専用の公開）は、全宣言の
   インベントリに対して別途横断で調べた。

## 結果

| 判定 | 件数 | 割合 |
| ---- | ---- | ---- |
| 1 | 3,000 | 71.8% |
| 2 | 305 | 7.3% |
| 3 | 536 | 12.8% |
| 4 | 296 | 7.1% |
| 5 | 41 | 1.0% |

領域別の内訳は [`areas/`](./areas/) の各ファイル冒頭にある。

**判定4の件数は領域間で直接比較できない。** 単一の原因を宣言ごとに数えた結果が混ざっているため
（`loader` の43件のうち24件は `RawObjectDef`/`RawTrait` の二重化1つ、`domain-state` の29件のうち16件は
`WorldSession` の観測口1つ）。件数ではなく**原因の数**で読むこと。
