# `docs/CodeStructure.md` との突き合わせ

このレビューは、層（配置）の判定を [`docs/CodeStructure.md`](../../docs/CodeStructure.md) を基準に
行った。全担当に本文を読ませたうえで採点している。

突き合わせは両方向に効いた。**方針があるから機械的な指摘を捨てた**ものと、
**機械的な指摘が集まりすぎていて方針側を疑うべき**ものの両方が出たので、分けて記録する。

## 1. 方針を優先し、機械的には NG に見えるが指摘にしなかったもの

### 1-1. `src/game/ui/` に UPPER_SNAKE の定数が228個ある

意匠（`src/game/looks/`）の49個を大きく上回り、`Card.ts` だけで44個。数だけ見れば「意匠が部品に
漏れている」と言いたくなる。

**指摘にしなかった。** CodeStructure.md 1節が部品に禁じているのは「世界の語彙（レシピ・スロット名・
プロパティ名）」であって、寸法ではない。**数の多さは根拠にならない。**

指摘として残したのは、この方針でも説明できない2つだけ。

- **色**: `MapWindow.ts` の `CHART_PAPER` / `CHART_LINE` / `ROAD_INK`。配色は `theme.ts` の `COLOR` が
  一箇所と定められているのに、`src/game/ui/` で唯一ここだけが生の16進を持つ。
- **複数箇所で一致すべきもの**: `NO_DESCRIPTION`（同一の文言が2ファイル）、`HOLD_MS = 400`
  （`src/ui/` の汎用側とゲーム部品の両方）、`BLINK_DURATION_MS = 450`（同じ「警戒の明滅」が2ファイル）、
  `ITEM_PADDING_X` / `LIST_PADDING`（一覧シーン2つ）。

### 1-2. ウィンドウが全部の層を参照している

`ObjectWindow` などが世界・映し・意匠・部品のすべてに触れている。層の違反に見える。

**指摘にしなかった。** CodeStructure.md 2節が「組み立ては層ではない。全部の層を知ってよい唯一の場所」と
明示している。代わりに各担当には「**これは結線か、判断か**」を問わせ、判断であるものだけを挙げさせた。

### 1-3. `src/domain/views/` が `src/domain/` の下に居る

名前が「映し」なので、映しが世界のサブディレクトリに居るように見える。

**指摘にしなかった**（ただし名前は 2-5 で扱う）。CodeStructure.md の「映し」は `src/game/view/` で、
「今の断面を作り直し、何が出ていて操作が何を意味するかを答える」もの。`src/domain/views/` の5クラスは
そうではなく、trait 合成モデルの `WorldObject` に世界の語彙で名前を与えた型付きラッパで、
`explore` / `travel` / `takeTurn` のように**世界を書き換える**。世界の側にあるべきものが世界の下に居る。

### 1-4. 逆に、方針があるために判定を厳しくしたもの

- `Interaction.name` / `showMenu` は `this.def.name` の素通しゲッター。単体では無害に見えるが、
  CodeStructure.md 3節が「宣言は `def` から直に読む」と定めているため判定4とした。
- `WorldObject.storageFillRatio` は「最も詰まっているスロットを返す」＝どのスロットを映すかという
  見せ方の判断。CodeStructure.md 3節の「読んだ値から答えを組み立てているなら映しのもの」に照らして判定4。

## 2. アーキテクチャ側に返すべきもの

機械的な指摘がここに集中している、あるいはドキュメントの記述が実装と合っていないもの。
**コードを直すのではなく `CodeStructure.md` を直す（または方針を足す）ほうが筋が良い**と考えられる。

### 2-1. `Button` の例が実装とずれている（誤りの訂正）

CodeStructure.md 3節は「部品が汎用か、このゲームのものか」の判定例として、

> 名前で決めません——`Button` は汎用に見えて、スロットボタンの紙のテクスチャキーを持っています。

と書いている。しかし **`SLOT_BUTTON_PAPER_TEXTURE` は `Button.ts` のモジュール定数であって、
`Button` クラス自身は一度も参照していない**。読むのは `BootScene`（ロード）と `PlayScene`
（スロットボタン列の紙）だけ。

つまり `Button` クラスの中身は汎用で、`src/ui/` へ出せない理由は別のところ（意匠の色トークンを
直に引いている1点）にある。同じことが `Curtain` と `ScrollIndicator` にも言える。
**判定例を実装に合わせて差し替える必要がある。**

### 2-2. 「起動」の区分が表に無い

`src/main.ts` と `DeviceScreen` は `Phaser.Game` を作って端末の解像度に追従させる。これは
世界・映し・意匠・部品・組み立てのどれでもない。**表に区分が無いことが、置き場所が
決まらない原因**になっている。

現在は `CodeStructure.md` 1節の表が両方を**組み立て**の置き場として名指ししており、起動を別区分に
するかどうかだけが残っている（同 2節は「起動は組み立ての一番外側」と答えている）。

### 2-3. 「効果の木を外へ出さない」に、入れ子を表す語彙が無い

CodeStructure.md 5節の方針は、**再帰する3箇所でだけ破れている**——`ConditionReader.all` / `any` / `not`、
`GateReading.conditions`、`PickCandidateReading.effect`。この3つだけが `ConditionNode` /
`ActiveEffect` の実体を読み手へ手渡している。

現在の Reader は「1回の呼び出し＝1つの葉の宣言」を前提にしており、入れ子を表す語彙（読み上げの
入れ子の開始/終了、または読み手が子ノード用のリーダを返す形）が無い。**方針が不完全なので、
入れ子を持つところだけが例外になっている。** 語彙を足せば例外なしで成立する。

### 2-4. 層のテスト1本が、5件の自然な配置を止めている

`describeObjectDef` / `describeProperty` / `describeSlot` / `describeRecipe` / `describeInteraction` は
定義の公開フィールドをなぞるだけで、**定義自身が持つのが自然**。止めているのは
「`DescriptionWriter` をドメインの契約にしない」という層のテスト1つだけ。

これは方針が歪みを生んでいる側の例。`EffectReader` は同じ「ドメインに読み上げ口を置く」形で
既に認められているので、**なぜ `DescriptionWriter` は認められないのかを CodeStructure.md が説明していない**。
認めるか、認めない理由を書くかのどちらかが要る。

あわせて、`DefNames` のコメントは今も「実装は `WorldCodex`」と書いており、`DescriptionWriter`・
`CodexView` 冒頭と合わせて**3箇所が describe をドメインに置いていた頃の記述のまま**残っている。

### 2-5. `src/domain/views/` の名前が「映し」と衝突していた（解決済み）

1-3 のとおり中身の配置は妥当だったが、CodeStructure.md が「映し」に `view` の語を当てているため、
ディレクトリ名が層の名前と衝突していた。`src/domain/wrappers/` へ改名し、共通の基底
`ObjectWrapper` を置いた。「なぜ継承ではなくラップなのか」の理由が `World`・`Location`・`Animal` の
3つのコメントに**鎖状に**書かれていた（`Animal` →「`Location` と同じ理由で」→「`World` と同じ理由で」）
のも、基底が1箇所で言うようになって解けた。

### 2-6. 意匠に「部品1つぶん」の粒が無い

`theme.ts` は画面全体で共有する `COLOR` / `SIZE` / `FONT_FAMILY` の置き場で、
**「この札の紙の余白」「この覆いの濃さ」という部品1つぶんの意匠**を置く単位が無い。
その結果、`Card.ts` に44個・全10シーンに散る形で部品側へ溜まっている。

`looks/cardFlight.ts` / `heatHaze.ts` / `rainStyle.ts` は既にその粒で切られているので、
方針としては「**意匠は全体のトークンと、部品1つぶんのモジュールの2段**」と書けば済む。
合わせて、汎用部品（`src/ui/`）へ意匠を差し込む口が `labels.ts` の `setLabelDefaults` にしか無い点も、
方針として決めるべきところ（1-1 の色の指摘と 2-1 の `Button` はどちらもここに帰着する）。

### 2-7. 画面のことばの置き場が層のどこにも無い

`src/locale/` はワールド定義の語（オブジェクト名・変種・タグ）に語を与える口しか持たない。
**ワールド定義に由来しない画面の地の文**（`'閉じる'` が4箇所、`NO_DESCRIPTION` が同一文字列で2箇所、
`UNNAMED_LOCATION` / `LOCKED` / `OTHER`）の置き場が、世界・映し・意匠・部品のどこにも無い。

`ui-window`・`game-view`・横断チェックの3つが、互いを知らないまま同じ欠落に行き着いた。
**独立した3つが同じ穴を指したので、コード側ではなく層の設計の穴と考えるのが自然。**

### 2-8. 「宣言に対する見せ方の宣言」というデータの層が無い

`rainStyle.ts` の `RAIN_STYLES` は天気の識別子ごとの見せ方の表。天気そのものは `src/assets/` の宣言
（`core.yaml`）が持つのに、**それを「どう見せるか」を宣言するデータの居場所が無い**ため、
意匠の**コード**が世界の語彙を写し取っている。

`heatHaze` / `skyTint` が数値の閾値で済んでいるのに `rainStyle` だけ語彙を持つのは、天気が連続値では
なく識別子だから。3節の「意匠か素材か」の線（`src/art/` は「どのファイルがどの絵か」）に、
演出版が無い状態。

### 2-9. 重なりの決め方が2系統ある

`looks/screenDepth.ts` が「重なりの順序は1箇所にだけ書く」と宣言している一方、子ウィンドウ4つは
「表示順は生成順で決まる」を前提にコメントで注意書きを配っている（`ObjectWindow`・
`StatusDetailWindow` の構築子、`PropertiesPane`・`RecipeWindow` の「面は中身より先に敷く」、
`Tooltip.bringToTop`）。**同じ規約が5箇所に散っており、宣言と実態が食い違っている。**

### 2-10. `src/domain/` 直下に、層の線がディレクトリとして映っていない

47ファイルの平置きで、**ロード後不変の宣言（Def）と実行時の状態（実体）が混ざっている**。
宣言側（`ObjectRef` `ReferenceRoot` `AlertLevel` `SlotPosition`）・実体側（`WorldObject` `Slot`
`PropertyValue` `ObjectStack` `WorldSession` `EffectSite`）・出来事の記録（`WorldChange` `WorldSignal`
`PropertyGain` `PropertyInfluence`）・手続きモジュール（`actionTime` `autoFill` `crafting`）が同じ階層に並ぶ。

CodeStructure.md 3節は「インスタンスへ訊くか定義へ訊くか」という線を繰り返し引いているのに、
**ディレクトリがその線を映していない。** 判定4の相当数が「定義側に問いを立てる口が無い」に
帰着している（[`Candidates.md`](./Candidates.md) B-3）のは、この線が構造として立っていないことと
無関係ではない。

## 3. まとめ

CodeStructure.md は判定の基準として機能した。1節のとおり、方針があることで**捨てられた指摘のほうが多い**
（228個の定数のうち残したのは9個）。

一方で 2節の10件は、**個々のコードを直すより方針側を直すほうが効く**もの。うち 2-1 は
ドキュメントの誤り、2-2・2-3・2-6・2-7・2-8 は方針の欠落、2-4・2-9 は方針と実装の食い違い、
2-5 は命名の衝突、2-10 は方針が構造に反映されていない件。
