# 分析のプロンプト（二次）

一次の分析係（[`analysis-prompt.md`](analysis-prompt.md)）が回ごとに書いた `## 傾向` を**横断して
読み、複数の回に現れている形に根本的な対策を打つべきかを決める**係の本文（出どころ: ユーザーの指示・
2026-09-07）。投入するのは盤面（[`board-move.mjs`](../../scripts/agent/board-move.mjs) の `CYCLES`）で、
前の周より後に書かれた一次の記録があれば週に一度立つ。渡し方は
[`dispatch-chore.sh`](../../scripts/agent/dispatch-chore.sh)。

**一次と二次を分けるのは、回をまたぐ数を一次が畳んでしまわないため。** 一次は1つの帯しか見ないので
「この形が何回の帯にまたがって出たか」を原理的に知らない。**同じ形が別々の回に独立して現れたこと
自体が、根本対策を打つべきかの根拠**なので、一次が過去へ足しに行くとその回数が消える。

**入力は一次の記録だけ。** PRのコメントも issue も読み直さない——一次が既に読んで、拾うものは拾って
いる。二次が足すのは**回をまたいで見ないと出ない結論**だけ。

**クラウドで走る。** 切るのは新しい issue で、記録は自分のPRに載せるので、クラウドに用意された道具で
どちらも通る。

題は下の `題:` の行が持つ（[`board-design.md`](../board-design.md) 2.9）。

題: 傾向 回をまたぐ形

---

````
[デーモン] 一次の分析係が書いた記録を横断して読み、繰り返している形に手を打つか決めます。

まず `CLAUDE.md` と `agent-ops/parallel-work.md` を読んでください。

**一次の分析係**（`agent-ops/prompts/analysis-prompt.md`）は、マージ済みPRに残ったスメルを回ごとに拾い、
その回の帯で繰り返し現れた形を `agent-ops/analysis/<日付>.md` の `## 傾向` へ書きます。**一次は
過去の回の `## 傾向` を読みません**——1つの帯しか見ないので、「この形が何回の帯にまたがって出たか」を
知らないまま書いています。

**ただし、一次が過去の記録を開いた回はあります**——その回のスメルが過去の記録の行を名指していたとき
だけで、開いた範囲は各回の `## 開いた過去の記録` に書かれています。

**それを数えるのがあなたの仕事です。**

## 読む範囲

- **`agent-ops/analysis/*.md` の `## 傾向` 節。** 手を打つ形を探すのはここです。
- **各回の `## 読んだ範囲` も読み、帯が連続しているかを確かめてください。** 一次は自分の回の帯しか
  見ないので、**前の回との間にPRが落ちていることは、回を並べて見るあなたにしか分かりません。**
  切れ目が在れば、落ちた帯を名指しして issue を切ってください（窓の幅か、係の立つ間隔の話になります）。
- `## 切った issue` は、その形に一次が既に手を打ったかを確かめたいときに読んでください。
- **`## 開いた過去の記録` に何か挙がっている回は、そこを読んでから数えてください。** 一次はその範囲を
  読んだうえで `## 傾向` を書いているので、**その回の帯に出ていない形が混ざっていれば、回の数が
  実際より多く出ます。**
- **`agent-ops/analysis/summary/*.md`**（前の周までのあなたの出力）。**最新のものは必ず読みます**
  ——そこに「様子見」として置かれた形が、今回また出ているかもしれません。
- **PRのコメントも issue も読み直さないでください。** 一次が既に読み、拾うものは拾っています。
  ここで足すのは**回をまたいで見ないと出ない結論**だけです。

**見出しは回ごとに揃っていません。** 一次は自分の言葉で節を立ててよいことになっている（同じ形が
別の回で別の見出しで書かれる）ので、**同じ形かどうかはあなたが読んで判定してください。** 見出しの
一致では引けません。

## やること

1. **`## 傾向` を全部読み、同じ形をまとめる。** 判定の軸は「**書かれている現象が同じ原因から出て
   いるか**」で、言い回しでも見出しでもありません。
2. **何回の帯に現れたかを数える。** 同じ回の中で何本のPRに出たかは一次が既に書いているので、
   あなたが出すのは**回の数**のほうです。
3. **帯が連続しているかを確かめる。** `## 読んだ範囲` を回の順に並べ、**前の回の末尾と次の回の先頭の
   間にPRが落ちていないか**を見てください。落ちていれば、そのぶんのスメルには 👀 が付かないまま
   誰も読んでいません。
4. **根本対策を打つべきものは issue を切る。** 判定は下の「打つべきか」。
5. 記録を書き、コミットしてPRを出す（下の「記録」と「PR」）。

## 打つべきか

**回数だけでは決めません。** 見るのは次の2つです。

- **同じ形が、別々の回に独立して現れているか。** 1つの回だけに厚く出ている形は、一次が既に issue に
  しているはずです（一次の `## 切った issue` で確かめられます）。
- **一次が切った issue が、その形を止める側に効いているか。** 効いていれば入るのを待てばよく、
  **効いていないなら、個別の直しでは止まらない形**だという証拠になります——そこが根本対策の要る
  ところです。

**打つ根拠を、他の形との優劣（最多・唯一）で書かないでください。** 次の周のあなたは、この回の記録を
数え直すところから始めます——優劣で書いた根拠は数え直した時点で揺れ、**なぜ打ったのかが後から
読めなくなります。** 根拠は、その形だけを見て成り立つ形（「当たるはずの決めごとが在るのに外れて
いる」のように、他の形が増えても減っても揺れない書き方）にしてください。

**打つべきだと判断したら、issue を1件切ります。**

- `kind:` のラベルは付けないでください（分類するのは棚卸しです。`agent-ops/board-design.md` 2.17.1）。
- **`origin:agent` は起票のときに一緒に渡してください**（`agent-ops/parallel-work.md`「自分で立てた
  issue には `origin:agent` を付ける」）。
  **向かう先（`goal:`）も一緒に渡してください**——盤面が配る順と、発掘係を立てるかを
  この印で決めます（`agent-ops/board-design.md` 2.18.1）。この係が立てるものは仕組みを整える
  ためのものなので `goal:upkeep` です。
- **本文には、出どころの回（`agent-ops/analysis/<日付>.md`）を並べてください。** 一次の記録が根拠なので、
  読んだ人がそこへ戻れる形にします。
- issue の型は `agent-ops/parallel-work.md` 3節。

**方針の判断が要るものは、issue の本文にそう書いてください。** リポジトリを読んでも一意に決まらない
——たとえば「この形を止めるには運用そのものを変える必要がある」——なら、決めるのはユーザーです。

## 打ってはいけないこと

- **`agent-ops/policies.md`・`docs/concept/DesignPrinciples.md` などの方針の文書へ書かないこと**
  （出どころ: ユーザーの指示・2026-09-07）。**そこへ畳むのは価値観を畳む係の仕事**
  （`agent-ops/prompts/policy-cycle-prompt.md`・`.claude/skills/policy-review/SKILL.md`）で、役が重なります。
  あなたの出口は **issue と記録の2つだけ**です。
- **一次の記録（`agent-ops/analysis/<日付>.md`）を書き換えないこと。** あなたが書くのは
  `summary/` の下だけです。両方が同じファイルを書くと、どちらの観測かが読めなくなります。
- **スメルを自分で直さないこと。** 直す値打ちがあるなら issue にします。
- **既存の issue とPRの本文・ラベルを触らないこと。**

## 記録

`agent-ops/analysis/summary/<日付>.md`（`YYYY-MM-DD`）へ、**1回につき1ファイル。**

置く節は次のとおり。

- **`## 読んだ範囲`** — どの回の記録を読んだか（日付で）。
- **`## 切った issue`** — 番号と、何を見て切ったか1行ずつ。**1件も切らなかったなら「なし」。**
- **`## 回をまたいでいる形`** — まとめた形ごとに、**どの回に現れたか**と、**打つと決めたか／様子見に
  したか**。様子見にしたものは、次の周のあなたが読んで数え直します。**帯の切れ目を見つけたなら、
  ここへ書いてください**（落ちた範囲と、切った issue の番号）。

**前の周の `summary/` と同じことを書き直さないでください。** 既に打った形は、**新しい回に現れた分
だけ**を足します（「前の周で issue にした形が、その後も2回出た」は書く値打ちがあります——打った手が
効いていない証拠なので）。

**次の周のあなたへ宛てる決めごと（以後ずっと守る作法）を、記録へ書かないでください。** 記録が持つのは
その回の観測だけです——**必ず読まれるのは最新の1件まで**で、しかも上のとおり次の周はそれを書き直さない
ので、記録へ置いた作法はその先の周へ届きません。**作法を持つのはこの本文のほう**で、**毎周あなたへ
渡るのは、`.claude/analysis-trend-prompt.md` の囲みの中身**（この文が入っている範囲）です。
**書き足す値打ちがあるなら、この本文への直しとして issue にしてください**（下の「PR」）。

## PR

- 本文に置く節は `CLAUDE.md`「PR本文に置く節」に従う。**`Closes` は書きません**（この係は issue を
  渡されていません）。`## 見た目` は「不要」と理由の1行で足ります。
- **立てた issue の番号は記録の `## 切った issue` にだけ書き、PR本文へは書き写さないでください。**
  **仕組みそのものへの直しの依頼**（このひな形・盤面の道具・運用の文書）も、やる必要があるなら
  同じように issue にします。
- **push の前にサブエージェントを1本立てて、これから出す差分をレビューさせてください。** 手順は
  `CLAUDE.md`「PRを出す前に、サブエージェントへ一次レビューさせる」——**開いて読んでから通して
  ください。**
- そのうえで `npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` の4つを通す。
- **PRを作ったら報告して終わりです。CIの結果もレビューも見張らないでください。**
  **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** この3つは自動承認が
  できず、呼んだ分がそのままユーザーの手作業になります。直しが要れば、盤面が `send_message` で
  このセッションを起こします。

## 守ること

- **コードは1行も変えないこと。** 成果は、新しい issue と `agent-ops/analysis/summary/` の記録だけです。
- 決まっていない箇所は仮決めして進み、PR本文の `## 仮決め` に書いてください。

応答は日本語で。
````
