# 参照を検めるプロンプト

**節番号の参照の指し先に、その話が本当に書いてあるかを読む**係の本文。投入するのは盤面
（[`board-move.mjs`](../../scripts/daemon/board-move.mjs) の `CYCLES`）で、渡し方は
[`dispatch-chore.sh`](../../scripts/daemon/dispatch-chore.sh)。

**機械で見ているのは指し先が実在するかだけ**（`tests/docs/docReferences.test.ts`）。中身まで広げる案は
採らなかった——**取りこぼしと誤検知が同時に出る**からで、どちらにも実例がある（#2065）。語の一致で
見ると、指し先に同じ語が在るだけで通ってしまう一方、同じことを別の言い方で書いている箇所が全部
赤くなる。**読むのはモデルで、機械が渡すのは範囲だけ**（[`policies.md`](../policies.md)「仕組みの
作り方」——促すだけなら判定はモデルに任せる）。

**どこまで読んだかは [`ref-audit.md`](../ref-audit.md) が持ち、この周に読む範囲は
[`refAudit.mjs`](../../scripts/daemon/refAudit.mjs) が出す。** 範囲の数え方をひな形にも持たせると、係が
読んだ範囲と台帳へ書く到達点がずれる。

題は下の `題:` の行が持つ（[`board-design.md`](../board-design.md) 2.9）。

題: 検め 節番号の参照

````
[デーモン] 節番号の参照を検める周です。**指し先の節に、その参照が支えている話が本当に書いてあるか**を
読んでください。

まず `CLAUDE.md` と `agent-ops/parallel-work.md` を読んでください。

## この周に読む範囲

次のコマンドが出す一覧だけが対象です。

    node scripts/daemon/refAudit.mjs

出るのは2つの並びで、どちらも `参照元<TAB>件数<TAB>なぜ読むか<TAB>どこを見るか` の形です。

- **変わった分** … **全部読んでください。** 前の周から今までに書き足された参照と、指し先の節が
  動いた参照です。ここを読まずに台帳の `検めた時点` を進めると、そのぶんが二度と読まれません。
- **掃く分** … 既に在る参照を、上から順に。**この係が立つ前から在る参照は誰も読んでいない**ので、
  変わった分だけを追っても減りません。

**自分で範囲を広げないでください。** 目についた別のファイルを読み始めると、読んだ範囲が台帳の
到達点と食い違い、次の周が同じところをもう一度読みます。

**「どこを見るか」の欄は手がかりであって、範囲の指定ではありません。** 行や節が挙がっていても、
その参照が何を支えているかは前後を読まないと決まりません。**挙がった参照が、指し先の文書を
そもそも指していないこともあります**——絞りは番号だけを見ているので、別の文書の同じ番号を指す参照が
混ざります。その場合は「不一致なし」として次へ進んでください。

## 何を見るか

**参照がどの文書のどの節へ解決するかの規約は `docs/DocumentStyle.md` 5節。** 裸の番号は自分の文書、
`同` を付けたものは直前に名前を挙げた文書、コード・YAML の裸の番号は WorldCodex 文法の文書です。

**見るのは1つだけ——その参照が支えている主張が、指し先に書いてあるか。** 壊れ方はこう出ています。

- **記述が別の節・別の文書へ移った。** 指し先は実在するが、そこには別の話が書いてある
- **記述がどこにも無い。** 参照元が、書かれていないことを「書いてある」として引いている
- **意図しない文書へ解決している。** 直前に別の文書を名指ししていたせいで、`同` や裸の番号が
  書き手の思っていない文書へ流れている。自分の文書に同じ番号の節が在るときも同じ
- **番号の繰り上げにずれた。** 節が1つ消えて後ろが繰り上がると、参照は**繰り上げ後も実在する
  別の節**を指す。リンクは切れないので、指し先の中身を読むまで見つかりません

**指し先が実在するかは見なくてよい。** そこは自動テストが毎回見ています。

**語が一致しないことは不一致ではありません。** 参照元と指し先が同じことを別の言い方で書いている
箇所は多く、語を要求すると全部が挙がります。**逆に、語が一致していても中身が主張を支えていない
ことがあります**——見るのは意味のほうです。

**どちらが正しいかまでは決めないでください。** 参照を直すのか、指し先へ書き足すのかは、直す側が
決めます。

## 不一致が見つかったら

**この周ぶんをまとめて issue 1本**にします。**1件ずつ立てないでください**——参照の不一致は毎周いくつ
も出るので、1件1本にすると**整備の issue が在庫を満たし続け、完成へ近づける仕事が配られなくなります**
（`agent-ops/board-design.md` 2.18.1）。

道具は `agent-ops/github-access.md`「issue を読む・書く」に従ってください。

- **ラベルは `origin:agent` と `goal:upkeep`。** `kind:` は付けないでください（分類は棚卸しです）。
- 題は `参照の検め: 指し先と中身が食い違っている箇所（<日付>）` の形。
- 本文は `agent-ops/parallel-work.md` 3節の**タスク issue の型**に従う（`## 担当`・`## 完了の条件`）。
  `## 担当` には、参照元のパスと、指し先として読んだ文書・節を1件ずつ並べます。
  `## 完了の条件` は**食い違いが消えていること**で、参照を直すか指し先へ書くかは配られた側が
  決める、と書いてください。
- **1件ずつに「何が書いてあると読めるか」と「指し先に実際に書いてあること」を並べてください。**
  どちらかが無いと、配られた側が最初から読み直すことになります。
- **同じ形が繰り返し出ているなら、箇所ではなく形で切ってください。** 「ある文書の節が動いたのに
  指す側が追いついていない」は1本で、見つけた箇所は `## 担当` へ置きます。

**自分で直さないでください。** この係は読む役で、直す役は配られたセッションです。**範囲の外にある
参照まで直しに行くことになる**ので、手を出すと1周で終わらなくなります。

**不一致が0件ならそう書いて終わりです。** issue は立てません。

## 台帳を書き換える

`agent-ops/ref-audit.md` の2行だけを書き換えます。

- **`到達点`** … 掃く分のうち、**読み終えた最後のファイル**。掃く分を1つも読まなかったなら、
  書き換えないでください。
- **`検めた時点`** … **変わった分を全部読めたときだけ**、道具が出した「現在」の指紋へ。読み切れ
  なかったら**書き換えないでください**——次の周が同じ窓をもう一度出します。書き換えてしまうと、
  読まなかったぶんは窓から落ちて二度と読まれません。

**変わった分が1周で読みきれない量になったら、そのことを issue にしてください**（仕組みの側の直し）。
窓が進まない周が続くと、掃く分がいつまでも始まりません。

## PR

- 本文に置く節は `CLAUDE.md`「PR本文に置く節」に従う。**`Closes` は書きません**（この係は issue を
  渡されていません）。`## 見た目` は「不要」と理由の1行で足ります。
- **立てた issue の番号をPR本文へ書き写さないでください。** issue が在れば盤面が配ります。
- **push の前にサブエージェントを1本立てて、これから出す差分をレビューさせてください。** 手順は
  `CLAUDE.md`「PRを出す前に、サブエージェントへ一次レビューさせる」——**開いて読んでから通して
  ください。**
- そのうえで `npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` の4つを通す。
- **PRを作ったら報告して終わりです。CIの結果もレビューも見張らないでください。**

## 守ること

- **差分は台帳の2行だけ。** 参照元も指し先も書き換えないこと。
- **範囲を広げないこと。** 読むのは道具が出した一覧だけです。
- **`kind:` のラベルを付けないこと。** 分類は棚卸しがやります。
- **`subscribe_pr_activity`・`send_later`・`delete_trigger` を使わないこと。** 自動承認ができず、
  呼んだ分がそのままユーザーの手作業になります。
- 決まっていない箇所は仮決めして進み、PR本文の `## 仮決め` に書いてください。
````
