# 価値観を畳む係のプロンプト

`agent-ops/decisions/` に溜まった判断の履歴を読み、一般則へ畳む候補を並べた issue を1本起票する係の
本文。投入するのは盤面（[`board-move.mjs`](../../scripts/daemon/board-move.mjs) の `CYCLES`）で、
`archive/` に入っていない履歴が1件でもあれば週に一度立つ。渡し方は
[`dispatch-chore.sh`](../../scripts/daemon/dispatch-chore.sh)。

**畳む手順そのものは [`policy-review` skill](../../.claude/skills/policy-review/SKILL.md) が持つ**——束ね方も、
一般則の書式も、行き先も、総量の上限もそちらが唯一の定義。ここに書くのは、**周期の係だけが持つ
事情**——諾否を訊く相手が居ないので、答えを issue のチェックで受けること。

**この係はリポジトリへ1行も書かない。** 反映するのは、ユーザーがチェックを付けて `判断待ち` を
外した後に配られる、別のセッション。**候補を出す仕事と、チェックを読んで書く仕事を1本に混ぜない**
——混ぜると、諾否を待つ間セッションが止まる（[`board-design.md`](../board-design.md) 2.15.1）。

**`判断待ち` を付けた状態で起票する**（出どころ: ユーザーの指示・2026-09-06）。ラベルが付いている
間は誰にも配られないので、チェックが埋まる前に反映されることがない。

題は下の `題:` の行が持つ（`board-design.md` 2.9）。

題: 価値観 畳む候補

---

````
[デーモン] `agent-ops/decisions/` に溜まった判断の履歴を棚卸しし、候補を issue にします。

まず `CLAUDE.md`「価値観の記録」と `.claude/skills/policy-review/SKILL.md` を読んでください。
**束ね方・一般則の書式・行き先・総量の上限は、すべてその skill が持ちます。** ここへ書き写して
いないので、開いて読んでから始めてください。

## GitHub を触る道具

**道具は `agent-ops/github-access.md`「issue を読む・書く」に従ってください。**

この係が読むのは、**前の周にこの係が立てた issue が開いていないか**だけです（下の「先に、前の周の
issue が残っていないか見る」）。**取りこぼすと2本目を立てることになる**ので、**開いている issue を
打ち切らずに全部引いてから**絞ってください——**引く数を渡さないと30件で切れます。** 絞ったものは
**本文まで読みます**（同じ表の「本文を読む」）——**見分けるのは本文の印で、題ではありません。**
立てるときのラベルは下の「起票する issue」。

`origin:agent` は、人が立てた issue と見分けるための印です（`agent-ops/parallel-work.md`「自分で立てた
issue には `origin:agent` を付ける」）。**起票のときに一緒に渡してください**——後から付け直す道は
ありますが、別の手が要る形にすると、付け忘れた issue が「人が立てた」として数えられます。

## 先に、前の周の issue が残っていないか見る

**この係が立てた issue は、本文の先頭に印を1行持っています**（下の「起票する issue」）。**前の周が
残っているかは、この印で判定してください。題の綴りでは判定しません**——題は誰でも同じ語で始め
られるので、綴りだけで見ると**別人の1本で黙る周**が出ますし、止まったことは誰にも届きません。

引くのは2段です。**開いている issue を全部引き**、次のどちらかに当たるものの**本文を読んで**、印が
在るかを見ます。2つとも要るのは、**答え待ちの間は札が残り、札が外れた後は題が残る**からです。

- 題が `価値観の棚卸し: 畳む候補の諾否` で始まる
- `判断待ち` が付いている

読み分けは次のとおりです。**黙って終わる道は「印が1本」のときだけです。**

| 印を持つ open | どうするか |
| --- | --- |
| 1本 | **何もせずに終わる。** まだユーザーが答えていないか、答えを反映するセッションが走っている最中です。そこへ2本目を出すと、同じ履歴に対する候補が2つ並び、**どちらを反映しても残りが嘘になります** |
| 0本 | **そのまま進む。** 題だけが一致する issue が在っても、それはこの係のものではありません。**進んだうえで、立てる issue の本文へ「#<番号> が同じ綴りで開いているが、印が無いので別物と読んだ」と1行書いてください**——黙って進むと、次の周も同じ判断を一からやり直します |
| 2本以上 | **既に二重に立っています。** 候補は出さずに、**新しいほうの issue へコメントを1つ置いて終わってください**——「この周は候補を出していません。#<番号> と #<番号> が開いているので、片方を閉じてください」。**同じことを書いたコメントが既に在れば、置き直さないこと**（この係は間隔を空けて立ち続けるので、直るまで1つずつ増えます） |

## やること

1. **`agent-ops/decisions/*.md` を全部読む**（`archive/` の中は読まなくてよい——処理済みです）。
   **先に全部読んでから**束ね始めてください。1件だけを見て「これは一般則か」は判断できません
   ——通底しているかは、**別の題材で同じ選び方をした判断が在るか**でしか分かりません。
2. skill の手順1〜2で**候補を作る**。候補は3種類あります。
   - **乗せる** — 束が skill の「一般則と、個別の判断の見分け方」を通ったもの。行き先も1つ選ぶ。
   - **外す** — 既に在る一般則のうち、その見分け方を通らないもの・既に他所に在るもの。
   - **移す** — 既に在る一般則のうち、置き場が違うもの。移す先を1つ選ぶ。
3. **候補が1件も無ければ、issue を立てずに報告して終わり。** 同じ題材への判断しか溜まっていない週
   はこれが正解です（別の題材で同じ選び方が出れば通底するので、履歴には残します）。
4. 候補があれば、下の形で issue を1本起票する。**1本だけです**——候補ごとに立てると、ユーザーが
   同じ判断を何度も開くことになります。

## 既に在る一般則にも、同じ見分け方を当てる

**既に在る一般則を頭から読み直し、skill の「一般則と、個別の判断の見分け方」を1項目ずつ当てて
ください。** 通らないものが在れば、それは今も個別の判断・ベストプラクティスのまま置かれている
ので、外す候補・移す候補になります。**新しく乗せる候補と同じ重みで探すこと。**

**`agent-ops/policies.md` には行数の上限があります**（`tests/docs/policies.test.ts` の `MAX_LINES`）。
何行増えて何行空くのかを、issue の本文に数字で書いてください。**ただし上限は、乗せる候補の数を
決める理由にはなりません。** 空きが足りないのは、見分け方を通らない項目が居座っている合図で、
乗せる側を削る合図ではありません。**数を合わせにいかないこと**——外す候補が0件でも、乗せる候補が
0件でも、それが検査の結果ならそれが正解です。

## 起票する issue

**本文の先頭に、次の1行をそのまま置いてください。** HTMLのコメントなので、ユーザーの画面には
出ません。**次の周はこの行で前の周を引きます**——落とすと、次の周が2本目を立てます。

<!-- 周期の係の印: policy-ballot 次の周がこの行で前の周を引く。消さないこと -->

**題は `価値観の棚卸し: 畳む候補の諾否（<日付>）` の形で**——例: `価値観の棚卸し: 畳む候補の諾否
（2026-09-13）`。**上の引き方は、日付より前を本文を読む候補の絞りに使います。** 縮めたり言い換えたり
すると、**`判断待ち` が外れた後のこの1本が、次の周の候補から落ちます**（印を持つのは本文なので、
候補に入らなければ読まれません）。

**付けるラベルは `判断待ち` と、上の `origin:agent` と `goal:upkeep`**——どれも立てるときに渡します。`kind:` は
付けないでください（分類するのは棚卸しの係です。`agent-ops/board-design.md` 2.17.1）。

本文は `agent-ops/parallel-work.md` 3節の**タスク issue の型**に従います（`## 担当`・`## 完了の条件`
は必ず置く）。**この型で書くのは、チェックが埋まった後そのまま配られるから**です——型を外すと、
棚卸しの係が本文を書き換えにかかります。

型に加えて、**候補の一覧をチェックボックスで置いてください。**

```markdown
## 乗せる候補

- [ ] **`agent-ops/policies.md`「名前の付け方」へ**
  - **場面**: …
    **選ぶ方**: …
    **重視**: …
  - 出どころ: `2026-09-05-xxx.md` / `2026-09-06-yyy.md`

## 外す候補

- [ ] **`agent-ops/policies.md`「宣言漏れの扱い」の「場面: …」を消す** — 一般論から同じ答えが出る。

## 移す候補

- [ ] **`agent-ops/policies.md`「仕組みの作り方」の「場面: …」を
      `agent-ops/board-design.md` へ** — 盤面の作りの決めごとで、どのセッションも要るものではない。
```

- **1項目1チェックボックス。** 束ねると、ユーザーは一部だけ通す答えを出せません。
- **乗せる候補は、そのまま貼れる形で書く。** 反映するセッションが文面を考え直さずに済みます。
- **出どころの履歴のファイル名を、候補ごとに全部挙げる。** 反映したあと `archive/` へ移すのは
  この一覧です。**挙げ忘れた履歴は残り続け、次の周でまた同じ候補になります。**
- **何行空くのか・何行増えるのかを書く。** ユーザーはリポジトリを開かずに答えます。

`## 担当` に挙げるのは、**候補の行き先に実際に出てくる文書**と `agent-ops/decisions/**` だけです
（使わない行き先を書かない）。`## 完了の条件` は次の形で。

```markdown
## 完了の条件

- 上の候補のうち、**チェックの付いたものだけ**が反映されている（付いていないものは反映しない）
- 反映した候補の出どころの履歴が `agent-ops/decisions/archive/` へ `git mv` されている
- **チェックの付かなかった候補の出どころの履歴も `archive/` へ移す。** ただし front matter へ
  `declined: <この issue の番号>` の行を足してから移すこと（見送ったことが残らないと、次の周で
  同じ候補がまた挙がります）
- どの候補にも入らなかった履歴は、`agent-ops/decisions/` に残す（束になっていないだけなので）
- `npm run lint` / `npm run typecheck` / `npm test` / `npm run format:check` が通る
```

## 守ること

- **リポジトリを1行も書き換えないこと。** 成果は issue 1本だけです。**PRは作りません。**
  `agent-ops/policies.md` も `agent-ops/decisions/` も、この係は読むだけです。
- **既存の issue とPRを触らないこと。** コメントを付けるのは、上の読み分けで**印を持つ issue が
  2本以上開いていた周**だけです——**二重に立ったことに気づけるのは次の周のあなただけ**で、黙ると
  ユーザーは「どちらを反映しても残りが嘘になる」2本をそのまま読むことになります。
- **一般化はここでやり、諾否はユーザーに任せる。** ただし**通底しているかの見分けは、あなたの
  仕事です**——skill の「一般則と、個別の判断の見分け方」を通らないものは、候補に出さずに落として
  ください。**「迷ったら出す」をしないこと。** 個別の判断を並べた一覧は、ユーザーがチェックを
  付けないことでしか止められず、**その手間ごとユーザーへ渡すことになります。** 迷うのは検査を
  通った後の話で、そこまで来たものはチェックへ委ねてよいです。
- **履歴の原文を引くこと。** 候補の根拠は、要約ではなくユーザーの発言そのものです。
- 決まっていない箇所は仮決めして進み、起票した issue の中に書いてください。

報告には、読んだ履歴の件数・出した候補の数（乗せる／外す／移す）・立てた issue の番号を書いて
ください。**候補が無くて立てなかったなら、そう書いてください。**
````
